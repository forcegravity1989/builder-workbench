# 过程指标目录(playbook 26 条的总账)

> **30 秒导读**:这是什么——《AI-Native SDLC Playbook》13 个 play 的全部 26 条引领/滞后指标,逐条翻成 BW 统计方式的总账:能算的指到脚本,等前置的写明等什么,不建的写明为什么。给谁看——跑运作活①(更新指标)的 agent 挑引领/滞后候选时、以及想知道「这个数怎么来的」的人。现在作数吗——作数(2026-08-25 起,规范 5.1)。**铁律:代码仓是唯一统计源**——每条指标的输入只允许本仓 git 历史、本仓远端(PR / issue / 检查)、仓内文件;本机库不作数据源,仓看不见的事不建指标。

## 怎么用这份目录

- 目录里的指标是**过程指标**:量的是研发过程自身,不是业务成效。北极星永远不放过程指标。
- 想让某条点灯:把它写进 `.bw/config/metrics.toml` 的引领/滞后格(引用下面的脚本、设目标)——荐入规则见 `metrics-refresh` 剧本:**空位才荐、至多两格、人确认才写**。
- 每份脚本头部有口径全文和一行复算命令;改口径就改脚本,脚本即文档。

| 指标 | 引/滞 | 一句话口径 | 脚本(`.bw/scripts/`) |

| 每周提交数 | 引领 | 当前分支提交时刻落在本周的提交数 | `git-commits.py` |

| 评审等待 | 引领 | 本周合入的 PR,开出→合入的中位时长(小时) | `github-review-wait.py` |
| 首过率 | 引领 | 本周合入的 PR 里,开出后零追加提交的占比(%) | `github-first-pass.py` |
| 返工轮数 | 滞后 | 本周合入的 PR,平均「开出后追加的提交数」 | `github-rework-rounds.py` |
| 首审等待 | 引领 | 开出→首条评审事件的中位时长;单人仓常年空,空如实 | `github-first-review-wait.py` |
| 意图成文时长 | 引领 | 分支首提交→PR 开出的中位时长(按开出周) | `github-intent-lead.py` |

## 二、能算但不做走势脚本(2 条)

| 指标 | 为什么不做脚本 | 复算命令 |
|---|---|---|
| 接入→首个合入(≈「新成员首合入时长」) | 一次性标量,每个项目只有一个数,不成走势 | `gh pr list --state merged --json createdAt,mergedAt --limit 1000` 里最早那张的时刻,对照 `.bw/` 骨架首提交 |
| 规范过期件数(≈「政策变更→技能更新」) | 对账现值(`.bw/state/managed.toml` 指纹比对每次现算) | 界面的规范对账区,或按指纹清单手工比对 |

## 三、等前置的(8 条)——指标随实践走,不空挂

| 指标 | 等 Workbench 的哪个能力 |
|---|---|
| 活建立→计划落盘时长;计划落盘→合入时长;计划返工次数 | 「先计划后动手」剧本(开工先落实施计划)——落地时随它交付 3 份脚本 |
| 引用规范的评审发现数;合入前拦获缺陷数 | 评审剧本(发现落进 MR 评论才有数可解析) |
| 重复错误计数(手册应拦而未拦) | 资产盘点的「重复错误进手册」回路 |
| CI 首跑通过率 | 过程指标块 + MR 检查列(要按提交查检查运行,不是列表口径) |
| 越线→活入队时长;发现→修复占比;同类复发;变更失败率 | 事件触发(MVP 后) |

## 四、不建的(5 条)——和为什么

| playbook 指标 | 为什么不建 |
|---|---|
| 越门违规到生产的次数 | **恒为 0,不用统计**:「完成」唯一入边、自动活最远到评审中、信号无法手设——这些门由状态机和密封类型在编译期消灭,不存在「违规发生了再数」的空间 |
| 评测通过率 / 事故→评测时长 / CI 拦截 vs 生产逃逸 | 不建评测集实体(对单人过重);轻量对应 = 技能「用了几次」现算 |
| 驾驭时间 vs 等待时间占比 | 无数据源,BW 不采终端行为 |
| 无人碰分支解决的评审意见占比 | 单人语境分不出「谁解决的」;多人纳管同仓后再议 |
| 流水线故障无人介入分诊占比 | BW 不管 CI 编排(反蔓延) |
