# 过程指标目录

> **30 秒导读**:这是什么——《AI-Native SDLC Playbook》各个 play 的引领/滞后指标,逐条翻成 BW 统计方式的清单:能算的指到脚本,等前置的写明等什么,不建的写明为什么。给谁看——执行更新指标与版本计划 Issue 的 agent 挑引领/滞后候选时、以及想知道「这个数怎么来的」的人。现在作数吗——作数(2026-08-25 起,规范 5.1)。**铁律:代码仓是唯一统计源**——每条指标的输入只允许本仓 git 历史、本仓远端(PR / issue / 检查)、仓内文件;本机库不作数据源,仓看不见的事不建指标。

## 怎么用这份目录

- 目录里的指标是**过程指标**:量的是研发过程自身,不是业务成效。北极星永远不放过程指标。
- 想让某条指标参与健康计算:把它写进 `.bw/metrics.toml` 的引领/滞后格(引用下面的脚本、设目标)。写不写人定;格式见 `references/metrics.md`。
- 每份脚本头部有口径全文和一行复算命令;改口径就改脚本,脚本即文档。

| 指标 | 引/滞 | 一句话口径 | 脚本(`.bw/scripts/`) |

## 二、单值指标与尚未实现的统计

| 指标 | 为什么不做脚本 | 复算命令 |
|---|---|---|
| 接入→首个合入(≈「新成员首合入时长」) | 一次性标量,每个项目只有一个数,不成走势 | `gh pr list --state merged --json createdAt,mergedAt --limit 1000` 里最早那张的时刻,对照 `.bw/` 骨架首提交 |
| 规范过期件数(≈「政策变更→技能更新」) | 当前没有接入这项统计；`.bw/managed.toml` 是待清理的旧文件，不能作为现行指标来源 | 尚无现行复算入口；不能将旧指纹工具描述为已交付的界面能力 |

## 三、等待前置能力的指标——指标随实践走,不空挂

| 指标 | 等 Workbench 的哪个能力 |
|---|---|
| Issue 创建→计划保存时长;计划保存→合入时长;计划返工次数 | 「先计划后动手」剧本(开工先落实施计划)——落地时随它交付 3 份脚本 |
| 引用规范的评审发现数;合入前拦获缺陷数 | 评审剧本(发现落进 MR 评论才有数可解析) |
| 重复错误计数(手册应拦而未拦) | 资产盘点的「重复错误进手册」回路 |
| CI 首跑通过率 | 过程指标块 + MR 检查列(要按提交查检查运行,不是列表口径) |
| 越线→创建 Issue 的时长;发现→修复占比;同类复发;变更失败率 | 事件触发(MVP 后) |

## 四、当前不采集的指标与边界

| playbook 指标 | 为什么不建 |
|---|---|
| 越门违规到生产的次数 | 当前未采集这项统计，不能报告为 0。完成必须由用户显式发起，状态机允许从未排期、待办、进行中、待评审、阻塞转为完成；健康信号由数据推导。这些约束不等于生产违规事件的统计结果 |
| 评测通过率 / 事故→评测时长 / CI 拦截 vs 生产逃逸 | 当前未实现评测集实体及这些统计。Skills 数字只统计当前项目引用 workflow 的 Issue 数，不能代表评测结果或调用次数；计数文案与未统计时显示 0 的缺口由 [Issue #169](https://github.com/forcegravity1989/builder-workbench/issues/169) 跟踪 |
| 驾驭时间 vs 等待时间占比 | 无数据源,BW 不采终端行为 |
| 无人碰分支解决的评审意见占比 | 单人语境分不出「谁解决的」;多人纳管同仓后再议 |
| 流水线故障无人介入分诊占比 | BW 不管 CI 编排(反蔓延) |
