# Issue 格式与计划补充

> **维护约定**：供提单用户、提单助手和计划助手读取。只规定 Issue 的最小格式、纳入计划时的补充和材料关联；具体工作怎么处理由对应工作流决定。计划、验收和其他入口引用同一份格式；格式变化时同步提单模板与随包指南。

## 提单时

- 先查是否已有相同 Issue，能复用就更新原单。
- 标题用一句话说清问题或需求。没有版本和目标时直接写问题描述，不要求预先加版本、周次或目标编号。
- 正文只要求一段 **问题描述**：谁在什么场景遇到什么问题，或希望得到什么结果。截图、链接、版本、环境、复现步骤和方案可以一并提供，也可以后补；不知道的内容留空或写待确认，不编造。
- Issue 类型使用 provider 的 Bug、Feature 或讨论/预研入口。类型表示提单性质，不表示执行状态。

## 分类标签

- `Bug` 表示已有行为在实际场景中没有满足预期；`Feature` 表示新增能力或行为。两者是 provider 的原生提单分类，不能当作 open/closed、阶段或完成信号。
- 计划拆解中的每条新 Issue 都应按人确认的提单性质选择一个分类；讨论或预研继续使用 provider 的原生入口。性质不清先向人核对，不从标题、状态、关闭原因或目标名称推断。
- 读回任务时保留 provider 返回的分类。标签中有 `Bug` 或 `缺陷` 时归 Bug；有其他非空标签或没有标签时默认归 Feature。不批量补标，也不从标题、状态或关闭原因猜测分类。

## 纳入计划时

计划助手在用户确认版本和目标后，沿用原问题描述补齐同一条 Issue：

1. 标题整理为 `【<版本>|<目标>】问题描述`，例如 `【v0.5|G1】支持从 GitHub Release 更新 Workbench`。没有已确认的版本或目标就不加前缀，不猜版本、周次或编号。
2. 正文补充 **处理范围** 和 **验收条件**。Bug 需要时再补复现步骤、预期与实际；截图和链接始终可选。原问题描述、已有事实和用户决定保留在同一条 Issue，不另开格式不同的承接单。
3. 精确增加 `bw:plan:<版本>` 标签供人检索，保留已有标签；跨版本纳入时追加对应标签。标签不是执行状态，也不替代计划材料中的任务引用。
4. 将真实 provider、repository、number 和目标 `goalId` 写入 `.bw/planning/<版本>/data.json` 的 `tasks`。计划屏按这条引用读取任务；版本／目标标题前缀与 `bw:plan:` 标签用于阅读与检索，不能替代 tasks 的版本归属。现有计划任务继续使用原任务标题和标签，不批量改名；新建或补充时使用本格式。

### 特性主单与拆分任务

人确认需要整体设计、评审并可能跨版本延续的特性时，复用一条主 Issue 并增加 `特性` 标签。它区别于 provider 的 Bug／Feature 提单分类，不代表阶段或完成。普通任务无需为了总览补标。

拆分执行 Issue 时，在原标题中保留 `【特性#334】` 这样的主单引用；按同一 provider、仓库解析，不能用目标编号或同名标题充当跨版身份。主单可以关联设计与开发两个 PR/MR，不强制拆成两个 Issue。跨版时沿用同一主单；每版本承担哪些任务仍写各版计划的 tasks，不自动将主单所有任务纳入本版。

计划助手引导人核对主单、当前版本目标及拆分任务，按授权维护标签与引用并读回；不批量改写历史。成果可在主单补关联 PR/MR 链接，合入后也能补，保留原人工结论。已明确设计或开发用途时，使用独立行 `设计 PR：完整链接`／`开发 PR：完整链接`（CodeHub 可写 MR）；不明确用途时只记录关联，不猜阶段。

## 处理结果

Issue 使用 provider 的原生 open / closed。关闭原因按 provider 能力准确记录：已完成、决定不做或重复都表示这条 Issue 已经过处理决定；关闭不等于版本目标或验收自动完成。保留现有项目的闭环统计口径。

改写时保留原问题和仍有效的资料，补充内容直接接在同一条 Issue；重复项指向承接单。关闭、重开、改标题、改正文和改标签按用户或项目工作流授权执行，写前读最新对象，写后独立读回。
