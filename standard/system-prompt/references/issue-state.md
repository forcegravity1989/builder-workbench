# Issue 规范

> **维护约定**：供日常提单、计划拆解和 Issue 维护时读取。本文统一规定标题、正文最低要求、提单性质、特性主单关联与处理结果。项目具体归属名称由项目 AGENTS.md 或其引用资料定义；纳入计划的额外动作由计划工作流规定。规则变化时核对相关入口、提单模板与随包指南。

## 提单与正文

- 先查是否已有相同 Issue，能复用就更新原单。
- 正文只要求一段 **问题描述**：谁在什么场景遇到什么问题，或希望得到什么结果。截图、链接、版本、环境、复现步骤和方案可以一并提供，也可以后补；不知道的内容留空或写待确认，不编造。
- 更新原单时保留原问题、已有事实、有效资料和人工决定。

## 标题与归属

- 标题用一句话说清问题或需求。提单或整理标题前，先读取项目 AGENTS.md 及其引用的归属约定；项目尚未定义分类时，不自行创造一套分类。
- 归属已经明确时，在问题描述前加 `【归属名称】`。沿用项目约定的名称，不自行增加同义分类或新立特性。一个 Issue 标记一个主归属，按它主要解决的用户问题判断；涉及的实现模块或技术来源可以另作说明。
- 版本和目标已经确认时，使用 `【<版本>|<目标>】`，放在归属名称之前。没有已确认的版本或目标时省略这一段，不影响标记特性归属；不猜版本、周次或编号。
- 归属尚不明确时，按项目约定标待定或请人判断；未知归属不妨碍先记录清楚问题。

示例：

```text
【任务管理】修复任务列表筛选后无法刷新
【v0.9|G4】【任务管理】统一特性单量统计口径
【v0.9|G2】【版本总览】【特性#334】补充跨版历程展示
```

示例中的归属名称由各项目自行定义。标题中的版本、目标和归属名称用于阅读与检索，不能替代特性主单引用或计划材料中的任务关联。

纳入版本计划时，还须执行 `ORCA skills get week-planning` 读取计划指南正文；已经读取本次指南时直接沿用。处理范围、验收条件、计划标签和 tasks 的补充按该指南执行，不只凭本篇的标题格式判断已经纳入计划。

## 特性主单与拆分任务

人确认需要整体设计、评审并可能跨版本延续的特性时，复用一条主 Issue 并增加 `特性` 标签。它区别于 provider 的 Bug／Feature 提单分类，不代表阶段或完成。普通任务无需为了总览补标。

拆分执行 Issue 时，使用并保留 `【特性#334】` 这样的主单引用，放在归属名称之后、问题描述之前；按同一 provider、仓库解析，不能用特性名称、目标编号或同名标题充当跨版身份。跨版时沿用同一主单。普通任务不为显示或统计强制建立主单、拆分 Issue。

主单可以关联设计与开发两个 PR/MR，不强制拆成两个 Issue。成果可在主单补关联 PR/MR 链接，合入后也能补，保留原人工结论。已明确设计或开发用途时，使用独立行 `设计 PR：完整链接`／`开发 PR：完整链接`（CodeHub 可写 MR）；不明确用途时只记录关联，不猜阶段。

## 提单性质与处理结果

- `Bug` 表示已有行为在实际场景中没有满足预期；`Feature` 表示新增能力或行为。提单按人确认的性质选择 provider 原生分类，讨论或预研使用相应入口。性质不清先向人核对，不从标题、状态、关闭原因或目标名称推断。
- Bug／Feature、标题归属、`特性` 主单标签各有用途，都不表示执行阶段或完成。
- 读回任务时保留 provider 返回的分类。标签中有 `Bug` 或 `缺陷` 时归 Bug；有其他非空标签或没有标签时默认归 Feature。不因此批量补标，也不从标题或关闭原因猜测分类。

Issue 使用 provider 的原生 open / closed。关闭原因按 provider 能力准确记录：已完成、决定不做或重复都表示这条 Issue 已经过处理决定；关闭不等于版本目标或验收自动完成。统计口径遵循项目约定。

## 修改与授权

- 关闭、重开、改标题、改正文和改标签按用户或项目工作流授权执行，写前读最新对象，写后独立读回。重复项指向承接单。
- 整理标题时保留有效的版本／目标、特性归属、主单引用及项目要求的实现提示；规范更新不自动授权批量修改存量 Issue。
