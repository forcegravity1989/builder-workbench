# 更新指标与版本计划 Issue 评论 — 界面认的格式

> 周一屏流程已改为每版 JSON 保存目标、总结和评审，本文件只用于旧流程的评论协议及首次历史导入。BW 计划/总览目标已经改读同份 JSON；不要为周一屏新版本再复制一份目标评论。

旧流程的版本目标与每周进展正本在**更新指标与版本计划 Issue 的评论**,不在正文、不在仓文件。只追加,不改旧评。
多条从新到旧扫。版本目标以最新一条为准;每周进展该版本上有几条列几条(新的在前)。纳入和读数人点开这个 Issue 看。

旧流程的周初评论使用这三个二级标题(后面可以跟括号或空格说明):

```
## 版本目标
人说的话。一句或一段。不能空。

## 本周纳入
- #12
- #15（自 v0.2 遗留）
- 新拆:标题

## 本周指标读数
快照。没采到的不写行、不写 0。
```

历史评论修复时才跑 `week-planning` 技能目录里的 `check-week-comment.py`(和注入的 `week-planning/SKILL.md` 同级,不在本 reference 目录,也不在工作区根)。过了再贴。缺任一标题、或「版本目标」「本周纳入」空着会失败。
不要写「周目标」「本周目标」(旧评界面还能读,新写不认)。

`## 本周纳入` 先写已经挂了这个版本的 `#iid`,再写新拆。从别的版本遗留后又纳入本版的,可写 `#iid（自 <旧版本> 遗留）` 给人阅读；评论不是版本归属正本，新拆的不写遗留。

## 标签

确认版本后,先给**这个更新指标与版本计划 Issue 自身**改标题为「更新指标 + 制定版本计划 <版本名>」,并增加 `bw:plan:<版本名>`(界面靠这个判断本周做过)。纳入的业务 Issue 也增加本版 plan，保留已有旧版 plan；一个 Issue 可以同时属于多个版本。完整标签纪律听 `issue-state.md`。裸 `codehub-cli issue update --labels …` 是整张替换——先读回全部标签、加入本版 plan 后完整写回；GitHub 精确 `--add-label`。写后读回，确认没有盖掉既有 `bw:plan` / `bw:status` / `bw:released` / `bw:category`。纳入的 Issue 还没有 `bw:category:*` 的再补 `{prototype|build|optimize|growth|ops}`。
版本名推荐 `vX.X`(如 `v0.3` / `v1.0`),人要用别的也行。不要打 `bw:week`。会话里改标签不会走 Workbench 投影,要自己打。

codehub 再挂同名里程碑(没有就建,起止默认本周周一到周五)。挂不上就说,不回滚标签,不阻塞评论。GitHub 不投影。计划屏「创建版本」只建系统入口和标签，新版目标在 JSON,里程碑同样只补充。

## 版本执行进展（周五总结）

新流程的进展只写该版本 `.bw/planning/<version>/data.json` 的可选 `progress_updates` 数组，每项 `{id, recorded_at, text, sources}`；id 用本次资产盘点 Issue 的浏览器链接，同一任务重跑更新同一项。text 用人能读懂的实际结果，sources 保留证据链接，不按提交数推算指标。总览读取该版本更新；后续周一屏的 summary.progress 汇总 previous_version，作为该版更晚的结果总结。不要把当前执行进展写到 summary.progress（那属于前序版本），不再另发目标或进展评论。

从项目已登记的 bw/week-plan 工作树读取同一 JSON，用已安装 week-planning 的 planning.py read/update 按 etag 更新，命令和字段见同 Skill 的 references/data-and-runtime.md。保留其他内容与用户未提交修改。没有版本数据或无法确认规划工作树就说明缺口，在资产盘点报告列出待补进展，不初始化旧版本来编造计划、不跨树提交人的草稿。更新只是事实采集，不代表用户确认计划；归档由计划会话与 Leader 审核。资产盘点报告附文件落点和是否已写回。
