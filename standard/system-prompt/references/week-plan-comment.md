# 运作活①评论 — 界面认的格式

版本目标与每周进展正本在**运作活①的 issue 评论**,不在正文、不在仓文件。只追加,不改旧评。
多条从新到旧扫。版本目标以最新一条为准;每周进展该版本上有几条列几条(新的在前)。纳入和读数人点开这张活看。

周初这场新写必须用这三个二级标题(后面可以跟括号或空格说明):

```
## 版本目标
人说的话。一句或一段。不能空。

## 本周纳入
- #12
- #15（自 v0.2 遗留）
- 新拆:标题

## 本周指标读数
快照。没采到的不写行、不写 0。
```

挂评前跑 `week-planning` 技能目录里的 `check-week-comment.py`(和注入的 `week-planning/SKILL.md` 同级,不在本 reference 目录,也不在工作区根)。过了再贴。缺任一标题、或「版本目标」「本周纳入」空着会失败。
不要写「周目标」「本周目标」(旧评界面还能读,新写不认)。

`## 本周纳入` 先写已经挂了这个版本的 `#iid`,再写新拆。从别的版本遗留后又纳入本版的,可写 `#iid（自 <旧版本> 遗留）` 给人阅读；评论不是版本归属正本，新拆的不写遗留。

## 标签

确认版本后,先给**这张运作活①自己**改标题为「更新指标 + 制定版本计划 <版本名>」,并增加 `bw:plan:<版本名>`(界面靠这个判断本周做过)。纳入的业务活也增加本版 plan，保留已有旧版 plan；一张活可以同时属于多个版本。完整标签纪律听 `issue-state.md`。裸 `codehub-cli issue update --labels …` 是整张替换——先读回全部标签、加入本版 plan 后完整写回；GitHub 精确 `--add-label`。写后读回，确认没有盖掉既有 `bw:plan` / `bw:status` / `bw:released` / `bw:category`。纳入的活还没有 `bw:category:*` 的再补 `{prototype|build|optimize|growth|ops}`。
版本名推荐 `vX.X`(如 `v0.3` / `v1.0`),人要用别的也行。不要打 `bw:week`。会话里改标签不会走 Workbench 投影,要自己打。

codehub 再挂同名里程碑(没有就建,起止默认本周周一到周五)。挂不上就说,不回滚标签,不阻塞评论。GitHub 不投影。计划屏「创建版本」走同一套评论和标签,里程碑同样只补充。

## 每周进展(周五收口)

周五发版或运作活②盘点才**追加**一条评论,收口当周。不要改周初那条三标题评论。

```
## 每周进展 2026-W36
这一周这个版本实际走到哪。没发生就写没发生,不编。
```

标题认 `## 每周进展`(后面可以跟空格 + ISO 周)。挂在**本周在研版本那张运作活①**上,这样总览按版本能读到。没有在研版本 / 找不到①,写在这张②上并说一句,总览那一格会空着。
周初三标题评论**不要**带这一段;`check-week-comment.py` 也不查它。
