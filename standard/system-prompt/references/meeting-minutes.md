# 会议纪要规范

> 给计划/验收会话整理或改写纪要前读。本文定义共识与遗留两类条目的内容标准与提炼方法；读写机制（批注、转写、人工确认与冻结）在对应 Skill，字段契约在[版本材料](version-records.md)。纪要口径变化时更新。

## 纪要是什么

纪要是会议的提炼结论，不是会议记录，更不是板面复读。目标达成情况、Issue 状态、指标读数板面已逐条呈现，一律不进纪要；人看纪要只为看到会上产生的新决定与新安排。无实质结论时如实写「本次无新共识」，不凑数。

## 共识（consensus）

值得留存的结论性决定：方向确定、口径认可、方案通过、明确否决或调整。每条做到：

- **是决定不是过程**：写讨论出的结论，不写谁说了什么、不写讨论经过。
- **可执行或可判定**：读这一句的人事后知道定了什么、按什么口径。
- **一事一条**：不同议题的结论不混在一条里；按会议议题顺序组织。
- 带必要的口径与范围，涉及数值写清口径；否决与调整也是共识，写结论与理由。

| 不写 | 写 |
|---|---|
| 大家讨论了部署问题，一致认为要持续推进 | 演示环境按项目 X 入口部署，本版验收以 web 服务形态为准 |
| G1 目标基本达成，但还有一些问题需要关注 | G1 按新仪表盘旅程通过；导出耗时口径调整为服务端 P95，下版复核 |
| （逐条复述目标达成情况或 Issue 状态） | （不写——板面已呈现） |

## 遗留（followups）

会议中待落实或需要后续跟踪的行动项。每条做到：

- **写清要做什么**：是动作不是现象或感受。
- **去向明确**：归档前写明已落实到哪条计划或结论，或关联真实跟进 Issue。没有 Issue 时按会话已有授权查重、建单；授权不足再问，不编编号、不自行关闭。
- **负责人与时限**：会上点名的才写，没点名的不编。
- 会上直接形成的决定写共识；已有遗留在归档前落实后，可在原条目写清落实结果，同一件事不重复记录。
- 关联 Issue 表示有人继续跟踪，不代表已完成；无需等 Issue 关闭才归档。由助手核对去向、人在归档 PR 确认，不维护另一套逐项完成状态。

| 不写 | 写 |
|---|---|
| 关注性能问题 | 首屏加载超 3s 的场景优化，建 Issue 跟踪（#123），下版验收会复核 |
| 这个问题后面再看 | 演示环境的权限检查由 #123 跟进，本次归档保留该引用 |
| 已闭环 | 已落实：目标 G2 的验收标准已补充断链恢复路径 |

## 提炼方法

按会议议题顺序整理：同一议题的多条批注与转写发言归并成一个结论；逐议题提取决定与行动项，丢弃寒暄、重复与无结论的发散讨论。条目用自然中文写清结果或跟进去向，不嵌套结构。已确认验收纪要的遗留供下版计划回顾，已落实项不自动转任务，跟进 Issue 不自动纳入下版，由本版讨论决定。
