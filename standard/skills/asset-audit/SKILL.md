# 资产盘点(asset-audit)

一周的收尾。周五早上没人在场的时候,把这个仓里所有资产过一遍:文档齐不齐、新东西登记
了没有、规范件落后没有、指标数据还新不新鲜、有没有大到该拆的文件、旧铺底残留清了没有。

**这次会话很可能没有人在场。** 按「能做的先做、拿不准的写进报告等人看」推进,不要因为
没人回应就停下来等。

## 第一步 · 判断模式

读这张活自己的说明(issue body),找一行 `mode: ...`。

| `mode` | 什么时候 | 干什么 |
|---|---|---|
| `weekly`(默认,没写就是它) | 定时,默认每周五 09:00 | 只盘这一周的变化,走下面第二至五步 |
| `first` | 接入老仓时一次,或人手动重跑一次 | 给已有 issue 挂周标签,走本篇末尾的「首次模式」段 |

判错模式会造成很难收拾的后果(把首次挂周当周盘点跑,报告对不上;反过来则会重扫一遍本
周已经盘过的活)——**读不到 `mode` 就按 `weekly` 走,并在报告里写明"说明里没写模式,
按每周增量处理"**,不要猜。

## 第二步(`mode=weekly`) · 盘点仓内全部资产

五类,一类一段,每段写清楚「查了什么、发现了什么、要不要人管」:

1. **文档**——本周 ops① issue 在不在、codehub Release 有没有落下版本;这周新增
   的文档有没有登记进知识库资产页。
2. **产物与技能 / workflow**——新增的技能包、新挂的 workflow 有没有登记。
3. **规范对账**——该有的件(`.bw/project.toml`、`.bw/issue-policy.toml`)在不在。
   缺的只记报告,不在这次补铺(补铺是接入那一次的事)。
4. **指标数据新鲜度**——`.bw/metrics.toml` 里哪些指标超过保鲜期没有真实读数(读数在
   `.bw/metrics/readings.jsonl` 与本周 ops① issue 评论里的读数快照段)。
5. **代码图大文件榜**——`codegraph files -j` 找超过行数上限的文件。
6. **旧铺底残留**——下面白名单里还在的,这次在这张活自己的工作目录里删掉或改瘦,随盘点
   MR 走。不是建议,是修复。拿不准的(不像 Workbench 铺的、人或项目自己的文件)只写报告。

   **整份可删**(新规范不再铺、也不再读):
   - `.bw/standard.toml`(版本账)
   - `.bw/managed.toml`(指纹账)
   - `.bw/PROJECT.md`(和 `.bw/project.toml` 重复的名片副本)
   - `.bw/connectors.toml`
   - `docs/Workbench/`(整棵)
   - `.bw/plan/`
   - `docs/plan/`
   - 确认没人再跑的 V3 采集脚本

   **`.bw/issue-policy.toml` 只瘦、不换正本**:若还有 `[[tool]]` / `[review]` / `[kanban]`
   段,删掉这三段;mapping 五行和 `[cadence] ops2_schedule` 原样留着,人手改过的工具/
   workflow/周五几点一个字不覆盖。文件头可改成现行三行注释。不要整份换成模板默认值。

   旧格式 `.bw/metrics.toml`(schema 1)不要在盘点里重写——那是运作活①的事,这里只
   记一句「指标还是旧格式,下周或现在开运作活①重定」。

**不做「零调用者就当死码删」**:`codegraph` 对 `dyn Trait` 这类动态分发看不见,零调用者
经常是误判。疑似没人用的东西只写进报告,不动手删。白名单之外的文件也一样。

## 第三步(`mode=weekly`) · 微重构只写建议,不动手

格式、命名、疑似死码、该拆的大文件——这类「可做可不做」的改动**不在这次会话里直接改
代码**。每条整理成一张建议活草稿:

- 标题、说明、类别「优化」
- 为什么值得做、不做的话会怎样

草稿连同盘点报告一起写进这次 MR 的说明。人周一评审时勾选要建的,勾中的那些才真的建成
正式活。

需要动业务逻辑或公开接口签名的,一律只写建议,连草稿都不生成——那种改动要人自己拍板
才动得。

## 第四步(`mode=weekly`) · 写盘点报告

挂进本周 ops② issue 的评论。

**没有可重构的东西是正常结果**,如实写「无」。不要为了让报告看起来有产出,硬凑几条改
名建议。旧件删了几份,在报告里点名列出。

## 第五步 · 提交 + MR

正常提交,`gh pr create` 开 PR,把地址打屏(多半没人当场看,仍然要打)。`gh pr merge`
禁止——合入是人的动作。

## DoD(`mode=weekly`)

- 报告确实挂进了本周 ops② issue 的评论。
- 建议活草稿都在 MR 说明里,一条不落。
- **这次会话自己没有直接改动业务代码**:`git diff --stat` 应当只见格式/命名类小改动、
  白名单里的旧铺底残留删除或 issue-policy 瘦身,或者完全没有代码改动。

## 首次模式(`mode=first`) · 给老仓的历史活对上版本

一个项目通常只跑一次:这个仓接入之前就已经有 issue。Workbench 没有单独的「回填」命令,
也不按 git 周去建假文件。历史要出现在计划屏某个版本,就是给那些 issue 打已有的
`bw:plan:v0.x`。对不上的就留未分配,不要打 `bw:week:*`。

你要做的:

1. 列出远端已有 issue(开着的和关过的)。
2. 能对上已有 `v0.x` 的,打 `bw:plan:v0.x`(该打类别的补类别)。对不上的不要硬编号,
   也不要打周标签。不要改 `created_at`,也不要为凑版本去时间倒流。
3. 某个版本需要对版本目标:补一张运作活①,标题 `更新指标 + 制定版本计划`,评论写
   `## 版本目标` / `## 本周纳入` / `## 本周指标读数`,正文写明这是补记,不假装当时就写过。
4. 证据里没有的东西不写。当时没目标,就不要硬编一句。

**不做**:不写 `.bw/plan/`;不按提交日期倒推版本号;不写 `bw:week:*`;不把补记的活算进健康灯(健康灯只看本周)。

失败与边界:读不到 issue 列表 → 如实停下,报告写清楚缺什么。

## 常见坑

- 把「疑似未使用」直接删掉,而不是先写成建议活。
- 报告写空话:「整体质量良好,建议继续保持」——这一行等于没查。
- 微重构悄悄做了,却不在 MR 说明里说清楚它是「这次自己动手改的」还是「一条建议」。
- 没人应答就卡住等待。这次会话大概率无人在场,等不来的。
- `mode=first` 时为凑版本目标编一句当时没写过的话,或假装创建时间在过去。
- 瘦 issue-policy 时把 mapping / cadence 换成模板默认,盖掉人手改过的开工工具。
