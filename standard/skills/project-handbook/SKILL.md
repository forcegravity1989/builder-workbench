# project-handbook：给项目写开发手册

## 1. 核心目标

提议给这个项目写仓根 `AGENTS.md`(项目自己的手册,不是 Workbench 资产)。人要才写、开 MR;人不要就零改动。不把 Workbench 纪律写进用户仓。

## 2. When to Use / When NOT to Use

- 用:人明确要写仓根 `AGENTS.md`,并且点了你。
- 不用:接入当下、每周盘点、资产盘点自动会话(产品不自动派这份)、没问就写。沉默当不要。

## 3. 前置依赖检查

读一遍再问:仓根 `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`、`README.md`、构建文件、CI 配置(空目录不算)、顶层目录。已有手册则通读,**原文不删**。

## 4. 标准执行流程

**第 1 步 · 摊现状,问一句**  
走到请示。说清要动哪个文件。没有手册就问要不要新增 `AGENTS.md` + 一行 `CLAUDE.md`。已有就问要不要补哪几节。人说不要或不确定 → 写进盘点回执「提过、人不要」,下次不再问,结束。

**第 2 步 · 人点头才写**  
走到起草。

| 节 | 怎么写 |
|---|---|
| 建 / 跑 / 测 | 命令原样可跑。每条真跑过;跑不通的不写 |
| 门禁 | 以 CI 为准;和 README 冲突在 MR 里指出 |
| 目录 | 顶层各一句;看不懂写「待补」,不编 |
| 项目规矩 | 只写仓里看见的 |

`CLAUDE.md`:没有或空壳 → `@AGENTS.md`;有实质内容 → 文首插入 `@AGENTS.md`,原文后移不删。

**第 3 步 · 开 MR**  
走到交付。MR 说明每一节一行来源。凭推测的单独列请人核。提交 + 开 MR。

## 5. 参考资源

- 仓内 README / CI / 构建文件:命令和门禁的证据。
- 不要读、不要抄本仓 `AGENTS.md` 当用户手册模板。

## 6. error_handling

| 现象 | 处理 |
|---|---|
| 人不要 / 不确定 / 沉默 | 零改动 + 回执一句 |
| 命令跑不通 | 不写进手册 |
| 看不懂的目录 | 写「待补」 |

## 7. 示例

仓根没有 `AGENTS.md`,CI 里有 `cargo test`。问人要不要写。人要。手册里的测试命令取自 CI 并真跑过。MR 说明写「测试命令来自 `.github/workflows/ci.yml`」。

## 8. 纪律表

| | |
|---|---|
| 必须 | 先问;原文不删;命令真跑 |
| 禁止 | 没问就写;把「完成由人点」写进用户仓 |
| 你不做的事 | 判断手册写得对不对(那是人评审) |
