# 产品 Skill 写作约定

> 给维护 standard/skills 的人和模型读。只管技能结构、分层与可执行性，不规定产品行为；产品行为由特性规格决定。结构或加载约定变化时更新，旧文件小修只处理相关主题，整体重写遵循本篇。

## 最小结构

SKILL.md 必须有 YAML name、description；name 与目录名一致，使用小写连字符。description 说明实际触发场景与必要边界，不塞 SOP 或依赖不存在的 workflow 标签。

正文按实际任务组织：目的与边界、执行流程、必要失败处理、按需参考。无需固定八章、重复的 When NOT to Use、示例和纪律表；短任务可以更短。主文只保留会改变模型决策的信息，不堆项目历史、目录全表或重复规则。

交互式业务流程先让用户看见完整 SOP 与当前所在步骤，再围绕缺失信息交流。已有输入直接采用，不每步重新索要许可；关键目标和人的判断不由模型代定。用户明确的授权与项目约定优先，Skill 不凭自身出现扩展到外部写入、完成或发布。

## 渐进披露

| 内容 | 放哪里 |
|---|---|
| 这次会话怎样带人走完、产物是什么 | SKILL.md |
| 特定任务的思考方法、目标例子、证据判断 | 本 Skill 的 references，主文说明何时读取 |
| 多 Skill 共用的字段/标签/指标/材料协议 | system-prompt/references，保留单一正本 |
| 输出用的纪要等格式 | assets；格式变化同步生成方 |
| 确定性且已实现的机械动作 | scripts 或宿主工具，说明真实输入输出 |
| 当前项目决定、运行记录、产品设计 | 项目正本/特性文件/运行产物，不抄进 Skill |

允许必要的 references，不把冗长主文原封不动搬过去。删除失效规则前查调用方；仍在使用的脚本与模板随消费方一起退役，不靠改一份 MD 冒充运行时已切换。

## 写作与验证

- 按业务主题替换旧内容，不加“本轮补充”流水。已有 Skill 优先改原件，不并列新旧 SOP。
- 协议/规范只引用一次正本，流程不锁定旧 UI 页数或硬编码步骤编号；界面只呈现对象、动作和结果。
- 入口下发实际存在的工具、项目、版本和工作区，Skill 不编命令或路径。设计稿要标明未接入，不能作为已发布能力。
- 检查 frontmatter、引用、真实加载方和样例；改变交互方法时，用代表任务观察是否抓到用户信息并交付。静态通过不代表模型行为改善。
- 来源有冲突先核对用户决定、现行规格与真实能力；不让存量资产自动否决已经认可的新流程。

写作分层见 [standard](../README.md)，注入实况见 [模块说明](../../docs/06-module/系统提示词与渐进加载.md)。其他未涉及 Skill 不因本规范重写而批量改动。
