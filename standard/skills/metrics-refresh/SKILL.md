# 配置与核对指标

帮助用户形成能支持判断、能按日/周采集真实历史的指标。正常刷新由服务执行；配置入口每次在固定维护树中新建 Orca 原生会话，不占用计划或验收会话。先核对宿主提供的项目、工作区和工具，不编造路径。

## 开工与恢复

完整读取[公共执行规范](../../references/execution.md)、项目 AGENTS.md 和[指标协议](../../references/metrics.md)。用原生身份核对项目与固定维护树，直接读取该树的 `.bw/metrics.toml`、其中引用的采集脚本及 Git 改动。区分文件不存在、解析失败与读取失败；失败不当作未配置，不凭空准备新定义。正式目录的来源通过已配置远端和主分支提交核对，不把维护草稿当成已合入配置。

## 执行流程

1. **让全程可见。** “明确用途 → 核对历史来源与归属 → 准备脚本 → 实跑验证 → 交付接入”。开工前核对固定维护树与基线分支关系：落后且无本地提交可快进更新；有未合入草稿改动先与人确认顺序，不自行合并、不 reset。读取固定维护树已有定义及未完成改动，复用有效资产，已有输入不重问；本次是新会话，不按标题寻找或续接旧任务。
2. **明确与核对。** 读取项目约定和现有定义，仅追问缺失的用途、口径、特性归属、场景价值与引领对象。按指标协议核对历史来源及存量定义；没有可信来源就报告缺口，与人确定取舍，不先写承诺。
3. **准备与验证。** 首次准备定义时完整读取[指标模板](../../templates/metrics.toml.tmpl)，按已读协议补定义和脚本。用实际窗口执行并独立核对输出、失败与覆盖范围；缺凭据或项目入口如实报告，不能把脚本存在说成可采集。被替代资产同一交付内清理。
4. **交付与采用。** 定义和脚本按项目分支/PR 流程交付。维护工作区里会话下方的记分牌直接显示这份配置文件，尚未提交时标明草稿，保存后隔几秒跟上；读数仍按已提交修订，提交后再刷新才换新读数。记分牌上的批注直接发到这个会话。
   - 合入主干后，主干基线成为各屏正式目录。
   - 新采集采用本次读到的配置修订，单次执行固定这次修订；旧计划 baseline 和归档证据保留，不回写历史。验收可选择新指标；会话须说明定义或单位变化对比较的影响，界面证据来源供人核对，不声称有自动口径比较。人的目标、合入和完成权限沿项目约定。

## 边界

本会话只沿指标配置 SOP，不因版本目标加载计划 SOP。指标使用独立固定维护分支与工作树，创建、目录、登记和宿主定位复用 Orca 原生能力；不硬编码物理目录或项目主分支。每次入口新建会话并保留维护树未完成改动，不 reset、删除重建或自动合并草稿树。不建立永久指标会话，不代项目在 BW 里登记每日指标采集自动化；项目在自己基础设施上自挂的定时数据准备不在此限（见[指标协议的历史脚本输出](../../references/metrics.md#历史脚本输出)）。维护位置与正式读取来源分别核对，草稿试采不自动成为三屏正式目录。

失败保留已有定义和真实错误；没有数据保持未知。材料/读数证据引用读 [版本材料](../../references/version-records.md)，不维护人工数和每日账本。
