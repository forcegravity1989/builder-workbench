# 配置与核对指标

帮助用户形成能支持判断、能按日/周采集真实历史的指标。正常刷新由服务执行；配置入口每次在固定维护树中新建 Orca 原生会话，不占用计划或验收会话。先核对宿主提供的项目、工作区和工具，不编造路径。

## 执行流程

1. **让全程可见。** “明确用途 → 核对历史来源与归属 → 准备脚本 → 实跑验证 → 交付接入”。开工前核对固定维护树与基线分支关系：落后且无本地提交可快进更新；有未合入草稿改动先与人确认顺序，不自行合并、不 reset。读取固定维护树已有定义及未完成改动，复用有效资产，已有输入不重问；本次是新会话，不按标题寻找或续接旧任务。
2. **明确与核对。** 读取项目约定和现有定义，仅追问缺失的用途、口径、特性归属及引领对象。脚本必须按日/周查历史；来源无此能力就说明缺口，不用当前快照或手填数代替。源数据和必要历史存储由用户项目或服务管理。存量定义/脚本来自旧分支或旧系统时，对照现行协议逐项核对（回溯能力、窗口参数、数据目标环境变量、失败语义），不合协议的改写后再实跑验证；被替代的旧资产同一交付内退役，不留双路径。
3. **准备与验证。** 按 [指标协议](../../system-prompt/references/metrics.md) 补定义/脚本，用实际窗口执行、独立核对输出和失败。缺凭据或项目入口如实报告；不能把脚本存在说成可采集。来源直查太慢或历史不可直查时，数据准备归项目自建自持（定时预采集与事件账等存储机制由项目选，BW 不代建也不约束机制），协议脚本只读已备好的源全量返回；准备脚本与协议脚本是两类脚本，各自职责与数据来源写清，不混写成一个。
4. **交付与采用。** 定义和脚本按项目分支/PR 流程交付，合入后回总览同步最新目录。新采集采用最新已合入来源，单次执行固定本次修订；旧计划 baseline 和归档证据保留，不回写历史。验收可选择新指标；会话须说明定义或单位变化对比较的影响，界面证据来源供人核对，不声称有自动口径比较。人的目标、合入和完成权限沿项目约定。

## 边界

宿主为配置任务加载通用 SYSTEM、项目约定和本 Skill，不附带 week-planning SOP。指标使用独立固定维护分支与工作树，创建、目录、登记和宿主定位复用 Orca 原生能力；不硬编码物理目录或项目主分支。每次入口新建会话并保留维护树未完成改动，不 reset、删除重建或自动合并草稿树。不建立永久指标会话，不代项目在 BW 里登记每日指标采集自动化；项目在自己基础设施上自挂的定时数据准备不在此限（见执行流程 3）。维护位置与正式读取来源分别核对，草稿试采不自动成为三屏正式目录。

失败保留已有定义和真实错误；没有数据保持未知。材料/读数证据引用读 [版本材料](../../system-prompt/references/version-records.md)，不维护人工数和每日账本。
