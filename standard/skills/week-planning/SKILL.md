# week-planning：版本计划

## 1. 核心目标

用固定 HTML 和每版一份 JSON，先核对结果，与 Builder 讨论 SMART 目标，带去 Leader 会议调整，会后拆为任务 Issue，再提 PR 归档。目标说明要达到的结果，任务说明为此要做的工作；二者不能互相代替。

## 2. When to Use / When NOT to Use

用于版本规划业务会话或用户手工填写时的协助。用户可以独立填完三屏，不必先由模型造空行。不用于开发模板或替用户验收任务。

## 3. 前置依赖检查

从任务参数核对工作目录、分支和版本；命令显式传 workdir、git -C 或 --workspace，宿主 cwd 不同不要求用户搬迁任务。检查项目 AGENTS.md 和当前数据，保留所有已有修改。Python 3 在本机必须可用，先验证实际解释器；缺失时明确告知，不静默更换保存方案。规划树长期保留；读取主工作目录的新提交作为结果证据，不把规划分支的旧 HEAD 当作项目最新实现。

本目录 assets 是出厂资源；项目内容在工作目录 .bw/planning。初始化只补缺失文件，不能覆盖已写内容。运行约定见 [数据和运行](references/data-and-runtime.md)。

## 4. 标准执行流程

1. **打开材料**：运行 planning.py 的 start（只需版本目录名，不必先读全量 JSON），打开返回的完整本地 URL（含版本与连接凭据），恢复已有内容；JSON 之后按需 read/update 读取。开页后先向使用者讲一段：三屏各做什么、全程可以手填、自动保存语义（保存只是草稿，保存≠确认）、三个确认点在哪；讲完由使用者选择自己填还是会话辅助，不默认代劳；事实收集尽量并行跑，不让使用者串行等。start 在当前规划工作树启动或复用服务，不逐版本开服务。没有历史数据时先 init 创建 default 空版本；用户定版号后 set-version，再以新版本 start。模板自带样式；直接打开 HTML 只读，不用浏览器目录授权。服务程序、模板与工具随 Skill 安装；项目树只放各版本数据（data.json、交付件与纪要）、可重建的 HTML 离线缓存与 .local 运行记录。用户结束规划并要求关闭时运行 stop。
2. **上周版本结果**：原目标优先读上版已确认 JSON 的 plan.goals（第三屏），首次缺历史才读旧计划 Issue 的目标评论，按目标定义辨认结果与工作项；仍无来源就留空。不把任务清单当目标，不编造旧 SMART 承诺。目标卡一句话；结合项目 commit、MR、测试或其他真实指标来源核对读数。口径或指标值不清楚，正常问用户；无数不填 0，不按提交量或任务数推算完成率。任务以该区所核对版本的 bw:plan 标签采集真实 Issue，类型和目标关联按注入的 issue-state 规范，实际进展用人能读懂的短句；旧评论的无编号工作项只保留来源，不冒充任务 Issue。主动问用户有没有版本发布报告或其他交付件要归档，填 results.deliverables 的交付内容、目标和链接，不逐任务索要交付件。会话先查询当前项目空间（含已核实属于该项目的工作树）的 Orca/Cursor/Claude 记录，只列真实标题；没有标题留空，没有可靠项目归属或可用读取接口就说明缺口，不拿聊天摘录代替列表。
3. **与 Builder 拟定目标，再去评审**：提醒用户检查现有 Issue，是否还有未排期、遗留或 Bug 要纳入本版；展示候选，让用户选择，不自动全部纳入。第二屏“总结三段”中，summary.risks 基于第一屏识别风险、影响和所需支持；summary.progress 用简短 SMART 读数总结第一屏结果，缺数明确待核对。先和 Builder 交流形成 plan.goals；逐目标一句话说明具体结果、指标和目标值，期限默认版本、负责人默认 Builder。确认可达性、相关性和取数方式；指标未知要问人，不替人编数。会议前准备好目标，再由 Leader 和 Builder 现场调整目标及指标；第二、三屏共用同一个 plan.goals。页面上 plan.goals 只显示编号和一句目标，不显示进度条、读数或目标值；metric/target 等 SMART 字段仍写入 JSON，由会话与人核对。第一屏 results.goals 另显示实际值、目标值、进度条与结果标签。会议版确认只记录状态、不另存快照，材料仍是同一份 data.json；页面已无「导出会议评审版」按钮，需要分享件时由会话按当前 data.json 另做只读导出或打印，现场不要求拆任务。切屏用顶栏页签；第二屏底栏不再放前进/后退按钮。
4. **会议与纪要**：现场核心记录与纪要在页面直接填写。页面已无会议链接输入框；用户给出链接后，由会话写入 `review.meeting_url` 再跑转写。Skill 内置 eMeeting 转写脚本与三节纪要模板，init 后默认配置即可用；换脚本或模板只改 `.local/settings.json`。自动整理按 [会议接入](references/meeting.md) 取转写、开一个子 agent 严格按模板三节提炼，不新增章节、不加无来源的负责人或指标；主会话核对后写回。转写失败按异常分支处理，连续失败改人工纪要，不模拟处理。
5. **会后拆解为 Issue**：Builder 消化会议决定后，先用 `gh issue list --repo <项目仓 origin 指向的 owner/repo> --label "bw:plan:<版本名>" --state all --json number,title,state` 查本版入口 Issue（--repo 显式给出，取工作树 origin 远端，不靠 cwd 推断），取标题以「更新指标 + 制定版本计划」开头的那条，不用全文搜索（正文命中会带进大量无关 Issue）；被管项目 provider 为 CodeHub 时按同口径换用其 CLI 查询；缺少时经本轮具体清单确认再创建；该系统条目挂 bw:plan:<版本名> 供 BW 识别在研版本，不复制目标评论、不改完成状态。在第三屏继续同一份目标，按目标拆任务；先查现有 Issue，避免重复创建。每项在 Issue 正文明确问题与范围、验收条件，Bug 补复现、预期和实际；不强制逐任务填交付件。依 issue-state 规范准备标题、Bug/Feature、bw:plan 和 bw:category 标签，展示具体纳入清单后创建/更新并读回真实编号、浏览器链接、标题、正文和完整标签。页面草稿尚未建 Issue 就不显示假编号；最终提交前必须有真实 Issue。已有排期/状态标签保留，不能顺便改完成状态。review.decisions 留下目标或范围变更原因。任务仍由远端 Issue 承载，JSON 是本次展示、补充进展和归档材料，不反向覆盖 Issue 实时状态。
6. **确认与归档**：第一屏用「确认结果，进入总结与评审」写入 `confirmation.results`。第二屏页面不再触发会议版确认；进入第三屏最终确认前，会话先执行 `planning.py confirm --stage review_ready`（或等价 API），再由用户点「确认计划」。用户确认目标、任务 Issue 和归档内容并要求 PR 后，运行项目门禁、提交与读回；提交脚本优先使用项目已有统一验证入口，其他项目由会话按 AGENTS 配置 validation_argv，不套用 BW 的 Rust 命令；Leader 在 PR 审核目标、拆解和交付承诺，完成最终握手。data.json 是唯一内容正本，确认只记录状态；修改继续写同一份文件，历史以 Git 与 MR 为准。不自动合入或关闭 Issue。

## 6. error_handling

| 情况 | 处理 |
|---|---|
| 无前序归档 | 查该版本旧计划 Issue 的目标评论；仍没有则留空，不能凭本次提交反推旧目标 |
| 旧目标没有可计算口径 | 来源保留原文，卡片一句概括，缺读数显示 —；不追造历史 SMART 承诺、不估百分比 |
| 新目标缺指标或目标值 | 澄清如何衡量、到什么程度；允许保存草稿，缺项或接受的例外可见 |
| Issue、父目标或交付件查不到 | 对应字段留空，记清缺口；不凭标题相似度和提交日志造编号、关联或验收报告 |
| 前序哈希已变 | 重读并核对，以 data.json 为准 |
| 用户手填需写入文件 | 在 start 返回的服务地址编辑；停顿自动写同一 JSON，无目录授权；失败保留输入并提示 |
| 服务中断或链接失效 | start 恢复服务并提供完整新地址；提醒保留未保存输入，不重置版本内容 |
| 数据冲突 | 保留手填内容，重读后合并，不强盖 |
| 转写脚本或纪要模板不可用 | 按会议接入的异常分支处理；转写不可得改人工纪要，保留已填材料，不模拟处理 |

## 7. 示例

例如讨论“提升版本材料完整性”时，先和人明确衡量指标、目标值及取数方式，用一句话写出结果承诺；期限默认该版本、负责人默认 Builder；现场对齐目标后，会后再拆成模板开发、数据采集与首用验收等任务。任务各自挂真实 Issue 和可核实目标；版本报告集中归档，不能自动证明目标值达成。示例不作为当前项目的已确认目标或数值。

## 8. 纪律表

| 必须 | 禁止 | 你不做的事 |
|---|---|---|
| 人和模型修改同一 JSON；自动保存与确认分开 | 每版另造日常 HTML、编造结果、强盖用户修改 | 偷改模板样式、自动认可会议提议、替 Leader 审核 |
