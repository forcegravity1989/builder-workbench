# 更新指标 + 制定本周计划(week-planning)

一周的开头。人只点一下「开始本周」,剩下的是一次对话:先看上周实际发生了什么,再把
绑不上数据的指标接上最便宜的采集路径,最后和人一起敲定这周要干哪几张活。

**人不写周目标——你引导他说出来,然后照着写。** 这条是整篇的重心,搞反了这次会话就
白跑了。

## 何时用

只在运作活①被开工时用。Workbench 建这张活的判据是**按标题查**——同名的活还没有(或已经
完成)才建得出来,所以**不要假设本周的 ops① issue 一定还不存在**:人可以
在计划屏、会话屏手动再建一张,那时候 issue 可能已经在了。

- 本周 ops① issue **不存在** → 正常建一张。
- 本周 ops① issue **已经存在** → 先读它的评论,原地补该补的,**不推倒重来**;在会话里说
  清楚你改了哪几段。

`.bw/metrics.toml` 不存在或是旧格式(项目刚接入、或指标还停在 V3 那套采集方案)则第
二步走**完整起草/重定**:借鉴旧脚本和旧口径,把已有读数迁进新流水,删掉 V3 废弃件。
不是内核静默改仓,也不是丢掉历史重起炉灶。

## 第一步 · 复盘上周

读上一周 ops① issue 的评论(周目标、指标读数快照)与 codehub Release 记录。

- 上周计划的活,哪些真做完了、哪些没动、哪些中途换了方向。
- 上周有没有发版,发的是什么。
- **没有上一周文件就如实说「首次制定周计划,无历史可复盘」**,不要用空话填满这一段,
  更不要根据 git log 编一段"上周大概做了这些"冒充上周计划。

这一步**只读不改**。

## 第二步 · 更新指标

调用子技能 `metrics-refresh`(和本篇同级:`../metrics-refresh/SKILL.md`):补齐缺的引领/滞
后指标、给每条指标判一次「这条指标的历史现在还能不能重新算出来」、能自动采的写成脚本、
跑一次采集。旧格式还要迁已有读数、借鉴旧脚本、删 V3 废弃件——细则在子技能第四节。

三条硬性约束,和整个产品的健康推导链是同一条:

- **绝不伪造读数**。采不到就是采不到,指标保持灰。
- **绝不为了点亮而改指标定义**。把"周活跃用户"改成"注册用户总数"因为后者好采——这
  是把管理体系变成自欺,比灰着更糟。
- **每撞到一条手填指标,都要认真问一次「这个数能不能写成脚本」**,并给出当次结论。
  你的价值是帮人把手填升级成能自动重算的,不是每周替人抄一次数。

这一步做完,**先用人话讲清北极星 / 滞后 / 引领是什么、这次为什么这么定**,等人单独
点头。第三步确认周目标、第四步落文件,都不能顶替这一下。还没确认指标,不要进第三步,
也不要写进仓。

改动**先不提交**,和第四步合成一次提交。

## 第三步 · 引导出本周(不许自己下结论)

结合指标现状、代码现状(codegraph 索引)、上周记录,以及(若这个项目配了项目群)一份
上周群消息摘要,和人交流出本周。

**先列出远端开着的 issue**(标题 / 状态 / 有没有本周标签),问人:

- 哪些纳入本周(只打标签,不新建)
- 哪些留在待办池
- 还要新拆哪些

不要跳过已有清单、直接起草一堆新卡。

然后交流:

- **周目标**。人说的话你来记。一句或一段都可以(总纲加要点也行),不要规定必须几行。
  给 1–2 个起手候选、并明确鼓励用 Other 自填即可,不要为合规硬凑 3–4 个选项把人框死。
- **还要新拆的业务活草稿**,每张:标题 / 说明 / 类别 / 预期推动哪个指标 / 建议的开工
  工具与 workflow。

**写完草稿必须停下来等人明确的确认信号**,才能进第四步。人没说"确认"之前不许落文件、
不许建活。这一下确认的是周目标和纳入清单,不是指标——指标在第二步已经确认过。

## 第四步(需人确认后才能做) · 落文件 + 建卡

写这几份:

1. `.bw/metrics.toml`(第二步的改动)
2. `docs/metrics.md`(指标说明:每条指标的判定与理由,没数的要有诚实说明)
3. 第二步新写或改过的采集脚本(`.bw/scripts/` 下)
4. 按下面模板追加一条 ops① issue 评论(不动正文、不改旧评)

**人确认之后,当场建新业务 issue,并给纳入的旧 issue 打 `bw:week:本周`。**
新建的每张业务 issue **必须同时打 `bw:category:{prototype|build|optimize|growth|ops}`**——
Workbench 读回用类别查开工工具,不打类别就开不了工。不要只把草稿写在评论里等另一条
命令。评论留给人看周目标和快照;范围内有哪些活,正本是标签。

打完周标签之后,codehub 上还要把这张 issue 挂到**同名里程碑** `YYYY-Www`(没有就建,
`start_date` / `due_date` 用那一周周一到周日)。失败说出来,不要回滚标签。GitHub 不
投影。会话里 `issue update --labels` **不会**走 Workbench 内核投影,要自己挂。

`git diff --stat` 只许出现:

- `.bw/metrics.toml`
- `docs/metrics.md`
- `.bw/scripts/` 下这次新写或改过的脚本

见了别的路径就停,把多改的收回去。评论走 issue comment,不进这次 diff。

评论必须用这三个二级标题(字写对;后面可以跟括号)。先写到文件,用同目录
`check-week-comment.py` 过一遍(非零退出不许贴):

```
## 周目标
人说的话。一句或一段都可以。

## 本周纳入
- #12 已有活(只打标签)
- 新拆:标题……

## 本周指标读数
每条已采到的引领/滞后各一行——数字 · 来源 · 采集时间。这一段是快照,不是正本。
没采到的不写行、不写 0。
```

Workbench 界面展示「周目标」整段;纳入和快照人点开这张运作活看。多条评论从新到旧,

同一段以最新一条为准。

metrics.toml 等仓文件产出在这张活自己的工作目录里,随这次改动提交。仓是正本,合入才算数。

然后正常提交,`gh pr create` 开 PR,把 PR 地址打屏。**`gh pr merge` 禁止**——合入是人
的动作,和所有 Issue 共用同一条铁律。

## DoD

- 落进仓文件的每份结构合法(TOML 能解析),挂进 issue 评论的每段格式清楚。
- 改动是这条活分支上的真实提交,不是只写在工作区里。
- 「本周指标读数」里的每一行都来自这次真采到的数,并注明这一段是快照。
- 仍然没数的指标,每条都有一句诚实说明:为什么采不到、最便宜的下一步是什么。
- 这次会话没有替人合入任何 MR。
- 当场新建的业务 issue 都打了 `bw:category:*`,纳入的旧卡如果还没类别,建卡时一并补上。

## 常见坑

- 把「引导」做成「代写」——人还没说话,周目标已经写好了。
- 跳过复盘直接进第三步:没有上周的账,这周的计划就是拍脑袋。
- 给采不到的指标编一个看起来能跑的采集方案,跑出来的数没人核对得了。
- **上来就给人一串「手填」了事**——手填是结论,不是起手式;每一条都要先问过「能不能
  写成脚本」、先找过有没有带时间戳的接口。
- 人说了"看起来不错"就当成确认——那不是确认信号,再问一句。
- 跳过已有 issue 清单、只拆新卡。
- 打了周标签却不挂 codehub 同名里程碑。
- 指标没单独讲给人听,拿第四步整包确认顶替。
