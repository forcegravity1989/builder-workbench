# 版本计划

帮助 Builder 与 Leader 形成清楚、有依据的版本目标，并连接真实任务和归档。目标由人决定；不要根据不完整仓库信息先替人写完。

## 开工与恢复

1. 完整读取[公共执行规范](../../references/execution.md)与当前项目 AGENTS.md，按其中的方法核对 CLI 和当前原生工作树。
2. 完整读取[版本材料规范](../../references/version-records.md)。从工作树读回的项目、工作树和宿主身份填写命令参数，再执行 `ORCA bw materials context --repo-id <id> --worktree-id <id> --host-id <host> --workflow plan --json` 核对当前选版；用 `list` 读取材料候选，异常时完整读取[旧格式材料](../../references/legacy-materials.md)。
3. 已绑定版本沿用绑定，入口提到的版本须与绑定/选版一致；不按标题、日期或最近文件猜版本。归档前核对真实分支，固定流程树内交付，不另建同用途树。

## 旅程与阶段校准

计划屏旅程四区：**计划准备 → 本版目标 → 会议纪要 → 归档 PR**。对用户讲话一律用这四个分区名——开场讲解与每步回执都按它说，用户能在板面上找到你说的每一步。

材料的 `workflow.stage`（preparation/goals/breakdown/review/archive）记录最近完成的阶段。面向用户的会话指引使用上面的板面分区名。每完成一个阶段用 `ORCA bw materials save` 更新：

| stage         | 何时写入                                                                           |
| ------------- | ---------------------------------------------------------------------------------- |
| `preparation` | 版本明确、现状与上版交付核对完成                                                   |
| `goals`       | 版本目标成形并写入 goals                                                           |
| `breakdown`   | Issue 创建/更新完成，版本标签与标题目标段已写定                                    |
| `review`      | 用户在会话中明确确认评审通过后                                                     |
| `archive`     | 提交归档 PR 之前；PR 开出后把 provider/repository/number 写入 `workflow.archivePr` |

恢复会话时先校准：按材料实际进度把 stage 补写到真实到达的阶段，再继续。评审必须由用户明确表达确认才写 `review`，不因改过目标就代人记录。内容实质调整使后续阶段失效时，把 stage 回退到实际阶段。PR 是否合入由界面按 `archivePr` 读 provider 显示，合入依人的授权，stage 不代表已合入。

## 执行流程

1. **开场：讲清 SOP、恢复本版。**首条消息按四区讲旅程，并按材料实际进度说明现在在哪一区：
   - 入口已带版本或工作树已绑定版本（绑定即单一正本）直接恢复，不重复问；尚未关联版本时立即列出现有候选并给出推荐版本号（顺延最近的归档版），一轮交流定版，不先扫仓库再定。无绑定树经人定版后，执行 `ORCA bw materials select --repo-id <id> --worktree-id <id> --host-id <host> --workflow plan --version <版本> --json`，读回 context 确认，再读材料；已有绑定不重复 select。
   - 新建版本时宿主已准备空计划；先读回再讨论目标，不重复创建文件。板面随会话打开呈现四区，尚无目标保持空，不把“渲染四区”当作会话任务。只有明确版本且确认材料不存在时，才按材料工具新建；旧格式或读取失败不能当作不存在覆盖。
   - 每步完成在会话中打一行回执（做了什么、结果、下一区），直接继续、不中断等确认；已有输入直接采用，不要求重新填写；用户可在右侧直接编辑并自动保存。
   - 定版确认前不创建或修改计划（绑定工作树以绑定为定版，不在会话内再确认）；旧格式文件读不出时按[旧格式材料](../../references/legacy-materials.md)处理，不阻塞正常版本。

2. **计划准备区：核对上版遗留和本版安排。**先完整读取[材料与运行能力](references/data-and-runtime.md)，再读本版材料及其已确定的验收来源：
   - 按[里程碑与版本排期](../../references/version-records.md#里程碑与版本排期)读取已合入的 `.bw/milestones.json` 及可选 `versionPlans`，作为特性和日期的讨论参考；没有里程碑照常制定计划。首日采用日期写本版计划，差异不自动回写里程碑。
   - 新建计划默认接续版本目录中紧邻的前版；已有 `summary.progressSource` 时沿用该固定引用，不重复问选哪版、不改选最新验收。前版只有计划、没有可用验收来源时，告诉用户上版尚未完成验收、回顾暂空，继续本版讨论；首个版本没有上版正常留空。不得跳到更早版本凑回顾，也不以实时 Issue 状态代替验收结论。未确定来源的旧计划按同一前版规则核对后写入固定引用，不能按日期或 mtime 猜。
   - 会议遗留优先读该固定验收**已人工确认**纪要的 `minutes.followups`（按数组序编号 M1…Mn，未确认草稿不流入）；旧格式材料的回退读法见[旧格式材料](../../references/legacy-materials.md)。带入候选时按来源和原目标/Issue 与已有候选查重，说明会议要求和来源，让用户决定哪些成为本版目标。没有可读的已确认纪要时如实说明，不推断没有遗留。
   - 用户提供会议 ID 要求补充会议要求时，先完整读取[会议转写](../../references/meeting-transcript.md)显式给出读取范围（明确只需某场时用 `--recording`，不把部分场次说成整场会议），必须由独立 subagent 按本项目与原承诺提炼，并展示来源和不确定清单；先由用户确认建议，再由用户选择目标，不能自动写入承诺。获取失败说明原因，让 Builder 在当前会话直接输入关键信息，不要求导入文件。
   - 仓库分支若落后，或已有未归档的材料提交，单独问要不要先更新，不自行合并。
   - 核对完成写 `stage=preparation`，请人核对板面两行遗留后进入本版目标。

3. **本版目标区：目标、拆解与评审。**
   - **讨论目标**：按[目标引导](references/goal-guidance.md)把目标说成能验收的结果——谁走通哪段旅程、交什么、怎样算完成。目标要能联到特性，特性要有用户旅程。不让用户先选类别，不按第几周套。
     - 再核对上一轮实际交付和本版约束；来源不明不编成绩，已有进展先核对再修改。形成少数几条结果目标，不强制分类、报告、指标或点数。目标成形写 `stage=goals`。
     - `summary.risks` 字段屏上没有填写入口：模型不代写不代改（模型通道写该字段会被拒绝），会话中谈到风险只作为讨论内容交人定夺。
   - **连接真实工作（会前拆解）**：创建、改写或关联 Issue 前，完整读取 [Issue 规范](../../references/issue-state.md)和项目 AGENTS 指向的归属约定，再查重、核对标题与主单身份。
     - 人确认版本、目标和纳入范围后，在同一条 Issue 补处理范围和验收条件，保留原问题。**版本成员靠标签、目标靠标题**：精确添加 `bw:plan:<版本>` 标签，并把标题写成 `【<版本>|<目标 id>】`（放在归属名称前）；跨版保留其他版本标签。目标段即计划材料里的目标 id（如 `G1`）。
     - 计划屏按标签 `bw:plan:<版本>` 读回本版成员、按标题目标段归到目标；**不再把每条任务写进计划材料 tasks**。确认特性改名时依版本材料同步主单与里程碑。按授权独立读回 Issue 标签与标题，拆解完成写 `stage=breakdown`。版别或目标段无法匹配本版的成员显示为「未归类」。
   - **与 PL 评审**：目标与 Issue 会前成形后与 PL 开会；不要求先生成纪要才能评审。
     - 评审形式：直接在目标卡修改目标句、验收标准与指标承诺，或进入板面「批注模式」把评审意见记在对象旁、经批注面板发送到会话。
     - 批注发送有双重意图：你按对象（目标句/验收标准/指标承诺/Issue 行/板面级）理解意见，帮人按批注调整本版目标——改动经用户确认才落；这些批注同时是会议纪要整理的输入之一。
     - 指标：有诉求时从共用目录选取并采集；**缺定义或采集脚本时引导用户点板面目标区「配置指标」入口另开配置会话——本会话固定在计划工作树，不修改指标配置**，配置合入后再回来选取采集，不编读数。
     - 人确认版本或目标调整后，同步受影响的版本／目标标题段与计划标签，保留主归属、主单身份和其他版本的关联。用户明确确认评审通过后才写 `stage=review`。

4. **会议纪要区。**用户在纪要区或会话中要求整理纪要时：
   - 先问一次是否需要按 eMeeting 会议 ID 拉取语音转写稿辅助总结——需要就给 ID，不需要或没有 ID 就仅凭批注生成，不重复追问。读取经原生发送弹窗递交的板面在线批注与可选转写稿（拉取前完整读取[会议转写](../../references/meeting-transcript.md)）；会话中每次发送的批注都是全量清单，以最新一次为准，不按累加理解；会话中找不到批注时先提醒从「板面批注」面板发送，不凭空编造。
   - 内容按[会议纪要规范](../../references/meeting-minutes.md)提炼：共识写决定，遗留写处理结果或跟进去向；板面已呈现的目标达成情况与 Issue 状态不复述进纪要。
   - 写入计划材料可选 `minutes` 节：`consensus` 若干点、`followups` 若干点（稳定 id 与 text），可在 `sources` 记录来源。仅在未确认时撰写或改写，保留人工已改的条目；确需整体重写先给人 diff。整份 `confirmed/confirmedAt` 由人确认，模型不得代填；已确认正文要改先由人在屏上撤销。材料中的 `closed` 原样保留，新增条目填 false，不用它表达本次处理结果；界面不做逐项闭环标记。
   - 随后与用户基于纪要逐条调整目标（落回第 3 区）；认可随归档 PR 评审表达，生成或填写纪要不等于确认，不另存第二份纪要正文。

5. **归档 PR 区。**用户在会话中要求归档时，按会议纪要规范逐条核对遗留的落实结果或真实跟进 Issue，补齐去向后由人在 PR 审查；跟进 Issue 可以未完成，不要求先关闭。再核对当前材料和待确认项，写 `stage=archive`。在本版固定计划工作树（绑定版本树为 bw/<版本>/plan，无绑定树的旧上下文为 bw/week-plan）内提交并推送，创建到主分支的 PR/MR，按项目门禁与授权执行，不另建工作树或分支。PR 开出后写入 `workflow.archivePr` 并回显链接与实际状态；合入依人的授权，后续修改同步同一 PR。归档后继续同一份计划并保留 cycleId。自动化按用户保存的配置运行，会话恢复沿 Orca。上版验收尚未完成不阻止本版规划。

## 按动作完整读取

- [版本材料](../../references/version-records.md)：保存、修订、归档或跨屏引用前读，含 workflow 契约与文本写入要求。
- [会议纪要规范](../../references/meeting-minutes.md)：整理或改写纪要前读，含共识/遗留两类条目的内容标准与正反例。
- [旧格式材料](../../references/legacy-materials.md)：读回异常、字段对不上或需要迁移时才读；正常流程用不到。
- [材料与运行能力](references/data-and-runtime.md)：核对固定前版来源、工具缺失、旧数据与并发冲突时读；使用宿主提供的真实入口。
- [指标](../../references/metrics.md)：涉及指标数据或写入时读。

保存失败保留输入，冲突先重读比较；缺数据保持未知。任务、归档和人的认可分开，不把文档存在、Issue 关闭、PR 合入或 stage 记录自动判为目标达成。
