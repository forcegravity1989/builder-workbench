# 版本计划

帮助 Builder 与 Leader 形成清楚、有依据的版本目标，并连接真实任务和归档。目标由人决定；不要根据不完整仓库信息先替人写完。

宿主下发原生项目、工作树与运行身份。先通过 `orca skills get week-planning` 核对版本匹配的产品技能；参考资料用同入口的 `--references` 和 `--reference <名称>` 按需读取。命令或权限不可用时保留讨论内容并报告真实错误。

## 阶段状态

计划材料的 `workflow.stage` 记录**最近完成的阶段**。两屏都不渲染旅程灯（计划自 G3、验收自 v10 退役），stage 只供会话恢复校准与自动化读取。每完成一个阶段就用 `ORCA bw materials save` 更新，让屏上进度与会话里的进度始终一致：

| 阶段 | stage 值 | 何时写入 |
|---|---|---|
| 准备 | `preparation` | 版本明确、现状与上版交付核对完成 |
| 目标 | `goals` | 版本目标成形并写入 goals |
| 拆解 | `breakdown` | Issue 创建/更新完成并写入 tasks 引用 |
| 评审 | `review` | 用户在会话中明确确认评审通过后 |
| 归档 | `archive` | 提交归档 PR 之前；PR 开出后把 provider/repository/number 写入 `workflow.archivePr` |

恢复会话时先校准：按材料实际进度把 stage 补写到真实到达的阶段，再继续。评审必须由用户明确表达确认才写 `review`，不因改过目标就代人记录。内容实质调整使后续阶段失效时，把 stage 回退到实际阶段（如评审后大改目标则回到 `goals`）。PR 是否合入由界面按 `archivePr` 读 provider 显示，合入依人的授权，stage 不代表已合入。

## 执行流程

1. **让全程可见，先明确版本。** 开口先讲旅程：准备 → 目标 → 拆解 → 评审 → 归档，并按校准后的 `workflow.stage` 说明现在在哪一步。本次运行尚未关联版本时，列出现有候选，让用户在界面选已有版本，或在会话确认沿用或新建；确认前不创建或修改计划。已有明确关联（包括入口附带的当前选版）则恢复，不重复问。用户可直接编辑右侧并自动保存，或在会话讨论；不要求重新填写已有信息。
2. **准备与讨论目标。** 按 [目标引导](references/goal-guidance.md) 把目标说成能验收的结果：谁走通哪段旅程、交什么、怎样算完成。目标要能联到特性，特性要有用户旅程。不让用户先选类别，不按第几周套。再核对上一轮实际交付和本版约束；来源不明不编成绩，已有进展先核对再修改。验收依据可能是同版上周或上一版，由用户明确应接续哪份已归档记录；核对后把其固定引用写入 `summary.progressSource`，计划屏上版回顾会按该固定来源回显延期遗留与会议遗留两类条目；找不到记录才与用户讨论回填 `summary.progress` 文本，不按版本号、日期或最新一条猜。会议遗留优先读该固定验收**已人工确认**纪要的 `minutes.followups`（按数组序编号 M1…Mn，未确认草稿不流入）；材料没有纪要节时（v10 之前写下）才回退读 `meetingDirectives`——只把 confirmed 且 tag=next-week-plan 的条目带入本周候选，record-remaining 保留为遗留背景，resolved-this-acceptance 不重复承诺，pending 不当作已采纳要求。带入候选时按来源和原目标/Issue 与已有候选查重，说明会议要求和来源，让用户决定哪些成为本周 Top 3。没有可读的已确认纪要或指导时如实说明，不推断没有遗留。用户提供会议 ID 要求补充会议要求时，按 [会议转写](../../system-prompt/references/meeting-transcript.md) 显式给出读取范围（明确只需某场时用 `--recording`，不把部分场次说成整场会议），必须由独立 subagent 按本项目与原承诺提炼，并展示来源和不确定清单；先由用户确认建议，再由用户选择目标，不能自动写入承诺。获取失败说明原因，让 Builder 在当前会话直接输入关键信息，不要求导入文件；把实际消息交给独立 subagent 整理并保留人工来源，展示不确定项后由用户确认候选，不要求重复抄录。`summary.risks` 字段保留但当前屏上没有风险填写入口：模型不代写不代改（模型通道写该字段会被拒绝），会话中谈到风险只作为讨论内容交人定夺。仓库分支若落后，或已有未归档的材料提交，再单独问要不要先更新，不自行合并。形成风险和少数几条结果目标，不强制分类、报告、指标或点数。准备完成写 `stage=preparation`，目标成形写 `stage=goals`。
3. **连接真实工作（会前拆解）。** 按 [Issue 格式](../../system-prompt/references/issue-state.md) 查重并创建或更新任务。首次提单只需问题描述；用户确认版本与目标后，再在同一条 Issue 补处理范围、验收条件，按 `【<版本>|<目标>】问题描述` 整理标题并精确增加 `bw:plan:<版本>` 标签。逐条拆解时根据用户确认的提单性质给 Issue 加 provider 原生 `Bug` 或 `Feature` 分类；Bug 表示现有行为未满足预期，Feature 表示新增能力或行为，讨论/预研保留 provider 的原生入口。性质不清时先问人，不从标题、状态或关闭原因猜；两屏的读回分组遵循 Issue 格式中的分类标签规则，不为显示分组批量补标。将 provider/repository/number/goalId 写入计划材料 tasks；无确认的版本或目标不猜。依会话授权执行并读回编号、正文、状态、分类和任务引用。右侧呈现真实关联；任务详情与编辑使用 Orca。先定结果再拆工作，不顺便改完成状态。拆解完成写 `stage=breakdown`。
4. **与 PL 评审并修改目标。** 有指标诉求时从共用目录选取并采集，缺定义/脚本先用 [metrics-refresh](../metrics-refresh/SKILL.md) 补齐，不编读数。目标与 Issue 会前成形后与 PL 开会，直接在目标卡修改目标句、验收标准与指标承诺，或进入计划屏「批注模式」把评审意见记在对象旁、经板面批注面板发送到会话作为纪要输入；不要求先生成纪要才能评审。用户明确确认评审通过后写 `stage=review`。评审中或评审后调整了目标，同步核对已建关联 Issue：标题标记 `【<版本>|<目标>】` 与 `bw:plan:<版本>` 标签跟着目标变化更新，不留旧标记。
5. **归档与接续。** 界面不再有归档按钮，用户在会话中直接要求归档：核对当前材料和待确认项，写 `stage=archive`；在本版固定计划工作树（绑定版本树为 bw/<版本>/plan，无绑定树的旧上下文为 bw/week-plan）内提交材料并推送远端同名分支，创建由该分支到主分支的 PR/MR，按项目门禁与授权执行，不另建工作树或分支。PR 开出后把 provider/repository/number 写入 `workflow.archivePr`，回显链接与实际状态；合入依人的授权。PR 开出后再改材料时，核对 PR 是否需要同步更新。归档后继续修改同一份计划并保留 cycleId，材料按新修订再次提交。自动化首次登记默认不复用会话，后续按用户保存的配置运行；同次恢复与标题沿 Orca。实际开展上版验收进入独立验收屏，不当作本版规划前置门槛。

**会议纪要。**用户在纪要区或会话中要求整理纪要时：先问一次是否需要按 eMeeting 会议 ID 拉取语音转写稿辅助总结——需要就给 ID，不需要或没有 ID 就仅凭批注生成，不重复追问。读取经原生发送弹窗递交的板面在线批注与可选转写稿（按 [会议转写](../../system-prompt/references/meeting-transcript.md)）；会话中每次发送的批注都是全量清单，以最新一次为准，不按累加理解；会话中找不到批注时先提醒从「板面批注」面板发送，不凭空编造。总结为固定两块写入计划材料可选 `minutes` 节——`consensus` 共识若干点、`followups` 遗留若干点（每条含稳定 id 与 text，新增条目 `closed=false`），可在 `sources` 记录输入来源描述。仅在纪要未确认（`confirmed=false` 或整节缺省）时撰写或改写正文；改写前核对屏上是否已有人工编辑——保留人工已改的条目，只新增或改写人未动的部分，确需整体重写时先给人 diff 确认；已确认纪要对模型通道整节冻结，要改先由人在屏上撤销确认。`followups[].closed`（闭环 = 版本计划已按该条修改）与 `confirmed/confirmedAt` 只能由人在计划屏标记，不代写代标。随后与用户基于纪要逐条调整目标；认可随归档 PR 评审表达，生成或填写纪要不等于确认，不另存第二份纪要正文。

## 需要时读取

- [版本材料](../../system-prompt/references/version-records.md)：保存、修订、归档或跨屏引用前读，含 workflow 契约与文本写入要求。
- [运行能力](references/data-and-runtime.md)：工具缺失、旧数据与并发冲突时读；使用宿主提供的真实入口。
- [指标](../../system-prompt/references/metrics.md)、[Issue](../../system-prompt/references/issue-state.md)：涉及对应数据或写入时读，不复写协议。

保存失败保留输入，冲突先重读比较；缺数据保持未知。任务、归档和人的认可分开，不把文档存在、Issue 关闭、PR 合入或 stage 记录自动判为目标达成。
