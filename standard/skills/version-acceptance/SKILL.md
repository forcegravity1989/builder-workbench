# 版本验收

协助 Builder 完成“准备交付 → 出包 → Showcase 与验收 → 归档”。典型是周五上午准备、下午展示后归档；版本与项目要求优先，不把时钟当门禁。

通过宿主的 `orca skills get version-acceptance` 读取本流程；`--references` 列出可用引用，`--reference <名称>` 按需读取。只使用实际下发的身份、材料命令和原生执行能力，普通项目无需检出 BW 源码。入口提供当前选版与实际工具身份；先使用这些上下文，不要求用户提供 BW 源码。

## 阶段状态（与验收屏的灯共用）

验收材料的 `workflow.stage` 记录**最近完成的阶段**，验收屏旅程灯直接按它点亮：到 stage 及其之前为绿，之后为灰。旅程里的「出包」灯是唯一例外——它不跟 stage，随出包区块读到的最新制品包点亮，读到真实包才绿；出包不是 stage，不为它写值。每完成一个阶段就用 `ORCA bw materials save` 更新：

| 阶段 | stage 值 | 何时写入 |
|---|---|---|
| 准备交付 | `preparation` | 候选固定、交付件与材料按目标收齐 |
| 展示验收 | `showcase` | 展示完成、每个目标的人工结论都已在界面记录 |
| 归档 | `archive` | 提交归档 PR 之前；PR 开出后把 provider/repository/number 写入 `workflow.archivePr` |

恢复会话时先校准：按材料实际进度把 stage 补写到真实到达的阶段。人工结论（`results[].decision`）仍只由人在界面记录，不代签；stage 只是进度信号，不代表目标达成，也不代表 PR 已合入——合入状态由界面按 `archivePr` 读 provider 显示。

## 执行流程

1. **恢复本次验收。** 先展示完整流程和已有进度（按校准后的 `workflow.stage`），再核对场外要求、实际项目与固定 bw/week-acceptance 工作树。入口已给出版本时直接恢复该版材料，不再选第二次。页面读回已有验收；没有验收时基于本分支该版已提交计划初始化草稿并自动保存。版本未明确时先列候选，与人明确后才写材料；保留固定计划来源，未合入计划只能明确标为草案预验收。工作树目录由 Orca 原生创建和登记。开工前核对固定树与基线分支关系：behind 且 ahead=0 可 fast-forward 更新；ahead 含未归档材料提交时先与人确认顺序，不自行合并。新周运行新会话，同次上午/下午与重试继续原会话，不混用 bw/week-plan。
2. **准备交付。** 确定候选提交，读取项目已有测试/交付入口，按已有授权执行并独立核对结果。先查本次原生任务和进程是否仍在运行，再恢复或重试；保持源码执行区检出的提交与候选一致，不能从验收树旧 HEAD 打包。整理项目需要的交付件、报告和 showcase 材料；缺入口明确说明。生成时记录实际命令、工作区、候选、时间与适用的校验值，不凭文件名判断来源。交付与材料按目标收齐后写 `stage=preparation`。
3. **出包。** 需要安装包时用验收屏「出包」区块：它按项目远端自动对接出包流水线，流水线下拉只列可出包的流水线。由人选流水线并点「出包」；启动受理后流水线在平台上运行约数分钟，最新包信息每分钟自动刷新，不重复启动。最新制品包的项目名称、版本号、创建时间与包文件是平台真实读数——核对它们确实对应本次候选，不把旧包当本次交付包；「下载」把最新安装包本体保存到人选择的目录，可直接作交付件。区块报错（无流水线、无权限、远端认不出）时如实转告，改按项目自有出包入口执行并核对；没有包要求就不造包要求。
4. **核对事实。** 原目标、约定交付、验收说明与指标目标保持只读；只按原承诺核对交付件和指标，不为每个目标强加两类材料。页面只显示已承诺或已保存的指标；“刷新指标”采用最新已合入定义执行真实脚本并保存读数，失败不填零。任务通过 Orca provider 刷新，与计划屏共用任务展示。实际材料能打开，失败与缺口显式保留。
5. **Showcase 与判断。** 沿原目标打开同一候选的材料，由人判断达成、未达或待核，用户在页面填写后自动保存，模型不代签；保存不代表验收通过。需要方法时读 [证据与后续](references/evidence-and-follow-up.md)。补某目标的材料只使该目标待重新核对；更换计划修订、源码候选或候选交付包（package）时全部目标待重新核对，即使源码提交不变，也要按实际包更新校验值等来源，保留原结论文字。未达项在原卡写原因和安排，不自动进入下版承诺。Issue 只核对真实状态，不在验收中再次拆任务。全部目标的人工结论记录完成后写 `stage=showcase`。
6. **归档接续。** 界面不再有归档按钮，用户在会话中直接要求归档：验收纪要由当前结构化材料派生，核对版本/周次/修订/来源及当时的任务快照后，写 `stage=archive`；在固定 bw/week-acceptance 工作树内提交材料并推送远端 bw/week-acceptance，创建由 bw/week-acceptance 到主分支的 PR/MR，按项目流程和授权执行，不另建工作树或分支。开出后把 provider/repository/number 写入 `workflow.archivePr` 并回显链接。合入后从项目主干基线（主检出）读回，总览每版显示一份当前材料；归档后补证继续编辑同一份验收并保留 cycleId，形成新修订，旧依据从 Git 追溯。出包、合入、Issue 完成和正式发布不互相代替。首用时记录材料找不到、候选不一致、重复录入和未达无安排等实际问题，不预填改善结果。

## 需要时读取

- [版本材料](../../system-prompt/references/version-records.md)：跨树读取、候选、修订、保存、workflow 契约与文本写入要求。
- [指标](../../system-prompt/references/metrics.md)、[Issue](../../system-prompt/references/issue-state.md)：涉及对应事实与远端写入。

失败保留草稿和原来源；先核对仍在运行的任务再重试，不能重复开构建、覆写脏树、伪造新读数或替人确认。
