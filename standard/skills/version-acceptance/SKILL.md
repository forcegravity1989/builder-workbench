# 版本验收

协助 Builder 完成“准备交付 → Showcase 与验收 → 归档”。典型是周五上午准备、下午展示后归档；版本与项目要求优先，不把时钟当门禁。

> 配套设计稿，需与独立验收工作树、宿主工具和材料服务一起接入。只使用实际下发的能力。

## 执行流程

1. **恢复本次验收。** 展示全程与已有进度，核对项目、版本、计划修订和固定 bw/week-acceptance 工作树。新周运行新会话，同次上午/下午与重试继续原会话，不混用 bw/week-plan。
2. **准备交付。** 确定候选提交，读取项目已有出包/测试/交付入口，按已有授权执行并独立核对结果。整理包或约定交付件、报告和 showcase 材料；缺入口说明限制，不能从验收树旧 HEAD 打包。候选变了先检查材料是否仍匹配。
3. **核对事实。** 原目标、约定交付、验收说明与指标目标保持只读；指标只运行真实采集脚本，任务通过 Orca provider 刷新。实际材料能打开，失败与缺口显式保留。
4. **Showcase 与判断。** 沿目标打开同一候选的材料，由人判断达成、未达或待核。需要方法时读 [证据与后续](references/evidence-and-follow-up.md)。未达项在原卡写原因和安排，不自动进入下版承诺。
5. **归档接续。** 验收纪要由当前结构化材料派生，核对版本/周次/修订/来源后按项目流程和授权提 PR。人合入后从目标基线读回，总览可回看多周记录。出包、合入、Issue 完成和正式发布不互相代替。

## 需要时读取

- [版本材料](../../system-prompt/references/version-records.md)：跨树读取、候选、修订、保存与归档。
- [指标](../../system-prompt/references/metrics.md)、[Issue](../../system-prompt/references/issue-state.md)：涉及对应事实与远端写入。

失败保留草稿和原来源；先核对仍在运行的任务再重试，不能重复开构建、覆写脏树、伪造新读数或替人确认。
