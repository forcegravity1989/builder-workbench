# 版本验收

协助 Builder 走完验收屏四步:**验收准备 → Showcase → 会议纪要 → 归档 PR 及发版本**。对用户讲话一律用这四个分区名——开场讲解与每步回执都按它说,用户能在板面上找到你说的每一步。本屏为周五验收会议服务:会前把材料备齐(预订的验收会议 + 部署好的真机演示环境 + 一份聚合各 Issue 验收件的证据报告),会中对着勾勾表逐目标演示,会后纪要确认、归档、按需发版。个人对需求的逐项自验与举证都发生在周中的会话与开发流程——验收证据随各 Issue/PR 合入时留下,验收屏只聚合呈现、不采集。典型周四准备、周五开会;版本与项目要求优先,不把时钟当门禁。

通过宿主的 `ORCA skills get version-acceptance` 读取本流程;`--references` 列出可用引用,`--reference <名称>` 按需读取。只使用实际下发的身份、材料命令和原生执行能力;入口提供当前选版与实际工具身份,先使用这些上下文,普通项目无需检出或提供 BW 源码。

## 会话驱动板面

右板各操作与会话的分工:**板面按钮要么直接读回材料,要么把一句话请求注入本会话;实际工作由你按下表做**。板面按钮与人直接在会话里说同一请求完全等价,不因入口不同改变行为:

| 板面动作 | 你做什么 | 写回材料什么(板面读回) |
|---|---|---|
| 「出包」 | 固定逻辑在板面(按项目远端直连出包流水线),无需你执行;包出现后核对四字段对应本次候选,不把旧包当本次交付包 | `candidateRef`(候选固定即写);`preparedArtifacts` kind=package(checksum/location/实际命令) |
| 「部署」 | 注入部署请求:下载最新包,**按项目自有部署入口**部署启动——各服务部署逻辑不同,无固定脚本;桌面应用=安装并启动,web 服务=部署并起前端。缺入口说明缺什么,不虚构命令;缺工具请人安装,不降级绕道 | `demoEnv`:web 服务写 kind=url,附系统名 label 与 URL;桌面应用写 kind=launched,附启动状态。板面「演示环境」行显示系统名(缺省回退 URL),点击经内置浏览器打开 |
| 「预订会议」 | 注入预订请求:生成完整预览(起止时间、与会人、议题),**人确认后创建会议**;与会人默认取项目绑定项目群的全部成员,没有绑定群就请人给群号(见「预订会议与纪要同步」节) | `meeting`(标题、时间、会议 ID、会议页面链接、与会人工号);板面「验收会议」行读回标题、时间、ID、与会人数与页面入口 |
| 「更新代码」 | 板面原生同步,快进不了时按提示在会话处理 | — |
| 「聚合」 | 注入聚合请求:把各 Issue/PR 合入时留下的验收件按目标归并成一份验收证据报告并登记(见下节);缺证如实标出,由人确认或自行补充,不代采 | 报告文件落 `.bw/planning/<版本>/` 并登记(verification 制品) |
| 「发布」 | 注入发布请求:先呈现知情状态 → 核对一致性 → **经人明确授权**按项目发布入口执行 → 独立读回并在会话中报告 → 把 tag 引用写入 `workflow.release` | 板面读回行现算呈现是否已发布、标签、时间、Release 地址与资产(读数不落材料,正本在 Git 标签与 Release 页) |
| 归档(会话中发起) | 核对材料 → stage=archive → 固定树提交推送 → 开 PR → 写 archivePr | 归档引用与状态 |

目标结论、Issue 备注与遗留标记、纪要人工确认,**都由人在界面落**;你不代选、不代填这些人工字段、不代确认。纪要正文可按人的请求在未确认态整理,人也可直接编辑。助手入口按对象就近放置:准备区「聚合」「预订会议」、纪要区「让验收助手整理纪要」「同步会议纪要」、归档区「让验收助手发起归档」同样经 Orca 原生发送弹窗注入一句话请求,与人在会话里直说等价;Showcase 无模型填写事务,不设助手入口。

## 验收证据报告(聚合)

举证在各 Issue/PR 合入时已经留下:**有开发的 Issue**,证据在 PR 评论中关于该开发或修复的验证评论;**无开发直接关闭的 Issue**,证据在 Issue 相关评论。形式为截图或其他易于人理解的实物,不是大段文本。验收准备不采集证据、不做演示分诊;「本版目标值 vs 本期读数」对比与缺口清单随旧前提退役。

「聚合」请求到达时,按各目标的 Issue 清单归并验收件,按[报告模板](assets/evidence-report-template.md)生成一个版本一份的报告:目标 → Issue → 验收说明 + 逐条证据(PR 验证评论/Issue 评论的链接与摘要、截图、平台读回、文件位置)。缺证的 Issue 在报告里如实标出,由人确认缺口或自行补充;你不代采、不代补、不用大段文本凑数。验收件只进报告,板面不回显。与 workbench-release 的版本收尾总结报告分工:本报告逐 Issue 罗列验收件(给核对与会议用),收尾报告偏总结叙事(给领导与升级试用者);两者独立,不可互相代替。

## 预订会议与纪要同步

会议动作由本流程自带,不需要额外安装会议技能;边界固定:**先预览后执行**——创建会议、写入纪要草稿,每一项外部写入都先给人完整预览,经确认后才执行;对未变化的预览给出一次明确同意即视为本次执行的一次确认,预览有变化原确认即失效、须重新确认,不在建会、写草稿之间重复索取确认。**只把纪要写入会议草稿**,由人在会议系统复核并手动点击发送,你不代发;不代订会议室、不推断发言人、不做未经预览的外部写入。会议工具缺失或未登录时如实转告缺什么、请人安装或登录,不虚构步骤、不绕道。

- **预订会议**:收到预订请求 → 按下面顺序执行,不再临时翻 `--help`:
  1. 先跑 `welink-cli auth status`。未登录且无法自动刷新时如实请人先登录,不继续预订。
  2. 定与会人:读项目根 `.bw/project.toml` 的 `[chat].group_id`(项目绑定的项目群),执行 `welink-cli im query-group-member --group-id "<群号>"`,取 `memberAccount`,只保留 `TYPE_OWNER`/`TYPE_ADMIN`/`TYPE_NORMAL`,排除 `TYPE_AGENT_ASSISTANT`/`TYPE_ASSISTANT` 等机器人。**没有绑定项目群、`.bw/project.toml` 读不到或 `group_id` 为空时,先请人提供群号**;人没有群号,再请人直接给与会人工号。不猜、不编与会人。
  3. 定时间:缺省按本周五验收会时段;时间或与会人仍缺时只问缺的那一项,不重复追问。会议室不是 `meeting create` 的参数,不作为阻塞项。
  4. 生成完整预览(起止时间、与会人、议题),不执行外部写入;人确认后再创建。
  5. 用毫秒时间戳创建(AI 听随会议创建默认开启,无单独参数,不伪造开启步骤):
     ```bash
     welink-cli meeting create --start-time <开始毫秒> --end-time <结束毫秒> --subject "<标题>" --meeting-user-list <工号...>
     ```
  6. 用 `welink-cli meeting info --meeting-id <meetingId>` 读回 `meetingId`、`jumpUrls` 与时间;`meetingNo` 不是会议主键,不要拿它当 ID。
  7. 把会议信息写回验收材料 `meeting`:`{title, time, id?, link?, attendees?}`——`id` 存 `meetingId`;`link` 取 `jumpUrls` 中 `type=basic`(缺省用 `summary`)的地址;`attendees` 存实际传给 `--meeting-user-list` 的工号;`time` 用「MM-DD(周X) HH:mm–HH:mm」的人读写法。写回用原生材料服务,`--repo-id`/`--worktree-id` 用入口提供的原生身份:
     ```bash
     ORCA bw materials read --repo-id <id> --worktree-id <id> --workflow acceptance --version <版本>
     ORCA bw materials save --repo-id <id> --worktree-id <id> --workflow acceptance --version <版本> --expected-revision <revision> --input <JSON 草稿文件>
     ```
     先读拿 `revision`,再带 `--expected-revision` 保存,不直接改文件;完整参数见[版本材料](../../system-prompt/references/version-records.md)。写回后告知人板面「验收会议」行已读回标题、时间、会议 ID、与会人数与会议页面。
  8. 已预订不重复订;改期用 `welink-cli meeting update`,取消用 `welink-cli meeting cancel`,由人说明后同样先预览再执行。
- **同步会议纪要**:把材料中已形成的纪要按固定样式渲染成草稿——按目标分节(目标句作小标题),节内共识与遗留逐条,只写人已填写或确认的内容,不虚构、不补写 → 完整预览(含写回目标会议)经人确认后写入该会议的纪要草稿 → 返回纪要链接并提醒人最终发送是手动动作。已写入且草稿未变化的重复执行直接跳过、不重复写入;草稿或目标会议有变化时不盲覆盖,先向人说明再按新预览确认。中断或状态不确定时先打开会议系统核对草稿是否已写入,不直接重试覆盖。材料尚未预订会议时说明先在准备区预订。

## 阶段进度(材料内部,界面无灯)

`workflow.stage` 记录最近完成的阶段,只用于会话恢复校准与自动化读取,界面不渲染灯,也不把 stage 值当作面向用户的步骤名:

| stage 值 | 何时写入 |
|---|---|
| `preparation` | 候选固定、验收会议预订完成(或人说明自行安排)、演示环境部署可用、验收证据报告聚合生成并登记 |
| `showcase` | 会议演示完成、每个目标的达成/不达成已由人在界面标记 |
| `archive` | 提交归档 PR 之前;PR 开出后把 provider/repository/number 写入 `workflow.archivePr` |

纪要的人工确认是材料字段事实,不占 stage。恢复会话时先按材料实际进度校准 stage;stage 不代表目标达成,也不代表 PR 已合入或版本已发布。

## 执行流程

1. **开场:讲清 SOP、恢复本版、先备料不发散。**
   - 首条消息按四步讲旅程,并按校准后的 stage 说明现在在哪一区;再核对场外要求、实际项目与本版固定验收工作树(绑定版本树为 bw/<版本>/acceptance,无绑定树的旧上下文为 bw/week-acceptance)。
   - 入口已给出版本或工作树已绑定版本(绑定即单一正本)时直接恢复该版材料,不再选第二次;没有验收时基于本分支该版已提交计划初始化草稿并自动保存。
   - **计划归档 PR 未合入也允许开始验收会话**。首轮核对计划归档状态并及时提醒人处理,不自行合入;计划来源尚不可读时先说明缺口,不伪造目标、修订或 planRef。只有核对到本版已提交的固定计划才初始化验收材料,不能使用 kind=draft 的 planRef。
   - 开工前核对固定树与基线分支关系:behind 且 ahead=0 可 fast-forward 更新;ahead 含未归档材料提交时先与人确认顺序,不自行合并。
   - 每步完成在会话中打一行回执(做了什么、结果、下一区),直接继续、不中断等确认;同次会议的准备与重试继续原会话,不混用本版计划会话与计划工作树(绑定版本树 bw/<版本>/plan,旧无绑定树 bw/week-plan)。

2. **验收准备区:出包、部署、预订会议、聚合报告。**
   - **出包**:人在界面点「出包」(或按项目自有出包入口执行);受理后最新包每分钟自动刷新,不重复启动;核对最新包四字段对应本次候选。候选固定后**写入 `candidateRef`**;包出现后**登记 `preparedArtifacts`**(kind=package,含 checksum、location、实际命令)。
   - **部署**:收到部署请求(板面「部署」或人口头)→ 下载最新包 → 按项目自有部署入口部署启动 → **把演示环境写回材料 `demoEnv`**(web 服务:kind=url,附一句系统名 label 与 URL;桌面应用:kind=launched,附启动状态),并告知人板面可点击打开。区块报错(无流水线、无权限、远端认不出)如实转告,改按项目自有入口执行并核对;没有包要求就不造包要求。
   - **预订会议**:收到预订请求 → 与会人默认取项目绑定项目群的成员,没有绑定群先请人给群号 → 生成完整预览(起止时间、与会人、议题)→ 人确认后按「预订会议与纪要同步」节的命令创建 → 读回会议 ID、页面链接与与会人并写回材料 `meeting`,告知人板面「验收会议」行已读回;已预订不重复订,改期或取消由人说明后同样先预览再执行。
   - **聚合报告**:收到聚合请求 → 按各目标的 Issue 清单归并验收件(有开发=PR 验证评论,无开发直接关闭=Issue 评论;截图等实物)→ 按模板生成一份报告并登记;缺证的 Issue 如实标出,由人确认缺口或自行补充,不代采、不凑数。
   - 包重出不自动刷新板面已填内容;检测到包变化时在会话提醒是否重新部署演示环境、是否重新聚合报告,由人决定——验收件在各 Issue/PR 合入时已留下,包重出不改变它们。板面批注是人的意见输入:收到批注按对象(目标/验收标准/Issue/板面级)理解意见,回应或修订材料。准备齐后写 `stage=preparation`。

3. **Showcase 区:会中演示支持。**复用计划目标,只读回显。会中逐目标:现场演示的带人走演示环境操作路径,或打开报告对应 Issue 的验收件展示;**行内单个状态标识(计数后)由人选择未判定/达成/不达成,你不代选**;未判定不冒充结论,演示过与否不进材料。人标记前如实报告缺口(「该目标还有 N 个 Issue 缺验收件」),标不标由人决定。不达成目标:原因与安排进纪要、目标「下一步」与对应 Issue 的备注/「遗留」标记(Issue 只有遗留标记,无风险标记;已关闭 Issue 不计遗留、已存备注只读)。全部目标标记完成后写 `stage=showcase`。

4. **会议纪要区。**纪要固定两块:「共识」与「遗留」,常驻板面,条目按目标组织;人点「编辑纪要」进入编辑态后才增删改或粘贴。人要求整理时:
   - 先问一次是否需要按 eMeeting 会议 ID 拉取语音转写稿辅助总结——需要就给 ID,不需要或没有 ID 就仅凭批注生成,不重复追问;读取按[会议转写](../../system-prompt/references/meeting-transcript.md)显式给出范围(明确只需某场时用 `--recording`,不把部分场次说成整场会议),没有稿件或来源不可读时如实说明,不凭空补写会议内容。
   - 板面批注每次发送都是全量清单,以最新一次为准,不按累加理解;会话中找不到批注时先提醒从「板面批注」面板发送,不凭空编造。
   - 内容按[会议纪要规范](../../system-prompt/references/meeting-minutes.md)提炼后写入材料 `minutes` 节,并按目标组织:条目带「G<n> ·」目标前缀,共识记各目标会上产生的结论性决定,遗留记录该目标待处理事项及其落实结果或真实跟进 Issue;板面已呈现的达成情况、Issue 状态与指标读数不复述进纪要。板面读视图按前缀分组到各目标小标题下,协议仍是平铺清单(呈现级实现,协议级目标绑定留待后续会议相关 Issue)。可在 `sources` 记录输入来源描述。
   - 纪要由人在界面逐条编辑、**人工确认后生效**;你不代确认、不代签。改写前核对屏上是否已有人工编辑——保留人工已改的条目,只新增或改写人未动的部分,确需整体重写时先给人 diff 确认。已确认的纪要整节冻结,你不得改写;人在界面撤销确认后才能在未确认态重新整理。
   - 遗留条目不另设闭环开关。归档前逐条核对:已落实到计划或结论,或已关联真实跟进 Issue;关联 Issue 不代表事情完成,开放的 Issue 可以随纪要归档。确认后的纪要可供下版回顾,由人决定哪些事项继续纳入计划,不自动建任务或排期。
   - **同步会议纪要**:收到同步请求 → 把材料纪要按固定样式(按目标分节)渲染草稿 → 完整预览(含目标会议)→ 人确认后写入预订会议的纪要草稿 → 返回纪要链接并提醒人最终发送是手动动作;材料尚未预订会议时说明先在准备区预订。中断或状态不确定先核对草稿是否已写入,不直接重试覆盖。

5. **归档 PR 及发版本区。**
   - **归档**:人在会话中要求归档时,核对固定计划来源、计划归档状态、材料与人工结论,并逐条核对纪要遗留的落实结果或真实跟进 Issue;缺口先向人说明,由人在 PR 评审确认,不增加界面硬门禁。随后写 `stage=archive`;在本版固定验收工作树(绑定版本树为 bw/<版本>/acceptance,无绑定树的旧上下文为 bw/week-acceptance)内提交材料(验收 JSON、证据报告及截图)并推送,创建到主分支的 PR/MR,按项目流程和授权执行,不另建工作树或分支;开出后写 `workflow.archivePr` 并回显链接;屏内只呈现引用、状态与原生 PR 页入口。
   - **发版**:呈现各目标达成/不达成与遗留——**不达成不阻断发布,由人知情决定**;核对发布提交与验收的包一致,不一致(如会后修复)列出差异与来源待人确认;经人明确授权后按项目自有发布入口执行;发布后**独立读回**(tag、时间、资产、校验值)并在会话中如实报告,并把 tag 引用写入 `workflow.release`(仅读回键,同 archivePr 的「引用落材料、读数现算」;时间、地址、资产等读数不落材料,正本在 Git 标签与 provider Release 页)。板面发布区按该引用现算读回,呈现是否已发布、标签、发布时间、Release 页地址与资产;引用在而 Release 查无、读回失败均如实呈现,不猜;总览仍不显示已发布。未经人明确授权不创建 Release、不打标签;不合并 PR、不关闭 Issue、不替人确认版本达成。
   - **归档之后**:合入后从项目主干基线(主检出)读回,总览每版显示一份当前材料;纪要「遗留」条目与 Issue「遗留」标记分别作为下版计划屏「会议遗留」与「延期遗留」回显,由下版计划会话与人形成候选,不自动承诺或排期。归档后补证继续编辑同一份验收并保留 cycleId,旧依据从 Git 追溯。出包、合入、Issue 完成和正式发布分别成立,不互相代替。首用时记录材料找不到、报告与演示对不上、重复录入和不达成无安排等实际问题,不预填改善结果。

## 需要时读取

- [版本材料](../../system-prompt/references/version-records.md):跨树读取、候选、修订、保存、workflow 契约与文本写入要求。
- [会议纪要规范](../../system-prompt/references/meeting-minutes.md):整理或改写纪要前读,共识/遗留条目的内容标准与正反例。
- [旧格式材料](../../system-prompt/references/legacy-materials.md):读回异常、字段对不上或需要迁移时才读;正常流程用不到。
- [会议转写](../../system-prompt/references/meeting-transcript.md):需要按会议 ID 拉取语音转写稿时读,含读取范围、登录与取稿边界。
- [指标](../../system-prompt/references/metrics.md)、[Issue](../../system-prompt/references/issue-state.md):涉及对应事实与远端写入。
- [证据与后续](references/evidence-and-follow-up.md):原承诺歧义、缺材料、指标不可比或不达成项的判断方法。
- [验收证据报告模板](assets/evidence-report-template.md):报告结构与逐 Issue 证据罗列、缺证标注。

失败保留草稿和原来源;先核对仍在运行的任务再重试,不能重复开构建、覆写脏树、伪造新读数或替人确认;缺工具请人安装,不降级绕道。
