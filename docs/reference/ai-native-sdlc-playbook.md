## 一句话主张

代码生成不再是瓶颈,瓶颈是围着代码的那套流程——构建塌缩到小时级,而计划、评审、发布还是人的速度。解法不是加人,是把直线流程改成**环**:AI 嵌在每个环节,人守判断。全文题眼一句(也是全篇与 BW 契合度最高的一句):环一直转,**人的判断在环之上**——和 BW 的「人永远在首尾」是同一句话。

## 贯穿机制:产物链

每个阶段以「提交一份进版本控制的产物」收尾,下个阶段从读这份产物开始:**意图件 → 规格件 → 实施计划 → 带测试的改动 → 带评审结论的 PR → 事故记录**,事故记录又写成新的意图件,环闭合。每份产物有具名的验收人,接受与否用合入/关闭留痕。

**BW 落点**:这就是「仓是正本」的企业版。`.bw/` 件是我们的产物层;**单变更的产物链已由 [`principles/01-document-organization.md`](../../principles/01-document-organization.md) 固化**——特性级变更走仓根 `changes/<id>/`(intent → spec → plan → STATUS,小 bug 直修不开链),本次过程指标变更的三件随 PR #125 迁入 `changes/process-metrics/`。

## 六阶段逐段:主张、关键做法、BW 落点

### 1 · 计划(意图件)

想法不再排队等委员会,发起人和 AI 聊到具体,一次成文进版本控制;产品负责人审,合入即接受。**BW**:运作活①里活草稿必须人确认才建活;活 = 远端 issue,合入 PR 连带完成关闭——接受与否天然留痕。

### 2 · 设计(规格件)

需求与设计压成**一次会话**:AI 读意图件、套上组织写成技能的约束(品牌 / 安全 / 合规),产出规格,**冲突当场标出**而不是几周后评审才发现;跑顺后可由意图件的接受自动触发。**BW**:方法论技能 + 类别→工具→workflow 映射;单人小项目不做重规格层,压进活说明与会话,是有意取舍。

### 3 · 构建

- **先计划后动手**:写码前先让 AI 产出实施计划(改哪些文件 / 顺序 / 什么证明算做完),人改计划比改代码便宜;计划批准前 AI 不许动文件;实现偏离计划时同一提交里把计划改成实况。**BW**:#121,剧本级落地。
- **项目手册当代码维护**:给 AI 的手册只写新人第一天要的(命令 / 约定 / 常错点),保持一页内;**工作规则:同一个错误犯两次,修正就进手册**。**BW**:仓根手册人点头才写;「错两次进手册」回路是 #123。
- **建议性与确定性分层**:技能是建议性约束(让违规变稀有),必须无例外的政策要配确定性拦截(让违规接近不可能)。**BW**:铁律由类型与状态机在**编译期**拦——比运行期拦截更硬,这是 BW 强于 playbook 的一处。
- **并行**:一人多会话、各占一棵 git worktree、互不知晓;重复职责(如「验证应用真能跑」)做成范围受限的子代理。**BW**:每活一 worktree 天生如此。
- **遗留系统**:每类产物指定**唯一事实源**——仓为正本 / 老系统为正本 / 最低限度两边互挂编号。**BW**:拍死了第一种,仓是正本。

### 4 · 测试

给 AI 一条**能自己跑的验证路**(测试 / 构建 / 截图对比),自验通过才交人看,验证输出**原样进 PR 当证据**;修 bug 先让 AI 把 bug 重现成一条失败测试、提交它、再修——且**禁止改测试文件**(用拦截保证)。评测集是 agent 配置的回归测试:手册、技能、拦截的每次改动都该像代码一样被回归。**BW**:「验证证据必须进 MR」进 #122 剧本收尾段;评测集不建(对单人过重),轻量对应 = 技能使用记录现算。

### 5 · 发布

所有 PR 过**同一套评审遍**(bug / 安全 / 与规格计划的一致性),发现按严重度排好,人的注意力抬到「这个改动是不是当初想要的、风险收不收得住」;**写码的 agent 无权批自己的码**;审批门做成确定性拦截,拦下时要自己说明理由和去哪审批;**生产门永远在人手里**——agent 可以做到门前的一切,过不了门。**BW**:#122 评审剧本(建议性,人仍守门);合入与完成人点、Done 唯一入边,状态机锁死。

### 6 · 运维(环闭合)

**检测保持纯脚本零模型**(滚动基线 + 越线规则,版本控制、可单测);越线才唤起 AI,响应分层——轻度只记录、中度只读诊断、重度也**只许开 PR 进评审门或触发预批准的回滚**;诊断写成意图件回流进环;修完补一条评测防同类复发。**BW**:#124 的设计蓝图,与「自动建的活绝不被自动推进」严丝合缝;「指标越线」信号已在 main 落地(读数流水 `.bw/metrics/readings.jsonl` 对 `.bw/metrics.toml` 目标比对),PR #126 补具名理由与判读健壮性。

## 治理哲学四条(适用面最广的提炼)

1. **建议劝、拦截拦,分清哪条必须无例外**——政策的强度要选对执法层。
2. **证据随改动走**:验证输出、评审发现、批准记录都长在 PR 上,**PR 即审计记录**——和 BW「读回为证」同构。
3. **自治按环境分层**,而且**门要先于加速存在**:先立好人守的门,再让自动化提速,顺序不能反。
4. **回滚是最该排练的路径**:自动化敢闭环的前提,是撤退的路真演练过。

## 明确不采纳的(和为什么)

| playbook 内容 | 不采纳的理由 |
|---|---|
| 托管设置 / MDM 管控 | 单人工作台没有「管理员锁住工程师」的关系,违反反命题 |
| 多环境部署梯度、发布授权人 | BW 不管部署 |
| OpenTelemetry 观测栈 | BW 的对应物是 `codehub-cli`/`gh`/`git`/`cat .bw/…` 读回 + 深链证据日志,已经够硬 |
| 评测集进 CI | 对单人项目过重;真要做也是鱼塘里的事 |
