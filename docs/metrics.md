## 逐条 A/B/C 判定与采集理由

### 滞后 · 纳入 workbench 管理的项目数 —— C 类(手填)

- 判据:今天人能从 buddy 项目列表看一眼数出来,「上周三那天的值」还算得出来吗?
  **算不出来**。被管项目清单在 buddy 应用态、不在仓;没接入事件日志。判 B 之前找过:
  仓里没有带时间戳的接入记录接口,`.bw/managed.toml` 是铺底指纹快照、不是追加日志。
  所以是 C 类(压根没有自动采集路径),不是 B 类。
- **能不能写成脚本?** 暂时不能。缺的是 buddy 接入项目时落一条带时间戳的事件
  (最便宜:追加进 `.bw/metrics/readings.jsonl`)。补上就从 C 升 B,再加按周现算脚本就到 A。
- 当前读数:**7**(人·朱宇 2026-08-28 手填,记在账本 worktree `bw/ledger` 的
  `.bw/metrics/readings.jsonl`,不在主检出、不在本分支;同日同一指标只留一行)。
  本周快照照此抄一行。账本由 buddy 点采集时写、agent 不手编。

### 引领 · 每周闭环的 issue 数 —— A 类(可回溯,脚本)

- 判据:`codehub-cli issue list --state closed` 带 `closed_at` 时间戳,带时间戳就有任意一周的
  现算——A 类。判 A 之前确认过:不是只能查「当前 closed 总数」,closed_at 是逐条时间戳。
- 脚本 `.bw/scripts/codehub-closed-issues.py`,本会话(W36)真跑过:
  `--since 2026-07-06 --until 2026-09-07` 出 `W28…W34=0, W35=21, W36=0`。W35 最终 21
  含 7 张取消卡(bw:status:cancelled:#4/#13/#19/#21/#28/#29/#30),真闭环 14。本轮口径
  复审:人确认维持「计所有 closed」不改——取消也算一种闭环结果(活被提出又终结),
  且改口径会让数变小(非为点亮),属定义精度非采集失败。W36 周一刚开、本周尚无
  闭环=0 是真值(采集成功),不是采失败。
- 为什么收这条不收提交数 / MR 合入数:那两条是代码仓指标,workbench 平台本身会记,
  再写一份等于一份数两个正本,故撤。issue 闭环是工作管理类、平台不代记,自己采。
