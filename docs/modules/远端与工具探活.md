# 远端与工具探活(Remote dispatch + 工具注册与探活调度)

> 30 秒导读:这是 buddy MVP 模块设计之一,讲两件互锁的事——issue 正本在远端(codehub/GitHub)怎么读写、怎么按 provider 分发,以及开工工具(终端类 / 本机网页内嵌类)怎么声明、怎么探活。作数。不讲会话/PTY/worktree(模块7 会话与执行)、不讲 Open Design 内嵌标签(模块9)。

## 这个模块是什么

两件互锁的事。一是远端分发层:`Remote` enum 按 provider 把 issue 正本读写、MR 开合、Release、走势时序统一路由到 `gh` 或 `codehub-cli`,调用方只见方法、不见 provider 分支。二是开工工具的声明与探活:工具声明住在项目仓的 `.bw/issue-policy.toml`,探活分三种机制(候选路径 / 版本命令 / 套接字握手),探不通一个字节都不写,如实回灰。

## 数据落哪

issue 正本在 codehub/GitHub 的 issue + 标签(标题=标识,`bw:status:*`/`bw:week:*`/`bw:released:*` 标签=状态/排期/版本,issue closed=Done);工具声明与类别映射在项目仓的 `.bw/issue-policy.toml`。**本地零数据库**——远端读都走 CLI,不留读缓存;探活结果只在内存里走一圈发事件,不落盘。

## 依赖什么

- **上游**:`v4-engine` 的 `tokio_cmd`(Windows conpty / 便携 PTY 起子进程);OS keyring(codehub-cli `auth login` 存的 token,这里不碰);本机 `gh` / `codehub-cli` / `agent` / Open Design 进程(探活靠它们真实在不在)
- **自身**:`Remote` 依赖 `github.rs` / `codehub.rs` 两个臂;`probe` 依赖 `claude_bin.rs` / `open_design.rs` 的资源发现
- **下游**:`bw-v4::app::issue_store`(issue↔标签映射,模块1)经 `Remote` 走远端;`bw-v4::app` 的 `run_issue` 开工前置校验经 `agent_for` + `build_startup_plan` 拒不合法工具;走势图(`bw-v4::trend`)经 `merged_mr_times`/`issue_times` 拉原始时刻按周分桶

## 产出与验证

远端读写用 `gh issue view` / `codehub-cli issue view` 直接读回标签与 state 核对;MR 合入后复跑 `mr view` 读回 `state=merged` 才算成功(退出码靠不住,只信读回)。探活:项目墙「测一下」按探活结果显示——装了报版本/地址,没装报灰「未装 · 怎么装」,没接实现报灰「还没接」,**绝不把灰项当红项**。headless 指挥器走 Mock 远端(issue 正文与评论带【mock】字样),不碰 codehub、不碰 `gh`、不碰网关,重跑不产生重复数据。

## 没建什么

- 本地读缓存(MVP 不要,读都走 CLI,卡点认了)
- `welink_cli` 的探活实现(留着位置如实说「还没接」,见 `tools.rs:136`)
- Cursor 的能力清单(Phase 1 未支持,`capabilities=[]` 如实留空,见模板 :21)
- 有状态的 `CodehubClient`(每次调用现带 host/path,省下 per-call `project view` 的优化没做,见 `remote.rs:54` 注释)
- 新增 provider 仍需填一条臂(不是加配置就能跑;但调用方一处不用改,只在 `Remote` 各方法里多一个 match 分支)
