# 技能与蒸馏

> 30 秒导读:这是 buddy 自带技能加载 + 蒸馏的模块设计。自带十份技能编进二进制、开工时摊到 buddy 自己的资产目录,提示词只给名字加一句话加路径,正文 agent 按需读。蒸馏把做完的活提炼成技能、记着来源活——今天没建,按钮灰着。给接手技能这块的人看。现在作数(buddy MVP),设计原文在 `docs/archive/v4-prototype/design.md` §7.4 / §7.5 / §7.8。

## 这个模块是什么(1-2 句)

buddy 自带十份技能(六份方法论 + 四份运作剧本),编译期 `include_str!` 进二进制,开工前摊到 buddy 自己的资产目录 `<asset_root>/skills/`,系统提示词只给 agent「名字 + 一句话 + 完整路径」,正文让它按需读(渐进加载)。蒸馏是活的附属动作——把一件做完的活提炼成带做法的技能,永远记着来自哪件活。

## 数据落哪

buddy MVP 本地零库。十份技能正本编进二进制(`include_str!`),开工时摊到 `<asset_root>/skills/<slug>/SKILL.md`(全局一份,不随项目复制)。活挂的 workflow 名在 codehub issue 正本上;「用过几次」每次现查 issue 列表聚合,不落表、不缓存。产出的系统提示词是一次性字符串,经 `--append-system-prompt` 送进 CLI,不落盘。蒸馏产出(未建)设计上直接写进项目仓的技能目录,不落库。

## 依赖什么

内核内:`crate::standard::skills`(技能包表)、`crate::standard::CORE_TEMPLATES`(段③规范索引,但拼装归模块4)、`super::ops::skill_slug`(workflow→slug)、`v4_engine::LaunchPlan`(`--add-dir`)、Issue 模型(`workflow`/`kind` 字段)。外部:无数据库、无网络。设计依据见 `docs/archive/v4-prototype/design.md` §7.4(workflow 是 SOP 技能包,识别规则扫目录现场判、不建登记表)、§7.5(两批技能两个地方,自带的不进用户仓)、§7.8(蒸馏)。

## 产出与验证

- **产出**:摊到 `<asset_root>/skills/` 的十份 `SKILL.md` + 进提示词的「名字+一句话+路径」索引。
- **验证**:`crates/bw-v4/src/app/mod.rs:207-214` `agent_briefing` 只读预览口子——和真开工走同一个 `agent_system_prompt`,显示什么 agent 就收到什么(试点第一天用户问「我看没有技能路径」,路径其实一直在,只是终端看不见,这个口子为它开的)。`ensure_skill_assets` 写不下返回 `None`,段④如实省略不编路径(`mod.rs:169`)。活挂的 workflow 名在技能目录里找不到 → `skill_pointer` 返回 `None` → 段④如实跳过,活照常能开工(design.md §7.9)。配置屏「不在册」那类如实列出,不假装存在。
- **蒸馏**:V1/V2 已用真实数据跑通,buddy MVP 只搬入口、去库那一步——**按钮今天还是灰的,命令没接**(design.md §7.8)。

## 没建什么(如实标 defer)

- **蒸馏**:会话屏顶部「蒸馏」按钮灰着,`crates/bw-v4/src` 里 grep 不到任何 distill/蒸馏 代码,命令未接(design.md §7.8 / §7.10)。设计上是起一次交互式会话、agent 整理成技能草稿、人确认名字/描述/正文、直接产出到项目仓技能目录、来源活写进文件头部,不再落库。
- **workflow 目录扫描识别**:design.md §7.4 写的「扫技能目录、按判据区分包(workflow)还是单技能、找入口技能」那条规则,在 buddy MVP **没有对应实现**——`skill_slug` 只硬编码映射两个运作剧本。仓里 `.claude/skills/` 的扫描(`vm_panels.rs:444`)只列包名、不判包/单技能结构。判据判出来的结构事实不建登记表,这条仍待建。
- **默认 workflow 打包**:`issue-policy.toml` 默认指向 `mattpocock-skills`/`proto-design`,但自带库只打包了那十份,构建类活 workflow 命中 `None`、段④如实省略(详见模块4)。
