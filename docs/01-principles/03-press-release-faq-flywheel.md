- 相关：[`02-working-backwards.md`](02-working-backwards.md)（方法）、[`../architecture.md`](../architecture.md)（**现行实现**的拆解与工程对照；落后于本文时以本文为主张、以实况为「做到哪」）、[`../hifi/home.html`](../hifi/home.html)（内圈五站的界面长什么样）
- 读者：对外讲清用「新闻稿 + 外部 FAQ」；立项/技术/代价挑战用「内部 FAQ」；选型约束用「飞轮」

> **30 秒导读**：Builders' Workbench 是帮 super builder 用 AI 时代的方式构建产品 / 完成项目的工作台——把一次迭代收成五站同台（项目版本、构建交付、治理、反馈、进化）。**全自动不现实**：早期任务类型还没沉淀成做法时，人在 IDE 里带、AI 在受控轨道上跑能跑的段；跑通的做法沉淀进 `standard/` 随版本分发，下一轮这类任务就能少带你。高效是飞轮转出来的，不是起点假设；能自动跑的范围随做法沉淀越来越大，但永远有新任务类型要从「人机协作」开始。

> **用词**：**站** = 一类任务。一次迭代收成五站：项目版本（立项）、构建交付、治理、反馈、进化 ↺。每站是一类任务——AI 把 `standard/` 覆盖到的段自动跑完，你审结果；没覆盖的人机协作并沉淀。它与工程侧的**门禁**（提交前的检查组，`CONTEXT.md` 里的 Gate checks）不是一回事：门禁由机器跑、管编译期；站由人审结果、管这次迭代要不要往下走。**迭代** = 五站走完一次（对 super builder 通常 1–2 周一次）；本文不再用「转圈 / 周环 / 这一圈」。**做法（best practice）** = 一类任务真实跑通后提炼出来的、可复用的做法；沉淀进 `standard/`（产品方维护、随版本分发），不是某个用户项目里的私有配置。**人机协作** = 人与 AI 协作完成一类任务（与 `standard/` 覆盖到的「自动跑」相对：任务类型没沉淀成做法时走人机协作，跑通、沉淀进 `standard/` 后这类就走自动跑；永远有新任务类型要从人机协作开始）。**沉淀** = 把交互 / 试错里跑通的东西写成知识文档、skill、workflow 配置，让下次同类任务少带。文中把负责执行的 agent 一律叫 **AI**，不再用「队友」。

> **三件事**：你给任务时说清、审结果时对照的三样——**做哪些事**（值不值得做、落不落本周）、**结果长什么样**（必须配能点的原型）、**怎么验收**（操作逻辑写清主路径 / 分支 / 出错怎么办，你点完成才算完）。这三样既是任务的输入也是审结果的清单。不满意时三条路：**反馈重做 / 开 worktree 亲手试 / 认了点完成**。对话和探路都是过程，不是完成——没点完成不算完，改动落 worktree 不碰主仓。

> **分层纪律**：A 新闻稿与 B 外部 FAQ 只写**目标体验**，一律人话，不写实现。**实现怎么做、现在做到哪、怎么防作弊、代价与风险**，全部在 C 内部 FAQ 回答。写特性时不得拿仓里现有的草稿界面当成本文描述的产品形态。

## A. 新闻稿（Press Release）

> 模拟产品「可对内/对外讲清」当天的公告。人话，约一页。技术细节不进正文。

### 标题

**Builders' Workbench：你定方向，AI 跑完能跑的**

### 副标题

给 Super Builder 的 AI 时代工作台。

一个人从想法 own 到运营，叫 super builder。AI 已经能写代码、改方案、跑检查，规划到运维一次迭代一两周走得完。但方向不能外包：做什么、对标谁、成功长什么样、这周推什么，得你定。

Builder 决定项目往哪走、这周推什么；AI 跑完所有能跑的。你在 IDE 里和 AI 共同完成其他的工作——过程沉淀下来，下一次 AI 就能多做一步。每天出现必须你拍板的三件事：做哪些事情，结果长什么样，怎么验收。不满意就在 IDE 里跟 AI 聊到满意；如果发现 AI 能力不足，就在这个 IDE 上开一棵独立 worktree，和 AI 一起完成。你的每一次指导，都会让 AI 更好地完成工作。

「能跑的」不是凭空说的。一类任务能不能自动跑，看做法库 `standard/` 里有没有沉淀出做法：跑通了，下一轮 AI 就多跑一段、你少带一段；还没跑通的，你在 IDE 里带着做，做法慢慢试出来。项目早期、任务新，多带是正常的——这是飞轮的原料。全自动不是起点，是越用越近的方向。

一次迭代收成五站：项目版本、构建交付、治理、反馈、进化 ↺。五站是五类任务——AI 把 `standard/` 覆盖到的段自动跑完，你审结果；不满意就当场聊到满意、正文当场改写；要亲手试就在 Issue 上开一棵 worktree，改动不碰主仓。认了就点完成。

### 如何获得

本机桌面应用（macOS / Windows），执行工作需要本机可用的 AI 命令行工具。当前以内部构建者试用为主，对外分发与签名仍在路上。实际做到哪、哪些还只是主张，见内部 FAQ「现在做到哪」。

## B. 外部 FAQ（客户会问）

> 按角度分五类，每类 ≤7 题。先一张速览，再逐题。

### 速览：五大拷问


| 拷问       | 答案                                                                                                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 谁是客户？    | **Super builder**：一个人端到端 own 产品或项目。不是协作套件里的「全员」。                                                                                                                                                 |
| 痛点 / 机会？ | 方向被代填或留在脑子里；一周一到两次迭代已经可能，人却在搬运和过密审批里耗掉判断力；审结果只给同意 / 退回，商量与亲手试都没地方坐；架构技术债务没有正本；工具假装全自动，落地要么全程靠人机协作要么假自动出事，且没有一层东西讲清「哪类任务能放手、哪类还得人机协作」。                                                                |
| 核心利益？    | **一站式迭代**（你确定目标与范围，五站同台）；**越用越高效**（`standard/` 覆盖到的段自动跑完、你审结果，覆盖不到的人机协作，跑通的做法沉淀进 `standard/` 下一轮少带你）；**能商量也能上手**（审结果时就地对话，或开独立 worktree 亲手试，结论落回这件事）；                                                   |
| 如何知道？    | 行业侧：写代码已非瓶颈，瓶颈在规划 / 评审 / 发布 / 维护；且全自动在真实项目早期不现实，能自动跑的范围要靠做法沉淀长出来。产品侧判断：人审的段要少而准；带过的段要能提炼成 skill，不是永远人机协作。                                                                                      |
| 体验什么样？   | 接入确定目标与范围 → 每版本定目标(周计划自动生成版本计划) → AI 把 `standard/` 覆盖到的段自动跑完，你审结果对照「做哪些事 / 长什么样 / 怎么验收」；没覆盖的人机协作 → 不满意当场聊，或开独立 worktree 亲手试 → 反馈站评哪类卡住（沉淀原料）→ 进化站写本机配置次周期生效 → 和负责架构的 AI 盘技术债务 → 排进下一次迭代；做法随版本进 `standard/`，下一轮少带你。 |


### 一、它是什么，和谁不一样

**这不就是又一块看板吗？和 Jira / Linear 差在哪？**
差在你坐在哪、要点头的地方有多少。Jira / Linear 的主角是 Issue 状态，交棒靠评论和列；派给云端 agent 之后，人还是在列之间搬。这里的主角是一件事从想法走到上线，迭代收成五站：立项切版本 → 构建交付（审结果在这里）→ 治理 → 反馈 → 进化。你每天面对的是自己的判断队列，不是一块全生命周期审批板。

**那不就是 Cursor / Claude Code 外面套一层壳？**
不是。它们是构建段的手，解决「这段代码怎么改」。迭代的瓶颈在手的两边：这件事该不该做、长什么样才算对、架构欠了什么账、下一次迭代改什么。Workbench 管整个迭代，构建段里 `standard/` 覆盖到的自动跑完、你审结果，没覆盖的你在 IDE 里带，跑通的做法沉淀进 `standard/` 下一轮自动跑——不把你按在编辑器里永远旁观打字。把「写代码更快」当成核心利益，是买错产品。

**Lovable / Bolt 已经能从想法到 URL，为什么还要审结果、还说全自动不现实？**
因为 URL 不是运营，检查全绿也不代表这是你要的东西。提示生成应用把人审省光、把「全自动」喊满，落地到真实项目早期要么全程靠人机协作、要么假自动出事。我们是把人审的段**收少**、把「全自动」**说真**：做哪些、长什么样、怎么验收仍要你审、审过才点完成；风险大的仍优先给你看；`standard/` 没覆盖到的任务类型，人在 IDE 里带，带的过程把做法沉淀下来，下一轮才能少带。

**「一站式」是不是六套软件焊在一起？**
不是。一站式 = 一次迭代的最小动作能在台上做完并交棒，你不当搬运工。不自建完整的设计器、编辑器、托管、投放。原型和操作逻辑是规格的一部分，不是另做一套设计产品。

### 二、我每天干什么

**每天该我拍板的「三件事」到底是哪三件？**
**做哪些事**（值不值得做、落不落本周目标）、**结果长什么样**（必须配能点的原型，纯文字不算）、**怎么验收**（操作逻辑写清主路径 / 分支 / 出错怎么办，你点完成才算完）。这三样你给任务时说清、审结果时对照。技术方案默认不来烦你，只有风险大的才优先给你看。其余工作，AI 把 `standard/` 覆盖到的段自动跑完。

**不满意，但说不清该怎么改，只能退回吗？**
不。不满意时三条路：**反馈重做**，或**开一棵独立 worktree 亲手试**。反馈：追问它为什么这么设计、说出顾虑、要它出两个备选、把不要的拿掉；来回几轮换出新方案，正文就地改写，然后你点完成。创建工作树：改动落在挂在这件事上的独立树上，不碰主工作区；试清楚把结论带回这件事。没点完成的东西不会算完成。

**审结果时的对话，会不会最后变成聊天软件？**
差别是对话有归属、有出口。它绑在具体这件事上，不是通用聊天流：隔天回来接着聊不用重交代背景，聊出的结论必须落回这件事的正文，否则等于没聊。会话记录是过程，正文才是正本——下游 AI 照正文执行工作，不去猜你们聊天时的语气。产品要是让你只剩一个大聊天框、什么都靠翻记录，那就做砸了。

**开独立 worktree 不就是又把我按回写代码？和 Cursor 差在哪？**
差在座位和归属。你是从**这件事**上创建工作树，不是另开一个和 Issue 断开的编辑器窗口。树挂在这件事上：干完结论要落回正文，合回与点完成仍要你显式认。默认路径仍是 AI 自动跑能跑的段、你审结果；创建工作树是 escape hatch——聊不够、或大风险必须亲手验证时才用，不是每天主业。

**技术方案我是不是永远不用看？**
默认不用。AI 按你认过的样子自己拆、自己做。只有风险大的才优先送到你面前：动到不可逆的数据、扩大权限与密钥、改变对外承诺、发出去收不回来。什么算风险大由产品判定，不靠 AI 临场觉得「这个是不是该请示一下」——那样要么事事请示，要么从不请示。

**没有大风险时，AI 能不能直接改代码？**
可以——前提是「做哪些事」「长什么样」「怎么验收」你都定了，且这类任务 `standard/` 覆盖到了、或你在 IDE 里带着干。样子没定就动代码，不行；该优先看的风险没看、或你还没点完成就往下做，也不行。去掉的是「每份方案都得等人」，不是「什么都没定也能动手」。

**AI 说全绿了，我还要干什么？**
绿的是它自己给自己的检查，不能替你点完成，也不能替你审「做哪些事」「长什么样」「怎么验收」，也不能把架构技术债务涂绿，更不能把 `standard/` 没覆盖的任务说成「自动跑通了」。你的工作仍是：确定目标与范围、审那三样、和负责架构的 AI 把技术债务排进下一次迭代、把卡住的任务类型反馈上去沉淀。全绿却跳过审结果、或让模板代填周目标、或把需要人机协作的工作藏起来假装全自动，比没有工作台更危险，因为假完成会进真实用户。

### 三、飞轮：自动跑 vs 人机协作

**不是说自动跑吗，为什么我早期还要在 IDE 里带这么多？**
因为「能自动跑」是分任务类型的，看 `standard/` 里有没有沉淀出做法。项目早期、文档不全、任务类型新，`standard/` 还没覆盖到，人就得在 IDE 里带着 AI 干——这是飞轮的起点，不是 bug。带的过程跑通了，做法沉淀进 `standard/`，下一轮这类任务 skill 就能多跑一段、你少带一段。要是工具假装这一段也能全自动、闷头跑出一个你没法验收的东西，那才是真坑。

**还要自己试用吗？和「自动跑」冲不冲突？**
不冲突。自动跑的是 `standard/` 覆盖到的中间段；增量能点的时候你仍应自己走一遍，别扭写成反馈或新意图。试用不是卡在每一步后面的强制审，而是回流的燃料——发现问题就进下一次迭代，而不是拦着 AI 把你已经认过的东西做完。

**沉淀下来的做法是谁的？我项目里的做法会不会被别人用？**
本机就是本机。你在本机试出来的好做法，写成本机 skill / harness 配置，只让下周期的你受益，不上荐、不外流。跨用户共享的 `standard/` 由产品方维护：你反馈哪类任务跑通了、哪类卡住，产品方把**可泛化**的做法提炼进去（去掉项目敏感、做成标准化能力），随版本分发。用户之间共享的是「怎么做这类任务」的标准化能力，**不是**彼此的项目工作区或项目私有做法。要做多人协同一个项目（共享看板、成员、群聊、收件箱），那是另一类产品，先改本文再开 `docs/05-features/`。

**高效体现在哪？**
你的日程是确定目标与范围 + 审结果 + 定期盘架构，不必全程参与执行，也不必逐步审批。`standard/` 覆盖到的段自动跑完；覆盖不到的段你在 IDE 里带，带通就沉淀进 `standard/`，下一轮少带。看着不对就聊，必要时开独立 worktree 亲手试。你反复退回的东西会被记住，下一次迭代少解释一遍。方向和周目标不会被「自动替你想产品」。

**这不就是把我变成瓶颈？一周还怎么迭代得完？**
人审的段少了、能自动跑的段随沉淀变多了，才转得快。确定目标与范围是低频；日常待办只有那三类，风险大的才加塞；`standard/` 覆盖到的段自动跑完、你审结果。真瓶颈是把自动跑的段又做成等你点头，或者把审视架构与技术债务做成每天一场答辩，或者把「全自动」喊满却让人永远靠人机协作。产品要是让你在终端里逐次点「允许」，或者每份方案都排进你的队列，那是设计失败，不是迭代节奏失败。

**五站一周迭代一次，跟不上怪谁？**
先怪产品。标志：没有你确认的周目标却在报进度；没有原型也算规格过了；没有大风险却塞满技术方案；架构全景长期不更新却说技术债务可控；反馈和技术债务写不回下一次迭代；`standard/` 长期不动却报「全自动覆盖」。再怪使用：一律盲过、从不点原型、从不盘架构、从不把卡住的任务类型反馈上去。

**AI 能不能自动帮我写目标和周目标？**
能起草，不能生效。没经你确认的目标视同没定。这与「中间自动跑，但确定目标与范围和审结果不代做」是同一条底线。

### 四、确定目标与范围、架构、可靠

**项目基础信息、发展方向、周目标，是不是在待办里点一下就行？**
不是。那是**确定目标与范围**，和审一件具体的事不是一类。接入时你要回答：做什么、对标谁、成功长什么样；方向变了你改方向；每周要有一句周目标。AI 可以起草候选，正本必须你确认。没有周目标，本周的事无处对齐，应该先拦住你去确定目标与范围。

**为什么规格结果必须配原型和操作逻辑？**
因为纯文字最容易「看起来很完整，做出来不是那回事」。原型让你能点；操作逻辑写清主路径、分支和出错怎么办。缺这两样审结果时直接退回、不许点完成，不许拿「先让 AI 做着」跳过。这是把设计段的最小动作留在台上，而不是把你赶去另一个设计工具再口头对一遍。

**架构全景是什么？谁维护？**
一份跟着代码走的架构说明：系统由哪些部分组成、跑起来怎么交互、代码怎么组织、部署在哪，再配上关键场景。由负责架构的 AI 持续更新，你定期和它一起盘：哪笔技术债务现在还、哪笔先记着。盘出来的结论变成下一次迭代要做的事，不是在待办里多出一列「请批准这份重构方案」。

**人既定产品又盘架构，职责分离还成立吗？**
分离的是**人和 AI**，不是两个工种的人。同一个人可以既定范围又盘架构，但写出这份改动的 AI 不能宣布你的结果已审过，也不能自己把技术债务悄悄勾掉，也不能自己把做法写进 `standard/`。你是审结果和技术债务的主人，`standard/` 由产品方随反馈迭代，它是手。

**数据在哪？要上云吗？**
默认本机。要做什么、长什么样、架构全景、发过哪些版本、回流了什么，正本都落在你自己的代码仓，和代码同一套历史。本机进化的 skill / harness 配置也在本机，不上荐、不外流。AI 用你本机的命令行工具。

### 五、我适不适合，怎么开始

**我很会写代码。为什么不自己打开 IDE 把关？**
你会写代码，是你盘架构、判断大风险、以及必要时开独立 worktree 亲手验证的资格，不是把你拉回全职实现岗。`standard/` 覆盖到的段，自动跑完、你审结果；覆盖不到的段，你在工作台的内嵌终端 / IDE 里带——但这个 IDE 是挂在 Issue 上的，不是另开一个断上下文的窗口。另开一个和 Issue 断开的 IDE，正是这套「少审」要淘汰的断上下文；在这件事上创建工作树则挂在这件事上，合回与点完成仍要显式认。创建工作树是 escape hatch，不是每天主业。

**我不太会写代码，是不是用不了？**
Super builder 仍要 own 后果：发出去的版本、数据、密钥、能不能回滚。你可以少写实现，但不能不定「做哪些事」「长什么样」「怎么验收」，也不能对架构全景里标红的技术债务长期装作没看见。审结果时的原型和操作逻辑应该用人话写清；看不懂风险大的方案就退回去，让 AI 讲明白再来。不适合的人：只想口头说一句「做个 App」，既不定对标和周目标，也不认样子，还指望全自动交付。

**怎么开始？**
安装桌面应用 → 接入项目并确认基础信息 → 定这周目标 → 立项切版本 → AI 起草落在这个目标里的事 → 你审结果对照「做哪些事」「长什么样」「怎么验收」（`standard/` 没覆盖的在 IDE 里带）→ 认过之后看 AI 跑能跑的段；周期性和负责架构的 AI 盘一次技术债务，排进下一次迭代；把卡住的任务类型反馈上去，等做法进 `standard/` 下一轮少带。

## C. 内部 FAQ（硬核挑战 · 实现与现状）

> 本节承接实现质疑：结果怎么审、怎么防作弊、现在做到哪、代价与风险。术语可以用工程话。按角度分五类，每类 ≤7 题。

### 一、现状与边界

**现在做到哪，哪些还只是主张？**
草稿里已有：完成权在人、没数据不装绿、agent 能在真实目录改文件并留运行记录；接入时问对标与成功标准、V4 有周目标链与会话表 / 内嵌终端，issue worktree 供给已在执行路径存在，仍是草稿形态。**尚未交付**：结果审阅主界面（人面对待审结果队列，不是看板）、审结果时的对话（绑制品、续聊、谈定即改写正文）、**「开独立 worktree」探路**（树挂制品、合回 ≠ 点完成）、规格结果缺原型不许点完成、验收结果缺操作逻辑不许点完成、大风险任务标记路由、认过之后中间段真正自动跑完（`standard/` 覆盖判断 + 覆盖到的自动跑 + 人审结果）、架构全景（4+1）正本与「审视技术债务 → 下一次迭代的意图」回流、**反馈站评各环节效率 + 进化站写本机配置次周期生效**、`**standard/` 随版本分发的做法库与「反馈 → 提炼 → 沉淀」回路**。现行主路径仍是项目墙 / 看板 / 建卡开工 / 人点完成，是脚手架，不得对外讲成新闻稿里的形态。签名分发等技术债务写进 architecture 留白或对应 `docs/05-features/`，不另开第二份总表。

**「全自动不现实」是不是给没做到打圆场？**
不是，是一条要写进约束的真话。一类任务能自动跑，看 `standard/` 里有没有沉淀出做法（有可核记录、有出口、可复现）；有 → 自动跑完、人审结果；没有 → 人在 IDE 里带。边界随 `standard/` 增长而移动，只能往「能自动跑」方向长，不能用嘴说「这个能自动」把需要人机协作的工作藏进绿。早期一个新项目、新任务类型，需要人机协作的工作多是飞轮起点，不是故障；但若长期人机协作且从不沉淀、`standard/` 不长，就是产品没转起来，不是「全自动不现实」的开脱。

**全自动化做不到，怎么界定哪些任务能自动跑、哪些要人机协作？**
`standard/` 覆盖到的任务类型，自动跑完、人审结果；覆盖不到的，人在 IDE 里带。边界随 `standard/` 增长而移动，只能往「能自动跑」方向长。判断「覆盖到没」要有可核依据（有做法条目 + 真跑过 + 有出口），不能用嘴说「这个能自动」。新任务类型默认走人机协作，跑通才沉淀——这是飞轮，不是「全自动」的缺口。

**现行看板、开工、人点完成怎么处置？**
脚手架。保留铁律：完成是人点、agent 真改仓、灰灯未知。主界面迁到结果审阅；中间段改为「`standard/` 覆盖到的自动跑完、没覆盖的人机协作并沉淀」；完成键不得冒充规格 / 验收已审过。特性若方案仍是「加一列看板」或「每份方案进队」或「喊全自动却让人全程靠人机协作」，对齐本文驳回。

### 二、结果怎么审 · 怎么防作弊

**审结果时的对话怎么做，才不会退化成聊天流？**
四条约束。（1）**有归属**：会话绑定具体制品（这份 intent / 这份 spec / 这次审视技术债务），不是项目级通用聊天；同一制品可多轮续聊，历史随制品加载，不靠人重新粘上下文。（2）**有出口**：会话的产出必须是**制品修订**——谈定即改写 intent / spec 正文并留下版本痕迹。只有会话记录、正文没动，视为没结论。（3）**对话 ≠ 点完成**：点完成仍是显式动作；禁止用「聊过了」「上面聊过一版」推断已接受。（4）**正本分层**：正文是正本，会话是过程证据；下游自动跑段读正文，不读聊天记录，避免把语气当规格。

**对话与内嵌终端 / 执行会话是同一条东西吗？**
不是同一用途，可共用底座。审结果时的对话是**商量制品**（改文本、出备选、质询设计），默认不落代码改动。**开独立 worktree** 是另一条显式动作：从该制品 / 这件事起一棵隔离工作树，人（可带 AI）在树里改文件、跑检查；用途是亲手验证或探路，不是悄悄合进主工作区。共用执行器与会话存储可以，但三条不得破：（1）创建工作树 ≠ 点完成；（2）树内改动不得自动合回主工作区或自动推进下一步；（3）合回 / 点完成仍须显式认。禁止把「反馈重做」默默打通成改仓——那等于绕过「没点完成主仓不动」。V4 已有会话表、内嵌终端与 issue worktree 供给可作底座，审结果入口形态仍是草稿。

**探路 worktree 怎么防「开了就算过」？**
四条。（1）**有归属**：worktree 绑定具体制品 / 这件事，不是项目级随便开的旁路目录。（2）**有出口**：试清楚后的结论应写回制品正文或作为可核证据；只有工作树改动、正文不动，视为没结论。（3）**创建工作树 ≠ 点完成**：点完成与合回都是显式动作；禁止用「我改过了」「树里绿了」推断已接受。（4）**主仓隔离**：未点完成之前，自动跑段与主工作区不得吃这棵树的改动。escape hatch 用得多到变成主路径（人天天在树里亲自干）→ 产品失败信号，不是特性成功。

**大风险任务怎么标记路由给人，才不退化成事事请示或从不请示？**
产品给可核清单（初值可含：破坏性迁移、权限 / 密钥面扩大、对外契约变更、不可逆发布、跨边界数据流出）。命中则 AI 标记给人优先审；未命中不标记。清单可演进，变更要留痕。**优先级低于规格 / 验收**——那两样缺原型 / 操作逻辑直接退回、不许点完成；大风险只是优先给你看，不阻塞自动跑。禁止「模型自觉重要」当标记条件。

**规格结果缺原型、验收结果缺操作逻辑怎么拦？**
用类型或提交守卫：缺原型附件 / 链接，不许从规格结果点完成；缺操作逻辑段或未经人审，不许从验收结果点完成。口头「就是那个按钮」不算。**这是后审退回**——AI 跑完出结果，审时缺这两样就退回重做，不是先拦着不让跑。现行草稿无此守卫，主张如此。

**没规格就改仓，怎么保证不是提示词自觉？**
保护靠隔离和铁律，不靠前置规格审查：改动落 issue worktree（隔离于主仓）；人审 MR、人合、人点完成；没点完成主仓不动。状态机守的是「没点完成不算完」，不是「没 spec 不许跑」。命中大风险清单而人未审，标记给人但不阻塞跑。这条靠类型或钩子，不靠提示词。

**默认不审实施计划，实施会不会漂出规格？**
会，这是工程要扛的风险。已接受的 spec（含原型与操作逻辑）是基准；自动跑段必须能对照 spec 自检并标出偏差。漂出且命中大风险清单 → 标记给人优先审。漂出但不命中 → 记入架构全景 / 审视技术债务，必要时生成下一次迭代的意图，而不是默默当完成。禁止「做完再补一份好看的 plan」冒充依据。

### 三、沉淀与做法库（飞轮怎么不腐烂）

**本机进化和 shared `standard/` 是一条东西吗？**
不是，严格分开。（1）**本机进化**：你在本机试出来的好做法，写成本机 skill / harness 配置，**次周期的你**受益。本机、本地、不外流、不上荐——本机就是本机。（2）**shared `standard/`**：跨用户的标准化能力库，由**产品方**维护、随版本分发；用户只反馈意见（哪类任务跑通了、哪类卡住），产品方把可泛化的做法提炼进去，去掉项目敏感。两者靠「反馈站」接起来：本机进化 + 反馈是产品方提炼 `standard/` 的原料，但本机做法本身不上荐、不进共享库。禁止把本机做法悄悄上荐外流（用户隐私破），也禁止把 `standard/` 做成用户互相贡献的社区市场（治理面胀、调性破）。

`**standard/` 的条目怎么防「文档坟场 / 模型编的模板」？**
三条。（1）**真跑过**：每条 `standard/` 做法必须有可核的真实运行记录（哪类任务、哪个项目跑通），不是模型凭空编的「最佳实践」。（2）**有出口**：一条做法进 `standard/` 后，下次同类任务真能让 skill 多跑一段、人少带一段；否则不收。（3）**可复现**：有版本、可回退。长期没人真用、或用了没让人少带的条目 = 腐烂指标，要清。禁止用「模型自觉这是最佳实践」当 `standard/` 条目来源；写代码的会话不能给自己写进 `standard/`。

**测试全绿但产品不好用，以谁为准？**
体感与 spec。绿只能证明自动跑段里写过的检查。不好用写成反馈或新意图；禁止用 CI 绿关闭「spec 已兑现」，也禁止用 CI 绿把需要人机协作的工作说成「自动跑通」。修 bug 时禁止改测试取绿。

**Agent 代填基础信息、目标、周目标怎么办？**
起草必须标明草稿；未确认不得据此计算健康信号、不得当正本、不得当对齐基准。铁律，不是文案偏好。同理，agent 不得自行把做法写进 `standard/`——`standard/` 由产品方随反馈提炼，不是 agent 现场编的。

**写代码的和盘架构的是同一个模型，架构全景是不是装样子？**
所以人必须参与审视技术债务确认：哪笔债进下一次迭代、哪笔接受暂缓。负责架构的 AI 可起草视图与候选意图，不能自行宣布债已还清、不能让周目标生效。禁止同一会话改完代码后把开发视图里的债项静默勾掉。写代码的会话不得给自己点完成。

### 四、架构、发版、维护

**架构全景具体是什么？**
Kruchten 4+1：逻辑、过程、开发、物理四视图 + 场景。正本在项目仓，由负责架构的 AI 对照代码持续更新。人读的是「相对上次变了什么、哪笔债建议进下一次迭代」，不是读一篇全量文档。长期无更新却报绿 = 腐烂指标。审视技术债务的产出必须是意图候选，不是又一篇永久 wiki。

**周目标和人审结果如何分工？**
周目标是框。单次意图问：是否服务这句目标。审视技术债务产出的意图同样要对齐框。改目标走确定目标与范围，不走「点完成这份意图」。禁止从完成卡片反推周目标。

**过生产 / 发版还要人吗？**
命中大风险清单的必须标记给人审。常规发版可走自动跑，但要留可核记录，且沿用灰灯规则（无数据 = Unknown，不装绿）。「敢不敢给这批用户」若改变了范围相对周目标的关系，走立项，不塞进技术方案队列。

**维护段：模型诊断 vs 人，谁说了算？**
越线检测尽量确定性脚本（阈值 / 控制带），不用模型决定「有没有事」。模型可起草诊断与新意图。人经立项决定现在修、排期、或关掉并写明为何不是故障；关掉必须留痕，不能用嘴把灯按灭。维护段同样更新过程 / 物理视图。

### 五、风险、代价、度量、定位

**还可能翻车的产品风险？**
待办又被方案和日志塞满；审结果时的对话滑成通用聊天框，结论只在记录里、正文不动，或「聊过」被当成已接受；**开独立 worktree 变成每天主业**，或创建工作树 / 树内绿被当成点完成、有未提交改动的工作树自动合回主仓；规格结果不强制原型；验收结果不强制操作逻辑；大风险标记清单过宽或过窄；4+1 变文档坟场；用第二个 agent 静默点完成；对外把草稿看板讲成已交付；创建流用生成文本冒充用户已定方向；**假装全自动、把早期需要人机协作的工作藏起来或闷头跑出没法验收的东西**；`**standard/` 条目是模型编的不是真跑过、长期没人用却报「覆盖」**；**本机做法被悄悄上荐外流（用户隐私破）**；**把多人协同一个项目塞进 `standard/` 伪装成做法库**；扩大客群到不愿确定目标与范围、不认 spec、也不愿总结人机协作中的经验的人，或做成团队全员收件箱，须先改本文。

**主要技术难点？**
后审状态机（没点完成不算完；大风险标记但不阻塞跑；规格 / 验收缺原型 / 操作逻辑不许点完成）；审结果对话与制品的双向绑定（续聊上下文、谈定即改写正文并留版本痕迹、对话不算点完成）；**探路 worktree**（树挂制品、隔离于主仓、创建工作树 / 合回均 ≠ 点完成）；规格结果缺原型退回、验收结果缺操作逻辑退回；大风险标记清单与自动跑的交接；4+1 与代码对照及「审视技术债务 → 意图」回流；点完成即真正启动下一步；`**standard/` 覆盖判断（有做法条目 + 真跑过 + 有出口）与覆盖到的自动跑、没覆盖的人机协作**；**反馈站评各环节效率 + 进化站写本机配置次周期生效 + 反馈供产品方提炼 `standard/`**。本机终端、灰灯派生、agent 真改仓仍是底座。V3 / V4 只覆盖底座切片。

**成本与代价？**
工程：从「密审每份方案 + 人点完成」收敛到「能跑的自动跑 + 人审结果 + 没覆盖的人机协作并沉淀 + 4+1」，草稿路径让路，不为旧主路径留兼容层。用户：本机 CLI 与配额；必须愿意确定目标与范围、认 spec、认验收、周期性盘架构；**早期任务类型没沉淀时，预期在 IDE 里多带、把做法试出来**——这是飞轮起点，不愿 own 技术后果、也不愿总结人机协作中的经验的人不是客群，不能用「全自动交付」去卖。

**成功怎么量？**
一周内同一张台上：有你确认的周目标；意图与带原型的 spec 被真审过、验收被人点完成；`standard/` 覆盖到的段自动跑完而无需密审方案、没覆盖的段人机协作并产出沉淀原料；4+1 有更新或明确「无变化」记录；至少一笔技术债务 / 体感回流成下一次迭代的意图；全部仓内可核。正向信号还包括：审结果时聊过的制品有对应正文修订（谈定→改写的转化率）；`**standard/` 覆盖的任务类型数随版本涨、需要人机协作的工作随版本缩短**；反馈站真评出哪类卡住、并用于改进 `standard/` 提炼。**反指标**：无大风险却高频方案入队、无原型仍算规格过了、验收没人认却报完成、代填目标未确认却生效、4+1 长期不动却报绿、盲过留痕率为零、会话轮次涨而正文修订数不涨（聊了不落）、`**standard/` 条目长期无真实调用却报「覆盖」、假自动率（把需要人机协作的工作说成自动跑）**、本机做法上荐率不为零（隐私破）。不设公开营收 KPI。

**我们会不会做成带 AI 的 GitHub 或又一条审批流？**
若主路径变成「每 PR 必审」或「去托管网站点完成再回来点一下」，就是做成了。目标主路径：人审结果（规格 / 验收 / 大风险优先）→ `standard/` 覆盖到的自动跑、没覆盖的人机协作并沉淀 → 4+1 审视技术债务回流意图 → 反馈站评估效率、总结经验。GitHub / codehub 是仓与合入的执行面，可以是正本所在，不是人每天的主座位。

**为何不是云多人协作？**
假设 1 个 Super builder + Agent Loop（含负责架构的 AI）。他人可靠同一代码仓审和合，不在产品里建成员、群聊、全员收件箱。多人审批流是另一类产品，先改本文再开 `docs/05-features/`。**注意区分**：被拒的是「多人协同一个项目」（共享看板 / 成员 / 群聊 / 收件箱 / 审批队列）；保留的是「跨用户共享一个做法库 `standard/`」——用户各自独立项目，共享的是「怎么做这类任务」的标准化能力，不是彼此的项目工作区或项目私有做法，且 `standard/` 由产品方维护、用户做法不上荐、只反馈意见。这两件事不同，不混。

## D. 飞轮（The Flywheel）

两个圈：**内圈**是单用户在本机本项目上 1–2 周转一次的迭代（[`docs/hifi/home.html`](../hifi/home.html) 画的五站）；**外圈**是产品级、跨用户、随版本分发的做法沉淀。内圈的「反馈」+「进化」是外圈的原料；外圈的 `standard/` 分发下去，让内圈「构建·交付」站里需要人机协作的工作减少。

```text
═══════════════════════════════════════════════════════════════════
  内圈（单用户 · 1–2 周一次 · 本机本项目）
═══════════════════════════════════════════════════════════════════

  ┌───────────────┐      ┌───────────────┐      ┌──────────────┐
  │ 项目版本          │ ───▶ │ 构建·交付     │ ───▶ │ 治理         │
  │ 项目背景/知识 │      │ IDE/harness/  │      │ 代码结构/文档│
  │ 文档/issue    │      │ skill + SDLC  │      │ 结构/一致性  │
  │ + 版本切片    │      │ SDLC 开发活动      │      │ + 架构全景   │
  └───────────────┘      └───────────────┘      └──────────────┘
                                    │
                                    ▼
                          ┌───────────────┐      ┌──────────────┐
                          │ 反馈          │ ───▶ │ 进化  ↺      │
                          │ 立项/构建/    │      │ 本机优化     │
                          │ 交付效率      │      │ skill/harness│
                          │（沉淀原料）   │      │ 次周期生效   │
                          └───────────────┘      └──────────────┘
                                                          │
                                    ┌─────────────────────┘
                                    ▼
                              （回到项目版本，下一轮）

  ┄┄┄┄┄ 人审结果 横切五站 ┄┄┄┄┄┄
     审结果对照：做哪些事（立项）· 长什么样+怎么验收（构建交付）· 审视架构与技术债务（治理）
     大风险优先给人看（优先级低于规格/验收）
     不满意时：反馈重做 / 开 worktree 亲手试 / 认了点完成
     对话和探路都是过程 · 没点完成不算完 · 改动落 worktree 不碰主仓 · 没数据显示未知

═══════════════════════════════════════════════════════════════════
  外圈（产品级 · 跨用户 · 随版本分发）—— 最底端
═══════════════════════════════════════════════════════════════════

  内圈的「反馈」+「进化」是原料（哪类任务已跑通、哪类仍需人机协作）
                    │
                    ▼
  产品方提炼 → 沉淀进 shared standard/（覆盖更多任务类型）  ◀──┐
                    │                                          │
                    ▼                                          │
  越多 super builder 愿用（standard/ 覆盖到的段自动跑完）     │
                    │                                          │
                    ▼                                          │
  更多用户 → 更多反馈                                        │
                    │                                          │
                    └──────────────────────────────────────────┘
                    │
                    ▼
  standard/ 随版本分发 → 内圈「构建·交付」站里需人机协作的工作减少 ── 回到内圈
```

**飞轮检验（任何特性级变更都要答）：**
它加强的是上面哪一截？内圈（人定的框 / 五站迭代 / 人审结果 / 审结果时聊或创建工作树探路 / 自动跑完能跑的段人审结果 / 审视架构与技术债务回流），还是外圈（做法沉淀进 `standard/` / 覆盖更多任务类型 / 更多用户更多反馈）？
会不会把人拽回「盯终端、拖卡片、当搬运工」，或「每份方案、每处改动都要点头」，或「好方案聊出来了 / 试出来了却要手工搬回 Issue」，或「让模板与 agent 代填方向和周目标」，或「开独立 worktree 变成每天主业」？
会不会破坏这几条：做哪些事与长什么样、怎么验收必须人审、审过才点完成 / 聊过不等于点完成、谈定必须落成正文修订 / 创建工作树不等于点完成、树内改动不得自动合回主仓 / 没点完成主仓不动 / 大风险标记给人但不阻塞跑 / 没数据显示未知 / 写代码的 AI 不能给自己点完成 / 定时只建队列、不代做判断或确定目标与范围 / `**standard/` 条目必须真跑过、有出口、可复现，不是模型编的模板** / **本机做法不上荐、不外流** / `**standard/` 由产品方维护、不做用户互相贡献的社区市场**？
说不清、削弱上面任一条、做成团队协同云、六套车间并集或密审批流、或喊「全自动交付」却让人全程靠人机协作 → 立项应驳回或拆小。
