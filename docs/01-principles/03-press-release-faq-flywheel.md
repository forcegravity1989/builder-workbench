> **30 秒导读**：Builders' Workbench 给**组织里带一条产品线、要向 Leader 汇报的 Builder**。这类人同时要两样：**高效**（AI 把能跑的跑完，人少搬运、少带）和**负责**（承诺能被评审、交付能逐项核对、数字信得过）。产品在三个要向 Leader 交代的时刻兑现这两样——**定承诺、交结果、看实况**——并坚持一条：**交代是干活的副产品**，不另做材料、不手填数字。底下有两层：执行底座继承 Orca（隔离并行地干）；上下文底座由 BW 自建（让模型读懂项目，同一份上下文也让 Leader 能核对）。全自动不现实：没沉淀成做法的任务由人带着做，跑通的做法进 `standard/`，下一轮少带。

> **用词**：**高效** = 对下，Builder 驱动 AI 时少搬运、少记账、少带；**负责** = 对上，结果能被没在会话里的 Leader 核对。**代表用例** = Builder 要向 Leader 交代的三个时刻：定承诺（版本开始）、交结果（版本结束）、看实况（随时）。**上下文底座** = 项目身份、度量口径、版本承诺、交付事实、项目知识，以及把它们送到模型的提示与 Skill；对外不单独作为卖点。**执行底座** = 继承 Orca 的执行机制（worktree、终端、会话、任务、定时、资源管理器与 Diff）。**站** = 一类任务；一次迭代收成五站：项目版本（立项）、构建交付、治理、反馈、进化 ↺，是长期目标旅程。它与工程侧的**门禁**（提交前的检查组，见 `CONTEXT.md`「gate / 门禁」）不是一回事。**迭代** = 五站走完一次，通常 1–2 周，跟组织节奏走。**做法（best practice）** = 一类任务真实跑通后提炼出来的、可复用的做法；沉淀进 `standard/`（产品方维护、随版本分发）。**人机协作** = 任务类型没沉淀成做法时，人与 AI 协作完成。文中把负责执行的 agent 一律叫 **AI**。

> **三件事**：你给任务时说清、审结果时对照的三样——**做哪些事**（值不值得做、落不落本版）、**结果长什么样**（必须配能点的原型）、**怎么验收**（操作逻辑写清主路径 / 分支 / 出错怎么办，你点完成才算完）。这三样既是任务的输入，也是向 Leader 交代的依据。不满意时三条路：**反馈重做 / 开 worktree 亲手试 / 认了点完成**。对话和探路都是过程，不是完成——没点完成不算完，改动落 worktree 不碰主仓。

> **分层纪律**：A 新闻稿与 B 外部 FAQ 只写**目标体验**，一律人话，只讲高效与负责。**实现怎么做、上下文底座、现在做到哪、怎么防作弊、代价与风险**，全部在 C 内部 FAQ 回答。写特性时不得拿仓里现有的草稿界面当成本文描述的产品形态。

## A. 新闻稿（Press Release）

> 模拟产品「可对内/对外讲清」当天的公告。人话，约一页。技术细节不进正文。

### 标题

**Builders' Workbench：做得快，也交代得清**

### 副标题

给组织里带一条产品线的 Builder 的 AI 时代工作台。

AI 已经能写代码、改方案、跑检查，一个人带一条产品线、一两周走完一个版本已经可能。但你仍要向 Leader 交代：这一版承诺了什么、做成了没有、项目有没有在变好。今天这件事很贵——会前另写材料，数字靠手填，会上再口头对一遍；AI 报的「全绿」也不能直接拿去交代，因为没人能核对它对着什么绿。

Workbench 在三个要交代的时刻帮你。**定承诺**：版本开始时，你带着 Leader 的要求、用户反馈和项目现状，和 AI 把这一版的 Top3 目标说清楚——做什么、长什么样、怎么验收；评审会上 Leader 直接在页面上改，定下来就落成真实任务。**交结果**：版本结束时，AI 在干活时顺手把证据和包备好，你逐个目标对照、自己下结论，没做到的写清下一步，纪要直接从目标生成。**看实况**：任何时候，进展和指标都从真实数据算出来，没数据就显示未知，不装绿。

交代用的东西都是干活顺手留下的，不用另外记账。方向和完成永远由你定：AI 可以起草目标，不能替你定；检查全绿，也要你点完成才算完。每一版的承诺和结论都留在项目里，下一版 AI 不用你重新交代背景；带着 AI 跑通的做法沉淀下来，下一轮你少带一段。

### 如何获得

本机桌面应用（macOS / Windows），执行工作需要本机可用的 AI 命令行工具。当前以内部构建者试用为主，对外分发与签名仍在路上。实际做到哪、哪些还只是主张，见内部 FAQ「现在做到哪」。

## B. 外部 FAQ（客户会问）

> 按角度分五类，每类 ≤7 题。先一张速览，再逐题。

### 速览：五大拷问与代表用例

| 拷问 | 答案 |
|---|---|
| 谁是客户？ | **组织里带一条产品线、要向 Leader 汇报的 Builder**：自己定方向、带 AI 交付，同时要对结果负责。Leader 是评审者和读者，不是产品成员。 |
| 痛点 / 机会？ | 执行已经交给 AI，但交代的成本没降：目标说不清怎么验收，交付时没东西可对照；会前另写材料、数字手填；AI 的「全绿」没法核对；模型每次都要重新交代项目背景。 |
| 核心利益？ | **高效**：AI 跑完能跑的，你少搬运、少记账、少带。**负责**：承诺能被评审，交付能逐项核对，数字信得过，完成由你确认。两样同时成立——交代是干活的副产品。 |
| 如何知道？ | 行业侧：写代码已非瓶颈，瓶颈在定目标、评审、交付与维护；全自动在真实项目早期不现实。用户侧：试用中的版本计划与验收按真实的 Leader 评审会、周五出包与 showcase 节奏提出要求（如「目标变成任务清单」「会议纪要重复填写」「模型把仓内不完整信息当全部事实」），交代成本是被反复提出的痛点。 |
| 代表用例？ | **定承诺**（版本开始，定可验收的 Top3 目标并经 Leader 评审）、**交结果**（版本结束，逐目标对照证据下结论并归档）、**看实况**（随时，进展与指标从真实数据现算，没数据是未知）。 |
| 体验什么样？ | 接入项目、确认方向与北极星 → 定承诺：和 AI 澄清目标、Leader 评审、落成任务 → 版本内 AI 隔离并行地干，你审结果对照「做哪些事 / 长什么样 / 怎么验收」 → 交结果：备证据、出包、逐目标下结论、未达写下一步、归档 → 随时看实况 → 下一版从上一版的结论接着来。 |

### 一、它是什么，和谁不一样

**和 Orca 差在哪？**
Orca 解决「一个人能同时驾驭多少条 agent 线」：每件事一个独立工作区、统一面板、改动审完合回。这些能力 Workbench 都有。差在要判断的对象：Orca 让你判断一份改动合不合；Workbench 让你判断一版承诺兑现了没有，并且能把这个判断交代给 Leader。并行留在执行层，到版本承诺这一层收敛——每版聚焦 Top3 目标，多开几条 agent 线不会让要交代的东西翻倍。

**这是不是又一套汇报系统？**
不是。汇报系统要你另外填；这里交代用的东西是干活顺手留下的：目标在定承诺时就写成了 Leader 看得懂的样子，证据在交付时就备好，纪要从目标直接生成，指标由脚本从真实历史算出来。如果用了它反而要多写一份周报、多填一张表，就是产品做砸了。

**这不就是又一块看板吗？和 Jira / Linear 差在哪？**
差在主角。Jira / Linear 的主角是 Issue 状态，交代靠你把状态翻译成结论。这里的主角是版本承诺：一版要兑现什么、证据在哪、结论是谁下的。Issue 仍是任务的真实状态，但你向 Leader 交代的是承诺兑现，不是一列卡片。

**那不就是 Cursor / Claude Code 外面套一层壳？**
不是。它们是构建段的手，解决「这段代码怎么改」。瓶颈在手的两边：这件事该不该做、长什么样才算对、做完怎么证明做对了。Workbench 让 AI 有足够的项目背景去帮你把这两边做好，也让结果能交代。把「写代码更快」当成核心利益，是买错产品。

**Lovable / Bolt 已经能从想法到 URL，为什么还要审结果、还说全自动不现实？**
因为 URL 不是交付，检查全绿也不代表这是 Leader 要的东西。我们是把人审的段**收少**、把「全自动」**说真**：做哪些、长什么样、怎么验收仍要你审、审过才点完成；没沉淀成做法的任务，你带着 AI 做，做法沉淀下来，下一轮才能少带。

**「一站式」是不是六套软件焊在一起？**
不是。一站式 = 一个版本从定承诺到交结果的最小动作能在台上做完，你不当搬运工。不自建完整的设计器、编辑器、托管、投放、发布平台。原型和操作逻辑是规格的一部分，不是另做一套设计产品。

### 二、三个要交代的时刻

**定承诺时我做什么？**
带着场外要求来：Leader 口头提的、用户反馈的、你自己判断的。AI 先问只有你知道的事，再帮你把目标说清楚——做哪些事、长什么样、怎么验收、看哪个指标。评审会上 Leader 在同一页面直接改；你确认范围后，AI 才创建或更新真实任务。AI 可以起草，不能替你定框。

**为什么「定可验收的目标」值得一个产品帮忙？**
因为它本身就难。一个能验收的目标要同时知道项目往哪走、怎样算变好、上一版做成了什么、Leader 这次在意什么。前三样项目里可以留下来，AI 自己能读；最后一样只在你脑子里，AI 必须开口问。目标说不清，交结果时就没东西可对照，前面跑得再快也交代不了。

**交结果时我做什么？**
上午和 AI 一起备交付：包、证据、实测指标都对着同一个候选版本。下午 showcase，逐个目标看材料、下结论——达成、未达或待核，没做到的写清下一步。纪要从目标直接生成，归档后随时能回看。AI 和定时任务都不能替你下结论。

**看实况看的是什么？**
项目方向、北极星、各特性的引领与滞后指标，以及提交、合入、开放 Issue 的趋势；多个项目一眼扫过时（你自己，或 Leader 周一扫一遍），每张卡只给版本、承诺进展、在跑会话、待审 PR 几个读数，判断与催办归人。都是从真实数据现算的，没数据显示未知，不是绿；零、未知、失败分得开。需要新指标时，和 AI 一起把口径和取数方式补上，不靠每天记账。

**Leader 要不要也装一套？**
可装可不装。Leader 可以用同一套视图扫项目墙和总览，也可以只在评审会上看你的页面、直接改，会后读归档的纪要。无论哪种，Leader 是评审者和读者，不是产品里的成员——不为 Leader 另建角色、成员、群聊、收件箱和审批队列，页面也不替 Leader 下结论。

**AI 能不能自动帮我写目标？**
能起草，不能生效。没经你确认的目标视同没定，不能拿去算进展，也不能拿去向 Leader 交代。

### 三、两次交代之间我干什么

**每天该我拍板的「三件事」到底是哪三件？**
**做哪些事**（值不值得做、落不落本版目标）、**结果长什么样**（必须配能点的原型，纯文字不算）、**怎么验收**（操作逻辑写清主路径 / 分支 / 出错怎么办，你点完成才算完）。这三样你给任务时说清、审结果时对照，也是交结果时向 Leader 交代的依据。技术方案默认不来烦你，只有风险大的才优先给你看。

**不满意，但说不清该怎么改，只能退回吗？**
不。**反馈重做**：追问它为什么这么设计、说出顾虑、要它出两个备选；来回几轮换出新方案，正文就地改写，然后你点完成。**开一棵独立 worktree 亲手试**：改动落在挂在这件事上的独立树上，不碰主工作区；试清楚把结论带回这件事。没点完成的东西不会算完成。

**审结果时的对话，会不会最后变成聊天软件？**
差别是对话有归属、有出口。它绑在具体这件事上：隔天回来接着聊不用重交代背景，聊出的结论必须落回这件事的正文，否则等于没聊。会话记录是过程，正文才是正本——下游 AI 照正文干活，Leader 照正文核对。

**开独立 worktree 不就是又把我按回写代码？**
差在座位和归属。你是从**这件事**上创建工作树，不是另开一个和任务断开的编辑器窗口；干完结论要落回正文，合回与点完成仍要你显式认。默认路径仍是 AI 跑能跑的、你审结果；创建工作树是 escape hatch，不是每天主业。

**技术方案我是不是永远不用看？**
默认不用。只有风险大的才优先送到你面前：动到不可逆的数据、扩大权限与密钥、改变对外承诺、发出去收不回来。什么算风险大由产品判定，不靠 AI 临场觉得「这个是不是该请示一下」。

**AI 说全绿了，我还要干什么？**
绿的是它自己给自己的检查，不能替你点完成，不能替你审那三件事，也不能把没沉淀成做法的任务说成「自动跑通了」。全绿却跳过审结果、让模板代填目标、或把需要人机协作的工作藏起来假装全自动，比没有工作台更危险——你会拿着假完成去向 Leader 交代。

### 四、越用越省力

**不是说 AI 跑完能跑的，为什么我早期还要带这么多？**
因为「能跑」是分任务类型的，看 `standard/` 里有没有沉淀出做法。项目早期、文档不全、任务类型新，就得你带着 AI 干——这是起点，不是 bug。带的过程跑通了，做法沉淀下来，下一轮这类任务你少带一段。

**为什么用久了会更省力？**
两个原因。一是项目本身被记住了：每一版的承诺、结论和指标口径都留在项目里，下一版 AI 从这里接着帮你，不用你重新交代背景。二是做法被记住了：跑通的做法沉淀成可复用的能力，同类任务下一轮少带你。

**沉淀下来的做法是谁的？我项目里的做法会不会被别人用？**
本机就是本机。你在本机试出来的好做法，写成本机 skill / harness 配置，只让下周期的你受益，不上荐、不外流。跨用户共享的 `standard/` 由产品方维护：你反馈哪类任务跑通了、哪类卡住，产品方把**可泛化**的做法提炼进去，随版本分发。共享的是「怎么做这类任务」，**不是**彼此的项目或项目私有做法。

**还要自己试用吗？和「AI 跑完能跑的」冲不冲突？**
不冲突。增量能点的时候你仍应自己走一遍，别扭写成反馈或新意图。试用不是卡在每一步后面的强制审，而是下一版的原料。

**这不就是把我变成瓶颈？**
人审的段少了、能自动跑的段随沉淀变多了，才转得快。定承诺和交结果各是一个版本一次；日常待办只有那三件事，风险大的才加塞。真瓶颈是把自动跑的段又做成等你点头、把交代做成额外记账、或者喊「全自动」却让人永远在带。

**跟不上怪谁？**
先怪产品。标志：没有你确认的目标却在报进度；没有原型也算规格过了；交结果时要另外整理材料；指标要手填；`standard/` 长期不动却报「全自动覆盖」。再怪使用：一律盲过、从不点原型、从不把卡住的任务类型反馈上去。

### 五、我适不适合，怎么开始

**我很会写代码。为什么不自己打开 IDE 把关？**
你会写代码，是你判断大风险、盘架构、必要时开独立 worktree 亲手验证的资格，不是把你拉回全职实现岗。另开一个和任务断开的 IDE，正好丢掉了 AI 需要的项目背景，也丢掉了交代用的痕迹。

**我不太会写代码，是不是用不了？**
你仍要对结果负责：发出去的版本、数据、密钥、能不能回滚。你可以少写实现，但不能不定那三件事。看不懂风险大的方案就退回去，让 AI 讲明白再来。不适合的人：只想口头说一句「做个 App」，既不定目标也不认样子，还指望全自动交付。

**架构全景是什么？谁维护？**
一份跟着代码走的架构说明：系统由哪些部分组成、跑起来怎么交互、代码怎么组织、部署在哪，再配上关键场景。由负责架构的 AI 持续更新，你定期和它一起盘：哪笔技术债务现在还、哪笔先记着。盘出来的结论变成下一版要做的事。

**人既定产品又盘架构，职责分离还成立吗？**
分离的是**人和 AI**，不是两个工种的人。写出这份改动的 AI 不能宣布你的结果已审过，不能自己把技术债务悄悄勾掉，也不能自己把做法写进 `standard/`。

**数据在哪？要上云吗？**
默认本机。目标、验收结论、架构全景、发过哪些版本、指标口径，正本都落在你自己的代码仓，和代码同一套历史。AI 用你本机的命令行工具。

**怎么开始？**
安装桌面应用 → 接入项目并确认方向与北极星 → 配好要看的指标 → 定承诺：和 AI 定这一版的 Top3 目标，Leader 评审后落成任务 → 版本内 AI 跑能跑的、你审结果 → 交结果：逐目标下结论并归档 → 下一版从这里接着来。

## C. 内部 FAQ（硬核挑战 · 实现与现状）

> 本节承接实现质疑：价值结构、上下文底座、结果怎么审、怎么防作弊、现在做到哪、代价与风险。术语可以用工程话。按角度分五类，每类 ≤7 题。

### 一、价值结构与现状

**价值、用例、底座怎么组织？**
两个价值：**高效**、**负责**。三个代表用例：**定承诺**、**交结果**、**看实况**，每个都必须两头兼顾，见下表。两个底座：**执行底座**继承 Orca（worktree、终端、会话、Tasks、Automations、资源管理器与 Diff；执行机制本身不算 BW 价值）；**上下文底座**由 BW 自建（下一题）。两次交代之间的日常执行分两层：机制归 Orca；其上「审结果对照三件事、对话与探路挂制品、点完成与缺原型守卫、大风险路由」这一层归 BW，服务定承诺与交结果的可交代性，多数尚未交付（见「现在做到哪」）。各特性服务哪个用例或底座，登记在 [`docs/05-features/README.md`](../05-features/README.md) 的特性矩阵。

| 用例 | 高效体现在 | 负责体现在 | 成功判据 |
|---|---|---|---|
| 定承诺（版本开始） | 模型帮着澄清，不在聊天、会议材料和任务列表之间搬运 | 承诺写成 Leader 能评审的样子，可追溯到任务 | Leader 不翻聊天就能看懂这版承诺了什么 |
| 交结果（版本结束） | 证据随干活备齐，出包对接流水线，纪要从目标派生 | 每个目标有证据和人下的结论，未达有安排 | 验收者能逐目标核对，未达项有明确下一步 |
| 看实况（随时） | 读数现算，不写周报、不记账 | 可独立复算；零、未知、失败可区分 | 各界面对同一指标口径一致，缺数据显示未知 |

五站是长期目标旅程：定承诺落在「项目版本」站，交结果落在「构建交付」站的收尾，看实况给「反馈」站提供读数；「治理」「进化」两站目前没有已接线的用例。

**上下文底座是什么？为什么对外不讲？**
模型要最大限度帮 Builder，必须有足够的项目上下文；同一份上下文也是 Leader 核对的依据——**模型能读懂的项目，就是 Leader 能核对的项目**，投入一份、回报两份。分层：

| 层 | 回答什么 | 谁产生 |
|---|---|---|
| 项目身份 | 是什么、对标谁、往哪走、北极星 | 接入时人确认 |
| 度量口径 | 怎样算变好；特性的引领 / 滞后指标与可回溯脚本 | 人确认口径，模型补脚本 |
| 版本承诺 | 这版要什么、怎么验收 | 人和模型定，Leader 评审 |
| 交付事实 | 做成了什么、证据在哪、结论是谁下的 | 人下结论；归档后成为下一版输入 |
| 项目知识 | 架构、设计、文档 | 平时维护 |
| 送达模型 | 按需把以上交给模型 | 产品方维护的 `standard/` 提示与 Skill，渐进加载 |

模型可自取的只是仓内能沉淀的部分；Leader 的口头要求、组织优先级、场外约束只在人脑子里，模型必须先问、不得把仓内不完整信息当成全部事实。用户买的是结果，不为「上下文」本身付费，所以对外只讲高效与负责；上下文底座是内部设计原则。

**新特性怎么判定值不值得做？**
它要么直接服务一个代表用例（且不让高效与负责互相吃掉），要么让项目对模型和 Leader 更可读。两样都不沾就不做。不服务被管项目 Builder、只服务 BW 自身开发的，登记为开发方法资产，讲产品价值时不计入。

**现在做到哪，哪些还只是主张？**
三个代表用例都有特性接线：定承诺 = 版本计划，交结果 = 版本验收（含出包；出包合入后首跑失败已修，GitHub 变体完整受理闭环与安装包传输待补验），看实况 = 总览指标与项目墙读数；接入项目与项目名片、CodeHub 适配已在用。**但三个用例都还没有一次真壳端到端旅程验证**，验收点与旅程证据见各特性 STATUS 与 [`05-features/README.md`](../05-features/README.md)；知识库仍含演示数据，给模型提供了什么上下文、能否在定承诺中真正用上尚未定义。**尚未交付**：结果审阅主界面（人面对待审结果队列）、审结果对话与制品双向绑定、「开独立 worktree」探路挂制品、规格缺原型 / 验收缺操作逻辑不许点完成的守卫、大风险标记路由、`standard/` 覆盖判断与覆盖到的自动跑、架构全景（4+1）与技术债务回流、反馈站评效率与进化站写本机配置、`standard/` 随版本分发的「反馈 → 提炼 → 沉淀」回路。未建的不得对外讲成新闻稿里的形态。

**「全自动不现实」是不是给没做到打圆场？怎么界定哪些能自动跑？**
不是，是一条要写进约束的真话。`standard/` 覆盖到的任务类型（有做法条目 + 真跑过 + 有出口），自动跑完、人审结果；覆盖不到的，人带着做。边界随 `standard/` 增长而移动，只能往「能自动跑」方向长，不能用嘴说「这个能自动」把需要人机协作的工作藏进绿。若长期人机协作且从不沉淀，就是产品没转起来。

### 二、结果怎么审 · 怎么防作弊

**审结果时的对话怎么做，才不会退化成聊天流？**
四条约束。（1）**有归属**：会话绑定具体制品（这份 intent / spec / 这次验收），不是项目级通用聊天；同一制品可多轮续聊，历史随制品加载。（2）**有出口**：会话的产出必须是**制品修订**——谈定即改写正文并留下版本痕迹；只有会话记录、正文没动，视为没结论。（3）**对话 ≠ 点完成**：点完成仍是显式动作。（4）**正本分层**：正文是正本，会话是过程证据；下游自动跑段读正文、Leader 核对正文，不读聊天记录。

**对话与内嵌终端 / 执行会话是同一条东西吗？**
不是同一用途，可共用底座。审结果时的对话是**商量制品**，默认不落代码改动。**开独立 worktree** 是另一条显式动作：从该制品起一棵隔离工作树，人（可带 AI）在树里改文件、跑检查。共用执行器与会话存储可以，但三条不得破：（1）创建工作树 ≠ 点完成；（2）树内改动不得自动合回主工作区或自动推进下一步；（3）合回 / 点完成仍须显式认。

**探路 worktree 怎么防「开了就算过」？**
四条。（1）**有归属**：worktree 绑定具体制品，不是随便开的旁路目录。（2）**有出口**：结论写回制品正文或作为可核证据。（3）**创建工作树 ≠ 点完成**：禁止用「我改过了」「树里绿了」推断已接受。（4）**主仓隔离**：未点完成之前，自动跑段与主工作区不得吃这棵树的改动。escape hatch 用到变成主路径 → 产品失败信号。

**大风险任务怎么标记路由给人，才不退化成事事请示或从不请示？**
产品给可核清单（初值可含：破坏性迁移、权限 / 密钥面扩大、对外契约变更、不可逆发布、跨边界数据流出）。命中则 AI 标记给人优先审；未命中不标记。清单可演进，变更要留痕。**优先级低于规格 / 验收**——大风险只是优先给你看，不阻塞自动跑。禁止「模型自觉重要」当标记条件。

**规格结果缺原型、验收结果缺操作逻辑怎么拦？**
用类型或提交守卫：缺原型附件 / 链接，不许从规格结果点完成；缺操作逻辑段或未经人审，不许从验收结果点完成。**这是后审退回**——AI 跑完出结果，审时缺这两样就退回重做，不是先拦着不让跑。现行实现无此守卫，主张如此。没规格就改仓也一样，保护靠隔离和铁律，不靠前置规格审查：改动落 issue worktree；人审 PR、人合、人点完成；没点完成主仓不动。命中大风险清单而人未审，标记给人但不阻塞跑。这条靠类型或钩子，不靠提示词。

**默认不审实施计划，实施会不会漂出规格？**
会，这是工程要扛的风险。已接受的 spec（含原型与操作逻辑）是基准；自动跑段必须能对照 spec 自检并标出偏差。漂出且命中大风险清单 → 标记给人优先审。漂出但不命中 → 记入架构全景 / 审视技术债务，必要时生成下一版的意图，而不是默默当完成。禁止「做完再补一份好看的 plan」冒充依据。

**Agent 代填目标、验收结论、指标读数怎么办？**
起草必须标明草稿；未确认不得据此计算进展或健康信号、不得当正本、不得拿去向 Leader 交代。读数只能从数据推导，没数据就是未知。同理，agent 不得自行把做法写进 `standard/`。测试全绿但产品不好用，以体感与 spec 为准；禁止用 CI 绿关闭「spec 已兑现」，修 bug 时禁止改测试取绿。

### 三、沉淀与做法库（飞轮怎么不腐烂）

**本机进化和 shared `standard/` 是一条东西吗？**
不是，严格分开。（1）**本机进化**：本机试出来的好做法，写成本机 skill / harness 配置，次周期的你受益；不外流、不上荐。（2）**shared `standard/`**：跨用户的标准化能力库，由**产品方**维护、随版本分发；用户只反馈意见，产品方把可泛化的做法提炼进去，去掉项目敏感。禁止把本机做法悄悄上荐外流，也禁止把 `standard/` 做成用户互相贡献的社区市场。

**`standard/` 的条目怎么防「文档坟场 / 模型编的模板」？**
三条。（1）**真跑过**：每条做法必须有可核的真实运行记录。（2）**有出口**：进 `standard/` 后，下次同类任务真能让 skill 多跑一段、人少带一段；否则不收。（3）**可复现**：有版本、可回退。长期没人真用、或用了没让人少带的条目 = 腐烂指标，要清。写代码的会话不能给自己写进 `standard/`。

**项目上下文怎么防腐烂？**
同三条精神：项目身份、指标口径、版本承诺都由人确认才生效；交付事实以归档 PR 合入为准；正式内容读主干，草稿不冒充正本。长期不更新的项目身份或指标目录，在定承诺时应被模型指出，而不是默默当真。

**写代码的和盘架构的是同一个模型，架构全景是不是装样子？**
所以人必须参与审视技术债务确认：哪笔债进下一版、哪笔接受暂缓。负责架构的 AI 可起草视图与候选意图，不能自行宣布债已还清、不能让目标生效。写代码的会话不得给自己点完成。

### 四、架构、发版、维护

**架构全景具体是什么？**
Kruchten 4+1：逻辑、过程、开发、物理四视图 + 场景。正本在项目仓，由负责架构的 AI 对照代码持续更新。人读的是「相对上次变了什么、哪笔债建议进下一版」。长期无更新却报绿 = 腐烂指标。

**版本目标和人审结果如何分工？**
版本目标是框。单次意图问：是否服务这版目标。审视技术债务产出的意图同样要对齐框。改目标走定承诺，不走「点完成这份意图」。禁止从完成卡片反推目标。

**过生产 / 发版还要人吗？**
命中大风险清单的必须标记给人审。常规出包可走自动跑，但要留可核记录，沿用无数据 = 未知。出包不等于正式发布；打 tag、发 Release 由人决定。

**维护段：模型诊断 vs 人，谁说了算？**
越线检测尽量确定性脚本（阈值 / 控制带），不用模型决定「有没有事」。模型可起草诊断与新意图。人决定现在修、排期、或关掉并写明为何不是故障；关掉必须留痕。

### 五、风险、代价、度量、定位

**还可能翻车的产品风险？**
**负责吃掉高效**：交代变成额外记账——另写周报、手填数字、会上再对一遍。**高效吃掉负责**：AI 代填目标、自己点完成、全绿当交付。此外：待办又被方案和日志塞满；审结果对话滑成通用聊天框；开独立 worktree 变成每天主业；规格不强制原型、验收不强制操作逻辑；大风险清单过宽或过窄；4+1 变文档坟场；用第二个 agent 静默点完成；对外把未建能力讲成已交付；创建流用生成文本冒充用户已定方向；`standard/` 条目是模型编的、长期没人用却报「覆盖」；本机做法悄悄外流；把多人协同一个项目塞进 `standard/` 伪装成做法库；把 Leader 做成产品成员、把交代做成审批流。扩大客群到不愿定目标、不认 spec、也不愿总结人机协作经验的人，或做成团队全员收件箱，须先改本文。

**主要技术难点？**
定承诺时模型对项目上下文的取用与「先问人」的边界；交结果时证据、包、指标与目标对同一候选版本；读数可回溯复算、三态可区分；后审状态机（没点完成不算完；大风险标记但不阻塞跑；规格 / 验收缺原型 / 操作逻辑不许点完成）；审结果对话与制品的双向绑定；探路 worktree 隔离；`standard/` 覆盖判断与提炼回路。

**成本与代价？**
工程：上下文底座要持续维护，草稿路径让路，不为旧主路径留兼容层。用户：本机 CLI 与配额；必须愿意定目标、认 spec、认验收；早期任务类型没沉淀时，预期多带。不愿对结果负责、只想「全自动交付」的人不是客群。

**成功怎么量？**
一个版本内同一张台上：定承诺产出 Leader 评审过的 Top3 目标并关联真实任务；交结果对每个目标有证据和人的结论、未达有下一步，纪要不另写；看实况的读数各界面口径一致、可复算；4+1 有更新或明确「无变化」记录；至少一笔技术债务 / 体感回流成下一版的意图；全部仓内可核。正向信号：交代用的材料由工作过程直接生成的比例；下一版定承诺时直接引用上一版结论；`standard/` 覆盖的任务类型数随版本涨、需要人带的工作随版本缩短。**反指标**：交结果前需要另外整理材料、指标靠手填、代填目标未确认却生效、验收没人认却报完成、会话轮次涨而正文修订数不涨、无大风险却高频方案入队、盲过留痕率为零、4+1 长期不动却报绿、`standard/` 条目长期无真实调用却报「覆盖」、假自动率不为零、本机做法上荐率不为零。不设公开营收 KPI。

**我们会不会做成带 AI 的 GitHub 或又一条审批流？**
若主路径变成「每 PR 必审」或「去托管网站点完成再回来点一下」，就是做成了。GitHub / CodeHub 是仓与合入的执行面，可以是正本所在，不是人每天的主座位。

**为何不是云多人协作？Leader 算不算用户？**
假设 1 个 Builder 带一条产品线 + Agent Loop。Leader 是**评审者和读者**：评审会上在 Builder 的页面上直接改，会后读归档 PR、纪要与总览；不在产品里建成员、群聊、全员收件箱、审批队列。团队成员共享 Builder 主机是执行位置的复用，不是多人协同同一项目。Leader 独立入口暂不做；出现真实需求时先改本文再开 `docs/05-features/`。保留的是「跨用户共享一个做法库 `standard/`」，共享的是做法，不是项目。

## D. 飞轮（The Flywheel）

两个圈：**内圈**是单项目 1–2 周转一次的版本迭代，每转一次，项目上下文就厚一层；**外圈**是产品级、跨用户、随版本分发的做法沉淀。内圈的「反馈」+「进化」是外圈的原料；外圈的 `standard/` 分发下去，让内圈里需要人带的工作减少。

```text
═══════════════════════════════════════════════════════════════════
  内圈（单项目 · 1–2 周一次 · 本机本项目）
═══════════════════════════════════════════════════════════════════

  ┌───────────────┐      ┌───────────────┐      ┌──────────────┐
  │ 定承诺        │ ───▶ │ 构建·交付     │ ───▶ │ 交结果       │
  │ 项目版本站    │      │ AI 隔离并行干 │      │ 逐目标核对   │
  │ Top3 + 怎么验收│      │ 人审结果      │      │ 人下结论·归档│
  └───────────────┘      └───────────────┘      └──────────────┘
          ▲                                             │
          │        ┌──────────────────────────┐         │
          │        │ 项目上下文（逐版累积）   │ ◀───────┘
          └─────── │ 身份·口径·承诺·事实·知识 │
                   └──────────────────────────┘
                     ▲ 看实况：读数现算，没数据是未知
                     │
           治理（架构与技术债务）· 反馈（哪类卡住）· 进化（本机配置次周期生效）

  ┄┄┄┄┄ 人审结果 横切 ┄┄┄┄┄┄
     审结果对照：做哪些事 · 长什么样 · 怎么验收 · 大风险优先给人看
     不满意时：反馈重做 / 开 worktree 亲手试 / 认了点完成
     对话和探路都是过程 · 没点完成不算完 · 改动落 worktree 不碰主仓 · 没数据显示未知

═══════════════════════════════════════════════════════════════════
  外圈（产品级 · 跨用户 · 随版本分发）
═══════════════════════════════════════════════════════════════════

  内圈的「反馈」+「进化」是原料（哪类任务已跑通、哪类仍需人带）
                    │
                    ▼
  产品方提炼 → 沉淀进 shared standard/（覆盖更多任务类型）  ◀──┐
                    │                                          │
                    ▼                                          │
  更多 Builder 愿用 → 更多反馈 ─────────────────────────────────┘
                    │
                    ▼
  standard/ 随版本分发 → 内圈里需人带的工作减少 ── 回到内圈
```

**飞轮检验（任何特性级变更都要答）：**

1. 它服务哪个代表用例（定承诺 / 交结果 / 看实况），或让项目上下文对模型和 Leader 更可读？加强的是内圈哪一截（人定的框 / 人审结果 / 审结果时聊或创建工作树探路 / 能跑的自动跑 / 上下文累积 / 架构与技术债务回流），还是外圈（做法沉淀进 `standard/`）？
2. 会不会让负责吃掉高效（交代变成额外记账、另做材料、手填数字），或让高效吃掉负责（模板与 agent 代填方向和目标、代下结论）？会不会把人拽回「盯终端、拖卡片、当搬运工」，或「每份方案都要点头」，或「好方案聊出来了 / 试出来了却要手工搬回任务」，或「开独立 worktree 变成每天主业」？
3. 会不会破坏这几条：做哪些事、长什么样、怎么验收必须人审 / 审过才点完成、聊过不等于点完成 / 谈定必须落成正文修订 / 创建工作树不等于点完成、树内改动不得自动合回主仓 / 没点完成主仓不动 / 大风险标记给人但不阻塞跑 / 没数据显示未知 / 写代码的 AI 不能给自己点完成 / 定时只建队列、不代做判断或确定目标与范围 / `standard/` 条目必须真跑过、有出口、可复现 / 本机做法不上荐、不外流 / `standard/` 由产品方维护、不做用户互相贡献的社区市场 / Leader 是评审者不是产品成员？

说不清、削弱上面任一条、做成团队协同云、汇报系统或密审批流、或喊「全自动交付」却让人全程带 → 立项应驳回或拆小。
