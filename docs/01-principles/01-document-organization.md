# 01 · 知识管理原则与文档组织

> **本篇维护约定**：给调整知识归属、文档边界或清理知识库的人与模型读取。只规定知识管理三原则、整仓分层、特性制品链、正本与投影及共用头部要素；不代写每篇的格式，不列开发命令或变更流水。结构按三原则 → 分层 → 改文档时同步什么 → 正本与投影 → 制品链 → 入口与头部组织；三原则、分层或共用规则经人确认变化时更新。日常维护操作见 [AGENTS](../../AGENTS.md)，各篇具体范围看其头部。

> **30 秒导读**：知识库按三条原则取舍——**少即是多**（每篇都是深文档，过不了删除测试就删或并）、**模糊的正确胜过精确的错误**（写心智模型、约束与取舍，会漂移的精确细节交给代码和 Git）、**定期扫描，一次改好一项**。原则慢变；**特性级**变更走 `docs/05-features/` 制品链，人 gate 是 intent + 带原型的 spec，`plan.md` 仅大风险升 gate；依据齐备的小 bug 直接修、不新立特性，所属特性缺必要文档时按 [02 §6.3](02-working-backwards.md) 补齐并确认。Markdown 是唯一真相，HTML 决策页只是投影。gate 与门禁的区别见 [CONTEXT](../../CONTEXT.md)。

## 0. 知识管理三原则

下面各节的分层、制品链和头部要素都是这三条的落实；某篇文档该不该写、写多少，先回到这里判断。

### 0.1 少即是多：每篇都是深文档

借 [codebase-design](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/SKILL.md) 的深模块说法：一篇文档的**接口**是它的头部——给谁、何时读、管什么；它的**深度**是读者读完后少查了多少地方。好文档接口小、独有价值多；浅文档只是把别处的内容换个说法再讲一遍，读者读完还得去原处核对。

- **删除测试**：设想删掉这一篇或这一段。没人会再问起 → 删；同样的知识会在几处被重新问出、重新写出 → 它在挣自己的位置，留；只是转述别处 → 并回正本，原处留链接。
- 一个事实只有一个正本，其他地方链接不复述。宁可一篇写全，也不拆成互相引用的碎片；不为安放一段内容新建文档，也不为保留空目录造占位文件。
- 删的是重复、转述、过时内容和防御性套话；约束、原因和取舍是深度本身，不为变短删掉。

### 0.2 模糊的正确胜过精确的错误：写心智模型，记录取舍

文档写**不容易变、变了要有人拍板**的东西：职责边界、概念关系、约束，以及为什么这样选、放弃了什么。会随代码和运行漂移的精确细节——条数、行数、文件与字段清单、测试数量、用 PR 号串起来的状态流水、「截至某日」的读数——交给代码、命令、Git 和运行产物当正本，文档只写去哪里取、怎么取。

- 协议值、命令、阈值这类精确值本身就是契约：写明来源，改契约的 PR 同时改文档。
- **记录取舍**：读者可能问「为什么不那样做」的选择，写一句「选 A 不选 B，因为……；代价是……」。模块篇写主要矛盾与取舍（格式见 [06-module](../06-module/README.md)）；难回头的决定写 ADR（放 `docs/02-adr/`），一段话即可；被否决、以后可能再被提起的方案也记一句理由。
- 拿不准就写拿不准：未知写未知，候选写候选，不用精确数字装出确定。

### 0.3 定期扫描，一次改好一项

知识会随代码腐烂，靠定期扫描保持新鲜，不靠一次性全库重写。

- **扫描**：以近期 Git 改动热点定范围，用上面两条做检验（删除测试、漂移细节、缺取舍、重复、断链、没人链接），把候选排成**强 / 值得探索 / 推测**三档，交给人一份候选报告。
- **一次一项**：人挑一项，原文、旧段落去向和入站引用一起改，一个 PR 合入。
- **记下否决**：人否决某项且理由以后还用得上，就把理由写进目标文档的取舍或 ADR；下一轮扫描读到后不再重提。
- 执行方法与扫描脚本在 [project-knowledge](../../.claude/skills/project-knowledge/SKILL.md)。

## 1. 分层与各层边界

口诀：**`01-principles/` 是原则，`05-features/` 是这次变更，`docs/` 其余把产品说清楚（设计 / 决策 / 指南）；仓根只留约定的入口文档。** 路径和读取时机的地图在 [docs/README](../README.md)，本表只管各层回答什么、不写什么。

| 层 | 回答什么 | 变多快 | 不写什么 |
|---|---|---|---|
| 仓根入口（§5.1） | 从哪读、开发规矩、领域词 | 规矩或入口变化时 | 单次变更正本；产品主张 |
| `docs/01-principles/` | 怎么组织知识、产品主张与飞轮、信什么铁律（拍板才改） | 慢 | 单次需求、当周实验、施工日记 |
| `docs/architecture.md` | 整体旅程、逻辑模块、Electron 叠层与数据流（docs 内不编号的设计正本） | 跨模块边界变化时 | 逐文件实现清单、任务历史 |
| `docs/02-adr/`（预留） | 难回头的决定、备选与取舍 | 迁移产生新决策时新增 | 日常小修流水；可随代码漂移的操作细节 |
| `docs/03-guide/`（预留） | 人怎么用、怎么讲（只写已实践） | 真实 Orca 旅程验证后补 | 未上线功能、旧 Rust 操作步骤 |
| `docs/04-design-system/`、`docs/hifi/` | 视觉规范与屏幕原型 | 界面改变时 | 业务规格；原型冒充已交付 |
| `docs/05-features/<id>/` | **特性级**要什么、规格与原型、链状态 | 每个特性一条；小修沿用所属特性 | 为小 bug、文案、琐修另立特性；产品总设计、词表 |
| `docs/06-module/` | 单个模块的实现心智——主要矛盾与取舍 | 模块新增或大改时 | 代码路径、数据字段、没建清单等会漂移的细节 |
| `docs/10-reference/` | 外部资料提炼与历史参考 | 来源变化时 | 当前实现证据 |
| `ref/` | 按需读取的 Orca 工程参考 | 执行核或上游同步时 | BW 产品规格的第二份正本 |

预留目录当前没有文件，有内容时再建，不为占位造文件。本地草稿放 `docs/draft/`（不进仓）。`.claude/skills/` 是 BW 研发方法；`standard/` 给被管项目提供执行规范，被管项目的文档落点遵循它自己的 `AGENTS.md`，术语边界见 [CONTEXT](../../CONTEXT.md)「知识与规范资产」。

## 2. 改文档时同步什么

- 先确认读者、适用任务与正本位置，再决定改哪篇。规则写清约束和原因；产品硬约束不因换模型或追求简短而删除。反复出现的问题先查已有规则和实现，不往入口叠禁令。
- 移动文档、调整职责或改变契约时，同步入口索引、链接与章节引用（包括「见某篇某节」这类普通文字）、示例，以及实际读取这些内容的代码与调用方。文件存在、被链接、被读取、被遵守是四种证据，分别说明。
- 日常新增与小修只检查本次改动和必要引用，不默认全仓审计。变更原因与验证证据留在 commit/PR；当前知识写回正本，不另建提交流水或平行规范。

## 3. 正本与投影

- **正本**：Markdown 及仓内约定的结构化文本。agent 读写、git diff、跨工具同步都以正本为准。
- **投影**：HTML 决策页、扫描报告、应用内决策台，为 gate 与评审提供摘要、风险和证据；从正本生成或引用正本，不当第二份真相。
- **禁止**：把 HTML 当成 intent/spec/plan 的唯一正文，再维护一份 md「备份」。

`01-principles/` 单向约束 `05-features/`：写 intent 不得违背已作数的原则篇（尤其 [03](03-press-release-faq-flywheel.md)）。特性验证后改 architecture / 指南；还没做的写进对应特性的开放问题或 architecture 留白，不另开总表。原则要改，先议再改本目录，必要时写 ADR。仓根 `iterations/` 层已退役（选 commit/PR 留过程、正本留现状，代价是过程史只能从 Git 找），不再恢复。

## 4. 变更制品链（docs/05-features/）

### 4.1 粒度（硬规矩）

`docs/05-features/` 只装**产生用户价值的新能力或新信息**——给客户一个以前没有的价值（新能力 / 新数据维度 / 能做成以前做不成的事）。

| 新立特性制品链 | 不另立特性（复用依据，直接修 + 留痕） |
|---|---|
| 新能力：用户以前没有、现在能做新事 | 命名 / 统一口径（版本号归一、标签体系合并） |
| 新信息维度：用户能看见以前看不见的 | 基建接线（已有设计系统接上、样式正本归一） |
| 大改行为或信息架构**且**产生新价值 | 重构 / 重排不产生新价值（仅更顺 / 更好看） |
| 跨多模块、要产品拍板范围 | 小 bug、文案、测试补洞、依赖钉死 |

判定关键：**用户感知到新价值**，不是「工程更顺」。拿不准时问：发布当天客户看见什么新东西？没有新价值的小修不另立特性，复用所属特性的明确行为与验收，直接修复留痕（commit 说明 + 必要知识同步）。这不豁免存量独立特性缺文档时的补齐与人确认，具体执行 [02 §6.3](02-working-backwards.md)；不把小修本身另写成一份 intent。一条 `docs/05-features/<id>/` 可以对应多笔提交、多个 PR，只要仍是同一个特性意图。

### 4.2 目录与 gate（少而硬）

```text
docs/05-features/<change-id>/
  intent.md       # 要什么 / 为何 / 约束 / 开放问题（意图 gate）
  spec.md         # 需求+设计；必须含可点原型的链接与操作逻辑（规格 gate）
  prototype.html  # 可选：设计阶段原型的归档，参考用；真界面以壳为准
  plan.md         # 改哪些文件、顺序、风险、如何证明——默认自动跑；仅大风险升 gate
  STATUS.md       # 链状态；格式见 02 §6.2
```

**人 gate（必须过）：**

1. **意图 gate** —— 批 `intent.md`（做不做、是否落在周目标 / 03 飞轮里）。
2. **规格 gate** —— 批 `spec.md`：缺可点原型或操作逻辑直接退回。**非 UI 变更**（纯脚本 / 规范包）豁免「可点」：仍须有操作逻辑（脚本协议、输入输出契约或样例输出），不必是界面原型。原型归档在特性目录，`spec.md` 链到它；落点与取舍见 [02 §3.2](02-working-backwards.md)。

**默认不进 gate**：`plan.md` 由 agent 在规格认过之后自拟并自动跑；仅命中大风险清单（破坏性迁移、权限/密钥面扩大、对外契约变更、不可逆发布、跨边界数据流出等，清单正本在 [03](03-press-release-faq-flywheel.md) 的 FAQ）时才升 gate。

接受某一制品 = 允许进入下一阶段；聊过、口头批准不等于过 gate，git 历史即审计轨迹。小修不新开本链；所属特性缺必要依据时按 [02 §6.3](02-working-backwards.md) 补原链。

### 4.3 与 Superpowers / grill-me 兼容

它们是**过程工具**（发散、质询、写计划草稿），可以继续用，兼容规则三条：

1. **正本唯一**：gate 批的是 `docs/05-features/<id>/intent.md` 与带原型的 `spec.md`，不是 `docs/superpowers/specs/` 里另起的一套。
2. **产出要落仓**：brainstorming / grill-me 的结论写回或迁入对应 `docs/05-features/<id>/`；只留在聊天或草稿、正文不动 = 没过 gate。
3. **plan 仍听少 gate**：writing-plans 的产出可进 `plan.md`，默认不另开必批 gate。

## 5. 入口与头部

[docs/README](../README.md) 管 docs 树地图，设计正本是 [architecture](../architecture.md)。docs 目录内的落盘细则听 docs/README 与 architecture；跨目录归属听本文。

### 5.1 仓根只留四份入口文档

| 仓根文档 | 职责 | 谁先读 |
|---|---|---|
| `README.md` | 产品介绍、当前能力边界、快速开始、继续阅读入口 | 浏览仓库的人 |
| `AGENTS.md` | 任务读取路径、开发硬约束、文档维护与交付规则 | 在本仓工作的模型与开发者 |
| `CLAUDE.md` | 只含一行 `@AGENTS.md`，不另立规则 | 对应工具通过它导入开发约定 |
| `CONTEXT.md` | 领域术语、歧义边界与相关正本 | 需要理解或维护领域用词的人与模型 |

整体设计直接指向 `docs/architecture.md`，不设仓根设计指针或变更流水。其余知识文档进入 `docs/` 的已有职责层；临时报告作为仓外 artifact 或留链接，不为报告新建常驻知识层；特性原型按 §4.2 归档在特性目录。工具配置、源码及结构化项目资产不属于本条的 Markdown 入口清单。

### 5.2 头部是文档的接口

- **本文**规定分层、共用要素与例外；**AGENTS** 规定模型如何读、维护、验证以及何时征得人确认；**每篇头部**是该篇职责与格式的正本。索引只导航，不复制全套规范。
- 头部让读者一眼知道：**读者与读取时机、写什么 / 不写什么、正文结构、何时更新、依赖哪些正本**。用简短导读或维护块表达，不要求每篇套同样的章节数量；头部写不清这一篇管什么，往往说明它该并入别处（§0.1）。
- 头部放在标题附近、正文之前。`README.md` 可用顶部 HTML 注释兼顾仓库门面，模型须读 Markdown 原文；`CLAUDE.md` 只作导入，不加头部。
- Skill 保持 YAML frontmatter 和自身结构；上游镜像、生成文件遵循来源格式，由其入口说明维护方式。既有文档按实际改动补齐，不启动无差别全库格式改造。
- 新增或恢复内容先检查目标范围；范围外优先找正确正本，确需扩责须**先提出头部边界变更并经人确认，再改头部与正文**。具体维护顺序只在 [AGENTS](../../AGENTS.md) 维护，头部不得覆盖上层原则。

读取顺序按任务走 AGENTS「按任务读取」，本文不另列一份。
