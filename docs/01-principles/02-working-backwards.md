# 02 · 产品开发：逆向工作法（Working Backwards）

- 状态：**现在作数**（2026-08-26）
- 位置：`01-principles/` 产品开发原则篇
- 相关：[`01-document-organization.md`](01-document-organization.md)（`docs/05-features/` 粒度与制品链）、[`03-press-release-faq-flywheel.md`](03-press-release-faq-flywheel.md)（**产品级**新闻稿/FAQ/飞轮正本）、[`../architecture.md`](../architecture.md)（现行工程设计正本）

> **30 秒导读**：特性级变更**先写清客户体验与证据，再写代码**。产品级 PR/FAQ/飞轮在 [03](03-press-release-faq-flywheel.md)；单次特性落在 `docs/05-features/<id>/`——**人 gate = intent + 带原型的 spec**；plan 仅大风险升 gate；依据齐备的小修直修，所属特性缺文档先按 §6.3 补齐并确认。可用 Superpowers / grill-me 辅助发散与质询，结论必须落回 `docs/05-features/`。

> **用词**：一律 **gate**（不再写「人闸」）；与工程**门禁**区分见 01 / `CONTEXT.md`。

## 0. 两层逆向工作法

| 层 | 正本 | 何时改 |
|---|---|---|
| **产品级** | [03 新闻稿·FAQ·飞轮](03-press-release-faq-flywheel.md) | 慢变；改主张/客群/飞轮须拍板 |
| **特性级** | `docs/05-features/<id>/intent.md` + 带原型的 `spec.md` | 每个大特性一条；必须对齐 03，不得偷偷改写产品主张 |

## 1. 原则一句话

**以终为始：先站在「发布当天客户看见什么」写清楚，再决定做不做、怎么做。**  
禁止在 intent/spec 未对齐前，用实现细节或技术方案冒充产品决策。

适用范围：与 [`01`](01-document-organization.md) 一致——**仅产生用户价值的特性**（新能力 / 新信息维度）新立制品链；统一命名 / 基建接线 / 重构重排 / 小 bug 复用明确依据直修留痕。所属独立特性缺必要文档时仍按 §6.3 补原链。

## 2. 五大灵魂拷问（立项与写 intent 时必答）

写 `docs/05-features/<id>/intent.md`（及后续讨论）时，必须能回答：

1. **谁是客户？** —— 清晰画像，禁止「所有人」。
2. **客户有什么痛点或机会？** —— 真实、迫切，不是闭门想象。
3. **最核心的客户利益是什么？** —— 最直接、最明显的那一条价值。
4. **你如何知道客户想要这个？** —— 访谈、数据、调研、真实使用读回等客观依据；禁止纯直觉当唯一依据。
5. **客户体验看起来是什么样的？** —— 旅程、关键界面或极简原型，可想象、可指摘。

答不清这五问 → **不进入写码**；意图 gate 批 intent 时优先查这五问。

## 3. PR/FAQ 机制（本仓怎么落）

亚马逊用新闻稿 + 外/内 FAQ 逼团队站在客户与挑战者视角。本仓**不强制另起三套文件名**，映射到已有制品：

| 亚马逊构件 | 本仓落点 | 要求 |
|---|---|---|
| 新闻稿（Press Release，≤1 页、人话） | **`intent.md` 主体** | 通俗、非技术黑话；说清痛点、利益、为谁、发布时客户怎么获得 |
| 外部 FAQ | **`intent.md` 末节或 `spec.md`「客户会问」** | 怎么用、和现状/竞品差在哪、边界与不做的事 |
| 内部 FAQ | **`spec.md`「硬核挑战」** | 技术难点、成本/代价、运营与合规风险、成功怎么量 |

### 3.1 intent 结构：为什么值得做

给 Builder、Leader 与评审者先读；用约一页人话回答五大拷问。新写或整体重写时按以下语义结构组织，小特性可合并相邻短节，不为凑模板填空话。

| 顺序 | 必须回答 | 不写入 |
|---|---|---|
| 导读与状态 | 一句话用户价值；读者、职责与更新时机；草案或已认可及认可来源 | 用聊天方向冒充整篇认可或已经实现 |
| 用户与问题 | 谁在什么场景受阻，现有做法为什么不够 | 产品总介绍、技术排查流水 |
| 价值与依据 | 最核心的收益，来自哪些反馈或证据；假设明确标出 | 无来源收益、测试通过即用户受益 |
| 目标体验 | 从入口到有用结果的简短叙事，能让人想象实际使用 | 控件清单、数据字段、工程步骤 |
| 范围与边界 | 做什么、不做什么、与相邻特性的关系 | 把公共接线包装成独立特性 |
| 成功判据与待决问题 | 怎样判断值得用；只列会改变意图的未决选择 | 历次会议纪要、重复 spec 的验收表 |

客户常问的问题就近回答；需要操作细节的内容链接 spec，不另养一套重复 FAQ。

### 3.2 spec 结构：用户怎样完成，怎样验收

给交互设计、实现者与验收者读取；描述一套完整的目标行为，不混写多个历史方案。新写或整体重写时按以下顺序展开：

| 顺序 | 必须回答 |
|---|---|
| 导读与状态 | 职责、范围、更新时机；链接 intent、原型和 STATUS；整篇是否认可 |
| 范围与入口 | 用户从哪里进入、操作哪个对象；相关界面如何区分；原型覆盖与限制 |
| 完整用户旅程 | 从开始到交付的主路径；每步用户动作、系统响应与留下的材料 |
| 行为规则与异常 | 对象和来源、确认语义、保存与恢复、权限边界；缺失、冲突、失败及如何继续 |
| 验收与衡量 | 稳定验收标识、场景和可观察结果；指标按意图需要给口径，运行成绩链接 STATUS/报告 |
| 取舍与待决问题 | 被放弃的可行选项及理由、重要成本/风险；尚缺的产品决定，不能以实现细节代答 |

外部 FAQ 与内部硬问题融入上述对应章节：怎么用、边界、技术难点、代价、运营/法律/安全风险和成功依据。只展开本特性实际涉及的风险，不套空清单。

**规格 gate 硬要求**（对齐 03）：`spec.md` 必须带**可点原型**与**操作逻辑**（主路径、分支、出错怎么办）。缺这两样 → 规格 gate 直接退回，不许「先让实现跑着」。

非 UI 变更按 [01 §4.2](01-document-organization.md) 的既有豁免执行：纯脚本或规范包可用脚本协议、输入输出契约或样例输出代替可点界面原型，仍须写清操作逻辑。下文的特性制品链与小特性规格要求同样适用这一例外。

**特性原型归入所属特性目录**：可交互文件放在 `docs/05-features/<id>/prototype.html`，`spec.md` 与 `STATUS.md` 链接到它；各屏可编辑源码与本地资源可放同目录 `prototype/`，生成物标注来源和构建入口，不手改打包依赖；各特性可独立打开，共用资源仅保留一份并以相对路径引用。共用整份原型时，其他特性才放 `prototype.md` 索引；不为共享原型另立特性目录。来源、适用版本与设计或历史身份写在所属特性的 spec 中；原型不表示能力已交付，现行行为与证据以 spec、STATUS、真壳及 PR 截图为准。历史附件可保留固定提交链接，注明联网要求；需要完整离线评审时提供原评审包链接，不重复收录无运行依赖的图片、报告和过程记录。

### 3.3 按主题维护，不追加聊天流水

- 每篇头部遵循原则 01，给出读者/读取时机、职责边界与更新触发；正文保持上述可稳定定位的语义顺序。小改直接替换受影响段落，不新增“某日补充”“本轮迁移增量”等重复章节。
- intent 管价值与范围，spec 管行为与验收；实现取舍和工程步骤进入 plan 或模块正本；当前链状态、认可和运行证据进入 STATUS/报告；变更原因和旧内容去向进入 commit/PR。历史从 Git 追溯，不复制一套归档堆栈。
- 讨论决定落回对应主题；已经解决的问题从待决列表移除。未决仅记录具体问题、推荐选择及影响，不能将整段聊天粘入正文。
- 一项规则只在一个位置完整定义，其他文档引用；章节替换同时处理入链。旧平台结果不得列作当前验收成绩，原型和目标规格不得写成已实现行为。
- 本结构适用于新建和整体重写的特性文档；日常局部改动只清理所影响的主题。不得借格式整改扩展为未授权的全库重写。

## 4. 叙事备忘录（六页纸精神）

复杂特性或跨原则的决策：用**短叙事文**把逻辑写完整，再开会辩；禁止用一堆幻灯片标题代替论证。

本仓约定：

- 默认长度：能在一次静默阅读里读完（大约数页 md，不追求字数仪式）。  
- 会议：先读后辩——参与者先读 `intent`/`spec`（或合并备忘），再讨论；gate 决策台应优先展示叙事摘要，而非装饰性幻灯。  
- 与 AI-Native SDLC 一致：**制品进 git**；读与批的对象是文件，不是会后口述。

## 5. 飞轮与长期主义（选型约束）

构思特性时，除客户价值外，必须能回答 [03](03-press-release-faq-flywheel.md) 的**飞轮检验**（本篇不重复画图，以 03 为准）：

1. 它加强的是飞轮哪一截（人定目标与范围 / 人审结果 / 讨论或创建工作树验证 / 已有做法覆盖的工作自动执行 / 未覆盖的工作由人机协作完成 / 架构审视结果回流 / 可复用技能持续改进）？
2. 会不会把人拽回搬运工、密审批、断上下文的 IDE，或让模板/agent 代填定框，或让开独立 worktree 变成每天主业？  
3. 会不会破坏产品主张中的约束：做哪些事、结果长什么样、怎么验收须由人审 / 讨论与创建工作树不等于确认完成 / 工作树改动不得自动合回主工作区 / 风险大的事项标记给人优先审阅 / 没数据显示未知 / 写代码的 AI 不能给自己点完成 / 定时只建队列、不代做判断与目标确认？本仓特性开发的 intent/spec gate 仍按本篇前文执行，不与产品操作混用。

说不清飞轮贡献、削弱任一条、又占大改动带宽 → **意图 gate 应驳回或拆小/推迟**。

## 6. 与制品链、gate 的衔接（少而硬）

```text
五大拷问 + 新闻稿式 intent
        → 意图 gate（批 intent）
        → spec（含外/内 FAQ + 可点原型 + 操作逻辑）→ 规格 gate
        → plan.md：默认自动跑；仅大风险升 gate
        → 实现（认过之后中间段自动跑；可选用 gate 上开独立 worktree 探路）
```

- gate 要快：决策投影应突出拷问答案、痛点/利益、FAQ 风险、原型，而不是全文墙。  
- Agent 可起草 PR/FAQ 式 intent/spec；**纠错与放行必须是人**。聊过 / grill-me 质询过 ≠ 过 gate；谈定须改写制品正文。  
- **小 bug：依据齐备时直接修复，不新立特性；缺文档判定与补齐见 §6.3。**
- **小特性豁免**：体量小**但产生用户价值**的特性可把 spec + 原型 + 实现一并送评审（不必「规格 gate 先过再动代码」）；但 spec 仍须含原型与操作逻辑，缺则退回。此豁免不覆盖 §6.3 的存量独立特性缺文档情形，不能跳过缺失决定的人确认。认可即合，不认可按意见改或退回。大特性仍按规格 gate → 实现 的次序。统一命名 / 基建接线 / 重构不产生新价值的，不新立特性，依据齐备时直接修复留痕。

### 6.1 Superpowers / grill-me（兼容，非第二正本）

| 工具 | 怎么用 | 落点 |
|---|---|---|
| Superpowers brainstorming 等 | 发散、澄清、写设计草稿 | 结论迁入 / 写成 `docs/05-features/<id>/intent.md`·`spec.md` |
| grill-me | 对 intent/spec（或草稿）做质询加压 | 修订必须回写 `docs/05-features/<id>/` 正文 |
| writing-plans | 起草实现步骤与风险 | 进 `plan.md`；默认不另开必批 gate，大风险才升 |

禁止：只在 `docs/superpowers/specs/` 或聊天里「批过」就开干，而 `docs/05-features/` 无对应已接受制品。细则见 [01 §4.3](01-document-organization.md)。

### 6.2 六环交付链

§6 的制品链到「实现」为止；一次完整交付按**六环链**延伸，横切站随每个 PR、收口站随每个版本：

```text
intent（原始意图对齐）→ spec（规格与验收点）→ 实现设计
        → TDD → 验收点E2E → 用户旅程E2E
横切站A 实现门禁（每 PR）   横切站B 验证 Review（每 PR）   收口站 人验收/发布归档（每版本）
```

与 **V-model** 同构：左翼分解（intent→spec→实现设计），右翼验证（TDD→验收点E2E→旅程E2E），两端对应——spec 验收点↔环5 用例、实现设计↔环4 单测。配比按**测试金字塔**（单测底座、验收居中、旅程少而真）；**特性初期三层都克制**——单测只守核心推导，验收点与旅程先覆主路径，行为稳定后专项回补（见环 4–6），追溯取 **RTM 的活文档形态**：链本身就是追溯矩阵，不另维护一张表。业界源：V-Modell；Cohn《Succeeding with Agile》(2009)、Fowler TestPyramid、《Software Engineering at Google》Ch.11；Martraire《Living Documentation》(2019)、Cucumber 可执行规格、Adzic《Specification by Example》(2011)；ISO/IEC/IEEE 29148:2018（RTM 定义）、DO-178C（双向追溯）。

每环硬要求（应然态；某特性现状缺口以该特性 `docs/05-features/<id>/` 制品与 PR 记录为准）：

| 环 | 硬要求 |
|---|---|
| 1 intent | §2 五大拷问 + §3.1 骨架；人 gate 后才进 spec。**自用工具不自动成为产品特性**——按用户身份分别立 intent（分层判据见 6.3） |
| 2 spec | 行为要求 + **可判断的验收点**必须有；原型链接按 §3.2。**指标不强求**；要挂必须是价值指标：按[指标协议](../../standard/system-prompt/references/metrics.md)写清口径/窗口/来源/目标，引领经 `leads` 写明它盯的滞后指标，**最终能反馈到北极星指标得到收益**。本分支没有 `.bw/metrics.toml` 的现存北极星占位；指标定义与采集随特性迁移、经人确认后落地，候选不当成已运行指标 |
| 3 实现设计 | 动代码前在 [architecture](../architecture.md) 定位（§1 用例哪一站 → §2 能力 → §3 Electron 叠层与数据流）；**实现落地后回写 [06-module](../06-module/README.md)**——设计与代码漂移即断环 |
| 4 TDD | **测试用例规范（2026-09-29 拍板，同日修订为两类看护）**：业界 TDD/测试金字塔实践在本仓收敛为只立两类看护——①**核心算法函数**：从数据算出数值或状态的纯函数推导（信号/健康推导、状态机与视图路由、现算重算、调度触发判定、数据契约与协议解析——toml/JSON/标签协议等）；②**与用户 E2E 强相关**：直接对应验收点 E2E 的数据读写协议——协议错误会让用户旅程失败或重启读回数字不一致。判别一句话：**被测对象是「从数据推导数值/状态的算法或协议」才立单测，是「界面怎么渲染和交互」就不立**。**负面清单**：UI 组件渲染、布局外观、文案、交互序列、hook/界面装配不立单测，行为正确性交验收点/旅程 E2E 与真壳 Review。**数量控制**：一个特性的核心算法函数通常个位数；每特性每次交付新增单测默认 ≤10 例，超出须在 PR 正文说明理由；不把新增回归大坝当交付物（AGENTS）。已有合规单测随改维护，特性大改时同批盘点裁并、失效即删。旧 Rust 类型名不作为本分支实现要求。测试的特性归属清单**暂缓**（2026-09-20 拍板：义务定义未清） |
| 5 验收点E2E | spec 每条验收点与对应注册用例**双向可查**；用例登记特性归属，运行结果带证据。**应跑用例缺跑不得判通过，覆盖按验收点与用例双向映射核对**。**初期控量（2026-09-29 拍板）**：行为仍快变时先注册核心验收点用例，其余验收点在 STATUS 记缺口、稳定后专项回补，不一次追全量；已注册用例缺跑仍不得判通过。Electron 现有入口为 `tests/e2e/` 与 `tests/playwright.config.ts`；迁移时由特性任务补映射，交付验证入口由 CI/CD 任务收口。不得拿旧 Rust suite 的通过记录作本分支证据，也不得以「看见有用例」反推「有 E2E」 |
| 6 用户旅程E2E | 每个**在用**特性至少一条注册旅程：驱动**真实 Electron 壳**，从头到尾完成一件完整的事，判据可判断，能独立读回结果。初期每特性只守这一条主旅程，分支与异常旅程待行为稳定后专项回补。模拟不算数；旧 `BW_OPEN/BW_PANEL` 深链不适用于本分支 |

- **横切站 A（实现门禁）**：执行 [AGENTS](../../AGENTS.md)「提交前门禁」与本分支 PR workflow；检查范围和未验项写进 PR。现有 CI 不等于已覆盖 BW 的全部特性，不搬用 Rust verify 命令或旧分支的绿灯。
- **横切站 B（验证 Review）**：推 PR 前工作会话必须开**独立 subagent 全方位检视**（2026-09-29 拍板；步骤登记为交付 TODO，SOP 见 [workbench-start §6](../../.claude/skills/workbench-start/SKILL.md)），发现项在同一交付内修正后才推 PR。检视四维：①顶层文档与正本——AGENTS、原则、architecture 与本次改动一致；②特性文档资产——intent/spec/STATUS 与特性矩阵随本次同步，老方案文档、无效冗余记录该删已删；③实现代码——被替代尝试、兼容层、双路径已清除；④测试资产——配比符合环 4–6 口径、不堆量。界面/行为改动另发验证报告，判据附真壳截图四件套（AGENTS）。独立评审的机制是**召唤制**（reviewer-agent，2026-09-29 迁入 bw-orca）：PR 评论单独一行 `/code-review` 触发 `.github/workflows/claude-code-review.yml`，评审当前 head SHA 并发布结论评论，回执脚本校验 `bw-code-review:<SHA>` 标记；默认分支仍为 main 期间触发定义在 main、回执脚本由本分支 head 提供。未召唤 = 未评审，没有实际运行就标「未独立评审」，不缺省绿。动四铁律机制、门禁或发布链必须提供独立评审；未能执行须在 PR 明列原因和待审项。
- **收口站（人验收/发布归档）**：Done、合入和正式发布由人确认。版本说明与 Release 草稿可先准备；发布前必须核对候选提交、安装包、校验值与验包证据对应同一版本，发布后独立读回。Electron 发布链与归档协议由交付任务落实；旧 Rust 发布工具和 ADR 不能冒充本分支已经具备的机制。

**补链分两层**：**定义层**（intent 草案、spec 骨架、验收点、旅程定义）先对齐用户目标；**实现层**（实现设计、单测、真实 E2E）随特性迁移或修改补齐。迁移包含在 Orca 上重新决策用户旅程，不要求照搬 main 的实现。历史文档经清理后不自动补回；处理某特性时按 §6.3 从本次相关的第一个缺环开始，仍成立且已获认可的决定可复用，不能复制旧分支的验收绿灯。小修不机械补六份文件，未覆盖的实现和验收债如实记录。

**STATUS 格式**：每特性 `docs/05-features/<id>/STATUS.md` 使用六环表——每环一行：环 / 状态（●齐、◐部分、○缺、待建、—不适用）/ 证据或已知债。按真实迁移逐项补，不预填齐全；不适用须写原因。本分支不导入 main 的旧特性矩阵；叠层自己的特性清单与链状态正本在 [docs/05-features/README.md](../05-features/README.md)，现存目录与读取入口见 [docs 地图](../README.md)，保留历史材料不等于通过 Electron 验收。

### 6.3 特性边界与带入判定

- **边界判据**：特性 = **持续提供给用户的一件完整的事**（用户目标导向；方法源：JTBD、Google HEART、knowledge-model 正本「特性=持续用户能力」）。目录数/页面数/模块数/屏数 ≠ 特性数；组合形态（自动化+skill+屏，如周一屏）算**一个**特性；四铁律等横向约束是横切站/内核义务，**不是特性，不随单个特性低频而放松**。
- **分层判据（看特性的用户身份）**：被管项目的 Builder ⇒ **产品特性**（`docs/05-features/`）；BW 开发团队自己 ⇒ **开发方法资产**（CI/门禁/发布工具链、`.claude/skills/`）；分发给被管项目使用的 `standard/` ⇒ **产品执行规范资产**，按实际服务的用户目标归属；尚无真实用户 ⇒ **预研**（不开链、不计特性）。自用工具实现不自动算成对外特性。
- **带入三问**（新工作开工前必答，决定「修改存量 vs 新增承载」）：
  1. 这件事服务哪个**已有特性的用户目标**？⇒ **修改存量特性**：带入该特性的链，按影响更新其 intent/spec；优先复用已有目录，原承载缺失时按下述规则补齐，不另立新特性；
  2. 开的是**新用户目标**（说得出为谁、完成什么完整的事）？⇒ **新增特性**：立 intent 经人确认后再开发；
  3. 答不出「谁在用、完成什么事」？⇒ **预研或不做**：不开链、不计特性。
- **归属变更**：能力被外部重构接管时标「归属待定」，交接后移出产品特性。

**存量独立特性缺文档时的开工规则（含小 bug）**：先核对所属特性的 intent、spec 以及本次涉及的行为、验收点和旅程定义是否存在且适用于目标分支。缺失或已失效时，先在该特性的承载处补本次所需的定义草案，写明可追溯来源、仍成立的认可与待定部分；不根据现有代码替人认定产品行为。对缺失、失效或未获认可的决定，交人按 intent/spec gate 确认后，才改依赖这些决定的代码。已有可追溯且仍成立的认可直接复用，不重复审批；调查、复现和不依赖未决项的准备可以继续。

补齐的是已有特性的必要知识，不是给每个小修新立特性，也不是在开工前补完全部历史实现和 E2E。实现与验证仍按 §6.2 随改补齐；未涉及的旧债留在该特性 STATUS 或现有 PR 中，不伪报完成。不属于独立产品特性的文案、工程整理等复用各自正本，行为依据明确时直接修复。

## 7. 明确不做

- 不为每个小修写新闻稿或 FAQ。  
- 不用技术方案章节冒充新闻稿。  
- 不把「感觉用户会喜欢」当作第 4 问的唯一答案。  
- 不在本篇规定具体 UI 组件实现。  
- 不把 plan 默认做成第三道必批 gate（与 03「少 gate」冲突）。  
- 不禁止 Superpowers / grill-me；也不允许它们另起一套 gate 正本。
