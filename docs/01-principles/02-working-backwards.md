# 02 · 产品开发：逆向工作法（Working Backwards）

- 状态：**现在作数**（2026-08-26）
- 位置：`01-principles/` 产品开发原则篇
- 相关：[`01-document-organization.md`](01-document-organization.md)（`docs/05-features/` 粒度与制品链）、[`03-press-release-faq-flywheel.md`](03-press-release-faq-flywheel.md)（**产品级**新闻稿/FAQ/飞轮正本）、[`../architecture.md`](../architecture.md)（现行工程设计正本）
- 方法来源：亚马逊 Working Backwards / PR·FAQ / 叙事备忘录文化（外部实践；本仓取其机制，不照搬组织流程）

> **30 秒导读**：特性级变更**先写清客户体验与证据，再写代码**。产品级 PR/FAQ/飞轮在 [03](03-press-release-faq-flywheel.md)；单次特性落在 `docs/05-features/<id>/`——**人 gate = intent + 带原型的 spec**；plan 仅大风险升 gate；小修直修。可用 Superpowers / grill-me 辅助发散与质询，结论必须落回 `docs/05-features/`。

> **用词**：一律 **gate**（不再写「人闸」）；与工程**门禁**区分见 01 / `CONTEXT.md`。

## 0. 两层逆向工作法

| 层 | 正本 | 何时改 |
|---|---|---|
| **产品级** | [03 新闻稿·FAQ·飞轮](03-press-release-faq-flywheel.md) | 慢变；改主张/客群/飞轮须拍板 |
| **特性级** | `docs/05-features/<id>/intent.md` + 带原型的 `spec.md` | 每个大特性一条；必须对齐 03，不得偷偷改写产品主张 |

## 1. 原则一句话

**以终为始：先站在「发布当天客户看见什么」写清楚，再决定做不做、怎么做。**  
禁止在 intent/spec 未对齐前，用实现细节或技术方案冒充产品决策。

适用范围：与 [`01`](01-document-organization.md) 一致——**仅特性级（或同级大改）**走本原则；小 bug / 琐修直接修。

## 2. 五大灵魂拷问（立项与写 intent 时必答）

写 `docs/05-features/<id>/intent.md`（及后续讨论）时，必须能回答：

1. **谁是客户？** —— 清晰画像，禁止「所有人」。
2. **客户有什么痛点或机会？** —— 真实、迫切，不是闭门想象。
3. **最核心的客户利益是什么？** —— 最直接、最明显的那一条价值。
4. **你如何知道客户想要这个？** —— 访谈、数据、调研、真实使用读回等客观依据；禁止纯直觉当唯一依据。
5. **客户体验看起来是什么样的？** —— 旅程、关键界面或极简原型，可想象、可指摘。

答不清这五问 → **不进入写码**；意图 gate 批 intent 时优先查这五问。

## 3. PR/FAQ 机制（本仓怎么落）

亚马逊用新闻稿 + 外/内 FAQ 逼团队站在客户与挑战者视角。本仓**不强制另起三套文件名**，映射到已有制品：

| 亚马逊构件 | 本仓落点 | 要求 |
|---|---|---|
| 新闻稿（Press Release，≤1 页、人话） | **`intent.md` 主体** | 通俗、非技术黑话；说清痛点、利益、为谁、发布时客户怎么获得 |
| 外部 FAQ | **`intent.md` 末节或 `spec.md`「客户会问」** | 怎么用、和现状/竞品差在哪、边界与不做的事 |
| 内部 FAQ | **`spec.md`「硬核挑战」** | 技术难点、成本/代价、运营与合规风险、成功怎么量 |

### 3.1 intent 建议结构（新闻稿式）

可按下列骨架写（有则写，无则标「待补」——待补过多则意图 gate 应驳回）：

1. **标题**：产品/特性叫什么（一眼看懂）  
2. **副标题**：核心受益人群 + 终极价值  
3. **总结**：一短段核心利益  
4. **痛点**：今天客户卡在哪  
5. **解决方案**：新品如何轻松解决（体验语言，不写技术栈）  
6. **为何现在做**（可选）：负责人视角的「为什么」  
7. **客户会怎么说**（可选）：发布后可验证的体验描述，不是空夸  
8. **如何获得**：怎么用上（入口、权限、是否内测）  
9. **五大拷问答案摘要** 或链到证据  
10. **开放问题**

### 3.2 spec 中必须有的「FAQ 硬问题」与原型

至少覆盖（答不出就标风险，勿装懂）：

- 客户：怎么用？不做哪些？和现有能力/竞品边界？  
- 内部：技术难点？代价与取舍？上线后运营/法律/安全风险？成功指标是什么？

**规格 gate 硬要求**（对齐 03）：`spec.md` 必须带**可点原型**与**操作逻辑**（主路径、分支、出错怎么办）。缺这两样 → 规格 gate 直接退回，不许「先让实现跑着」。

## 4. 叙事备忘录（六页纸精神）

复杂特性或跨原则的决策：用**短叙事文**把逻辑写完整，再开会辩；禁止用一堆幻灯片标题代替论证。

本仓约定：

- 默认长度：能在一次静默阅读里读完（大约数页 md，不追求字数仪式）。  
- 会议：先读后辩——参与者先读 `intent`/`spec`（或合并备忘），再讨论；gate 决策台应优先展示叙事摘要，而非装饰性幻灯。  
- 与 AI-Native SDLC 一致：**制品进 git**；读与批的对象是文件，不是会后口述。

## 5. 飞轮与长期主义（选型约束）

构思特性时，除客户价值外，必须能回答 [03](03-press-release-faq-flywheel.md) 的**飞轮检验**（本篇不重复画图，以 03 为准）：

1. 它加强的是飞轮哪一截（人定的框 / 少 gate 待办 / gate 上聊或开树探路 / 认过即自动跑 / 架构盘账回流 / 可信所以敢放手 / 技能更贴）？  
2. 会不会把人拽回搬运工、密审批、断上下文的 IDE，或让模板/agent 代填定框，或让开独立 worktree 变成每天主业？  
3. 会不会破坏：做不做与长什么样必须人认 / 聊过≠过 gate / 开树≠过 gate / 没认过样子不动主仓 / 该升 gate 的没认过不许继续 / 没数据显示未知 / 写代码的队友不能给自己放行 / 定时只建队列、不代做判断与定框？

说不清飞轮贡献、削弱任一条、又占大改动带宽 → **意图 gate 应驳回或拆小/推迟**。

## 6. 与制品链、gate 的衔接（少而硬）

```text
五大拷问 + 新闻稿式 intent
        → 意图 gate（批 intent）
        → 按标准建活（活 = codehub issue，承载正本；打 bw:category / bw:plan 标签；活号与 docs/05-features/<id>/ 互链）
        → spec（含外/内 FAQ + 可点原型 + 操作逻辑）→ 规格 gate
        → plan.md：默认自动跑；仅大风险升 gate
        → 实现（认过之后中间段自动跑；可选用 gate 上开独立 worktree 探路）
```

- gate 要快：决策投影应突出拷问答案、痛点/利益、FAQ 风险、原型，而不是全文墙。  
- **活是承载正本**：意图 gate 一过（或发起人当面拍板）**先建活再写 spec**。活号写进 `docs/05-features/<id>/`（intent 状态行与 STATUS），目录 id 写进活正文；**无活承载的产物链 = 未立项**——看板、周记账、过程指标都看不见它，自狗食就断在这一步。  
- **两 gate 可合并送审**：发起人已当面拍板「做不做」时，意图 gate 与规格 gate 可合并为一次送审（单人节奏的取舍）；批的仍是制品文件，缺可点原型或操作逻辑照样退回。  
- Agent 可起草 PR/FAQ 式 intent/spec；**纠错与放行必须是人**。聊过 / grill-me 质询过 ≠ 过 gate；谈定须改写制品正文。  
- **小 bug：不走本篇全套；直修即可。**
- **小特性豁免**：体量小的特性可把 spec + 原型 + 实现一并送评审（不必「规格 gate 先过再动代码」）；但 spec 仍须含原型与操作逻辑，缺则退回。认可即合，不认可按意见改或退回。大特性仍按规格 gate → 实现 的次序。

### 6.1 Superpowers / grill-me（兼容，非第二正本）

| 工具 | 怎么用 | 落点 |
|---|---|---|
| Superpowers brainstorming 等 | 发散、澄清、写设计草稿 | 结论迁入 / 写成 `docs/05-features/<id>/intent.md`·`spec.md` |
| grill-me | 对 intent/spec（或草稿）做质询加压 | 修订必须回写 `docs/05-features/<id>/` 正文 |
| writing-plans | 起草实现步骤与风险 | 进 `plan.md`；默认不另开必批 gate，大风险才升 |

禁止：只在 `docs/superpowers/specs/` 或聊天里「批过」就开干，而 `docs/05-features/` 无对应已接受制品。细则见 [01 §4.3](01-document-organization.md)。

## 7. 明确不做

- 不为每个小修写新闻稿或 FAQ。  
- 不用技术方案章节冒充新闻稿。  
- 不把「感觉用户会喜欢」当作第 4 问的唯一答案。  
- 不在本篇规定具体 UI 组件实现。  
- 不把 plan 默认做成第三道必批 gate（与 03「少 gate」冲突）。  
- 不禁止 Superpowers / grill-me；也不允许它们另起一套 gate 正本。
