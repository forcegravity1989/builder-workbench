## 用户与问题

版本迭代的会议与通知全靠手工搬运：计划会/周中评审/验收会要在 WeLink 里手动建会；eMeeting AI 纪要手工抓取核对进计划/验收屏（v0.8 计划归档 PR #446 验证段「纪要与转写全文已抓取核对」即为此例）；发布了没人知道，群成员不进 BW 就跟不上迭代。人不在工位时 BW 没有入口：提不了 Issue、查不了 worktree 状态。项目公共信息（成员、负责人、主机目录）逐仓维护在 `.bw/project.toml`，在 BW 里每改一次就要创建提交、走固定分支 PR 合入（project-intake 配置链）——信息本该随人员变动即时更新，却背上了代码合入的仪式；跨成员对不齐，且成员数据至今未落实（project-intake STATUS）。周中节奏（白天对大需求发起讨论、会上批注、发给模型继续改、晚上夜跑）本来就发生在群里和会上，BW 不在场。

## 价值与依据

核心收益：**会议、通知、远端入口、公共信息四条链路经 WeLink 自动流转**——会前 BW 建会（邀请带议程）、会后转写回 BW 喂纪要（零搬运）、结论摘要回群；发布/部署状态即时报群；远端 @助手 提 Issue、查 worktree；公共信息改在 WeLink 侧即生效（群成员变动本就是群操作，不再为改信息逐仓提交 PR），项目墙读回一致。

依据：#199「会上补充建议」（2026-10-26 版本计划会 AI 纪要行动项：梳理现有 5-6 个关键步骤旅程，形成完整的版本迭代流转）＋ PR #446 设计建议（项目组成员与 WeLink 项目群成员统一考虑；WeLink 聊天工具与共享文档空间承载 BW 公共项目信息，减少各仓重复维护）。核心范围 owner 已定（2026-10-28）：①会议全生命周期（计划/周中评审/验收：场景创建会议＋会后导出录音，便于纪要总结填写）；②未来新增部署屏，助手等经 WeLink 对接，读生产环境基本信息；③以远端 WeLink 为入口，提 Issue、查 worktree 信息。扩展取舍（同日）：发布/部署状态通知进；公共信息承载×项目墙扩展考虑（owner 补充动机：项目信息在 BW 里每改一次都要创建提交、走 PR，落在公共 WeLink 群里改更便捷——修改面免合入仪式是本主题的主要动机）；夜跑结果通知、评审意见回流、指标快照发群暂缓。能力面 owner 已定：助手服务可增量开发、亦可完全耦合进 Workbench 项目，接收面按需实现，不阻塞功能设计。**假设（未验证）**：群通知降噪边界、会议转写归档精度，首用周观察后再定口径。

## 目标体验

一个版本周期走一遍：

1. **计划会**：Builder 在计划屏点「创建计划会」——WeLink 会议建好，邀请带议程与上版回顾链接。会开完，录音转写自动回 BW 计划屏作纪要原料，AI 起草共识/遗留候选，Builder 核对填写（今天这步是手工抓取 eMeeting 纪要）；纪要结论摘要发群，群成员知道这版定了什么。
2. **执行中**：群成员在 WeLink 里 @助手 提了个 bug——Issue 建好、进日常通道；@助手 问「issue-199 什么状态」，助手答 worktree 与 Issue 读数。
3. **周中评审**：评审会同样在 BW 里创建，会后转写回 BW 作批注与意见原料；结论摘要发群。
4. **验收会**：验收会创建，会后转写进验收屏纪要原料，结论 Issue 跟进；摘要发群。
5. **发布与部署**：版本发布，群里收到通知——版本号、Release 链接、变更摘要；部署状态变化（成功/失败）同样报群。未来部署屏经 WeLink 读生产环境基本信息（版本、服务状态、主机）。
6. **公共信息**：项目加了人、换了负责人、主机目录变了——直接在 WeLink 项目群（成员管理）或共享文档里改，即改即生效；项目墙读 WeLink 呈现最新值。Builder 不再为这类信息改动创建提交、开 PR、等合入（今天 `.bw/project.toml` 每改一次走一次 PR），各仓也不再逐份维护这些字段（成员数据今天本就未落实）。

## 范围与边界

- **做**：①会议全生命周期——计划会/周中评审/验收会的场景创建（邀请带议程）＋会后录音转写回流 BW 喂纪要链＋纪要结论摘要发群；②发布/部署状态通知发群；③未来部署屏经 WeLink/助手读生产环境基本信息；④远端 WeLink 入口——@助手 提 Issue（进日常通道）、查 worktree 信息；⑤公共信息承载（扩展考虑）——成员/负责人/主机目录以 WeLink 项目群＋共享文档为正本、项目墙只读呈现，公共信息修改不再走 commit/PR 合入。
- **暂缓候选（本轮未入选，不承诺）**：夜跑会话结果通知；群里评审意见回流挂材料（welink-review-invite spec「下一站」暂缓在此）；指标快照/周报发群；远端查询扩展（版本进度/验收结论/项目知识问答）。
- **不做**：群文档编辑（#199 明示延后）；远程批注协作（[#447](https://github.com/forcegravity1989/builder-workbench/issues/447) 另单）；BW 内建成员/群聊/收件箱（03 飞轮红线——读外部正本，不建协同系统）；远端确认完成（群里 @助手「确认完成」是否算四铁律的人确认——边界敏感，待人拍板，不做默认承诺）；录音转写质量本身（上游系统负责）；开工/任务级通知（噪音大于价值）。
- **相邻**：welink-review-invite＝发起评审第一站（v0.8|G3），本特性承接 #199 第二件事；connectors 管 welink-cli 个人登录态，本特性全程群助手身份，不消费个人登录；reviewer-agent 管 MR/PR 评审召唤，不混；project-intake 管项目墙与接入，公共信息正本切换是该特性的联动方。
- **序列与分期**：本篇为 #199 第二件事的总意图件；实现按主题分期拆 spec（会议面 / 发布部署面 / 远端入口 / 公共信息），进哪个版本由后续版本规划定，不在本篇锁死。

## 成功判据与待决问题

**判据**：一个真实版本周期内——计划/周中评审/验收三类会议在 BW 里创建，会后纪要零手工搬运（转写自动回 BW，人工只核对填写），结论摘要到群；发布/部署通知零手工；远端经 WeLink 提的 Issue 与查询可追溯；公共信息单正本（WeLink 侧改一处、项目墙读回一致，改公共信息不再创建提交/PR）。杀进程重开，群配置与公共信息仍从正本读回，不装绿。

**待决（实现期输入，不阻塞意图 gate）**：

1. 助手服务架构：独立服务增量开发，还是耦合进 BW 主进程——owner 已说两者皆可，实现期按运维与发布面定。

3. 共享文档空间的信息范围与读取方式（PR #446：「具体信息范围、存储与维护方式由负责人结合用户旅程设计」）；与 `.bw/project.toml` 既有字段的正本切换边界（哪些字段迁 WeLink、哪些留仓）。
4. 远端 @助手 问答的知识底座（答「worktree 什么状态」读什么：Issue 原生状态？项目墙读数？）。
5. 远端确认的纪律边界：群里 @助手「确认完成」算不算四铁律的人确认——待人拍板。
6. 分期与降噪口径：哪些主题先进下一版、每类通知的触发边界，首用周观察后定。
