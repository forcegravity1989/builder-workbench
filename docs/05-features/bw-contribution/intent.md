# 贡献 BW：边用边改

> **读者与时机**：评审 BW 自身反馈与研发旅程的人、设计者和模型，在调整入口、原型或执行方式前读取。
> **职责与维护**：本篇维护用户、问题、价值、目标体验和范围；操作规则归 [spec](spec.md)，证据与认可范围归 [STATUS](STATUS.md)。不保存施工计划、遗留事项或讨论流水。用户结果或范围经人确认改变时更新。

## 导读与状态

让使用 BW 的人就地把问题交给懂规范的助手，让愿意修复的人顺着同一份 Issue 开工，并把真实人工补位反哺到原有规范。

归属为**研发保障的一条贡献旅程**，不新增独立产品特性。用户已认可批注交接、助手提单、原生开工的方向；本文记录该方向，局部交互与 Skill 第一版待实际体验，不代表产品已接通。操作与验收见 [spec](spec.md)。

## 用户与问题

A 是正在 BW 项目工作的 Builder；B 是在其他项目中使用 BW 的同事，可能没有 BW 源码；C 是只愿提供清楚反馈的普通使用者。三者不是三套开发流程，差异在可取得的现场、可用模型与源码，以及愿不愿参与修复。

用户日常发现问题后，需要重新描述现场、复制资料、手写提示、找 Issue 再开工。问题最初没有讲清楚，又会让 PR 描述、截图与 dev 验收难以理解。已有 workbench-start 的开发、验证和检视约束，需要接到更清楚的输入上。

## 价值与依据

先让 Builder 自己边用边开发顺手，再让同事照着同样的方法贡献。依据是用户描述的自用、同事机器反馈和原型体验；收益假设是减少人工搬运、重复解释和调度。借鉴 Orca 的就地使用、隔离执行及结果回传，不用未经核实的 PR 数量作效率承诺，也不受某个版本 G3 限制。

本旅程落实 [产品主张](../../01-principles/03-press-release-faq-flywheel.md) 的高效与负责，复用工作台已有能力和 BW 的完整约束体系。

## 目标体验

人在当前页面用快捷键进入批注，指出对象并说一句问题。在原批注工具复制动作旁点“交给改进助手”，现场与原话先进入 floating workspace 的独立智能体草稿，原批注在前、短起手提示在后；人按回车后，助手读取完整 Skill；后续补充在同一会话继续，不要求手动粘贴、选源码仓或建修复树。交接有回执，人可继续原工作，必要时回应助手。

助手优先利用用户本机材料与知识，源码有则参考，无则仍能澄清和提单。形成或关联 Issue 后，人可在会话里点“开始修复”，直接使用任务界面的原生开工弹窗，选择本机或已授权共享主机上的 BW 项目。开工备注自动带最短工作请求，workbench-start 接续原有开发规范。

PR 的说明、同路径前后证据和 dev 身份回指原问题。工作流自身负责检视，强模型守门员是可选辅助。获准发布后可沿原反馈找到可用版本再验。清楚反馈本身即为贡献，C 不必亲自修复；未来 Bot 沿同一方法接入。

## 范围与边界

包括小诉求与 BUG 的现场交接、问题整理、Issue 与开工衔接、交付回看和既有反哺。复用批注、原生会话、Skill 完整包、开工及 workbench-start；不另建工作台、反馈表单、任务状态或反哺引擎。

采集与整理不以 BW 源码或 BW 项目为前提。助手需要可执行会话，但不把专门目录、宿主配置或修复 worktree 暴露为反馈前置操作。BW 项目用于修复；本机或已有共享主机由原生开工选择。默认从本机补充必要现场，不引入独立远端取证流程。

本次交付规范、Skill 第一版和局部体验稿，不实施产品接线。合入、关单、产品完成与正式发布仍由人决定。

## 成功判据

人无需记住个人 prompt 或搬运同一份信息，便能把问题交清楚、知道助手在哪里、按原问题看懂交付。B 不污染自己的业务项目，C 能只反馈；有源码能更准确，没有源码仍可继续。通过真实任务观察人工介入与返工是否减少，不以脚本存在或原型点通替代结果。
