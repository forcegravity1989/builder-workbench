# 贡献 BW：边用边改

> **读者与时机**：评审 BW 自身反馈与研发旅程的人、设计者和模型，在调整入口、原型或执行方式前读取。
> **职责与维护**：本篇维护用户、问题、价值、目标体验和范围；操作规则归 [spec](spec.md)，证据与认可范围归 [STATUS](STATUS.md)。不保存施工计划、遗留事项或讨论流水。用户结果或范围经人确认改变时更新。

## 导读与状态

让使用 BW 的人就地留下清楚的问题，让愿意参与开发的人沿同一套工作方法把它交付，并把真实人工补位反哺到原有规范。

归属为**研发保障**。本目录组织 BW 自身的贡献旅程，不新增面向任意被管项目的通用反馈产品。本文和 [规格及原型](spec.md) 为待评审草案；聊天中认可的方向不等于整篇规格已认可。

## 用户与问题

- **A：BW Builder**，正在 BW 项目工作，也在日常使用正式版或开发版。发现不舒服或不正确的地方时，不想停下手头任务，重新描述现场、切版本找 Issue、手写开工提示，再猜该如何验收。
- **B：组内贡献者**，正在 BW 中做其他项目，愿意参与 BW 修复。他可能没有本机 BW 源码，不应因反馈而在业务项目中创建修复分支，也不应默认借用另一人的机器。
- **C：普通反馈者**，通过现有反馈渠道或 WeLink 提供信息，可能没有本机 BW、源码或模型。反馈清楚本身就是贡献，不以亲自修复为条件。

现有 workbench-start 已约束开发、验证、检视与交付，但其输入不清楚时，模型和人都会反复补背景。用户目前靠主目录会话描述问题、人工关联任务、转交工作流，再读 PR 或打开 dev；上下文搬运和脑中的提示词尚不能让同事自然照着使用。

## 价值与依据

先让 Builder 自己用得顺，再让同事观察同一日常做法就能参与。目标是减少人工解释、重复确认和调度，而不是增加一套界面或增加并发数量指标。

依据来自用户提供的日常自用和同事反馈场景，以及当前 BW 对原生会话、工作区、现场采集、宿主和编排的核对。借鉴 Orca 边用边开发、隔离并行执行和回传结果的方式；未经核实的社区 PR 数量不作为效率承诺，也不让某个版本的 G3 编号限制目标体验。

本主题落实 [产品主张](../../01-principles/03-press-release-faq-flywheel.md) 的高效与负责：少搬运、少带模型，同时让原问题、验收路径和交付证据可核对。

## 目标体验

人在当前 BW 画面发现问题，选定相关元素或附上现场，说一句期望即可提交，然后继续原工作。独立收集会话使用已有证据理解问题，只在缺少必要事实或需要人作决定时再找人。问题明确后形成合格 Issue；愿意开发且已有授权配置的人不必重复调度，系统沿原生工作区与编排交给 workbench-start Worker。

Worker 返回的 PR 说明、同一路径的前后证据和 dev 身份与原问题相连。人因此知道该看哪里、怎么点。强模型守门员作为可选辅助，不成为每次交付的固定人工步骤，也不替代工作流自身的独立检视。

C 留在原渠道补充信息，由维护侧承接；Bot 接通后承担入口、持续对话与回告，复用同一整理方法和任务交接，不另立一种贡献标准。

## 范围与边界

包括小诉求与 BUG 的现场整理、Issue 形成、A/B/C 会话位置与交接、BW 独立修复工作树、交付回传和人工介入的反哺。现场来源、收集会话执行位置、源码与修复宿主分别确定。

复用 BW 已采用的 Orca 执行能力和 BW 的完整约束体系：原型、用例、开发、workbench-start、检视与资产维护规范。先复用实际组件和调用链，再补必要接线；不另建会话屏、任务状态协议、批注引擎或反哺指标体系。

不因本主题默认开放任何人的电脑、远程读取未提供的现场，或要求普通用户承担研发。合入、关单、产品完成和正式发布仍由人决定。此轮制品用于设计评审，不授权产品实现。

## 成功判据

人在原工作中能找到真实触发入口；提交后原工作可继续；信息足够时无需重复解释。A/B 无需记忆个人 prompt，C 无需准备开发环境。修复发生在明确的 BW 宿主与独立树，证据能回答原问题。真实会话中的人工补位进入既有反哺链，后续同类任务减少相同介入；不以脚本存在、原型点通或 PR 数量替代实际效果。
