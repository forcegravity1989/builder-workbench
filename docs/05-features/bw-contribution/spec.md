# 贡献 BW：操作与验收规格

> **读者与时机**：设计评审者、实现者与验收者，在制作原型、改变接报或派工路径前读取。
> **职责与维护**：维护入口、完整旅程、运行位置、异常、验收判据和产品取舍；价值归 [intent](intent.md)，认可与验证归 [STATUS](STATUS.md)。不放遗留清单、施工步骤或讨论流水。行为决定改变时同步原型和验收判据。

## 导读与状态

本篇为待评审目标，非现行能力说明。原始方向为先让 BW Builder 边用边开发顺滑，再让组内同事沿同一方式参与；普通用户的清楚反馈也构成贡献。当前具体入口及自动接线尚待原型评审，不能据此进入产品实现。

当前唯一原型入口：[真实组件原型](prototype/index.html)。原型直接挂载 BW 组件，模拟数据和宿主，不代表完整 Electron 壳、真实模型或跨主机已验收。源码与构建入口在同目录，具体边界见 STATUS。

原型使用仓库已有开发依赖，在仓根运行 `node docs/05-features/bw-contribution/prototype/build.cjs` 后打开上述入口；生成资源位于忽略的 `prototype/dist/`，从源码重建，不另维护第二份当前稿。未与完整真壳画面对照校准，不作为高保真样板。

## 范围与入口

### 产品中的触发位置

在 BW 工作区标题栏操作区新增常驻 **反馈 BW** 按钮，使用现有 Button/Tooltip，直接打开反馈表单。按钮必须出现在产品画布内，不允许用画布外的评审按钮代替。它是本主题的**拟新增入口**，不能描述为已有功能。

已有帮助菜单的反馈入口保留其现有 WeLink 投递语义；拟议的就地贡献入口接续收集会话，两者来源和结果可区分。现有工作区切换面板不是本主题的通用命令中心，不冒用其快捷键。未来 Bot 可增加入口，不替代桌面的就地入口。

开发版可用 React Grab 提供的原生元素选取与上下文复制；不能自造矩形圈选来冒充它。正式版按可用范围提供元素语义和现场附件；结构化元素信息与可见截图互补，不要求用户重复定位。浏览器 guest 的抓取、板面批注、整个桌面壳的采集范围分别说明，不把一种能力泛化成全壳已具备。

### 三类人、三个位置

| 角色 | 现场来源 | 第一个收集会话 | 修复 Worker |
| --- | --- | --- | --- |
| A：BW Builder | 自己正在使用的 BW 项目、界面与实例 | 自己本机独立的非 Git 反馈工作区；每个问题独立会话 | 已配置且授权的 BW 开发宿主上的独立 Issue 工作树 |
| B：其他项目的同事 | 同事当前业务项目中的 BW 界面与实例 | 同事本机同样的非 Git 反馈工作区，无需 BW 源码；不是业务项目的 cwd | 同事自己的 BW 仓或已授权、已连接的团队 BW 执行宿主 |
| C：普通反馈者 | 原渠道消息、用户提供的附件或报告 | 当前由维护者在维护侧的反馈工作区承接；Bot 自动入站属于接入后的目标 | 维护侧授权的 BW 开发宿主；反馈者无需创建树 |

反馈工作区复用原生非 Git 文件夹与会话机制。自动准备目录、登记工作区、加载收集 Skill 和后台提交为目标接线；不能把现有目录支持说成这些动作已自动完成。非 Git 目录不是权限沙箱，读取能力仍受执行工具权限约束。若模型未就绪，保留反馈与附件，告知继续方式，不转而污染当前业务会话。

原生 Floating Workspace 当前的结构化会话限制与默认目录不满足本方案，不能直接当作已经可用的隔离收集会话。原工作区与收集工作区独立，返回时恢复原草稿和位置。

## 完整用户旅程

### 1. 就地提交，再回原工作

人选中相关元素或附现场，在产品标题栏点反馈 BW，简述问题或期望。表单复用原生反馈输入、附件与失败恢复。系统保留来源实例、项目/工作区/会话定位、时点与返回点，交给独立收集会话；发送成功不强制导航到该会话，不抢当前焦点。

发送失败保留文字与附件，可重试同一次提交；取消不产生 Issue 或修复树。重复点击和恢复不得重复创建同一贡献记录。无需先选版本、目标、源码仓或开发主机才能提交现场。

### 2. 结合现场形成确定的问题

收集会话完整读取版本化的收集 Skill、模板和适用 Issue 规范。启动上下文明确来源机器、收集 cwd、能读到的材料及不能直接访问的来源；Skill 路径必须在执行宿主可读，不把提示词中的路径当成正文已经读取。

| 输入种类 | 作用与处理 |
| --- | --- |
| 用户原话、元素与截图 | 保留所指对象、实际显示和期望，源码栈有则使用；不足时才请求补充 |
| 应用版本、平台、实例与时点 | 区分正式版/dev、配置和事件发生位置；未知明确保留 |
| 操作、错误、trace 或崩溃材料 | 按相关性和已有授权取最小可用范围，诊断材料按现有审阅/脱敏流程，不默认捆绑全部日志 |
| 现行行为与已有 Issue | 查重并判断 BUG 或小诉求，能从证据回答的不反复问人 |

BUG 需要实际与应有行为、复现或观测路径、环境与证据；无法复现的事实不能写成已确认根因。小诉求需要对象、期望结果、范围和验收方式；涉及新的产品决定时遵循原型/规格确认规则，不因叫“小诉求”绕过必要确认。

必要澄清通过原生会话和需要回应的提示送达，保留原工作。Issue 沿通用规范查重与创建，附原始现场和可以执行的验收路径。纳版仅在已确认版本/目标时沿计划规范进行，不强绑 G3。反馈清楚但暂不修复，可以交给维护者继续，不强迫 C 配置模型或源码。

### 3. 从 Issue 交给 Worker

收集与修复是一个闭环中的两个职责、两个会话；不要求两个长期 Bot。A/B 已有开发位置与授权时，沿配置继续，不逐单重复选主机。缺配置时复用原生工作区创建器，目标项目固定为正确 BW 仓，可选本人已登记位置或已授权团队执行宿主。目标主机没有源码时沿已有项目位置设置/clone 路径处理，反馈记录不丢失。

先复用 BW 原生 Issue 开工/创建链建立任务关联的独立工作区，再通过原生编排向精确 workspace ID 派发 Worker。不能从编排的自动新树能力推断 BW 的 Issue/版本关联已写入。协调 Run 留在协调宿主；远端派工使用已配对可用的执行宿主，不能把任意 SSH 连接等同联邦执行。

Worker 收到明确 Issue、现场引用、预期与验收路径，在实际 BW 工作树读取 AGENTS、workbench-start 和相关规范。原生编排承接进展、阻塞、结果和消息回传；远端终端与本机结构化会话按真实支持条件呈现。回执显示宿主、仓库、工作树、分支及关联身份。断连或未知结果先按身份读回，不盲目新建第二条 Worker。

### 4. 看懂交付，必要时同路径复验

workbench-start 自身承担完整开发、独立检视和交付要求。PR 的问题描述、用例路径、基线/修复证据回指原 Issue；dev 入口说明对应的宿主、源码、分支、profile 与实例，避免看错环境。多个 dev 可隔离并行，不把某台验证机的性能限制写成产品规则。

人可读报告、打开正确 dev 验证或请强模型辅助检查；强模型守门员不是每单默认强制步骤。交付回传不抢原工作焦点。确认阅读记录、技术验证、合入、Issue 关闭和产品完成分别处理，模型不替人确认完成。

获准发布且修复进入可用版本后，将版本与原反馈关联并通知贡献者；贡献者可在日常使用的实例重复原动作。C 当前由维护者沿原渠道回告，Bot 接通后沿同一来源回传。未发布不得把 dev 验证当作正式版已修复。

### 5. 从真实人工介入反哺原件

收集会话与修复会话复用 workbench-start 的原始会话提取、逐条标注和报告脚本及六项指标，不另建反哺引擎。人的补充、澄清回答、批注、附件和评审意见按来源关联同一任务；跨渠道转发去重，模型转述不重复计为人消息。

Issue 标签用于筛选采用该工作方式的样本，不承载完成状态。提单阶段的报告写入 Issue 评论，没有 PR 时扩展同一报告脚本的输出目标；有 PR 后保持同一任务口径与来源，不重复计算。反哺的目标是减少相同人工补位：区分缺规范、未加载、未遵守、规则冲突和必要人的判断，经确认修回所属原件，包括收集 Skill、原型/用例规范或 workbench-start，而非在此复制规则。

### C 的渠道衔接

普通用户可以继续在 WeLink 或现有反馈渠道提供信息。当前人工接续保留原消息和附件出处；Bot 接通后沿同一整理 Skill 持续澄清、向维护侧交接并回告。Bot 自动入站、身份与附件传递、对外回告必须有真实接线证据；原生编排内部 mail 不能充当 WeLink 回告。是否参与修复是独立选择，不取消仅反馈的贡献路径。

## 验收与衡量

| 标识 | 场景与可观察结果 |
| --- | --- |
| BC-01 | 不操作评审工具，仅在产品画布找到并触发反馈 BW；位置、标签及新增身份一致 |
| BC-02 | A/B 发送后仍在原工作，草稿与位置保留；失败重试保留同一现场、不重复提单 |
| BC-03 | B 没有 BW 源码仍能整理问题；收集 cwd 不在业务仓，修复树只在指定 BW 宿主 |
| BC-04 | C 无本机 BW/模型/源码仍能反馈；维护侧会话保留来源，不假装远程看见用户现场 |
| BC-05 | 元素、附件、环境与问题对应；不足、未知与已观测事实分开，小诉求和 BUG 采用各自必要材料 |
| BC-06 | 已配置位置无需重复人工调度；缺配置使用原生创建器，派工与回执可按身份独立读回 |
| BC-07 | Worker 结果回指原问题与验收路径；原工作不被抢占，dev 身份可核对，完成由人确认；获准发布后可沿原反馈找到可用版本并重复原动作 |
| BC-08 | 收集和修复的人消息进入原脚本链，转发去重，Issue/PR 阶段口径一致，反哺修回原件 |

这些是目标验收依据；原型点击不计为真实 E2E。正式验收需覆盖实际模型、宿主、消息通道及独立读回。效率从真实任务的人工介入和返工观察，不在本规格另造指标公式。

## 取舍

本机中立收集目录让 A/B 可沿同一入口开始，不把有 BW 源码作为反馈门槛；代价是需要目录准备、Skill 分发与源现场转交的薄接线。正式版采集保留目标完整性，不能以当前仅 dev 支持 React Grab 为理由取消现场能力，也不能把尚未支持的能力画成已实现。

常驻反馈动作作为当前入口候选，优先让人可见、可就地操作；原型评审后再按原则 02 完成关键业务决定的最后对齐。仓外 plan 承载设计整理和后续执行安排，不替代本篇的目标行为。
