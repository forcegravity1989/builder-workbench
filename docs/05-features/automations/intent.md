# 定时任务：把定时工作调好再上线

> **状态：已 gate，2026-10-10 再审收窄**（首轮 gate 2026-10-09 用户逐条确认；2026-10-10 用户携能力矩阵证据再审，砍除零业界先例的边缘配置，收窄为会话创建、webhook 触发、导入导出三条主线，见范围）。本文不表示能力已交付。行为见 [spec.md](spec.md)，工程取舍见 [design.md](design.md)，链状态见 [STATUS.md](STATUS.md)。
>
> **维护约定**：给判断「定时任务值得做什么、做到哪」的人读。本文管价值与范围，不写控件与实现。目标或边界变化时更新，不追加讨论流水。

## 用户与问题

Builder 已经能把一件工作交给会话执行，也希望这类工作自动发生：每天早上巡检依赖、发版前准备材料、明早九点提醒一次。

现在的定时任务做不到「调好再上线」：

- prompt 直接手写保存，写错要到下次到点跑了才发现，没有生成和调试的过程。（本期 composer 会话解决）
- 调度只有五种无限循环预设，「明早九点跑一次」表达不了。（本期一次性任务解决；「每 N 分钟」预设增强经再审砍除，现有自定义 cron/rrule 已可表达间隔）
- 上次没跑完，到点会再开一个终端，越堆越多。（本期固定跳过解决）
- 任务只能定时触发，外部事件想触发只能人手动点。（本期 webhook 最小形态解决）
- 调好的任务搬不到另一台机器，得重填一遍。（本期导入导出解决）
- 任务后来被改过，历史说不清当时跑的到底是什么。（**本期不解决**：提示词快照经再审砍除，运行历史保留状态/错误/输出尾部）

## 价值与依据

核心收益：定时工作从「配好祈祷它跑对」变成「会话里调好再上线、外部事件能触发、配置可搬运」。

依据是两轮竞品调研（[research.md](research.md)），以 2026-10-10 能力矩阵（15 产品 × 9 能力，官方证据口径）为准：

- **会话内自然语言创建**有四家先例（Cursor `/automate`、DeepSeek Harness 对话建提醒、Devin 模板会话、Manus 自然语言创建），业界共识形态是「草稿 → 人确认 → 保存」。
- **非定时触发器**有四家先例（Cursor 多触发器、Copilot 仓库事件、OpenClaw Webhook、Manus 应用事件与 Webhook）。
- **配置导入导出**有先例（n8n JSON 导入导出；Cursor/Devin 模板），业界并明确建议「分离可分享定义与运行凭据」。
- **一次性任务**有四家先例（OpenClaw `--at`、DSH、Copilot CLI `/after`、Manus），引擎已随首轮实现落地。
- 被砍能力在矩阵中**零原生先例**：执行次数上限（15 家无一证实）、每任务并发策略配置（无一证实，业界做法是定死一种明确行为）、自动携带上次输出（无一证实，业界用持久记忆/会话复用/状态文件三种机制替代）。提示词快照业界普遍只到运行日志级，经用户判断本期不做。
- 早期依据的两处降级（2026-10-10 矩阵核实）：WorkBuddy 九项能力全部未查到官方证据，不再引用；DSH 的「指令快照」降级为未查到完整快照（其内置 Schedule 是会话内提醒投递）。

多个真实 Builder 的使用读回还没有，价值效果仍是假设。

## 目标体验

用户在计划屏点「AI 创建自动化」，用一句话说清目标，比如「每天早上九点检查依赖有没有新版本」「明早九点提醒我发周报」。AI 起草完整配置并展示全文，创建一个禁用状态的任务，试跑一次，自己读回结果、分析偏差、迭代修改——全程在对话里闭环。满意后，人自己在自动化页启用。

到点时如果上次还在跑，跳过这一次并记录。serve 模式下任务可拿到一个 webhook 地址，外部系统带 token 调用即触发一次。跑完或跑失败，沿用现有的会话完成通知。任务能导出成文件，在另一台机器导入、重新绑定后就能用。

## 范围与边界

- **做**：AI 生成与调试会话（composer）；webhook 触发最小形态（serve 模式 + 每任务 token，桌面模式如实提示）；导入导出；一次性任务（引擎已落地，暴露面走 composer 与 CLI）；并发固定跳过（不重叠、记 skipped_overlap、手动不受限）。
- **后续待办**：按任务通知设置与 Welink 群推送——现有会话完成通知已覆盖「跑完知道」（2026-10-09 拍板沿用）；届时随 Welink 接入一并设计。
- **不做**（2026-10-10 再审砍除，依据见上）：每 N 分钟/小时调度预设；执行次数上限；每任务并发策略配置；携带上次结果；提示词快照。另：GitHub/CodeHub 等事件源接入、模板市场、截止日期 UNTIL 仍不做，webhook 之外的触发器届时单独立特性。
- **沿用**：调度、运行、编辑器全部复用 Orca 原生 Automations；存储维持原结构，只追加可选字段，便于增量同步 upstream；外部 provider（hermes/openclaw）表达不了的新字段如实降级显示，不阻塞其余功能。
- **硬边界**：启用永远由人操作。AI 只创建禁用态任务和迭代修改，不替人启用——这是铁律三「完成由人确认」的延伸。webhook 触发的是已启用任务的执行，不改变启用状态。

## 成功判据与待决问题

判据：Builder 能从一句话出发，经试跑迭代得到一个按时正确触发的任务。一次性任务到点真实触发，跑完即终结。高频任务上次未完成时不堆叠。serve 模式下外部系统带 token 调 webhook 能真实触发一次运行。任务文件在另一台机器导入即用。杀进程重开，这些数字读回一致。

待决（需 gate）：无。原型豁免已拍板（2026-10-09）；2026-10-10 再审砍留已经用户逐项确认。
