## 用户与问题

Builder 已经能把一件工作交给会话执行，也希望这类工作自动发生：每天早上巡检依赖、发版前准备材料、明早九点提醒一次。

现在的定时任务做不到「调好再上线」：

- prompt 直接手写保存，写错要到下次到点跑了才发现，没有生成和调试的过程。
- 调度只有五种无限循环预设。「明早九点跑一次」「每半小时」「跑五次就停」都表达不了。
- 上次没跑完，到点会再开一个终端，越堆越多。
- 任务后来被改过，历史说不清当时跑的到底是什么。
- 跑失败了没人知道，要自己翻运行记录。
- 调好的任务搬不到另一台机器，得重填一遍。

## 价值与依据

核心收益：定时工作从「配好祈祷它跑对」变成「调好再上线、跑坏能知道、历史说得清、配置可搬运」。

依据是 2026-10-09 的竞品调研：Cursor 的 `/automate` 用自然语言生成配置；腾讯 WorkBuddy 把一次性当作一级调度类型；DeepSeek Harness 固定间隔与日历时间分模型、给每次运行留指令快照、错过只补最新；OpenClaw 给一次性任务完整生命周期；GitHub Copilot CLI 有 `/every` 和 `/after`。这些是同类产品的标配能力。本仓代码核对确认缺口真实存在：RRULE 解析器静默忽略 `INTERVAL` 和 `COUNT`，没有并发保护，运行记录里没有 prompt 快照。

多个真实 Builder 的使用读回还没有，价值效果仍是假设。

## 目标体验

用户在计划屏点「AI 创建自动化」，用一句话说清周期目标，比如「每天早上九点检查依赖有没有新版本」。AI 起草完整配置并展示全文，创建一个禁用状态的任务，试跑一次，自己读回结果、分析偏差、迭代修改——全程在对话里闭环。满意后，人自己在自动化页启用。

调度配置覆盖一次性、每 N 分钟、每 N 小时和执行次数上限。到点时如果上次还在跑，跳过这一次。每次运行留存当时实际递交的提示词快照，可以选择把上次结果带给下次。跑完或跑失败，沿用现有的会话完成通知（悬浮窗与系统弹窗）。任务能导出成文件，在另一台机器导入、重新绑定后就能用。

## 范围与边界

- **做**：调度表达扩展（一次性、固定间隔、次数上限）；AI 生成与调试会话；运行提示词快照；并发跳过；携带上次结果；导入导出。
- **后续待办**：按任务通知设置与 Welink 群推送——现有会话完成通知（悬浮窗与系统弹窗）已覆盖「跑完知道」（2026-10-09 拍板沿用）；届时随 Welink 接入一并设计通知判定与推送通道。
- **不做**：事件触发器（GitHub/CodeHub 事件，届时单独立特性）；agent 自适应节奏；按任务配工具白名单；模板市场；截止日期 UNTIL；precheck 独立调试。
- **沿用**：调度、运行、编辑器全部复用 Orca 原生 Automations；存储维持原结构，只追加可选字段，便于增量同步 upstream；外部 provider（hermes/openclaw）表达不了的新字段如实降级显示，不阻塞其余功能。
- **硬边界**：启用永远由人操作。AI 只创建禁用态任务和迭代修改，不替人启用——这是铁律三「完成由人确认」的延伸。

## 成功判据与待决问题

判据：Builder 能从一句话出发，经试跑迭代得到一个按时正确触发的任务。一次性任务到点真实触发，跑完即终结。高频任务上次未完成时不堆叠。任何一条历史运行能回答「当时用的什么提示词」。跑失败当天能看到通知（沿用现有完成通知）。任务文件在另一台机器导入即用。杀进程重开，这些数字读回一致。

待决（需 gate）：无。原型豁免已拍板（2026-10-09：无新屏，UI 均为现有编辑器与列表加控件，以真壳为对照，先例见 project-intake）；Welink 推送移后续待办（见范围）。
