## 里程碑与版本联动

里程碑安排特性在哪个版本上线、在哪个版本维护；单条操作不改变其他特性的安排。实际显示正式版本周期和该特性对应目标的人工结论。

### 规划：默认两版，整段安排

1. 每个特性默认两段：前五阶段 Plan / Design / Build / Test / Deploy 合为一段上线计划，后一段为 Maintain，处理众测反馈、问题和需求。没有阶段拆分表单、内部手柄或逐阶段排期。
2. 默认正常工作周是起点，不限制版本为一周。版本可为 5 天、8 天或其他长度；同版特性可以有不同起止。五阶段颜色保留原样，整段伸缩时按原比例变化，只表达规划分配。
3. 拖条身移动或换版，不改变版本边界；按抓取点所在日期识别目标，保留本段时长并在目标窗口内吸附，放不下则提示先调整时长或版本，不悄悄压缩或扩版。条身移动落在非法位置时恢复本次拖动前的原始计划，不提交途中经过的合法位置。拖两端才伸缩本段，超出所属窗口时扩容该窗口，其他特性不随之补长；缩短一条不自动缩短共享窗口。上线段换版若与自己的 Maintain 冲突，仅把该 Maintain 顺移到下一已有版本；无下一版本时沿新增特性的规则生成空周窗口。没有冲突则保留 Maintain；单独拖 Maintain 只动它。这一整次操作可一次撤销，不动其他特性。
4. 拖版本表头才是显式整版平移，带动本版所有规划；拖表头两端调整窗口，不能裁掉已有特性安排。调整与相邻版本产生新重叠时拒绝并提示先调整相关版本，不擅自推动其他版本；已有明确并行版本保持。操作、联动与撤销作为一步。
5. 移除特性旁“版本名 · 目标”标签及选择器，版本归属在上方表头读取，通过拖动安排。里程碑不选择 G1–G4，不存新目标关联；特性名默认就是规划行名。目标如何分配在版本首日 Plan 中决定。
6. 旧版、已经开始的版本也可重新编排，不因开工或验收冻结规划。编排仍经过草案、评审和主干更新；并发与身份检查继续有效。改规划不改已归档的计划、验收及实际事实。版本名是身份的一部分，生产改名仍沿既有安全条件，解除排期冻结不等于重命名已归档版本。

默认两版不限制实际只能出现两版。未完成时，后版计划继续纳入同一个特性主 Issue；里程碑 JSON 可以保持原先 A 上线、B Maintain，也可以由人重新编排，不自动新增、改写或回退它的阶段。

### 实际：默认不显示，只读目标结论

默认显示计划，实际只消费正式目标验收。当前范围不采集真实阶段工期，不再用五段 SDLC 颜色表示实际。特性首次交付显示“已上线 / 未上线”；已有前版上线后的目标结果显示“维护完成 / 维护未完成”，只指本版维护工作。未判定、未合入或读取失败不生成完成或失败结论；不计算延期、按期率或版本异常。

首次达成按正式版本历史顺序推导，不按可重新拖动的里程碑日期排序：A 未达成、B 首次达成、C 未达成，分别是 A 未上线、B 已上线、C 维护未完成；C 不会抹掉 B 已上线。C/D 正式纳入与结果不受 JSON 默认两段限制。这一投影不替代 provider 发布记录，不自动关闭 Issue，也不回写规划。

[日期差异样例](prototype.html?review=551&example=dates)使用独立样例草案，不覆盖原规划。开启实际时保留原版本头，在同一块中并列“规划日期 / 实际日期”；表头按里程碑规划定位，仅正式存在的版本补入并标“规划未安排”。实际日期指正式版本计划采用的周期，不代表测得的部署时刻。

特性旁以只读文字保留“规划：A 上线 → B 维护”；结果条按正式日期落在同一日历轴上，直接标明“版本名 · 已上线/未上线/维护完成/维护未完成”。实际视图取消贯穿泳道的版本分界，不能靠落在哪个版本头下猜归属。不叠加第二套 SDLC 或大版本表头，不把特性计划工期与版本周期当成同一对象比较。

日期不同的例子：里程碑 A 1–5、B 7–11；A 正式采用 1–10。A 头部同时显示两个周期，结果条为 1–10 并明确标 A；B 仍显示规划 7–11 和“实际：暂无正式计划”，不给它补造交付结果。若 B 正式也是 7–11，结果条保留真实重叠并按版本分层，不自动顺延。切回计划保留原编排，实际读取不回写 JSON。

### 关联与计划助手配合

里程碑不关心目标标题。读取某版计划纳入的、带精确 **特性** 标签的主 Issue，标题包含完整里程碑特性名时作为候选；名称去首尾空白，保留完整字符串匹配，不做简称、相似度或关键词猜测。`【版本|目标】` 前缀不影响包含匹配。无候选或多个候选均不选，保留规划。普通 UI 的 Feature 分类不等于这个主单标签。

唯一匹配后，以 `provider + repository + number` 的完整主 Issue 身份查后续版本，再读取该版 `tasks.goalId` 对应目标。一个目标最多一个特性，一个特性在同版归到一个目标，可含多条同特性的执行 Issue。后版沿用同一主 Issue，不因版本或阶段改变重建主单。历史不符合唯一关系时不广播结果、不另建消歧界面，留给计划材料核对。

验收只消费该份验收 `planRef` 固定的计划与人工 `results[].decision.outcome`，并核对归档 PR/MR 已合入。不能从当前编辑计划、Issue 关闭、PR 数、日期或目标标题猜完成。版本没纳入该主单就不生成该版实际。计划助手的完整步骤、最小材料例子与分发落点见 [计划助手与里程碑衔接](../version-planning/spec.md#计划助手与里程碑衔接)。

里程碑预期与首日 Plan 可有差异：`.bw/milestones.json.versionPlans` 保存预期版本日期，本版 `data.json.timeWindow` 保存正式采用日期；二者独立。Plan 决定本版目标、范围及日期，差异在现有会话中核对。没有里程碑不影响计划制定、保存和渲染。确认特性改名时同步主单标题与里程碑 title，经既有项目材料评审提交，保留稳定身份和历史引用；普通目标改名不触发同步。实际归档按固定计划读取，规划由人决定是否重排；不引入跨树自动同步、额外承诺快照或冻结流程。计划约定截止后照常发布，未达成范围由后版再次纳入；本轮不做延期判断。

| 标识 | 可观察结果                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------ |

| MF02 | 8 天版本含 5 天特性；整段等比伸缩，没有内部阶段手柄；表头平移才带动全版                                      |
| MF03 | 没有目标选择；旧规划可重排，已归档结果与顺序不变，JSON 不接收实际投影                                        |
| MF04 | 默认显示计划；正式结论映射上线/维护结果；无关联、冲突、未判定、未合入和失败不造结论                          |
| MF05 | A 未达成/B 首次达成/C 维护未达成/D 后续达成，分别未上线/已上线/维护未完成/维护完成；C/D 不依赖 JSON 有对应段 |
| MF06 | 精确特性标签、完整名称与完整 Issue 身份接通；目标标题可不同；一目标一特性，多执行 Issue 不重复计数           |
| MF07 | 后版纳入由计划决定；不自动结转、关单、改写目标结论，也不新增确认或特性结果表单                               |
| MF08 | 原撤销/重做、草案恢复、提交、返回和只读实际保持；生产重启后能由正式材料重算                                  |

存量排期继续可读可重排；旧 goalSlot/goalId 在读取时归一化移除，不参与里程碑匹配或保存约束。缺 versionPlans 时可借当前可读版本窗口展示，正常提交再保存预期，不宣称恢复了未记录的原始日期。旧空阶段只显示明确版本归属，不伪造历史计划；人重新安排时才生成默认段。

交付需核对完整旅程：规划 → 计划纳入 → 人工验收并合入 → 后版复用 → 重启读回。认可、实现和运行证据分开记录；原型、静态检视与生成一致性不能替代 Electron、模型或 provider 真实证据。

## 沿用的原界面与材料行为

每行一项特性，负责人是属性；上方关键节点写明日期与预期成果，版本仍在下方表头呈现。保留项目背景、记分牌、侧栏，不新增工作区。

### 关键节点与操作反馈（原型待评审）

关键节点使用具体日期，例如 11/05 发布 1.0 并正式推广；同月、同日都可有多个。保留原横轴和旗帜，节点区固定 88px；常态成果最多两行，点击旗帜或摘要展开全文。制定中，“关键里程碑”和“特性 / 负责人”各在表头单元格右上角放一个＋，点击添加对应对象，悬停或聚焦显示名称。成果直接在节点文本框编辑，聚焦时展开长文本，不撑高节点区；右上角 X 独立于文本框，编辑时位置和大小固定，点击直接删除，不弹确认，误删使用撤销。点旗帜展开日期和全文，日期就地修改。相同日期合为带数量的旗帜，展开后逐项操作；相邻日期拥挤时收起摘要，保留准确日期位置及可点击旗帜，不向下堆行。编辑继续使用可伸缩多行文本框。与特性共用等宽日轴和同一滚动区域，左右浏览保持对齐；更改特性/版本排期不自动移动关键节点。删除及修改纳入现有撤销和评审摘要，不增加目标绑定、依赖、自动完成或开发/维护段增删。

仅有月份的旧成果保留原文并显示“未指定日期”，由人补日期，不能捏造为月初或月末。原型样例模型使用 `milestones` 节点；生产目前仍采用月度 `months`，本轮不修改正式 schema、材料写入或迁移协议。待交互确认再按独立身份、保留原精度和统一评审原则落实。

引导沿仓内 Orca `ContextualTourOverlaySurface` 的锚定浮层思路：标题栏问号打开分步提示，支持跳过、关闭及记住已看状态；首次进入编排且从未看过引导时才自动提示。常态不增加说明行、折叠区或页面占位。原型模拟浮层交互，生产接入沿原生 contextual tours，不另建引导系统。提交开始立即锁住重复请求，按钮显示“提交中…”，全局通知随后更新为成功或失败；成功可查看评审，仍须合入后更新正式安排。失败保留草案，页面仅留简短重试/详情入口，原始错误不铺在泳道。正式接入沿项目里程碑已使用的 `sonner` 调用及应用壳统一的 `Toaster`，复用通知样式和宿主，不移植原型的演示通知组件；请求互斥贯穿提交过程。原型顶部“演示提交反馈”选择成功或失败后立即播放进行中与结果，失败可重试；这条演示不要求先修改草案，也不改变正式样例、提交基线或真实 Git/PR。实际编辑后的提交仍走原评审流程。

交互参考 [Linear 项目里程碑](https://linear.app/docs/project-milestones) 的日期节点和展开详情，以及 [Asana Timeline](https://help.asana.com/s/article/plan-and-execute-projects-with-timeline?language=en_US) 的菱形节点表达；只借用与 BW 现有规划相关的部分。

日轴每天等宽，特性栏 220px；计划模式的版本起止分界贯穿泳道，相邻版本以极淡底色区分，日格线保持次要；工作日历复用 `workCalendarDay`，休息日底纹贯穿泳道，没有真实年度样本时按普通周末，不增加导入/配置入口。空周只是背景，使用或命名时才登记版本，不批量建材料/会话。“添加特性”位于特性表头内，新增行插在顶部；默认先取覆盖当前日期的已有版本，没有则取最近未来版本，再取起点晚于首版终点的紧邻已有版本。没有相应版本才生成默认周窗口，不因首版跨周而跳过下一已有版本。默认两段；就地编辑名称和负责人，行首排序、行尾移除，统一撤销。计划与实际常态行均为 88px；正式版本真实重叠时按版本分层增加行高。统计和图例共用一行，实际模式以版本周期说明替代阶段图例，版本段内标示版本名和结果，同一版本头内增加一行日期对照。

同一特性前后计划不重叠或倒序，不同特性可并行；拖动按半天、版本表头按天吸附，Escape 取消；边缘伸缩遇非法候选时保留最后合法位置，条身移动落在非法位置时恢复本次拖动前的原始计划。比例内部分界不要求半天吸附，不显示可编辑内部时点。版本名清空只撤回从未提交且无人引用的草案空版本，不删除真实版本材料。历史空阶段不自动补五阶段。

### 编辑历史、提交与正式来源

恢复本机草案时若项目材料已更新，明确提示本机草案与最新规划不同，保留输入并由人选择载入最新规划；退出编辑仍显示正式安排，不将其称作草案。来源冲突未解决前，提交保护仍有效；不因版本已开工增加排期冻结。Git 回退项目材料不会自动删除本机未提交草案。

进入编辑后保留一张含本次输入的泳道，不再设置“查看正式安排”切换按钮。标题左侧返回箭头结束编辑，回到只读正式安排；草案和本次撤销记录保留，再次点“规划里程碑”继续编辑，不提交也不放弃修改。右侧不为返回新增按钮。顶栏用同一个评审入口表达下一步：有改动时提交或更新评审，无改动且已有 PR/MR 时查看评审，已合入但本机未更新时更新正式安排。正常状态不再另列标签、评审链接行或草案保存提示；保存失败与评审读取失败仍明确提示。提交按钮按实际变更及材料完整性启用，改动摘要内仍可查看已有评审。左右弯箭头逐步撤销/重做一次字段编辑、节点拖动或行排序；字段输入及离开时的空白整理合为一步，输入框内保留原生文本撤销。相同修订的刷新和版本页返回保留历史；旧版本也可重新编排；恢复草案只核对来源修订和并发，不按开工状态锁定排期。提交成功建立新的编辑基线并清空撤销记录，不撤销 Git 提交、推送或合入。撤销/重做使用标准弯箭头图标；旁边以分隔线区分独立的恢复图标，悬停/聚焦明确为“放弃本次修改，恢复最近提交”，直接恢复最近一次提交后的基线；外部冲突时明确以新读到的材料重新开始。

| 当前情况                   | 呈现与动作                       | 结果                                         |
| -------------------------- | -------------------------------- | -------------------------------------------- |
| 与最近提交一致、无待审记录 | 提交评审禁用，历史按实际记录启用 | 不创建无意义提交                             |
| 有未提交变化               | 撤销/重做、提交评审              | 核对只读变更摘要后提交                       |
| 已提交                     | 查看评审                         | 最近提交成为新的还原基线，正式安排保持原样   |
| 待审时继续修改             | 更新评审                         | 提交更新同一评审草案，未提交部分仍独立       |
| 人工合入                   | 更新正式安排                     | 只采纳已合入的提交快照                       |
| 合入后还有本次编辑         | 更新正式安排                     | 更新后保留这些修改，不能把它们夹带进正式安排 |

“放弃本次修改”仅恢复到最近一次提交快照，第一次提交前恢复到进入规划的正式基线；不会撤销已提交/已合入内容。普通总览读本机主干基线，编辑读取项目材料提案与本次输入；刷新材料/评审不等于更新主干代码。提交、待合入、待更新不代表阶段成果或特性交付已完成。

复用现有 `bw/project` → PR/MR → 主干的项目材料链，不增加审批角色。正式材料从固定主干基线读取，已提交草案与应用内未提交编辑分别保存。提交前验证内容指纹、分支 HEAD、工作副本与文件修订；冲突保留草案并提示核对。只自动快进，不重置分叉或脏树。失败区分本地提交、推送与评审创建，可重试已提交内容。

应用内切页返回保留月份、编辑和视口；未提交草案与对应基线异步保存于本机 profile 文件，名称或负责人未填完也保留。正常保存不占据独立一行；只有最新快照耐久写入确认后才作为可恢复记录，尚在写入的输入不承诺强退后恢复。重启核对 Git 来源后恢复已保存输入。保存失败显式提示；基线变化保留输入并阻止静默覆盖。该缓存不跨机器同步，不替代 .bw 正式材料。撤销栈不跨重启，已提交草案和正式材料仍从 Git 重读。浏览器客户端未接入本机文件恢复，会明确提示。具体事务和数据源见 [里程碑实现设计](milestone-design.md)。

### 进入版本与返回来源

版本表头名称旁及实际结果条均可进入对应版本总览。打开前核对正式材料的 version + cycleId；尚未正式登记的版本提示先合入更新。返回恢复项目、草案和视口，不覆盖未提交修改；不根据名称猜某个目标的导航位置。版本总览用于查看目标、Issue 和验收细节。

## 入口与用户旅程

项目连接、宿主路由、文件与命令执行沿用 Orca 原生能力；BW 不按本机、Web/配对或 SSH/WSL 另设产品限制。操作在工作树所属宿主执行，连接或权限不可用时呈现原生失败，不切换到其他机器读写。

指标在总览的记分牌里呈现，替代原业务／项目两区；项目研发统计（提交、合入 PR、开放 Issue）不再在总览展示。场景即指标目录里的特性，未指定特性的指标归“主要”页签，不等于项目研发指标。

| ---- | ---------------------------------------------- | -------------------------------------------------------------------------------------- |

## 行为与异常

### 配置与目录

定义来自 .bw/metrics.toml，沿 schema2，协议见 [metrics](../../../standard/system-prompt/references/metrics.md)。北极星可缺席，占位不成为指标。可选的 [[feature]] 声明场景名称（name）和价值说明（value），决定页签顺序；场景与说明随目录编辑，产品不写死。缺文件、坏定义、缺脚本和采集失败分别表达；feature/leads 歧义或场景重名提示修正，不随意关联。

“配置指标”每次在独立固定的 bw/metrics-refresh 分支和工作树中新建 Orca 原生会话，并离开总览进入该会话；已有同分支工作树和未完成改动保留，不续接上次会话，不另建 BW 配置面板或登记指标自动化。维护树干净且只是落后于当前基线时，读取目录会把它快进到基线，使会话改的就是记分牌上这份目录。记分牌读基线；维护分支已从该基线提交了新目录时，回到总览重读那次提交。维护工作区里的配置文件直接显示在记分牌上，和已提交内容不同时标为配置草稿；打开这个工作区时，会话在上、记分牌在下，中间的分隔可以拖动高度，文件保存后隔几秒跟上。记分牌上的批注直接发给这个指标配置会话，不再选择会话。读数仍按已提交修订采集，草稿不写入正式读数。工作树定位、创建、目录、登记和宿主路由沿用 Orca，不另设目录规则或删除重建。接入已有指标工作树时保留该项目此前接入的其他工作树；切换计划、验收后指标工作树仍可从侧栏进入。加载项目约定、通用 SYSTEM 与 metrics-refresh Skill；提示携带当前定义、来源问题和返回总览上下文，不注入 week-planning。返回时恢复原总览的指标场景页签。

定义和脚本按项目规则评审合入。目录从主干基线（主检出 HEAD，或仓库设置钉定的基线）读取最新已合入修订，不在后台 fetch，不把固定计划/验收树的旧 HEAD 当最新目录，也不向这些材料树合并指标草稿。读取失败保留原目录及其来源并显示错误，不能假报最新。配置树草稿可试采，须标明草稿，未合入前不成为三屏正式目录；主检出的新鲜度由总览「更新代码」按钮负责。

### 采集与可信度

仅 collect.kind=script 且 retro=true 的有效业务定义进入可用目录，脚本按 day/week 返回真实历史 points。retro=false、手填或仅返回当前 value 的输出均不作为可用采集；页面提示配置历史来源，不补造曲线。源数据和必要的历史存储由用户项目或外部服务负责。

刷新使用明确项目/宿主/cwd 和 argv，复用权限、失败和超时规则。相同来源/定义/窗口/宿主的并发刷新去重；切项目不串值，旧响应不覆盖新请求。成功标 value、source、collectedAt，历史另有真实窗口。失败保留可识别的陈旧证据，不换新时间、不补 0、不补前值；真实 0 有效。

首次加载读取目录及已有采集缓存，并准备最近五周、十四天所需数据。业务日／周口径分别采集，不能用日均值简单合成周均值；记分牌先回显周窗口，日窗口随后准备，准备期间不清空已得数据、不重复联网或跑脚本。仅 not-collected 的缓存缺口自动采集一次，失败不自动重试。缓存缺口及正在采集不计为读取失败，等待时显示“正在读取”；采集结束后才展示本次实际失败，无数据保持未知。之后离开再返回总览仅复用本次应用运行的快照；用户点「更新代码」（快进主检出并重读目录）或对应指标刷新按钮（重新采集）才更新。业务手动刷新维持阻塞遮罩，完成或失败均解除；来源或采集失败保留旧读数及原采集时间，明确提示失败。显示窗口固定于采集时刻，跨日／周不把缓存旧数标成今日或本周。

不引入每日采集自动化、bw/ledger 或每日 readings 写回。每次新采集解析主干基线目录，并在本次执行期间固定同一份定义、脚本及相关依赖修订；项目身份、窗口与来源随结果保存。旧计划 baseline 和归档证据保持只读，不能被刷新覆盖，也不用于阻止新采集。无可用采集可保存目标草稿并提示配置，不能标成有依据的数值承诺。

### 呈现与关联

记分牌按场景分页签：先列 [[feature]] 声明的场景，再列只在指标上出现的特性，未指定特性的指标归“主要”。每签展示一个结果（计划写了目标值的滞后指标优先，否则该场景第一条）和一个引领（leads 指向这个结果的引领，计划写了目标值的优先；没有则取未关联任何结果的引领，不借用关联其他结果的引领；仍然没有引领时，第二格展示该场景的下一个结果，并标成结果）。其余指标不在牌上列出，缺结果或引领时该栏只留角色名。每个指标显示名称、最近读数（带单位）和最近五周窗口的走势柱；有完成线时，完成线原文贴在读数右侧。口径、采集时间和未知原因不写在牌上。失败与无读数都显示未知，无读数的走势柱与 0 值可区分，字符串读数只作文本。leads 不等于已证明因果。

聚焦由当前版本的计划推出：计划目标里给某个场景的任一指标写了非空目标值，该场景即本版聚焦，页签排在前面，名字前有一个点；其余场景隔开一段，不写“聚焦”“日常”。完成线依次取所展示结果、所展示引领的目标值，贴在读数旁。输赢只由最近数值读数对比带比较方向的完成线（≥、≤、>、<、=）得出：达到时点和数字用成功色，未达到时用警告色；完成线是纯数字、方向缺失、单位与指标不一致，或没有数值读数时点和数字保持中性色，不装绿，也不写“已达完成线”“未达完成线”“看不出输赢”。完成线比较不是验收结论，目标达成仍由人确认。价值说明留在指标目录，不出现在牌上。产品不在记分牌上写每周短会用法，也不另存承诺记录。

计划只写版本目标，不改项目长期目标；验收可从最新目录选择指标补充实测，实际值由脚本提供。旧 baseline 保留，不能因 definitionHash 或 configurationCommit 与旧计划不同而阻止采集。证据详情展示来源、采集时间、配置提交与采集脚本修订，定义指纹保存在材料中，供人追溯核对；界面不提供专门的定义或单位变化对比，不自动计算跨口径改善幅度或判断达成。新增验收指标不改原计划承诺。

指标依据版本从主干现行目录与有效当前计划读取，固定修订和来源校验沿原材料服务；落后的固定工作树不覆盖正式基线。读取失败与没有材料分别表达。计划/验收全文和相互引用核对在原生版本入口完成。

### 布局与动作

- 顶部为可折叠的项目名片：默认收起为一行，显示项目名称、健康状态与版本；点开后展开「想做什么／对标／目标方向／项目群／仓库」；名片 PR 状态行（待合入／已合入未更新／没读到）不随字段折叠。缩小卡片纵向内边距与字段行距，保留字号和完整字段；高度随内容增长，不用固定高度裁切长文本。缺失字段如实表达。总览不显示北极星卡片，不以“有读数”代称项目健康。
- 总览不再铺计划/验收全文双栏；不再放独立的指标依据版本选择器，当前版本提供指标聚焦上下文，版本全文由原生版本入口承接。页头“更新代码”快进主检出并重读现行材料，保留未提交里程碑草案。
- 记分牌位于项目里程碑之下：标题行是记分牌，配置草稿在标题旁标「草稿」，旁边是「批注」「配置指标」和一个刷新图标。「批注」打开与计划/验收相同的板面批注：点击指标记下讨论，编号角标与面板一致，可复制或直接发给指标配置会话；批注只留在当次打开的总览里，重启不保留，也不改指标目录和完成线。进入批注时按钮保持按下，牌上不另起说明。走势固定为周窗口。刷新重新采集各场景读数，配置入口只保留一处。没有任何场景时不另写配置步骤；指标目录未就绪时显示这一状态。
- 页面不放迁移过程、协议字段或“为什么尚未实现”的长说明。草稿、未采集、失败和数据日期等影响判断的信息保持可见，具体原因按需展开；目录和版本读取失败仍在对应位置可见，记分牌上没有读数时只显示未知。
