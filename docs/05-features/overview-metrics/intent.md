# 总览指标：用真实数据理解项目与特性

> 给 Builder、Leader 和产品评审者在判断价值时读取。本文管用户问题与范围；行为见 [spec](spec.md)，设计见 [design](design.md)，证据见 [STATUS](STATUS.md)。价值或边界变化时更新。
>
> 状态：三特性边界与本特性定义已合入，用户已授权实施；产品尚未交付，执行证据见 STATUS。

## 用户与问题

Builder 和 Leader 需要据实际情况制定版本目标、核对交付。bw-orca 总览仍有演示数据，main 的业务指标、特性归属、引领/滞后关系及项目研发趋势尚未完整迁入。手填数字和多屏各自记数不能提供可核对的依据；为补历史而增加每日记账又带来使用负担。

## 价值与依据

让总览、计划、验收读同一个定义与脚本来源；能查历史就查历史，只能查当前就诚实显示当前及时间，缺数据保持未知。依据是 main 已有 UI/协议/采集脚本、目标分支源码和本轮用户反馈。旧 Rust 功能不构成 Electron 交付证据。

## 目标体验

总览保留业务和项目两区：业务按“主要／特性”组织滞后及引领指标；项目显示提交、合入 PR、开放 Issue。已有脚本直接刷新；需要新指标时点“配置指标”，在独立的 Orca 项目任务内确定口径、补采集脚本并验证，完成后回总览。计划选择有效指标填写目标值，验收刷新实测，由人判断。

## 范围与边界

- 沿 main 保留图表、特性归属、引领/滞后、日/周和来源，优化当前前端呈现；不新增指标侧栏。
- 仅支持脚本实际读数，优先可回溯查询，允许仅当前查询。不新增人工录数、每日采集自动化、常驻记账分支或每日写回链。
- 计划/验收归档保留当时采用的读数证据；这不是持续采集台账。无来源、无当前能力的指标不进入可承诺目录。
- 保留项目卡、北极星和版本记录上下文；多周计划/验收摘要由两个版本特性提供，集成层装配，不另开里程碑特性或重构整个总览。

## 成功判据

三个界面对同一定义、窗口和来源显示一致；零、未知、失败和过期可区分；脚本能重算的历史可独立复算，不能回溯的事实不被画成连续历史。首用周收集口径歧义、采集失败和实际数据决策案例，建立有效观测后优化；不先编收益比例或健康评分。
