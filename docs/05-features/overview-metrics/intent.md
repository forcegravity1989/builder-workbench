# 项目总览：用连续排期安排持续交付

> 给 Builder、Leader 和产品评审者判断价值时读取。本文管项目总览的用户问题与范围；行为见 [spec](spec.md)，现行指标实现见 [design](design.md)，认可与证据见 [STATUS](STATUS.md)。价值或边界变化时更新，不承担跨版本持久化协议或版本执行细节。

**状态**：自由日期排期与再次维护的意图及[最新原型](prototype.html?review=590)已获人工确认，关键逻辑已确认，进入正式实现。这里描述目标体验，不把原型当成已交付能力。

## 用户与问题

Builder 与 Leader 会在月初规划接下来几个版本，但一个特性不一定在某版结束时做完，已上线的老特性也可能隔一段时间再次投入维护。把特性锁进固定版本，会迫使人迁移或重建记录；只看新特性，又会漏掉老特性的维护安排。

项目总览应让人看到哪些工作正在安排、还要持续多久、哪些老特性重新投入，同时能回看前月和正式结果。规划需要粗粒度，名称之外不应强迫先填负责人、目标或版本关联。

## 目标体验

关键里程碑记录日期和预期成果；版本在连续日轴上表达交付节奏；每项特性以 Build 和可重复的 Maintain 段独立编排。Build 没做完就延长，跨多少版本都不限制；维护再发生就给原特性追加一段，间隔留白。

查看范围跟随用户正在浏览的日期并可恢复，不随月初清空。近期还有安排的特性易于看见，历史行通过筛选找回；再次维护沿用同一身份。排序帮助找工作，不拿条长代表优先级或工作量。

规划颜色表示预期阶段，正式完成由已有目标验收确认；维护结束只表示本轮安排结束，不意味着这个特性永远结束。维护投入通过对应版本的目标与任务体现，里程碑不另造人天统计或完成台账。

## 范围与边界

- 特性日期与版本窗口分别调整。日期交集供计划参考，正式纳入由各版计划中的特性主 Issue 与目标关系决定；跨版和再次维护复用同一主单。
- 原计划、验收、PR/MR 及主干更新链继续承担协作。里程碑只编辑规划，不改固定验收、不自动纳入后版，也不创建或修改 Issue；任务创建与状态由原有计划和任务流程处理。
- 特性名称必填并给清楚的字段反馈，负责人选填。添加和追加维护就近放在对应表头或特性单元格，以紧凑图标和短提示表达，不铺开大量文字按钮。
- 默认按查看日期筛选，历史资料保留；不增加完成后自动归档、独立结果表单或第二套业务数据库。
- 项目背景、记分牌和版本执行入口沿用。版本总览读取需适配自由排期，不能把跨版日期跨度当成每版工作量或真实阶段工时。

## 成功判据与证据

人能在同一条旅程里完成月初编排、跨版延期、老特性再次维护和跨月回看，且不重建特性、不改历史结论。新增必填反馈明确；没有负责人也能继续评审；误加的一次维护可以撤销。
