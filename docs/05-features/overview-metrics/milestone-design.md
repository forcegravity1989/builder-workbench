# 项目里程碑：材料与提交设计

> 给实现、计划助手接口维护与检视者读取。本文只管 #440 的数据源、编辑状态、提交事务和版本入口；用户行为见 [spec](spec.md)，指标实现仍在 [design](design.md)。协议或代码责任变化时更新；不定义 #334 的特性卡持久化关系，不收录交付流水。

**适用边界**：开始制定版本计划时冻结原计划及版本日期。实际进度复用 #334 的 useVersionFacts 和 featureTimeline，按已开始版本的目标回显；不建立宏观特性行到 Issue 的持久化绑定。原计划单独保留，避免把无对应关系的排期当成实际目标的基线。

## 同一份版本材料

版本日期保存于 `.bw/planning/<version>/data.json` 现有 schema 3 的可选 `timeWindow: {start, end}`。两端均为 ISO 日历日期，包含起止日；开始不能晚于结束。没有日期的历史版本保留，但不画时间窗口；不扫描 Releases、标签或提交日期补时间。

浏览空周不会生成材料。实际安排特性节点或填写空周版本名时，草案按周一至周五登记未来版本；提交才生成空计划及 cycleId，不准备工作树或会话。真正开始版本计划时沿现有 initializeEmptyPlan 的 create-only 路径，已有计划与 cycleId 保留。计划助手、界面和材料 CLI 使用同一 schema，编辑其他字段时保留 timeWindow。固定树与主干间仍通过 Git 评审同步，不把不同工作副本说成即时镜像。

宏观规划保存于 `.bw/milestones.json`：

- `schema_version: 2`。
- `months[]: {month: YYYY-MM, outcome}`：一个月一条阶段成果。
- `features[]: {id, month, title, owner, deliveries}`：数组顺序就是显示顺序。每次安排为 `{id, version: {version, cycleId}, stages}`；稳定安排 id 不随拖动改派版本变化。阶段为 `{phase, start, end}`；日期使用北京时间的民用半日坐标 `YYYY-MM-DDT00:00` 或 `T12:00`，结束为不包含的边界。首版 Plan/Design/Build/Test/Deploy，后续 Maintain；实际事件不写入这份规划正本。
- 行 id 仅识别宏观规划行，不是主 Issue 身份；不复制版内目标、任务、验收或执行状态。

版本引用必须同时核对名称与 cycleId。改名只允许未开工、仅有空计划且无原生版本绑定/其他材料的版本，保留 cycleId 并更新本次规划引用。已开工版本名称只读，版本计划助手核对宏观安排与实际计划差异；不得用宏观改名改写历史。整体移动版本时关联阶段同比平移；扩缩版本边界不缩放阶段。阶段超出版本、次序倒置、Maintain 早于上一版结束均阻止提交。版本可以重叠，表头分行避免覆盖；拖入多个重叠候选时不猜归属。

冻结以现行原生版本绑定、已有计划内容，或留存原生计划分支上名称与 cycleId 双重吻合的版本材料为依据，不等待计划 PR 合入。提交服务从来源快照比较已开始版本的名称、日期和各特性的原计划，不信任客户端的开工标记；列表截断时不能判为未开工；原生树删除后仍核对留存计划材料，分支名不单独作为身份。写入锁内再次读取绑定和材料，阻止编辑期间刚开工的版本被旧窗口覆盖。原计划的阶段不能新增、移除或改派；名称、负责人及行排序不改变原计划，后续未开工版本仍可排期。

## 正式、已提交与未提交

正式材料固定读取主干基线提交。bw/project 仅提供已提交提案，不能覆盖主干正式投影。按文件内容构造修订，不能以 PR 状态代替实际材料。

应用视图会话保存未提交草案、最近提交基线、月份与视口；从版本页返回恢复原状态。恢复记录通过本机薄 IPC 写入当前客户端 profile 的 `workbench/milestone-drafts/<scope哈希>.json`，以项目、仓库、执行宿主、runtime owner 和工作树隔离，不走远端材料路由。复用原生耐久写入：临时文件刷盘后原子替换；异步保存不阻塞输入，只有最新快照得到落盘确认才显示“本机草案已保存”。强退时尚在保存的输入不作已保存承诺。

同 scope 的读取、修订校验和写入串行；客户端一次只有一个在途保存，后续输入合并为最新快照，旧响应不覆盖新输入。清除草案也写入新修订的空记录，避免陈旧窗口复活旧输入。坏文件、读写失败或其他窗口修订冲突保留输入并明确报告，不静默覆盖。恢复允许名称/负责人尚未填完；重启先从 Git 读取最新材料，基线一致才续编，否则保留草案并阻止覆盖。它不是正式数据源，也不跨机器同步；实际提交仍经过同一 .bw 事务。提交成功/全量放弃后清除对应恢复内容；撤销栈不跨重启。提交期间各页面共用写入状态，迟到响应不覆盖另一份编辑。浏览器客户端尚不支持该本机文件恢复，编辑时明确提示，不能假报已保存。

编辑会话在内存中维护撤销/重做快照；一次字段编辑及其失焦整理合为一步，节点拖动、行排序和移除独立成步。历史不持久化，不回退 Git；相同基线的刷新/返回保留历史，已确认的新提交清空历史。“放弃本次修改”恢复最近一次提交后的基线；第一次提交前恢复正式基线。外部修订变化后旧草案不能静默提交，须核对；界面保留冲突输入。待合入可继续修改并更新同一 PR/MR；推送或创建评审失败可重试已经落盘的提交。

## 写入事务与执行宿主

复用 Orca 原生项目/宿主/工作树解析、bw/project 创建登记、Git runner、现有 GitHub/CodeHub 评审入口。RPC 只接收受信任 scope，不接收任意文件根。当前文件事务支持所属本机/配对 runtime；SSH 执行适配仍未接入，明确返回错误，不把 SSH 路径交本机文件 API。

同项目名片与里程碑提交共用串行队列；多进程通过与材料服务一致的文件锁协作：

1. 核对 bw/project 登记、实际分支、干净工作副本、调用方读到的正式内容修订及分支 HEAD。
2. 只自动快进；分叉保持原样交原生会话合并，不 reset 或强推。
3. 校验所有材料、准确身份和排期冲突；已有计划非日期字段保真往返，不能通过此入口删除已有版本。
4. 获取变更文件锁，再重查权限、基线、HEAD、分支及所有源文件字节；全部核对后才写入。路径拒绝符号链接和非普通文件。
5. 耐久替换文件、提交指定路径，文件锁持续到提交结束。失败保留工作副本供核对，不自动回滚用户输入。
6. 非强制推送，复用开放评审或创建新 PR/MR。提交、推送、创建评审是不同结果；不得把失败当正式安排或人工验收。

多文件写入与 Git 提交不是跨系统原子事务；进程中断或工具失败可能留下未提交文件，下一次入口检测脏树并停止覆盖。此时用原生会话核对后继续，不静默补写。

## 界面及版本衔接

上方独立月度轴每月一个旗帜及一句成果；正式视图隐藏空成果，空成果不阻止特性排期提交。点击月份定位下方连续泳道，所有特性按一个稳定顺序呈现，不按月份过滤。下方直接编辑特性名/负责人、拖动阶段与行序；行末移除，统一顶栏撤销/重做和恢复图标。

版本与背景周共用日期坐标。已有 timeWindow 原样绘制；空周只在使用时生成版本，失败或取消拖动不遗留登记。新特性在当前月当周安排，未来月份优先复用该月首个已有窗口；新版本名称按现有名称末尾数字递增，缺少数字风格时使用 v1.0.0 起的可编辑默认名；不会据此修改旧版本身份。

界面支持按天调整未开始版本日期，阶段按半天调整；不提供月份选择器、版本登记弹窗、旧版本关联、独立日历或定位最新。模型可在原版本材料中补日期或修改为跨周窗口，下一次材料读回照实渲染；未开工才允许改名。预置加班日未有真实来源，不带入样例、不提供用户导入。

仅在版本表头提供跳转，打开前核对正式材料的 version + cycleId；未正式登记提示合入并更新。来源作为页面临时参数保留，返回恢复月份、草案与视口。版本表头只定位准确版本，不提示缺少特性绑定。计划助手继续负责特性 Issue 与版本范围。

日历由 `src/shared/workbench/work-calendar.ts` 独立查询，全年预制数据按年份建立一次 Set 索引；原型和生产共用。没有预制年份时按普通工作周，不冒充真实华为班/休数据。

旧试用格式不会自动推算为阶段工期：正式材料解析失败会明确指出 `.bw/milestones.json`，本机草案解析失败会指向当前客户端 profile 的 `workbench/milestone-drafts/`。两处原文件都保留、阻止覆盖，由模型核对转换后刷新/重试。恢复文件以 scope 的 SHA-256 命名，JSON 外层 payload 保留原草案、基线及来源修订；迁移要同时核对它们，不改修订伪装同源。
