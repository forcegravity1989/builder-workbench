# PR / MR 评审通知实现计划

> 给本轮实现者与 reviewer 读取；维护收件人选择、项目访问和 CodeHub 接入的实现顺序、复用落点及验证边界，不承载施工流水。产品行为正本为 [spec](spec.md)，价值为 [intent](intent.md)，交付状态为 [STATUS](STATUS.md)。范围确认或实现依赖变化时更新，执行证据进入 PR。

状态：owner 已通过本轮 AskUser 确认范围，实现和简单 CDP 已完成，正在交付 PR。以下是本轮交付目标；实际验证与未验边界以 STATUS 和 PR 证据为准。

关联 [Issue 199](https://github.com/forcegravity1989/builder-workbench/issues/199)，继续 [PR 478](https://github.com/forcegravity1989/builder-workbench/pull/478) 原分支 `kanadead/issue-199-v0.8-g3-welink`。工作树沿用主仓 E 盘 `.bw/worktrees/pr-478-review/builder-workbench`。

## 1. 拟定范围与交互

1. 原生工作树菜单「发送评审…」打开小弹窗，展示当前 PR / MR、可搜索的已连接主机多选列表、全选操作及「发送至 N 台主机」。复用原生 Dialog、Command、多选与 Button；通知浮层继续展示收发记录，不新增导航或设置页。
2. 首次默认全选当前已验证、传输就绪的主机，用户可以取消或多选；不再探测对方是否登记同项目。列表明确是主机，不把主机名视为人员账号或角色。
3. 再次发送使用同一弹窗，默认沿用这条评审请求上次的收件名单，可显式增减。新增连接不自动加入；旧目标断开、移除、重配时明确显示不可用，不静默替换身份。取消弹窗或零选择不投递、不推进轮次。
4. 发送前重新核对原生连接与配对版本；逐台投递、逐台显示结果。一台主机失败不阻断其他已选目标；接收端持久保存后才记送达，至少一个成功才推进轮次，全部失败不创建虚假成功记录。
5. 对方未在本机接入项目也接收并保存通知。打开时优先选择本机相同远端身份的项目，其次复用当前可访问的原生远程项目及其宿主上下文；两者都没有时保留通知并提示「暂时无法访问该项目」。项目或连接后来可用时重试定位与事实读取。
6. 你连接对方即可通过该方向投递；对方要使用你主机上的项目，需要自己已有对你的有效连接。通知不创建反向连接、不授予新权限、不自动克隆或接入项目。
7. GitHub PR 与 CodeHub MR 使用同一通知旅程，详情、评论操作、Checks 与合入权限沿用各 provider 的既有能力。只有原生查询能够明确定位的开放 PR / MR 才可发送，定位失败或有歧义时明确说明原因。

本期不接 WeLink，不做群组、成员管理、角色识别、人员账号与多设备映射、离线代投或后台自动重试。未来群组可以成为选择收件对象的入口，本次不预建群组协议或占位页面。

## 2. 实现顺序与复用落点

### A. 行为、原型和发送 UI

- 同步现有 intent / spec 的发送对象、两类项目访问路径、再次发送、CodeHub 和验收点；调整 STATUS 时区分本轮待实现、历史验证和当前证据。
- 在 `WorkbenchSendReviewMenuItems.tsx` 与通知再次发送入口共用收件人选择流程；弹窗通过原生挂载方式持有，避免菜单关闭导致弹窗卸载。
- 优先复用 `components/github/PRFilterPickers.tsx` 的现有多选能力及 `components/ui/` 原语。只在确有共用需要时抽出原组件，不复制一套主机管理器或扩大改造其他选择器。
- 原型继续直接导入产品展示组件；新增弹窗和场景使用同一组件，只有主机、请求与反馈使用模拟数据。原生 PR / MR 详情继续标为「沿用」，不另画页面。

### B. 收件名单、投递和持久化

- `transport.ts` 仅列出当前已验证且就绪的原生主机；删除同项目探测及其整体中止逻辑。发送仍保留 pairing revision、实际 runtime 身份和鉴权校验。
- 删除 `workbench.review.project` RPC 及无用 schema 引用、生成目录登记和对应废弃用例；接收端删除项目登记门槛。项目身份匹配仍保留给详情定位使用。
- `store.ts` 接收用户明确选择的目标，保留逐主机结果及完整选定名单；增加或移除收件人不重建旧请求，继续同一周期的新轮次。被移除主机已收到的旧通知不远程撤回。
- 保留原生 RPC 接收、串行原子保存、周期与轮次防重放以及损坏存档不覆盖的行为；失败结果不得变成成功或零意见。投递前持久保存待重试请求和明确选择的名单，确认丢失时手动重试复用相同时间与身份；成功后移出待重试，删除本机记录时同步清理，不新增后台重试。
- 仓库身份采用原生规范化规则，保留主机与完整仓库路径，支持 CodeHub 多级路径；同步通知键、项目匹配和相关消费者。已有内部试用存档需要时在读入边界一次性迁移到唯一结构，不静默丢弃，也不长期维护两套发送协议。旧宿主不支持新契约时明确失败。
- 本期保持现有持久化保留方式，不新增自动淘汰规则。不得简单截断最近 500 条并丢弃旧轮次水位，导致过期请求重新出现；容量政策若要改变，单独对齐用户可见的数据删除行为。

### C. CodeHub 查询、统计与详情

- 沿既有 provider 识别和宿主上下文分流，复用 `parseCodeHubRemote`、原生远端身份工具及任务来源路由；不将 CodeHub 冒充 GitHub，也不新增 CLI 执行器。
- 分支定位复用 `readCodeHubBranchReview` 的列表、分页和身份校验能力。没有 MR 编号时先从分支查询取得候选，再用 `viewCodeHubTask` 复核；目标分支不足时在现有查询能力内做最小扩展，不先假定编号或目标分支。
- MR 标题、分支、状态复用原生详情；Checks 复用 `readCodeHubMrChecks`；完整讨论读取复用 `listCodeHubComments({ requireCompleteThreads: true })`。
- 补齐通知统计真正需要的原生评论元数据：以讨论根的 resolved 判断线程状态，回复不得覆盖；系统活动、独立普通评论不计入未解决线程，但仍保留在原生详情中。
- 完整分页不等于统计字段完整。缺少根记录、解决状态、有效时间或分页失败时显示未知；不得用缺省 false / 空数组伪造未解决状态或零意见。GitHub 继续沿用现有完整线程读回。
- 点击通知复用原生任务详情的 provider 与 source context；本机和远程项目都走原生路由，不另设通知专用详情或读取通道。

### D. 同次清理与文档收敛

- 删除被替代的项目探测、整体拒发、接收拒收分支、废弃注释与失效测试，保留仍服务于项目定位的共用函数。
- 同步本特性 intent / spec / STATUS / 原型 README 与资源、特性矩阵、architecture 的相关段落；只调整本次影响的知识，不进行全库治理。
- 交付时同步 PR 正文及关联 Issue 的现行范围，保持 Issue 开放；不再让“同项目自动全发”“仅 GitHub”“再次发送名单不可调整”充当当前规则。旧方案从 Git 与 PR 历史追溯，不新增决策流水或兼容页面。
