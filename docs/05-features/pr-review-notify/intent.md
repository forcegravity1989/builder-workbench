# 通知：把 PR 评审请求送到人

> 给产品、设计、实现与验收者读取。本篇只定义用户结果、价值、范围与排除。行为见 [spec](spec.md)，当前实现与证据边界见 [STATUS](STATUS.md)，不记录开发流水。

## 用户结果

Builder 完成 PR 或 MR 后，可以从当前工作树选择已连接主机发起评审请求。评审者从通知进入对应的原生 PR 或 MR 详情，沿用原生评论、检查和合入权限。发起方能看见本轮请求的送达结果、未解决检视意见、状态与 Checks，并可再次发起评审。

同一通知入口可承载团队协作特性的「原型评审」事件：发起人可以发送通知，评审人也可以直接进入发起人主机上的共享工作树和浏览器页签；通知只负责告知，不控制批注权限。评审人在同一页面元素上提交文字批注，发起人读回批注后明确发送给自己的工作模型。原型批注不修改项目文件，也不改变 PR/MR 的 provider 评审事实；首期不跨主机传输截图附件。

通知在窗口重载和 runtime 重启后仍可读。事实读取失败时显示未知和原因，不把失败变成零意见、成功或已读。

## 范围

- 首期沿用 GitHub PR 与 CodeHub MR 的评审请求、接收、结果读回和本机删除；G1 另扩展「原型评审」通知事件，复用收件箱和主机送达，不复用 provider 详情或合入状态。
- 收件对象是已连接主机。主机名称不代表人员身份，项目和仓库按原生远端身份匹配。
- 连接、配对鉴权、宿主路由、原生 PR/MR 详情和浮动工作区复用 Orca。BW 只维护通知内容、周期、轮次和本机持久记录。
- 收件端没有项目副本时仍保存通知，打开时仍定位到发起人主机的源工作树、会话和浏览器页签；源主机不可用时保留通知并显示不可用原因，不改走收件人的本地副本。

## 排除

本期不建立 WeLink、群聊、成员名册、角色或权限系统，不自动配对、授予项目访问权限、克隆项目、离线代投或后台重试。原型、静态检查和模拟投递不能代替双主机、跨网络、真实 provider 检视与合入验证。

## 成功判据

作者能够选择收件主机并看到逐主机发送结果。至少一个收件端保存成功才确认送达。评审者能从通知进入正确的 PR 或 MR。两台真实主机完成发送、检视、重发、合入或关闭后的读回和删除后，才能声明完整旅程已验收。
