# 通知：先打通 PR 评审旅程

> 给 Builder、Leader 和设计评审者在判断价值、范围时读。本文定义通知为什么做、为谁做及边界；首期只交付 PR 评审通知。行为与验收见 [spec](spec.md)，实现与验证见 [STATUS](STATUS.md)。价值或范围改变时更新，不记开发流水。

作者完成 PR / MR 后，需要请共同开发者与评审决策者评审，并持续知道检视意见和合入结果。评审本身沿用原生 PR 详情；通知只补齐从发出请求到进入评审的通路。

## 目标体验

1. 工作树右键「发送评审…」，在原生小弹窗中多选已连接主机；首次默认全选，发送前可调整。没有开放 PR / MR 或没有可发送主机时说明原因。
2. 对方收到请求后，从自己的项目副本或已有共享主机上的项目进入原生 PR / MR 详情；暂时无法访问项目也保留通知。评论、检视和合入权限沿用原生能力。
3. 发起方保留发出记录，读取当前轮次的未解决检视线程、PR 状态和 Checks；支持再发起和删除本机记录。
4. 重启后恢复已接收和已发出的通知；无法读取事实时显示未知，不把失败变成零意见或通过。

## 边界

- 首期通知类型只有 PR 评审，不接 WeLink，不增加群聊、项目成员系统或新的 PR 详情页。
- 收件对象是原生已连接主机，不将主机名称当作人的身份。项目按原生仓库远端身份匹配，不依据目录名或项目墙排序。
- 连接、配对鉴权、撤销、宿主路由和 UI 优先复用 Orca。BW 只维护通知内容、轮次与持久接收，不另设端口、token 或同伴配置文件。
- 本期同时接入 GitHub PR 与 CodeHub MR，复用对应 provider 的原生能力。通知不自动建立反向连接或授予项目访问权限；真实跨主机、跨网络和内部 provider 验证按 STATUS 留白。

## 成功判据

作者从工作树选择收件主机并完成发送，评审人从通知直接进入对应 PR；发送结果逐主机可见，只有接收端保存成功才确认送达。两台真实主机完整旅程通过后才能声明该旅程已验收，原型与代码检视不能替代。

范围及收件对象由 owner 在 PR 478 本轮修正中确认，具体证据留在 PR。
