# PR 评审通知：把评审请求送到人，并跟踪评审结果

> 给 Builder、Leader 和设计评审者在判断价值、范围时读。本文定义 PR 评审通知为什么做、为谁做及边界；行为与验收见 [spec](spec.md)，现状与证据见 [STATUS](STATUS.md)。价值或范围改变时更新，不记开发流水。

## 用户与问题

PR 做完以后，作者要请同项目的人看一眼。今天这一步靠人肉传递：作者去聊天工具里单独说「帮我看下这个 PR」，评审人收到后还要自己打开 BW、找到项目、找到 PR 才能开始评审。通知容易被其他消息淹没，进入要经过多步查找；作者也看不到对方到底看没看、提没提意见、最后合没合入。

评审本身已经有地方做：BW 的任务屏 PR 详情页带着完整的检视意见、合入等原生动作。缺的是「请人评审」和「站到评审位」之间的通路，以及作者对评审结果的持续可见。

## 目标体验

1. **发出**：作者在版本工作区对着某个工作树右键，点「发送评审」。请求直接送到本机连接的其他主机上的同项目用户，不需要去聊天工具里手打消息。工作树没有关联的开放 PR 时，这一项如实置灰。
2. **收到**：对方 BW 的评审通知入口出现一条请求；点开即可进入该 PR 的详情页，直接开始检视或合入，不再自己找项目、找 PR。
3. **跟踪**：作者发出的评审通知长期留在本机，不随发送动作消失。它持续读回该 PR 的评审动态：有人提了检视意见，通知上多一行未解决意见数；意见处理完，作者可以「再发起评审」进入下一轮；PR 被合入，通知显示「该 PR 已合入」。这条通知可以由作者删除。
4. **进入**：本机收到的评审请求和发出的评审通知，点击任意一条都直接落到对应 PR 的详情页，而不是任务屏的列表页签。

评审不是一个「已评审／未评审」的开关。评审人合入了 PR，或者在该 PR 下提交了检视意见，都是评审已经发生的事实；作者侧以这些可读回的事实更新通知，侧栏不显示评审状态。

## 价值与依据

核心收益：**评审请求一键到人，作者对结果持续可见**。发送侧从右键到发出只有两次点击；接收侧从看到通知到站上 PR 详情页只有一次点击；双方都不离开 BW，也不手工拼评审信息。作者不必反复去问「看了吗」「改完了吗」，通知跟着 PR 数据走。

依据：[#199](https://github.com/forcegravity1989/builder-workbench/issues/199) 立项后曾按「WeLink 群聊面板 / Windows 通知」双通道开发；2026-11-05 owner 看过重做的高保真后确认新方向——不接 WeLink，使用 BW 自有的评审通知承载，并以「发出方持续跟踪 + 接收方点击直达」为核心。原双通道实现撤出本交付，Git 历史可查。高保真见 [prototype](prototype/index.html)，已经 Playwright DOM 断言验证；原型只证明交互，不代表能力已交付。

## 范围与边界

- **做**：工作树右键「发送评审」；把评审请求送达本机连接的其他主机；接收方的待评审通知；发出方持续保留的评审通知，读回轮次、未解决检视意见数与合入状态；有检视意见且未合入时可再发起评审；删除通知；两类通知点击直达 PR 详情。
- **不做**：不接 WeLink，不做群消息、IM 卡片、群历史或群未读；不在 BW 内新造一套 PR 详情页，评审动作复用原生 PR 详情；不做侧栏评审状态标记；不做跨项目/跨版本的评审大盘；不自动导航，所有进入都由用户点击触发；不替用户把 PR 上的检视意见标记为已解决。
- **相邻**：任务管理继续负责跨来源查找和处理 PR；本特性只负责评审请求的送达、通知与结果跟踪。版本工作区提供右键入口和工作树与 PR 的关联事实。原生通知系统可承载到达提醒，但通知的持续状态和跟踪归本特性。
- **传输边界**：评审请求走 BW 自有的主机间评审通道，不经聊天工具。可送达范围限于已配置、已连接的主机；未连接或投递失败时如实告知作者，不显示已送达。

## 成功判据与待决问题

**判据**：作者从右键到发出 ≤2 次点击；接收方从看到通知到 PR 详情页 ≤1 次点击；作者的通知在重启后仍在，轮次、检视意见数与合入状态与 PR 数据一致；读不到 PR 数据时显示未知而不是「无意见」；删除通知后重启不再出现；两台真实主机完成一轮「发送 → 收到 → 提意见 → 再发起 → 合入 → 删除」的完整旅程。

**待决（实现期输入，不阻塞范围确认）**：

1. 主机间评审通道的端点发现与授权方式：显式配置、从既有主机连接推导，还是二者结合；跨网段是否支持。
2. 评审动态的读回频率与触发点（应用前台、PR 详情刷新、定时轮询）及失败后的重试边界。
3. 「检视意见」在 GitHub / CodeHub 上的计数口径：只看评审意见（review comment），还是含普通评论；平台不支持「已解决」时怎样表达未解决数。
4. 同一 PR 多轮评审时，新一轮是否只统计轮次起点之后的意见；原型按轮次起点演示，口径待实现时确认。
