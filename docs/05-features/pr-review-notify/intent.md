# intent — PR 评审通知与顺滑进入（pr-review-notify）

> **30 秒导读**：PR 评审请求从发出者一键到评审人直达评审位——两个方案并行调研开发，之后都保留或做取舍：①项目绑定 WeLink 群，BW 内浮动群聊面板（看历史、发文本、未读红点计数），版本工作区 worktree 右键「发送评审」自动展开面板并填好评审信息，发送后对方 BW（有该项目的用户）红点提示未读，点开面板点击评审消息即跳到该 PR 的任务屏详情页；②同一发送动作**不经 WeLink**——复用 Orca 现有远程连接送达，接收侧弹 Windows 系统通知，点通知直达同一详情页（调研评估原生能力是否足够）。两案都是用户点击后才跳转，不自动导航。重点是丝滑：发送一键、接收一点即达、评审人不离开 BW 就站到评审位。承接 [#199](https://github.com/forcegravity1989/builder-workbench/issues/199)（2026-10-28 会议评审扭转后的范围）。
>
> **状态**：意图 gate 已过（2026-10-28 owner「调研并进行开发」）；双方案已开发，随交付 PR 人审。
>
> **维护约定**：给过意图 gate 的人、审这批改动的人读。功能范围或方案取舍变化、待决拍板时更新本篇；不抄行为清单，不记过程流水。

## 用户与问题

PR 评审请求今天靠人肉传递：发出者要在 WeLink 里手动组织消息告诉对方「帮我看下这个 PR」，对方收到后要自己打开 BW、切到项目、找到那条 PR 才能开始评审——通知不保证达（群消息容易被淹没），进入要多跳（开应用→找项目→找 PR）。评审本来就该发生在 BW 任务屏的 PR 详情页（原生 PullRequestPage 已带完整评审动作），但「请人评审」和「到达评审位」之间没有通路。#199 原计划铺开的会议/纪要/远端入口/公共信息等大范围（两份草案已废弃，git 留史）经 2026-10-28 会议评审扭转：先只把这一件事做丝滑。

## 价值与依据

核心收益：**评审请求一键到人、评审人零查找直达 PR 详情页**——发送侧 worktree 右键「发送评审」两步内发出；接收侧自动跳转（方案一）或点系统通知直达（方案二）；全程不离开 BW、不手工拼信息。

依据：#199 会议评审结论（2026-10-28）——范围扭转，只关注 PR 评审的顺滑通知与进入；两方案形态由 owner 会上给出，并行调研开发，之后都保留或做取舍。owner 同日两条纠正：接收侧两案均为**用户点击后跳转**，不做消息到达自动跳转；方案二**不经 WeLink**——现有远程连接已能接收，调研重点是评估 Orca 原生能力（远程连接＋Windows 通知框）是否足够。方案一通道定为 welink-cli 个人登录态（connectors 已管安装与登录；本机实测 `im send-to-group` 支持文本/图片/文件、`im query-history-message` 按群分页读历史（message-id 游标）、`query-recent-conversation` / `query-group-member` 均可用——发送与接收读回都有 CLI 落点）。现有挂点已核：任务屏 PR 详情页（`task-page/Content` → `PullRequestPage`，含评审人请求/移除、checks）；Orca 通知系统（`notifications:dispatch`＋点击路由，现用于终端铃/任务完成的点击聚焦）；浮动面板模式（`FloatingTerminalToggleButton` / `FloatingTerminalPanel`）；版本工作区右键菜单（`VersionNativeTrees`）。**假设（未验证）**：群消息轮询的到达延迟与降噪口径、评审消息识别格式的稳定性，首用周观察后再定。

## 目标体验

1. **发送**：Builder 在版本工作区对着某 worktree 右键点「发送评审」——WeLink 群聊面板自动展开，评审信息（PR 标题、编号、链接、工作树）已填进输入框，点发送即到群。
2. **接收（方案一）**：同项目另一个 BW 用户，群里的评审消息到达后浮动按钮红点显示未读数；他点开面板、点击评审消息，BW 跳到该项目该 PR 的任务屏详情页，直接开始评审。跳转由点击触发，不自动导航。
3. **接收（方案二）**：同一发送动作不经 WeLink——对方经 Orca 现有远程连接收到 Windows 系统通知「XX 请求评审 PR #N · 标题」，点击通知，BW 到前台并跳到同一详情页。
4. **群聊面板**：平时点浮动按钮展开，可看项目群历史消息、输入文本发送（经 welink-cli）；收起后未读消息在按钮上以红点计数。

## 范围与边界

- **做**：①项目绑定 WeLink 群（`.bw/project.toml [chat]`，沿用既有群配置口径）；②浮动群聊面板——历史只读、文本发送、未读红点计数；③worktree 右键「发送评审」——评审信息自动拼装、面板自动展开；④接收侧识别评审消息、**用户点击后**跳转任务屏 PR 详情页——方案一红点＋面板内点击评审消息跳转，方案二 Windows 通知点击跳转（两案均点击触发，不自动导航）；⑤两方案并行调研开发，真实双用户各跑通后由 owner 定都保留还是取舍。
- **调研点（进 spec 前摸清，已核部分见依据）**：方案一接收链路取轮询 `query-history-message` 还是更实时的通道（auth 声称 WebSocket，im 面为查询式）；评审消息的识别格式与未读游标（message-id）；方案二原生能力评估——Orca 现有远程连接能否承载评审信号送达另一用户、通知点击路由从「聚焦终端面板」扩展到「页面导航」的改造成本（不经 WeLink，若原生能力不足则方案二不成立或需补原生面）；PR 详情跳转的导航参数化（项目＋PR 定位到任务屏详情页，两案共用）。
- **不做**：会议创建/纪要回流/远端入口/公共信息承载（原 welink-iteration-flow 四主题随会议扭转废弃，git 留史，未来要捡回从 git 找）；早前「助手服务 AK/SK＋WebSocket 群助手身份」通道与任务屏 Issue 行入口（原 welink-review-invite 草案，随扭转废弃——通道改 welink-cli 个人登录态，入口改 worktree 右键）；BW 自建消息存储/成员/协同系统（03 飞轮红线——消息正本在 WeLink，BW 只做呈现与发送客户端，未读计数仅存最小本地游标）；富媒体消息编辑（先文本；图片/文件发送能力随调研定）；群管理操作（建群/拉人走 WeLink 客户端，BW 不做）。
- **相邻**：connectors 管 welink-cli 安装与登录（本特性消费其登录态，EXPIRED 即不可用照旧）；reviewer-agent 管 MR/PR 的 CI 侧评审召唤（机器召唤），本特性管人对人的评审请求通知，不混；任务屏 PR 详情页是原生能力，本特性只做「到达」，不做评审动作本身。
- **序列与分期**：意图 gate 后写 spec（含原型），两方案同 spec 分节定义、同批实现、真实双用户验证后取舍；进哪个版本由版本规划定。

## 成功判据与待决问题

**判据**：发送侧从右键调出菜单到发出 ≤2 次点击（发送评审→发送）；接收侧从收到提示（红点/系统通知）到站在 PR 详情页评审位 ≤1 次点击（方案一点击面板内评审消息，方案二点击系统通知），全程不自动导航、不手动找项目找 PR；两个方案在真实双用户环境各完成一轮「发送→收到提示→点击进入详情页开始评审」；杀进程重开，群绑定、未读游标、面板状态读回一致，不装绿。

**待决（实现期输入，不阻塞意图 gate）**：

1. 方案一接收链路形态：轮询间隔与实时性的平衡（或 WebSocket 通道可行性）——调研结论进 spec。
2. 方案二原生能力评估结论：现有远程连接承载评审信号送达的可行性与通知点击路由的改造成本——若原生能力不足，方案二取舍或补原生面，由 owner 定。
3. 两方案都保留还是取舍的判据（各跑一轮真实评审后由 owner 定）。
4. 评审信息拼装口径（PR 标题/编号/链接/工作树/材料清单哪些进消息）与识别格式的稳定性——spec 定。
