# design — PR / 原型评审通知

> **状态：已实现设计，待 Electron 与双主机验收。** 本篇记录原型评审事件对现有通知、HTML 预览和 Orca 批注能力的复用边界。用户结果见 [intent.md](intent.md)，当前行为与验收见 [spec.md](spec.md)，证据边界见 [STATUS.md](STATUS.md)。
>
> **维护约定**：只在实现落点或复用边界变化时更新，不记录讨论过程、施工日志或原型视觉稿的逐项变化。

## 能力复用

| 能力 | 复用落点 | 约束 |
| --- | --- | --- |
| 发送入口与主机选择 | `src/renderer/src/workbench/pr-review-notifications/` 的发送弹窗和 transport；原型评审入口是 HTML 预览工具栏的「邀请评审」图标按钮（`BrowserChromeToolbar` 的 `shareControl` 槽，`PrototypeReviewInviteButton`） | 原型评审只新增事件类型；不改 PR/MR 请求和 provider 路由；工作树菜单只保留 PR 评审 |
| 浮动通知 | `PrReviewNotificationsView`、`PrReviewNotificationItems` 的浮窗、计数、分区、删除和刷新 | 事件增加「PR 评审 / 原型评审」二级页签；每页保留「我发出的评审 / 待我评审」；原型通知按用途显示「邀请你评审 / 提交了 N 条批注」 |
| 源文档定位 | 通知携带发起主机、工作树和 HTML 文件绝对路径；点击后用 `openFileInBrowserTab` 在接收方自己的预览里打开（远程工作树经宿主读文件） | 不共享、不挂接对方的浏览器页签，也不按收件人的本地项目重新定位 |
| 浏览器批注 | Orca HTML 预览的工具栏、选元素、确认卡片与批注托盘，完全在各自本机运行 | 成员批注托盘的发送按钮换成「提交给 {主机名}」，成员没有发给模型的入口；持有人侧沿用原生「发送给模型」 |
| 刷新保留 | PR #711 引入的同文档 retention 判断 | 同文档刷新保留，换文档清空 |

发送弹窗中可共享的是主机多选、逐主机结果和发送状态；PR 的 provider 请求字段与原型评审的文档字段保持两套 payload，不能用 PR 编号或仓库身份充当原型评审身份。

## 数据边界

- PR/MR 通知继续使用现有 provider 请求模型、状态读回和本机存档。
- 原型评审使用独立事件记录：事件身份由周期、来源主机和文档路径推导，另含用途（邀请 / 提交）、来源工作树、文档标题，提交类通知含批注条数；不把原型事件伪装成 PR/MR，也不带会话或浏览器页签身份。
- 成员点「提交给 {主机名}」时，把每条批注（文字、意图、优先级、元素定位，不含截图和本地图片路径）经专用批注 RPC 写入宿主的批注存档，再发一条「提交了 N 条批注」通知。存档以文档路径为键、持久化在宿主用户数据，作者身份取自已配对 RPC 上下文（成员姓名）。
- 持有人打开该文档的预览时每 5 秒读回存档，成员批注进入原生批注托盘并显示作者；只有宿主侧（文档所有者）读回，成员侧不轮询。普通本地批注不会写入存档。
- 局限：提交后持有人再改了 HTML，成员批注里的元素选择器可能对不上，这一点不做自动修复。

## 权限与失败

- team-read 成员可以调用专用批注 RPC 的添加与撤回；不再需要对宿主浏览器页签的任何读写，也不能借此执行 `browser.eval`、写文件、改工作树或打开宿主本地文件。
- 发送动作只写通知，不授予项目权限。共享主机原有只读策略继续生效；提交与撤回批注写访问日志。
- 邀请与提交通知都需要对方主机已连接；源主机、工作树或文件不可用时，通知保留并显示原因，不自动切换到收件人的本地副本。
- 读回失败必须显式返回未知/不可用，不能把缺读当成零批注。

## 原型关系

[prototype/index.html](prototype/index.html) 复用当前 BW 工作区壳和真实 PR 通知结构，其中原型评审的入口与批注画面早于现实现（工作树菜单入口、共享页签点位批注），与现行的「预览工具栏邀请评审 → 成员本机批注 → 提交给持有人」不一致，待人确认后刷新。原型与实现仍未经过 Electron 和双主机验收。
