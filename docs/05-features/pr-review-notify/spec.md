# 通知规格：PR / MR 评审请求

> 给设计、实现、评审与验收者读取。本篇只维护当前行为、边界和可观察判据。价值见 [intent](intent.md)，实现与证据见 [STATUS](STATUS.md)。本特性属于探索 BW 的 W03「构建交付」和 W04「验收成果」，完整旅程定义见 [探索规格](../explore-workbench/spec.md#范围与完整旅程)。

## 入口与展示

- 工作树原生上下文菜单提供「发送评审…」。没有可定位的开放 PR/MR 时置灰并说明原因。
- 一个可拖动的原生浮动入口分为「我发出的评审」和「待我评审」。角标表示两类记录总数，不表示未读数。位置、拖动、夹取、尺寸和主题复用浮动工作区能力，并使用独立位置键。
- 点击通知进入对应 provider 的原生 PR/MR 详情。评论、检查、检视线程和合入权限沿原生详情与 provider 权限决定。
- [原型](prototype/index.html)只展示通知组件和模拟主机、请求数据，PR/MR 详情沿用原生页面，不表示生产实现或验收通过。

### 事件类型

通知入口保留同一收件箱和送达状态，但按事件类型进入不同的评审对象：

| 事件 | 进入对象 | 结果 |
| --- | --- | --- |
| PR / MR 评审 | 对应 provider 的原生详情 | 评论、Checks、检视线程和合入事实沿 provider 读回 |
| 原型评审（G1） | 发起人主机上的共享浏览器评审会话 | 评审人提交页面批注；发起人读回后明确发送给自己的工作模型 |

原型评审只读进入发起人主机上的共享浏览器会话，批注是评审记录，不修改原始 HTML、工作树或终端；它不生成 PR/MR 线程，也不冒充 provider 的评审结果。发送动作只负责通知，不决定评审人是否可以批注；只要评审人已进入共享主机的浏览器页签，批注按钮就可用。通知打开时始终定位源主机的工作树、会话和页签；收件人没有同名项目也不创建或打开本地副本。首期批注只支持页面元素和文字，不跨主机传输截图附件。原型评审的入口、页面对象和批注交互见[通知原型](prototype/index.html)。

本地页复用 Orca 浏览器现有批注按钮、批注浮层和批注托盘；共享页签同样使用 Orca 原生工具栏、选元素和批注卡片：成员在画面上移动鼠标，宿主页内高亮对应元素，点击后弹出原生确认卡片，批注进入同一份批注存档，宿主在自己的原生托盘里看到。这些选取调用只是读页面，不开放通用浏览器控制。评审会话绑定一个共享页签/页面身份，参与者连接同一页签，不为每个人隐式复制 N 份页面；每条批注显示提交成员和来源主机。批注状态由源主机的共享页签统一保存和读回。原型页面刷新仍属于同一文档时应保留批注，跳到另一文档才清空；这一行为已有 [PR #711](https://github.com/forcegravity1989/builder-workbench/pull/711) 的静态修复，覆盖同文档 URL、片段变化和本地文件预览的刷新，但 Electron、双机真实刷新、远程批注同步、重连和 runtime 重启后的持久化仍待验。

## 发送对象与投递

1. 弹窗展示当前 PR/MR、可搜索的已连接且传输就绪主机、多选列表、全选和发送按钮。首次默认全选当前可用主机，用户可逐项取消。
2. 再次发送沿用上次确认的完整名单，允许调整。新连接不自动加入。断开、移除或重配的旧目标明确显示不可用，可保留以取得失败结果或移除。
3. 发送前重新核对连接、配对版本、runtime 身份和当前远端。逐台投递，一台失败不阻断其他目标。全部成功、部分成功、全部失败及原因逐主机显示。
4. 接收端验证请求并持久保存后才确认送达。至少一个保存成功才推进轮次。全部失败保留待重试请求，不制造成功记录。重试复用同一请求身份和时间，不后台自动重试。
5. 投递复用原生加密 RPC 与鉴权，不增加端口、token、群组或项目登记门槛。收件端不自动反向配对、授予权限或克隆项目。

## 周期、轮次与删除

- 同一 PR/MR 的发出记录持续到作者删除。送达后再次发送创建新轮次并重置该轮次统计起点。删除后重发创建新周期，从第 1 轮开始。
- 接收端按项目和 PR/MR 汇总。同一周期的重复或较旧轮次不重建条目，较旧周期不覆盖新周期。旧在途结果不得写入新轮次。
- 「待我评审」不会因点击消失。项目未接入或暂不可访问时保留通知并提示原因，恢复后重新定位和读回。
- 读回 PR/MR 已合入或已关闭后，接收端自动移除条目。接收方也可以手动删除。删除只影响本机收件箱，不撤回发出方记录，不关闭 PR/MR。
- 从名单移除主机不撤回已保存的旧通知。存在当前轮次未解决意见且 PR/MR 仍开放时，允许“解决检视意见后再发起评审”，通知不替 provider 标记线程已解决。

## 事实读取与失败

- 记录实际托管仓库的主机、完整路径和编号。GitHub fork 与 upstream 即使编号相同也分别识别。打开通知优先匹配本机登记，其次使用当前可访问的远程登记，并沿原生 source context 路由。
- 支持 GitHub PR 与 CodeHub MR。未解决数只统计当前轮次起点之后创建且仍未解决的完整检视线程。同一线程只算一次。CodeHub 以讨论根的时间和 resolved 状态为准，回复不覆盖根状态，独立普通评论和系统活动不计入未解决线程。
- 缺少线程根、解决状态、有效时间、分页完整性或 provider 查询失败时显示未知和最后读回时间。隐藏旧徽标，不以空数组或默认 false 伪造零意见。
- 打开面板、窗口聚焦、发送或接收新轮次时刷新。同一轮次自动刷新至少间隔 30 秒，手动刷新可立即重读。runtime 收件箱与本机发出记录分别持久保存，读写失败明确报错，不覆盖损坏存档。

## 验收点

| 编号 | 可观察判据 |
| --- | --- |
| N01 | 有开放 PR/MR 时可从工作树发送，无目标或已关闭时置灰并说明原因 |
| N02 | 多台已连接主机可搜索、多选和全选，未登记项目的收件主机也可接收 |
| N03 | 全部、部分和全部失败逐主机如实显示，至少一台保存成功才推进轮次 |
| N04 | 收件窗口重载和 runtime 重启后，已确认通知仍可读 |
| N05 | 本机副本、共享远程项目或暂不可访问时，通知按事实定位、保留或恢复读回 |
| N06 | 新轮次、删除后重发、重复请求和过期结果按周期隔离 |
| N07 | GitHub/CodeHub 只统计本轮完整且未解决的线程，缺失事实显示未知 |
| N08 | 读回失败时隐藏旧徽标并显示原因与最后读取时间 |
| N09 | PR/MR 合入或关闭后，接收方读回确认并自动移除条目 |
| N10 | 重发沿用上次名单，收件人可调整，不自动加入新连接或替换旧身份 |
| N11 | 发出记录、收件箱、删除结果和重启读回保持一致 |
| N12 | 浮动入口拖动、尺寸变化、位置保存和明暗主题沿原生能力工作 |
| N13 | 接收方手动删除后条目与角标减少，发送方记录不受影响，重载不复现 |

## W03 / W04 交叉索引

W03 观察从工作树发起评审、通知送达、进入原生 PR/MR、提交检视意见和作者再次发起。W04 观察合入或关闭后的状态读回、接收方自动移除和发出记录保留。探索目录和播放样例只证明入口可达，不计为业务验收证据。

完整双主机旅程需要 A/B 建立原生连接，分别验证本机副本和共享远程项目、重载与重启、失败读回、重发与删除、GitHub fork/upstream 同号仓库识别，以及真实 CodeHub MR。具备条件的内部环境负责该验证。
