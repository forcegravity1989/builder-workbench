# 通知规格（v0.8 交付 PR 评审通知）

> 给设计、实现、内部评审与验收者读取。本文维护「通知」特性的行为、来源边界、验收与旅程；v0.8 只含 PR 评审通知（下称评审通知）这一种通知类型，其他类型不在本版，纳入时在本文补充对应主题。价值见 [intent](intent.md)，认可和验证结论见 [STATUS](STATUS.md)。行为变化时更新对应主题，不追加施工流水。

## 承载与复用

- 入口在工作树右键菜单，沿用版本工作区已有的原生工作树上下文菜单；本特性只新增「发送评审」一项，不改树本身。
- 通知沿用 BW 现有的浮动按钮 + 浮层面板形态：本机一个入口同时承载「待我评审」和「我发出的评审」，不占侧栏，不新增全局页签。
- PR 详情不自建。点击通知走任务屏既有的 PR 跳转，直接落到原生 PR 详情页；作者打开自己的 PR 只读，评审人沿用原生检视意见与合入动作。
- 评审请求走 BW 自有的主机间通道，不接 WeLink。接收端在已连接主机上监听评审请求，发送端按已知同伴坐标投递，token 鉴权；端点发现方式与网络边界见[待决](#待决)。
- 设计原型：[prototype/index.html](prototype/index.html)。原型用同一页面里的两个悬浮球模拟本机与另一台主机，PR 详情为简化演示页；正式实现中 PR 详情复用原生页面。

## 术语

- **评审请求**：作者请某个人或某些人看一个开放 PR 的事件，携 PR 定位与请求人身份。
- **轮次**：同一 PR 的评审请求可以再发起；每次发出产生新一轮，从 1 开始递增。
- **检视意见**：评审人在该 PR 下提交的评审意见。评审人合入 PR 也算评审已发生，但与检视意见分别呈现。
- **未解决意见数**：当前轮次起点之后、PR 上仍处于未解决状态的检视意见数。平台没有「已解决」概念时不伪造成 0，按该平台可读回的口径呈现或说明未知。
- **已合入**：PR 的合入事实从 PR 数据读回，不由通知自己设置。

## 发送

- 工作树上下文菜单新增「发送评审」。只有该工作树能定位到一个开放 PR 时可用；没有关联 PR、PR 已关闭或已合入时置灰，并在菜单项上说明原因。
- 点击「发送评审」即发送，不再要求打开面板、编辑消息或二次确认。发送目标为本机已连接的同伴主机；没有可送达的同伴时如实提示，不假装已送达。
- 发送成功后，本机出现一条对应的「我发出的评审」通知，轮次为 1；对方主机的评审通知入口出现同一请求。发送结果对每个目标主机分别回报：全部成功、部分成功、全部失败都要能看见；失败项保留可读原因。
- 同一 PR 已存在发出通知时，再次发送视为新一轮：轮次加 1，沿用同一条通知，不重复堆叠；不同 PR 各自独立一条通知。

## 送达与接收

- 评审请求负载只承载定位与展示所需的最小信息：仓库/项目身份、PR 编号、标题、源分支、目标分支、请求人展示名、轮次与发送时间。请求人展示名只作人读标识，token 才是凭据。
- 接收端收到请求后落本机「待我评审」：显示项目、请求人、`PR #<编号>` 与到达时间，跨项目汇总，不要求先打开对应项目。
- 「待我评审」不随点开而消失，也不做「已评审／未评审」二元标记；评审是否发生由 PR 上的评论与合入事实表达，本特性不另造状态。
- 接收端未接入该仓库、项目不可用时保留条目并说明「本机没有该项目」，不猜、不跳转。
- 同一 PR 同一轮重复投递不生成重复条目；同 PR 新轮次更新原条目并显示轮次。应用未打开时错过的请求，在下次打开后仍以本机已存储的通知为准；是否补拉历史请求见[待决](#待决)。

## 通知与跟踪

本机评审通知入口的角标为「待我评审」条数加「我发出的评审」条数；面板分两段呈现，列表可滚动。入口沿用 Orca 原生浮动工作区按钮的尺寸与表面，面板复用原生 Popover 与工作树悬浮窗 PR 段的排版和状态徽标，不另造一套浮层与配色。

### 待我评审

- 每条显示 PR 编号、PR 标题、项目、请求人与时间，整条可点击。
- PR 状态、Checks 与未解决检视意见数以原生徽标呈现，数据从 PR 回读；读不到时不显示徽标，不补绿灯。
- 点击后进入对应 PR 详情页；进入时通知面板关闭，不自动导航。

### 我发出的评审

- 每条显示项目、`请求评审 PR #<编号> · 第 <轮次> 轮`、发送时间与「自动同步」。
- 通知持续存在，直到用户删除。发送动作结束、面板关闭、应用重启都不清除。
- 有未解决检视意见时以消息图标加数字显示；数字从 PR 数据读回，不由发送动作或本地计数推定。
- PR 合入后状态徽标显示「已合入」，停止显示再发起入口；仍可打开详情、仍可删除。
- 读不到 PR 数据时不显示状态/检查/意见徽标，并显示读取失败及上次读数时间；从未读到过则显示读取中。不得把读不到当成 0 条意见、未合入或检查通过。
- 通知上的状态由 PR 数据推导，应用重启后重新读回；重启本身不改变轮次与已记录的通知。

## 再发起评审

- 仅在同时满足「存在该 PR 的发出通知」「PR 未合入」「当前轮次存在未解决检视意见」时，出现「解决检视意见后 · 再发起评审」。
- 点击即向同一目标主机发出新一轮请求：轮次加 1，记录新一轮起点，通知上的未解决意见数从新一轮起点之后重新统计；旧轮已提出的意见继续留在 PR 历史中，但不再计入新通知。
- 本动作不代替评审人在 PR 上标记意见已解决；PR 上的解决状态仍以平台为准。
- 发送失败时轮次不前进，通知保留原轮次与意见数，并给出失败原因。

## 删除

- 「我发出的评审」可删除，只删本机这条通知及其轮次记录，不关闭 PR、不撤回对方已收到的请求、不影响其他主机。
- 删除后角标相应减少，重启后不再出现；之后再次发送同一 PR 会生成从第 1 轮开始的新通知。

## 进入 PR 详情

- 任意「待我评审」或「我发出的评审」条目点击后，直接定位到该项目的原生 PR 详情页，不经过任务列表页签。
- 跳转所需的最小定位为仓库身份与 PR 编号；渲染前按项目接入情况与 PR 数据校验。
- 作者打开自己发出的 PR 为只读视角；评审人打开收到的请求可用原生的检视意见与合入动作。
- 不能定位项目或 PR 时如实提示，不打开空白详情页。

## 持久化与失败

- 本机通知（入口、轮次、发送时间、轮次起点、待我评审条目）存入本机用户数据，不写项目仓库，不建业务数据库；重启应用后读回一致。
- PR 动态（未解决意见数、PR 状态、Checks 状态、合入状态）不持久化为「结果」，每次按触发点重新读回；读取失败保留同范围旧读数与时间，缺数据保持未知。
- 发送失败、接收端未接入项目、PR 数据不可读、目标主机不可达分别给出可读原因；任何一类失败都不显示成功态。

## 验收点

| # | 场景 | 期望 |
|---|---|---|
| N01 | 工作树有可定位的开放 PR 时打开右键菜单 | 「发送评审」可用 |
| N02 | 工作树无关联 PR、PR 已关闭或已合入 | 「发送评审」置灰并说明原因 |
| N03 | 点击「发送评审」且有可送达同伴 | 本机出现第 1 轮发出通知；对方出现同一请求；不要求二次确认 |
| N04 | 无同伴或投递失败 | 如实显示未送达及原因，不出现已送达态 |
| N05 | 对方点击「待我评审」条目 | 直接落到对应 PR 详情页，不经过任务列表页签 |
| N06 | 对方未接入该仓库 | 条目保留并提示本机没有该项目，不跳转 |
| N07 | 评审人在 PR 上提交检视意见 | 作者通知的意见徽标数字为 N，N 与 PR 数据一致 |
| N08 | PR 被合入 | 作者通知的 PR 状态徽标显示「已合入」，不再显示再发起入口 |
| N09 | PR 数据读不到 | 不显示状态/检查/意见徽标，显示读取失败及上次读数时间；从未读过显示读取中，不当作 0 条或检查通过 |
| N10 | 存在未解决意见且未合入时点击「再发起评审」 | 轮次加 1，对方收到新一轮，通知按新起点统计；失败时轮次不前进 |
| N11 | 删除发出的评审通知 | 本机通知消失、角标减少、重启后不再出现；PR 与对方请求不受影响 |
| N12 | 杀进程重启 | 待我评审与发出通知、轮次、起点读回一致；PR 动态重新读回 |
| N13 | 全流程检查 | 不出现 WeLink 群、IM 卡片或侧栏评审状态；所有进入均由点击触发 |

## 旅程

**PJ01（两台真实主机完成一轮评审）**：A 在版本工作区右键 `#383` 工作树 → 点「发送评审」→ B 的评审通知入口出现请求 → B 点击条目进入 PR 详情 → B 提交检视意见 → A 的通知意见徽标显示 1 → A 处理完意见后点「再发起评审」→ B 收到第 2 轮 → B 合入 PR → A 的通知 PR 状态徽标显示「已合入」→ A 删除通知，角标回落。全程 B 不手动找项目、找 PR，双方不离开 BW。

## 已定与已弃

**已定**（owner，2026-11-05）：按新高保真重写本特性；不接 WeLink；评审状态不显示在侧栏；作者发出的评审通知持续保留并可跟踪检视意见、再发起、合入与删除；两类通知点击直达 PR 详情；评审动作复用原生 PR 详情。

**已弃**：WeLink 群聊面板、群历史与未读红点、IM 卡片、`workbench://` 外发深链、Windows 系统通知作为主承载、侧栏评审状态标记。原双通道实现代码撤出本交付，Git 历史可查。

## 待决

1. 主机间评审通道的端点发现与授权：显式配置、从既有主机连接推导，还是二者结合；跨网段是否支持。
2. 评审动态读回频率与触发点：应用前台、打开通知面板、打开 PR 详情、定时轮询各承担什么；失败重试与退避边界。
3. 「检视意见」与「未解决」的平台口径：GitHub review comment 与 CodeHub 评论的差异；平台无已解决态时的呈现。
4. 应用未打开期间错过的评审请求是否需要补拉，以及补拉的时间窗口。
5. 同一 PR 的通知是否允许同时发给多个同伴，以及部分成功时的轮次与状态表达。
