## 用户与问题

Builder 把版本发布出去之后，生产部署就成了 BW 的盲区：验收屏的「部署」只覆盖会中演示环境，发布后要在生产机器上装包、确认服务活着，只能回到终端里手敲命令。

而真实的部署动作往往是**散的**：项目里有构建脚本、有装机脚本、有重启脚本——都是项目自己沉淀的资产——但它们之间没有一条入口串起来。人要记得先跑哪个后跑哪个、去哪看服务起没起来、拿什么确认版本对不对；换个人来就接不上。部署做了没有、结果如何，BW 一律看不见。

每个项目的构建方式、服务形态、健康口径、目标环境都不同，通用面板给不出真实读数——硬编码一套「标准部署」只会造出假绿灯。真实读数只能来自按项目实际代码生成、并复用项目已有资产的脚本，且只能从执行结果推导。

## 价值与依据

给发布链路补上「发布之后」的一段：出包（项目流水线）→ 验收（演示环境）→ 发布 → **CI 屏部署（一条入口 + 独立读回 + 执行记录）**。两句话主张：

- **简化部署动作**：一条命令（板面上一个按钮）完成「构建版本包 → 部署到指定环境 → 独立读回服务状态与版本 → 写执行记录」，人不记顺序、不盯输出。
- **构建和使用已有的部署脚本**：CI 助手按 ci-ops skill 先勘察项目实际代码，已有资产编排复用、缺失环节才按模板生成——不另造平行机制，不推倒项目自己的沉淀。

依据为 #461 的明确缺口（生产部署无入口、无流程、无状态读回）与四铁律：信号只能从数据推导，没数据就是灰，不是绿；完成由人确认。脚本资产按项目实际代码生成、经人审合入，沿用 standard/ 沉淀方法资产的既有做法。gtsllm-dfx 样板间已实证该方法在真实项目上成立（已有脚本一行未改，只补编排、读回与记录）。

## 目标体验

新项目第一次进 CI 屏，部署模块的灯是灰的——未接入，不装样子；板面给「主分支未见脚本」的事实与「生成部署脚本」入口。人点生成，CI 助手按 ci-ops skill 勘察项目实际代码与已有部署资产，生成固定路径 `.bw/ci/deploy.sh`（复用优先），提 PR 经人审合入 main；板面每 5 秒扫描主检出，扫到资产灯变黄：已接入，待执行。

人点「部署」，请求进左侧 CI 助手会话，脚本在会话里真实执行，板面流程条按步骤标记逐步点亮：**软件包准备 → 预检 → 清场 → 部署 → 验证 → 记录**（四阶段六步，两种模式同骨架）。软件包准备在最前——没有可用包时失败发生在清场之前，不该把正在跑的服务停了。**开发部署**在本地执行启动命令把服务跑起来；**上线部署**连服务器把所选版本的软件包（来自验收屏的包登记，默认最新）部署到远端，密码只在执行时输入、不落盘。任何步失败流程停在该步，失败步定位进记录；修复后「从失败步重试」，已完成步不重复执行。成功灯绿，失败灯红、报错进记录——失败如实红，不重试到绿，恢复靠下一次真实成功。

部署的效率来自确定性：会话里模型遇到端口冲突要试错排查十分钟，板面把「清场」变成流程里的一个确定性步骤，秒级完成——UI 的价值是把模型的试错变成脚本的步骤。

执行与报错就近显示在流程列表对应步骤（在哪用在哪显示）：步骤名后跟执行时间，每步读数内联；历史报错常驻失败步——上次失败时间与原因一行事实，报错日志与该步日志一起按步骤回显，纠错在哪步失败就在哪步看，不用去后台翻文件。执行历史经模式行「历史记录」下拉切换最近 10 次部署记录，流程列表回显所选那次的每步状态、时间、读数与日志（失败带步序定位），默认最近一次——板面不设独立记录区，历史在哪看就在哪显示。错误日志与记录存在 bw/ci 固定树的本地目录，默认不上仓——生产报错内容不进代码评审流。

## 范围与边界

- 包含：部署脚本资产的生成链路（ci-ops skill 方法 + 项目实际代码 + PR 人审）、会话驱动的单次部署执行（开发/上线两种模式，上线选版本）、四阶段六步流程与失败停步、从失败步重试、独立读回、每步命令详情（板面读 deploy.sh 步骤分段回显，纠错不经会话）、部署卡统一「配置」入口（配置请求经会话落项目资产，板面不显示配置事实）、从记录推导的四态灯、历史记录下拉与报错步骤归位（每步时间与日志在流程对应步骤显示，历史报错常驻失败步）、bw/ci 固定树的本地存储。
- **灯是健康信号，不可手设**：灰=未接入/未知，黄=已接入·待执行，绿=最近一次成功，红=最近一次失败；最新结果决定绿红；历史报错永久保留。没数据就是灰，不是绿。
- **错误日志不默认上仓**：执行记录与日志存 bw/ci 固定树本地 `.bw/ci/`；脚本资产在项目 main，代码与数据分离。
- 不做出包（出包归项目流水线与验收屏）、不做通用部署平台（读数来自项目自有脚本与探针口径）、不重建会话或调度器（复用 Orca 原生）、不代判健康（探针说了算）、不替人确认任何完成。
- **监控、故障检测、重启不在本版**：原四模块草案中的这三个模块（轮询调度、停止回黄、人触发重启）转后续演进，待部署模块在真实项目用稳后再议；其设计讨论保留在 git 历史。
- 单环境起步：先服务「指定环境」一个部署目标，多环境维度是否扩展见待决。

## 成功判据与待决问题

新项目首次进入灯灰、无预置记录；脚本合入后五秒内变黄；部署成功绿（六步全过）、失败红且失败步定位进记录，从失败步重试不重跑已完成步；上线部署能选验收登记的版本、所选版本进记录可追溯；报错在流程列表对应步骤能看到时间、原因与日志原文；「历史记录」下拉能切换最近 10 次部署记录并回显该次执行；杀进程重开，灯与记录从真实数据重新推导、前后一致。样板间口径：在真实项目上一条命令完成构建→部署→读回→记录，项目已有脚本零改动。

**待决**：①监控/故障检测/重启三模块的带入时机与形态（部署用稳后再议）；②多环境维度（是否扩环境选择与按环境分灯）；③告警通知通道（报错是否推 WeLink 等外部通道）；④脚本模板细则归 ci-ops skill 正本，随首批真实项目使用打磨。
