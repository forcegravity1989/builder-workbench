# ci-ops skill 草案（部署模块）——CI 助手的工程能力与执行方式

> **本篇维护约定**
> - **读者与时机**：评审 CI 屏部署模块的人（本 PR gate）、后续把本 skill 落地到 `standard/skills/ci-ops/` 的开发者、以及被 ci-ops prompt 激活的 CI 助手会话本身。
> - **职责与边界**：只装 ci-ops skill 部署部分的正文草案——工程能力从哪来（勘察→复用→生成→读回→记录的方法）、部署流程契约（三阶段六步）、递交 prompt 的真实文本、执行与记录协议、助手边界。**不装**：屏面行为（[spec](spec.md)）、价值论证（[intent](intent.md)）、样板间证据（[showcase-gtsllm-dfx](showcase-gtsllm-dfx.md)）。
> - **状态**：草案，随本 PR 交人 gate；gate 通过后正文迁入 `standard/skills/ci-ops/SKILL.md`（按 [SKILL-MD-SPEC](../../../../standard/skills/SKILL-MD-SPEC.md) 格式整理），本篇转为指针。
> - **更新触发**：prompt 文本、方法步骤、流程契约或记录协议变化时更新；首批真实项目使用反馈驱动打磨。

## 这个 skill 解决什么

「生成部署脚本」不是让模型凭空写一段通用脚本。每个项目的构建方式、服务形态、健康口径、目标环境都不同，通用模板只会造出假绿灯。ci-ops skill 给 CI 助手一套**对每个项目先勘察、复用已有资产、缺失才生成、执行后独立读回**的方法——工程能力来自项目自己的代码与脚本，不来自模型的想象。

## 方法：助手接到生成请求后的四步

### 第一步 · 勘察（不勘察不生成）

读项目实际代码，回答四个问题，答案写进生成会话的回复里（人审 PR 时核对）：

| 问题 | 看什么 | gtsllm-dfx 样板间的答案 |
|---|---|---|
| 怎么构建出包 | build 脚本、流水线配置、打包产物形态 | `build/build.sh` → `dist/gtsllm-dfx-<版本>-<时间戳>.7z` |
| 服务长什么样 | 端口、探针、进程模型（前台/systemd/容器） | Node 零依赖服务，8025，`/healthz` 判 `"ok":true`、`/readyz` 判数据可写 |
| 已有哪些部署资产 | deploy/、scripts/、systemd unit、Dockerfile、监督脚本 | `deploy/install.sh`（Linux systemd 装机）、`restart.sh`、`watch-win.sh`（Windows 监督拉起）、`status.sh` |
| 部署到哪 | 目标环境、目标目录、运行用户、传输方式 | Linux 生产 `/opt/gtsllm-dfx`（systemd）；本机 Windows 验证环境 |

### 第二步 · 复用优先（不另造平行机制）

已有资产**编排**进固定路径 `.bw/ci/deploy.sh`，一条入口串起来：软件包准备 → 预检 → 清场 → 部署 → 验证 → 记录。已有脚本原样被调用，deploy.sh 只补项目没有的那一段——通常是「编排 + 读回 + 记录」。样板间里 build/build.sh、watch-win.sh、install.sh、restart.sh 一行未改，deploy.sh 只是把它们按序串起来并补了读回与记录。

### 第三步 · 缺失才生成

勘察后确实没有的环节，按模板生成并写入 deploy.sh（同一份脚本里，生成段与编排段用注释分界）：

- **软件包准备段**：dev 模式校验启动命令已配置；release 模式校验所选版本包存在可读。**这一步必须在预检与清场之前**——没有可用包（或未配置启动命令）时失败发生在清场之前，不该把正在跑的服务停了。
- **预检段**：dev 查端口占用与旧实例（旧实例不是失败，是待清场）；release 查 ssh 连通、磁盘余量 ≥ 包大小×2、目标目录存在。
- **清场段**：停旧服务、等端口释放；无旧实例输出「跳过」不报错。
- **部署段**：dev 执行启动命令拉起服务；release 传输到目标环境并落位。Linux 优先 systemd（装机一次，之后 restart），Windows/Git Bash 用监督脚本拉起。
- **读回段**：**必须独立读回**——不信任部署动作本身，另起探针确认服务状态、版本、耗时；探针口径用项目自己的（样板间用 `/healthz` 的 `"ok":true`，这是项目监督脚本同款判据）；release 模式加版本核对（部署目录版本 = 所选包版本）；未配探针退化为进程存活+退出码。
- **记录段**：结果追加写 `.bw/ci/records.jsonl`（协议见下节）；失败同样写记录，`ok:false` 带错误摘要与日志指针。

### 第四步 · 人审合入

生成的 deploy.sh 提项目仓 PR，**经人审合入 main**——板面不直接写脚本、不绕过评审。合入后板面 5 秒扫描主检出，扫到 `.bw/ci/deploy.sh` 灯灰→黄。

## 部署流程契约：三阶段六步

deploy.sh 无论编排还是生成，都按同一条六步骨架执行（两种模式同骨架，差异在每步内容）：

| # | 阶段 | 步骤 | dev | release |
|---|---|---|---|---|
| 1 | 部署前准备 | 软件包准备 | 校验启动命令已配置 | 校验所选版本包存在可读 |
| 2 | 部署前准备 | 预检 | 端口占用、旧实例探测 | ssh 连通、磁盘 ≥ 包×2、目标目录 |
| 3 | 部署前准备 | 清场 | 杀本地旧进程、等端口释放 | 远端停服务 |
| 4 | 开始部署 | 部署 | 执行启动命令拉起服务 | 上传包 → 解包 → 按项目方式启动 |
| 5 | 部署后验证 | 验证 | 本地探针（退化：进程存活） | 远端探针 + 版本核对 |
| 6 | 部署后验证 | 记录 | 写 records.jsonl | 同左 |

**步骤标记协议**（板面流程列表据此逐步点亮）：脚本在执行输出里按步打标记行——`[ci-step] <步骤> <start|ok|fail|skip>`，如 `[ci-step] precheck start`、`[ci-step] cleanup skip`。任何步 `fail` 后脚本立即停止，不再执行后续步骤。

**从失败步重试**：deploy.sh 接受 `--from <步骤>` 参数，从指定步骤起跑，之前步骤视为已通过不重复执行（清场过的不用再清）。

## 递交 prompt 真实文本

板面按钮经 Orca 原生发送弹窗把文本递交进 CI 助手会话；与会话里直接说同一句话等价。文本是评审对象，改文本等于改行为。

| 入口 | 递交文本 |
|---|---|
| 生成部署脚本（灰态板面按钮） | `按 ci-ops skill 为本项目生成 .bw/ci/deploy.sh：先勘察项目实际代码与已有部署资产（构建方式、服务形态、探针口径、目标环境），已有资产编排复用、缺失环节按模板生成；按三阶段六步骨架（软件包准备→预检→清场→部署→验证→记录）编排，软件包准备必须在清场之前；执行时按步骤标记协议输出 [ci-step] 进度，执行后必须独立读回服务状态与版本并写 .bw/ci/records.jsonl 记录，失败如实写 ok:false 与 failedStep。完成后提 PR 经人审合入 main，不直接改 main。` |
| 配置（部署卡统一按钮） | `按 ci-ops skill 配置本项目部署所需资产：开发启动命令与端口、探针 URL、上线服务器信息（IP/用户/上传路径）。已有配置先从项目资产读出来给我确认，缺失或要改的向我收集；配置写进项目资产随 .bw/ci/deploy.sh 同审合入。密码不进配置，只在部署执行时输入。` |
| 部署（开发模式，黄/绿/红态板面按钮） | `执行本项目的 .bw/ci/deploy.sh --mode=dev：软件包准备（校验启动命令）→ 预检（端口/旧实例）→ 清场（杀旧进程）→ 部署（执行启动命令）→ 验证（独立读回服务状态）→ 记录。按记录协议把结果追加进 .bw/ci/records.jsonl（mode=dev），失败如实写 ok:false 与 failedStep，不重试到绿。` |
| 部署（上线模式，黄/绿/红态板面按钮，携带所选版本） | `执行本项目的 .bw/ci/deploy.sh --mode=release --version=<所选版本>：软件包准备（校验所选包）→ 预检（连通/磁盘/目录）→ 清场（远端停服务）→ 部署（上传解包启动）→ 验证（探针读回+版本核对）→ 记录。按记录协议把结果追加进 .bw/ci/records.jsonl（mode=release、version=<所选版本>），失败如实写 ok:false 与 failedStep，不重试到绿。` |
| 从失败步重试（红态板面按钮） | `执行本项目的 .bw/ci/deploy.sh --mode=<原模式> --version=<原版本> --from=<failedStep>：从失败步起跑，之前步骤不重复执行；结果按记录协议追加进 .bw/ci/records.jsonl，失败仍如实写 ok:false 与 failedStep。` |
| 停止（会话直说；板面不设按钮，属脚本能力） | `执行 bash .bw/ci/deploy.sh --stop，停掉本机监督实例并确认端口释放；结果如实回报。` |

## 记录协议（板面灯的正本）

`.bw/ci/records.jsonl`，一行一个 JSON，追加写，存 bw/ci 固定树本地、默认不上仓：

```json
{"ts":1793184085077,"iso":"2026-10-28T10:41:25.077Z","module":"deploy","mode":"release","ok":true,"version":"1.0.0","steps":{"pkg":"ok","precheck":"ok","cleanup":"skip","deploy":"ok","verify":"ok","record":"ok"},"readings":{"pkg":"dist/gtsllm-dfx-1.0.0-20261028_1841.7z 存在可读","precheck":"ssh 连通 · 磁盘余量 4.2G ≥ 包×2","cleanup":"远端服务已停止","deploy":"退出码 0","verify":"/healthz 200 · 部署目录版本 1.0.0 = 所选","record":"已写记录"},"pkg":"dist/gtsllm-dfx-1.0.0-20261028_1841.7z","gitRev":"e62623f","healthz":200,"readyz":200,"elapsedMs":5348,"log":".bw/ci/logs/deploy-20261028T184114.log"}
{"ts":1793184227485,"iso":"2026-10-28T10:43:47.485Z","module":"deploy","mode":"release","ok":false,"version":"1.0.0","failedStep":"pkg","steps":{"pkg":"fail"},"error":"打包失败，看日志","log":".bw/ci/logs/deploy-20261028T184341.log"}
```

- 必备字段：`ts`/`iso`/`module`/`ok`/`mode`；上线附 `version` 与 `steps`（各步 `ok|fail|skip`）；成功附 `readings`（每步一行读数事实，板面流程列表内联展示）与 `elapsedMs`；失败附 `failedStep` 与 `error` 摘要；两者都带 `log` 指向 `.bw/ci/logs/` 下的完整输出。
- 灯由记录推导：最近一条流程全步通过绿、停在失败步红、有脚本无记录黄、无脚本灰。**助手不得为「让灯变绿」重试刷记录或手改记录**——失败如实红，恢复靠下一次真实成功。

## 配置资产与密码

- 六步流程所需的配置——开发启动命令与端口、探针 URL、上线服务器信息（IP/用户/上传路径）——经部署卡统一「配置」按钮向 CI 助手递交配置请求（文本见上表）：已有配置先从项目资产读出给人确认，缺失或要改的经会话收集，落项目资产、随 deploy.sh 同审合入；板面随模式显示各配置项「已配置/未配置」，不显示配置内容。
- **密码不是资产**：只在部署执行时输入（密文显示、不可复制），不落盘、不进记录、不进日志；连接失败重新输入，不缓存复用。

## 助手边界

- 不替人确认完成：部署成功只写记录与读回，不关 Issue、不宣布「发布完成」。
- 失败不降级：探针不通就是红，不写成「未知」或「应该没事」。
- 日志与记录只写 bw/ci 固定树本地，不提交进项目仓；deploy.sh 脚本资产本身进项目 main，代码与数据分离。
- 单次执行不自动重试；重复部署请求在会话里如实串行执行；重试只在人点「从失败步重试」后发生。
