# 项目周报：自动呈现进展，手动兜底

## 用户与问题

许多项目由一个人维护开发，需求、缺陷和日常工作已汇聚到 CodeHub Issue。原先独立的 DTS 和需求系统不再使用，信息来源更集中，项目管理要关心的目标、进展、风险、交付节点与责任仍然存在。

Builder 每周需要向 Leader 说明项目怎样推进，却还得逐条翻 Issue、评论和 MR，把零散变化填进表格，再整理排版。固定空表无法随项目内容变化：不同项目关注的指标、工作方向和节点不同；维护表格又形成一份容易与真实工作脱节的记录。BW 已有项目方向、版本目标和关联工作，周报应利用这些内容，让会话完成整理与呈现。

## 价值与依据

核心收益是让 Builder 直接审阅一份有依据的项目周报，把时间用在判断进展、处理风险和纠正歧义上。模型自动读取工作事实、调用工具统计、按目标组织信息并渲染报告；人只在缺失、歧义、失败或结论需要纠正时补充。

依据是用户在本次任务中提供的两份日常周报样例，并明确了三个条件：保留完整的项目管理关注点；适应以单人开发和 CodeHub Issue 为主的项目；采用“自动渲染，手动兜底”。样例证明需要关注哪些内容，不要求每个项目沿用同一份固定空表，也不以旧系统仍存在为前提。减少搬运是否达到预期，应通过真实项目的一次完整周报生成与审阅观察，不预填收益比例。

## 目标体验

Builder 在 BW 中打开项目周报，选定报告周期，开始生成。会话沿用项目已确认的目标和工作范围，读取 CodeHub Issue、评论、关联 MR 以及可用的项目材料和指标，自动整理本周发生了什么、离目标还有哪些差距、哪些风险值得关注。报告随实际内容安排分组和表格，读者先看目标、关键进展和风险，再按需展开详细工作和问题单。

有里程碑、客户支撑或特殊业务指标时，报告显示对应内容；没有可靠材料时说明缺口。单人项目的成员部分简洁呈现真实维护责任，有协作时再展开。周报周期和版本是两个范围：同一个版本可跨多周，报告呈现本周变化及期末情况，继续引用原有目标，不每周另造目标。

Builder 可以查看结论依据，或在同一会话中说“这项还没验收”“这里补上客户反馈”，让模型就地修订。不能自动解决的内容提供直接编辑入口；生成失败也能使用已有草稿继续补充。再次生成保留人工补充，并把与新事实冲突的地方交给人核对。审阅后可导出完整 HTML，满足日常汇报与分享；报告确认不替代工作完成或目标验收。

## 范围与边界

- 保留目标、关键进展、关键风险、子目标／需求详细进展、问题单进展、项目成员这些关注点；里程碑和客户／局点支撑按实际内容出现。栏目组织随项目内容调整，不把逐栏手填设成生成前置条件。
- CodeHub Issue 是工作状态事实源，需求与缺陷沿用项目已有命名和协议组织；评论、MR、Git、版本材料及可靠指标是相应证据来源。周报是有来源和统计范围的汇总产物，不建立第二套工作状态、需求系统或成员协同系统。
- 默认由大模型会话取数、统计、分析并渲染；人工补充、对话修订、直接编辑和失败后的继续整理是兜底路径。修订需保留身份与依据，不能把人的补充包装成平台读回事实。
- 统计依赖真实记录与工具计算；缺失、取数不全、失败和零值分别呈现。没有可靠风险记录不能写成“无风险”；无法证明目标达成不能写成已完成。
- 复用 Orca 的会话、工作树和自动化能力，不另建会话或调度器。MVP 先验证手动启动生成与兜底体验；周期执行属于后续接线，启用和时间由项目使用者确认。
- 不自动更改 Issue 状态、关闭 Issue、合入 MR、确认目标达成或发送报告。报告审阅只确认本份汇报内容，交付与目标验收仍由人决定。无需 DTS 或独立需求系统。

## 成功判据与待决问题

Builder 能从已有项目材料和 CodeHub 工作记录获得一份完整且可追溯的周报，正常路径无需逐栏填写；Leader 能理解目标推进、关键风险和下一步，并从结论找到依据。缺失或失败时仍能继续处理，不用从空表重新开始；重新生成不会悄悄丢掉人工修订。相同范围和来源的数字可独立重算，报告不把未知或未验收显示成完成。

本轮交付意图草案和可点击 MVP demo，供人判断是否符合上述体验；不宣称生产会话与 CodeHub 取数已经跑通。生产接线前须确认本篇和 [规格](spec.md)，并验证真实平台支持的期间事件、分页取数及证据范围；能力不足时按规格说明缺口，不以当前状态猜历史。
