## 范围与入口

目标入口是 BW 项目内的“周报”，面向当前项目和所选周期；这是新入口设计，现行生产导航尚未增加它。报告周期独立于版本，同一周可涉及跨版本工作；目标沿用项目已确认材料，不能把 Issue 标题自动升级为已确认目标。

demo 使用固定示例周期，通过场景切换演示自动生成、随材料组织报告、查阅依据、人工补充与显式修正、重新生成后的核对提示、失败重试及 HTML 导出。人工修正明确标记，重新生成后提示核对，不声称模型已经识别自然语言中的语义冲突。原型中的场景选择和示例数据说明仅用于评审，不进入最终产品主流程。

真实选周期、期间历史与部分分页读取、客户／局点支撑、自然语言冲突识别和真实会话尚未接线；下文完整旅程和验收表定义目标行为，超出上述原型覆盖的部分保持未建。自动化采用 Orca 原生能力，MVP 不新建周期调度；生产配置需在后续接线中确认启用、时间和模型。

## 完整用户旅程

1. Builder 打开项目周报，看到项目、周期和当前报告。首次没有报告时显示生成入口及取数范围，不要求逐栏填空；已有报告时能继续阅读、补充和导出。
2. 点击生成，会话读取项目方向、版本目标与现有工作关联，取得范围内 CodeHub Issue、期间评论和事件、关联 MR，以及可用交付、验收和指标材料。界面显示正在准备报告；失败不得将已有报告替换成空白。
3. 工具在约定窗口和口径内统计，模型按目标总结期间变化和期末情况，组织关键进展、风险、详细需求和问题。报告标明周期、时区、取数范围与时间，关键结论能查看对应来源。
4. Builder 阅读报告。有里程碑、客户支撑或业务指标时出现对应信息；无可靠记录的关键管理内容显示缺口，不能默认无风险或正常。成员从已有资料和责任关联整理，单人项目采用简洁责任展示，不猜人员身份。
5. Builder 对结论提出反馈，由会话修订；也可直接编辑补充，注明人工补充身份。正常路径无须编辑。歧义、缺失、读取失败可先补充材料或重试，全部生成失败时提供可编辑草稿继续整理。
6. 重新生成刷新自动取得的内容，保留人工补充；新事实与人工内容冲突时标出待核对，不能默默覆盖。Builder 审阅后导出完整 HTML，输出带范围、证据与缺口，报告确认不触发 Issue 完成或目标验收。

## 行为规则与异常

### 内容组织与证据

目标、关键进展、关键风险、需求详细进展、问题单进展和责任归属是固定关注点，具体分组、摘要和表格随项目材料组织。里程碑、支撑与特殊指标有则展示；无数据时区分“不适用”“未发现相关记录”“读取失败”，不强行生成项目没有的内容。

同一 Issue 可作为需求明细、问题跟踪或关键进展的依据，身份通过平台、项目及原始编号确定；分类沿用项目既有协议与标题，不增加 `kind`、`tool`、`workflow` 等标签。栏目引用同一事实，不创建重复工作或重复完成记录。问题单仅汇总已明确为缺陷／问题的 Issue，不能把全部 Issue 当作缺陷。

每份报告说明选定日期及其时区，统计采用起始日零点至结束日次日零点的半开窗口。新增／关闭来自期间事件；期末开放量需要期末可证明状态。重复开闭应按去重口径说明，不能把关闭事件数混称为关闭问题数；当前快照不伪装成过去一周的历史。取数未完成分页或范围不完整时，项目总量保持未知，可展示明确范围的已读取数量。

数字由工具根据数据计算，模型负责筛选重点和解释。MR 合入、Issue 关闭和目标达成各有依据；[CodeHub 当前规格](../codehub/spec.md) 无法读回的合入证明仍保持未知，不以 Git 可达性替代平台合入。目标结论引用原有验收及人的确认；自动生成不产生新的完成决定。

### 手动兜底与重新生成

人工补充可以用于尚未进入 Issue 的背景、风险判断和修正。保留补充者、范围与人工身份；能修正源记录的工作由人另行授权，不在生成周报时顺带修改 CodeHub。模型使用补充时仍区分事实、判断与待确认内容。

报告中的人工段落或修订单独保留，重新生成只替换自动内容；明确删除人工补充才可移除。若自动事实与人工修订冲突，在报告中给出待核对提示，保持可导出草稿。不能以“已重新生成”为由丢失输入。

| 情况 | 用户可见结果与继续方式 |
|---|---|
| 个别记录缺失或无法分类 | 有证据的部分继续生成，缺口定位到栏目或事项；可补充或稍后重试 |
| 部分 CodeHub 取数失败或未读全分页 | 显示范围不完整，受影响数字为未知；保留已读事实，可重试 |
| 全部生成失败 | 显示失败原因及重试入口，保留上次报告和人工补充；首次可开始可编辑草稿 |
| 没有目标或目标未确认 | 报告说明目标信息缺失，工作仍可整理为待归属事项，不自造已确认目标 |
| 没有风险证据 | 提示风险信息不足或待核对，不能显示绿色健康状态或“无风险” |
| 重新生成与人工内容矛盾 | 保留人工内容并提示冲突，由人核对，不静默覆盖 |
| 导出前仍有缺口 | 允许导出带未知和待核对标记的草稿，不把导出当作审阅通过 |

### 报告产物与权限

报告保存本次范围、采用来源、生成时间和人工修订，是一次汇总快照；当前工作状态仍在 CodeHub，项目目标仍在已有材料。生产保存位置及原子写入、恢复与会话并发协议随实现设计确认，MVP 不新建数据库。demo 本地状态仅用于交互设计；它不代表真实 CodeHub 独立读回或生产数据恢复。

HTML 导出包含可读报告、人工补充、证据身份与信息缺口，能独立打开。模拟来源明确标为示例，不能导出带真实取数假象的报告。导出是用户下载动作，不自动发送给 Leader 或项目群，不更改 Issue/MR/目标状态。

## 验收与衡量

以下判据定义目标行为；demo 只能验证模拟交互，生产取数、真实会话、保存与重启须以后续 E2E 证明。

| 标识 | 场景 | 可观察结果 |
|---|---|---|
| W01 | 记录齐全，启动生成 | 无须逐栏填写即可获得目标、进展、风险、需求、问题与责任的完整汇总，结论可定位依据 |
| W02 | 同项目不同周期或内容 | 工作与摘要随周期变化，有节点／支撑时出现相关部分，版本目标继续引用原身份 |
| W03 | 缺目标、风险证据或期间历史 | 定位缺口，相关结论或统计显示未知，不制造目标、绿灯或历史 |
| W04 | 人补充后重新生成 | 自动部分更新，人工补充保留；冲突可见且等待核对 |
| W05 | 部分读取失败或生成失败 | 未被证明的总量为未知；已有报告和补充保留，可以重试或继续手动草稿 |
| W06 | 导出存在人工补充与缺口的报告 | HTML 可独立阅读，包含周期、来源、人工身份和缺口；不写 CodeHub 状态、不自动发送 |

主旅程 WJ01：单人 CodeHub 项目打开周报 → 选周期 → 自动生成 → 查一条关键进展依据 → 补充一项判断 → 重新生成且补充仍在 → 导出。异常旅程 WJ02：取数失败 → 保留旧报告／草稿 → 人工补充或重试 → 导出带缺口的草稿。demo 中周期固定，仅演示场景切换；自然语言语义冲突识别不在本轮覆盖内，人工显式修正与重新生成后的待核对提示可用于评审兜底体验。生产验证待建，模拟原型通过不标成真实 E2E。

价值观察关注是否仍需逐栏搬运、关键结论能否核对、缺口能否继续处理，以及 Leader 能否据报告理解目标推进；暂不编造效率收益和健康评分。

## 取舍与待决问题

固定管理关注点使报告完整，动态组织使内容适应项目；不把固定表格字段设成会话的唯一输入。先复用 CodeHub 和项目现有记录，不恢复 DTS、独立需求系统或多人协同套件。

本轮仅供设计评审：来源真实读取和分页／历史能力、与 Orca 会话及工作区的接线、报告保存协议尚未实现，需在意图与规格确认后写入实现设计并以真实证据核对。各项目报告周期和可选内容由项目上下文与使用者决定；不在 MVP 假定新的全局自动化时间。
