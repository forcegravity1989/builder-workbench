## 用户与问题

Builder 需要与模型一起核对本版交付，再向 Leader/showcase 参与者说明兑现了什么、有哪些证据、未达项如何处理。准备材料与逐目标验收应当连贯，不能要求用户在另一组通用交付清单、特殊迁移弹窗和重复会话入口之间来回操作。

Leader/Owner 在验收现场需要几分钟内读懂本版结论：哪些目标达成、哪些 Issue 遗留、遗留中哪些带风险、交付件在哪。验收屏若把计划材料、长文本与 Issue 清单平铺，目标和 Issue 又分处两大块，展示者就提炼不出结论，观看者也找不到有价值的信息。周报与验收数据同源（目标、Issue、交付件、风险），另立独立屏会造成双导航与双正本；周报应当是验收数据随时可出的导出件，不是第二个信息入口。

## 价值与依据

按原计划承诺组织交付、演示和人的判断，让包、证据、实测指标与结论都能追溯到同一候选版本。依据为本轮用户对周五上午出包、下午 showcase、独立验收分支以及 #257 相关交付反馈的明确要求。一次验收不依赖先开启下版计划。

## 目标体验

用户进入验收，即可看到“准备交付 → 出包 → 展示验收 → 归档”。左侧完整复用固定 bw/week-acceptance 工作区的 Orca 会话、历史和工具，右侧围绕原目标核对实际交付。首行“新建验收”让首次进入、尚无会话或遇到旧数据的用户都能开始协作；已有会话由原生入口继续。版本是主对象，周次是运行上下文。会话栏可收起，把整幅宽度让给板面——平时看板、展示时投屏都收起来，要看某个目标的报告或页面时再展开；收折行为与计划屏共用同一壳。

验收板分两个面。**准备面**给 Builder 与工作模型：在会话里按项目实际需要准备交付与证据，在同一组目标卡查看材料、历史指标读数及 Issue 状态；关联 Issue 直接列在所属目标卡内，长文本默认收起、点开编辑，板内可搜索目标与 Issue；哪些 Issue 验收后遗留、遗留中哪些带风险，由人在目标卡内逐条标记，不自动判定。由人判断达成、未达或待核并说明下一步。页面不额外设置统一的交付准备清单。

**Showcase 面**给展示时刻：只呈现提炼后的结论——逐目标的判定、约定与实际交付、交付件链接、指标实测、遗留与风险汇总，Builder 拿着这一屏向 Leader/Owner 讲述。跨周版本每周五做一轮进展刷新验收（可以不出包），轮次记录随材料保留、历史轮次只读可回溯；周报不是独立屏，而是在 Showcase 面把当前轮次材料一键派生为导出件（周报 HTML 或可复制文本），缺值如实写未知，人已填写的结论与说明不被导出重新生成。归档通过会话提 PR、人合入，总览按实际记录回看。

## 范围与边界

- 包含交付准备的会话协作、候选与证据关联、展示材料、原承诺核对、人的结论、未达安排、纪要归档和原生周期触发；不重建会话、历史或调度器。自动化首次登记默认关闭，由用户在原生编辑器配置。
- 周报并入验收作为导出件：不设独立周报屏、独立周报自动化或独立固定分支，不养第二份周报数据正本。周报试点（PR #321，未合入）中可继承的资产随本特性整改吸收（清单见 [spec](spec.md)「轮次与周报导出」），其余弃用；周报模板栏集不定死，按用户旅程调整，经人与 leader 确认后定稿。
- 包构建与测试复用项目实际已有工具；没有安装包概念的项目直接准备约定交付件，不强制二进制包或同一种报告格式。
- 不自建通用发布平台，不把出包等同正式发布，不自动完成 Issue、合入 PR、打 tag 或发布 Release。
- 原目标和约定保持只读，交付说明与人的判断可编辑。实际指标可选当前目录中支持日／周历史的脚本，保留计划原目标与基线，由人说明可比性；不反推读数或自动判定达成。
- 不做里程碑规划器；总览只读取已形成的版本记录。

## 成功判据与待决问题

Builder 能从上午准备连续完成下午展示与归档，验收者能核对每项目标及同一候选的材料，未达项有明确安排。Leader 在 Showcase 面不滚动长文本即可逐屏核对每项目标结论、遗留与风险、交付件链接；周报导出不需要任何二次录入。首用周记录取证困难、候选不一致、重复录入与归档遗漏，建立可用于优化的真实观察，不预填改善比例。

正式发布与验收人为项目既有安排；周五时间是典型旅程，不禁止其他日期使用，也不强制所有项目同一时刻。
