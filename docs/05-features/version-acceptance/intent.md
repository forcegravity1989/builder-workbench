# 版本验收：准备真实交付，展示成果并归档

> 给 Builder、Leader 与验收负责人判断价值和范围时读；本文管用户目标，不写控件与实现。行为见 [spec](spec.md)，设计见 [design](design.md)，证据见 [STATUS](STATUS.md)。目标或边界变化时更新。
>
> 状态：独立屏、独立固定分支和周五全旅程的定义已合入，用户已授权实施；产品尚未交付，执行证据见 STATUS。

## 用户与问题

周五不只是填验收结论。Builder 上午需要准备候选包、检查结果和展示材料，下午向 Leader/showcase 参与者说明本版兑现了什么，再处理未达项并归档。现有迁移设计把它缩成结果填写，还共用规划工作树，不能清楚承接准备到归档的完整工作。

## 价值与依据

按原计划承诺组织交付、演示和人的判断，让包、证据、实测指标与结论都能追溯到同一候选版本。依据为本轮用户对周五上午出包、下午 showcase、独立验收分支以及 #257 相关交付反馈的明确要求。一次验收不依赖先开启下版计划。

## 目标体验

用户进入验收，即可看到“准备交付 → Showcase 与验收 → 归档”。左侧是固定 bw/week-acceptance 工作树的 Orca 会话；每周新运行新会话，上午到下午、重开或重试继续同一次会话。版本是主对象，周次是运行上下文。

上午由会话核对本版计划及候选提交，调用项目已有出包/验证入口，整理包、交付件、验收报告、展示链接，刷新指标及 Issue 状态。下午沿同一组目标卡打开材料进行 showcase，由人判断达成、未达或待核并说明下一步。最后形成验收纪要，通过会话提 PR、人合入，回到总览可看该版本不同周的记录。

## 范围与边界

- 包含交付准备的会话协作、候选与证据关联、展示材料、原承诺核对、人的结论、未达安排、纪要归档和周期触发。
- 包构建与测试复用项目实际已有工具；没有安装包概念的项目直接准备约定交付件，不强制二进制包或同一种报告格式。
- 不自建通用发布平台，不把出包等同正式发布，不自动完成 Issue、合入 PR、打 tag 或发布 Release。
- 原目标和约定保持只读，交付说明与人的判断可编辑，指标实测只能来自脚本；缺历史不反推承诺或读数。
- 不做里程碑规划器；总览只读取已形成的版本记录。

## 成功判据与待决问题

Builder 能从上午准备连续完成下午展示与归档，验收者能核对每项目标及同一候选的材料，未达项有明确安排。首用周记录取证困难、候选不一致、重复录入与归档遗漏，建立可用于优化的真实观察，不预填改善比例。

正式发布与验收人为项目既有安排；周五时间是典型旅程，不禁止其他日期使用，也不强制所有项目同一时刻。
