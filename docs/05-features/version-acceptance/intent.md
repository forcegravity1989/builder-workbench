## 用户与问题

Builder 需要与模型一起核对本版交付，再向 Leader/showcase 参与者说明兑现了什么、有哪些证据、未达项如何处理。准备材料与逐目标验收应当连贯，不能要求用户在另一组通用交付清单、特殊迁移弹窗和重复会话入口之间来回操作。

Leader/Owner 在验收现场需要几分钟内读懂本版结论：哪些目标达成、哪些 Issue 遗留、遗留中哪些带风险、交付件在哪。验收屏若把计划材料、长文本与 Issue 清单平铺，目标和 Issue 又分处两大块，展示者就提炼不出结论，观看者也找不到有价值的信息。周报与验收数据同源（目标、Issue、交付件、风险），另立独立屏会造成双导航与双正本；周报信息应当直接由验收屏承载，不设第二个信息入口，也不再设导出件（2026-10-16 leader 拍板）。

## 价值与依据

按原计划承诺组织交付、演示和人的判断，让包、证据、实测指标与结论都能追溯到同一候选版本。依据为本轮用户对周五上午出包、下午 showcase、独立验收分支以及 #257 相关交付反馈的明确要求。一次验收不依赖先开启下版计划。

## 目标体验

用户进入验收，即可看到“准备交付 → 出包 → 展示验收 → 归档”。左侧完整复用固定 bw/week-acceptance 工作区的 Orca 会话、历史和工具，右侧围绕原目标核对实际交付。首行“新建验收”让首次进入、尚无会话或遇到旧数据的用户都能开始协作；已有会话由原生入口继续。版本是主对象，周次是运行上下文。会话栏可收起，把整幅宽度让给板面——平时看板、展示时投屏都收起来，要看某个目标的报告或页面时再展开；收折行为与计划屏共用同一壳。

验收板是单页，一个目标一张卡，整卡可收缩：收起只留结论行（结论灯、目标、人的结论、Issue 计数与遗留/风险标记），展开是完整故事——约定交付、内列的关联 Issue、指标实测、实际交付与依据、未达与下一步、可直接打开的交付件链接。哪些 Issue 验收后遗留、遗留中哪些带风险，由人在目标卡内逐条标记，不自动判定。由人判断达成、未达或待核并说明下一步。页面不额外设置统一的交付准备清单。

严格意义上验收覆盖 showcase 会前、会中、会后三个阶段，三个阶段看的是同一块板、同一组主要信息：会前 Builder 与工作模型展开卡片备料——填实际交付与依据、标记遗留与风险、刷新指标、出包；会中拿着验收屏给 Leader/Owner 逐目标讲——「全部收起」后结论行一览，讲到哪张卡展开哪张；会后补未达安排与下一步、确认结论、在会话中发起归档，人合入，总览按实际记录回看。跨周版本每周五做一轮进展刷新验收（可以不出包），界面按周呈现、历史周只读可回溯。周报不设独立屏也不设导出件；「预览纪要」是唯一派生文本。

## 范围与边界

- 包含交付准备的会话协作、候选与证据关联、展示材料、原承诺核对、人的结论、未达安排、纪要归档和原生周期触发；不重建会话、历史或调度器。自动化首次登记默认关闭，由用户在原生编辑器配置。
- 周报并入验收后进一步简化为不设导出件（2026-10-16 leader 拍板：信息由验收屏承载）：不设独立周报屏、独立周报自动化、独立固定分支与周报导出件，不养第二份周报数据正本。周报试点（PR #321，未合入）整体废止、资产不迁移。
- 包构建与测试复用项目实际已有工具；没有安装包概念的项目直接准备约定交付件，不强制二进制包或同一种报告格式。
- 不自建通用发布平台，不把出包等同正式发布，不自动完成 Issue、合入 PR、打 tag 或发布 Release。
- 原目标和约定保持只读，交付说明与人的判断可编辑。实际指标可选当前目录中支持日／周历史的脚本，保留计划原目标与基线，由人说明可比性；不反推读数或自动判定达成。
- 不做里程碑规划器；总览只读取已形成的版本记录。

## 成功判据与待决问题

Builder 能从上午准备连续完成下午展示与归档，验收者能核对每项目标及同一候选的材料，未达项有明确安排。Leader 在会中逐卡核对每项目标结论、遗留与风险、交付件链接，收起态不需要滚动长文本；周报没有第二出口，也就没有二次录入。首用周记录取证困难、候选不一致、重复录入与归档遗漏，建立可用于优化的真实观察，不预填改善比例。

正式发布与验收人为项目既有安排；周五时间是典型旅程，不禁止其他日期使用，也不强制所有项目同一时刻。
