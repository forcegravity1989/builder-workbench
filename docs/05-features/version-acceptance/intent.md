## 用户与问题

Builder 需要与模型一起把本版交付备齐，再在周五的会上向 Leader 和参会者说明兑现了什么、证据在哪、未达项怎么安排。备料与开会应当是同一块板面上的连续动作，不能要求人在另一组通用交付清单、特殊迁移弹窗和重复会话入口之间来回操作。

Leader 在会上需要几分钟内读懂本版结论：哪些目标达成、哪些没达成、没达成的安排是什么、哪些 Issue 带入下版、交付件和演示环境在哪。验收屏若把计划材料、长文本与 Issue 清单平铺，目标和 Issue 又分处两大块，展示者提炼不出结论，观看者也找不到有价值的信息。

逐项核对需求有没有做完，是周中在会话与开发流程里发生的事，不是周五会上的事。把它塞进验收屏会让会上既有备料又有自查，两边都做不完。

## 价值与依据

按原计划承诺组织会议材料、演示和人的判断，让包、演示环境、证据报告与结论都能追溯到同一个候选版本。依据为本轮用户对周五上午出包、下午 showcase、独立验收分支的明确要求，以及 #257 相关交付反馈；一次验收不依赖先开启下版计划。

## 目标体验

用户进入尚未开始的验收时，先看到简短开始卡；原生运行会话实际打开后，呈现连续的会议流程：**验收准备 → Showcase → 会议纪要 → 归档 PR 及发版本**。左侧完整复用本版验收工作区的 Orca 会话、历史和工具，右侧是单页四区板面，顶部导航只做同页定位，不是门禁也不代表完成——先备哪步、回头改哪步都可以。

会前，Builder 与验收助手把材料备齐：人点出包、点部署，模型下载包并按项目自有的部署入口把服务或桌面应用跑起来，把演示环境写回材料；人点预订会议，模型先给完整预览、人确认后才订，会议信息写回材料；人点聚合，模型把各 Issue/PR 合入时留下的验收件按目标归并成一份验收证据报告——一个版本一份，逐 Issue 给验收说明和一条条可核对的实物证据，缺证的如实标出、由人确认缺口或自行补充。

会上，对着勾勾表逐目标讲：计划里的目标原样只读复用，讲到哪条就地演示（打开真机演示环境实操，或翻到报告对应 Issue 的验收件），讲完由人在单个状态中选择未判定、达成或不达成。界面不替人推定、不拿演示过当达成。不达成的目标，原因和安排写进纪要、目标的下一步与对应 Issue 的备注。

会后，会上记的批注和可选的会议转写稿由验收助手按目标总结成两块——共识与遗留，人可以随意增删改，也可以直接粘贴自己写的，确认之后才算生效，确认了也还能撤销；纪要形成后可把已填写或确认的内容按固定样式同步到预订会议的纪要草稿，最终发送由人在会议系统手动完成。归档前每条遗留已落实或有真实跟进 Issue，助手核对后交 PR 人审；Issue 不必先关闭，不增加界面门禁。已确认遗留成为下版的固定来源参考，不自动变成任务或新承诺。归档由助手在会话里提 PR，屏上只放引用、真实状态和打开原生 PR 页的入口；要发版的由人点一下发布，请求进会话，预检、授权、执行和读回都在会话里完成。

会话栏可以收起，把整幅宽度让给板面——平时看板、开会投屏都收起来，要看某个目标的报告或页面时再展开；收折行为与计划屏共用同一壳。

## 范围与边界

- 包含会议材料准备的会话协作、候选与证据关联、演示环境、展示材料、原承诺核对、人的结论、未达安排、纪要、归档与原生周期触发；不重建会话、历史或调度器。自动化首次登记默认关闭，由用户在原生编辑器配置。
- **个人自验不在本屏，举证随各 Issue/PR 合入时留下**：逐项核对需求是否完成发生在周中的会话与开发流程，验收件（有开发取 PR 验证评论，无开发直接关闭取 Issue 评论）在那时留下；本屏只聚合呈现、不采集，屏上不提供逐条验收件核对工作面。
- **不做多人协作验收**：结论选择与纪要确认都是单人人工动作，不承载多人协同批注、签署或分派。
- **一个版本做一轮验收**：不再承载跨周版本每周五刷新一轮进展、按周呈现、历史周只读回溯的场景。历史仍可按固定提交读回，因为下版计划要据此回看上版的延期遗留与会议遗留。
- **两份报告，各管一件事，不互相代替**：验收证据报告是逐 Issue 的验收件罗列，给会上核对与展示用；workbench-release 的版本收尾报告是偏总结的叙事，给领导与升级试用者用。BW 自身收尾时两份都出。这不是给同一份周报开两个出口——验收屏不设独立周报屏、不设周报导出件、不养第二份周报数据正本。
- **发布执行在会话，状态回显在板面**（#462 修订 v10「板面不呈现发布状态」决策）：板面提供注入入口与发布状态读回——是否已发布、标签、发布时间、Release 页地址与资产，全部按材料里的 tag 引用向 provider 现算，读数不落材料；预检与授权在会话里由人做，发布读数的正本在 Git 标签与 Release 页。总览仍不显示「已发布」。
- **会议动作先预览后执行、只写草稿**：预订会议先生成完整预览、人确认后才执行；同步会议纪要只把已填写或确认的内容写进预订会议的纪要草稿，最终发送由人在会议系统手动完成。会议动作的逻辑内置于验收助手，用户不需要额外安装会议技能；模型不代发、不代订会议室、不推断发言人、不虚构会议步骤。
- 包构建与测试复用项目实际已有工具；没有安装包概念的项目直接准备约定交付件，不强制二进制包或同一种报告格式。
- 未合入计划也能先开启验收会话，由助手先提醒并协助处理；没有可读固定计划时目标留空，不伪造依据或结论。
- 不自建通用发布平台，不把出包等同正式发布，不自动完成 Issue、合入 PR、打 tag 或发布 Release。
- 原目标和约定保持只读，交付说明与人的判断可编辑。验收件只进报告，板面不再回显指标行；不拿旧读数冒充本期值，也不反推读数或自动判定达成。
- 界面不用灯表态：旅程、出包、归档的灯全部退役，状态一律以文字和真实读回呈现，读不到就是未知，不默认绿。
- 风险标记与呈现能力整体去掉（2026-10-21 决定，与计划屏同步）；未来有真实需要再议恢复。
- 不做里程碑规划器；总览只读取已形成的版本记录。

## 成功判据与待决问题

Builder 能从上午准备连续完成下午展示与归档，验收者能核对每项目标及同一候选的材料，未达项有明确安排。Leader 在会中逐条核对目标结论、遗留与演示环境，收起态不需要滚动长文本；纪要确认后能直接成为下版计划的输入，不需要二次录入。首用周记录取证困难、候选不一致、重复录入与归档遗漏，建立可用于优化的真实观察，不预填改善比例。

正式发布与验收人为项目既有安排；周五时间是典型旅程，不禁止其他日期使用，也不强制所有项目同一时刻。

**已随 #471 关闭**：个人自验落点——自验与举证发生在周中会话与开发流程，验收件随各 Issue/PR 合入时留下，本屏只聚合呈现。**待决**：会议通知等其余会议环节与纪要协议级目标绑定，留待后续会议相关 Issue。「查看验收依据」已确定进入固定来源的只读历史整页，帮助人在不改写历史材料的前提下核对上版结论。
