# 版本验收

协助 Builder 走完验收屏四步:**验收准备 → Showcase → 会议纪要 → 归档 PR 及发版本**。本屏为周五验收会议服务:会前把材料备齐(部署好的真机演示环境 + 一份验收证据报告),会中对着勾勾表逐目标演示,会后纪要确认、归档、按需发版。个人对需求的逐项自验发生在周中的会话与开发流程,不在验收屏;典型周四准备、周五开会,版本与项目要求优先,不把时钟当门禁。

通过宿主的 `orca skills get version-acceptance` 读取本流程;`--references` 列出可用引用,`--reference <名称>` 按需读取。只使用实际下发的身份、材料命令和原生执行能力,普通项目无需检出 BW 源码。入口提供当前选版与实际工具身份;先使用这些上下文,不要求用户提供 BW 源码。

## 阶段进度(材料内部,界面无灯)

验收材料的 `workflow.stage` 记录**最近完成的阶段**(preparation/showcase/archive),只用于会话恢复时校准进度与自动化读取,**界面不渲染灯或进度条**——板面状态一律以文字与真实读回呈现。每完成一个阶段就用 `ORCA bw materials save` 更新:

| 阶段 | stage 值 | 何时写入 |
|---|---|---|
| 验收准备 | `preparation` | 候选固定、服务部署可演示、验收证据报告生成并登记 |
| Showcase | `showcase` | 会议逐目标演示完成、每条目标的达成/不达成已由人在界面标记 |
| 归档 | `archive` | 提交归档 PR 之前;PR 开出后把 provider/repository/number 写入 `workflow.archivePr` |

恢复会话时先校准:按材料实际进度把 stage 补写到真实到达的阶段。达成/不达成与纪要确认仍只由人在界面记录,不代签;stage 不代表目标达成,也不代表 PR 已合入或版本已发布。纪要的人工确认是材料字段事实,不占 stage。

## 验收证据报告

**一个版本一份,所有目标合并**,是会议展示与验收核对的证据正本:

- 结构:按「目标 → 验收点」组织;每个验收点含**详细的验收说明**与**一条条罗列的验收证据**(截图、指标读数、平台读回、文件位置)。
- **演示分诊**:适合周五现场演示的验收点标注「现场演示」并写清操作路径(在部署好的服务里点哪几步),不落静态证据;不易演示、步骤复杂或需要等待的,把证据落进报告。
- **指标证据只进报告**,验收屏板面不回显指标行。
- 由模型在验收准备阶段生成,落 `.bw/planning/<版本>/` 并登记进验收 JSON;经内置 Orca 浏览器打开。
- 只收可核对实物与说明,不用大段文本代替证据;缺证据的验收点如实标缺,不凑数。
- **与版本收尾总结报告分工**:本报告逐验收点罗列证据(给核对与会议用);workbench-release 的收尾报告偏总结叙事(给领导与升级试用者用)。两者独立,不可互相代替。

## 执行流程

1. **恢复本次验收。** 先展示完整四步流程和已有进度(按校准后的 `workflow.stage`),再核对场外要求、实际项目与固定 bw/week-acceptance 工作树。入口已给出版本时直接恢复该版材料,不再选第二次。没有验收时基于本分支该版已提交计划初始化草稿并自动保存。版本未明确时先列候选,与人明确后才写材料;未合入计划只能明确标为草案预验收。开工前核对固定树与基线分支关系:behind 且 ahead=0 可 fast-forward 更新;ahead 含未归档材料提交时先与人确认顺序,不自行合并。同次会议的准备与重试继续原会话,不混用 bw/week-plan。

2. **出包与部署。** 需要安装包时用验收屏「出包」区块:按项目远端自动对接出包流水线(从主分支构建),由人选流水线并点「出包」;受理后最新包每分钟自动刷新,不重复启动。核对最新包四字段确实对应本次候选,不把旧包当本次交付包。确定候选后**写入 `candidateRef`**;包出现后**登记 `preparedArtifacts`**(`kind=package`,含 checksum、location、实际命令)。随后**部署**:界面「部署」自动下载最新安装包并本地部署启动,部署后的服务就是版本的**真机演示环境**,在内置 Orca 浏览器打开;会话侧执行等价动作时按项目自有部署入口进行。缺入口说明缺什么,不虚构命令;**环境缺少所需工具(如浏览器自动化)时,说明缺什么并请人安装后继续,不降级绕道**。区块报错如实转告,改按项目自有出包入口执行并核对;没有包要求就不造包要求。

3. **准备验收证据、生成报告。** 从固定计划的目标与验收标准整理每个目标的验收点;对着**部署后运行中的服务**采集证据:浏览器实操截图(每张记核对哪个验收点、执行路径、期望结果)、真实指标脚本读数(按指标协议写 readings)、平台读回(PR/CI/Issue/Release 链接+摘要)。按「演示分诊」把每个验收点定为现场演示或报告条目,合并生成**一份**验收证据报告,落材料目录并登记。批注是人的意见输入通道:人在板面批注并发送给你时,按批注对象(目标/Issue)理解意见并回应或修订材料。包重出不自动刷新已填内容;检测到包变化时在会话中提醒「包已重出(旧→新),涉及哪些目标的证据,是否重核?」,人同意才重核,且只重核受影响部分。准备齐后写 `stage=preparation`。

4. **Showcase 支持。** 勾勾表复用计划屏目标行,目标与验收标准只读回显。会中对着目标逐条进行:现场演示的在内置浏览器实操真机演示环境,报告条目打开对应验收点展示;**每条目标行尾的达成/不达成由人标记,模型不代勾、不代签**。未标保持空白,不冒充、不推定;演示过与否不进材料。不达成的目标:原因与安排进纪要、目标「下一步」和对应 Issue 的备注/「遗留」标记(Issue 只有遗留标记,无风险标记)。全部目标标记完成后写 `stage=showcase`。

5. **会议纪要。** 纪要卡与计划屏同款:输入=板面在线批注(人发送给你)+可选会议转写稿(会议 ID 由人提供;没有稿件或来源不可读时如实说明,不凭空补写会议内容)。你把输入总结为固定两块:「**共识**」(若干点)与「**遗留**」(若干点);遗留条目**不设闭环状态**——会上已解决的写进共识或不写入遗留,遗留条目原样成为下版计划屏「会议遗留」的来源。总结经人在界面编辑(可直接粘贴修改)、**人工确认后生效**;你不代确认、不代签,纪要确认前不推进归档。

6. **归档与发版本。** 用户在会话中直接要求归档:核对材料与结论状态后写 `stage=archive`;在固定 bw/week-acceptance 工作树内提交材料(验收 JSON、验收证据报告及截图)并推送远端,创建由 bw/week-acceptance 到主分支的 PR/MR,按项目流程和授权执行,不另建工作树或分支;开出后把 provider/repository/number 写入 `workflow.archivePr` 并回显链接;屏内只呈现引用、状态与原生 PR 页入口,评论与再审回原生界面。需要发布的版本:**先向人呈现各目标达成/不达成与遗留——不达成不阻断发布,由人知情决定**;核对发布提交与验收的包一致,不一致(如会后修复)列出差异与来源待人确认;按项目自有发布入口与既有授权执行;发布后**独立读回**(tag、时间、资产、校验值)写入材料发布记录;PR 未合入时发布记录随同一 PR 补注,已合入按归档后补证处理。未经人明确授权不创建 Release、不打标签;不合并 PR、不关闭 Issue、不替人确认版本达成。

7. **归档之后。** 合入后从项目主干基线(主检出)读回,总览每版显示一份当前材料;纪要「遗留」条目与 Issue「遗留」标记分别作为下版计划屏的「会议遗留」与「延期遗留」回显,由下版计划会话与人形成候选,不自动承诺或排期。归档后补证继续编辑同一份验收并保留 cycleId,旧依据从 Git 追溯。出包、合入、Issue 完成和正式发布不互相代替。首用时记录材料找不到、报告与演示对不上、重复录入和未达无安排等实际问题,不预填改善结果。
