# intent · 开工认领（Issue Start Claim）

> **30 秒导读**：多人用 Workbench 并发开发同一项目时，谁开工了哪个 Issue 只有开工者自己的实例知道，协作者的任务屏一律显示未开工。本特性让「开工创建工作区」自动把当前用户标记为 Issue 责任人（assignee），开工状态借 GitHub/CodeHub 原生字段跨机可见。读者：评审本特性的产品与实现者；认可后由 [spec.md](spec.md) 承载行为与验收。更新时机：客户价值、范围或认领语义变化时。

- 状态：**已认可**（2026-10-30 人拍板；来源：[#512](https://github.com/forcegravity1989/builder-workbench/issues/512) + 产品负责人 2026-10-30 拍板「开工就把当前开 worktree 的用户标记为责任人」）

## 用户与问题

多个 Builder 各自在自己电脑上跑 Workbench、连到同一台远程开发机开发同一项目。开工状态（谁正在做哪个 Issue）目前锁在各人实例本机：任务屏 Issue 行的 Open/Start 判定只读本实例的工作区元数据（`linkedIssue` 存在实例本地用户数据目录，不进 git、不上平台），开工动作也不写任何跨机信号。结果是协作者 A 开工了 #1，B 的任务屏上 #1 仍显示 Start——B 无法判断哪些任务已有人在做，容易重复开工或误判无人认领（[#512](https://github.com/forcegravity1989/builder-workbench/issues/512)）。

## 价值与依据

**最核心利益：开工即认领，谁在做哪个 Issue 对所有协作者即时可见**——不需要任何新界面，任务屏原生责任人列和 GitHub/CodeHub 平台原生视图就是呈现。

依据：#512 是真实使用反馈；产品负责人 2026-10-30 明确拍板方向「增加一个开工就把当前开 worktree 的用户标记为责任人」。上游核对（v1.4.223–244，2026-10-30）确认 Orca 无同类能力，需 BW 自建；而认领信号写进 Issue 原生字段是现有约束下最薄的跨机通道（平台是所有实例共享的正本）。

## 目标体验

A 在任务屏（或计划板/目标行）对一个 Issue 点 Start，创建工作区成功后，该 Issue 的责任人自动出现 A 的账号；A 什么都不用多做。B 稍后刷新任务屏，#1 的责任人列显示 A——B 知道这个任务已有人在做，转去看别的任务或去和 A 对齐。在 GitHub/CodeHub 网页上同样能看到认领，不依赖 Workbench。

## 范围与边界

- 做：Issue 开工创建工作区成功后，自动把当前用户 add 为该 Issue 责任人（GitHub 与 CodeHub，BW 开工面已就绪的两个 provider）。
- 不做：不新增任何界面（复用原生责任人列）；不自动摘除责任人（完成、关闭、删树都不动 assignee——完成由人确认）；不改 Issue 的其他字段（标题、标签、状态一律不碰）；PR 开工不认领（PR 已有作者语义）；GitLab/Linear/Jira 不在本期；不做认领开关设置项（有真实反馈再加）。
- 与相邻特性的关系：挂载点与 version-workspace 的「真实创建结果处写版本绑定」同站点、同模式（失败不阻断、如实提示），但认领不依赖版本上下文——无 BW 范围的原生任务屏 Start 同样认领。

## 成功判据与待决问题

**成功判据**：两台机器两个实例对同一远程项目并发开工不同 Issue，各自任务屏都能看到对方认领的 Issue 责任人；认领失败时开工不受影响且如实提示。

**已决问题**（2026-10-30 人拍板；行为细则见 spec「取舍与已决问题」）：

1. Issue 已有其他责任人时，开工者仍把自己追加进去（幂等，不移除他人）。
2. CodeHub 认领与 GitHub 首期一起交付。
