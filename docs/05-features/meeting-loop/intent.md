# 会议工作台：让 BW 会议结果回到团队和项目

> 给 Builder、Leader 和产品评审者读取。本文只定义用户价值、范围和边界，行为与验收见 [spec](spec.md)，可交互原型见 [prototype.html](prototype.html)。当前处于原型评审阶段，原型不表示能力已经交付。用户价值或会议边界改变时更新，不追加讨论流水。
>
> 状态：基于 Issue 159 最新评论、PR 719、PR 709、仓内 WeLink 接入和计划/验收规范形成的设计草案，等待原型评审确认。

## 用户与问题

团队成员和项目负责人需要在 BW 中安排版本计划会、项目原型评审会、PR 评审会和验收会等会议。团队会议通常覆盖多个项目，项目在一段时间内也可能有多场不同会议。当前 WeLink 已经负责视频、录音、AI 听会、转写、通用总结和正式纪要，BW 仍缺少一条把团队或项目上下文带进会议、在会中辅助推进、再把确认后的共识和遗留带回工作状态的路径。

用户因此需要在团队群、项目资料、计划屏、WeLink 预订页、会议纪要和后续任务之间反复搬运信息。会议助手如果只负责问问题或生成一份总结，仍然不知道会议属于哪个团队或项目，也无法减少固定会议准备和会后跟踪的重复工作。

## 价值与依据

核心利益是让人从 BW 的团队或项目上下文发起一场会议，会议助手按已确认的会议模板准备议题和参会人，WeLink 负责会议事实，BW 负责把人确认后的结果组织回团队、项目和版本。

设计依据包括 Issue 159 对会议助手意图、WeLink 能力和会议工作台边界的连续反馈，PR 719 对团队多人协作入口的现有原型，PR 709 对团队概念和 BW 工作台骨架的设计，以及仓内 `welink-cli`、计划批注、版本计划和版本验收的现行实现与规范。内部调研的稳定结论是，WeLink 承载会议事实，BW 承载会议改变了哪些项目或团队工作状态。

## 目标体验

用户从 BW 全局 WorkbenchRail 的「会议」入口进入会议工作台。左侧按团队、项目和会议组织会议实体，一个团队可以有多个项目，一个项目可以有多场会议。用户在团队或项目节点旁发起会议，会议助手收到一条带有对象上下文的可编辑请求。固定会议模板减少首次提问，临时会议仍可直接发起。

会议助手在复用的 Orca 会话中用普通消息和 AskUser 多选完成必要确认。确认前展示时间、参会人、议题和关联材料，外部预订和群通知按现有规范先预览再执行。每场会议有自己的主会话，人可以在会议间隙新建个人议题会话整理发言或问题。会话属于会议记录，不创建新的项目目录或工作树。

会议开始后，WeLink 原生视频会议打开为主要视区，会议助手在旁边后台运行。议题开始、临近结束、超时、WeLink 议题结果和计划上下文变化以轻量状态回显。助手不在讨论中途用 AskUser 阻塞人，议题结束后的候选共识和遗留进入待确认队列。人在议题间隙或散会后确认哪些结果写回 BW。

WeLink 继续保存视频、AI 听会、转写和正式纪要。BW 保存会议归属、模板、议题进度、人工确认的共识和遗留，以及指向项目、团队或版本的跟踪入口。BW 不复制一份完整纪要，不自动创建或完成 Issue。

## 范围与边界

- 包含全局会议入口、团队/项目/会议树、固定会议模板入口、会议助手会话、同一会议下的个人议题会话、会中后台状态、待确认结果队列和 BW 跟踪回显。
- 首期模板覆盖团队版本计划会和项目原型评审会。PR 评审会、团队验收会和项目验收会复用同一会议对象与会话外壳，模板内容随后补齐。
- 复用 BW WorkbenchRail、Orca 会话屏和浏览器页签，复用 WeLink 原生视频、AI 听会、转写、总结和纪要页面。
- 会议预订、群通知和写入纪要草稿遵守现有预览、人工确认和手动发送规则。
- 不新增项目工作树、会议专用文件目录、独立视频或转写系统、平行的完整纪要系统、自动 Issue 完成协议或无人值守的人工确认。

## 成功判据与待决问题

用户能从团队或项目节点发起一场会议，确认次数随模板记忆减少，能在 WeLink 中完成会议并在 BW 中看到待确认结果。会议中途不因助手等待回答而停住，会议结束后人能清楚知道哪些结果仍待确认、已经写回哪里以及下一次会议会带入什么。

仍需在实现前确认 WeLink 议题和时间事件的可靠读取方式、模板保存的具体材料位置、会议对象的权限范围，以及全局会议入口在 BW 正式导航中的最终位置。原型已用可观察的占位状态表达这些边界，不能替代真壳和真实 WeLink 验证。
