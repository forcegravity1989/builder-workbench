# 版本总览：看清一版的承诺、成果与交付

> 给 Builder、Leader 和设计评审者在判断价值、范围时读。本文定义版本总览为什么做、为谁做及边界；行为与验收见 [spec](spec.md)，认可、实现和验证见 [STATUS](STATUS.md)。价值或范围改变时更新，不记开发流水。
>
> 状态：用户确认的设计已随 #459 合入，#334 开发沿 #474 交付。修订 13 的六节点、验收 PR 交付时间、集中采集来源与目标内 workflow 六项读数已接入生产；首次后台读取、来源范围隔离缓存与独立刷新沿已确认决定实现。实际运行结果与未验证边界见 STATUS，不以原型或旧验证代替本轮证据。

## 用户与问题

Builder 需要知道当前版本为什么做、正在做什么、有哪些成果可以评审、接下来从哪里继续工作。Leader 需要对照当时承诺与实际交付，核对试用范围、风险和人工验收，而不必先翻遍会话、PR 和归档文件。

版本总览原先以简表回看主干计划和验收，未合入成果不易发现。本特性把目标、特性历程与原生成果入口放在同一页。会话结束、PR 合入、用户可用、Issue 关闭和目标达成仍是不同事实，不能被一盏状态灯替代。

## 目标体验

从 BW 现有“项目 → 版本 → 总览”进入，侧边栏、版本计划、任务、验收、原生工作树和工作会话始终有上下文。未计划、版本中和交付后共用按版本目标组织的结构，随后是 AI workflow 生产力与本版记录。目标保留名称、负责人、任务数量和原生目标任务入口，人工验收徽标原位回显来源、确认时间和后续处理；不再提供“范围与验收标准”入口、弹窗或“本版范围”展开块。完整承诺继续从原有计划／验收导航查看，数据逐步填充，历史版不切换成另一张报告。

特性用六个节点串起横向历程：周期起点、意图确认、设计定稿、开发交付、Pre、Release。周期起点取首次包含该特性的计划 PR 合入所在周的周一 09:00，是固定统计基线，延期不重置，也不冒充实际开工；计划 PR 合入代表意图确认。intent、spec 与原型共同评审后，设计 PR 合入代表设计定稿；随后详细设计、Plan 与开发在原生会话中推进，开发 PR 合入代表 Builder 交付，无法识别开发 PR 时才以特性 Issue 关闭时间兜底，并保留来源。

六节点之间形成意图收敛、设计评审、开发、测试与随版准备、试用完善五段日历历时。时间精确到小时和分钟，按间隔呈现；测试与修复可以并行、回返，不套用强制审批链，也不把随版等待算成纯测试工时。轴下集中列出计划、设计、开发、Pre 验收、Release 验收的全部采集来源，轴与悬停提示承载时点和历时，不再另开过程详情或重复阶段说明面板。移除特性时间轴的工作会话按钮，原生侧栏的会话能力继续保留。Plan 通常留在原生会话中，真实开工或独立测试时点没有依据时继续留白。

项目版本发布与这个需求是否随版交付分别呈现。其他目标完成时版本可以正常发布，而本需求仍未形成 Pre；后续某版才提供 Pre，再由后续版本正式交付 Release。特性跨版持续，不以项目发布、单版验收或 PR 合入替代需求完成。反馈、新需求和 bug 均进入关联目标的 Issue。

与项目总览共同承接“选择需求与目标版本 → 先行版本 Pre → 部分用户试用 → 后续版本修理完善 → 后续 Issue 持续改善”。讨论、导航和承诺均以实际版本为单位；不强制 C/B 命名或周期分组。每版仅一次正式人工验收。正式计划关联和目标人工达成决定是否计入随版交付，交付时点统一取该版本验收 PR／MR 的合入时间，首次称 Pre，第二次称 Release；未达成不计，缺验收 PR、尚未合入或缺时间时保持未知，不能用人工确认时点补齐。该合入节点是本项目的交付约定，不冒充独立核验的包发布时间。同目标有多个特性时暂沿整体目标结论，不能区分个别例外。已登记且有完整依据的临时版可承接延期 Pre；未登记的临时出包不会自动发现，只呈现交付未记录。每周一版、两版完成只是规划默认值，不自动产生交付节点。

从项目总览或规划工作区进入版本时定位对应需求，返回保留来源上下文与草案。同一需求的关联版本以一排版本号标签呈现，悬停或键盘聚焦看一句目标范围，点击进入相应版本继续核对。只有明确关联才展示，历史未单列的增量保持未记录，不用当前理解补写历史承诺。

有特性主单或明确关联特性的执行 Issue 时，在其所属目标内分别呈现特性时间轴；其余任务保留数量和原生目标任务屏入口，不重复开发任务列表，也不要求每个项目设“小需求 / bug”专项目标。同一目标可以同时包含多个特性和普通任务。

目标下方的 AI workflow 生产力读取本版本目标内 Issue 所关联 PR 评论中的六项报告，沿 workflow 正本解释，单任务跨多个 PR 不重复计数，缺报告或缺覆盖保持未知。基础内容与 AI 读数可分别刷新，读数保留来源和截至时间；同一来源范围的刷新失败保留上次读数并提示错误，不把每次渲染变成全量请求。只对实际纳入目标的 Issue 负责，不扫描或自动纳入计划外任务。PR 合入不代表首次人审通过。

## 范围与边界

- 保留版本、目标、负责人、范围、时间、任务、计划 / 验收、纪要、归档与发布依据；按重要性组织，不堆成独立状态卡片。
- 正式承诺、计划草稿、最新成果与历史验收各有来源；缺证据保持未知。不能把计划 / 验收材料的 `workflow.stage` 当特性 SDLC，也不以 G1 / G2 充当跨版需求身份。
- 版本总览独立承载规格和原型；[版本工作区](../version-workspace/spec.md)继续负责侧边栏、工作树归属与版本收尾。计划、验收、项目总览、任务和会话沿既有能力，不因特性拆分另造执行器或复制公共资源。
- 首轮候选为单项目只读聚合与现有工作入口。跨版身份、版本关系、共享导航和未合入成果的关联载体由统筹会话协调；原型 JSON 只是固定读数，不是新业务协议。保留既有侧栏，不新增独立月度总览、C/B 分组或会话屏。

## 审阅与成功判据

先看[旅程](journey.html)，再操作[高保真](prototype.html)。版本中和历史版默认呈现同一完整模拟横轴，模拟时序、真实 PR 来源和 workflow 单任务报告分清身份；信息集中在轴、悬停提示与来源行，不用先寻找示例入口。用 Orca 原生浏览器批注反复修订，最终原型要能作为落地形态依据；面向评审的说明统一以 `原型注释:` 开头，不能混入拟交付的产品文案。

成功标准是用户能从本版承诺定位真实成果、待审项和原生工作入口，分清可用范围与缺失依据，并在历史版本核对当时人工结论。可观察判据与真实运行缺口见 spec / STATUS，不用截图、源码或 CI 代替用户认可与价值效果。

本次采用一个特性主 Issue、两个 PR：#459 承载本轮设计，设计经人确认合入后，开发另开 PR 继续关联 #334。是否拆执行 Issue 取决于分工与范围，不为阶段统计强制拆单。读取、节点解析与展示分开；项目规范改变时可更新解析规则，不把“两 PR”写成永久产品限制。
