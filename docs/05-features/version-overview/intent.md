# 版本总览：看清一版的承诺、成果与交付

> 给 Builder、Leader 和设计评审者在判断价值、范围时读。本文定义版本总览为什么做、为谁做及边界；行为与验收见 [spec](spec.md)，认可、实现和验证见 [STATUS](STATUS.md)。价值或范围改变时更新，不记开发流水。
>
> 状态：用户于 2026-10-27 明确版本总览独立为特性，并要求高保真保留 BW 原有旅程、使用自身真实数据、区分产品内容与原型注释。具体意图、规格和高保真仍在反复审阅中，不代表完整制品已获认可。

## 用户与问题

Builder 需要知道当前版本为什么做、正在做什么、有哪些成果可以评审、接下来从哪里继续工作。Leader 需要对照当时承诺与实际交付，核对试用范围、风险和人工验收，而不必先翻遍会话、PR 和归档文件。

当前生产总览已能读取主干提交的计划和验收，以简表回看；未合入的设计、Plan、开发和测试成果不易发现。会话结束、PR 合入、用户可用、Issue 关闭和目标达成也是不同事实，不能被一盏状态灯替代。

## 目标体验

从 BW 现有“项目 → 版本 → 总览”进入，侧边栏、版本计划、任务、验收、原生工作树和工作会话始终有上下文。未计划、版本中和交付后共用同一结构：承诺与验收 → 大需求 → 小任务 → AI workflow 生产力 → 本版记录。数据逐步填充，验收结论回填顶部承诺区；交付后仍保留需求与任务，不切换成另一张报告。

大需求用横向时间段看清过程：初始意图到原型 / spec 反复共同评审定稿，随后详细设计、Plan 与开发一起推进，测试与试用反馈穿插其中。时间精确到小时和分钟，点击轴上阶段就近打开 PR、原型、spec 等成果，保留评审状态与修订来源，避免另铺一大块成果看板；有依据的起止可比较日历历时，不把等待或并行区间当人工工时。Plan 通常留在原生会话，不要求入库。

项目版本发布与这个需求是否随版交付分别呈现。其他目标完成时版本可以正常发布，而本需求仍未形成 Pre；后续某版才提供 Pre（此前的 MVP），再由后续版本正式交付 Release。大需求跨版持续，不以项目发布、单版验收或 PR 合入替代需求完成。反馈、新需求和 bug 均进入关联目标的 Issue。

与项目总览共同承接“选择需求与目标版本 → 先行版本 Pre（MVP） → 部分用户试用 → 后续版本修理完善 → 后续 Issue 持续改善”。讨论、导航和承诺均以项目的实际版本为单位；月度、周只是可能采用的节奏，不强制 C/B 命名或周期分组。每版仅一次正式人工验收；设计批注、规格评审和试用反馈不增加版本验收次数。先行 MVP 的版本、包和可用范围记录在发布成果里；已知问题和后续工作统一通过目标下的 Issue 跟踪，不按两周周期决定反馈放在哪里。

从项目总览或规划工作区进入版本时定位对应需求，返回保留来源上下文与草案。同一需求的关联版本以一排版本号标签呈现，悬停或键盘聚焦看一句目标范围，点击进入相应版本继续核对。只有明确关联才展示，历史未单列的增量保持未记录，不用当前理解补写历史承诺。

任务列表显示是否实际采用项目 AI workflow 的依据；下方独立观察初始输入、澄清、原型评审、真机验证中的人工介入及返工。统计口径作为正式产品说明，可悬停或聚焦指标查看，用清楚的定义解释分母、范围和含义；原型尚未接线的说明另行标注。每个项目使用自己的流程，目标是在质量门禁不降低的前提下减少不必要介入和返工，不以 Issue 关闭数量代表 AI 生产力。

## 范围与边界

- 保留版本、目标、负责人、范围、时间、任务、计划 / 验收、纪要、归档与发布依据；按重要性组织，不堆成独立状态卡片。
- 正式承诺、计划草稿、最新成果与历史验收各有来源；缺证据保持未知。不能把计划 / 验收材料的 `workflow.stage` 当大需求 SDLC，也不以 G1 / G2 充当跨版需求身份。
- 版本总览独立承载规格和原型；[版本工作区](../version-workspace/spec.md)继续负责侧边栏、工作树归属与版本收尾。计划、验收、项目总览、任务和会话沿既有能力，不因特性拆分另造执行器或复制公共资源。
- 首轮候选为单项目只读聚合与现有工作入口。跨版身份、版本关系、共享导航和未合入成果的关联载体由统筹会话协调；原型 JSON 只是固定读数，不是新业务协议。保留既有侧栏，不新增独立月度总览、C/B 分组或会话屏。

## 审阅与成功判据

先看[旅程](journey.html)，再操作[高保真](prototype.html)。版本中默认呈现完整模拟横轴，模拟时序与实际成果入口明确分开，长过程记录按需展开；不用先寻找示例入口。用 Orca 原生浏览器批注反复修订，最终原型要能作为落地形态依据；面向评审的说明统一以 `原型注释:` 开头，不能混入拟交付的产品文案。

成功标准是用户能从本版承诺定位真实成果、待审项和原生工作入口，分清可用范围与缺失依据，并在历史版本核对当时人工结论。可观察判据与真实运行缺口见 spec / STATUS，不用截图、源码或 CI 代替用户认可与价值效果。
