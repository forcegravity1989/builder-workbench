## 实现范围与待验边界

`version-overview-page.tsx` 按目标呈现，替代原汇总简表。`version-overview-materials.ts` 区分正式材料、工作稿、没有材料与读取失败；历史验收沿 planRef 固定计划。`version-overview/` 内分开读取 provider／版本材料、纯函数节点解析、特性卡片与横轴，AI 报告另有独立读取和刷新状态。任务复用 `openVersionTasks`，会话继续从原生侧栏进入，特性轴不新增工作会话入口。浏览不创建工作树，不读取会话正文或新增数据库。

## 按目标组织，回显人工验收

按正式计划的目标顺序保留编号、名称、负责人、任务数量及原生目标任务入口，不用 G1/G2 充当特性身份。删除“范围与验收标准”入口及对应弹窗，不单列“本版范围”展开块，也不重复“本版承诺与验收”汇总；完整范围继续从原有版本计划／验收导航查看。目标任务成员按计划中的完整引用读取；导航自动附带的版本标签不再二次排除这些成员，其他用户筛选条件仍生效。

每个目标读取对应版本验收材料中的人工结论，回显验收屏的达成／未达成，以及已记录的结论来源、时间、后续处理；未记录结论与读取失败保持区别。已有结论在版本中也正常回显，不以“已归档”作为显示条件。特性阶段、PR 合入、Issue 关闭比例或项目发布均不能替代目标人工结论。每版仍只有一次正式人工验收；设计批注、试用反馈不是额外版本验收。

目标内按显式关联选择呈现：

- 有特性主 Issue，或有执行 Issue 明确引用特性主单：分别展示每个特性的时间轴。允许同一目标有多个特性。
- 没有识别到特性：保留任务数量和原生目标任务屏入口。无须增加“小需求／bug”专项目标，也不将目标改名。
- 混合目标：展示各特性；全部任务数量与入口只保留在目标标题下，不另列其他任务数量或重复入口。
- 未标记只决定普通任务呈现，不替 Issue 写入类型；关联读取失败不是“没有特性”。计划缺目标关联的任务仍从本版原生任务入口查看，不自动补归某个目标。

总览不内嵌另一套任务列表、过滤器或任务详情。入口复用本版本／目标已有的原生任务屏，天然带正确上下文。任务总数沿实际计划引用，不把为展示而读取的外部主单补算成当前版任务。

## 特性身份与执行 Issue

已确认的设计约定：特性主 Issue 显式使用 `特性` 标签；拆出的执行 Issue 标题包含 `【特性#334】` 这样的关联。编号按同一 provider／仓库解析，完整身份保留平台、仓库和编号，跨仓同号不得合并。现有 Bug／Feature 任务类型不能自动当作特性主单标记。CodeHub 不依赖平台父子 Issue 功能；GitHub 原生父子功能也不是本方案前提。

例如主单 #334 代表版本总览特性；设计、实现可直接关联此单，也可因分工拆出带 `【特性#334】` 的执行单。当前版只有执行单时仍能定位主特性。属于同一特性不代表自动纳入同一版本，版本与目标归属继续以已确认计划的任务引用为准；下一版不复制新特性，不凭需求名称或 G 序号归并。

关系在计划制定或任务拆解时建立，总览只读呈现。已确认的主单标签和标题引用写入现有 Issue 格式 reference，计划 Skill 引用该规范进行引导；不新增计划 schema 或共享导航协议。两屏复用该身份的运行证据见 STATUS。未标记的历史不批量补写；原型显式选取样本，不作为真实标签依据。

## 横向时间轴：遵循实际工作方式

[Claude SDLC](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 是参考。两屏统一阶段名称，时间边界沿用户确认的 BW 采集口径，不套成固定审批状态机，也不要求每个阶段已有可采集的完成节点：

| 阶段 | 含义、时间边界与来源 |
| --- | --- |
| Plan | 意图收敛。从首次包含该特性的正式计划 PR 合入所在周、项目时区周一 09:00，至该计划 PR／MR `mergedAt`；周一是约定基线，不是实际开工，延期不重置。不采用纪要 `minutes.confirmedAt` |
| Design | 设计评审。从意图确认至明确关联的设计 PR／MR 经人评审合入，表示 intent、spec 与原型联合评审通过 |
| Build | 开发。从设计定稿至明确关联的实现 PR／MR 合入；没有可识别实现 PR 时才用特性主 Issue 的人工关闭时间兜底。详细设计、实施 Plan 和开发均属此阶段，实施 Plan 不要求入库 |
| Test | 验收前交付区间。从 Build 交付至首次满足交付条件的验收 PR／MR 合入；要求正式计划明确关联该特性且目标人工达成，含测试、修复、出包与等待 |
| Deploy | 实际部署。暂未采集开始／结束时间，提示“未跟踪”；虚线半天仅作默认展示占位，不计算实际部署时长，不用验收、发布记录或 Maintain 补阶段 |
| Maintain | 后续明确关联版本对同一特性的关注、修理与完善。用户确认从首次交付连续计至后续版本验收 PR 合入且目标人工达成，包含首次交付至再次纳入计划之间的等待；不从后续计划合入才开始计时 |

横轴保留同一水平结构，已知区间按实际时间比例显示，精确到时分。后续阶段先按默认长度展示白底虚线，不写成实际区间或承诺日期。默认 Plan 1 天、Design 2 天、Build 半天、Test 1 天、Deploy 半天；Maintain 暂以 1 天占位。之后再接项目总览里程碑排期，本轮不建立读取协议。Deploy 缺少时点时保留横条及“未跟踪”提示，不作为 Maintain 的前置完成门槛，也不延后 Maintain 的实际起点。Maintain 须有明确后续版本关联；没有关联时不因项目下一版存在就补出维护事实。多个后续版本可继续产生交付节点，Maintain 总历时从首次交付至最后一个可确认的后续交付连续计算，各节点保留来源，不把重叠累计区间相加，也不把第二次交付当作整个特性结束。

进行中的 Test／Maintain 仅在已知起点、明确范围及当前状态时，以读取截至时点呈现虚线区间和“已历时”；该时点不能充当完成时间。历史视图仍受本版验收截止约束，不向后续未来延长。缺开始时点、无法确认次序或读取失败时保留未知，不补零、不用文件提交时间替代。历时包含等待、出包和评审，不是人工工时或独立测得的测试耗时。测试、修订与反馈允许并行或回返。

本次 #334 采用一个特性 Issue、两个 PR：#459 承载设计，已合入；#474 承载开发，仍关联 #334。是否拆执行 Issue 取决于范围与分工，不为计时强制拆单；后续项目规范可以采用不同 PR 组织方式。每个阶段节点只展示一个明确的交付来源，不叠加多个 PR；不能取第一个／最新一个 PR 自动代表开发完成。Issue 关闭兜底不覆盖已可识别的开发交付时间，重新打开或来源冲突时保留原始事件和缺口。

阶段徽标沿相同名称呈现可确认的工作，例如“Design · 评审中”“Build · 评审中”，缺历史依据仍为未记录。PR 阶段可由 PR 正文明确的“交付阶段：设计／开发”，或主 Issue 中“设计 PR：完整链接／开发 PR：完整链接”识别；显示名称变化不要求改写既有 PR 标记。没有标记或来源冲突时保持未知，不解析会话、不按 PR 次序猜阶段。合入只表示对应 PR 范围通过，不推断整个特性或目标完成。

本屏采用用户确认的简单交付口径：实际版本的正式计划包含主单或执行单，正式验收中对应目标明确达成，且对应验收 PR／MR 已合入并有可读取的 `mergedAt`，才形成该特性的随版交付节点。目标人工结论只决定是否计入交付；交付时间统一取验收 PR 合入时分。未达成不计交付，缺结论、缺验收 PR、未合入或缺合入时间保持未知，不拿人工决定的 `recordedAt`、归档文件时间或读取时间补齐。目标原位继续保留人工决定来源、确认时间和后续处理。验收 PR 合入是当前交付约定，不是独立核实的包发布时间；不接 GitHub Releases 或另建发布系统。

同目标多特性暂沿整体目标结论，不能区分特性个别例外；这是已接受的限制，不通过任务关闭率或实现 PR 合入替补判断。第一次符合条件的版本显示“首次交付”，后续明确关联版本显示“维护交付”，始终带实际版本号，取消特性 Pre／Release 二分。临时出包不会被自动发现；只有明确登记的版本计划关联、目标人工达成及验收 PR 合入齐全时才能识别。延期且未登记交付时保持未记录，项目下一次发版不自动产生本特性的后续交付。

横轴随容器宽度调整，同刻或过密事件聚合，不按事件数量无限扩宽；极窄窗口允许局部横滚。端点显示日期、时分和时区；同刻或过密事件保留各自来源与时点。Issue 创建、PR 提交／合入可以作为过程事件回查，但阶段历时按上表口径计算，不能用 PR 创建到合入替代整段 Design 或 Build。真实开工、独立测试起止没有可靠读取依据，不生成对应事实；不解析会话，也不把周期基线、PR 创建或读取时间说成真实开工。

阶段按状态用三种中性色表达：已结束浅灰、当前深色、后续白底虚线，不再使用六种阶段颜色或图例。一个节点使用一个明确来源，点击横条直接打开对应 PR（Build 关闭兜底时打开 Issue）；尚无来源不补造跳转。悬停仅展示单行来源，例如“设计 PR #459 · 已合入”“首次交付验收 PR · 未记录”“部署时间 · 未跟踪”。不保留常驻来源按钮排、单独 Deploy 行或重复阶段详情。版本交付卡片及连接虚线保留；未完成卡片不显示实际交付日期。评审用解释及模拟来源统一标“原型注释:”。版本计划、正式验收与原生会话沿现有导航进入。

当前主原型默认展开 #334，直接采用计划／设计合入、Build 进行中的 PR 快照；也可切换 Test、Maintain 进行中及维护交付后模拟。历史 #383 默认展开模拟历程。模拟状态、时分、版本及默认长度标清“原型注释:”，模拟已合入状态不跳到实际仍为 Draft 的 PR。原型仅用于形态审阅，不证明生产已实现。生产横轴的三色、默认占位和直接来源跳转待按本稿落地，当前生产只同步删除重复目标任务入口；详见 STATUS。

反馈、新需求、bug 均进入目标关联的 Issue，不新增反馈台账，也不按“两周内／以后”分流。具体反馈来自哪个版本、候选及使用范围应能追溯；未纳入计划的反馈不能算本版承诺。原始计划／验收引文保留当时用词，不因新阶段命名修改真实历史材料。

## 可调整的读取与解析边界

来源读取、节点解析、时间轴展示分开，以支持项目规范变化：

1. **来源读取**复用已有 provider、文件、PR 与原生工作区入口，保留原始来源和修订；不新增执行器或业务数据库，不读取会话正文。
2. **节点解析**按项目实际规范识别特性关联、计划／设计／开发 PR、Issue 关闭兜底及随版交付，独立计算已知区间，缺少的 Deploy 保持未知。规则或脚本可独立调整，不能按“第一个 PR 是设计、第二个是开发”猜，也不能把两 PR 数量永久写死。
3. **只读展示**消费解析后的事件、时间、范围与来源，不在页面组件中直接解析 Issue 标题、PR 正文或会话。

GitHub 复用已有 Issue 时间线回链、明确链接和原生工作树关联，回链是候选集合，仍需识别 PR 的交付阶段。CodeHub 保留现有正文 MR 链接及工作树关联；若内部 CLI 反查仍缺实现，以独立来源函数返回未知及原因，留给内部助手补该函数，不交出整屏实现或编造无 PR 结论。Issue 关闭时间同样须有原生来源，不能用 `updatedAt` 猜测。这里不固化新的持久化协议。

结果应可追溯原始对象、修订／commit、业务发生时间、读取时间、解析规则修订与对应范围。修改规则后可重新计算，但不能覆盖历史人工验收结论；无法识别的事件保留缺口。用少量具有代表性的真实输入验证解析规则，覆盖单／多 PR、回返、跨版以及缺证据。本稿只规定边界，不固化共享 JSON 字段、调度机制或脚本框架。

### 正式承诺、未合入成果与历史

| 信息 | 读取与展示规则 |
| --- | --- |
| 正式承诺 | 沿主干已确认计划的 sourceCommit／revision 读取，不以本地草稿替代 |
| 计划草稿 | 沿当前版本绑定的计划工作区读取，保留草稿身份，不猜另一台机器的路径 |
| 未合入成果 | 从明确关联的 Issue／PR 出发，PR 文件固定 head SHA；本地草稿标宿主、工作树与修订。多个候选列出，不按名称或最新时间猜唯一成果 |
| 人工评审 | 绑定对应 PR、成果和修订；本轮约定设计 PR 经人评审合入标记设计通过，后续范围变化仍需对应记录 |
| 测试与交付 | 开工与独立测试时点暂留空；目标人工达成决定交付资格，验收 PR／MR 合入时分决定交付节点，不把设计 CI 或人工决定时间当包发布记录 |
| 历史验收 | 沿 committed planRef 和验收修订读取当时计划与人工结论；当前动态和后续发布不重写历史 |

历史回看的截止时点统一取本版验收 PR 的 `mergedAt`，以覆盖该版本自己的交付节点；缺合入时间时保持截止未知，不拿更早的人工决定时间替代。BW 薄读取沿原生执行器提供 PR 正文及合入元数据，固定并核对特性主单的仓库身份；不读取完整评审文件、已阅状态或检查。排除截止之后创建的 PR，缺创建时间仍保留待核对，不因读取失败推断没有成果。该筛选不改变正式计划或人工结论。

继续使用 `VersionGoalSchema` 的 owner／deadline／deliverable 与任务 provider／repository／number／goalId。特性身份、事件和来源在读取时派生；没有新增持久化事件 schema。节点规则以独立纯函数实现，可随项目规范调整。

固定样本：v0.8 计划来自主干 90952d9；v0.7 计划按验收 planRef.sourceCommit 固定读取。#334／#440 初稿提交只证明设计文件存在，不代表认可或开发完成；历史示例为 #383，真实阶段未重建。原型不修改快照来伪造真实“特性”标签。Git 分支不证明宿主登记或会话状态。

## AI workflow 生产力

读取已有 PR 评论中的 workflow 报告，展示六项任务读数、记录覆盖、来源与截至时间，不再使用“指标待定”四个空占位。指标名称、计数、分母、交付与返工解释沿 [workbench-start 真实任务反馈](../../../.claude/skills/workbench-start/references/workflow-feedback.md)，本特性只负责读取、归并和展示，不复制另一套公式，也不读取会话正文。PR 已合入不能推出首次人审通过，待审／未知不填成零返工。

生产范围以当前版本实际读取计划的目标 Issue 引用为边界，只读取这些 Issue 关联 PR 的报告，不全仓扫描、不靠版本标签额外纳入任务，也不把外部主单的读取补算成目标任务。小需求／bug 按一个 Issue、一次开发交付、一份 PR 报告读取；PR 合入后的新开发另开 Issue，不为同一任务跨 PR 归并统计。报告修订更新原评论。关联读取找到不唯一的报告时保留未知，不选择第一份、最新一份或合并读数。缺报告或记录覆盖不足也保留未知与来源，不能用“未读到”推断为0。特性设计／开发分 PR 的 SDLC 证据规则保持独立。

原型采用 [PR #505 的报告评论](https://github.com/forcegravity1989/builder-workbench/pull/505#issuecomment-6494691114) 的固定快照展示单任务样例，采集时点与后续远端更新分开。每项按“涉及任务数／总轮次或批次／本指标有明确结论的任务数”显示三个数，下方按同一顺序标明含义；原型与生产共用解析、归并和显示口径。开工输入每任务记 0 或 1，前两数相同；返工第一数沿 workflow 正本表示首次人审退回任务，第二数表示已完成返工轮次。第三数含明确的零值，不等于所有有报告任务数；缺报告、覆盖不足或冲突不计入。无明确结论时保持未知。样例原始记录与各指标未知任务数放在折叠来源区。Issue #469 不在这份固定 v0.8 计划内，样例明确不计本版汇总；用户自行纳入 G4，总览不代写计划。该样例不证明当前版本汇总或生产读取已通过，真实结果见 STATUS。

AI 读数首次进入独立后台读取，不阻塞版本基础内容；后续优先同范围缓存，手动刷新仅更新指标。两者独立保持加载和错误状态。使用按项目、provider、仓库、宿主来源、版本及实际材料／报告修订隔离的内存缓存，重复渲染不触发全量查询；切换来源或修订不串读数，显式刷新只刷新相应部分。不新增数据库，不固定任意 TTL。刷新失败时，同一来源范围已有成功读数继续显示其截至时间并标明错误与重试；没有旧值时显示未知，不能把其他版本缓存当作本版成功结果。GitHub 评论完整分页读取；CodeHub 严格读取拒绝未识别或可能截断的返回，尚无 owner runtime 的旧 SSH 项目明确返回未知，不在本机误执行 CLI。

AI workflow 的报告来源与未读取范围默认折叠，按需展开查看各 PR 评论、采集时间与失败范围。

## 导航与跨屏关系

沿 #455 的当前项目进入定位、完整原生任务页和工作树行。计划／验收沿 navigateVersionWorkflow，任务沿 openVersionTasks；原生工作会话与 activateVersionWorktree 保留完整项目、任务源和宿主身份。唯一匹配直接进入，多实例用现有选择器，无匹配沿原生创建入口。总览不后台建树，也不仿制另一套会话屏。

项目总览或规划工作区从版本表头进入准确版本，返回恢复来源、视口和未提交草案；不要求附带特性身份。未开始计划时仍可进入上下文而不创建计划。关联版本为一排版本号标签，悬停／聚焦看一句本版范围，点击进入对应总览定位同一特性；只有这种明确携带主 Issue 的入口才核对该特性关联。重复版本名需明确身份，不按日期推断，不把分组当 Git 分支关系。

本原型的 scene／focus 和来源弹窗只演示本屏，输入保留于页面内存，刷新清除，不作为路由或持久化协议；真实跨屏验证见 STATUS。关联样本按完整任务引用读取固定计划；当前固定计划中 #334 仅关联 v0.8，v0.7 使用 #383 演示历史特性。

### 两屏共用事实与导航

- 项目总览已开始版本按正式计划的目标回显实际，使用版本名称、cycleId 与版内 goalId 定位；不增加宏观规划行到 Issue 的绑定协议或界面。目标内通过现有特性标签与执行 Issue 标题引用识别主单。目标序号不是跨版身份；同目标多个特性不能合成单一历程，项目层提示数量，具体历程在版本总览分别呈现。
- 两屏使用同一 useVersionFacts、来源限定缓存和 featureTimeline 纯解析。键包含宿主、项目、版本、材料内容及修订、任务来源、历史截止和解析规则版本；共享在途请求与刷新通知，失败保留同范围旧值及截至时间，不串版。不回写实际到规划材料。
- 项目总览按连续日比例画只读实际，悬停保留时分；版本总览按小时比例画完整历程。原计划仍以独立规划行保留，可开关，不把没有对应关系的排期贴到某一实际目标。默认计划天数不能补实际空缺，Deploy 未跟踪。
- Maintain 从首次交付连续至后续明确关联且目标达成的验收，包含中间等待。后续版本可以超过两个；已有更晚达成交付时，较早未达成的版本不让区间永久延长。尚待交付的明确后续安排显示截至本次读取的进行中区间，历史页以验收截止时间截断。
- 项目总览只从版本表头进入准确版本；返回恢复原有规划视口和未提交草案。关联版本芯片仍可带已知主 Issue 定位。本轮不按标题、G序号或日期猜对应，不新增 C/B 命名或月度总览。
- 共享设计输入仍引用 [PR #458 的固定修订](https://github.com/forcegravity1989/builder-workbench/blob/d69058d15aad9362456dbe353b9318275fa2b9e4/docs/05-features/version-workspace/overview-design-inputs.md)，不复制正本。目标验收以现有材料为准，自动解析不得覆盖人工结论。
