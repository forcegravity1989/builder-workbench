## 三种版本生命周期

顶部情景下拉至少包含以下三种。此选择是原型评审工具；实际产品从侧栏版本上下文进入，不新增第二套产品选版器。

| 情况                     | 高保真数据                                 | 页面行为                                                                                                                                                   |
| ------------------------ | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 版本计划未制定           | v0.9 是未创建版本的布局示例，已标原型注释  | 保留 BW 壳和计划 / 任务 / 验收入口；主区明确计划未制定，提供“开始制定版本计划”，关联既有计划短卡、原生会话及计划板旅程；不伪造目标、任务、负责人或交付比例 |
| 版本计划制定完（版本中） | v0.8 正式计划与 GitHub Issue / PR 固定快照 | 呈现完整 G1–G4 承诺和责任人；分别展开大需求的整体目标、本版范围、成果与待审事项；G4 展示真实任务，未读会话和缺失试用证据保持未知                           |
| 版本交付后               | v0.7 已归档验收及其 planRef 指定的计划     | 显示当时承诺、逐目标人工结论、候选包 / 报告 / 发布与归档；后续补丁和下一版另列，不能用后来状态覆盖历史。已归档不等于所有目标达成                           |

三种情景共用“本版承诺与验收 → 大需求与本版交付 → 小需求 / bug → AI workflow 生产力 → 本版记录”。未计划在原位置显示空态和制定计划入口，删除空态中的旅程讲解和“从上一版继续”导览。版本中不生成独立文字成果摘要；真实状态与成果直接显示在所属对象上。交付后人工结论回填顶部每项目标，仍保留大需求与小任务。读取成功但未开始计划与读取失败必须区分：后者为状态未知，不能呈零任务或计划未制定。

版本生命周期与大需求的 SDLC 含义不同。需求可以跨版，也可以回到设计修改；不将计划 / 验收 workflow.stage 作为需求阶段，不因切换情景生成状态或重复人工验收。

## 信息层级与真实数据

基础信息保留版本、目标、负责人、范围、确认时间、交付时间、任务、计划 / 验收及纪要、归档、发布入口。缺失截止时间保持“计划未记录”，不从按周反馈推算日期。首屏直接呈现承诺及其人工验收，完整 G1–G4 可达；两个总览是 G2 的需求，不代替整个版本。产品主区不放模拟的自然语言周报摘要，所有解释性原型说明收在注释或右上来源 / 参考弹窗。

### 需求阶段、成果与评审

参考 [Claude AI-native SDLC 原文](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)的六阶段，并遵循本次用户明确的 BW 口径。它是需求工作视图，不替代原则 02 六环交付链，也不是新增门禁状态机。

| 阶段     | 主要成果                            | 当前工作与认可                                                                 |
| -------- | ----------------------------------- | ------------------------------------------------------------------------------ |
| 意图规划 | intent、关联 Issue、价值与范围      | intent 可单独评审；文件存在不等于已认可                                        |
| 设计     | spec、原型设计、批注意见            | spec 与原型各有入口和认可，允许反复修改                                        |
| 开发     | 详细实施 Plan、代码、PR             | Plan 属于开发，不与 intent / spec / 原型并列成产品评审门；大风险按已有原则处理 |
| 测试     | 检查结果、测试 / 真机验证报告和截图 | 对应具体修订；设计原型 CI 不证明生产实现                                       |
| 上线     | 包 / 部署、版本、提交、使用范围     | PR 合入与可用范围分开核对                                                      |
| 反馈维护 | 本版目标关联的 Issue 及相应修订     | 反馈、新需求和 bug 使用相同任务来源与计划关联                                  |

阶段表示当前在做什么，成果表示形成了什么，人认可表示哪一修订已确认。原型当前 #334 / #440 处于设计评审工作，并不声称 intent / spec 已完成确认；缺历史阶段则未知，不从目标达成推导整个需求完成。

MVP 的版本、包和使用范围留在发布成果中。某需求 v0.7 已提供 MVP、v0.8 继续做时，按本版计划拆出目标与承担，反馈转为该目标下的 Issue；大需求只聚合目标关联任务与成果。移除独立 MVP 反馈板块，不设置“两周内在大需求跟踪、之后才去小需求 / bug”的分流，也不创建平行反馈清单。是否纳入某版仍由已有计划确认；未纳入的 Issue 不伪装为本版承诺。

### 小任务与项目 AI workflow

任务表保留任务、目标、Issue 原生状态、AI workflow 使用依据、会话与 PR 入口。取消“执行中 / 待处理 / 已有结果”这套混合过滤：它把执行状态、处理状态和交付结果混为一谈。长标题限两行并可打开全文，窄内容区改成每任务两行信息，不强制 600px 横向表格。样本中的 13 项属于 G4；落地应按明确任务类型与关联汇总各目标的小需求 / bug，不用 G4 序号定义任务类型，不把所有 Feature 标签自动当大需求。

AI workflow 列回答是否有本次实际使用项目流程的证据、名称 / 修订及会话来源；允许“已发现依据、待核对、证据不足”，不以项目有 Skill 或点击 BW 开工判定已使用，更不代表流程执行质量。本稿尚未解析会话，显示待核对。

详情“继续处理此任务”携带完整 provider / repository / number、本版与目标，沿既有任务开工、工作区选择和原生会话，不猜测分支或自动建树。Issue 关闭是任务原生处理事实，不推导版本达成或 AI 质量。PR 线索当前来自最近 12 条交叉引用（排除计划归档），只是有界提及关系，不自动归因。

### AI workflow 生产力（独立视图，统计口径草案）

在任务表下方单列项目 AI workflow 的生产力。BW 的示例为 workbench-start；其他项目显示自身流程，比较需带实际使用修订，不统一强加 BW Skill。先区分四类人参与：初始信息（文字、截图、附件、约束）、需求澄清（askuser 与回答）、原型评审（批注与修订）、真机验证（报告 / 截图与复验），并保留其他原因和不适用情况。

建议的统计单位是同一 Issue 的一次处理过程，可能跨多个会话。流程使用覆盖需列已核对分母与未核对数；首次交付可合入率需完整交付的第一次人工评审结论及质量门禁；追加介入按原因与等待区分；返工按修订轮次区分需求变化、实现缺陷、验证遗漏。初始输入是上下文，必要的首次澄清 / 评审 / 验证不直接算返工；一批多条批注不机械计成多个返工轮次。未观察不填 0，未判定不计入成功分子。Issue 关闭数、PR 合入数和 AI 自述都不能替代上述证据。对比应控制任务类型和必需步骤，减少介入不能以省略质量门禁为代价。

可复用链路已做源码核对：issue-start-action / scoped-task-workspace 与原生创建器记录任务归属，worktree meta / version binding 保留宿主与版本，agent-session-record / tab-types 关联会话，linkedPR 与 get-pr-for-branch 关联 PR。workflow: issue 只是树用途。原生 issueCommand、默认命令、实际提交到会话和充分执行是不同事实。

会话首条输入、原生 transcript（工具、结果、图片引用）、结构化 journal（question / approval / resolution）和浏览器批注可作为未来脚本的事件候选；不另建执行器或会话存储。展示 transcript 会过滤部分 Skill 注入，不能因没显示就判未使用；浏览器批注持久化丢弃临时截图，不能因此判定已真机验证。任务/修订归属、必要性、返工原因、真实设备与验证结论仍需规则和人工核对。当前仅展示拟落地视图和口径，未实现解析、统计接口或持久化协议。

### 正式承诺与未合入成果的可见方案

以下是待主会话协调的读取方案，不是新增持久化协议。当前 `version-overview-materials.ts` 经版本目录固定 `sourceCommit/revision`，通过 `nativeVersionHistoryPort` 读取主干已提交计划/验收，再按 `archivePr` 薄读归档状态；没有 PR 分支文件、阶段成果或发布结果装载。`VersionGoalSchema` 已有 owner/deadline/deliverable，任务引用有 provider/repository/number/goalId，尚不能直接表达跨版需求、成果修订及其评审关系。生产页仍为表格汇总。

| 信息             | 建议来源与规则                                                                                                       | 失败与冲突                                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 正式承诺         | 沿已确认且已合入的计划修订，保留 commit、revision、cycleId；只读投影                                                 | 没有正式计划显示承诺尚未确认；草稿入口可见但不补造承诺                                                      |
| 计划修改草稿     | 沿本版绑定计划树已有材料端口读取，与固定承诺并列说明差异                                                             | 没有权限/宿主不可达如实提示；不回退猜另一台机器的路径                                                       |
| 未合入成果       | 从明确关联的任务/PR 和原生已登记工作树出发。PR 文件固定 head SHA；本地草稿标宿主/工作树/文件及读取修订，保留脏稿身份 | 多 PR、多宿主或多个候选修订明确列出供选择；不按名称、最新时间或 G2 猜唯一成果。尚未建立明确关联时显示未记录 |
| 评审结论         | 绑定具体成果和修订的人工意见/认可，PR Review 与规格认可分开                                                          | head 更新后旧认可不能自动覆盖新修订；会话结束不构成认可                                                     |
| 测试、试用、上线 | 实际报告、候选提交/包、访问入口、用户范围和运行环境分别核对                                                          | CI 通过不等于可用；没有入口/环境证据保持未知；不自动创建公开部署                                            |
| 日常任务         | 沿任务源原生 Issue/PR 读取；会话与工作树沿已登记绑定定位                                                             | 关联缺失与远端读取失败分开；不把“无匹配会话”当已完成                                                        |
| 历史验收         | 沿现有 committed planRef 与验收材料修订读当时承诺、人工结论和当时证据                                                | 历史读回失败不以当前材料顶替；当前 Issue/PR 动态另列，不覆盖历史                                            |

每条最新成果应能核对“来源对象、文件/链接、修订或 head、读取时间、是否未提交、是否过期/读取失败”。只读聚合不另存完成状态；具体发现/关联载体、刷新触发与缓存策略在共享对象决定后再定。后续需先验证现有原生 PR/文件读取、provider 和宿主路由是否足够；仅当确须改变核心/协议/路由才提出技术方案，不先另造通道。

### 现有导航与工作会话

沿 #455 的项目进入定位、完整原生任务页和工作树行。项目总览链接由 #440 承接；进入版本总览不激活或恢复工作树。计划/验收走 `navigateVersionWorkflow`，任务走 `openVersionTasks`；目标筛选仍限本版目标，不改变完整任务源。成果评审打开文件/PR 对应的原生预览与评审面；继续工作沿现有任务开工和 `activateVersionWorktree`，保留项目、任务来源和宿主身份。唯一匹配直接打开，多实例使用已有工作区选择器；无匹配使用原生创建器，不后台建树。不能将两屏页面参数或临时演示对象直接当持久化契约。

### 来源定位、返回与关联版本

项目总览负责需求取舍与跨版安排，版本总览负责本版范围、执行、成果与人工验收。以项目真实版本名称交流，不要求 C/B 命名或先讨论月份。保留既有 v0.7/v0.8 侧栏和“项目 → 版本 → 总览”面包屑，不补造周期归属，不新增月度总览页。重复的显示名称必须靠明确的版本身份区分，名称、当前日期及 Git 分支层级都不能替代版本关系。

从项目总览进入时，携带明确的项目、版本、需求和材料来源，自动展开并定位该需求；顶部保留当前版本和返回实际来源的入口。返回恢复原版本 / 规划视图、需求、筛选与视口；若原来处于规划工作区，返回同一未提交草案，不能以正式快照覆盖。尚无计划时仍可进入版本上下文，来源需求作为待规划上下文呈现，不创建计划或补造承诺。已有计划但未关联该需求时明确提示，不按目标序号或同名标题猜关联。

需求卡片展开后提供“关联版本”折叠区：版本实际名称、各版承担范围、目标和固定材料依据；当前查看版本可辨，其他版本可进入并定位同一需求。这里只列核对过的显式关联，不声称完整特性注册表。样本通过完整 GitHub 仓库 / Issue 引用匹配固定计划：#334 同时关联 v0.7、v0.8；#440 只展示已读取的 v0.8。v0.7 未单列 #334 增量时展示关联目标范围并说明缺口，不能沿用旧周报设想补写承诺，也不从目标验收推导该需求整体完成。

原型顶部“原型注释: 来源导航”只用上下文弹窗演示进入和返回，不画 #440 的项目总览或规划屏。来源页面、目标版本、需求和草案输入仅在本页内存保留，刷新清除；返回按钮回到同一示例上下文。真实 #440 视口 / 草案恢复尚未联调，本地 `scene` / `focus` 仅供预览定位，不作为共享路由参数协议。产品字段、跨屏载体及返回恢复由双方共同协调。读取失败仍不能当未计划，但本轮不增加第四种异常演示情景；原型没有会话屏，也不新增会话承接区。

## 验收点与共同旅程

共同旅程为选择需求与目标版本 → 先行版本 MVP → 部分用户试用 → 后续版本修理 → 后续 Issue 持续改善；三个版本生命周期为进入和回看的外层情景。项目层取舍由 #440 承接，计划、验收与工作会话复用现有旅程。月度、周只描述节奏；用户以具体版本讨论和导航，每版仅一次正式人工验收。

| 判据                       | 浏览器原型检查                                                           | 后续产品验证                                            |
| -------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------- |

### 带可见方案交主会话的选择

1. **跨版身份**：建议用现有特性文档身份为大需求锚点，完整 Issue 引用作为任务关联；原型暂以 #334/#440 区分。版本总览已由用户明确独立为特性；跨版任务关联及其他特性的身份由主会话协调。G1/G2 只是本版目标序号，不能作跨版需求身份。
2. **版本关系**：同一需求分别说明每版承担的增量和后续候选；不自动创建版本，不把未确认 MVP 范围写进归档计划。名称按项目约定，不强制 C/B；v0.9 未计划空态不决定周期归属或编号，也不创建版本。
3. **导航与公共资源**：#440 进入版本后定位需求、返回恢复来源和草案的原型方向已确认；真实共享身份、材料关联与精确导航载体仍由主会话协调。双方复用现有设计系统及冻结 vendor，本轮仅修改本屏局部导航，不提取或改动公共壳源码。
4. **成果可见性**：本稿推荐在相同页面结构里按对象呈现正式承诺与未合入成果，详情揭示来源与修订；待审入口定位具体成果。需要评审信息密度、默认展开范围与关联缺失时的补充入口，不能在两窗口分别发明状态文件。
5. **MVP 边界**：本稿推荐先做单项目只读聚合与现有工作入口；跨宿主写入、全量阶段自动推断、远程批注系统均未纳入。具体候选包、使用范围及统计计算规则仍待人确认，当前原型不编造记录或实施采集。反馈已经明确统一走目标下的 Issue。
