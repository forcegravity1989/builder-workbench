# 版本总览规格

> 给设计、实现、内部评审与验收者读取。本文维护版本总览的行为、来源边界、验收与旅程；价值见 [intent](intent.md)，认可和验证结论见 [STATUS](STATUS.md)。行为变化时更新对应主题，不追加施工流水。导航、树归属与收尾由 [版本工作区](../version-workspace/spec.md) 维护。

## 页面与生命周期

页面按“版本基础信息 → 版本目标 → AI workflow 生产力”组织，保留 BW 原有侧栏及计划、任务、验收和原生会话入口。

| 场景       | 内容与来源                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------- |
| 计划未制定 | 读取成功且没有有效计划时，显示空态和原有制定计划入口；仅初始化、没有内容的绑定草稿也属于未开始 |
| 版本中     | 按实际计划逐目标展示负责人、任务、特性与人工验收；没有结论显示未记录验收                       |
| 交付后     | 沿验收 `planRef` 固定当时计划，保持同一目标布局，回显当时人工结论                              |

读取失败显示未知及错误，不能当作没有计划或零任务。版本名称沿各项目约定，不按当前日期推导归属。

页头显示负责人、计划 PR 合入与验收 PR 合入的时分，以及对应 PR 链接。时区在时间悬停提示中说明。版本刷新位于标题右侧，AI 指标在其面板内独立刷新。完整计划、纪要和验收从原有导航进入。

## 目标与人工验收

目标按正式计划顺序显示编号、名称、负责人、任务数量及原生目标任务入口。数量和入口只放在目标标题下。完整范围与验收标准在原有计划／验收屏查看，总览不另设范围弹窗、任务表或重复汇总。

每个目标读取相应版本验收材料中的人工结论，原位显示达成／未达成及已记录的来源、确认时间和后续处理。已有结论在版本中也正常回显，不以归档状态为前提。特性阶段、PR 合入、Issue 关闭比例和项目发布均不能代替目标人工结论。每版只有一次正式人工验收，设计批注与试用反馈不算额外版本验收。

目标任务成员以计划中的完整引用为准。导航附带的版本标签不二次排除已纳入目标的成员，其他用户筛选条件仍生效；任务入口进入本版本／目标原生任务屏。为展示而读取的外部特性主单不补算为版内任务。

目标内存在特性主 Issue 或明确引用它的执行 Issue 时，分别显示各特性时间轴。没有识别到特性时保留目标任务数量与入口；一个目标可以同时包含多个特性和普通任务。关联读取失败与没有特性不同。计划缺目标关联的任务从本版原生任务入口查看，不自动补归目标。

## 特性身份与关联版本

特性主 Issue 显式使用 `特性` 标签；执行 Issue 标题用 `【特性#334】` 这样的引用说明归属。编号按同一 provider／仓库解析，完整身份包含平台、仓库和编号；跨仓同号不合并。Bug／Feature 任务类型不自动视作特性主单标记，不依赖平台父子 Issue 能力。

关系在版本计划或拆解任务时明确建立，总览只读呈现。当前版只有执行单时也能定位主特性；跨版沿同一主单，不按名称、G 序号或日期猜配。是否拆执行 Issue 由范围与分工决定，不为统计强制拆单。

特性卡片只显示 Issue 标题、负责人、阶段、关联版本与横轴。关联版本以一排版本号标签呈现，悬停／聚焦显示一句关联目标范围，点击进入对应版本并定位同一特性。计划没有独立特性增量时，不自动拆分同目标多个特性的范围，也不补写历史承诺。

## 六阶段与时间依据

[Claude SDLC](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)提供阶段分析参考。实际边界采用 BW 的明确来源，不按 PR 序号猜测，也不把阶段做成强制审批状态机。

| 阶段     | 时间边界与来源                                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Plan     | 从首次包含特性的正式计划 PR 合入所在周、北京时间周一 09:00，至该计划 PR／MR 的 `mergedAt`。周一是约定统计基线，不是实际开工，延期不重置 |
| Design   | 从意图确认至明确关联的设计 PR／MR 合入，表示 intent、spec 与原型联合评审通过                                                            |
| Build    | 从设计定稿至明确关联的实现 PR／MR 合入；没有可识别实现 PR 时才用特性主 Issue 人工关闭时间兜底。详细设计、实施 Plan 与开发均属于此阶段   |
| Test     | 从 Build 交付至首次满足交付条件的验收 PR／MR 合入，包含测试、修复、出包和等待                                                           |
| Deploy   | 实际部署时点未采集，显示“未跟踪”；默认展示长度不产生部署事实                                                                            |
| Maintain | 从首次交付连续计至后续明确关联版本的验收 PR 合入且目标人工达成，包含再次纳入计划之前的等待                                              |

PR 阶段读取正文“交付阶段：设计／开发”，或主 Issue 中“设计 PR：完整链接／开发 PR：完整链接”等明确标记。每个阶段节点只使用一个可确认来源；多个候选、缺少标记或来源冲突时保持未知，不按第一个、第二个或最新 PR 选取。可识别的实现 PR 优先于 Issue 关闭兜底；关闭时间不能用 `updatedAt` 替代。

实际版本正式计划包含特性主单或执行单，正式验收中对应目标明确达成，且验收 PR／MR 已合入并有有效 `mergedAt`，才形成随版交付节点。目标人工结论决定是否计入，验收 PR 合入时间决定节点时分。未达成不计交付，缺结论或合入依据保持未知，不拿人工确认、文件提交、包发布时间或读取时间补齐。

第一次符合条件的版本显示“首次交付”，后续明确关联版本显示“维护交付”，均保留实际版本号。同目标多个特性沿整体目标结论，不能区分个别例外。临时版本同样需要计划关联、目标达成和验收 PR 合入；未登记出包不能自动发现，其他版本发布不自动产生本特性交付。

Maintain 的起点不受 Deploy 占位影响。多个后续版本可产生维护交付节点，总历时从首次交付至最后可确认的后续交付连续计算，不重复相加重叠区间。明确后续安排尚在进行时，可计算至读取截至时点；已有更晚交付时，较早未达成版本不让区间永久延长。没有后续关联不能补造维护事实，第二次交付也不代表整个特性完成。

## 横轴呈现与交互

六阶段保持一个水平轴。已结束区间为浅灰，当前区间为深色，后续为白底虚线。已知区间按实际历时比例显示，端点精确到时分；当前区间显示已历时和截至时点，该时点不是阶段完成时间。读取失败、次序无法确认或缺开始时点时，区间不显示实际耗时。

没有实际区间的阶段按下表保留展示宽度：

| 阶段     | 默认展示长度 |
| -------- | ------------ |
| Plan     | 24 小时      |
| Design   | 48 小时      |
| Build    | 12 小时      |
| Test     | 24 小时      |
| Deploy   | 12 小时      |
| Maintain | 24 小时      |

未来阶段和未跟踪的 Deploy 优先读取正式里程碑中唯一对应特性的阶段长度；以版本名称、cycleId、明确 goalId 和唯一特性 Issue 核对关系，不能按目标序号或名称猜配。规划缺失、关系不明确或首次读取失败时使用上表默认长度；刷新失败保留同来源已有的有效规划读数，不读取未提交草案。规划与默认长度仅是显示占位，不写入计划，不生成实际时点、承诺日期或采集事实。Deploy 显示未跟踪，不要求它先结束才呈现 Maintain。真实区间和占位在同一横轴上明确区分，窄窗口局部横滚。阶段名称直接写在横条内，不另设颜色图例。

点击横条打开对应的单个 PR／MR；Build 使用关闭兜底时打开特性 Issue。悬停仅显示一行来源，如“设计 PR #459 · 已合入”“首次交付验收 PR · 未记录”“部署时间 · 未跟踪”。无来源不补造跳转。时间轴不另列来源按钮排、Deploy 行、工作会话按钮或重复过程详情。

版本验收及交付显示为卡片及连接横轴的虚线。已有验收 PR 但目标未达成、结论或交付顺序未确认时，保留该版本结论与来源，不计为 Test 完成；不将未交付误写成没有验收 PR。已发生交付显示实际版本号与时分，未完成卡片没有实际交付日期。历时包含等待，不代表人工工时或独立测量的测试耗时。测试、修订与反馈可以并行或回返；阶段徽标只呈现有依据的当前工作。

## 来源、历史与缓存

`version-overview-page.tsx` 负责按目标呈现，`version-overview/` 分离 provider／材料读取、纯函数解析、缓存和展示。材料读取区分正式版本、绑定工作稿、没有材料与读取失败。浏览不创建工作树、不读会话正文、不写业务材料，也不新增数据库。

| 信息       | 来源规则                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------- |
| 正式承诺   | 读取已确认计划的 sourceCommit／revision，不以本地草稿替代                                |
| 计划草稿   | 读取当前版本绑定的计划工作区，保留草稿身份及宿主来源                                     |
| 未合入成果 | 从明确关联 Issue／PR 读取，保留对象、head 修订、状态和合入时间；候选不唯一不自动判断阶段 |
| 人工评审   | 绑定对应成果与修订，设计阶段使用明确设计 PR 的合入依据                                   |
| 历史验收   | 沿 committed planRef 和验收修订读取当时计划与人工结论，当前动态不重写历史                |

历史回看以本版验收 PR 的 `mergedAt` 为截止，覆盖本版自身交付节点。缺合入时间时截止未知，不用更早的人工决定时间替代。排除截止之后创建的 PR；缺创建时间保留待核对，读取失败不能推断没有成果。

GitHub 使用已有 Issue 回链、显式链接与原生工作树关联；回链只提供候选，须由 PR 正文的明确“关联”行核对同仓 Issue 身份，再识别交付阶段；普通正文提及不产生交付关系。CodeHub 使用 Issue 详情原生关联 MR、正文 MR 链接及原生工作树关联；原生关联须核对同仓链接与编号，关联列表缺失或未完整返回时保持未知，不能当作没有 MR。原生 `/merge_requests/<编号>` 与 `/-/merge_requests/<编号>` 链接按同一 MR 身份识别，阶段标记也沿同一规则匹配，不混用其他仓库或编号。特性主 Issue 仅在原生状态关闭且 `closedAt` 有效时提供 Build 关闭时间兜底，重开后不沿用旧关闭时间。结果保留原始对象、业务时间、读取时间、修订、规则版本与对应范围，规则调整可重新计算，但不能覆盖人工验收。

两屏通过 `useVersionFacts` 共用材料读取、来源限定缓存和 `featureTimeline` 事实解析。缓存区分宿主、项目、版本、材料内容与修订、任务来源、历史截止和解析规则版本；同源请求去重，失败保留同范围已成功读数及截至时间。项目里程碑在原泳道呈现实际阶段，版本总览保留详细来源。实际事实不回写规划数据，规划与默认展示长度不参与事实计算。正式里程碑读取另按相同宿主、项目和工作树共享快照；刷新传播至订阅方。

## AI workflow 生产力

只读取当前版本计划目标内 Issue 所关联 PR 的六项 workflow 报告评论。指标名称、计数和返工定义沿 [workbench-start 真实任务反馈](../../../.claude/skills/workbench-start/references/workflow-feedback.md)，本屏负责读取、汇总和展示，不另建公式，也不读取会话正文。

小需求／bug 按一个 Issue、一次开发交付、一份 PR 报告统计。合入后的新开发另开 Issue；报告修订更新原评论。报告不唯一、缺报告、缺结论或记录覆盖不足时保留未知，不选最新报告或跨 PR 归并。特性设计／开发分 PR 的 SDLC 证据与小任务报告统计分别处理。

每项主读数为“人工介入任务数 / 本指标有明确结论的任务总数”。分母包括明确为零的任务，不等于所有有报告任务数；缺报告、覆盖不足或冲突的任务不计入分母。返工分子沿既有口径表示首次人审退回任务。没有明确结论时显示未知，不补零。

累计轮次或批次放在指标右上角，仅累计分母内任务。开工额外输入按任务记 0 或 1，不重复显示次数。AskUser、高保真前审及返工显示轮次，验证指导和中途纠偏显示批次。返工右上角表示已完成返工轮次；首次人审通过后再次退回，分子仍为零，完成的返工轮次照计。PR 合入与待审都不能推出零返工。

首次进入后台读取 AI 报告，不阻塞版本基础内容；之后使用同范围缓存和面板内手动刷新。缓存按项目、provider、仓库、宿主来源、版本及材料／报告修订隔离；重复渲染不全量查询，不使用其他版本数据。失败保留同范围成功读数和原截至时间，显示错误；没有旧值时保持未知。

报告来源与未读取范围默认折叠，按需展开查看 PR 评论、采集时间、各指标明确结论数量与未知范围。GitHub 评论完整分页读取；CodeHub 按 CLI 的 offset 完整分页读取并展开 MR 讨论中的评论，JSON `null` 空页正常结束，重复页、字段不完整、分页失败或超过读取上限均返回未知，不使用部分评论计算。只有真实完成统计且确认没有样本时才显示无样本，读取失败不是零任务。

## 导航与边界

计划／验收沿 `navigateVersionWorkflow`，目标任务沿 `openVersionTasks`；原生会话沿现有项目、任务源和宿主身份进入。总览不后台建树或仿制会话屏。

项目总览或规划工作区从版本表头进入准确版本，返回保留来源视口和未提交草案；未开始计划也能进入版本上下文而不创建计划。明确携带特性主 Issue 的关联版本入口定位对应卡片。重复版本名依完整身份区分，不把展示分组当 Git 分支关系。

计划和任务仍使用现有版本、目标及任务引用。特性身份、阶段和来源读取时派生，不增加持久化事件协议。

## 原型与验收判据

入口：[高保真](prototype.html?rev=530-draft-1)、[审阅旅程](journey.html)。可编辑源码在 `prototype/overview-*.jsx`、`overview-data.js`、`overview.css`；`overview.js` 由 `build-overview.cjs` 生成。共用设计系统、version-workspace 壳样式与原型资源；固定样本 `bw-snapshot.json` 不是业务协议。

原型默认采用 #334 计划、设计和开发 PR 合入快照，显示 Test 进行中；读取时间随快照标明。规划长度、Maintain 与历史完整历程使用明确标注的模拟；模拟状态不链接到实际状态不同的 PR。workflow 使用 [PR #505 报告](https://github.com/forcegravity1989/builder-workbench/pull/505#issuecomment-6494691114) 的单任务快照，计划外样例不计入本版汇总。页面内编辑只用于评审，刷新还原；不写正式材料。原型说明统一以 `原型注释:` 开头，正式提示不加该前缀。

| 判据            | 可观察行为                                                                         |
| --------------- | ---------------------------------------------------------------------------------- |
| VO1 目标承诺    | 目标名称、负责人、唯一任务入口与人工结论保留，完整承诺仍能从原计划查看             |
| VO2 特性身份    | 标签和明确执行单引用识别主特性；同目标多个特性分别展示，跨版身份连续               |
| VO3 来源入口    | 横条直达单个明确来源，悬停显示简短状态；无来源不补跳转，Deploy 显示未跟踪          |
| VO4 时间与交付  | 已知历时按小时比例，默认长度无实际日期；首次和维护交付沿目标达成与验收 PR 合入推导 |
| VO5 普通任务    | 数量准确，原生目标任务入口自带上下文，无重复任务表或重复入口                       |
| VO6 人工验收    | 按版本与目标回显材料中的人工结论，特性状态不覆盖验收                               |
| VO7 缺证据      | 读取失败、没有材料、无样本、明确零和未知分别呈现                                   |
| VO8 原型边界    | 固定快照、模拟和临时编辑标清，不改正式计划与历史材料                               |
| VO9 生命周期    | 未计划、版本中与交付后保持同一目标骨架，历史按固定材料和截止读取                   |
| VO10 布局与交互 | 保留原有壳，窄窗口只在横轴局部滚动，键盘可聚焦来源入口                             |
| VO11 生产力     | 仅汇总目标内单份 PR 报告；主读数、独立次数、逐指标覆盖、缓存和错误状态一致         |
| VO12 来源返回   | 精确版本与明确特性定位，返回恢复原有来源上下文                                     |

静态原型、纯函数检查和真实 Electron 旅程分别提供对应证据。运行结论按匹配源码、实际 provider／文件读回、重载与独立进程重启区分，具体记录见 [STATUS](STATUS.md) 所链接的 PR 验证报告。人工验收、Issue 关闭、PR 合入和发布遵循人的授权。
