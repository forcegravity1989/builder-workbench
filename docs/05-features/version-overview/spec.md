## 实现范围与待验边界

`version-overview-page.tsx` 按目标呈现，替代原汇总简表。`version-overview-materials.ts` 区分正式材料、工作稿、没有材料与读取失败；历史验收沿 planRef 固定计划。`version-overview/` 内分开读取 provider／版本材料、纯函数节点解析、特性卡片与横轴。任务复用 `openVersionTasks`，会话复用 `openIssueWorkspaceOrStart`。浏览不创建工作树，不解析会话或新增数据库。

顶部提供三种场景，共用“版本基础信息 → 版本目标 → AI workflow 生产力 → 本版记录”的结构：

| 场景 | 内容与来源 |

读取成功但没有计划与读取失败分开，失败不能显示成未开始或零任务。本轮不新增第四个异常演示情景。版本名称遵循各项目约定，以版本讨论交付；月／周只是节奏，不强制 C/B 命名、侧栏分组或独立月度总览。

## 按目标组织，回显人工验收

按正式计划的目标顺序保留编号、名称、负责人、本版范围和验收标准，不用 G1/G2 充当特性身份。不单列“本版范围”展开块，范围与验收标准通过现有入口查看；任务数量与原生目标任务屏入口始终可达。不再单独重复“本版承诺与验收”汇总。

每个目标读取对应版本验收材料中的人工结论，回显验收屏的达成／未达成，以及已记录的结论来源、时间、后续处理；未记录结论与读取失败保持区别。已有结论在版本中也正常回显，不以“已归档”作为显示条件。特性阶段、PR 合入、Issue 关闭比例、Pre／Release 发布均不能替代目标人工结论。每版仍只有一次正式人工验收；设计批注、试用反馈不是额外版本验收。

目标内按显式关联选择呈现：

- 有特性主 Issue，或有执行 Issue 明确引用特性主单：分别展示每个特性的时间轴。允许同一目标有多个特性。
- 没有识别到特性：保留任务数量和原生目标任务屏入口。无须增加“小需求／bug”专项目标，也不将目标改名。
- 混合目标：展示各特性，并保留其他关联任务数量及本目标全部任务入口；不把特性所属的执行 Issue 重复列入其他任务。
- 未标记只决定普通任务呈现，不替 Issue 写入类型；关联读取失败不是“没有特性”。计划缺目标关联的任务仍从本版原生任务入口查看，不自动补归某个目标。

总览不内嵌另一套任务列表、过滤器或任务详情。入口复用本版本／目标已有的原生任务屏，天然带正确上下文。任务总数沿实际计划引用，不把为展示而读取的外部主单补算成当前版任务。

## 特性身份与执行 Issue

已确认的设计约定：特性主 Issue 显式使用 `特性` 标签；拆出的执行 Issue 标题包含 `【特性#334】` 这样的关联。编号按同一 provider／仓库解析，完整身份保留平台、仓库和编号，跨仓同号不得合并。现有 Bug／Feature 任务类型不能自动当作特性主单标记。CodeHub 不依赖平台父子 Issue 功能；GitHub 原生父子功能也不是本方案前提。

例如主单 #334 代表版本总览特性；设计、实现可直接关联此单，也可因分工拆出带 `【特性#334】` 的执行单。当前版只有执行单时仍能定位主特性。属于同一特性不代表自动纳入同一版本，版本与目标归属继续以已确认计划的任务引用为准；下一版不复制新特性，不凭需求名称或 G 序号归并。

关系在计划制定或任务拆解时建立，总览只读呈现。已确认的主单标签和标题引用写入现有 Issue 格式 reference，计划 Skill 引用该规范进行引导；不新增计划 schema 或共享导航协议。#440 复用此身份仍需跨屏联调。未标记的历史不批量补写；原型显式选取样本，不作为真实标签依据。

## 横向时间轴：遵循实际工作方式

[Claude SDLC](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 是参考，取共同评审、持续测试与回返的思路，不将其六阶段套成固定状态机。当前工作方式为：

| 过程 | 本轮的结束依据 |
| --- | --- |
| 已有 Issue → 准备 intent、spec 与原型 → 联合评审及修订 | 设计 PR 经人评审合入，标记对应设计范围通过 |
| 会话中的详细设计、Plan → 开发、自测与评审 | 实现 PR 合入，标记相应实现范围结束；Plan 通常不入仓 |
| 实现已合入 → 候选验证、出包及随版等待 | 按版本计划关联及正式验收推导本版交付；首个交付版本称 Pre |
| Pre 试用 → 反馈 Issue、修理与回归 | 同一特性在后续实际版本中继续规划并验收交付，称 Release；继续规划时仍保留后续版本 |

本次 #334 采用一个特性 Issue、两个 PR：#459 为设计 PR，人确认合入后同分支新开开发 PR，仍关联 #334。是否拆执行 Issue 取决于范围与分工，不为计时强制拆单；后续项目规范可以采用不同 PR 组织方式。多实现 PR 时分别保留合入事件，只有已明确本版范围及对应 PR 集合，才能判断该范围的开发结束；不能取第一个／最新一个 PR 自动代表全部完成。

阶段徽标分别呈现当前开放的设计／开发 PR 和已有版本交付。PR 阶段可由 PR 正文明确的“交付阶段：设计／开发”，或主 Issue 中“设计 PR：完整链接／开发 PR：完整链接”识别；没有标记或来源冲突时保持未知，不解析会话、不按 PR 次序猜阶段。合入只表示对应 PR 范围通过，不推断整个特性或目标完成。

本屏当前采用用户确认的简单交付口径：实际版本计划包含主单或执行单，正式验收中对应目标明确达成，即推导该特性随版交付。未达成不计交付；缺结论或待确认保持未知。节点时间取人工验收确认时点，提示其来源，不冒充另行核实的包发布时间；不接 GitHub Releases 或另建发布系统。Pre／Release 是首次、后续交付的称呼，节点始终带具体版本号，不要求项目按 C/B 或特定格式命名。

横向按真实时间差呈现过程宽度，端点显示日期、时分和所在时区。同刻或过密事件合为可展开节点，逐条保留真实时点。Issue 创建、PR 提交／合入与版本交付分别取据。PR 提交到合入称“PR 评审窗口”，包含等待，不等于完整阶段耗时。设计／开发实际开工、测试起止没有可靠读取依据，`workActivityTimes` 返回空值，用户已允许后续单独补齐；不解析会话，也不拿创建 PR 或读取时间代替开工。

设计 PR、实现 PR 合入及项目版本发布在同一轴上可点击；长过程记录默认收起。轴上的成果入口只保留对应 PR 与工作会话，进行中、历史版一致；intent／spec／原型等从 PR 文件或原生会话目录查看。未记录开发 PR 时不拿设计 PR 冒充，不编造历史链接。版本计划、正式验收与发布依据仍从原有版本入口查看。

原型中当前版与历史版默认使用同一完整模拟横轴，#334 默认展开；示例为设计评审30小时、开发6小时、随版准备6小时、Pre试用完善15小时，并显示并行测试记录。示例 v1.0 发版但未交付此特性，v1.1 提供 Pre，v1.2 提供 Release。所有版本、时间和过程状态标明模拟，不对应 BW 真实承诺；卡片真实设计状态、PR链接与目标验收不被模拟覆盖。来源核对集中在右上弹窗。

Pre 表示先行试用交付，Release 表示正式交付。反馈、新需求、bug 均进入目标关联的 Issue，不新增反馈台账，也不按“两周内／以后”分流。具体反馈来自哪个版本、候选及使用范围应能追溯；未纳入计划的反馈不能算本版承诺。原始计划／验收引文保留当时用词，不修改真实历史材料。

## 可调整的读取与解析边界

后续实现须将来源读取、节点解析、时间轴展示分开，以支持项目规范变化：

1. **来源读取**复用已有 provider、文件、PR 与原生工作区入口，保留原始来源和修订；不新增执行器或业务数据库，不读取会话正文。
2. **节点解析**按项目实际规范识别特性关联、设计／实现 PR、候选验证与随版交付。规则或脚本可独立调整，不能按“第一个 PR 是设计、第二个是开发”猜，也不能把两 PR 数量永久写死。
3. **只读展示**消费解析后的事件、时间、范围与来源，不在页面组件中直接解析 Issue 标题、PR 正文或会话。

结果应可追溯原始对象、修订／commit、业务发生时间、读取时间、解析规则修订与对应范围。修改规则后可重新计算，但不能覆盖历史人工验收结论；无法识别的事件保留缺口。用少量具有代表性的真实输入验证解析规则，覆盖单／多 PR、回返、跨版以及缺证据。本稿只规定边界，不固化共享 JSON 字段、调度机制或脚本框架；实现 Plan 再确认具体模块和执行方式。

### 正式承诺、未合入成果与历史

| 信息 | 读取与展示规则 |
| --- | --- |
| 正式承诺 | 沿主干已确认计划的 sourceCommit／revision 读取，不以本地草稿替代 |
| 计划草稿 | 沿当前版本绑定的计划工作区读取，保留草稿身份，不猜另一台机器的路径 |
| 未合入成果 | 从明确关联的 Issue／PR 出发，PR 文件固定 head SHA；本地草稿标宿主、工作树与修订。多个候选列出，不按名称或最新时间猜唯一成果 |
| 人工评审 | 绑定对应 PR、成果和修订；本轮约定设计 PR 经人评审合入标记设计通过，后续范围变化仍需对应记录 |
| 测试与交付 | 开工与测试时点暂留空；交付按实际版本计划和人工验收推导，不把设计 CI 当生产候选验证 |
| 历史验收 | 沿 committed planRef 和验收修订读取当时计划与人工结论；当前动态和后续发布不重写历史 |

继续使用 `VersionGoalSchema` 的 owner／deadline／deliverable 与任务 provider／repository／number／goalId。特性身份、事件和来源在读取时派生；没有新增持久化事件 schema。节点规则以独立纯函数实现，可随项目规范调整。

固定样本：v0.8 计划来自主干 90952d9；v0.7 计划按验收 planRef.sourceCommit 固定读取。#334／#440 初稿提交只证明设计文件存在，不代表认可或开发完成；历史示例为 #334／#383，真实阶段未重建。原型不修改快照来伪造真实“特性”标签。Git 分支不证明宿主登记或会话状态。

## AI workflow 生产力

本轮只保留空指标面板，各占位显示“指标待定”和“—”。具体指标、口径、会话解析和统计实现由 workflow 专项负责，不在本轮版本总览中提前固化，也不阻塞总览落地。不展示模拟0或推断生产力；后续接入时区分未读取、读取失败和确实无样本。

## 导航与跨屏关系

沿 #455 的当前项目进入定位、完整原生任务页和工作树行。计划／验收沿 navigateVersionWorkflow，任务沿 openVersionTasks；原生工作会话与 activateVersionWorktree 保留完整项目、任务源和宿主身份。唯一匹配直接进入，多实例用现有选择器，无匹配沿原生创建入口。总览不后台建树，也不仿制另一套会话屏。

从 #440 项目总览或规划工作区进入后定位本版相关特性，返回恢复来源、视口和未提交草案。未开始计划时仍可进入上下文而不创建计划；已读计划没有该特性时提示缺关联。关联版本为一排版本号标签，悬停／聚焦看一句本版范围，点击进入对应总览定位同一特性。重复版本名需明确身份，不按日期推断，不把分组当 Git 分支关系。

本原型的 scene／focus 和来源弹窗只演示本屏，输入保留于页面内存，刷新清除；真实 #440 返回恢复尚未联调，不作为路由或持久化协议。关联样本按完整任务引用读取固定计划；v0.7 未单列 #334 增量时保持缺口。
