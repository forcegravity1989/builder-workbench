# 团队协作与项目共享

> 供产品与设计评审者阅读；只定义 #342 的用户价值、范围与取舍。状态：设计提案，待人确认；不是现行产品承诺。行为与实现建议见 [spec](spec.md)，交互演示见 [完整旅程](prototype.html)，证据见 [STATUS](STATUS.md)。认可范围变化时同步更新。

## 用户与问题

2–3 位 Builder 共同做项目，每个人安装自己的 BW。新人希望接受邀请后找到项目，已有用户希望重新打开时看到最新团队项目并继续自己的工作。当前共享链首先要求交换主机配对地址，项目发现依赖主机在线；用户还没开始协作就需要理解执行位置。

当前代码已经支持原生仓库、工作树、配对、跨主机目录和版本材料。缺口在于稳定的人员与团队关系、独立于主机的项目目录，以及按项目限定的访问与撤销。现有个人／团队属性只过滤项目墙。

## 价值与依据

本次用户明确要求从首次使用与老用户刷新设计协作。已有 [#342](https://github.com/forcegravity1989/builder-workbench/issues/342) 现已承接项目组与权限；[#552](https://github.com/forcegravity1989/builder-workbench/issues/552)要求只读和项目／工作树范围；[#603](https://github.com/forcegravity1989/builder-workbench/issues/603)要求避免隐式切换别人的主机；[#479](https://github.com/forcegravity1989/builder-workbench/issues/479)提供地址变化输入；[#641](https://github.com/forcegravity1989/builder-workbench/issues/641)明确入口自己确定来源、任务通过本人本机身份读取的方向。Issue 描述是设计输入，不等同于全部实现已经存在。

过去 #342 的聚合研究保留两个结论：项目标题可合并，工作树／会话的真实宿主身份必须保留；配对设备不等于成员。旧“hosts.json 即团队”的薄路径继续作为历史能力，不作为新团队模型。

## 目标体验

第一次启动提供「加入团队」「创建团队」「先做自己的项目」。收到邀请直接定位团队和项目；必要的本机准备按工作需要出现。成员进入团队后可发现共享项目，默认用本机代码工作，缺代码才克隆。查看同伴工作区明确显示姓名、设备和访问方式；执行到远端始终是明确选择。

第二天打开，先恢复自己的工作，再同步团队目录。对方电脑关闭也不让项目消失；目录、代码、任务和远端工作区各自说明是否已更新。成员只需理解“谁在做、做哪个项目、我如何参与”。

## 范围与边界

本提案完整设计团队创建、邀请、加入、项目发布与撤回、目录刷新、跨设备使用、只读协作、远端执行与撤销。保留个人直接开工；不增加群聊、全员收件箱、多级审批或另一套 Issue／完成记录。团队管理员只管理协作目录与成员，代码写入权仍由 Git 平台决定。

这是对原则 03 中“不另建成员、角色或权限体系”的明确变更建议，不能靠给配对改名实现。本次只提供设计供评审，不修改原则或生产代码。若认可，应将原则边界调整为“小团队项目协作需要的最小成员与资源授权”，仍保留 Builder 对目标与验收负责。

## 成功判据与待决策

新人不配置共享主机即可发现获邀项目并在本机开始第一项工作；老用户刷新不丢现有工作区、不会重复计数项目；离线与撤销分开；只读请求在宿主端受限；权限变化后新请求被拒，已有本机 Git 文件不被删除。实际收益需以邀请到首次开工耗时、首次开工成功率、重复项目与误切主机事件观察，当前没有测量结果。

推荐采用真实团队目录与最小身份服务，用户与团队多对多，项目归一个团队。需要确认服务运营归属、身份接入以及宿主范围授权／隔离的产品投入；具体推荐与替代项见 spec。提案和动画完成不代表这些决定已获认可。
