# Spec · 独立评审（reviewer agent）

> **30 秒导读**：这是什么——本次变更的**规格件**：独立评审长什么样、怎么操作、怎么防作弊。给谁看——过规格 gate 的人、审这批 PR 的人。现在作数吗——**in_review**（2026-08-27；见 `STATUS.md`）；上游意图见同目录 `intent.md`，可点原型见同目录 `prototype.html`。

## 设计拍板

1. **评审对象 = MR/PR**。默认评这张活的 MR；人在评审会话里点名其它 PR/MR 号也照评。没有 MR 就没有可评之物——入口如实拒绝，不评未提交的散件（WIP 审不做，见 intent 开放问题 3）。
2. **独立性落在会话层**：评审会话是**另一场会话**——评审专用系统提示词 + `mr-review` 剧本，会话记录与写码会话分开存，互不覆盖。评审工具固定 `claude_cli`，与活的开工工具无关（Open Design 的活照样能评它的 MR）。
3. **评审产物唯一落点 = MR 评论**，由评审会话自己用 `gh pr comment` / `codehub-cli mr note` 发（成熟 CLI 为底座）；**Rust 层不新增 MR diff / MR 评论 API**——diff 也是会话自己 `gh pr diff` 拉。Workbench 只做入口、守卫、起会话三件事。
4. **评审绝不推状态**：命令层守卫「活必须已在评审中且 MR 开着」；评审路径没有任何状态写入；系统提示词与剧本三处（模板/剧本/阶段规范）都写死禁 merge、禁改状态、禁改实现代码。状态机（`can_transition_to`、Done 唯一入边）一条边不动。
5. **三层落点**（对齐 architecture §2 三层模型）：
   - 方法论：`standard/skills/mr-review/SKILL.md`（两轴评审：规矩轴对项目手册、意图轴对活正文；意见六段固定结构，首行机器可辨标记 `<!-- bw:review v1 … -->`）。
   - 规范：`standard/system-prompt/references/review.md`（评审阶段规范）+ **评审主提示词外置** `standard/system-prompt/REVIEW.md.tmpl`（与 SYSTEM.md.tmpl 同机制：`{{...}}` 占位、编进二进制、改身份=改 md + 抬 `standard/VERSION`）。
   - 承载：新命令「请评审」；评审事件即 MR 评论（只追加，事后抹不掉）——不落本地库、不建评审台账。
6. **MVP 不派生「已评审」信号**：界面不解析 MR 评论、不点评审灯——没读回的数据不装绿。人去 MR 上看意见（原型步 3 是评论在远端的样子）。
7. **CI 层自动评审（2026-08-27 谈定补入）**：GitHub 仓的自动触发放在 CI 层——官方 `claude-code-action` 在 PR 打开/更新时自动 review（本仓落一份 workflow，认证走订阅 OAuth token，secret 由人配；配好前 workflow 如实不生效）。边界三条：只覆盖 GitHub 仓（codehub 仍靠内建「请评审」）；review 口径不另立第二份正本——action 每次自动读仓根 `CLAUDE.md`→`AGENTS.md`，与 `mr-review` 剧本同源于仓内规矩；CI 评论与评审会话评论共存，靠评审会话首行的机器可辨标记区分。

## 操作逻辑

**主路径**：活在评审中、MR 开着 → 会话屏动作条 / 计划详情点**「请评审」** → Workbench 查该活分支确有开着的 MR（拿到号）→ 在这张活的 worktree 里起评审 PTY 会话（没有树就重新供给，评审只读不写）→ 评审会话读活正文与评论、`gh pr diff` 拉真实 diff、对照 `AGENTS.md` 与 `.bw/` 规范件、跑得动的只读检查真跑 → 意见按六段结构发到 MR 评论、地址打屏 → 人扫结论，在 Workbench 里点合入或打回（既有动作，不新增按钮）。

**分支**：
- 活不在评审中 → 按钮不出现（会话屏/计划详情都按状态渲染）。
- 在评审中但查不到开着的 MR → toast 人话：「这张活没有开着的 MR，没有可评之物」，不起会话。
- 评审会话还开着 → 拒绝重开，提示先停止（与写码会话同规矩）。
- 再评一轮 → 停掉旧评审会话再点「请评审」，新意见**追加**为新评论，不编辑旧评论。
- 人在会话里让它评别的 PR → 剧本内置，同一套规矩照评。

**出错怎么办**：
- claude CLI 探活失败 / PTY 不可用 → 原话进 toast，不假装开成。
- 评论发不出去（网络/权限）→ 会话里如实说「意见没落上」并把意见原文打屏（剧本约束）；Workbench 界面本来就不显示「已评审」，无假绿可言。
- 评审会话越权尝试 merge / 改状态 → 提示词与剧本双重禁令；且 Workbench 侧本来就没把这些命令给它（评审路径无状态写入，merge 只在人点的 `MergeAndSettle` 里）。

## 原型

同目录 [`prototype.html`](prototype.html)（浏览器直接开）：步 1 计划屏活详情（评审中 + MR，「请评审」主按钮；无 MR 灰）→ 步 2 会话屏（写码会话与评审会话并列，评审会话运行中）→ 步 3 MR 评论（六段意见 + 大风险顶格标注）。视觉沿用 `docs/hifi/` 变量。

## 客户会问

- **这不就是把我该做的评审外包了？** 不是。合不合仍是你点；它把「逐行读 diff」压缩成「扫一份带文件:行证据的意见」。你反而更容易行使 gate。
- **会不会变成每 PR 必审的审批流？** 不会。「请评审」是可选动作，不是关卡；不点它照样能合。03 点名的失败形态（每 PR 必人审）在这里没有生长点。
- **评审说可合入，是不是就能自动合？** 不能。评审意见只是证据，合并永远是人在 Workbench 里点的那一下。

## 硬核挑战（内部 FAQ）

- **会话身份 1:1 绑活，第二场会话怎么存？** 会话记录按活存成 `<slug>/<iid>.jsonl`；评审会话另存 `<slug>/<iid>-review.jsonl`，读写走同一套 SessionStore，只是键上多一个评审轴。worktree 不另开（评审只读不写，共用这张活的树；diff 从远端拉，不依赖树的干净度）。
- **`--resume` 接回怎么办？** MVP **不接**评审会话的续聊接回（SessionStart hook 的 run-dir 按活号键控，挂上去会覆盖写码会话的 session id）。评审会话进程死了就再点一次「请评审」，重新评一轮、追加一条评论——幂等且无害。如实标「没建」。
- **成本？** 一次评审 = 一场会话的预算（读 diff + 写意见，通常远小于写码会话）。不自动触发（intent 开放问题 1），花不花人说了算。
- **评审质量不齐怎么办？** 人仍是 gate：意见只是证据，烂意见的代价是被人忽略,不会污染状态或数据。剧本强制文件:行证据与「没跑的写没跑」，压低空对空点评的概率。
- **为什么不在 Rust 里加 `mr_diff` / `comment_mr` 远端方法？** 评审的读与写都发生在会话里,agent 直接用成熟 CLI；Rust 加一层只会造第二条平行通道。Workbench 侧唯一需要的远端读是「MR 开着没、几号」——`open_mr_for_branch` 已有。

## 要求与验收

- **R1 独立性**：评审会话与写码会话的记录文件分开（`<iid>.jsonl` / `<iid>-review.jsonl`），起评审会话不覆盖、不弄丢写码会话的接回 id；两场 PTY 可同时活着。
- **R2 守卫如实**：不在评审中 → 无入口；无开着的 MR → 人话拒绝不起会话；评审路径全程零状态写入（代码里无 `set_status` 调用）。
- **R3 三层齐**：剧本 / 阶段规范 / 评审模板编进二进制，`ensure_*` 摊到资产目录；「看看喂了什么」（agent_briefing 等价物）能读回评审会话将注入的提示词。
- **R4 门禁全过**：fmt / clippy / app-shell 编译 / 三结构守卫 / 行数守卫 / cargo test。
- **R5 规格 gate 自查**：可点原型 + 操作逻辑（主路径/分支/出错）齐备，即本篇与 `prototype.html`。

## 标注的冲突

1. **高保真正本（`docs/hifi/index.html`）未同步**：原型先落在本目录，hifi 大文件的整合等规格 gate 过了再做，避免未认的样子进视觉正本。
2. **`[review]` 段的关系**:`.bw/config/issue-policy.toml` 当时有 `[review] who_can_merge` 人类治理配置；本变更不动它、也不往里加评审开关（要不要「自动评审」等用出真需求再谈，见 intent 开放问题 1）。
   **2026-09-02 补记**:`[review]` 段已随 `.bw/` 去冗批(活 #133)整段删除——它当时就没有任何代码读。现在文件里再出现 `[review]` 会因 `deny_unknown_fields` **当场解析失败**(`retired_fake_config_is_rejected` 断言的就是这条)。这条冲突自然消解;人类治理配置若要重建,另立活。
3. **评审会话无接回**：与「会话身份进 jsonl、进程死了靠 --resume 接回」的既有设计（architecture 模块 7）相比是一处如实的降级，原因见内部 FAQ；不做兼容层，后续要接就把 run-dir 键控加上评审轴。
