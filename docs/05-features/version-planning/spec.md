## 自动化提示与真实用户首用

唯一开场正文是上述 Orca 自动化提示词，明确携带目标工作目录、预期分支、当前版本与 Skill 路径。用户在新/已有 Codex 窗口原样使用它，以实际 Builder 身份操作；无需先在界面切换目录。Skill 校验目标后，每条命令显式传 workdir、git -C 或 -Workspace；宿主默认 cwd 是 main 不构成阻断，不修改主检出的分支。仅目标本身不存在或不匹配时报告配置错误。个人研发起手 Skill 不注入本业务会话，不把编写模板或运行测试交给用户。

本轮固定首用树是对运行配置的隔离；Orca 使用既有 `bw/week-plan`，以同一部署参数同时设置任务 workspace 和提示中的目录/分支，业务流程不另写一套。打开项目会更新原 Orca 任务，整体替换旧“已有计划就退出/禁止确认前保存草稿”指令及对应 Skill/reference，不允许叠加冲突规则。Codex 首用能验证真实人机流程，不能证明 Orca 已触发、已在正确分支开会话或已注入附件。

[实战说明](manual-review.md)列出真实数据和共用模板位置。本次 v0.3 原承诺来自 #174 目标评论，v0.4 的 `results` 是当前对其结果的回填；同一页面选择不同版本后加载各自 JSON，不另生成每版日常 HTML。此次实战只填写 v0.4；v0.3 是未确认的重建资料，本次评审进一步纠正：来源保留 #174 的整体目标原文，卡片忠实缩为一句，11 项具体工作进入任务区，previous_version 直接指向该评论与保存的来源；不能把此前归并后的三组标题冒充原文。正常规划不改已归档原承诺，结果写当前版。需要分享件时由会话按当前 data.json 另做只读导出或打印，页面不再内置会议评审 HTML 下载。

## 2026-09-16 评审已确认的目标与任务关系

目标以一句话表达 SMART 结果承诺，有明确衡量指标和目标值；期限默认该版本，负责人默认 Builder，后续有例外再补。基线和实际读数按口径保留。旧目标没有这些仍能查看，缺项不造数。任务是目标确定后拆解的具体工作，不因旧评论的标题叫“版本目标”就把工作项全部画为目标卡。

第二屏先由模型和 Builder 交流拟定目标，再带去和 Leader 评审：风险上报、前序进展摘要和当前版本目标集中呈现。第三屏在会后继续同份目标，Builder 核对现有 Issue 纳入、拆任务并挂 Issue，在正文明确验收条件，随后提 PR，由 Leader 审核。标题、正文、类型和父目标约定见 Skill 数据参考；本次不改 BW 界面组件或批量修改远端历史 Issue。

## 2026-09-16 保存方案确认

用户已确认改用 Skill 管理的最小本地 Web 服务。服务扩展在原 planning.py，Python 标准库实现；不把服务源码复制进项目，不挂 BW 主程序启动。start/serve/stop/status 按工作树管理一个进程、一个自动分配端口，各版本共用。连接信息在 .local；仅本机监听，接口校验连接凭据、来源、版本范围和数据修订号。

页面 GET 读取版本，PUT 自动保存，确认走独立接口；模型继续使用原 CLI 写同一 JSON。停顿保存与手动保存共用入口；断线或冲突保留输入并提示。移除 File System Access API 与目录复制/授权流程，离线 HTML 只读。交付件与评审流程的其他行为沿现有模板；真实 Orca 接入与浏览器操作由后续实战验收。

## 模板、数据与 Skill 的关系

- 固定 HTML 模板决定内容放在哪里、长什么样；数据字段必须逐项对齐 SE 的区块，不先独立发明一套大 schema 再反过来改模板。
- 模板与数据样例留在 Skill 安装目录，不拷入项目树；由 JSON 填入展示数据，打开即渲染，不加目录选择起手页。没有历史时由 Skill 初始化 default，版号确定后再回填刷新；每个版本只新建自己的数据文件，记录模板版本。打开同一页面通过版本选择加载对应数据；项目树内的 HTML 是服务刷新生成的离线缓存，可随时重建、Git 忽略，不另生成每版日常 HTML。
- 配套空数据文件及字段说明决定每处填什么、来自哪里、谁能填写、未知怎么表达。自动采集、人手填和人机讨论的结果都进入同份版本数据。
- Skill 编排读取、填充、展示、讨论、评审与归档。生成工具只负责可靠地把数据填入固定模板；不让模型每次重新生成页面结构和 CSS。
- 实际使用持续更新版本数据与会议记录，同一模板展示当前所选版本；确认只记录状态、不生成快照；需要分享件时由会话另做，页面不再导出会议评审 HTML。切换版本前完成保存，冲突时保留当前内容，不跨版写入。

| 数据类型 | 填写方式 | 缺失处理 |
|---|---|---|
| 可查询事实：Issue、状态、已有计划、真实读数 | 模型调用现有来源读取，保留来源与时间 | 查不到写未知并记录原因，不能编造或填 0 |
| 人持有的事实：会议记录、约束、未入系统的信息 | 人直接填写/提供材料，模型可以整理并保留出处 | 标待填写，只有影响当前决定时才定向询问 |
| 讨论结果：风险分析、候选目标、纳入建议、批注 | 模型基于事实起草，随对话修改，人决定 | 标草案/待确认，不能表现为已承诺 |
| 当前不可得或不适用的信息 | 保留空值与原因；不适用与未知分开 | 允许带缺口讨论；影响承诺或评审结论的项在定稿时明确处理 |

缺失原因、待补信息和确认状态属于数据契约。字段空着不等于整个流程停止，也不要求每次运行先重定指标口径；只有本次讨论实际涉及指标定义变更时，按需进入 metrics-refresh。

## 替换后的 Skill SOP（三屏顺序）

| 步骤 | 每步动作 | 留下什么 / 如何继续 |
|---|---|---|
| 1. 打开材料、新建版本数据 | 在固定分支读取复用模板和上一版本已归档的周一屏数据；明确当前版本及前序版本，已有当前草稿则恢复 | 当前版本独立数据文件，包含前序版本与固定修订引用；不覆盖旧版 |
| 2. 第一屏：忠实回填前序版本结果 | 从上版第三屏读原定目标，任务按所核对版本标签实时查询 Issue，再查询读数和版本交付报告；用户可以手填或反馈让模型修改；用户认可结果后继续 | 第一屏的“原承诺 / 实际结果 / 来源 / 未知与原因”，及用户确认记录 |
| 3. 第二屏：拟定并评审目标 | 汇总第一屏 SMART 进展、上报风险；先和 Builder 交流目标，再与 Leader 现场调整；写入 plan.goals | 同屏评审，无须来回切屏；记录会议确认状态，目标尚未拆成全部任务 |
| 4. 现场记录与会后纪要 | 现场核心记录直接填并自动保存；会后用户给链接，内置脚本取得完整转写，Skill 开子 agent 按三节纪要模板整理并回写 UI | 原始转写、现场记录、按模板生成的纪要分别保留；输入变化后旧纪要失效，分歧/听不清不伪造决定 |
| 5. 第三屏：会后拆解任务 | Builder 消化评审意见，继续同一份目标，先提醒核对现有 Issue 是否纳入，再拆任务、在 Issue 正文明确验收要求，复用或创建 Issue | 任务记录真实编号、类型和所属目标；会后改目标记原因，最终交 PR 审核 |
| 6. 落盘并提 PR/MR | 用户在本地页面确认计划，随后在会话明确要求发 PR，由脚本检查与提交。Leader 要求修改时回第5步修订同一请求 | 仓库可追溯材料及 PR 读回；Leader 的真实审核为最终握手，模型不代审、不自动合入或关闭 Issue |
| 7. 生产对接（本轮交付） | 落实既有 Orca 自动化更新、附件分发与 BW 目标读取适配；替换旧入口，不另养双写正本 | 复用 BW 组件，更新原自动化；目标不双写 Issue 评论 |

各步自动保存同一 JSON。第一屏确认事实、第二屏确认可带去评审、第三屏确认提交以及 Leader 审核分别记录；相关内容变更使对应确认失效，沿用仍有效的确认。BW/Orca 接线已随本次功能实现交付。

### 前序版本与第一屏的事实来源

前序版本的 `plan.goals`（第三屏最终目标）回答“原先承诺什么”，本次查得的交付/验收资料回答“实际做到什么”。当前版本的数据中保留二者及来源，不根据今天的 Issue 状态倒推原承诺，也不把上版已经过时的结果快照直接当作最新完成情况。

前序版本用显式引用（版本名、归档路径、固定 Git 修订/确认状态）定位，不按自然周或简单字符串排序猜测。首次使用没有旧数据时，说明“无历史周一屏”；可用已有确认的版本计划评论或用户提供材料回填，并标明来源，不能伪造旧版周一屏。这只是首次导入数据，后续正常流程读取归档数据。

### 会议输入与结论

完整转写 MD 是“A 说了什么、B 说了什么”的原始讨论，由用户把会议链接交给会话写入 `review.meeting_url`、Skill 内置的 CDP 转写脚本产出（经本机已登录 Chrome 的代理抓取），本特性不实现语音转写。现场核心记录直接填写并自动保存。Skill 开一个子 agent，只读取转写、现场记录快照及三节纪要模板，写出纪要；主会话核对后回写 UI，再与用户消化形成第三屏。输入或模板变化则拒绝接收旧纪要。转写中的提议、反对、试探不能直接升格为决议；两份材料冲突时展示差异，缺件可先讨论已有材料，不能宣称完整评审。原始转写不被总结覆盖。转写脚本已在真实 90 分钟会议验证抓取；纪要整理质量待首用核对，不以测试夹具冒充真实会议。

### 读取位置与数据重复风险（本轮继续审查）

## 操作与读写

1. Orca 复用现有「定版本计划（Workbench）」任务，到点仍创建新会话，工作树为 `bw/week-plan`。已有计划时展示当前版本材料、允许继续修订，不再因“版本已经确定”直接退出。
2. Skill 先读项目入口和前序版本已归档数据，再查询 Issue、交付和指标来源补充实际结果。没有版本名先用 default，讨论确定后定名；已有授权和目标不重复提问。缺失事实写未知，来源附查询时间或固定 Git 引用。
3. 固定模板、数据样例、转写脚本与纪要模板随 Skill sidecar 分发并留在安装目录，不拷入项目树；项目树只保存各版本数据。本地 HTML 由服务刷新生成、可随时重建，Git 忽略。
4. 数据为正文来源，HTML 为其可分享阅读件。页面停顿自动保存到同一 JSON，会话按文件 etag 修改；冲突时保留文字并提示，不覆盖另一方修改。Skill start 后提供本地服务 URL，页面读取当前 JSON；服务模式自动保存，无浏览器文件授权；离线打开为只读，保存失败保留输入并提示。
5. Builder 确认用于会议的一版：页面确认结果后，会话执行 `confirm --stage review_ready`，再进入第三屏。需要分享件时由会话另做只读导出或打印；页面不再内置会议评审 HTML 下载，HTML 本身不向远端发送内容。
6. 录入真实会议日期、参与者、完整转写 MD 和核心会议记录；保留原件，消化后的结论关联到目标或任务批注。没有真实会议材料可继续讨论草案，但不得声明已经会议评审。
7. Builder 回到会话，逐项处理意见，形成最终版本计划；保留被取消/延后项及其原因。修改继续写同一份 data.json，历史以 Git 修订与 MR 为准，不再生成快照修订。
8. 用户确认具体版本目标、纳入差异和归档件后，沿当前平台提交 MR。Leader 在 MR 审核最终握手。保留审核对象与结果链接；模型不得代签、自动 merge、关闭 Issue。
