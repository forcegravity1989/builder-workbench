创建一个版本之后，
我们的工作会怎样展开？

以 Builder Workbench 自身的 v0.7 / G2 为贯穿示例，把侧栏、实际工作、Orca 配置、磁盘文件和仓库材料连在一起。

已有：仓内代码可定位已确认：G2 行为定稿复用：Orca 原生能力

这是一份设计说明，不是当前产品使用手册。v0.7 / G2 是真实计划对象；以下从零创建、会话与分支示例均为讲解，不代表已执行。正式行为以 spec 经确认的内容为准。

建议：创建版本时，把计划和验收的工作区都准备好

每版两个稳定的工作入口。目标目录来自计划，目标工作树与任务工作树按需出现。

2 棵

提前准备的固定树

一棵用于计划，一棵用于验收。以后该版本的新会话进入对应树；切换版本不会把正在运行的会话搬走。

0 棵

为展示目录而复制的树

“v0.7”和“G2”首先是业务目录。版本不额外建父树；G2 只有需要独立协作时才建立目标父树。

按需

Agent 与验收材料

创建版本不启动模型。验收树可先存在，正式验收材料等选定计划依据时再建立，避免空白结论和错误引用。

我推荐这个取舍。 两个工作区提前准备，使“计划 / 验收”从第一天起就是稳定入口。代价是验收尚未开始也占一份检出目录，真正验收时还要同步代码。若大仓库成本不能接受，才改为首次进入验收时准备；侧栏仍保持同样的一行入口。

“固定”指同一版本后续继续使用同一棵树；v0.9 有自己的树。分支名如 bw/v0.7/plan、bw/v0.7/acceptance 只是示例，不能单凭名称判断归属。

保留计划与验收的入口，把重复层级合并

点击“计划”这一行进入既有计划屏；点击它的展开箭头查看原生 agent。分支名放在悬停说明或详情中。

结构示意，可点击各行

这里仅说明行与行的关系，不是另一套原生工作树 UI。产品中要复用 Orca 卡片、agent 行、菜单与父子关系；“流程名称 + 页面入口”是 BW 所需的少量适配。

计划、任务、验收各有一个明确去处

  • 计划行：打开原有计划屏；其下的 agent 仍在这棵树里工作。多次会话不增加多棵计划树。
  • 任务行：打开限定本版的原生任务屏。G1/G2 来自计划，点击目标进一步缩小任务范围。
  • 目标下的分支：是真实工作树。点击分支或 agent 打开完整原生工作区。
  • 验收行：打开原有验收屏；下方直接列这棵树里的 agent。

复用不能解释为“所有行完全零改动”：新增版本/目标目录由 BW 负责，合并入口需要接入既有卡片的展示与激活动作。原生分支操作、会话、父子关系继续由 Orca 负责。

这一轮的问题：定稿、开工、保存与兼容

整体方向已理解；计划定稿已确认简化；开工收敛为复用原生创建器、预填上下文并保留用户选择，其余按既有复用边界收敛。

原计划屏整体沿用，由原板发起会话

点侧栏计划行就是打开本版计划工作树及其原有整屏，包含 Orca 会话区与右侧计划板。新会话仍从原板“新建计划”发起；打开旧版回显该版材料，屏内不再选版。高保真修订 7 只标一个整屏复用区域，不再分别画两块占位；内部布局继续由原计划特性负责。

两棵流程树与大量任务树如何算

分支记录本身很小，空间主要花在检出文件、依赖和构建产物。任务多时任务树通常占大头；历史版本多时两棵流程树也会累积。目标工作区可处理几个相关的小 Issue；需要独立并行时再分别开工，不强制所有 Issue 各建一棵树。

动作放在哪里结果与边界
显示 G1/G2 目录计划已保存后自动投影到侧栏。推荐不加“生成目录”按钮。目录出现不代表正式定稿；改名/排序按稳定目标身份保留工作区关联。
目标开工侧栏目标的“···”菜单；目标范围条可进入同一操作。调用与 Issue 同一原生创建器，预填目标名称、交付约定和关联任务引用。用户确认任务范围与执行选项，不另加 BW 开工向导。
Issue 开工原生任务列表/详情原有按钮。仍打开原生创建弹窗。有合适目标树时建议其为父级，用户可改或清空；实际是否新树、采用何种分支与执行方式沿用原生选择。已有明确关联则打开，避免重复创建。
目标树属于哪里业务上属于 v0.7 / G2。v0.7 是逻辑目录，没有“版本父工作树”。真实目标树可以成为 Issue 树的原生父级；目录缩进不决定 Git 基线或合入方向。
计划“本周固定”，怎样判断才可靠？

用户已确认复用人工评审与计划 PR 合入，核对实际采用的材料修订。工作流阶段灯亮、PR 曾经合入，都不能证明现在这份编辑稿没有再改动。显示目录和确认承诺分开处理，也就不需要每改一次目标都重新生成目录。

草案 / 尚未核对→待评审合入→已采用正式修订→ 再修改有待确认修改

用户已明确不增加周冻结、目录生成按钮或额外快照存储。以上状态从现有材料、评审与归档引用识别，不让用户再填一套状态。

业界做法与本轮判断

VS Code 官方把“相关工作共享工作区”和“独立任务用隔离工作树”列为不同选择，并区分会话关系与代码隔离。Claude Code 也提供工作树启动与复用方式。这些文档没有给出“每个 Issue 必须一棵树”的统一标准；据此，我建议 BW 提供业务上下文和可改的建议值，让隔离方式沿用原生选择。

目标开工和 Issue 开工共用 Orca 创建器，但目标不是伪造的 Issue。父工作树已有原生选择器，预填其建议值仍需接入；父级只影响嵌套，不改变代码起点。原生“采用已有分支”与“在现有工作区继续会话”也不是同一个动作。

工作树信息在哪，关掉应用会不会丢？

现行 Orca 会持久化工作树元信息和父子关系；桌面 profile 的原生状态文件是 orca-data.json，具体应用数据位置随 profile/宿主变化。G2 新增的版本/目标绑定也必须通过同一原生宿主体系持久化，不能只存侧栏内存。目标目录则由仓库的计划材料重建。

要求是正常重启、重连后读回同一关联，但这要在实现后验证。换电脑只克隆 Git、删除 profile 或删掉工作树，并不能保证恢复原来的 agent 会话；不能承诺任何情况下都不丢。

存量版本与共享项目会不会受影响？

兼容目标是继续可用，不能现在就断言零影响。旧材料可读，查看历史不批量建树；旧共享计划/验收树不搬、不改名、不整树归版，原有运行与自动化继续使用原工作区。版本下方统一的“Orca 项目工作区”中，当前项目入口保留所有尚未归版的原生树与会话；私人项目也在同一区域。

共享/配对继续访问原执行宿主、同一材料和原生记录，不在访问者机器另建副本。新增绑定必须沿既有权限通道提供；旧对端不支持时明确提示、保留原生访问。项目墙和总览当前依赖选版偏好与固定计划树，这些读取也需要同步适配，视觉与数据口径不借机改造。

BW 给 Builder 增加的价值：把计划承诺、执行工作区和验收依据串在同一版本里，让目标可找到、任务不串版、计划变更可识别、结果可回看。Orca 继续负责执行；不要求 Builder 重复维护一套目录、任务状态或聊天记录。

编辑工作树文件→提交到分支→推送并开 PR→人评审合入→团队读回

以上每一步都是独立事实。PR 合入也不等于已发布，材料归档也不等于目标达成。原生父子关系只描述工作区从属，不自动合并代码；子分支的改动仍须走明确的评审与合入路径。

哪些直接复用，哪些必须适配

用户不用手工改一串 Orca 配置文件。产品调用既有入口准备工作区；G2 补业务范围和定位。

能力已有能力继续承担G2 需要做的事

会新增或更新的本机记录

原生工作树登记、按需父子关系、原生会话/自动化记录，以及待定义的 BW 归属信息。这些是使用产品时产生的状态。

不会因建版本而要求重设的东西

仓库远端地址、Git/平台凭据、全局模型选择、已有自动化时间和启用状态。新版本也不自动让 agent 开跑、关闭 Issue、合 PR 或发布。

实现顺序仍是先复用原生能力，再做 BW 挂载与范围适配。若某点必须改变 Orca 核心执行协议或宿主路由，应回到方案确认；当前研究没有理由重写会话、调度或工作树引擎。

“目录很多”与“仓库被检出很多份”分开算

下方只是数量估算，不是磁盘实测。目标目录不计入物理工作树。

只计算这些版本带来的工作树，不含原 checkout、项目约定树、指标树等已有目录。两个并行版本先占四棵流程树；G1/G2/G3/G4 都显示，也不必多占四份代码。

空间会花在哪里

Git 对象通常共享，工作目录里的文件仍分别检出。依赖与构建产物可能更大。原生若按项目配置执行初始化脚本，还可能安装依赖；不能承诺“两棵流程树只占两个 JSON”。

轻量化可以预研，但暂不承诺

Orca 已有部分检出的能力；能否让计划/验收只检出材料，还要核对 Skill、脚本、指标和验收所需代码。现阶段不把它当默认方案，也不假设已有初始化脚本可无代价跳过。

两个版本同时工作，会不会互相影响？

计划/验收文件分别在各自树里编辑，agent 继续属于启动时的树。切换侧栏只改变当前显示，不迁移运行。Git 仓库和远端 Issue 仍是共享的：同一 Issue 的状态两版都能看到，分支合入主干也会影响之后的代码基线。因此“独立工作区”不等于“复制一套彼此隔绝的远端项目”。

计划合入后，提前创建的验收树会自动拥有最新代码吗？

不会。工作树保留自己的分支和文件。开始验收前要核对实际交付候选，并同步所需代码；现有同步不能安全快进时应说明原因、保留本地修改，由会话协助处理。正式验收依据可以从固定提交读取已合入的计划，不应误读另一树尚未确认的草稿。

目标父树是不是把子树改动自动汇总起来？

不是。原生父子关系解决“哪些工作区属于一起”的导航与管理问题。创建子树时从哪份代码开始、改动先合到目标分支还是主干，要单独确定。普通独立任务建议从项目约定基线起步；确需目标集成时再明确合入路径，不能让目录缩进偷偷决定代码流向。

目标与 Issue 共用原生创建器

BW 预填业务上下文、名称与合适父级建议；Builder 沿用原生分支、模型和执行选项。没有必要先选一种所有人必须遵守的工作树模式。

高保真修订 7 将计划/验收标为原有整屏复用，版本下方统一保留原生项目入口，并加入版本归档演示。初始为 v0.7（在制）与 v0.6（已归档回看）；从“＋”创建 v0.9 后体验新版本入口。点目标只改变同一 Orca 任务屏的筛选。新建版的计划内容由原有计划屏编辑，本原型不复制编辑器；后续目标执行使用 v0.7 已有快照体验。点击目标/Issue 开工先看原生创建器挂载说明，再演示提交后的结果；父级可选择或取消。

预研已核对的复用边界
  1. 绑定与恢复：版本/用途/目标绑定扩展原生工作区附属信息，经宿主契约与能力检测读回；重启、换机器按稳定身份恢复，不按分支名或标题猜归属。
  2. 创建与同步：两棵流程树的基线、重名、部分失败重试与初始化成本按原生登记核对；同步只走显式安全路径，不覆盖草稿。
  3. 任务与运行：任务范围以计划完整引用接原生列表与分页；同 Issue 跨版按明确绑定选树；自动化条目身份含版本，保留用户设置。
