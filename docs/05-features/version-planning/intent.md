# 版本计划：在会话中讨论，用 HTML 评审，用 MR 确认

> 30 秒导读：Builder 与模型围绕同一份版本材料持续讨论，带 HTML 参加评审，再将会议决定带回会话形成版本计划；Leader 审核归档 MR，完成双方确认。最终复用 Orca 和常驻分支，不改 BW 界面组件；当前交付可用于 BW/Orca 首用的分支，真实计划内容及 Leader 审核由 Builder 后续完成。

## 客户、问题与收益

客户是准备版本计划的 Builder 和评审计划的 Leader。现行流程主要通过会话和 Issue 评论对齐；缺少能随讨论更新、带到会议、保留评审意见并归档的统一可视材料。核心收益是让目标、事实、建议和评审后的改动在一份有来源的版本材料中看得清、接得上。

依据为 [#176](https://github.com/forcegravity1989/builder-workbench/issues/176)、[#207](https://github.com/forcegravity1989/builder-workbench/issues/207) 最新正文，以及用户本次补充。#176 交付可复用资源和流程；#207 交付 BW v0.4 的真实首用结果及特性自身的指标、采集与验收关联。不能用模板代替真实首用，也不能用页面中的项目指标代替特性价值证明。

## 客户体验

既有 Orca「定版本计划」自动化触发，在 `bw/week-plan` 起会话。Skill 携带固定 HTML 模板、数据模板与本地服务脚本，按规划工作树启动或复用服务，在会话右侧打开可编辑页面；离线 HTML 用于阅读归档。用户边聊边看、修改版本材料，确认一版后带 HTML 去评审。会议后录入评审记录，Builder 回到会话继续讨论，明确 SMART 版本目标并拆成任务、关联或创建 Issue。随后提交归档 MR，由 Leader 审核；提 MR 不等于确认完成。

当前由用户与本会话一起实战填写 v0.4，逐屏核对并调整 Skill 与 HTML；v0.3 只作前序资料，暂不继续填写或重写。任务宿主负责配置工作目录，业务会话不混入个人研发起手、开发原型或修改 spec 的指令。真实模型对话与用户操作是本次要验证的体验；自动化和附件分发随本功能接入，实际模型对话及定时触发与代码验证分别记录。

模板与数据样例随 Skill 分发、留在安装目录，每个版本只新建数据文件；日常打开同一页面切换版本并加载对应 JSON，需要分享件时导出会议评审 HTML（客户端下载件，不入库）。先读前序版本归档的最终计划，忠实回填实际结果，用户认可第一屏后再讨论第二屏。现场核心记录直接填写并自动保存；会后给会议链接，内置脚本取得完整转写 MD，Skill 开子 agent 按三节纪要模板整理并贴回页面，再共同消化形成第三屏。归档数据保存计划与评审历史；旧界面目标读取同份 JSON，不把 JSON 与 Issue 设成两个可独立编辑的正本。执行状态仍从远端事实读取。

页面只使用 v7-1 的计划区，移除实时对话区域，以「上周版本结果 / 总结与评审 / 版本计划」组织内容，页面以版本组织，不以周作为归档键；Issue 标题可携带用户约定的 W38 目标引用信息。调度仍可按周一执行；技术分支名保留现行 `bw/week-plan`。

## 范围与价值检验

加强原则 03 中的人定目标、人审结果、人机协作及可复用技能改进。未知数据明确显示未知，模型不代定目标、不伪造会议决定，不自动合入或关闭 Issue。

仅涉及版本计划自动化、其提示词/Skill/附件、结果归档及该特性的首用与衡量。原型其他屏幕、BW 界面重构、资产盘点扩展、员工助手、通用知识治理不在范围。

目标的 SMART 定义、任务的父目标、交付件与验收要求属于通用流程。新特性的完整引领/滞后指标体系及 E2E 对应关系仍只要求 BW 自身按 #207 落实，不要求所有被管项目在一次计划会议里完成。

## 客户会问

- 在哪里聊天？产品沿用 Orca；本轮先在新 Codex 窗口实战，HTML 不内置另一套聊天。
- 能改材料吗？页面手填自动保存，会话修改同一 JSON，冲突必须可见；HTML 从数据重建。
- 谁最终确认？Builder 确认提交，Leader 审核 MR；会议记录与 MR 审核是两个不同环节。
- 如何判断值得用？首用记录准备/返工事实和承诺定义情况；版本结束后记录原承诺的人验收结果，不编造基线或收益。
