# 版本计划：让目标清楚，便于讨论与评审

> 给 Builder、Leader 和产品评审者在判断价值与范围时读。本文只定义为什么做、为谁做；行为见 [spec](spec.md)，技术取舍见 [design](design.md)，认可与证据见 [STATUS](STATUS.md)。用户价值或边界改变时更新，不追加讨论流水。
>
> 状态：计划屏已按 G3 计划旅程高保真落地（2026-10-21，七轮设计反馈与落地校准经用户确认）；证据见 STATUS。设计认可不表示真壳验收通过。

## 用户与问题

Builder 要把场外要求、项目现状和自己的判断组织成一个版本的目标，Leader 要迅速看懂准备交付什么、为什么值得做、以后怎样核对结果。旧周一屏把上版验收、本版规划和任务拆解拆成三屏，会议记录又重复填写；目标有时变成任务清单，模型还会把仓内不完整信息当成全部事实。

## 价值与依据

核心利益是在一处形成可讨论、可编辑、可评审的版本承诺，不让用户在模型、会议材料和任务列表之间搬运。依据是 [#257 用户反馈](https://github.com/forcegravity1989/builder-workbench/issues/257)、[#249 迁移任务](https://github.com/forcegravity1989/builder-workbench/issues/249) 及本轮原型评审。自动化接线关联 [#252](https://github.com/forcegravity1989/builder-workbench/issues/252)，它服务本特性，不单独构造用户旅程。

## 目标体验

用户点侧栏“计划”，看到计划准备（上版回顾）、本版目标、会议纪要、归档 PR 四区沿一页自然展开，顶部导航负责定位。左侧完整复用固定规划工作区的 Orca 会话、历史和工具，右侧目标可直接编辑。尚无计划时由空板「与计划助手新建计划」直接开始协作；遇到旧数据时，同一入口带入具体文件问题，不增加特殊迁移旅程。模型先核对只有用户知道的要求，再帮助把目标说清，不先替用户定框。

目标可以是新能力交付、反馈优化或成熟能力在具体场景的成果。这是对话思路，不是强制分类表；验收标准、指标承诺按实际需要填写，交付件归版本级验收呈现。Builder 制定目标后与 PL（Leader）开会评审，双方在页面直接修改目标，评审意见经「批注模式」记录在对象旁并发送给计划助手。人确认工作范围后，模型创建或更新真实 Issue，用户能进入原生任务详情修改，再返回原计划。归档通过会话发起 PR，页面读回真实状态并可打开 Orca 原生 PR 页。会后由计划助手把在线批注与可选会议转写稿整理为「共识 / 遗留」两块纪要，经人工确认生效，遗留逐条闭环由人标记；认可随归档 PR 评审表达，生成或填写不等于确认。

## 范围与边界

- 包含单页规划、目标引导、会议纪要（批注 + 可选转写稿 → 共识 / 遗留 + 人工确认）、任务关联与返回、草稿恢复、归档状态，以及原生自动化和会话历史。自动化首次登记默认关闭，由用户在原生编辑器配置，手动开始不启用定时。
- 上版验收在独立 [验收屏](../version-acceptance/intent.md) 完成；未验收不阻止用户讨论新版本。
- 指标定义、采集与读数由 [总览指标](../overview-metrics/intent.md) 提供，只接入项目可查询日／周历史的脚本；配置指标每次开启原生会话。没有可靠读数时保持未知，目标值可以留作草案，不能宣称已形成可信数值承诺。
- 不重建 Orca 会话、任务编辑器或调度器；不新增共同编辑服务器，不接管发布链，不自动合入或完成 Issue。

## 成功判据与待决问题

用户能带入真实要求并完成一次版本规划，Leader 不依靠翻聊天就能理解主要目标和交付；再次打开可读回同一版本与材料。首用后的一个完整使用周观察目标澄清与返工原因，确认哪些引导有帮助，再决定有效指标；成熟后持续产出可评审的版本计划和实际成果，不把“字段填满”当价值。

本轮按用户要求重新评审计划屏布局与操作旅程并已落地：界面帮助 Builder 定出更清楚、可衡量的结果目标，初步拆解任务后接受 Leader 评审，普通意见直接改目标、评审意见经批注进入纪要，最终通过归档 PR 接受 Leader 再次审核。阅读体验以目标层次与自然滚动为先，导航负责定位，不为一屏看全压缩内容；会话沿用左侧 Orca 原生工作区。对应高保真见 spec 的 G3 段与 [计划旅程原型](planning-journey-prototype.html)。自动化具体时间、时区和启用仍由项目使用者配置。
