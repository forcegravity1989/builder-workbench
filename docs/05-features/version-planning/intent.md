# 版本计划：让目标清楚，便于讨论与评审

> 给 Builder、Leader 和产品评审者在判断价值与范围时读。本文只定义为什么做、为谁做；行为见 [spec](spec.md)，技术取舍见 [design](design.md)，认可与证据见 [STATUS](STATUS.md)。用户价值或边界改变时更新，不追加讨论流水。
>
> 状态：计划右板已按认可结构接线；G2 版本运作（含版本归档）设计于 2026-10-20 评审定稿，高保真修订 7 作为实施输入。定稿不表示生产接线或真壳验收通过，证据见 STATUS。

## 用户与问题

Builder 要把场外要求、项目现状和自己的判断组织成一个版本的目标，Leader 要迅速看懂准备交付什么、为什么值得做、以后怎样核对结果。旧周一屏把上版验收、本版规划和任务拆解拆成三屏，会议记录又重复填写；目标有时变成任务清单，模型还会把仓内不完整信息当成全部事实。

## 价值与依据

核心利益是在一处形成可讨论、可编辑、可评审的版本承诺，不让用户在模型、会议材料和任务列表之间搬运。依据是 [#257 用户反馈](https://github.com/forcegravity1989/builder-workbench/issues/257)、[#249 迁移任务](https://github.com/forcegravity1989/builder-workbench/issues/249) 及本轮原型评审。自动化接线关联 [#252](https://github.com/forcegravity1989/builder-workbench/issues/252)，它服务本特性，不单独构造用户旅程。

## 目标体验

用户点侧栏“计划”，先看到准备、目标、评审、拆解、归档的完整流程。左侧完整复用固定规划工作区的 Orca 会话、历史和工具，右侧是一页可直接编辑的版本进展、风险和 Top3 目标。首行“新建计划”让尚无版本或会话的用户直接开始协作；遇到旧数据时，同一入口带入具体文件问题，不增加特殊迁移旅程。模型先核对只有用户知道的要求，再帮助把目标说清，不先替用户定框。

目标可以是新能力交付、反馈优化或成熟能力在具体场景的成果。这是对话思路，不是强制分类表；交付件、指标、验收说明按实际需要填写。Builder 制定目标后与 PL（Leader）开会评审，双方在页面直接修改目标与交付约定。人确认工作范围后，模型创建或更新真实 Issue，用户能进入原生任务详情修改，再返回原计划。归档通过会话发起 PR，页面读回真实状态。Builder 在评审后填写会议纪要时，预览并复制当前目标生成的三段内容；通常在任务拆解和 PR 合入后整理，也允许在拆解前复制，不以复制代替评审。

## 范围与边界

- 包含单页规划、目标引导、三段纪要、任务关联与返回、草稿恢复、归档状态，以及原生自动化和会话历史。自动化首次登记默认关闭，由用户在原生编辑器配置，手动开始不启用定时。
- 上版验收在独立 [验收屏](../version-acceptance/intent.md) 完成；未验收不阻止用户讨论新版本。
- 指标定义、采集与读数由 [总览指标](../overview-metrics/intent.md) 提供，只接入项目可查询日／周历史的脚本；配置指标每次开启原生会话。没有可靠读数时保持未知，目标值可以留作草案，不能宣称已形成可信数值承诺。
- 不重建 Orca 会话、任务编辑器或调度器；不新增共同编辑服务器，不接管发布链，不自动合入或完成 Issue。

## 成功判据与待决问题

用户能带入真实要求并完成一次版本规划，Leader 不依靠翻聊天就能理解主要目标和交付；再次打开可读回同一版本与材料。首用后的一个完整使用周观察目标澄清与返工原因，确认哪些引导有帮助，再决定有效指标；成熟后持续产出可评审的版本计划和实际成果，不把“字段填满”当价值。

当前无须重新讨论特性数量或布局。按已合入定义实施，详细设计中的未决项由实施窗口请用户确认；自动化具体时间、时区和启用由项目使用者配置。

## G2 版本运作的补充意图

[#383](https://github.com/forcegravity1989/builder-workbench/issues/383) 要让 Builder 从项目墙进入项目后，沿“版本 → 计划承诺 → 目标与执行 → 验收结果”组织交付。BW 帮用户判断为什么做、当前为哪版工作、按什么核对成果以及后来如何回看；多个版本可并行，切版不改变原有工作区和会话的归属。

新增的是业务导航与关联：版本入口、计划派生的目标目录、原生工作区的版本/目标归属，以及从真实材料汇总的版本总览。用户已确认保留目标目录、目标工作树按需创建；又确认不增加周冻结、生成目录按钮或独立快照协议。目标保存后即可找到，正式承诺沿用人工评审与 PR 合入，后续修改如实区分，不让目录出现冒充定稿。

计划和验收继续使用现有业务板与 Orca 完整会话区，由原板的新建按钮发起会话，侧栏明确版本后屏内不重复选版。候选将每版两棵固定流程树与入口合并；目标与 Issue 开工复用同一原生创建器，BW 带入版本、目标、交付约定与任务来源，名称和执行选项由 Builder 调整。相关任务可在目标工作区一起做，需要隔离时再分别开工；不新增统一工作树习惯设置，也不因目录结构强制每个 Issue 一棵树。

项目总览、任务、工作树/父子、agent、自动化、知识库及共享宿主继续复用。保留旧版本材料、原共享树、在跑会话和原生项目工作区的可达性；不以“复用”代替迁移、权限、持久化与重启验证，不承诺 Git 材料能恢复所有聊天。上部围绕当前项目，知识库与版本之间分隔；版本下方统一保留 Orca 原生项目工作区，包括当前项目与私人项目。版本归档是版本生命周期收尾的显式人的动作：复用 Orca 原生工作树归档，已归档版本留在原位置带标识、默认可收起回看，不设专门历史会话或归档分区。

成功体验是：用户用现有操作即可形成承诺、进入正确工作区、并行推进版本并按同版依据验收；版本收尾时一次归档即可让在制工作区退场而材料与会话保留可回看；无需重复维护目录、任务状态或聊天记录。版本总结从材料与已有归档引用读取，不额外冻结或手填报告。设计依据为 [spec](spec.md#g2-版本运作设计定稿)、[高保真修订 7](version-workspace-prototype.html?rev=7) 与 [旅程及数据说明报告](version-workspace-journey.html)。
