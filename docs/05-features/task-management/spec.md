# spec — 任务管理：任务屏与链接直达

> **维护约定**：给设计、实现、检视和验收者读取。本篇维护当前任务屏、来源差异、详情处理和链接直达的可观察行为。用户结果与范围见 [intent.md](intent.md)，状态与证据见 [STATUS.md](STATUS.md)。原型 [prototype.html](prototype.html) 是任务屏的静态设计输入，不代表生产能力已经验收。

## 任务屏正本与入口

任务管理的正本是当前 BW 任务屏，而不是某一条链接演示。Electron 入口由 `AppWorkspaceShell` 在 `activeView === 'tasks'` 时挂载 `TaskPage`；页面结构由 `TaskPageFrame`、`TaskPageListChrome`、`TaskPageContent` 和各来源列表／详情组件组成。Workbench 壳中的任务入口是 `WorkbenchRail` 的「任务」按钮，项目和版本上下文沿现有侧栏读回。

任务屏至少要能表达这些可见层级：来源任务筛选条、来源特有筛选和搜索、范围标签（有版本或目标上下文时）、列表表头与行、加载／空态／失败／部分失败、分页，以及点击任务后的详情返回路径。原型可以使用演示数据，但不能把任务屏缩成一个链接动作卡片。

任务来源和外壳的归属保持分离：任务管理维护列表、详情和处理结果；CodeHub、GitHub、GitLab、Linear、Jira 的连接与来源差异回各自适配规格；Worktree、版本和目标身份回当前 Workbench 侧栏与版本导航。

## 探索入口与归属

任务管理归入探索 BW 的 W03「构建交付」。W03 负责从任务结果进入工作、评审和回看，任务管理承接任务屏查找、筛选、查看、处理，以及从终端或会话链接打开既有任务详情并返回原工作上下文。30+ 个功能项是能力入口，不各自生成用户旅程 E2E。

TLJ01 是旧的特性旅程标识。当前它映射到 W03 的任务详情片段，不再单独生成一条用户旅程 E2E。TL01–TL06 是本特性的验收判据，保留用于逐项对照。

## 用户路径

### 任务屏

1. Builder 从 Workbench Rail 的「任务」入口进入当前项目或版本范围的任务屏。
2. 任务屏按当前来源显示来源特有的模式、预设、筛选、搜索、新建和刷新控件；Workbench 中不另画一套项目侧栏，项目、版本和工作区沿原生侧栏与版本导航。
3. 列表明确显示任务编号、标题／上下文、负责人或评审人、标签或检查项、状态、更新时间和行操作。读取中、空结果、部分失败、来源不可用和有界结果都要有可理解状态。
4. 点击行进入该来源已有详情；详情返回任务列表时保留来源、筛选、分页和 Workbench 范围。Issue、PR/MR 的可写动作遵循来源规格，不在原型中虚构新的任务正本。

### 链接直达

1. Builder 在原生会话或终端找到完整任务链接。
2. 普通点击显示既有链接动作菜单。Workbench 启用时主项为「在任务中打开」，Ctrl／Cmd 点击直接执行主项。System Browser 继续使用 Shift+Ctrl／Cmd 点击，Orca Browser 作为可用的显式动作。
3. Workbench 按来源主机、完整仓库、任务类型和正整数编号匹配已登记项目，沿本机 `gh` 或 `codehub-cli` 只读任务详情。
4. 身份核对成功后进入已有 Issue、PR 或 MR 详情。关闭详情返回原视图，保留原工作区和会话。
5. 读取失败显示原因和下一步，不自动改走浏览器。用户可以重新点击原链接并显式选择浏览器。

## 匹配与失败边界

- GitHub.com 按完整 `owner/repository` 匹配。GitHub Enterprise 只接受已登记的来源身份，不把任意 `/issues/N` 页面当成 GitHub 任务。
- CodeHub 支持完整项目路径、主机和 `issues/N`、`merge_requests/N` 及 `/-/` 路由。Issue 与 MR 不互相猜测。克隆主机与网页主机不同，只有本机 CLI 的项目元数据证明二者属于同一登记项目时才接受。
- 项目匹配考虑已登记的 `origin` 与 `upstream`，本机副本优先，不按目录名或当前活动项目猜测。
- 编号必须是正安全整数。平台返回的来源、仓库、类型和编号任一不一致，停止打开并提示不一致。
- 未登记项目、缺 CLI、未登录、无权限或读取失败时保留原会话。显式浏览器选择保留原始查询和评论锚点。
- 后一次点击替代尚未完成的任务导航。离开原视图、工作区或会话后，旧结果不能抢回页面。
- 内部打开只读。评论、关闭、重开、评审和合入仍由已有原生动作及人的明确操作负责。

任务屏的来源差异以实现和来源规格为准：CodeHub 的 Issue/MR 列表、详情、评论、关闭、检查项和文件变更见 [CodeHub 规格](../codehub/spec.md#任务页行为)；其他来源不得因静态原型示例而声称已经完成同等写入能力。

## 验收判据

| 标识 | 场景 | 可观察结果 |
| --- | --- | --- |
| TL01 | 终端点击 GitHub Issue／PR | 菜单优先内部动作，详情中的来源、类型和编号与链接一致 |
| TL02 | 原生会话点击 GitHub／CodeHub 任务 | 与终端使用同一主动作，数据沿正确 CLI 来源读取 |
| TL03 | CodeHub Issue／MR 链接 | 完整项目路径和主机一致，Issue 不误开为 MR |
| TL04 | 显式选择系统或内置浏览器 | 原链接、查询和锚点按既有行为打开，任务路由不抢显式选择 |
| TL05 | 仓库未登记、身份不符或 CLI／访问失败 | 给出原因和下一步，不误开当前项目同号任务，不自动克隆或登记 |
| TL06 | 关闭详情并继续会话 | 返回原视图，工作区和会话保持，导航未产生业务写操作 |

## 取舍

复用既有任务屏、任务详情、来源路由和链接动作菜单，只做薄挂载。未登记仓库不走无检出浏览器式详情，因为现有详情需要明确项目上下文；失败时仍可用显式浏览器继续。原型的任务屏布局以当前组件结构为准，示例数据与当前 BW 外壳元数据分开维护。
