# 版本工作区：沿版本组织交付导航与收尾

> 给 Builder、Leader 和产品评审者在判断价值与范围时读。本文只定义为什么做、为谁做；行为见 [spec](spec.md)，技术取舍见 [design](design.md)，认可与证据见 [STATUS](STATUS.md)。用户价值或边界改变时更新，不追加讨论流水。
>
> 状态：设计于 2026-10-20 评审定稿（高保真修订 9，含版本级清理决定；修订 9 仅版本总览改表格周报风格，2026-10-22 人确认）；生产接线与真壳证据见 STATUS。

> 版本总览的用户价值与范围由独立 [版本总览 intent](../version-overview/intent.md) 承接，本特性继续维护版本导航、工作树归属与收尾。

## 用户与问题

[#383](https://github.com/forcegravity1989/builder-workbench/issues/383) 要让 Builder 从项目墙进入项目后，沿“版本 → 计划承诺 → 目标与执行 → 验收结果”组织交付。BW 帮用户判断为什么做、当前为哪版工作、按什么核对成果以及后来如何回看；多个版本可并行，切版不改变原有工作区和会话的归属。

## 价值与依据

新增的是业务导航与关联：版本入口、计划派生的目标目录、原生工作区的版本/目标归属，以及从真实材料汇总的版本总览。用户已确认保留目标目录、目标工作树按需创建；又确认不增加周冻结、生成目录按钮或独立快照协议。目标保存后即可找到，正式承诺沿用人工评审与 PR 合入，后续修改如实区分，不让目录出现冒充定稿。

## 目标体验

计划和验收继续使用现有业务板与 Orca 完整会话区，由原板的简短开始入口发起会话，成功打开后再展示四区，侧栏明确版本后屏内不重复选版。每版两棵固定流程树与入口合并；目标与 Issue 开工复用同一原生创建器，BW 带入版本、目标、交付约定与任务来源，名称和执行选项由 Builder 调整。相关任务可在目标工作区一起做，需要隔离时再分别开工；不新增统一工作树习惯设置，也不因目录结构强制每个 Issue 一棵树。任何已登记绑定树都可见，即使当前没有会话；绑定、改绑与解绑从同一原生右击菜单进入，解绑保留树、父子关系、文件和会话，不要求用户在版本上重复找绑定按钮。

## 范围与边界

项目总览、任务、工作树/父子、agent、自动化、知识库及共享宿主继续复用。保留旧版本材料、原共享树、在跑会话和原生项目工作区的可达性；连接中断时保留原生状态表达和其他导航，不因点一棵断链树丢掉整个版本目录；不以“复用”代替迁移、权限、持久化与重启验证，不承诺 Git 材料能恢复所有聊天。上部围绕当前项目，知识库与版本之间分隔；版本下方统一保留 Orca 原生项目工作区，包括当前项目与私人项目。版本收尾提供版本级清理：版本行删除图标＋与 Orca 同口径的确认对话框，沿原生删除链逐棵删除本版工作树（默认本机 owned），材料与版本目录保留、旧版本默认可收起回看，不设专门历史会话或归档分区。

## 成功判据

成功体验是：用户用现有操作即可形成承诺、进入正确工作区、并行推进版本并按同版依据验收；版本收尾时一次版本级清理即可释放本机磁盘而材料与版本目录保留可回看；无需重复维护目录、任务状态或聊天记录。版本总结从材料与已有归档引用读取，不额外冻结或手填报告。设计依据为 [spec](spec.md)、[高保真修订 9](version-workspace-prototype.html?rev=9) 与 [旅程及数据说明报告](version-workspace-journey.html)。
