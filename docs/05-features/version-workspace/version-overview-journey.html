这一版推荐的取舍

首屏保留版本与计划基本信息，用简明摘要对照承诺和交付，再按大需求展开成果与下一步。试用边界和日常任务各有位置，不用一盏状态灯代表整个 G2。

共同旅程

月度选择 → 先行 B MVP → 部分用户试用 → 后续 B 修理完善 → 后续 Issue 持续改善

  1. 01

    月度选方向，带着需求进入版本

    Leader 在 #440 的项目总览选择两个大需求及投入范围。进入 #334 版本总览后，先核对本版承诺、负责人、时间和计划依据。

    看点：需求完整目标与本 B 版本承担范围分开；G2 是计划目标编号，不是跨版需求身份。

    进入先行 B 总览 →#440 月度选择由另一窗口设计，本页只描述衔接。
  2. 02

    先审成果，让两个大需求各自推进

    #334 的设计正在评审，#440 已进入试用且有设计修订待审。展开任一需求，看意图、spec / 高保真、Plan、PR、测试和试用成果；从待审入口定位具体修订。

    看点：改稿可以返回设计；会话结束不能自动把需求推进到“已交付”。成果和原生工作会话都有明确入口。

    查看成果与待审 →
  3. 03

    MVP 先给部分用户使用

    先行 B 形成可运行、可试用的最小范围，明确谁能用、通过哪个候选包或部署、哪些验证已做、哪些限制仍存在。

    看点：合入代码不等于用户可用；试用反馈不是一次额外的正式版本验收。

    查看试用范围与依据 →试用者、包、部署和验证结果均为演示。
  4. 04

    按周反馈，后续 B 修理完善

    实际使用发现的问题进入 Issue。当前 B 的修理、后续 B 的候选与长期改善分开表达；大需求可以跨 B 版本，必要时跨周，时间主要用于反复握手与使用反馈。

    看点：小需求与 bug 沿原生 workflow，执行中、待处理和已有结果均能追到依据；同一成果不重复登记完成。

    查看后续 B 与日常任务 →v0.9 仅为下一 B 版本示例，不定义新的编号协议。
  5. 05

    人工验收一次，历史保留当时的承诺

    每个 B 版本只有一次正式人工验收。回看旧版，承诺和验收结论固定在当时修订；之后修理、发布、Issue 关闭和目标达成仍各自有据。

    看点：当前编辑不改写历史；历史验收示例只用固定演示归档，不把当前草稿伪装成已认可成果。
