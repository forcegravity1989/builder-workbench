## 人工澄清

### 月度里程碑决定做哪些及优先次序

月度大版本规划主要讨论一个月做哪些大需求、优先级是什么，再结合人数与工作节奏考虑安排。约两周一个大需求、一个月约 2–3 个大需求是讨论背景，容量与项目人数有关，不是固定数量或周期限制。

月度规划可能需要连续 1–3 天讨论。传统流程中理解业务、取舍范围等思考仍然存在，但 Builder 场景淡化了立项会、SA、版本经理等角色和手续，产品无需把它们具象化为角色编制或审批流。

月度讨论不要求提前明确原型、高保真或完整规格；这些具体设计落到 B 版本推进时讨论。项目总览的泳道和工作日历沿 #440 的方向设计，同时需要模型协作制定和调整，单有拖拽画布不足以支撑规划。

### B 版本承接具体交付并及时反馈

B 版本期望按周推进，以便及时交付、反馈和优化；必要时允许一个 B 版本跨周后再验收。用户明确「B 版本就一次验收，不搞多次」。周中的规格、高保真评审与试用反馈按各自用途开展，不复制为多次 B 版本正式验收。

B 版本的意图通常不难讨论，困难集中在具体交付什么：范围、体验和验收标准会反复收敛。周中的 spec、高保真评审因此重要；不能要求所有细节在版本开始前已经完整明确。

大需求在月度里程碑上有截止时间，可以安排在本月第二个 B 版本完成。第一个 B 版本的目标也要跟随大需求节奏：规格、原型、设计需要对齐，原则上 Plan 应接上开发落地，并形成先行 MVP。具体 MVP 范围要通过设计评审确定，不能只按阶段名称切成一个纯文档版本和一个纯编码版本。

### MVP 用真实使用推动需求收敛

MVP 可以先推给一部分用户使用，发现问题后继续修理和打磨。大需求延伸到约两周，核心背景是需求尚不明确时的反复握手，以及第一版 AI 实现后的实际使用问题修理；不能将其归因为 AI Coding 单纯需要两周才能写完代码。

MVP 是可运行、可试用的先行交付。高保真帮助评审体验，实际 MVP 带来真实使用反馈，两者分别提供证据。MVP 的用户范围、交付边界和试用入口在具体需求中明确，不要求一开始全面发布，也不凭先行版本推断整个大需求已经完成。

大需求完成后仍会产生 bug、优化和衍生小需求，以 Issue 承接，由 AI 沿 workflow 持续处理。单人、单日、单会话是日常小需求工作方式的追求，不能据此宣称自动处理能力已经成立。复用现有执行入口和事实源；Issue 关闭、目标达成、合入和发布仍遵循人的权限边界。

### 版本总览保留背景并展示进行中成果

用户已明确：同时呈现已确定的承诺与尚未合入的最新成果、待审事项；版本总览原本的基础信息仍需保留。

基础信息包括版本与目标、负责人、交付范围、已有时间约定、关联任务、计划与验收记录，以及纪要、遗留、归档和发布依据等入口。具体布局和信息优先级通过原型评审，不将现有所有字段机械变成首屏卡片。

当前阶段、成果是否形成、是否经过评审、PR 是否合入、是否供用户使用、Issue 是否关闭和目标是否达成各有依据。会话结束不直接变为完成；没有依据时保持未知或未记录。历史验收保留当时承诺与证据，后续推进不覆盖前版结果。

### 后续通过可见产物继续讨论

用户希望看到具体产物后继续交流，并会组织内部评审批注。本轮已经获得的输入足够开始首轮设计表达，未决细节优先放进可点击原型里比较，不要求通过持续抽象问答一次性定完。

#440 与 #334 都需要规格、高保真评审，后续会衍生小需求。先分别承接两项大需求的设计工作；领域上是否分别构成独立特性、怎样归属现有特性资料，仍按用户目标和现有正本确认，不按两个页面或两个 PR 自动认定。

## 两屏设计衔接

以下是供首轮高保真验证的设计组织建议，尚不作为已确认的界面或协议。

| 设计对象            | 项目总览侧                                          | 版本总览侧                                                 |
| ------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| 月度大需求          | 重点、优先级、大致安排、最终交付的 B 版本和截止时间 | 关联到整体目标，说明当前 B 版本承担的部分                  |
| 先行 MVP 与后续完善 | 让人看见需求经过哪些 B 版本逐步交付                 | 说明本版具体可用增量、当前成果、试用反馈及待处理问题       |
| 规格与高保真评审    | 查看推进情况并进入对应 B 版本                       | 打开当前 spec、高保真、Plan 及评审成果，继续原生会话       |
| 日常小需求与 bug    | 按需了解持续改善与对月度安排的影响                  | 汇总 Issue workflow 执行与处理结果，保留事实来源和必要动作 |

两个窗口共同校准以下关系，界面先使用一致的示例与文案，具体持久化方案留给设计：

- 同一个大需求能够跨 B 版本追踪；整体交付与本 B 版本增量可分别理解，不把版本目标序号直接当作跨版身份。
- 正式承诺、进行中成果和历史结果有清楚来源。未合入成果可见，但不自动覆盖已确认的承诺或历史验收。
- 评审和原生会话的入口能连续跳转；复用现有计划、验收、任务、工作树和会话，避免两屏另维护一份完成状态或执行器。
- 月度大版本、B 版本与实际发布记录的关系，以及具体编号，尚需设计校准；不因「月度」就批量改现有版本名。

## 两窗口交接

| 窗口          | 首轮工作                                                                                                | 共用边界                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| #440 项目总览 | 表达月度选择与优先级、模型协作、泳道和版本安排；保留项目背景与现有指标的适当入口；沿 Issue 探索工作日历 | 只在一处定义大需求与 B 版本的关联含义；基础布局沿 BW 壳与设计系统                  |
| #334 版本总览 | 保留本版基础信息，表达大需求的阶段、可审成果、先行 MVP/使用反馈，以及小需求与 bug 处理结果              | 消费同一组需求和版本关联，沿现有计划/验收和 Issue 事实源组织，明确进行中与历史来源 |

两个窗口均先读本文、对应 Issue 的最新内容和现行特性资料。先形成各自 intent/spec 的本次增量与可点击高保真，再进行内部评审；完整规格的人确认仍在制品上完成。两个开发 PR 可以分别推进，共享对象与导航决定由本统筹会话协调，不并行发明两套关系。

高保真各有独立入口和可编辑来源，共用资源保留一份，遵循仓内原型组织规则。具体特性归属确定后落入对应目录；不为共享原型额外建立一个产品特性。数据为快照或演示的部分直接标明，原型不冒充真实执行。

## 首轮评审与待决问题

首轮用一条连续旅程评审两屏：月度挑选大需求与优先级 → 安排目标 B 版本 → 进入先行 B 版本查看规格/高保真评审与 MVP → 部分用户试用并反馈 → 后续 B 版本修理、完善至大需求约定范围 → 后续 bug/小需求进入 Issue workflow。各 B 版本仍各自一次正式验收；这一演示旅程不改写 v0.8 已归档承诺。

用户先看原型，再组织内部评审批注。批注处理结果收进对应规格：明确采纳的行为、调整后的原型及仍待决的问题；每轮修订继续维护同一份材料，不另养聊天流水。现有批注能力可复用部分先核对，不把新的远程批注系统带入本次。

首轮高保真应暴露以下选择，暂不提前定为协议：

1. 跨 B 版本时，如何同时看懂大需求整体进展和本版交付，且避免信息重复。
2. 阶段与成果关联怎样来自可追溯材料，怎样处理草稿、退回修改、缺数据和尚未合入的成果。
3. 月度讨论如何连续收敛并落到泳道；工作日历输入和版本编号具体怎样表达。
4. MVP 试用反馈怎样回到需求及本版工作，哪些后续问题转为日常 Issue；当前阶段的修理与大需求完成后的持续改善怎样区分。
5. 月度里程碑是否关联效果指标、关联到什么程度。已有指标可作为输入，但用户尚未将「效果证据」确认为每个里程碑的统一验收门槛。
