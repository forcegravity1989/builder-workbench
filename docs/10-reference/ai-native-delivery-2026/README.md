## 先把初心说清楚：BW 的增量价值是什么

这份调研承接“梳理 BW 加持能力的价值”这个问题。它不是要证明 AI Coding 提效，也不是要把 BW 做成另一套项目管理软件；要问的是：**当 Orca、Agent 和现有研发工具已经能帮助 Builder 产出代码时，BW 额外帮助 Builder、共享 SE/Leader 和真实用户完成了什么？**

当前最稳妥的价值假设是：BW 把一个 Builder 的连续责任串起来——为什么做、本轮交付什么、用户是否真的用上、哪里受阻、下一步依据什么取舍——并让共享 SE/Leader 能在需要时看见同一份证据。这个假设只有在真实交付中改变了决定、减少了无效劳动或更早让用户用上时才成立；页面数量、任务完成数和 Agent 活跃度都不能单独证明它成立。

因此，报告中的“项目管理”不是增加审批层，而是检验一条价值链：

`目标与问题 → 本版承诺 → 实际交付与使用 → 证据与未知 → 人的下一步决定`

一周和一个月是帮助观察这条链的两个时间尺度，不是必须新增的管理仪式。周尺度要回答“这周究竟交付了什么、什么阻断了使用”；月尺度要回答“项目对外产生了什么可持续的价值、是否值得继续投入”。两者都必须允许 Unknown，也必须保留人的判断。

## 结合 v0.6 评论后的收敛边界

下面是 owner 对 v0.6 G2 的补充输入，**是产品规划输入，不是本轮调研已经证明的事实，也不是已批准的规格**。它把近期交付和更远的研究问题分开：

| 层次 | 当前应做什么 | 要证明什么 |
|---|---|---|
| v0.6 近期交付 | 收敛项目墙、总览、计划、验收的 BUG 与易用性；验收补周报；让计划与验收形成闭环 | Builder 能否少做重复整理，讲清一周交付与阻断；下一轮范围是否由验收证据真正改变 |
| 月度价值问题 | 观察项目在月粒度上对外产生的商业价值，而不是把任务完成率叫作价值 | 总览/阶段回看能否让 Builder 和 Leader 说清用户或业务发生了什么变化，证据缺口是什么 |
| 更远的牵引假设 | 研究“持续对外呈现价值的牵引功能”是否比“里程碑”更准确 | 它是否会改变投入、范围或找用户的决定；是否值得独立产品能力 |

所以，v0.6 不需要现在就回答长期牵引功能的最终形态；但周报也不能只做一份格式化总结。它应尽量从已有计划、验收和运行/使用证据中整理出“承诺、实际结果、阻断、未知和下一步”，否则只是新增填报。计划—验收闭环的价值也不在于两屏互相跳转，而在于验收结果确实能收敛下一轮承诺。

这条边界也修正本轮原型的定位：它可以讨论周观察、阶段回看和证据回流，但不把它们包装成已经交付的月度商业价值能力，不预设新的里程碑管理器，也不把假设演示当成收益证据。

## 已经对齐的用户问题

v0.5 已交给内部用户使用，这是本轮的用户背景。现在先盘点已有能力：Builder 可能被模型推动着写出大量代码，到周五却讲不清这周交付了什么，几个月后仍没有被用户实际使用的版本。AI Coding 已明显改变设计、实现和测试的成本，不宜继续只研究传统阶段管理。

**用户明确的组织事实：组内五个项目，每个项目只有一位 Builder；多个项目共用一位 SE 和一位 Leader。** 本报告默认“一项目 = 一 Builder = 一个人”。Builder 从用户问题、范围取舍、驾驭 Agent 到交付和反馈，承担连续的项目责任。共享支持不等于每个项目常驻三个人；SE 与 Leader 的具体职责和介入条件仍要结合实际确认。

若项目因规模或特殊能力需要扩为多人，那是后续适用边界，不作为本轮故事和产品设计的默认起点。现行[产品原则 03](../../01-principles/03-press-release-faq-flywheel.md)已以端到端负责的 super builder 为客群；这里修正研究场景，不改写原则，也不新增多人协作产品。

**我们正在检验的命题：** 当一个 Builder 可以让多个 Agent 持续写代码时，他是否仍能掌握“项目为什么做、本轮交付什么、用户用后怎样、下一步如何取舍”？SE/Leader 能否依据同一份材料看清多个项目，及时提供帮助，而不让每个 Builder 再填一套汇报？BW 若能减少失焦和找证据的成本，且没有把一个人的项目变成繁重流程，才有增量价值。

## 这轮研究改变了哪些判断

### 1. 原生工具的边界已向项目与反馈扩展

Cursor 2026-09 的 Projects beta 已包含持久上下文、协调与持续订阅；Linear 把 coding sessions 接到 Issue；WorkBuddy 已有团队项目与计划；Orca 也持续补全任务、执行、审阅和集成路径。因此不能把 BW 的差异建立在“别人只管一段代码”上。[Cursor 官方](https://cursor.com/blog/projects)、[Linear 官方](https://linear.app/changelog/2026-06-11-coding-sessions)、[WorkBuddy 官方](https://cloud.tencent.com/document/product/1831/138797)；细节与状态见对应专题。

这也不是说 BW 一定没有价值。内部仓库兼容、数据能否互相读回、跨次交付能否接续、是否真的减少人的负担，都要单独验证。

### 2. 传统角色的部分动作被压缩，但责任没有随角色一起消失

Anthropic 的企业 playbook 与内部实践不是一条固定流水线：前者给出阶段产物和度量，后者展示原型、已有上下文和按风险处理的方式。Codex 实践重视可执行检查和有证据的修复循环。可以借鉴把上下文、运行和审查结果放到工作对象附近；不能据此要求每个小项目重新走全套文档和审批。[Anthropic 专题](anthropic-sdlc.html)、[Codex 专题](openai-codex.html)

**我们的推论：** 传统产品、设计、开发、测试的许多动作可以由同一位 Builder 借助 Agent 完成，但用户选择、范围取舍、上线质量和结果解释仍需有人负责。默认责任人就是这个 Builder；遇到能力或权限边界时，带具体证据请求共享 SE/Leader 支持。执行可以越来越自主，完成与范围决定仍遵守 BW 的现行人确认规则。

### 3. 真实使用之后的改进值得看，但成熟度必须拆开

Spotify 的上下文与 Agent 执行是已有内部实践；2026-09-30 的 Confidence Loop 则处于设计伙伴早期预览，完整自主改进仍是发展方向。它值得研究的地方，是把真实信号整理成可追溯的问题与下一步，而非看到代码完成就结束。[Confidence Loop 官方](https://confidence.spotify.com/blog/confidence-loop)

**对 BW 的启发：** BUG、卡顿、困惑与反复失败，可以来自同一次实际使用，不必与“产品价值”分成互不关联的工作。先看用户在哪一步失败，再决定本轮做什么；完整实施和效果仍待 BW 试点。

### 4. 提效数字必须分清活动、过程、质量和结果

METR 2026 年研究提醒我们，AI 会改变任务组合；当前任务做得更快，不等于价值同比增加。其五月调查也只是自报结果，不能当作真实交付的因果增益。DORA 提供从目标选择度量的框架，但其 2025 样本不能冒充 2026 新实证。[METR 官方](https://metr.org/blog/2026-05-08-task-substitution-and-uplift/)、[DORA 度量指南](https://dora.dev/research/2025/measurement-frameworks/)

**对 BW 的启发：** PR 数、Agent 数、Token 和计划归档次数可用于诊断采用与过程；仍要另看可用版本、实际用户任务、失败与返工、人投入的注意力。没有数据时保留未知，尤其不能用忙碌程度算出绿灯。

### 5. 周交付、月里程碑可以试，但不能当行业统一答案

现有材料支持更短的反馈等待、可独立验证的增量和明确责任，没有证明每个单 Builder 项目都该采用同一种周/月节奏。可以把周作为检查承诺和阻塞的提醒，把月作为检查方向的提醒；工作一旦可交付，就不必等提醒日才让用户用。[DORA 小批量建议](https://dora.dev/capabilities/working-in-small-batches/)

这是待讨论建议。现行 03 已有通常 1–2 周迭代的表述，本轮不改它；若想引入新的强制周期或放宽现有约束，应先明确要解决的实际问题。

## 一个 Builder 的故事，以及共享 SE/Leader 为什么需要看见它

以下三幕是**围绕 BW 自身重建的假设故事，不是已发生的内部案例或收益证据**。角色始终是负责 BW 项目的同一位 Builder；SE 和 Leader 同时支持其他项目。其他五个项目的名称、进展和风险尚未采集，不在这里虚构。

### 周一：Agent 很忙，但这个版本究竟为了谁

BW v0.5 已给内部用户使用。负责 BW 的 Builder 让 Agent 继续完善总览、指标和计划；模型又建议加更多图表。若只看代码进展，功能不断增加，却还没有回答“一位内部 Builder 能否独立跑完自己的项目交付”。

本轮的候选承诺可以先收成一个可观察结果：约一位真实使用者，用现有 BW 跑一轮交付，找到最先阻断他的地方。负责 BW 的 Builder 据此暂缓新图表，先做能让这轮试用发生的修复。这里要检验的价值，是 BW 能否让原定问题始终可见，使 Builder 有依据拒绝 Agent 的扩展建议；一份短文档若同样有效，也应承认。

### 周中：代码完成了，用户仍然过不去

假设使用者卡在会话续接，Agent 却已经提交了下一项功能。负责 BW 的 Builder 保留实际失败路径、影响和下一次检查点，先修复再请同一位使用者复测。若问题涉及宿主或权限边界，再把具体阻塞交给共享 SE，请他协助判断最小方案；SE 不因此变成这个项目的第二位日常 Builder。

总览若只写“完成了多少任务”，看不见这次交付为何还没发生。候选的最小摘要应让人读出：承诺是什么、用户卡在哪、何时再次核对、需要谁提供什么支持。阻塞出现就处理，周五只是回看窗口。

### 周五与阶段回看：Leader 看五个项目，要作什么决定

同一位 Leader 面对五个由各自 Builder 负责的项目，不可能重读所有 Agent 会话。每个项目应能用自己的证据回答：本轮约定结果是否交到用户、用户问题有何变化、什么仍未知、下一步做什么、是否需要共享支持。不同项目的证据可以不同，不用代码量或完成率给五个人排名。

如果 BW 的修复只让首轮跑通，Builder 应如实说“本轮可用，持续复用与人的负担还未知”。Leader 据此决定继续观察还是调整投入；SE 关注反复出现的技术阻塞。阶段回看再问是否持续解决了值得解决的问题，而不是把四周功能相加当里程碑完成。这是待试点的工作方式，不能宣称当前总览已经具备跨项目汇总能力。

**到内部找故事时，沿同一个 Builder 的一次真实交付追问即可：** 原来要改善什么、Agent 推动新增了什么、用户最后拿到什么、何时发现走偏或受阻、SE/Leader 何时才知道、哪条证据改变了下一步。保留失败、暂停和没有反馈的项目；不要为迎合这个故事补造事实。

## 对照 BW：三条投资线，四块能力都要经得起反证

| 投资线 | 为什么可能值得做 | 首先要拿到的证据 |
|---|---|---|
| Orca 原生使用与适配优化 | 恢复、会话接续、评审、性能直接影响 Builder 完成工作 | 真实工作中卡在哪里；上游已有修复能否解决；移植后的真壳结果 |
| CodeHub 等内部兼容 | 内部团队能否进入真实仓库、评审与交付，是使用前提 | 主路径成功、权限与失败恢复、少掉多少手工搬运 |
| BW 差异化部分 | 可能帮助跨次交付保持目标、识别缺失证据、决定下一步 | 比“原生 Orca + 现有工具”多改变了什么决定，代价是多少 |

前三者不必争同一个故事。原生可靠性与内部兼容的价值可以直接发生在执行过程中；四块新增界面则要证明各自帮助人完成了什么工作。

| 已有部分 | 本轮建议检验的价值 | 应考虑简化的迹象 |
|---|---|---|
| 总览 | Builder 看清自己项目的目标与下一步；共享 SE/Leader 用同一份摘要判断哪些项目需要支持 | 仍需逐个翻会话、追问进度，或要求 Builder 再填一份周报 |
| 指标 | 某条读数确实改变范围、可靠性优先级或继续投入的决定 | 指标很多，却只能说明有人用了工具、完成了一些活动 |
| 计划 | 把本次要解决的问题收小，清楚哪些模型建议暂不做 | 不断拆更多任务，仍没有可让用户试的边界 |
| 验收 | 把实现、运行、部署/分发与真实使用分别核对，并留下下一步 | 只是重述测试通过；失败有记录，却无人处理下一步 |

这些是研究假设，不是新功能清单。先沿现有四块跑一条完整用户旅程；发现问题后，再区分实现 BUG、体验摩擦、数据缺口和产品定义缺口。

目前没有证据证明 BW 的总览、指标、计划和验收四块页面已经让 Builder 成为 super builder，也没有证据证明它们没有价值；下一步要用真实交付中改变的决定和新增负担来判断。

## 下一步：把一个真实项目的故事跑完整

**建议先回看已有五个单 Builder 项目，再从一个项目跑通。** 五个项目来自用户给出的组织背景，不能预设它们都遇到相同问题。先各还原最近一次交付和共享 SE/Leader 当时能看见的信息，再选一个有真实使用者、近期能够交付的项目试用 BW，观察 2–4 周；机制可用后再扩到其余项目。试点项目数与每项目人数是两件事，全程默认每项目一位 Builder。这是探索建议，不是已批准安排或统计显著保证。

每个项目先保留六样东西：目标用户及问题、本次可交付范围、暂不做什么、负责的 Builder、运行/使用证据、下一步。需要共享支持时说明具体请求及下一次检查点，不把每个动作都变成 SE/Leader 的审批。尽量从现有文件、Issue 和会话读回；同时记录 Builder 整理成本，以及 SE/Leader 找背景、判断和介入的成本。

对照两种实际做法：原生 Orca 加现有研发工具，以及同样基础上使用 BW。保留失败与放弃的任务，避免只拿成功案例。比较的重点是：是否更早让用户用上、是否少走无效方向、是否发现错误完成、是否减少人的重复劳动。前后工具和任务变化要注明，不声称小样本因果证明。

试点前不必新增大套埋点或第五块屏幕。先用现有能力和少量观察找出最具体的一处阻塞，再决定是修可靠性、减步骤、补连接还是调整产品定义。若原生工具已足够低成本地支持目标，BW 就应接受合并或删减的可能。

## 仍须与真实项目对齐的问题

- 最近一个项目从“决定做”到“有人用”最久等在哪里：范围、权限、可运行成果、发布、试用还是反馈无人接？
- Builder 被模型推动扩范围时，缺的是判断依据、停下来的动作，还是原先目标本就模糊？
- 一个真实版本已经发出去，却无人使用，谁负责找使用者并改变下一步？BW 能帮多少，哪些属于产品负责人的工作？
- 共享 SE/Leader 查看五个项目时，能否不逐个追问就知道目标、实际进展、证据缺口和需要支持的事项？哪些仍必须面对面讨论？
- 一个 Builder 卡住时，是缺能力、权限、用户接触还是决定？BW 的哪一次提示确实改变了下一步，哪些只增加填报？

这些问题用于检验研究，不预设必须再加功能。

## 给后续模型的接续与维护方式

先读本页的用户问题、仓库线索、未决问题，再读相关专题 Markdown；涉及新决定时打开原始来源核对日期和上下文。厂商推荐、内部自述、实验结果、我们的建议，以及 BW 实际交付是不同层次。不要从截图、原型或这份研究推断产品已实现。

分篇 HTML 共用 `report.css`，通过 `render.mjs` 从本目录 Markdown 生成；独立总报告由 `bundle-report.mjs` 将同一组内容与样式打包进 `report.html`。仓内依赖可用时：

```sh
node docs/10-reference/ai-native-delivery-2026/render.mjs
node docs/10-reference/ai-native-delivery-2026/render.mjs --check
node docs/10-reference/ai-native-delivery-2026/bundle-report.mjs
node docs/10-reference/ai-native-delivery-2026/bundle-report.mjs --check
```

独立工作树没有安装依赖时，可把本机已安装的 `marked/lib/marked.esm.js` 绝对路径作为第一个参数；不把本机路径写进内容正源。修改 Markdown 后再生成 HTML，`--check` 校验投影是否过期；头部 SHA-256 标识对应源文本，不证明事实永远有效。

本目录是外部研究参考。确认后的产品决定按仓内约定进入对应正本；报告不自动成为 `standard/`、模型系统提示或项目执行规则。
