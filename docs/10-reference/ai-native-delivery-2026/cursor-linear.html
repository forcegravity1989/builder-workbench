Cursor 与 Linear：少人团队怎样组织跨会话的 AI 交付

读者与边界：供 1–3 人 Builder 团队及 BW 产品决策者盘点存量价值。主要研究 2025-10-09 至 2026-10-09 的变化，截止与访问日均为 2026-10-09；一项更早的客户反馈机制仅作背景。只研究官方公开机制、自用经验与效果口径，不替代 BW 产品原则或实测。结构为结论、时间线、工作故事、指标、建议、局限与来源；产品状态、证据或内部实验变化时更新。Markdown 为内容正源，同名 HTML 为生成投影。

结论：原生工具已进入项目组织，BW 必须证明增量

【综合判断】 “编码工具负责开发、BW 负责计划和验收”的分工已经不够稳固。Cursor 的 Projects 于 2026-09-10 开始向所有用户推出 beta，面向超过一次聊天的工作；Linear 从已有客户请求与项目关系出发，加入 coding sessions、运行环境及浏览器验证。两者正在压缩上下文搬运、持续调度和验证交接。BW 若仅增加四个页面，容易重复已有信息；候选价值应是减少“等人决定什么、证据在哪里、这次交付是否解决原问题”的成本。S4、S5、S6

【职责事实】 Linear 区分人类 assignee 与 agent delegate：代理执行，指定的人仍负责。Cursor 的协调者与工作者分工也不是取消判断，而是让总体决策少受执行细节干扰。小团队值得抄的是清楚的决定权、可复用上下文和可检查产物；不需要先复制企业组织层级。S10、S2

三条工作故事：步骤压缩了，哪些判断仍在人

故事一：两名 Builder 修复真实客户阻塞

【按已发布机制重建的路径，非实测案例】 客户报告“导出后筛选条件丢失” → 将原始请求关联 issue，写复现条件与期望结果 → 人确认影响和优先级，保留负责人并委派 agent → Linear 会话携带历史、客户请求及讨论，用 Claude Code 或 Codex 产生修改 → 配置环境后运行浏览器旅程，返回差异和前后截图 → 人检查验收、决定发布，再回到原请求确认问题解决。S5、S6、S10

被压缩的是重新解释问题、搭环境、搬运修复与验证结果。人仍需给可复现输入、判断需求是否值得做、处理缺失凭证和环境配置，以及确认测试覆盖真实客户路径。截图证明一次被执行的旅程，不自动证明客户满意或生产环境无回归。

故事二：迁移可以跑三周，但“跑完”不等于可发布

【官方自用实验】 Cursor 一月披露内部 Solid→React 迁移连续超过三周，通过 CI 和初步检查时仍需仔细评审。早期平权 agent 用共享锁协调，20 个 agent 的有效吞吐只剩两三个；去掉锁后又出现回避难题、反复做安全小改的问题。S1

七月研究进一步承认早先浏览器实验远未成为打磨完善的软件；多规划者会形成互不兼容的设计，工作者处理冲突会覆盖或放弃修改。一月移除“集成人”以免形成瓶颈，七月在更大规模研究中又引入中立冲突处理 agent。【判断】 组织办法依赖任务和规模，不宜抄成固定多 agent 流程。S2

九月的 Projects 自用描述已改为与协调者先确定迁移方案，再逐个 PR 推进，早期密切评审；共享文件保存历史，订阅使工作可持续。【小团队应用假设】 一人定义兼容边界，一人验证高风险路径；agent 承担有边界的批次，留下回退条件与未验证项。首个批次不过关就收缩，避免积累一个无人能审的大差异。S4

故事三：跨周继续做什么，从客户请求而非完成数量出发

【产品事实与应用推断】 Linear 早在 2025-04-30 已让客户请求关联项目，并汇总项目下 issue 的客户请求；这是研究窗口前的基础。2026 年项目更新可从上次更新后的 issue、文档、讨论和关联 Slack 生成草稿，由人补判断再发布；initiative 将项目连接到高层目标，并能明确取消。S9、S7、S8

对于三名 Builder：几位试用者都卡在导出 → 聚成一个用户问题 → 本周只改最影响完成任务的环节 → 下周自动整理变化和请求 → 人比较失败率、回访与新增投诉，决定继续或取消。工具支持关联和整理；它没有替团队证明需求规模，也没有把“项目完成”变成“用户问题消失”。若团队只做一个产品，问题→issue→交付证据即可，不必再添 initiative 层。

指标机制：官方数字具体说明了什么

官方证据 样本、口径及限制 对 BW 的启示
Bugbot 报告 78.13% resolution rate S3 50,310 个公开仓库 PR；由 LLM 判断评审评论在合并前是否被处理。不是缺陷召回率、线上事故率或随机对照；未处理也可能是有效但延后修复的建议 记录误报、漏报和处理成本，不能用采纳率替代质量
Linear 自报约 30% 新进入的 bug reports 被其内部自动流程解决，多数首轮成功 S5 未公开样本量、周期、难度分布和解决后的复发；不证明任意团队省下 30% 工时 对比真人介入时间、重开和回归，并保留分母
Projects 声称新用户多合并 30% PR、主要使用者达 6 倍 S4 未给样本、对照和任务规模；熟练用户选择、PR 拆分均可能影响结果 PR 数只能描述活动；另看用户任务成功和返工

【可借鉴机制】 Bugbot 从人的反应、评论和人工评审遗漏中生成候选规则，持续评估后启用，也能降级或由人修改。S3 BW 可借鉴“证据改变后续行为”，但不应让低样本的单次赞同直接固化成规范。

对 1–3 名 Builder 和 BW 的取舍及反证

以下均为待内部验证的建议，不是本次新增功能要求。

已有能力 优先复用、精简或实验 反证：何时应收缩
总览 聚焦现在等人决定的阻塞、待审证据、失联客户问题；从现有 issue/PR 推导 若只重复原生会话列表和状态，新增页面没有增量
计划 只保存本轮要解决的用户问题、选择依据、最小验证及停做条件；任务拆分交执行核 若维护计划耗时超过省下的决策时间，减少字段与周期仪式
验收 将声明、实际执行路径、证据出处和未覆盖范围并排，保留人确认 若只是 agent 自报完成或重复测试日志，不能宣称降低交付风险
指标 区分执行吞吐、质量与用户结果；先选一个真实旅程测失败/重试/返工 没有使用数据时保持未知；数字不能改变下一步取舍就不必常驻

【最小实验】 连续观察两轮真实小交付，用现有 issue/PR 与原生工具作基线，再让 BW 帮同一类任务整理一次。记三项：人补上下文和找证据的时间、评审退回/发布后重开、原问题是否得到用户确认。样本小只判断机制是否有用，不报告统计显著提效。必须同时记手填与维护成本，不能只计生成报告的速度。

【不适用】 不照搬 Cursor 研究中的千级并行、专用版本控制或允许暂时破坏核心构建的实验办法；也不因 Linear 有公司级目标而给小团队加层级。执行环境不足、测试无法访问真实依赖时，先修环境；把待验证项画成绿色没有价值。

局限与未决

这里的可用性来自官方发布与文档，没有登录试用、运行 benchmark 或核验厂商内部数据。研究文章是第一手经验，但不等于独立复现。Projects 仍应按 beta 评估；本文没有找到这十项来源能证明“加计划/总览界面本身提升用户结果”。

仍需 BW 内部回答：用户目前丢失的是原始需求、执行上下文、等待中的决定，还是证据？现有 Orca 能直接承接哪一段？原生产品继续增加项目能力后，BW 能否仍减少一次实际操作？哪个真实案例即使 PR 全部合并仍没有解决用户问题？应先收集这些反例，再决定四块能力如何保留。
