DORA 与 METR：AI 时代怎样区分忙碌、提效与交付价值

读者与时机：供 BW 产品决策者、独立负责项目的 Builder 及共享 SE/Leader 选择试点和度量时阅读。范围：截至 2026-10-09 的一手实证、方法与可迁移建议；优先最近一年，2025 年研究仅作为明确标注的基线。本文不是统一绩效制度、BW 已批准规格或产品效果证明。结构：结论、证据变化、两种工作故事、度量建议、试点、局限与来源。数据或试点结果变化时更新；Markdown 为正源，同名 HTML 为生成阅读版。

先给判断：测量对象也被 AI 改变了

我们的判断： 不能只比较“过去这项开发要三天，现在三小时”。AI 会改变人选择做什么、做多少、允许多少次尝试；更低的成本既可能带来原来做不起的好产品，也可能带来更多不值得做的功能。BW 应帮助 Builder 看见从问题到实际使用的阻塞，并核对增加的产出究竟改变了什么。研究尚不能证明四块屏幕就是最佳实现。

METR 2026 年 5 月明确区分旧任务的提速、新任务组合的提速，以及最终价值增益；三者可以相差很大。这是当前问题最直接的分析工具。它解释了为何“Agent 一天做了原来一个月的活”和“项目两个月仍未交付”可以同时成立。S1

两个工作故事：什么会让判断发生变化

以下为我们的分析示例，不是实验样本或已发生客户案例。

故事一：代码生产很快，但周五仍然没有可用版本

一位 Builder 独立负责内部工单分流项目，SE/Leader 同时支持其他项目。Agent 很快生成分类器、看板、图表和配置页；实际使用仍卡在没有拿到真实工单权限，或者人工分流结果没有基线。此时代码量和任务完成率可以上升，用户节省的时间仍未知。

按本报告建议，下一个交付缩成“取得授权的真实工单样本，让一名值班人员完成一次分流并记录纠错”，先验证是否能减少他的工作。生成了多少附加页面不计作这个目标的进展；若模型建议再做一个管理后台，应回到目标判断是否必要。Builder 先请求共享 SE 协助解决明确的权限阻塞，让 Leader 看见这次交付受阻的原因和下一步。这里需要的是范围取舍、权限解决与用户尝试，不必先建立完整项目管理体系。

DORA 的小批量建议强调可独立交付并获得反馈，特别提醒不要把已拆小的工作又攒成大批次才测试发布。可借鉴的是缩短反馈等待；是否每天、每周或更长，仍取决于使用与部署条件。S6

故事二：多出来的工作不一定浪费，也不一定有价值

一个 Builder 用 Agent 很快补出数据导入诊断工具。原先因为开发昂贵，他会直接让用户发截图；现在新工具可能让每次接入少查一个小时，也可能成为几乎没人打开的维护负担。不能只按“过去手写要两周”记两周收益。

应记录被哪些用户在什么任务里用过、是否减少失败与人工补救，以及维护成本。若暂时只有一个用户，就保存一次完整操作和具体反馈，保留样本数，避免包装成稳定百分比。新能力让原本不可行的服务变得可行也是收益；评价应围绕实际服务，而非执着复刻旧任务组合。这个取舍受 METR 的任务替代理论启发，具体例子与判断方法是我们的建议。S1

给 BW 的四类信号：每个读数服务一个决定

以下是试点建议，不是新增指标协议或统一 KPI。一开始每类只选一项；无法可靠收集的保留 Unknown。小样本同时展示原始事件和分母，不能用综合健康分掩盖缺失。

信号 最小可核对记录 帮助作出的决定 不能替代什么
用户结果 某类目标用户是否完成约定任务；例如 3 位试用者中 2 位完成导入，另 1 位失败原因待核实 继续、改方向、缩范围还是停止投入 单次成功不能证明留存、规模收益或商业价值
交付流动 决定做 → 可运行 → 可访问 → 首次真实使用的时间点；停在哪一段 先解权限、修部署、约试用还是继续写代码 PR 合入时间不能冒充用户用上时间
质量与可靠性 主路径失败、回退、人工补救；BW 自身任务卡死/恢复失败 是否先修可靠性，何时减少并行度 CI 全绿、模型自评通过不能代替真实路径
人的负担与成本 主动干预分钟、等待、重复解释/录入；任务对应模型花费如能获取 BW 是否净省注意力，哪些步骤可省掉 Token、会话数和 Agent 数不是成功指标

时间口径要分开。 “周一到周三的经过时间”“人亲自操作的 40 分钟”和“几个 Agent 合计运行 8 小时”回答不同问题，不能直接相加成工作量。METR 新实验已遇到多代理并行导致人工计时不可靠的问题；工具升级、任务类型和验收标准也应随记录保留。S2

数据和感受可以互证。 日志告诉我们发生了什么，访谈解释为什么；日志也会受采集缺失和解释错误影响。DORA 的度量指南建议先确定要支持的决定，再选框架和数据，而非先把 SPACE、DORA 或 HEART 的所有指标搬进系统。S8

用户导向可以很小。 让 Builder 亲眼看一次用户操作，保存原始反馈，并记录它是否改变下一次取舍，比铺满满意度图表更容易起步。这是对 DORA 用户反馈与产品指标建议的小团队化解释，仍需本地验证。S7

先做怎样的比较，才能决定 BW 四块是否值得保留

先回看用户所在组的五个单 Builder 项目，从一个有具体使用者、能观察结果的项目开始试点，建议观察 2–4 周；这是探索窗口，不是统计功效保证。先还原最近一次交付，记录失败、暂停和放弃，随后在相近工作中比较“原生 Orca 加现有研发工具”和“同样基础上使用 BW”。不要求停用 AI，也不把单纯前后变化当因果效果。

每个项目只钉住一个用户任务、一段可交付范围、一位决定人和一条使用证据。记录 BW 额外花费的时间，并收集它实际改变决定的时刻：删掉了什么、发现了什么错误完成、提前解决了什么等待。共享 SE/Leader 另记录跨项目找背景和提供支持的时间，不能把这些支持藏在 Builder 提效数字外。模型版本、个人熟练度、任务难度都可能混杂；小样本先寻找可重复的机制和反例。

四块能力分别有可被推翻的判断：

  • 总览：是否减少找阻塞和判断下一步的时间；若只是复制会话/Issue 状态，应简化。
  • 指标：是否让人改变决策；若无人能解释读数与行动的关系，先减少指标。
  • 计划：是否帮人收敛本次结果、排除无关扩展；若变成重复填报，应降低负担。
  • 验收：是否发现已合入却不可用、未达用户结果，以及下一步无人负责；若只重复 CI，应重审。

周交付与月里程碑可以作为人的复盘提醒，但不应让已可交付的工作等到周五，也不应把尚无用户证据的功能堆成月底“大版本”。是否将这些建议变成 BW 规则，须回到产品讨论与既有原则。

证据限制与待补项

这组材料没有直接回答“中国内部一项目一 Builder 用了 BW 后会怎样”。METR 的受控任务与自报调查、DORA 的组织研究，均存在场景迁移限制。理论推导不是市场验证，质量和价值也难被单个指标完整表示。

目前最缺的不是再选一套方法论，而是内部真实项目的完整轨迹：最初承诺、最后用户拿到什么、中途为什么扩范围、实际等待在哪里。未来模型应先读这些记录，再判断本报告的建议是否成立。关于 Spotify 的实际上下文、执行和用户实验实践，另见专题报告。
