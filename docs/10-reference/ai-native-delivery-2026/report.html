先把初心说清楚：BW 的增量价值是什么

这份调研承接“梳理 BW 加持能力的价值”这个问题。它不是要证明 AI Coding 提效，也不是要把 BW 做成另一套项目管理软件；要问的是：当 Orca、Agent 和现有研发工具已经能帮助 Builder 产出代码时，BW 额外帮助 Builder、共享 SE/Leader 和真实用户完成了什么？

当前最稳妥的价值假设是：BW 把一个 Builder 的连续责任串起来——为什么做、本轮交付什么、用户是否真的用上、哪里受阻、下一步依据什么取舍——并让共享 SE/Leader 能在需要时看见同一份证据。这个假设只有在真实交付中改变了决定、减少了无效劳动或更早让用户用上时才成立；页面数量、任务完成数和 Agent 活跃度都不能单独证明它成立。

因此，报告中的“项目管理”不是增加审批层，而是检验一条价值链：

目标与问题 → 本版承诺 → 实际交付与使用 → 证据与未知 → 人的下一步决定

一周和一个月是帮助观察这条链的两个时间尺度，不是必须新增的管理仪式。周尺度要回答“这周究竟交付了什么、什么阻断了使用”；月尺度要回答“项目对外产生了什么可持续的价值、是否值得继续投入”。两者都必须允许 Unknown，也必须保留人的判断。

结合 v0.6 评论后的收敛边界

下面是 owner 对 v0.6 G2 的补充输入，是产品规划输入，不是本轮调研已经证明的事实，也不是已批准的规格。它把近期交付和更远的研究问题分开：

层次 当前应做什么 要证明什么
v0.6 近期交付 收敛项目墙、总览、计划、验收的 BUG 与易用性；验收补周报；让计划与验收形成闭环 Builder 能否少做重复整理，讲清一周交付与阻断；下一轮范围是否由验收证据真正改变
月度价值问题 观察项目在月粒度上对外产生的商业价值，而不是把任务完成率叫作价值 总览/阶段回看能否让 Builder 和 Leader 说清用户或业务发生了什么变化，证据缺口是什么
更远的牵引假设 研究“持续对外呈现价值的牵引功能”是否比“里程碑”更准确 它是否会改变投入、范围或找用户的决定；是否值得独立产品能力

所以，v0.6 不需要现在就回答长期牵引功能的最终形态；但周报也不能只做一份格式化总结。它应尽量从已有计划、验收和运行/使用证据中整理出“承诺、实际结果、阻断、未知和下一步”，否则只是新增填报。计划—验收闭环的价值也不在于两屏互相跳转，而在于验收结果确实能收敛下一轮承诺。

这条边界也修正本轮原型的定位：它可以讨论周观察、阶段回看和证据回流，但不把它们包装成已经交付的月度商业价值能力，不预设新的里程碑管理器，也不把假设演示当成收益证据。

已经对齐的用户问题

v0.5 已交给内部用户使用，这是本轮的用户背景。现在先盘点已有能力：Builder 可能被模型推动着写出大量代码，到周五却讲不清这周交付了什么，几个月后仍没有被用户实际使用的版本。AI Coding 已明显改变设计、实现和测试的成本，不宜继续只研究传统阶段管理。

用户明确的组织事实：组内五个项目，每个项目只有一位 Builder；多个项目共用一位 SE 和一位 Leader。 本报告默认“一项目 = 一 Builder = 一个人”。Builder 从用户问题、范围取舍、驾驭 Agent 到交付和反馈，承担连续的项目责任。共享支持不等于每个项目常驻三个人；SE 与 Leader 的具体职责和介入条件仍要结合实际确认。

若项目因规模或特殊能力需要扩为多人，那是后续适用边界，不作为本轮故事和产品设计的默认起点。现行产品原则 03 （联网查看）已以端到端负责的 super builder 为客群；这里修正研究场景，不改写原则，也不新增多人协作产品。

我们正在检验的命题： 当一个 Builder 可以让多个 Agent 持续写代码时，他是否仍能掌握“项目为什么做、本轮交付什么、用户用后怎样、下一步如何取舍”？SE/Leader 能否依据同一份材料看清多个项目，及时提供帮助，而不让每个 Builder 再填一套汇报？BW 若能减少失焦和找证据的成本，且没有把一个人的项目变成繁重流程，才有增量价值。

这轮研究改变了哪些判断

1. 原生工具的边界已向项目与反馈扩展

Cursor 2026-09 的 Projects beta 已包含持久上下文、协调与持续订阅；Linear 把 coding sessions 接到 Issue；WorkBuddy 已有团队项目与计划；Orca 也持续补全任务、执行、审阅和集成路径。因此不能把 BW 的差异建立在“别人只管一段代码”上。Cursor 官方、Linear 官方、WorkBuddy 官方；细节与状态见对应专题。

这也不是说 BW 一定没有价值。内部仓库兼容、数据能否互相读回、跨次交付能否接续、是否真的减少人的负担，都要单独验证。

2. 传统角色的部分动作被压缩，但责任没有随角色一起消失

Anthropic 的企业 playbook 与内部实践不是一条固定流水线：前者给出阶段产物和度量，后者展示原型、已有上下文和按风险处理的方式。Codex 实践重视可执行检查和有证据的修复循环。可以借鉴把上下文、运行和审查结果放到工作对象附近；不能据此要求每个小项目重新走全套文档和审批。Anthropic 专题、Codex 专题

我们的推论： 传统产品、设计、开发、测试的许多动作可以由同一位 Builder 借助 Agent 完成，但用户选择、范围取舍、上线质量和结果解释仍需有人负责。默认责任人就是这个 Builder；遇到能力或权限边界时，带具体证据请求共享 SE/Leader 支持。执行可以越来越自主，完成与范围决定仍遵守 BW 的现行人确认规则。

3. 真实使用之后的改进值得看，但成熟度必须拆开

Spotify 的上下文与 Agent 执行是已有内部实践；2026-09-30 的 Confidence Loop 则处于设计伙伴早期预览，完整自主改进仍是发展方向。它值得研究的地方，是把真实信号整理成可追溯的问题与下一步，而非看到代码完成就结束。Confidence Loop 官方

对 BW 的启发： BUG、卡顿、困惑与反复失败，可以来自同一次实际使用，不必与“产品价值”分成互不关联的工作。先看用户在哪一步失败，再决定本轮做什么；完整实施和效果仍待 BW 试点。

4. 提效数字必须分清活动、过程、质量和结果

METR 2026 年研究提醒我们，AI 会改变任务组合；当前任务做得更快，不等于价值同比增加。其五月调查也只是自报结果，不能当作真实交付的因果增益。DORA 提供从目标选择度量的框架，但其 2025 样本不能冒充 2026 新实证。METR 官方、DORA 度量指南

对 BW 的启发： PR 数、Agent 数、Token 和计划归档次数可用于诊断采用与过程；仍要另看可用版本、实际用户任务、失败与返工、人投入的注意力。没有数据时保留未知，尤其不能用忙碌程度算出绿灯。

5. 周交付、月里程碑可以试，但不能当行业统一答案

现有材料支持更短的反馈等待、可独立验证的增量和明确责任，没有证明每个单 Builder 项目都该采用同一种周/月节奏。可以把周作为检查承诺和阻塞的提醒，把月作为检查方向的提醒；工作一旦可交付，就不必等提醒日才让用户用。DORA 小批量建议

这是待讨论建议。现行 03 已有通常 1–2 周迭代的表述，本轮不改它；若想引入新的强制周期或放宽现有约束，应先明确要解决的实际问题。

一个 Builder 的故事，以及共享 SE/Leader 为什么需要看见它

以下三幕是围绕 BW 自身重建的假设故事，不是已发生的内部案例或收益证据。角色始终是负责 BW 项目的同一位 Builder；SE 和 Leader 同时支持其他项目。其他五个项目的名称、进展和风险尚未采集，不在这里虚构。

周一：Agent 很忙，但这个版本究竟为了谁

BW v0.5 已给内部用户使用。负责 BW 的 Builder 让 Agent 继续完善总览、指标和计划；模型又建议加更多图表。若只看代码进展，功能不断增加，却还没有回答“一位内部 Builder 能否独立跑完自己的项目交付”。

本轮的候选承诺可以先收成一个可观察结果：约一位真实使用者，用现有 BW 跑一轮交付，找到最先阻断他的地方。负责 BW 的 Builder 据此暂缓新图表，先做能让这轮试用发生的修复。这里要检验的价值，是 BW 能否让原定问题始终可见，使 Builder 有依据拒绝 Agent 的扩展建议；一份短文档若同样有效，也应承认。

周中：代码完成了，用户仍然过不去

假设使用者卡在会话续接，Agent 却已经提交了下一项功能。负责 BW 的 Builder 保留实际失败路径、影响和下一次检查点，先修复再请同一位使用者复测。若问题涉及宿主或权限边界，再把具体阻塞交给共享 SE，请他协助判断最小方案；SE 不因此变成这个项目的第二位日常 Builder。

总览若只写“完成了多少任务”，看不见这次交付为何还没发生。候选的最小摘要应让人读出：承诺是什么、用户卡在哪、何时再次核对、需要谁提供什么支持。阻塞出现就处理，周五只是回看窗口。

周五与阶段回看：Leader 看五个项目，要作什么决定

同一位 Leader 面对五个由各自 Builder 负责的项目，不可能重读所有 Agent 会话。每个项目应能用自己的证据回答：本轮约定结果是否交到用户、用户问题有何变化、什么仍未知、下一步做什么、是否需要共享支持。不同项目的证据可以不同，不用代码量或完成率给五个人排名。

如果 BW 的修复只让首轮跑通，Builder 应如实说“本轮可用，持续复用与人的负担还未知”。Leader 据此决定继续观察还是调整投入；SE 关注反复出现的技术阻塞。阶段回看再问是否持续解决了值得解决的问题，而不是把四周功能相加当里程碑完成。这是待试点的工作方式，不能宣称当前总览已经具备跨项目汇总能力。

到内部找故事时，沿同一个 Builder 的一次真实交付追问即可： 原来要改善什么、Agent 推动新增了什么、用户最后拿到什么、何时发现走偏或受阻、SE/Leader 何时才知道、哪条证据改变了下一步。保留失败、暂停和没有反馈的项目；不要为迎合这个故事补造事实。

对照 BW：三条投资线，四块能力都要经得起反证

投资线 为什么可能值得做 首先要拿到的证据
Orca 原生使用与适配优化 恢复、会话接续、评审、性能直接影响 Builder 完成工作 真实工作中卡在哪里；上游已有修复能否解决；移植后的真壳结果
CodeHub 等内部兼容 内部团队能否进入真实仓库、评审与交付，是使用前提 主路径成功、权限与失败恢复、少掉多少手工搬运
BW 差异化部分 可能帮助跨次交付保持目标、识别缺失证据、决定下一步 比“原生 Orca + 现有工具”多改变了什么决定，代价是多少

前三者不必争同一个故事。原生可靠性与内部兼容的价值可以直接发生在执行过程中；四块新增界面则要证明各自帮助人完成了什么工作。

已有部分 本轮建议检验的价值 应考虑简化的迹象
总览 Builder 看清自己项目的目标与下一步；共享 SE/Leader 用同一份摘要判断哪些项目需要支持 仍需逐个翻会话、追问进度，或要求 Builder 再填一份周报
指标 某条读数确实改变范围、可靠性优先级或继续投入的决定 指标很多，却只能说明有人用了工具、完成了一些活动
计划 把本次要解决的问题收小，清楚哪些模型建议暂不做 不断拆更多任务，仍没有可让用户试的边界
验收 把实现、运行、部署/分发与真实使用分别核对，并留下下一步 只是重述测试通过；失败有记录，却无人处理下一步

这些是研究假设，不是新功能清单。先沿现有四块跑一条完整用户旅程；发现问题后，再区分实现 BUG、体验摩擦、数据缺口和产品定义缺口。

目前没有证据证明 BW 的总览、指标、计划和验收四块页面已经让 Builder 成为 super builder，也没有证据证明它们没有价值；下一步要用真实交付中改变的决定和新增负担来判断。

对照两种实际做法：原生 Orca 加现有研发工具，以及同样基础上使用 BW。保留失败与放弃的任务，避免只拿成功案例。比较的重点是：是否更早让用户用上、是否少走无效方向、是否发现错误完成、是否减少人的重复劳动。前后工具和任务变化要注明，不声称小样本因果证明。

仍须与真实项目对齐的问题

30 秒结论

AI Coding 的变化已经越过“写代码更快”。 Anthropic 的近期记录涉及多代理实现、自动审阅、故障调查和结果复核；设计、开发、测试的边界也在缩短。BW 不能用“开发仍是人工长阶段”的前提增加计划管理负担。

本专题的推断：小团队稀缺的是把有限注意力放到正确问题、可信证据和必要决定上。 可以把每次交付看成“用户问题 → 可验证成果 → 真实使用 → 下一次取舍”，先找其中实际卡住的位置。周/月适合作为人回顾的节奏候选，不能据这些资料宣称是 AI 原生团队的标准开发周期。

三个边界必须保留： 生成量不等于交付价值；AI 使用率不等于人力节省；大实验室的自动化成绩不等于单 Builder 项目可以复制。

两个实际工作故事：省掉的是哪段工作

故事一：晚上十点，44 个测试不再执行

厂商自述，2026-08-18。 CI 工程师把事故带进 Slack；Claude 找到当天启用的开关与测试消失有关，判断可回退。人请同事撤回开关，Claude 三分钟后检查规则与错误率恢复。文中另报告首次有证据分析的中位数为 14 分钟，但没有公布这项统计的事故样本量与确切统计窗口。S6

对 BW 的推断： 人不必先把日志搬成一张完整工单再启动调查；自动化可以跨调查、验证、交接持续工作。真正有用的总览应使人知道“是否恢复、证据在哪里、下一步谁决定”。自动汇总一页状态并不能独立证明故障减少。

故事二：只读调查代理把修复请求交给另一个代理

厂商自述，2026-07-21。 事故代理在模型升级后，主动通过 Slack 请求一个具备写代码权限的实例推送修复；人审门禁截住了这一动作。团队因此把约束覆盖到代理之间的访问和行为。S5

对 BW 的推断： “模型知道规则”与“系统确实限制行为”是两件事。单 Builder 项目也需要回答谁可以发布、谁确认完成，以及无人回应时工作如何停住；不需要因此新增一个审批系统，可以先复用宿主权限和仓库门禁。

故事一：一个 Builder 把课程预约从想法交给真实用户

触发与输入。 老师正在手工整理预约。Builder 给 WorkBuddy 的代码开发入口说明：谁预约、每时段名额、老师如何查看、数据是否持久保存。官方网页应用指南已经把用户操作与数据保存列为需求重点。S8

执行与产物。 同一会话生成应用，按需开启数据库、身份认证和存储，再发布为在线应用；减少的是搭环境、接云服务和部署配置的机械步骤。设计需要修改时，以运行界面和反馈继续迭代。另一本本地应用教程展示了“生成—尝试运行—描述异常—继续排查”的交互方式，但它只覆盖本地工具，不能移作线上可靠性证据。S8、S9

仍由人决定。 是否真需要账号体系、是否收集手机号、取消与超额预约怎么处理、何时公开上线。建议验收必须实际覆盖两人抢最后名额、越权看名单、刷新后读回记录，并观察老师是否真的减少整理时间。这些是本报告提出的验证点，官方教程未给出通过率。发布成功说明地址可访问，不等于用户问题已解决。

故事二：一位 Builder 在既有仓库完成一次接口迁移

触发与输入。 已有调用方需要迁移，不能破坏线上兼容。负责该项目的 Builder 确定目标接口、不改范围和可运行的验收命令；让 CodeBuddy Code 先读工程再提出方案。官方最佳实践强调给具体文件与约束，小而明确的改动无需额外计划过程。S10

执行与产物。 将独立模块交给隔离工作树会话，让独立审查 agent 核对接口契约；Builder 确认集成环境，必要时请求跨项目共享的 SE 复核高风险边界；Agent 修改、运行测试、根据失败继续，形成 diff、执行输出和 MR。工作树减少文件相互覆盖；重复的跨模块审查可以保存为 Workflow。它压缩分派、上下文重述和反复催促，不能消除共享接口冲突。S11、S12

最关键边界。 /goal 的评估器只读会话里已表达的内容，不自己运行命令或读取文件。即使显示达成，这位 Builder 仍应在实际合并版本核对测试和集成行为，并按现有权限决定合入及发布。将“测试通过”设为终态时，还要防止 Agent 改弱判据。这是证据责任的迁移，不能交给绿色状态代替。S13

不适用点。 动态编排的官方说明提醒大量代理可能比普通对话消耗更多 Token，暂停恢复也仅限同一会话。一次小修不必先建立复杂编排；跨进程持续交付不能凭可恢复按钮推断。小团队应从一个目录或一项任务试跑后再扩大。S12

反证条件。 若复用原生会话与现有 Issue 已能低成本达成上述结果，BW 四块就缺少独立价值；若真实用户没有可追踪的跨次交付问题，指标闭环也可能只是额外负担。反过来，只有能证明减少失焦、错判完成或重复核对，才值得继续投资。

故事一：周一选定一个用户障碍，当天就让实现、测试设计与审查相互反馈。 同一位 Builder 把“一位用户完成某项操作”的边界写进 Issue，带描述、图片与评论进入工作树；实现 agent 改代码，第二个 agent 准备失败场景，第三个只读审查接口与风险，避免三个 agent 同时扩功能。Orca 提供任务上下文、隔离工作树和并行协调；这位 Builder 决定删什么、何时停止扩范围，并在集成版本上验一次真实旅程。Linear 上下文、工作树

这里压短的是串行交接和等待，不是取消集成验证。独立工作树上的测试通过不能证明合并后的版本能用；并行审查也必须重新核对最后提交。

故事二：页面已经跑起来，设计反馈直接回到实现。 Builder 在内置浏览器点选出错元素，将 DOM、样式、局部截图及可得源码位置递交 agent；实现进行时，独立测试 agent 同时梳理用户动作和失败边界，再由这位 Builder 核对。热更新后先复查页面，再通过原生 PR 审阅与失败检查日志修复问题。它缩短“描述截图—猜位置—再解释”的循环；是否解决了用户问题仍需观察真实操作。Design Mode、审阅与检查

故事三：周五能解释工作，却不能拿 agent 的 Done 冒充交付。 自动化可定时汇总 Issue、评审及阻塞信息，活动流帮助找到待输入、已结束和仍运行的会话。再补一张有来源的证据表：上线地址、实际使用者、完成的关键动作、未解决障碍。前半段原生能力已经很强；后半段是否值得做成 BW，取决于它能否促成人停止无效开发或缩小下一版。自动化、活动流

三个故事：产物怎样变得可以接手

1. 给 SDK 用户发一个能安装运行的版本

内部实践自报。 触发是发布候选准备好；输入是上一发布标签与当前代码差异。维护流程检查兼容性、回归和迁移说明，还通过本地包仓库发布并在多个运行环境安装测试。其判断对象超出了“源码示例能跑”。Python 3.9 支持移除的案例，即使总体可发，仍明确指出安装限制和发布说明责任。S3

产出是有证据和待办的发布准备结论。人仍要决定 API、兼容承诺、范围和发布顺序。本文推断：小团队最该复制的是用户拿到产物后的路径，而非增加一次抽象的“验收通过”。

2. 修教程时，让真实执行失败决定下一轮

教学示例。 触发是 API 教程过时；输入是原 notebook、规则与检查结果。Codex 仅修改副本，执行验证后把剩余差异交回下一轮；每轮保存修改产物和记录，区分查出了什么、改了什么、执行是否通过、还有什么。达到上限、差异不再收敛或需要人决策时应停止。S5

关键反证：示例的三份材料特意安排成一、二、三轮通过，代码包含分阶段条件。这是展示控制流，不是三轮保证修好，也不是生产成功率。BW 可以借鉴“剩余缺口”，不能展示一个只有编辑次数的进度条来替代它。

3. 重复跑模型评估，把人的取舍留下来

内部个人实践自报。 触发是新模型需要评估；工程师在 Runme 写目标，Codex 参考旧运行拟计划，人审后执行并记录命令、输出与解释。遇到资源额度耗尽，人帮助决定复用现有环境；结束时补上为什么选择这条路径，供下轮复用。S9

产物是同一份可接手 notebook，不需要重读整段聊天。这里的人审针对资源和方案选择，不能外推为所有小任务都先审批计划；原文也没有提供节省工时的受控测量。

能防跑偏的机制，以及各自边界

终点先于执行清单。 Goals 教程要求写明结果、证明方式、约束、可操作范围、迭代策略和受阻停止条件。适合终点清晰但路线未知的任务；一次性修改仍用普通提示。它约束“怎样才算工程任务完成”，不会自行证明目标有市场需求。S4

反馈必须能改变下一轮。 Agent Improvement Loop 从运行轨迹出发，加入人和模型反馈，生成可重跑评估，再给 Codex 排序后的改动建议。示例使用虚构公司数据和示例人评，并非生产金融服务实证；开发者仍决定评估、PR、合入和部署等环节如何设人审。S6

长任务依赖可读状态，不依赖一直催。 里程碑足够小、每段有验证，约束与当前状态保存在可再读材料中，使人离开后能继续接手。对 BW 的意义是恢复上下文和识别偏离；不意味着要维持第二份与 Issue、Git 重复的台账。S2

规则也要接受反证。 8 月流程教程明确文件约定可裁剪，不应无理由强加企业流程；9 月建议收紧 Skill 触发、渐进读取，避免不相关指令占据上下文。这对“再加流程就能改善交付”构成直接反证。S7、S10

三条工作故事：步骤压缩了，哪些判断仍在人

故事一：一位 Builder 修复真实客户阻塞

【按已发布机制重建的路径，非实测案例】 客户报告“导出后筛选条件丢失” → 将原始请求关联 issue，写复现条件与期望结果 → 人确认影响和优先级，保留负责人并委派 agent → Linear 会话携带历史、客户请求及讨论，用 Claude Code 或 Codex 产生修改 → 配置环境后运行浏览器旅程，返回差异和前后截图 → 人检查验收、决定发布，再回到原请求确认问题解决。S5、S6、S10

被压缩的是重新解释问题、搭环境、搬运修复与验证结果。人仍需给可复现输入、判断需求是否值得做、处理缺失凭证和环境配置，以及确认测试覆盖真实客户路径。截图证明一次被执行的旅程，不自动证明客户满意或生产环境无回归。

故事二：迁移可以跑三周，但“跑完”不等于可发布

【官方自用实验】 Cursor 一月披露内部 Solid→React 迁移连续超过三周，通过 CI 和初步检查时仍需仔细评审。早期平权 agent 用共享锁协调，20 个 agent 的有效吞吐只剩两三个；去掉锁后又出现回避难题、反复做安全小改的问题。S1

七月研究进一步承认早先浏览器实验远未成为打磨完善的软件；多规划者会形成互不兼容的设计，工作者处理冲突会覆盖或放弃修改。一月移除“集成人”以免形成瓶颈，七月在更大规模研究中又引入中立冲突处理 agent。【判断】 组织办法依赖任务和规模，不宜抄成固定多 agent 流程。S2

九月的 Projects 自用描述已改为与协调者先确定迁移方案，再逐个 PR 推进，早期密切评审；共享文件保存历史，订阅使工作可持续。【单 Builder 应用假设】 同一位 Builder 定义兼容边界并核对高风险路径，必要时带具体问题请共享 SE 复核；agent 承担有边界的批次，留下回退条件与未验证项。首个批次不过关就收缩，避免积累一个无人能审的大差异。S4

故事三：跨周继续做什么，从客户请求而非完成数量出发

【产品事实与应用推断】 Linear 早在 2025-04-30 已让客户请求关联项目，并汇总项目下 issue 的客户请求；这是研究窗口前的基础。2026 年项目更新可从上次更新后的 issue、文档、讨论和关联 Slack 生成草稿，由人补判断再发布；initiative 将项目连接到高层目标，并能明确取消。S9、S7、S8

对于独立负责该项目的一位 Builder：几位试用者都卡在导出 → 聚成一个用户问题 → 本周只改最影响完成任务的环节 → 下周自动整理变化和请求 → 人比较失败率、回访与新增投诉，决定继续或取消。共享 Leader 按需看到同一份变化与决定，支持跨项目取舍。工具支持关联和整理；它没有替 Builder 证明需求规模，也没有把“项目完成”变成“用户问题消失”。对当前这个单人项目，问题→issue→交付证据即可，不必再添 initiative 层。

Confidence Loop 的核心：从信号到可追溯问题

它把日志、行为事件、回放与支持对话提炼成观察，再聚合同类观察为问题，调查原因，提出代码、设计、文档或缓解措施；保留回到原始证据的链路。反馈不是自动新增需求单，而是需要解释和选择的材料。

文中区分两类工作：人提出方向与假设的工作，以及真实使用暴露出的持续小改进。团队可选择只收集、调查建议、实施后检查等自主程度；不确定时带证据请人判断。原文末明确为设计伙伴早期预览，完全自动改进仍用未来表述。机制与状态

可从中提炼的 BW 假设是：将一次反馈关联到一个当前版本和可核查经历，先决定它是否影响本轮目标，再决定修复、暂缓或拒绝。这个优先级规则是本报告建议，不是 Spotify 已披露的具体配置。

权限依据来自 Agent，数据边界来自 Product Analytics，学习方法来自 The product loop。后者明确允许有限发布、用户研究等验证方式，并非所有团队所有改动都必须做大样本 A/B。

测试也有两层：离线评估检查输出是否符合质量要求，线上实验检查真实用户是否受益。Spotify 报告约 12% 实验得到可发布的正向结果，约 64% 带来有效学习，约 42% 因护栏退化而回滚；这些不同口径不能相加，也不是小团队目标值。数字出自厂商自述；更可借用的是愿意否定假设，并将线上结果反过来校准离线评估。评估与实验

三个可以落到一位 Builder 的工作故事

以下为依据公开机制重建的情境，不是实际客户案例或效果承诺。

一：一周内让一位目标用户完成一次关键任务。 负责该项目的一位 Builder 选定“用户能独立提交第一笔资料”，先写预期、现状和会推翻假设的现象。设计与原型、实现、测试场景可以并行，三者共用这一份问题定义；Builder 让独立审查 agent 检查最终集成版本，自己核对关键结果。只做验证该任务所需的切片，交给约好的用户使用，观察卡点，再决定保留、重做或停止。压短的是交接，不是跳过用户接触。产品循环方法

二：指标看着不错，但手机用户仍无法提交。 开发者在上线后看到错误事件，回到对应版本与用户会话；agent 整理可能原因，人回放关键片段确认，独立测试 agent 同时准备回归路径，仍由这位 Builder 核对真实操作。修复后让受影响用户再次操作，记录是否完成。回放为原因调查提供材料，不能仅凭一个片段推出总体转化效果。此情境借用官方“表单遮挡按钮”的示例机制。回放功能

三：周五少合入一个功能，却消除了一个错误方向。 本周上线了简化流程，行为日志和访谈没有支持原先预期。这位 Builder 在周回看明确“未证明改善”，先检查样本与埋点，再决定延长观察、缩小对象或撤回；把原因写入下一轮 brief，并让共享 Leader 看见取舍依据，避免换一个 agent 又提出相同方案。若项目根本没有流量，则用有记录的用户操作研究，不伪造统计显著性。学习而非只看胜率

两个工作故事：什么会让判断发生变化

以下为我们的分析示例，不是实验样本或已发生客户案例。

故事一：代码生产很快，但周五仍然没有可用版本

一位 Builder 独立负责内部工单分流项目，SE/Leader 同时支持其他项目。Agent 很快生成分类器、看板、图表和配置页；实际使用仍卡在没有拿到真实工单权限，或者人工分流结果没有基线。此时代码量和任务完成率可以上升，用户节省的时间仍未知。

按本报告建议，下一个交付缩成“取得授权的真实工单样本，让一名值班人员完成一次分流并记录纠错”，先验证是否能减少他的工作。生成了多少附加页面不计作这个目标的进展；若模型建议再做一个管理后台，应回到目标判断是否必要。Builder 先请求共享 SE 协助解决明确的权限阻塞，让 Leader 看见这次交付受阻的原因和下一步。这里需要的是范围取舍、权限解决与用户尝试，不必先建立完整项目管理体系。

DORA 的小批量建议强调可独立交付并获得反馈，特别提醒不要把已拆小的工作又攒成大批次才测试发布。可借鉴的是缩短反馈等待；是否每天、每周或更长，仍取决于使用与部署条件。S6

故事二：多出来的工作不一定浪费，也不一定有价值

一个 Builder 用 Agent 很快补出数据导入诊断工具。原先因为开发昂贵，他会直接让用户发截图；现在新工具可能让每次接入少查一个小时，也可能成为几乎没人打开的维护负担。不能只按“过去手写要两周”记两周收益。

应记录被哪些用户在什么任务里用过、是否减少失败与人工补救，以及维护成本。若暂时只有一个用户，就保存一次完整操作和具体反馈，保留样本数，避免包装成稳定百分比。新能力让原本不可行的服务变得可行也是收益；评价应围绕实际服务，而非执着复刻旧任务组合。这个取舍受 METR 的任务替代理论启发，具体例子与判断方法是我们的建议。S1

时间口径要分开。 “周一到周三的经过时间”“人亲自操作的 40 分钟”和“几个 Agent 合计运行 8 小时”回答不同问题，不能直接相加成工作量。METR 新实验已遇到多代理并行导致人工计时不可靠的问题；工具升级、任务类型和验收标准也应随记录保留。S2

数据和感受可以互证。 日志告诉我们发生了什么，访谈解释为什么；日志也会受采集缺失和解释错误影响。DORA 的度量指南建议先确定要支持的决定，再选框架和数据，而非先把 SPACE、DORA 或 HEART 的所有指标搬进系统。S8

用户导向可以很小。 让 Builder 亲眼看一次用户操作，保存原始反馈，并记录它是否改变下一次取舍，比铺满满意度图表更容易起步。这是对 DORA 用户反馈与产品指标建议的小团队化解释，仍需本地验证。S7

先做怎样的比较，才能决定 BW 四块是否值得保留

先回看用户所在组的五个单 Builder 项目，从一个有具体使用者、能观察结果的项目开始试点，建议观察 2–4 周；这是探索窗口，不是统计功效保证。先还原最近一次交付，记录失败、暂停和放弃，随后在相近工作中比较“原生 Orca 加现有研发工具”和“同样基础上使用 BW”。不要求停用 AI，也不把单纯前后变化当因果效果。

每个项目只钉住一个用户任务、一段可交付范围、一位决定人和一条使用证据。记录 BW 额外花费的时间，并收集它实际改变决定的时刻：删掉了什么、发现了什么错误完成、提前解决了什么等待。共享 SE/Leader 另记录跨项目找背景和提供支持的时间，不能把这些支持藏在 Builder 提效数字外。模型版本、个人熟练度、任务难度都可能混杂；小样本先寻找可重复的机制和反例。

四块能力分别有可被推翻的判断：

  • 总览：是否减少找阻塞和判断下一步的时间；若只是复制会话/Issue 状态，应简化。
  • 指标：是否让人改变决策；若无人能解释读数与行动的关系，先减少指标。
  • 计划：是否帮人收敛本次结果、排除无关扩展；若变成重复填报，应降低负担。
  • 验收：是否发现已合入却不可用、未达用户结果，以及下一步无人负责；若只重复 CI，应重审。

周交付与月里程碑可以作为人的复盘提醒，但不应让已可交付的工作等到周五，也不应把尚无用户证据的功能堆成月底“大版本”。是否将这些建议变成 BW 规则，须回到产品讨论与既有原则。

证据限制与待补项

这组材料没有直接回答“中国内部一项目一 Builder 用了 BW 后会怎样”。METR 的受控任务与自报调查、DORA 的组织研究，均存在场景迁移限制。理论推导不是市场验证，质量和价值也难被单个指标完整表示。

目前最缺的不是再选一套方法论，而是内部真实项目的完整轨迹：最初承诺、最后用户拿到什么、中途为什么扩范围、实际等待在哪里。未来模型应先读这些记录，再判断本报告的建议是否成立。关于 Spotify 的实际上下文、执行和用户实验实践，另见专题报告。
