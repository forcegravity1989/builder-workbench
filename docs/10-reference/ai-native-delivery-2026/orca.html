结论：Orca 已超出写代码，结果约束仍需要人

Orca 已是围绕 agent 的开发工作环境，覆盖任务来源、并行执行、运行预览、审阅和合入。 官方面向会读 diff、管理提交的开发者，而非无代码用户；因此“Builder 有 Orca，只剩开发提效，其他都薄弱”不是可靠前提。官方定位

从任务板、自动化、跨机工作和恢复机制的扩展看，产品正在争取整个开发工作台；这是根据公开演进作出的判断，不是官方公布的商业路线图。原生工具能让有边界的工作更快完成，但本次未找到它默认保证“本周只交付这一小块、已有真实用户使用、下一周依据效果收缩方向”的证据。

对“写了两三个月仍无线上版本”的用户，BW 应验证的主张是：让一个小版本按期进入真实使用，并让使用证据改变下一轮取舍。 四块界面只有共同缩短这条链路才有价值。一个必须认真比较的对照方案是“原生 Orca＋现有 Issue 系统＋一份交付约定和周回顾 Skill”，不能预设它不够用。

三个可重建的 2026 工作故事

以下是以官方能力拼成的工作方式，不是客户案例，也没有实测提效倍数。

故事一：周一选定一个用户障碍，当天就让实现、测试设计与审查相互反馈。 负责人把“一位用户完成某项操作”的边界写进 Issue，带描述、图片与评论进入工作树；执行者改代码，第二个 agent 准备失败场景，第三个只读审查接口与风险，避免三个 agent 同时扩功能。Orca 提供任务上下文、隔离工作树和并行协调；负责人决定删什么、何时停止扩范围，并在集成版本上验一次真实旅程。Linear 上下文、工作树

这里压短的是串行交接和等待，不是取消集成验证。独立工作树上的测试通过不能证明合并后的版本能用；并行审查也必须重新核对最后提交。

故事二：页面已经跑起来，设计反馈直接回到实现。 Builder 在内置浏览器点选出错元素，将 DOM、样式、局部截图及可得源码位置递交 agent；实现进行时，测试者同时梳理用户动作和失败边界。热更新后先复查页面，再通过原生 PR 审阅与失败检查日志修复问题。它缩短“描述截图—猜位置—再解释”的循环；是否解决了用户问题仍需观察真实操作。Design Mode、审阅与检查

故事三：周五能解释工作，却不能拿 agent 的 Done 冒充交付。 自动化可定时汇总 Issue、评审及阻塞信息，活动流帮助找到待输入、已结束和仍运行的会话。再补一张有来源的证据表：上线地址、实际使用者、完成的关键动作、未解决障碍。前半段原生能力已经很强；后半段是否值得做成 BW，取决于它能否促成人停止无效开发或缩小下一版。自动化、活动流

机制和指标：谁决定什么

机制 决定与执行权 不能据此推出什么
原生 plan / goal Claude TodoWrite、Codex update_plan 由 agent 提供；Codex goal 由原生聊天呈现，用户可暂停、恢复、清除；状态来自相应会话 agent 的计划完成，不等于产品目标被用户接受
编排任务 coordinator 建任务、依赖和派发；worker 对本次 dispatch 报成功或失败；Run 只存命名空间与收件箱，不自行调度 原生 Run 不是自动决定优先级的项目经理
decision gate coordinator 创建阻塞问题并记录解决结果；worker 的 ask 发给 coordinator 默认 gate 不保证由人拍板，更不等同 BW 的人验收

前一行见原生聊天，后两行见实验性编排协议。Orca 的 decision gate 与 BW 术语中的“必须由人决定的 gate”不是同一语义。 若希望暂停新增范围、确定发布或确认结果，必须明确负责人、证据和协调者权限，不能仅靠同名组件。

原生 usage 关注额度、token 与费用估算，不能回答用户是否受益。用量说明 对 BW 更有解释力的候选指标是：从承诺范围到首次真实使用的时间、承诺版本的使用证据、未完成工作的数量与年龄、范围变更原因。它们也是假设；不要把提交数、agent 完成数或指标变绿作为价值替身。

BW 吸收边界与四块重叠

本仓上游说明记录基线为 caa465d1，2026-09-15；本次核查 BW 为 5202485e。任务、自动化、工作树和审阅执行核在本仓保留，不能把上游现有能力统称为 BW 缺失。

有一个确切的后续差异：本仓 ProjectViewStates.tsx 第 47 行只允许 Table、Roadmap；ProjectViewWrapper.tsx 仍无 Board 渲染分支。因此 10 月可拖拽 GitHub Board 尚未吸收，证据层级仅为源码。9 月 15 日之后的 goal 展示、性能和恢复修复未逐项比对，不冒称已吸收或全部缺失；基线日期也不能排除定向移植。

BW 区块 原生重叠与应借用部分 值得验证的差异；反证
总览 任务项目视图、活动流、会话历史 帮人看清本周实际可用增量；若只是搬运状态，原生足够
指标 原生工程状态、用量；沿用数据与执行通道 用真实使用结果改变决策；若指标无数据或从不改变取舍，新增屏无价值
计划 Issue、Roadmap、agent plan / goal、编排 固定一个可交付切片、明确不做什么和截止点；若只是 agent 待办镜像，应收回
验收 diff、PR/MR、CI、浏览器运行和审阅 把部署、用户关键动作与人工接受连起来；若只是重复 CI 和勾选清单，应复用原生

对 1–3 人 Builder 的建议与反证

先选一个真实项目做两轮小版本验证。每轮只承诺一个可独立使用的切片；新想法进入候选，变更当前范围要写明取舍。利用原生工作树、浏览器、审阅与自动化压短执行；BW 只尝试把“承诺—可用版本—使用反馈”联系起来。

同等支持下，与“原生 Orca＋轻量 Skill”交叉比较：是否更早首次使用、是否减少长期未完成工作、周五能否解释真实增量，以及额外录入花了多久。若两种方式效果相当，就没有四块独立界面的充分理由；若主要损耗来自启动失败、卡顿、断线或数据错误，应先修这些。若交付及时却没人需要，问题可能在需求选择与用户接触，不能继续加计划表解决。
