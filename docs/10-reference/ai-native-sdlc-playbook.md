# Anthropic 的 AI 原生软件开发方法

> 给需要理解 AI 如何参与软件开发生命周期（SDLC）的读者。本文提炼 Anthropic 在 2026-08-21 发布的方法指南，说明六个阶段各自需要什么证据、哪些决定留给人。团队可以在各阶段之间往返。2026-11-05 核对原文，指南修订时更新。[Anthropic 原文](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)

Anthropic 指出，代码生成加快以后，需求澄清、评审和发布仍可能让工作排队。它建议把每一阶段的决定和证据写进可追溯的产物。这样，接手的人或工具可以看到上一步接受了什么、依据是什么。团队可以从等待最久的环节选用其中的做法。

| 阶段 | 谁作决定，用什么交接 |
|---|---|
| 计划 | 发起人与助手一起写清用户问题、预期结果和约束，由发起人纠正误解。负责人随后评估这份意图。 |
| 设计 | 在同一次讨论里把意图细化为规格。助手读入已有设计标准，指出需求之间的冲突，由人决定取舍。 |
| 构建 | 工程师先审实施计划里的风险和验证办法，再让助手改代码。团队将经常要解释的命令、约束和易错点保存在版本控制中。 |
| 测试 | 给助手可独立运行的测试或验证环境。修复问题时保留能复现失败的用例，评审者可以核对修复前后的结果。 |
| 部署 | 自动审阅先检查差异、风险及其与规格的一致性，工程师集中判断高风险变更。生产发布由具名负责人授权，工具在执行处检查权限。 |
| 维护 | 服务指标越过预设边界后再启动调查。修复走评审流程，严重故障可触发预先批准并演练过的回滚。事故记录为下一轮工作提供输入。 |

这份指南把控制分成两类。团队约定和技能文件能告诉助手应该怎样工作，权限和执行钩子则能实际阻止越权操作。原文给的是组织可以采用的流程、示例和观察指标。判断这套流程带来的实际收益，还需要对照团队采用前后的数据。
