# 系统提示词与渐进加载 — 模块实现心智

> 30 秒导读:本页说明 SYSTEM 的渲染与递交边界：计划页签新开会话注入 SYSTEM 指针 + week-planning 指针；接回已有会话不重递交。设计层「是什么」在 [`architecture.md`](../architecture.md) §2 ③;**关键取舍 + 三层分工 / 维护对照表在本页**。代码落点看 `src/renderer/src/workbench/plan-week-planning-prompt.ts`。本页讲怎么理解它的**实现内部结构**和**主要矛盾**。

## 实现心智模型

主提示词是**外置模板** `standard/system-prompt/SYSTEM.md.tmpl`,不硬编码在代码里(改身份 / 纪律 = 改 md)。提示词只给「一句话 + 完整路径」——references / 技能文件不在硬盘就如实少一段不编路径。这就是渐进加载:提示词放索引、正文让 agent 按需读。

现行壳是 Electron 叠层，`standard/` 是仓内文件，**不**再 `include_str!` 编进二进制。计划页签新开 Claude 会话时，`plan-week-planning-prompt.ts` 解析真实绝对路径后注入。三层各装什么(主提示词 / references / skills)正本在 [`standard/README.md`](../../standard/README.md),本模块只写怎么注入。三层分工 / 维护对照表见本页下文。

## 当前可达性边界

路径解析只搜索规划工作树和主项目，不搜索安装包资产目录。普通被管项目若没有 `standard/`，提示会报告未找到；本仓文件存在并不能证明任意项目可用。该入口递交的是 `SYSTEM.md.tmpl` 文件指针，没有在这里渲染模板占位符；真正读取与遵守还需 Prompt Trace 或实际会话证据。分发、渲染与入口覆盖由特性迁移任务处理，本轮不修改运行时。

## 主要矛盾 / 取舍

- **正文一律不塞进提示词**:塞进去 = 改身份要改代码、且 agent 上下文被无关正文占满。只给索引 + 路径,agent 按需读。
- **共同纪律的正本在 SYSTEM，实际覆盖取决于入口**:计划页签新开会话会注入 SYSTEM.md.tmpl 与 week-planning 指针；接回已有会话只切回该标签，不重新递交。其他 Issue 开工若尚未接同一注入链，不能只改模板就声称所有会话已获得新纪律。
- **技能注入与 SYSTEM 同一次递交**:计划页签把 SYSTEM、SKILL.md、references、planning.py 的真实路径写进同一份开工提示。文件不在就少一段，不另开 HTML 服务、不 `orca tab create --url`。

## 三层分工与维护对照

> 从 architecture §2 ③ 迁来——三层各装什么、改了哪条流程同步哪份。`AGENTS.md`「按任务读取」指到这里。改 `standard/` 之前先对表。

**分工**(改提示词 / 加 reference / 改 skill 之前先对):

| 层 | 装什么 | 不装什么 | 改它何时 |
|---|---|---|---|
| **主提示词** `SYSTEM.md.tmpl` | 哪个 Issue、读仓根 `AGENTS.md`、按任务加载哪份 reference、和 BW 状态机怎么配合、references/技能的**名字+一句话+路径** | 文件清单、格式版本、某类 Issue 的步骤 | 所有 Issue 都该守的契约变了 |
| **任务规范** `references/*.md` | 执行**这一类**工作必须对照的现行契约 | 怎么一步步干;本周这个项目发生了什么 | 这类 Issue 的协议变了 |
| **技能** `skills/*/SKILL.md` | SOP:先干什么、产出落哪、人点什么 | 现行文件枚举当正本(会漂);铁律副本 | 这类 Issue 的步骤变了 |

本周项目侧变化(`git log`、开着的 MR、指标记录)每次现算,不写进上述任何一层。

**维护**(产品流程变了,同步哪份;目录变了就改 `standard/README` 那张表):

| 变了什么 | 同步哪份 | 规范面向的入口（实际覆盖以上述边界为准） |
|---|---|---|
| 所有 Issue 都守的纪律(最远待评审 / 提完 MR 改 inreview 标签 / 只提 MR / 提交优先用户技能 / 计划页签不另开 HTML) | `SYSTEM.md.tmpl`；同时核对计划页签注入提示 | 计划页签新开会话；接回已有会话不重注入 |
| issue 状态机、版本多值归属、程序/模型写入边界 | `references/issue-state.md` | 计划页签注入；其他挂了该 reference 的开工 |
| 指标协议(可回溯、窗口、不许写 0、schema) | `references/metrics.md` + `templates/metrics.toml.tmpl` | 更新指标与版本计划 Issue;资产盘点升级格式时 skill 会再指过去 |
| 旧计划评论核对、修复与导入 | `references/week-plan-comment.md` + 校验脚本(只查旧周初三标题) | 历史材料处理 |
| 版本材料与执行进展写入 | `references/version-records.md` + `week-planning` / `version-acceptance` / `asset-audit` | 原生材料服务已提供且版本明确的任务；旧脚本不作为回退入口 |
| 改仓:分支 / 提 MR / 合并是人 / 提完 MR 改 `bw:status:inreview` | `references/build.md` | 构建/优化/运维业务 Issue;资产盘点 Issue(改 `.bw` 也是改仓) |
| `.bw` 该有、整份可删、现行格式、与更新指标与版本计划的分工 | `references/bw-assets.md` | 资产盘点 Issue |
| 独立评审只评不改 | `references/review.md` + `REVIEW.md.tmpl` + `mr-review`(尚未派发) | 评审会话 |
| 某项周期工作怎么干 | 对应 `skills/<slug>/SKILL.md` | 挂了那个 workflow 的 Issue；计划页签新开会话注入 week-planning |
| 哪类 Issue 注入哪份 reference | `plan-week-planning-prompt.ts` 的路径解析；SYSTEM.md.tmpl 的加载表 | 计划页签新开会话；不含已有会话重注入 |

漏同步的结果就是周五盘点还在找已经不存在的登记表——协议变了只改界面、不改 reference,现场 agent 对不上。

## 周一屏资源与数据读取

week-planning 的空数据模板、planning.py、离线 HTML 缓存和 references 作为仓内 `standard/skills/week-planning/` 文件存在；计划页签按工作树与主项目解析真实路径后注入。离线 HTML 不是编辑器。

计划页签新开会话注入 SYSTEM + skill 指针；右侧原生三屏已打开 `.bw/planning/<版本>/data.json`，会话用 planning.py 的 read/update/confirm，不要再起 HTML 服务。此处描述现有硬编码提示的旧三屏行为。标准 Skill 已形成独立计划/验收的配套设计稿，不能在此混称已接入；目标设计见下文。

计划屏/总览读取同一 JSON：归档读主项目，已登记 bw/week-plan 的同版本草稿覆盖显示；损坏草稿显示未知。summary.progress 是 previous_version 的结果摘要，不算作新版本进展。没有 JSON 时不退回旧评论；首次历史导入由 Skill 处理。

[计划设计](../05-features/version-planning/design.md) 与 [验收设计](../05-features/version-acceptance/design.md) 要求入口只下发项目/版本/流程/真实工具与资产指针；SOP 留在 Skill，不在 TypeScript 再硬编码一份。模型先展示完整流程，目标方法按需读取 references。当前提示中的三屏、confirm 和 fetch-meeting 命令须与页面、材料服务及旧脚本同次切换；本轮只改设计与规范正文，没有运行时加载或行为验证。
