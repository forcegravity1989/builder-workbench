# 系统提示词与渐进加载 — 模块实现心智

> 30 秒导读:本页说明 SYSTEM 的渲染与递交边界：计划/验收屏与「配置指标」开工时注入渲染后的 SYSTEM + 对应 Skill（week-planning / version-acceptance / metrics-refresh）；恢复历史会话不重递交。设计层「是什么」在 [`architecture.md`](../architecture.md) §2 ③;**关键取舍 + 三层分工 / 维护对照表在本页**。代码落点看 `src/renderer/src/workbench/version-cycle/cycle-prompt.ts`。本页讲怎么理解它的**实现内部结构**和**主要矛盾**。

## 实现心智模型

主提示词是**外置模板** `standard/system-prompt/SYSTEM.md.tmpl`,不硬编码在代码里(改身份 / 纪律 = 改 md)。模板与三份 Skill 发现 Stub 以 raw 导入**随产品打包**(Stub 投影位于根级 `skills/`,由 `config/scripts/generate-bundled-skill-guides.mjs` 从 `standard/skills/` 正源生成,完整指南由原生 guide 分发机制打包);开工时 `cycle-prompt.ts` 解析全部 `{{占位符}}` 渲染整份提示,未解析字段直接抛错。Skill 完整指南与 references 都不塞进提示,只给「名字 + 一句话 + `ORCA skills get <topic>` / `--reference <name>` 命令」,agent 按需读——这就是渐进加载:提示词放索引与 Stub、正文让 agent 自取。

现行壳是 Electron 叠层，`standard/` 是仓内文件，**不**再 `include_str!` 编进二进制。计划/验收/指标配置新开原生会话时，`cycle-prompt.ts` 渲染后注入，并附宿主已确认的执行上下文（projectId/repoId/hostId/worktreeId/workspacePath/workflow）与 `ORCA bw materials` 材料 CLI 指引。三层各装什么(主提示词 / references / skills)正本在 [`standard/README.md`](../../standard/README.md),本模块只写怎么注入。三层分工 / 维护对照表见本页下文。

## 当前可达性边界

提示资产(SYSTEM 模板、三份 Skill 发现 Stub)编译进产品,没有 `standard/` 的普通被管项目也能获得完整开工提示;指南与 references 的按需读取依赖执行环境可用 `ORCA skills get`。递交提示、模型读取正文和遵守规范仍是不同证据,须以 Prompt Trace 或实际会话核对;真壳烟测已编写(结果见对应 PR),不替代行为遵守验证。

## 主要矛盾 / 取舍

- **reference 与指南正文不塞进提示词**:塞进去 = 改身份要改代码、且 agent 上下文被无关正文占满。提示只内嵌 SYSTEM 渲染结果与 Skill 发现 Stub,完整指南和 reference 给命令让 agent 按需读。
- **共同纪律的正本在 SYSTEM，实际覆盖取决于入口**:计划/验收屏与「配置指标」新开会话注入渲染后的 SYSTEM.md.tmpl;恢复历史会话只精确身份接回,不重新递交。其他 Issue 开工若尚未接同一注入链,不能只改模板就声称所有会话已获得新纪律。
- **技能注入与 SYSTEM 同一次递交**:开工提示把渲染后 SYSTEM、对应 Skill 发现 Stub、references 命令与材料 CLI 指引写进同一份提示;模板占位符解析失败即抛错,不递交半成品。不另开 HTML 服务、不 `orca tab create --url`。

## 三层分工与维护对照

> 从 architecture §2 ③ 迁来——三层各装什么、改了哪条流程同步哪份。`AGENTS.md`「按任务读取」指到这里。改 `standard/` 之前先对表。

**分工**(改提示词 / 加 reference / 改 skill 之前先对):

| 层 | 装什么 | 不装什么 | 改它何时 |
|---|---|---|---|
| **主提示词** `SYSTEM.md.tmpl` | 哪个 Issue、读仓根 `AGENTS.md`、按任务加载哪份 reference、和 BW 状态机怎么配合、references/技能的**名字+一句话+路径** | 文件清单、格式版本、某类 Issue 的步骤 | 所有 Issue 都该守的契约变了 |
| **任务规范** `references/*.md` | 执行**这一类**工作必须对照的现行契约 | 怎么一步步干;本周这个项目发生了什么 | 这类 Issue 的协议变了 |
| **技能** `skills/*/SKILL.md` | SOP:先干什么、产出落哪、人点什么 | 现行文件枚举当正本(会漂);铁律副本 | 这类 Issue 的步骤变了 |

本周项目侧变化(`git log`、开着的 MR、指标记录)每次现算,不写进上述任何一层。

**维护**(产品流程变了,同步哪份;目录变了就改 `standard/README` 那张表):

| 变了什么 | 同步哪份 | 规范面向的入口（实际覆盖以上述边界为准） |
|---|---|---|
| 所有 Issue 都守的纪律(最远待评审 / 提完 MR 改 inreview 标签 / 只提 MR / 提交优先用户技能 / 计划屏不另开 HTML) | `SYSTEM.md.tmpl`；同时核对 cycle-prompt 渲染字段 | 计划/验收屏与「配置指标」新开会话；恢复历史会话不重注入 |
| issue 状态机、版本多值归属、程序/模型写入边界 | `references/issue-state.md` | cycle-prompt 的 references 指引；其他挂了该 reference 的开工 |
| 指标协议(可回溯、窗口、不许写 0、schema) | `references/metrics.md` + `templates/metrics.toml.tmpl` | 更新指标与版本计划 Issue;资产盘点升级格式时 skill 会再指过去 |
| 旧计划评论核对、修复与导入 | `references/week-plan-comment.md` + 校验脚本(只查旧周初三标题) | 历史材料处理 |
| 版本材料与执行进展写入 | `references/version-records.md` + `week-planning` / `version-acceptance` / `asset-audit` | 原生材料服务已提供且版本明确的任务；旧脚本不作为回退入口 |
| 改仓:分支 / 提 MR / 合并是人 / 提完 MR 改 `bw:status:inreview` | `references/build.md` | 构建/优化/运维业务 Issue;资产盘点 Issue(改 `.bw` 也是改仓) |
| `.bw` 该有、整份可删、现行格式、与更新指标与版本计划的分工 | `references/bw-assets.md` | 资产盘点 Issue |
| 独立评审只评不改 | `references/review.md` + `REVIEW.md.tmpl` + `mr-review`(尚未派发) | 评审会话 |
| 某项周期工作怎么干 | 对应 `standard/skills/<slug>/SKILL.md`；同步重新生成根级 `skills/` Stub 投影 | 挂了那个 workflow 的 Issue；计划/验收/指标配置开工分别注入 week-planning / version-acceptance / metrics-refresh Stub |
| 哪类 Issue 注入哪份 reference | `cycle-prompt.ts` 的 references 列表；SYSTEM.md.tmpl 的加载表 | 计划/验收屏与「配置指标」新开会话；不含已有会话重注入 |

漏同步的结果就是周五盘点还在找已经不存在的登记表——协议变了只改界面、不改 reference,现场 agent 对不上。

## 周期工作资源与数据读取

week-planning 现只含 SKILL.md、`assets/minutes-template.md`、references（goal-guidance、data-and-runtime）与 `check-week-comment.py`（历史评论修复协议，配 `references/week-plan-comment.md`）。旧离线 HTML 模板 version-plan.html、空数据模板 data-template.json、planning.py 与会议 reference 已随消费方切换在同一交付内退役删除，不再有 HTML 缓存或 start/serve 入口。

计划/验收屏新开会话注入渲染后 SYSTEM + 对应 Skill Stub；右侧材料单页与会话经 `workbench.materials.*` RPC / `ORCA bw materials` CLI 读写同一份 `.bw/planning/<版本>/` 材料，不要再起 HTML 服务。

计划屏/总览读取同一 JSON：归档读采用基线上的合入证据，已登记 bw/week-plan 的同版本草稿覆盖显示；损坏草稿显示未知。summary.progress 是 previous_version 的结果摘要，不算作新版本进展。没有 JSON 时不退回旧评论；首次历史导入由 Skill 处理。

## 版本流程提示的接线现状

[计划设计](../05-features/version-planning/design.md) 与 [验收设计](../05-features/version-acceptance/design.md) 要求入口只下发项目/版本/流程/真实工具与资产指针；SOP 留在 Skill，不在 TypeScript 再硬编码一份——`cycle-prompt.ts` 已按此接线：下发宿主已确认的执行上下文、材料 CLI 指引与 Skill Stub，模型先展示完整流程，指南与 references 按需读取。旧提示中的三屏、confirm 和 fetch-meeting 命令已随 planning.py 退役删除。运行时加载有真壳烟测覆盖（已编写，结果见对应 PR）；模型对规范的实际遵守仍需会话证据。
