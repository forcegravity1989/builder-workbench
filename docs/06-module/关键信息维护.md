# 关键信息维护 — 模块实现心智

> 30 秒导读:这一层是 Workbench 的**事实层**——活态数据的唯一读写口、本地零库的现算推导源头。设计层(是什么 + 关键取舍)在 [`architecture.md`](../architecture.md) §2 ①;代码落点用 `codegraph` 探索。本页讲怎么理解它的**实现内部结构**和它面对的**主要矛盾**。

## 实现心智模型

正本分两类,代码对两类态度不同:

- **活态数据正本** = codehub / GitHub 的 issue + 标签。状态、排期、发版号、类别全在标签上,issue 本身是张白纸。两台 Workbench 接同一个 codehub 仓,读出来是同一份活态。本地一个字不存——每次读都现去远端拿。
- **仓文件 `.bw/`** = 项目约定 + 指标定义的正本(`project.toml` / `metrics.toml` / `readings.jsonl`)。人、agent、第二台机器要看的都住仓里走 MR。本地解析结果只在内存现用,不存第二份。

第三类**本机运行时资产**(`projects.toml` / `settings.toml` / `sessions/*.jsonl`)纯运行时、零正本:删掉重接就回来,append-only 取末行为最新。`NotifyEvent` 注册表管项目群事件枚举。

读写正本只有这一个口:别处不许自己拼路径读 `.bw/*.toml`。健康推导是这层的二级特性——把 ① 维护的信息派生成一盏灯,现算纯函数,密封类型守「没数据不装绿」。

## 主要矛盾 / 取舍

- **放弃本地读缓存,读全走 CLI**:多一台机器、多一份缓存就多一处对不上。MVP 卡点认了——读远端慢但永远一致。
- **仓文件不做 `deny_unknown_fields`**:人手写多一个字段就整份崩,代价太大;读到旧格式整份拒收、但不在打开项目时改仓(改仓是人 + agent 的事)。
- **写回手写渲染而非自动序列化**:把注释留给人看;自动序列化会把人的注释吃掉。
- **MR 合入复跑读回 state 真 `merged` 才算成功**:退出码靠不住(CLI 合入失败也可能退 0),绝不假 Done。
- **健康灯只能从数据推导不手设**:密封 `DerivedHealth`,构造点限仓内、仓内无 `set_signal`——守铁律「没数据是诚实的灰不是绿」。
