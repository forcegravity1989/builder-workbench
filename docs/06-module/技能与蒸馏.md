# 技能与提炼 — 模块实现心智

> 30 秒导读:这一层管 Workbench 自带的周期工作技能 + 技能提炼。设计层「是什么」在 [`architecture.md`](../architecture.md) §2 ④;**关键取舍在本页**。代码落点看 `standard/skills/` 与计划页签注入。本页讲怎么理解它的**实现内部结构**和**主要矛盾**。

## 实现心智模型

四份自有技能(week-planning / asset-audit / metrics-refresh / project-handbook)作为仓内文件放在 `standard/skills/`,提示词只给「名字 + 一句话 + 完整路径」,正文让 agent 按需读(渐进加载)。不编进二进制。`asset-audit` 是资产盘点 Issue 的剧本,对应 §1 用例。计划页签新开会话注入 week-planning 指针,右侧原生三屏读写同一 JSON。

技能内容的来源不等于派发范围。当前计划入口只搜索规划工作树和主项目的 standard，不能声称被管项目已自动收到整套技能。旧 Rust 设置屏的 workflow 引用计数不用于说明本分支；技能提炼尚未接入，不能将技能列表视为提炼结果。仓里另有一份评审剧本 `mr-review`:规范已收录,尚未派发。

会议转写依赖尚未齐备：`week-planning/scripts/planning.py` 的默认配置指向 `scripts/fetch-emeeting-transcript.mjs`，但该脚本在本分支缺失；Skill 与会议 reference 仍保留“内置脚本、init 后可用”的旧说明。依赖、执行指引与 Electron 验收须由周一屏迁移任务一并处理，旧 main 的会议验证不能证明本分支已经可用。

## 主要矛盾 / 取舍

- **不预建方法论技能**:原六份「阶段方法论」默认 workflow 没打包、一份没被真正派发过,删光。业界 workflow 是可选方法来源；本分支未迁 standard/vendor，不能把 mattpocock / proto-design 当作已打包默认。任务规范约束(references,如指标铁律、改仓规则)归本模块,不和技能混。
- **技能提炼是 Issue 的附属动作**:把一个已完成 Issue 中验证过的做法提炼成技能,始终保留来源 Issue。不预建、不在缺少来源时提炼技能。
- **技能正本留在 `standard/`,不进用户仓**:全局一份;用户自己的技能约定放被管仓 `.claude/skills/`(配置表扫成「项目自有」),不拷进 Workbench 资产目录。计划页签按工作树与主项目解析真实路径,文件不在就少一段。
