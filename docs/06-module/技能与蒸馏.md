# 技能与提炼 — 模块实现心智

> 30 秒导读:这一层管 Workbench 自带的周期工作技能 + 技能提炼。设计层「是什么」在 [`architecture.md`](../architecture.md) §2 ④;**关键取舍在本页**。代码落点看 `standard/skills/`(正源)、根级 `skills/`(Stub 投影)与 `version-cycle/cycle-prompt.ts`(注入)。本页讲怎么理解它的**实现内部结构**和**主要矛盾**。

## 实现心智模型

四份自有技能(week-planning / asset-audit / metrics-refresh / project-handbook)作为仓内文件放在 `standard/skills/`,提示词只给「名字 + 一句话 + 获取命令」,正文让 agent 按需读(渐进加载)。不编进二进制的是完整指南;开工提示内嵌的发现 Stub 由 `config/scripts/generate-bundled-skill-guides.mjs` 从 `standard/skills/` 正源生成到根级 `skills/`,经原生 guide 分发机制打包。`asset-audit` 是资产盘点 Issue 的剧本,对应 §1 用例。计划/验收屏与「配置指标」开工分别注入 week-planning / version-acceptance / metrics-refresh Stub,右侧材料单页与会话读写同一份版本材料。

技能内容的来源不等于派发范围。week-planning / version-acceptance / metrics-refresh 三份 Stub 与其指南经产品打包,普通被管项目不需要自带 `standard/` 即可按 `ORCA skills get` 读取;asset-audit 等其余技能未接入该分发,不能声称被管项目已自动收到整套技能。旧 Rust 设置屏的 workflow 引用计数不用于说明本分支；技能提炼尚未接入，不能将技能列表视为提炼结果。仓里另有一份评审剧本 `mr-review`:规范已收录,尚未派发。

会议转写链已退役:week-planning 的 planning.py、assets/version-plan.html、assets/data-template.json 与会议 reference 已随消费方切换在同一交付内删除(计划设计授权的原子切换),新 Skill 不做会议转写;保留 `check-week-comment.py` 与 `references/week-plan-comment.md` 作历史评论修复协议。旧 main 的会议验证材料只剩历史身份,不证明任何现行能力。

## 主要矛盾 / 取舍

- **不预建方法论技能**:原六份「阶段方法论」默认 workflow 没打包、一份没被真正派发过,删光。业界 workflow 是可选方法来源；本分支未迁 standard/vendor，不能把 mattpocock / proto-design 当作已打包默认。任务规范约束(references,如指标铁律、改仓规则)归本模块,不和技能混。
- **技能提炼是 Issue 的附属动作**:把一个已完成 Issue 中验证过的做法提炼成技能,始终保留来源 Issue。不预建、不在缺少来源时提炼技能。
- **技能正本留在 `standard/`,不进用户仓**:全局一份;用户自己的技能约定放被管仓 `.claude/skills/`(配置表扫成「项目自有」),不拷进 Workbench 资产目录。根级 `skills/` 的 Stub 投影从 `standard/skills/` 正源生成,改正源须同次重新生成投影。
