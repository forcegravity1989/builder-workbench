# 客户端更新

> **维护约定**：给维护 Workbench 客户端分发与下载的人读。只写原生更新器与下载适配的责任、网络恢复的取舍；发布操作见 [workbench-release](../05-features/workbench-release/spec.md)，整体边界见 [architecture](../architecture.md)。下载策略或缓存身份变化时更新。

## 原生更新器负责可信交付

版本检查、发布通道、用户选择下载与重启、SHA-512 与安装包发布者校验、NSIS 安装仍由原生更新链负责。下载适配只提供文件字节，不代替原生验证，不改签名规则，不自动安装。依据是 #421 的代理网络断流反馈及用户授权先实现一版；安装包命名按 #438 使用 `workbench-windows-setup.exe`，旧版本由发布清单中的文件名兼容读取。

## 用完整文件换取可恢复的下载

Windows Workbench 的 generic feed 经仅绑定回环地址、带随机路径的本地适配服务。它按原发布标签读取清单，并把清单中的文件地址投影为本地地址；其他平台、Orca 和本地构建切换沿用原生行为。

当前原生差分下载只复用旧安装包，无法持久保存一次失败下载的进度，且失败后会再下整包。首版因此禁用 Windows Workbench 发布更新的差分下载，改用可恢复整包。代价是成功差分场景的网络流量变大；收益是中断后不必重新下载已保留的字节。不能把这个取舍推广成所有网络下整包都更快。

下载缓存置于产品用户目录 `update-downloads/`，与原生失败时清空的 `pending/` 分离。缓存身份绑定原始资产 URL、清单 SHA-512 和大小；不以文件名或百分比复用。进程内最多自动重试五次，间隔 1、2、4、8、16 秒；之后保留缓存，用户仍可经原生“重试下载”继续。应用重新检查到同一资产后也可复用。超过七天的其他下载缓存按受控文件名清理。

恢复请求使用 `Range: bytes=<已保存字节>-`，校验 `Content-Range`。服务器忽略 Range 时丢弃响应中重复的前缀，再追加剩余内容；该场景仍会产生前缀的重复网络流量。完整文件必须通过 SHA-512，校验失败删除缓存；原生更新器还会独立验证一次。取消或退出保留未完成文件，重新检查与下载仍由用户及原生流程控制。

更新继续使用原来的 GitHub Release 地址，不需要配置新的下载地址。标签发现和清单读取沿用现有检查链，文件下载中断后向同一资产重试并请求剩余字节。
