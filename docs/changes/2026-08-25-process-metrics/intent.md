## 问题

BW 的指标体系(北极星 / 滞后 / 引领三层)今天只对着**业务成效**。《AI-Native SDLC Playbook》在 13 个环节各给出一对引领/滞后指标,量的是**研发过程自身**(首过率、评审等待、返工、发版频率……),且统计方式全部从 git / PR 史实直接读——与 BW「难造假」「现算不存」的哲学同构。BW 缺这一层:健康灯只有三条粗判据,「每周在正常演进」没有一排能核对的数。

## 拍板原话(约束的来源)

1. 「我认可将 playbook 的指标引入,结合我们已有的 BW 设计。」
2. 「playbook 在每个环节都提供了引领性指标和滞后性指标,我希望**把每个指标的统计方式都纳入**到我们的 bw 里。」(全目录,不是严选)
3. 「因为它是和代码仓强绑定的,所以**都是从代码仓去统计**相关的指标。」(纯度规则:仓是唯一统计源)
4. 「我们都先按照标准去建立 issue……**优先先建立一些当前项目可以直接统计的指标**。」(bench 还不具备的能力走 issue 跟踪,先交付即刻可算的)

## 盼到的结果

- playbook 全部 26 条指标,每条在 BW 里**有一个明确的统计方式**:能算的指到脚本,等前置的写明等什么,不建的写明为什么——一条不糊弄。
- 当前项目**今天就能算**的那批(约 12 条)以现成脚本随规范铺进项目,任何人 clone 仓 + 装 gh 就能复算,不装 buddy 也一样。
- 想点灯的条目可晋升进引领/滞后三格(同脚本 + 目标),与既有的健康推导、见红判据(遗留清单③)衔接。

## 约束

- **代码仓是唯一统计源**:输入只允许本仓 git 历史、仓远端(PR/issue/检查)、仓内文件;本机库不作数据源,仓看不见的事不建指标。
- 北极星永远业务;荐入至多两格、人确认才写;不建评测集与事故实体;指标随实践走,不空挂脚本。
