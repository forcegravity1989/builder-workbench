## 设计拍板(两层架构 + 一条纯度规则)

1. **纯度规则(凌驾一切)**:每条过程指标的统计输入只允许三种——本仓 git 历史、本仓远端(PR / issue / 检查)、仓内文件。换台机器、或不装 buddy 只有仓和脚本,算出来必须是同一个数。仓看不见的事(如人在本机点「完成」那一下)**如实不建**。
2. **层一 · 过程指标目录**(内置方法论,全项目同一套):统一走脚本、铺一次归项目、脚本即口径文档;默认**不点灯**、点了才采。**目录正本 = `.bw/process-catalog.md`**(随铺底进项目;buddy 仓内的源文件在 `standard/04-metrics/process-catalog.md`),26 条逐条给出统计方式或不建理由,本 spec 不复写那张表。
3. **层二 · 晋升进三格**:任一目录条目可写进 `.bw/metrics.toml` 的引领/滞后格(引用**同一份脚本** + 设目标)→ 获得点灯资格、参与见红(见红判据本身是 #119)。荐入规则的正本在 `standard/skills/metrics-refresh/SKILL.md`「过程指标包」一节:空位才荐、至多两格、退场条件写进指标说明、人确认才写、目标用真实水位校准。
4. **同一个数只有一份脚本一种口径**——目录与总览「代码仓级」块重叠的两条(每周提交、每周合入 PR)复用既有脚本,不重复实现。

## 本批范围(能落成脚本的 10 条 + 连带件)

十份脚本进 `standard/06-scripts/`,协议与既有三份完全一致(`--since --until --granularity week`、标准输出一个 JSON、失败如实、绝不写 0、顶到拉取上限整条不给数):评审等待 / 首过率 / 返工轮数 / 首审等待 / 意图成文时长 / 变更前置时间 / 同时开着的 MR 数 / 活存活率 / 手册修正频次 / 距上次发版天数。每条的完整口径以**脚本头部 docstring 为正本**(含复算命令)。

连带:`metrics.toml.tmpl` 补过程指标注释示例段(晋升即用);`metrics-refresh` 剧本加荐入节;铺底表登记十份脚本 + 目录文件(`LayAt::OnFirstUse`,与既有脚本同站);`standard/VERSION` 5.0 → 5.1;`design.md` §4.2 两处实况小修(版本号、目录树补 06-scripts 一行)。

## 明确不在本批(有主的,不散落)

CI 首跑通过率(#120,与 MR 检查列同数据源)、等前置的 8 条(#121-124)、见红接通(#119)、总览过程指标块(#120)、接入→首合入与规范过期件数(目录里给复算命令,不做走势脚本)。

## 要求与验收

- **R1 协议一致**:十份脚本对协议的遵守与既有三份逐条一致;`python3 -m py_compile` 全过。
- **R2 真跑读回**:每份脚本对 buddy 自己的仓真跑一次——GitHub 类出真数;`release-gap` 在没有发版记录的仓**如实报错**(这是正确行为,不是失败);`first-review-wait` 在单人仓大概率稀疏,空如实。
- **R3 复算抽查**:至少一条用脚本头部的复算命令手工对数,数字一致。
- **R4 门禁全过**:fmt / clippy / wasm 检查 / 三个结构守卫 / 两壳编译 / cargo test。
- **R5 幂等与不覆盖**:铺底走既有指纹机制,人改过的脚本永不被覆盖(既有机制,不新增代码,PR 评审确认没破坏)。

## 标注的冲突(playbook 要求 spec 把矛盾摆出来)

1. **文档边界没有本产物链的位置**——本目录是试验,固化要改 `docs/doc-boundaries.md`,留给人拍。
2. **`.bw/process-catalog.md` 的身份**:它是「buddy 的方法论件」铺进用户仓,但它引用的部分能力(评审剧本、事件触发)buddy 还没交付——目录里已如实写「等 buddy 的哪个能力」,不写 issue 号(用户仓读者无从查号)。
3. **两步拉取的成本**:四份吃提交清单的脚本按窗内 PR 数逐张查(GraphQL 节点预算所迫,见 plan.md 风险一节),重窗口一次采集约 1-2 分钟——与「点了才采」的交互契合,但配置定时采集时要留意。
