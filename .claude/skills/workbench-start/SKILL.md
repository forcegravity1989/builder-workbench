# workbench-start — Workbench 开发与交付

> 30 秒导读：先核对工作树与技术路线，再按用户目标分流。迁移重审受影响的决定，开发串起原则规定的六环；交付实现、受影响知识与对应层证据，经 PR 和人的判断后读回反哺。
>
> **状态：仓内 `0.4.0-pilot`。** 任何使用者都可以采用本入口。开发规则仍听目标仓 AGENTS；本方法不自动分发到 standard，实际效果按独立任务证据检验。

## 1. 适用范围与入口

- 适用于 BW 仓外 IDE 中开展的开发任务。执行具体任务，不自动启动全仓资产治理或重新制定本周计划。
- 本 Skill 是开发与交付的工作入口；不再强制把所有任务统一先送去 grill。已有明确决定直接复用，真正缺失的决定才对齐。
- 保留项目的工程约束、实际验证要求、隔离开发、由人合入与完成等边界。加载本 Skill 不新增 push、发消息、修改远端计划或扩大任务的授权；沿用当前会话已明确给予的授权，不重复请求。
- AGENTS、原则、Skill 都可以是授权任务的修改对象。涉及职责、格式或存量整改时，转 [project-knowledge](../project-knowledge/SKILL.md) 完成本轮治理；不把一次任务的试验结论自动推广到全仓或 standard。
- 在 BW 内部已有任务提示词时，不自动再叠此仓外入口。用户明确要求试用时先辨认其已加载规则，不构造第二套 issue/状态/定时机制。

**路径规则：** 本目录仅用于定位本 Skill 的 references。实际工作项目从当前会话工作目录与 Git 信息确认；从另一个 worktree 的绝对路径读入此 Skill，不表示在那个 worktree 实施业务任务。

## 2. 起手：读取足够证据，给出一个短判断

1. 核对目标仓根、分支/worktree、HEAD、未提交改动、远端 URL、PR base、当前任务与既有授权。更新用户指定的目标分支，不默认只拉 `main`。用当前 AGENTS、构建入口和源码确认技术路线；借另一棵树的 Skill 时，记录方法路径/版本和目标仓路径/版本，业务操作始终显式指定目标仓。
2. 读目标 AGENTS「按任务读取」、原则索引及相关原则、architecture、CONTEXT；沿引用只读受影响的特性、模块、实现与验证入口。`bw-orca` 走 Electron/Orca 叠层，读 `ref/upstream.md` 识别 BW 与 Orca 来源；`main` 的 Rust 实现只作按需历史来源，不合并覆盖目标树，不照搬其命令或验收结果。Orca 工程细节按需进 `ref/`。修改文档先读原文头部和原则 01。
3. 对目标、已认可决定、当前实现、当前验证和历史证据分别标识。源码证明现在怎样，不能独自决定应当怎样。保留目录不证明已迁移；已删除目录也不是必须恢复的交付清单。文档与代码冲突时先查决定，仍影响实现才提出具体分歧。
4. 追溯周一屏早期决定时才读 [历史参考](references/week-screen-v04.md)；当前迁移从目标分支的 spec、实现和实际任务出发。
5. 用简短文字交代：**这次要交付什么、依据是什么、选哪条路径、怎么验证、还有哪个决定确实缺失**。这不是等待批准的固定仪式；信息充分时说明后继续。

现有 standard 若与这次任务的读写协议有关，按入口读取以避免破坏界面或数据契约；不因“已存在”就认可它的方法有效，也不按旧 SOP 重问已经确认的问题。

## 3. 分流：按意图与影响判断，不按改动行数

| 这次工作 | 执行路径 | 需要用户的时机 |
|---|---|---|
| 小 bug：恢复已有明确行为 | 复现 → 最小修复 → 适当验证 → 交付；复用特性与验收 | 预期行为不明、影响扩大或修复需改变契约 |
| 已有特性调整：目标和边界已明确 | 记录行为增量 → 实现与知识同步 → 验收 | 涉及新的产品取舍或不能由已知约束决定的跨模块变化 |
| 特性迁移：目标可能沿用、实现路线已变 | 对照历史意图与目标实现 → 重审用户旅程/边界/验收 → 从受影响或缺失的环补链 | 迁移改变用户承诺、交互或边界且尚未决定；已批准部分继续 |
| 新特性/重大变化 | 草拟用户价值、范围、可见结果和验收 → 只确认缺失决定 → 拆解并执行 | 关键价值、范围、交互或架构取舍尚未确定 |
| 盘点、瘦身或整改文档/模型指令 | 转 [project-knowledge](../project-knowledge/SKILL.md)；多文档职责/格式未定时先给 HTML 决策报告，已定范围直接实施 | 职责或格式存在真实未决选择；已有认可直接复用 |
| 证据不齐/文档冲突 | 定向调查，给出具体选项及影响；不先猜设计 | 调查仍不能确定正确目标，或权限/外部依赖真的阻塞 |

新特性的规格与原型仍按已有项目制品落点承接；原型链接不冒充实物交付。用户已确认的方向不重复 grill。可以调用已有 vendor 中适用的澄清、实现、评审方法；核对文件是否存在、步骤是否适用，不整套安装更多框架或照搬其目录。

新工作先按目标仓 [原则 02](../../../docs/01-principles/02-working-backwards.md) 的“带入三问”判断服务已有用户目标、新目标，还是预研/工程方法；复用已有承载，不按页面或目录数另建特性。对特性级变更，将已有认可映射到 intent/spec 及来源。仍成立的 gate 不重走，路线变化使原决定失效的部分重新决策；不能把聊天方向或旧平台已通过当成目标平台制品已认可。小 bug 复用明确行为，不机械新开整套文档。

提问时先完成能独立推进的调查与准备，一次聚焦一个会改变实现的决定。没有答复不算认可；有既有授权也不因旧模板一句“必须确认”反复索要相同批准。

## 4. 用六环把交付说到能验

按目标仓原则 02 的六环要求执行：`intent → spec → 实现设计 → TDD → 验收点 E2E → 用户旅程 E2E`。原则是正本；本 Skill 只连接执行，具体证据与迁移差异见 [交付与证据约定](references/delivery-contract.md)。若依赖的原则更新尚未合入，记录依赖 PR/版本，不假定共享基线已更新。

先核对用户意图与 spec 验收点，再在 architecture 定位实现，按影响维护测试、验证具体验收点与完整用户旅程，回写受影响设计。小修只展开受影响的环；不能因此跳过已适用的验收。STATUS 按原则的六环格式记录来源、缺口和未验证项，不把六个文件齐全写成六环通过。

按 [交付与证据约定](references/delivery-contract.md) 的适用项整理在现有 Issue/特性文档/当前计划里，不新开一套台账。最少能说明：

- 用户预期结果、范围、已有特性或约束；找不到归属先记候选，不假装特性全集已确定。
- 改动行为与可判断的验收点；主路径之外，选择与风险有关的失败、重开、数据读回场景。
- 每个验收点由哪种检查/用例证明、证据落在哪里。
- 需要衡量新价值时：指标及口径、来源和采集方法；候选与已认可分开。小修复用已有衡量，不为填表硬造指标。

新增用户价值或用户明确要求“特性→指标→E2E”时展开价值衡量；数据暂不可得不伪造基线和目标，也不让等待滞后结果阻塞本周功能验收。

## 5. 实施与知识最小同步

- 优先修已有实现和对应知识，不为同一事实新增平行文件、配置或兼容路径。
- 复用当前任务已有 worktree/分支；另起工作按用户与项目约定隔离。开发过程不移动、删除别人的常驻树。
- 修改前定位受影响的契约、消费者和验证方式；正常实现选择自行完成，发现范围扩大回到第 3 节。
- 知识更新限本次行为：用户操作或契约变了更新现有规格/使用说明；架构取舍变了更新 architecture/对应模块，Orca 工程协议按需同步 ref。从 docs 地图找真实落点，不为旧模板恢复已删除指南或 ADR；目标文件职责容纳不了时按 AGENTS 处理。无需变化则说明理由。
- 按当前授权范围同步规则与知识；采用新规范要处理其覆盖的存量和引用，不能只新增模板。若当前会话明确要求“存量文档全不动”，在任务已有产物记录必要同步项，不虚报一致。
- 重复或冲突资料先辨认真正来源，做当前任务必要修订；需要全景或批量治理时读取 project-knowledge；普通编码无需先完成全仓分类。
- 实施/审查发现问题，修到根因并针对性复验；连续两次同因验证失败或修复将越界时，报告原因与可执行下一步，不无限重试、换判据或悄悄扩范围。

## 6. 验证、交付与完成

- 执行当前任务需要的验收，以及实际适用的项目门禁。计划提交时运行 AGENTS 要求的提交前检查；未执行不能报告已通过。
- E2E 要说清真实链路与边界：静态/脚本检查、单元/集成、真实 Electron 桌面、实际 Orca 模型会话、Git/文件/远端读回各证明不同层。历史 Rust/WebView2 证据只证明当时平台；HTML 原型、截图或模拟不能替代当前真实依赖的验收。
- 报告源码/产物版本、用例/方法版本、环境、命令、结果与证据。修改后旧报告是否仍适用要重新判断。
- 代码可运行、验收通过、用户认可、价值已证实是四件事；按实际证据分别陈述。合入和标完成遵循人的授权。
- 交付简短可读：**做了什么；实际产物/改动入口；验了什么及证据；未验/未实现；需要人的剩余决定。**
- 沿当前授权及仓库交付规则完成提交、push、PR 和验证报告；明确只本地时才停在本地。Skill 本身不新增合入、关闭 Issue、正式发版或修改远端计划/评论的权限；写入前核对对象与协议，写后读回。需要许可时先备好具体可审查结果。
- PR 核对真实 base/head、提交和检查状态；人确认合入后读回实际 merge commit 与目标分支，再更新依赖交接。依赖另一 PR 时明确顺序，将其已合入基线纳入本分支并复核引用、示例、适配和门禁；未合入不能称共享基线就绪。不开启未经授权的后续迁移。

## 7. 每次任务留一点有用的反哺

先完成当前任务，不把复盘变成另一件大工程。把以下实际观察放进同一份任务验证记录或现有反馈项：

| 观察 | 记录什么 |
|---|---|
| 用户纠正或返工 | 哪个事实/决定被误读，影响了哪个产物 |
| 知识问题 | 哪份来源冲突、过时或缺失，本次怎么处理 |
| 方法问题 | 哪一步造成无必要打断、错误分流或无效验证 |
| 下次怎么检查 | 针对原问题的候选修改与一个可观察判据 |

没有观察到写“未观察/无数据”，不凭记忆写零。项目事实错误修项目；文档契约或治理流程缺陷修 project-knowledge；开发分流和交付步骤缺陷修本 Skill；检查缺陷修工具。方法维护已在本轮授权范围内时，小步修原条款、补代表案例并复验；越出范围则留具体待办，不虚报已反哺。无缺陷可记录无需修订，不强迫每次新增规则。

当前任务可以整改并反哺，也可以交给独立维护任务；不依赖固定会话。用 PR/commit、Skill 版本和实际反馈交接，并行任务固定所用版本。版本、复验及共享流程见 [维护方法](../project-knowledge/references/maintenance.md) 与 [会话运作](../project-knowledge/references/session-workflow.md)。

## 8. 试用状态与来源

- 本版验收首先是“能在真实任务中正确分流和交付”；通过 YAML/链接检查只说明文件可用，不说明方法成熟。
- [交付与证据约定](references/delivery-contract.md) 连接六环执行与证据；[周一屏参考](references/week-screen-v04.md) 只保留历史定位和防误用边界。代表场景见 [固定评估案例](../project-knowledge/evals/cases.md)，实际结果留 PR/验证产物，不预填行为改善。
- 本版不要求先做全仓特性台账，也不要求先等 CI 整改完成。使用现有能运行的验证，真实缺口单列。
