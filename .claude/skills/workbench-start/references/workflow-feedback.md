# 开发 workflow 的真实任务反馈

> 在真实 Issue 交付收尾、提出 workflow 反哺、每周复盘或解释指标时读取。本文维护六项统计口径、反哺读取路径和效果观察；知识归属与修订确认执行 project-knowledge 的维护方法，日常开发路线留在 SKILL.md，验证与 PR 呈现要求见[开发规范](../../../../docs/development.md)。口径或反哺方式变化时更新本篇；真实读数与改动历史留在原 Issue/PR 和运行产物。
>
> 本文是方法约定；采集、统计与展示是否已接通须另有运行证据。版本总览引用本篇口径，不维护第二套公式。

## 采集与分析

按 Issue 本次约定的交付范围串起相关会话、PR 和人工评审；一个交付跨会话或包含多个 PR 时不重复计算。实际采用本 workflow 的任务均可采样，包括人主动推动、途中采用 Skill 的任务，不以全自动起手为条件。大需求可以按明确约定的阶段交付观察，不能通过拆分 PR 或重开会话改变统计单元、重复计数。

脚本先提取人的实际输入：初始提示、后续文字、AskUser 回答、原型批注、附件引用及 PR 修改意见，保留时间、来源定位和任务关联。复用现有 transcript、journal 和关联读取能力；注入的系统/Skill 内容、工具回显、恢复或分叉复制的历史不能冒充新的人工输入。不确定归属或记录缺失时标明，不能承诺提取完整。

供反哺模型使用的材料以用户输入为主，同时保留可回查的对应提问、展示的方案/原型、首次完成交付说明、PR 修订与评审结论。仅凭“可以”“不行”等孤立回答不能判断提问必要性或返工原因。模型分析每条建议时给出原会话证据、影响、建议修订的原件和下周要观察的结果；事实计数与原因判断分开，歧义保留待核对，不为了统计方便要求用户额外填表。

每次交付在主 PR 留一条由脚本生成的指标评论，包含六项计数、权限请求、用户输入摘要、方法版本与覆盖范围。同一 Issue 的版本总览指标评论保留一份。人审、补修或再次交付后，从最新原始会话重新提取、更新标注，重算并原位更新评论。待审保留未知。截图不可读等证据缺陷导致交付退回时计返工并保留原因，正常咨询另记。原始会话与消息定位留本地，按当前授权发布必要摘要。

用 PR 标题开头的 `[AI] ` 筛选可统计样本。主 PR 已读回脚本生成的评论，且至少一项指标有可核对结果时，在原标题前加一次前缀。修订后所有指标都变为未知时，移除前缀。验证 Review、CI 和合入状态各自留证，合入状态不能推出首次人审结论。历史手写评论仅在可找回原始证据时用脚本重算并原位更新；可核对一部分就只统计这部分，来源不足的旧评论可作为定性反馈，留在指标分母之外。无可统计值或前缀无法更新时，在交付说明里记实际原因。

## 指标口径

主结果是交付返工：模型明确本次约定工作与检查已完成、交 PR 供人审阅后，人认为不能合入、要求修改。首次 PR 链接或草稿创建不自动作为完成截点；实现前的正常方案或原型收敛不算返工。先记录退回与重新交付，再分析方案/原型偏差、实现缺陷、验证或证据不足；同一批意见可有多个原因。

采用以下六项，不增加综合分或另备离线案例；用一周实际运行的会话与返工原因决定是否调整。各项同时提供涉及任务数、可统计分母、来源和未核对范围，发生率不是缺陷率。

| 指标 | 分子、分母或计数规则 | 改进落点 |
|---|---|---|
| 开工额外输入率 | Issue 链接与自动上下文之外，人实际补充内容，本次开工记 1；分母为初始输入可核对的开工任务。保留原文，不按字数或段落累计 | 重复工作要求回 workflow；重复业务背景/约束回特性文档；本次独有要求留 Issue |
| AskUser 发生率与轮次 | 首次完成交付前有模型主动澄清的任务占比，同时记录提问批次、问题与回答；一批多个问题保留明细但算一轮。自然语言提问也需识别，无法识别的标未知；权限请求另标 | 缺答案补资料；已有答案未读到修读取路径；读到仍重复问修决策；真实产品决定保留 |
| 高保真前审发生率与轮次 | 首次完成交付前，模型要求人先审高保真的任务占比，另记评审轮次与批注；用户主动要求先看单列。大小需求分别统计 | 小任务多余审批修分流；反复纠正设计问题补设计规范/特性规格；大需求必要 gate 保留 |
| 人工验证指导率与轮次 | 首次完成交付前，人主动提醒或教模型搭环境、启动真机、跑场景、截图、补复验的任务占比及指导批次。模型主动交证据、人正常看结果不计入 | 不会运行补环境说明；不知道验什么补特性验收；有资料未主动做修 workflow；真实外部条件另记 |
| 人工中途纠偏率与轮次 | 首次完成交付前，人主动纠正理解、范围、既定方案或约束的任务占比及纠偏批次。正常新增要求、回答模型提问、设计探索另分；不把所有中断操作都算纠偏 | 输入理解、上下文选择、约束遵守与执行方式 |
| PR 交付返工率（主要结果） | 模型认为完成并交 PR 后，首次人审要求修改的任务数 / 有明确首次评审结论的交付数。每批意见引起修改并重新交付计一轮，保留原因；未审/未知不计成功，已退回未重交单列 | 先记录退回，再查方案/原型是否偏离预期、实现或验证是否不足，并关联前五项的原始证据 |

除开工额外输入率只需核对开工输入外，交付前过程发生率在同批开工到首次完成交付记录可核对的任务中计算；进行中或记录不全的事件可展示原始次数，不混进完整过程发生率。按 Issue 本次交付归并，不按会话或 PR 数扩大分母。一轮参与可有多个原因标签，总人工介入按原始事件去重，不把分类计数直接相加。返工后的提问、审核、验证与纠偏继续保留相同原因标签，但归入返工阶段，避免把返工造成的参与误当首次交付前补位。

首次可合入率使用返工率同一分母，可作为配套读数，不要求已经执行 merge。Workflow 使用覆盖、实际修订、任务量、待审/未完成和记录完整度是统计背景；仓里有 Skill、点过开工、会话结束、CI 通过、Issue 关闭或 PR merged 都不能替代本次使用与首次人工评审证据。

初始输入不把字数当作效率得分。是否该 AskUser、是否该审高保真、为何返工属于带证据的分析判断；次数、原始评审结论和修订来源可独立读回。模型完成真机操作不计作用户亲自验证；截图存在不代表验证通过，未观察不填零。

## 反哺确认与每周比较

当次任务先形成有证据的候选，经人确认后修回原件，不等每周才处理；每周归并实际修订，用后续真实任务观察效果。不要求另备离线题库，代码修改的工程检查与产品确认继续保留。

反哺写回前完整读取 [project-knowledge 的维护方法](../../project-knowledge/references/maintenance.md#如何反哺本-skill)，执行其归属盘点、具体改前改后对照、AskUser 确认、同批清旧和独立核验。知识放哪、哪些引用/消费者一起改均按当地文档规范决定；本篇不另设一份知识组织规则。

分析时区分缺知识、未读到、未遵守、规则冲突和必要的人决策。指标评论分清已确认并落实的修改与待确认建议，未确认建议不能当作现行 workflow。原话、根因、修改位置、确认来源和观察点留原 Issue/PR；规则正文只留现行方法，不积累每周提醒。

例如，“请启动真实 Electron，再验跨项目切换”反复出现：先查运行说明和验收场景。说明已有而未读，候选应修读取/执行位置；场景缺失则补所属特性的验收定义。查清关联资料后把具体修改交人确认，不同时在 Skill、交付约定和特性规格各追加同一句要求。

每次观察固定周窗口与时区，区分大需求、小需求和 bug，并显示任务量、未审/未完成、证据不足与实际采用修订。返工主指标按首次正式交付所属周归组；跨周才审阅或再次返工时回补原组，并保留本周新增事件，不能把待审当作零返工。跨周任务按实际使用的修订保留关系，无法唯一归因时不硬归新版本。

按标题前缀 `[AI] ` 筛选样本 PR，再逐项按评论的覆盖范围计算分子和分母。统计 workflow 使用覆盖时，另列已知使用但缺指标的交付。

先比较返工率、轮次和原因，再看五类过程参与是否减少；大需求的必要设计协作与小修分开解释。任务构成、模型或环境变化同时注明；一周前后变化是实际观察，不单凭下降就宣称因果改进。出现无依据少问、跳过设计确认或漏验证导致返工时，修正相应决策与资料，不以降低人工参与为由保留错误方法。

本节定义可执行的反馈方式，不表示已启动每周定时任务。版本总览后续展示这些结果时，应保留样本范围、来源、修订与未知情况。
