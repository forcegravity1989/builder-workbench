# BW 开发交付细则

> **读者与时机**：开发、测试和检视 BW 自身的模型与开发者；AGENTS 直接要求在相关开发与交付前完整读取，不依赖调用 workbench-start。
>
> **位置与职责**：本篇是 BW 测试用例、独立检视、验证证据和 PR 呈现的细则正本，沿用现有 Skill reference 承载，不向被管项目分发。上层开发约束听 AGENTS，特性决定与六环听原则 02；Skill 只编排，模板只规定呈现。
>
> **结构与维护**：按验收依据 → 测试 → 检视 → 运行证据 → PR 组织。相关规则或执行入口变化时更新正文，并同批核对 AGENTS、原则 02、workbench-start 与两个输出模板的引用；不保存任务流水、遗留事项或规则修订史。

## 验收依据

[原则 02](../../../../docs/01-principles/02-working-backwards.md) 定义特性制品、人的确认点和六环关系。每次交付沿已有特性、已认可行为、验收点、执行入口串起本次证据；复用现有标识与章节，不另建追溯台账。小修只展开受影响环节，缺失决定先补齐，仍成立的认可不重复审批。

先结合用户承诺、已确认设计与实际复现定性：偏离应有行为是 bug，调整已认可行为是增量需求；不能只凭 Issue 标签或当前代码判断。未复现先调查，不先写“可能的修复”。只写了用例、文件齐全或旧平台曾通过，都不代表当前验收通过。

新增用户价值或明确要求衡量时才展开指标，按已有口径和授权维护；小修不为填表造指标，未知不造数，等待滞后结果不阻塞功能验收。STATUS 只保留当前证据边界和相关 Issue 引用；遗留事项在原生 Issue，变化及验证过程在 PR。

## 测试用例

### 只立两类单测看护

| 可以入库 | 判断与例子 |
|---|---|
| 核心算法函数 | 从数据推导数值或状态的纯函数：信号/健康推导、状态机与视图路由、现算重算、调度触发判定、数据契约与协议解析（TOML、JSON、标签协议等） |
| 与用户 E2E 强相关的数据协议 | 直接对应验收点的数据读写协议；协议错误会使用户旅程失败，或重启后独立读回的数字不一致 |

被测对象是“从数据推导数值/状态的算法或协议”才立单测。**负面清单**：UI 组件渲染、布局外观、文案、交互序列、hook 与界面装配不新增单测；行为正确性由验收点/旅程 E2E 和真壳 Review 看护。文档修改、低风险文字调整不强造测试，旧 Rust 类型名不作为当前实现要求。

### 数量控制与存量维护

- **每特性每次交付新增单测默认 ≤10 例**；核心算法通常个位数，超出须在 PR 正文说明必要性，不把新增回归大坝当交付物。
- **总量只减不增**：`pnpm run check:vitest-count-ratchet` 以 `config/vitest-count-baseline.txt` 约束 `src/main/workbench`、`src/relay/workbench`、`src/renderer/src/workbench`、`src/shared/workbench` 的执行例数。新增须在同一交付删除至少同数量的存量，并在主验证评论说明新增属于哪类看护、删了什么及理由；不能靠提高基线、skip 或注释静音腾配额，skip 仍占额度。
- 已有合规单测随改维护；特性大改时同批盘点、合并重复、删除失效用例。删除依据是看护价值，不能为凑配额删除有效看护。
- 三个单位分开：存量按**模块/测试文件**盘点，单例按**正负面清单**取舍，新增配额按**每特性每次交付**计算。特性不是存量归属边界，不要求另建尚无明确义务的测试特性归属清单。
- 单测是核心能力的秒级回归看护，不追覆盖率；全量套件应保持开发机分钟级跑完。验收点与旅程的初期控量、注册和真实执行要求仍按原则 02 环 5–6。

### 失败先分诊

| 现状 | 同一交付内的处置 |
|---|---|
| 方案已替代被测对象 | 删除失效用例，不为旧方案保留兼容层 |
| 对象仍成立，断言过时 | 更新用例以表达已认可行为 |
| 以上均不成立，确为回归 | 修代码并复验 |

先判断用例价值再修复，不为变绿盲目改代码，不 skip 或注释掉失败。新增超额理由和存量对冲是两个约束，说明前者不能豁免后者。

## 独立检视

交付开始时把“验收与门禁 → 独立检视 → 修正复验 → 提交与 PR”登记为本轮执行清单。推 PR 前由独立 subagent 检视本次交付；可按专长拆分，不要求六个 agent。纯文档任务仍检查适用项，代码、原型或测试无改动时说明依据，不以“不适用”跳过受影响消费者。

### 输入和六项判据

给检视者目标仓与分支、基线和当前 HEAD、未提交 diff（如有）、Issue 范围、已认可 intent/spec/原型、仓外 plan 及当前验证证据。标明资料与实现的版本，让其能独立读取原件；不能只给实现者的“已完成”摘要。

| 检视项 | 必须回答的问题 |
|---|---|
| 代码 BUG | 本次路径及受影响调用方有无真实逻辑错误、边界遗漏或回归？发现须有具体触发条件与位置，静态怀疑和已复现区分 |
| 原型 / spec 一致 | 对照最终认可的规格、原型与实际行为/UI，逐项核对验收判据；有意偏差是否已获认可？截图或源码不能替代应有的运行观察 |
| plan 落实 | 仓外 plan 的每项约定是否有实现与适用验证证据？漏实现、漏验证、未经认可缩减分别指出；没有 plan 的小修按既定交付范围核对 |
| Orca 复用 | 是否先查当前仓已采用的 Orca 能力与真实调用链，并复用技术方案、代码、组件和 UI？另造实现是否确有必要，是否留下冗余机制或不一致界面 |
| 资产清理 | 顶层正本与特性资料是否同步，旧代码、错误尝试、兼容双路径、无效注释、重复文档和过时原型是否已清理？最终特性原型及必要源码是否按原则归档，正文是否混入流水账或遗留清单 |
| 测试与真实验证 | 单测准入、数量与失败分诊是否合规？适用验收是否实际执行、同一路径独立复验，证据版本/环境/读回是否足以支持结论？未验是否如实保留 |

### 发现、处置与复核

输出按发现写清严重程度、文件/用例位置、依据、触发条件或对照差异及影响；覆盖项无发现可合并说明，不写六句无依据的“通过”。每项标明已修正、经人认可调整范围，或确因阻塞未验；记录处置位置与复核结果。应修发现同一交付完成，复跑受影响检查，检视者复核原发现；修改影响其他判据时补检相关项。无法复核如实说明，不能报告检视通过或 PR 已就绪。

独立 subagent 检视须说明所审版本、范围、发现与复核结果；涉及四铁律机制、门禁或发布链时，重点核对对应机制和实际验证。没有实际执行的检视不能标通过。

## 运行证据

### 同一用例复现与独立复验

分析 bug 时在原 Issue 或验证材料固定标准路径：设计依据、未修改基线 SHA、必要数据/配置、入口、操作、用户可观察的预期与实际失败。界面问题同时截图；数据必须能触发判据，例如验证“隐藏会话”必须有会话。源码分支、单测失败或修改后的新行为不能独自证明原问题存在。

修复后由测试 agent 按相同用例、数据、路径和判据独立复跑，在相同观察位置截图并排对照。输入包括原问题、设计依据、路径及版本，不能只给 diff 或实现者结论。不可同时运行的环境顺序交接；不能独立执行标未验。对照仍失败、缺数据、路径改变或基线未证明失败，都不能报告“已修复”；确需改用例，说明原因并补跑基线。纯文档或非界面脚本用相同输入的输出/断言对照。

特性开发按已认可原型/spec 与实际落地对照；原型表明目标，真实执行表明当前行为，两者分别标识。每组证据保留用例名、执行路径、期望/实际结果和版本。

### 环境与证据边界

优先复用用户指定的稳定 dev 实例、已有项目和有效数据，先核对源码、实例归属与数据；首次初始化、破坏性操作或必须隔离时才用一次性 fixture。环境稳定不代表代码有效：改后确认新代码已加载，切换源码保留验证 profile 与数据。

主 checkout 的 `.bw/runtime/verification/environment.json` 可保存本机已确认的工具、限制和验证 profile，忽略不提交；PID、端口与连接现场核对，不把单机限制推广到所有宿主。首次、换机器或记录失效时运行：

```text
node .claude/skills/workbench-start/scripts/run-bw-verification.mjs prepare --root <当前工作树> --assistant codex
```

Claude 使用 `--assistant claude`。脚本定位记录并检查现有 profile/项目；缺依赖沿项目 setup，缺 profile/项目沿原生 dev 启动和纳入入口准备，再核对登记与真实界面。记录存在或启动成功不代表环境可用；未知账号/网络能力保持未知，确需用户独有条件才询问。Windows Codex 真壳操作再完整读取 [Codex 执行参考](codex.md) 的真壳验证部分。

按 AGENTS 与受影响用例执行实际门禁，复用当前 `tests/e2e/`、`tests/playwright.config.ts`、Vitest 和 PR workflow，不复制其他分支命令。界面/行为改动主动真壳取证；纯文档只报文档检查，不强启真壳。

记录源码/产物、用例/方法版本、环境、命令、结果和证据。静态检查、单元/集成、真实 Electron、实际 Orca 模型会话、Git/文件/远端读回分别陈述；HTML 原型、模拟、历史 Rust/WebView2 和截图不能替代真实依赖的验收。源码、用例或环境改变后核对旧报告有效性。实现完成、代码运行、验收通过、用户认可和价值效果分别判断；未知、未实现和未运行不记通过。

### 截图发布

界面/行为改变的判据用真壳截图保留四件套：用例名、执行路径、期望结果、截图。未变旅程链接已有验证报告与证据目录，不逐条重铺；未改 E2E 用例的修复也用相同格式提供临时验证。

截图推到永不合入的 `shots/<分支名>`，图片内嵌使用 `https://github.com/<owner>/<repo>/raw/<commit SHA>/x.jpg` 钉 SHA；不使用 `raw.githubusercontent` 或带斜杠分支名的图片地址。大改的改前/改后对照仍归所属特性 `docs/05-features/<id>/shots/`。

用 [证据发布脚本](../scripts/publish-pr-evidence.mjs) 构造二进制 Git 证据树与固定地址。推后读回远端图片内容，评论写后检查实际渲染能否加载；推送或评论成功不等于证据可读。

## PR 正文与主验证评论

| 载体 | 只放什么 | 更新方式 |
|---|---|---|
| 短正文 | 开头“关联 #编号”，简述问题、最终变化、关键取舍、知识去向和未验范围，链接主验证评论；文档改动交代头部职责变化及授权、内容迁移/删除去向 | 随最终实现重写，不保留讨论流水；不用 Fixes / Closes 自动关闭 Issue |
| 一条主验证评论 | 结论与证据版本，bug 前后或原型/spec 与实际对照，subagent 发现/处置/复核，真实验证及未验边界 | 补验、修复与 head 变化后原位更新，明确仍有效和重跑范围；命令、日志及额外截图折叠 |
| workflow 指标评论 | 脚本生成的六项反馈指标、来源覆盖和方法版本 | 按 [真实任务反馈](workflow-feedback.md) 另行维护，不混入主验证评论 |

正文按 [PR 模板](../../../../.github/pull_request_template.md)，主验证评论按 [验证模板](../assets/issue-verification.md) 裁剪。正文先让人知道最终改了什么，主评论先让人能判断结果；不把命令输出、重复方案和执行流水铺在顶部。

交付收尾完整读取上述真实任务反馈，从原始会话提取、标注并运行脚本，读回指标评论和 PR 标题；`[AI] ` 前缀的添加、移除及统计条件只按该正本维护。指标评论、验证评论、CI 与人审结论各自留证；不能以合入状态推断首次人审通过。

提交、push、开 PR 沿当前授权和 AGENTS 默认交付规则执行；合入、Issue 完成、正式发布或修改远端计划不因本篇获得额外授权。核对 PR 真实 base/head、提交与检查；获准合入后读回 merge commit 与目标分支。依赖 PR 未合入时写明顺序，不能称共享基线已就绪。
