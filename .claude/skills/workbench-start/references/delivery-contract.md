> 30 秒导读：实现、相关知识与可复核证据一起交付。内容定义与知识治理共用；任务大小决定展开程度，不给每个 bug 强加全部表格。

## 一个任务的最小关系

BW 的六环与带入三问以目标分支 [原则 02](../../../../docs/01-principles/02-working-backwards.md) 为正本。对迁移先判断旧用户目标是否仍成立，再处理变化的旅程、平台边界与验收；不把“迁移”当默认照抄或全部重新立项。

| 执行环节 | 本任务怎样接上 | 证据限制 |
|---|---|---|
| intent / spec | 复用仍成立的认可来源；把新取舍和可判断验收落到原件，按项目 gate 处理 | 旧平台批准不自动覆盖新交互承诺；方向明确不等于制品已认可 |
| 实现设计 | 在目标 architecture 定位用例、能力、Electron 数据流，按需读模块/ref；实现后同步取舍 | 设计或源码只说明目标/实现，不说明运行正确 |
| TDD | 维护受影响的已有单测；新增单测只立两类看护——核心算法函数、与 E2E 强相关的数据协议（规范与单特性上限见目标仓环 4） | UI/文案/装配默认不新增单测；文档修改和低风险文字调整不强造测试；存量随特性大改盘点裁并 |
| 验收点 E2E | 当前 spec 与实际用例双向可查，按受影响判据跑当前平台链路并独立读回；特性初期先注册核心验收点，其余稳定后专项回补 | 有脚本或单测不等于 E2E 已通过；未注册验收点与未迁用例在 STATUS 记缺口 |
| 用户旅程 E2E | 按原则在真实 Electron 壳走完整用户目标，标清模型、文件/Git、远端参与范围 | 渲染、HTML 原型、模拟接口或旧 Rust/WebView2 不替代真实旅程 |

实现门禁与验证 Review 随 PR：推前按 SKILL §6 的推 PR 前 SOP 登记 TODO 并逐步完成，其中 subagent 全方位检视覆盖目标仓横切站 B 四维（顶层文档、特性文档资产与老资产清理、实现代码与老方案清除、测试资产配比），发现项同交付修正并记入 PR。人的验收/合入与发布授权另行核对。复用实际 `tests/e2e/`、`tests/playwright.config.ts`、Vitest 和 CI 入口，精确命令从目标 AGENTS 与受影响用例取得，不复制另一分支的 suite、深链或 verify 协议。STATUS 按原则记录六环状态、证据和债务，不能将文档齐全涂成行为通过。

开发触及已有独立特性时，按原则 02 §6.3 核对 intent/spec 及本次行为、验收与旅程依据。缺失或失效的必要定义先落草案；缺失、失效或未认可的决定经人 gate 后再改依赖代码。已有且仍成立的认可直接复用，整理为可定位来源，不重复审批。既有承载缺失时按当前目标补所需内容，不自动恢复整套旧文档；其余实现/验证债留在 STATUS 或 PR。

先按用户承诺、已确认设计与复现结果判断任务性质：实现偏离应有行为是代码 bug；新增或调整已认可行为是增量需求。旧规格与实现一致不自动排除 bug，仍须核对规格是否偏离当前认可的用户语义；不能只凭 Issue 标签定性。依据明确且已复现的 bug 直接修复，不新立特性或机械补六份文件。未复现则说明版本、配置和结果，继续调查，不先写“可能的修复”。缺决定只暂停依赖实现，调查与验证准备继续。

```text
已有特性/约束 → 本次行为增量 → 验收点 → 场景/执行入口 → 本次运行证据
新价值（适用时）→ 引领假设及滞后结果 → 口径/来源/采集 → 观察结果
```

复用项目现有标识或章节链接，不先建 ID 系统。在当前 Issue、spec 或任务计划写清用户结果、范围、所属特性/约束、行为增量和证据入口，不复制第二份现行规格；归属未定记候选，不假装特性全集已确定。

| 验收点 | 场景与可观察预期 | 执行及独立读回 | 本次证据 |
|---|---|---|---|
| 本次改变的具体行为 | 有效输入及风险相关的失败/重开 | 用例、真实环境与数据来源 | 版本、结果、证据链接及限制 |

缺数显示 Unknown 的验收，应以缺数输入检查展示，再补真实读数核对变化；页面渲染成功不证明缺数行为正确。此例不要求给所有任务增加图表测试。

正式指标定义或版本目标的写入按已有授权及协议执行。候选口径不是已认可目标；基线未知不造数。源码、用例、环境改变后核对证据有效性；只写出用例应报告未执行。

新增用户价值或明确要求“特性→指标→E2E”时再展开衡量；小修复用已有口径，不为填表造指标，不让等待滞后结果阻塞功能验收。

## 同一用例复现与复验

分析阶段在原 Issue 或本次验证材料固定一条标准执行路径：设计依据、未修改基线 SHA、必要数据/配置、入口、操作步骤、用户可观察的预期与实际失败结果。界面问题同时截图；必要数据必须真的能触发判据，例如“隐藏会话”要有会话，空工作区不能证明该问题。源码分支、单测失败或改动后的新行为不能独自证明原问题存在。

修复后由测试 agent 使用相同用例、数据前提、操作路径和判据复跑，独立判断原问题是否消失，并在相同观察位置截图；把基线失败与修复后通过并排对照。测试 agent 接收原问题、设计依据、标准路径及版本，执行验证，不只阅读 diff 或复述实现者的结论。不可同时运行的环境按顺序交接；不能独立执行时标未验。对照仍失败、缺必要数据、路径变了或基线未证明失败，都不能报告“已修复”；确需改变用例时说明原因并补跑基线。纯文档和非界面脚本用同一输入的输出/断言作对照。

## 运行证据怎样报告

开工时根据本条变更安排环境与证据。日常 Issue 优先复用用户指定的稳定 dev 实例、已有项目和有效数据，核对源码、实例归属与必要数据后按同一路径取证；首次初始化、破坏性操作或必须隔离时才用一次性 fixture。环境稳定不代表代码可以过旧，改后确认新代码已加载；切换源码时保留验证 profile 与数据。主 checkout 的 `.bw/runtime/verification/environment.json` 可记录本机已确认的工具、网络/资源限制和验证 profile，忽略不提交；当前 PID、端口与连接仍现场核对，不把一台低内存机器的限制推广到所有宿主。

首次、换机器或记录失效时，运行 `node .claude/skills/workbench-start/scripts/run-bw-verification.mjs prepare --root <当前工作树> --assistant codex`（Claude 填 `claude`）。它自动定位记录并检查现有 profile/项目；缺依赖按项目 setup 补齐，缺 profile 或项目则沿原生 dev 启动和纳入入口准备一次，再核对登记与真实界面。未知网络、账号能力保持未知，只有确需用户独有条件时才问；记录存在或启动成功不等于验证环境已可用。界面/行为改动仍按目标 AGENTS 主动真壳取证，纯文档改动报告文档检查。

报告按 [Issue 验证模板](../assets/issue-verification.md) 裁剪：**问题与性质 → 分析/方案 → 标准路径 → 前后并排截图 → 结论**。代码 bug 说明恢复什么应有行为；增量小需求用人话说明方案、为何恰当及影响，让人判断是否沿用现有风格、复用已有能力、避免多余机制。代码质量判断须有实现检视和验证依据，不能只以测试通过背书。顶部只留这些判断信息，命令、门禁与额外截图折叠；每组保留用例名、路径、预期/实际和版本，未复现如实标明。

截图地址与权限遵守目标 AGENTS；用 [证据发布脚本](../scripts/publish-pr-evidence.mjs) 生成二进制 Git 证据树和钉 SHA 图片地址，避免临时文本管道改坏文件名。发布后检查远端图片内容，评论写入后再检查实际渲染图片能否加载；推送或评论写入成功不等于证据可读。

记录源码/产物版本、用例/方法版本、环境、命令、结果和证据，说明修改后旧报告是否仍适用。静态/脚本、单元/集成、真实 Electron、实际 Orca 模型会话、Git/文件/远端读回分别说明覆盖；历史 Rust/WebView2、HTML 原型、截图或模拟不能替代当前真实依赖的验收。反馈指标放单独的简短 PR 评论，保持验证报告专注于这条问题的结果。

代码可运行、验收通过、用户认可、价值已证实分别陈述。未实现、未运行和未知不记通过；合入、完成与发布仍按人的授权。
