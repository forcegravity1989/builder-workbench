## 3. 两个必须区分的交付

### A. 功能落地与 BW 首用结果

模板、数据格式、技能是可复用能力；**还要有 BW 作为被管理项目的本周 v0.4 真实周一屏结果**。整条链应实际走完：取得输入 → 模型会话/人工反馈 → 结果修订 → 确认归档 → 打开并读回。

朱宇复用、验收福东的产物并反馈具体缺口；不默认替福东重做全部设计。真实结果保留项目/版本、来源、确认状态、责任与变更记录。原型中的示例数值不得代入真实项目；缺数和待确认必须可见。

### B. 周一屏特性自身的衡量与验收

写清这一特性带给用户的价值，再分别建立：

- 价值目标 → 引领假设/滞后结果 → 公式、窗口、数据源与采集脚本/手工方式。
- 行为约定 → 验收点 → E2E 场景/执行入口 → 实际证据及未验证范围。

“结果 HTML 展示了哪些项目指标”与“用什么指标判断周一屏这个特性有没有价值”是两层，分别表述。本周应做到可定义、可采和实际首用验证；长期效果按真实观察周期收集，不伪造滞后结果。

## 4. 候选指标：讨论起点，不是已认可口径

| 候选 | 定义 | 来源与限制 |
|---|---|---|
| 引领：承诺可验收定义率 | 计划冻结时，同时有责任人、明确验收点和证据落点的承诺项 / 冻结承诺项总数 | 确认数据与 Issue；字段存在还需判断语义；基线/目标未知 |
| 滞后：原始承诺验收达成率 | 截止约定时点由人验收的原始承诺项 / 冻结承诺项总数 | 冻结快照与验收记录；关闭标签不单独证明验收主体；新增/取消单列 |
| 约束观察 | 准备/讨论耗时、定义不清导致的澄清与返工 | 首用先记事实，不从单个样本宣称因果改善 |

若用户或现有方案已经确认了更合适的口径，沿用它而非重新套本表。新口径/目标先展示具体定义，认可后才接入正式指标配置和采集。
