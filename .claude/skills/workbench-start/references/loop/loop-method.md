> **30 秒导读**：本文件只写两件**判据原文没覆盖、且不随项目变**的事：① 把"人读入口"变成"自转 loop"要做哪几件事；② loop 的运行时骨架有哪几种形态。**判断框架（六要素/四大器/builder/双指标/反哺）的权威原文在同目录 [`workflow-audit/`](workflow-audit/SKILL.md)，本文件不重抄**；一个真实 loop 实例见同目录 [`fixer-record.md`](fixer-record.md)；BW 的应用见 [`bw-loop-report.md`](bw-loop-report.md)。
> **读者与时机**：BW 侧负责落地的人与专家 agent；开工前读一次。

> **来源与自包含**：综合 `workflow-audit/` 判据与 `fixer-record.md` 实例得到；不依赖任何外部路径、无需联网。

## 0. 一句话

> **Loop = 常驻编排 + 薄状态机骨架 + 分诊决策 + 确定性卡口 + 蒸馏内联的纪律 + 证据驱动的独立证伪 + 编译报告 + 可回放的离线案例集。**

"入口"与"loop"的差别**不在自动化程度**，而在三者：

1. 骨架是否**外存**（状态不在对话里，能断点续跑）；
2. 判断是否被**独立证伪**（不是自审、不是"看着像好了"）；
3. 纪律是否被**机械卡住**（不靠 prompt 自觉）。

## 2. 六个转型动作（入口 → loop）

一个"人读入口"之所以还不是 loop，差的是下面六件事。**每件都在 `fixer-record.md` 里有对应的真实部件。**

| 动作 | 做什么 | 判据 |
|------|--------|------|
| **① 状态外存 + 单一权威状态机** | 把 SOP 的"步骤"提炼成**状态 + 转移条件表**；状态值见名知义；一处定义、编排与设计都依赖它 | 状态在文件里、不在对话里；能**断点续跑**（读已有产物 → 返回状态） |
| **② 编排只调度不执行** | 主 agent 只做"派子 agent → 读结构化返回 → 按状态机转移"；拆**单一职责、fresh-context 的 worker** | 编排**不**自己改码/判码/跳步/补刀；派发 prompt 只放场外事实，**流程步骤全在 worker 的 md** |
| **③ 确定性卡口** | 反复被绕过 / 总忘的纪律**下沉成脚本硬门禁**（退出码路由） | 卡口**不靠 prompt 自觉**；失败回退到对应 worker，而非再叮嘱一遍 |
| **④ 证据驱动 + 独立证伪** | 复现(RED)与验证(GREEN)**同一批测试点**；**禁 mock**；评估器与执行器分离 | 判定者**亲读原始证据**、**不信自审**；**可观测翻转才算验证** |
| **⑤ 报告是编译产物** | 结果报告**从证据文件拼装**（不是"写一篇"）；过程报告 = 执行轨迹 + 派发/返回原文 | 事实由自动渲染、人话解读由人写，**两者不重复**；**完成只由人确认** |
| **⑥ 双层记忆 + 改进器 + 反哺** | 项目记忆与"被处理对象"记忆分开；改进器 = 离线案例集 + 规范两套 | 被处理对象**一对象一条账**；偏差**记理由**（有理由=反哺素材，无理由=偷懒） |

> 通用模式：**Agent 每犯一个错，就工程化一个让它不再犯的方案**——回应踩坑不是"再加一句 prompt"（措辞总能被新话术绕过），而是把防御编码进卡口或规范。

## 3. 底座谱系（**不锁定**，选型由落地任务出证据后定）

loop 的运行时骨架至少有三种形态；**本文件不预设选哪种**：

| 底座 | 形态 | 已知优点 | 已知代价 |
|------|------|---------|---------|
| **A · SKILL 编排** | 编排 `SKILL.md` + `agents/*.md` worker + 脚本卡口 + 状态机 md | 无新依赖、可读可解释、与 `.claude/skills` 天然一致 | 编排在模型上下文里；状态机靠 md + 脚本维持 |
| **B · 脚本 + SDK harness-agent** | 确定性脚本当骨架，经 SDK 调 harness agent 并注入 `agent.md` 提示词 | 骨架纯确定，agent 只在真正需 LLM 处介入 | 需编排代码 + 宿主集成 |
| **C · 声明式 workflow 引擎** | activity DAG + 产物依赖 + `run_next_activity` / rollback | 断点续跑/回滚/可视化现成 | 接入需新造状态主从与本地规则接线 |

> **共同北方星**（见 `workflow-audit/framework.md` §六）：好的编排**理想可转脚本驱动**——脚本（卡口/状态机）是硬骨架，agent 干真正需 LLM 的活；**边界由脚本框 → agent 不越权**。

## 4. 拷问清单（改造前 / 每阶段收口时对照）

- [ ] 状态是否**外存**？有没有**单一权威状态机源**？断点续跑能否恢复？
- [ ] 编排是否**只调度**？有没有越权改码/判码/跳步/补刀？
- [ ] worker 是否**单一职责 + fresh-context**？派发 prompt 是否只放场外事实、步骤全在 worker 的 md？
- [ ] 反复被绕过的纪律，是否已**下沉成脚本卡口**（有退出码）？
- [ ] 复现与验证是否**同批测试点**？是否**禁 mock**？未复现是否走**人盯门**而非兜底？
- [ ] 判定者是否**独立于执行者**、亲读原始证据？是否**可观测翻转才算验证**？
- [ ] 报告是否**编译产物**？过程轨迹（含回退/重试/GATE）是否落盘？
- [ ] 是否**双层记忆**分得清？被处理对象是否**一对象一条账**？
- [ ] 四大器是否**齐**？改进器（离线案例集 + 规范两套）在不在？
- [ ] 反哺偏差是否**记了理由**？
- [ ] 完成/合入/验收是否**只由人确认**、自动化不推终态？
- [ ] 是否有 **GATE 人盯门**，且**自主性是阶梯挣来的**？
