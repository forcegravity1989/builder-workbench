# workflow-audit 框架（思想 home，自包含）

> v1,慢慢完善。本文件是"workflow/loop 项目审计优化"思想的总纲：把六要素/四大器/builder实践/双指标/反哺编码成可复用判据。跑 `workflow-audit` Skill 于任何 workflow 项目即用此框架拷问。不依赖任何本地路径。

---

## 一、Harness 六要素（每要素 = 业界做法 + 落地判据）

驾驭模型稳定跑闭环的六块控件,缺一块都漏。审计时每要素判"到位否"。

| 要素 | 业界做法 | 落地判据（怎么算到位） |
|------|---------|----------------------|
| **上下文** | 活文档、按需检索、不全量喂 | 有薄入口(SKILL/README)分层供给；**谁读哪段**有约定（非整本喂）；活文档有 owner、不 stale；上下文与代码同源不漂移 |
| **工具** | 工具隔离、白名单、确定性卡口 | 工具白名单显式；**反复被绕过的检查变成脚本硬卡口**(不靠 prompt 自觉)；副作用操作有安全边界(打哪安全明确) |
| **编排** | Orchestrator + Worker、思考与执行分离、状态外存 | 主编排**只调度不执行**；有单一权威状态机源；断点续跑可恢复；执行轨迹 append-only 落盘 |
| **记忆** | 文档园丁、持续还债、双层 | 分**项目记忆**(工程自身)与**作物记忆**(被维护对象)；改动必落账(ChangeLog)；防反复横跳改坏 |
| **评估观测** | Agent 审 Agent、测试 oracle、证据驱动 | **结果评估器**+**过程评估器**分开；**禁自审**(独立证伪)；oracle 客观可判优先(退出码/JSON/扫描器 > LLM 判)；**可观测翻转才算验证**(RED→GREEN 状态机判,不读措辞) |
| **约束恢复** | Linter/CI 阻断、Human Steer、架构约束 | 有 GATE 人盯门(难题人介入)；机械卡口(validate_step)覆盖关键纪律；**验证有效性门禁**(状态翻转才算验证,否则判测试无效)；不过拟合单案例(防 Architecture Drift) |

> 六要素到位否判据：每要素都有对应组件 + 真实运行证据,不是写进文档就算。缺组件 = GAP,有组件但没运行证据 = 名实不符 GAP。

## 二、Workflow 四大器（一个能自转的 loop 必备）

| 器 | 是什么 | 到位判据 |
|----|--------|---------|
| **生成器** | 产案例/产执行/产修复的主编排+角色 | 有角色定义(单一职责) + 真实跑通至少 1 条 issue→MR 闭环 |
| **评估器 ×2** | **结果评估器**(逐测试点判定) + **过程评估器**(终审+看门) | 两器分开；结果评估器机判读状态/产物不 grep 措辞；过程评估器不信自审亲读原始证据 |
| **可视化可反馈报告 ×2** | **结果报告**(证据编译,前后对账) + **过程报告**(执行轨迹卡) | 报告是**编译产物**(从证据脚本拼成),不是写出来的；**清晰 > 标准**,人有反馈渠道；过程报告含回退/重试/GATE 决策轨迹 |
| **改进器** | 离线案例集(能跑) + flow 维护规范两套(公共 spec + 私有资产 md 规范) | 离线数据集本地留存可回放；**公共 spec**(agent/skill-md-spec)与**私有规范**(各资产 md 维护/agent 解题/沙箱 md 规范)齐全；遇到问题按 flow 规范改,不靠记 |

> **四大器缺口判据**：任何一器缺 = loop 不能自转。改进器是最常缺的——离线案例集 + flow 维护规范两套到位,loop 才能自转改进。
> **connectors**：连接外部数据源/业务流的基础连接器(skill script 里 import 调用),是后续可统计的资产方向。

## 三、builder 工作台实践（4 条铁律）

| 实践 | 要点 |
|------|------|
| **看板反向约束规范** | "统计不到 = 没规范"——看板能统计的才有规范,统计不到的等于没规范。看板是规范的检验器,不是装饰 |
| **资产台账** | 每个资产有 owner / 活跃度 / last_verified；无 owner = 无人看护 = 活跃度可疑；超期未核验 = stale。**注：env.md 不单列 owner**——归属=它服务的 skill（隐式 owner），单列是冗余（反哺自 fixer builders 看板实践，2026-07） |
| **建规范→SubAgent 检查→砍冗余 loop**（铁律） | 规范建到哪层 → 开 SubAgent 检查该规范约束的资产 → 砍冗余/不通顺/非规范衍生。偏差都记理由,供后续公共 spec 对比回流 |
| **connectors**（外部系统连接） | **我们连接的外部系统**（如 fixer 对接的 welink/codehub），不是数据源连接器（maas 把 connectors 当数据源连接器，fixer 实践后纠正）。refresh-board-data 是 skill 归 SkillHub、定时脚本归 CronHub，不塞 Connectors——资产分类清晰才能统计（反哺自 fixer builders 看板实践，2026-07） |

## 四、双指标（引领性 + 滞后性）

> **（反哺自 fixer builders 看板实践，2026-07）** 原写"引领=流量/滞后=存量"，与 loop-buddy 4DX 权威轴标签相反。修正为 4DX 轴：引领=可控行动、滞后=结果。权威源：loop-buddy HTML 原型 step3/4/5 + 用户网搜确认——"滞后告诉你结果是什么，引领告诉你现在该做什么改变结果"。

| 指标 | 是什么 | 可统计判据 |
|------|--------|-----------|
| **引领性**（可控行动） | 本周/本周期可主动推动的**先行动作**——"现在该做什么改变结果" | **脚本/台账可统计**——可控/可统计/难造假（缺一不可） |
| **滞后性**（结果） | 反映结果、验证引领是否有效、无法直接操控、滞后几周才动；不动则质疑引领选错 | **结果可统计**——只用于验证引领是否真的驱动了结果 |

> 双指标必须都能统计才算闭环。引领=可控行动（脚本/台账可统计）；滞后=结果（验证引领有效性）。**引领驱动结果，滞后验证引领**——轴标签以 loop-buddy 4DX 为准。

## 五、反哺点（深度实践偏差 → 公共 spec 回流素材）

> 深度实践项目会因场景特有取舍偏离公共 spec。偏差都记理由,是反哺公共 spec 的素材。**待对比验证后回流**,不盲回流。

| 偏差点 | 实践取舍 | 理由 |
|--------|---------|------|
| agent `description` 角色式非触发式 | 写"角色+做什么+边界",不写"何时触发" | fresh-context 派发 agent 由编排 SKILL 决定何时触发；agent 拿到 prompt 需自我定位,角色式比触发式有用 |
| 8 段头+红旗表 hybrid（非纯 implementer-prompt 8 段） | 用 8 段标准头统一结构 + 保留 superpowers 红旗表（Excuse→Reality）作纪律子段；Before You Begin 段在但 = 状态码指针（"有疑问→`NEEDS_CONTEXT`/`BLOCKED` 不交互问"） | 8 段头统一少自定义偏差；红旗表保留 superpowers 精华；Before You Begin 不开交互通道，状态码契约覆盖"有疑问" |
| superpowers 红旗表+步骤风格 vs implementer-prompt 8 段 | 用红旗表(借口→现实)+步骤+返回格式,不用 8 段散文 | 红旗表内联纪律 = superpowers 6.x 风格,比 8 段精简 |
| 四码状态 + verdict 并存 | `DONE`/`DONE_WITH_CONCERNS`/`BLOCKED`/`NEEDS_CONTEXT` 四码 + reviewer `verdict` 另一轴 | 状态码供编排路由；verdict 是审查判定,两者并存不互斥 |
| 诊断+执行非码类豁免 Code Organization | reviewer/test-runner/skill-user/executor 无代码可组织时强加 = 空话 | maas §十一已豁免诊断类,本 workflow 扩到执行非码类 |

> 这些偏差是**深度实践的产出**。审计任何 workflow 项目时,看它有无类似取舍 + 是否记了理由。无理由的偏差 = 偷懒,有理由的偏差 = 反哺素材。

## 六、审计补遗原则（来自 fixer 重构纠正，2026-07-21）

> 这些是审计 fixer 时用户纠正揭出的原则，通用化为审计判据。审计任何 workflow 项目时一并拷问。

| 原则 | 审计判据 |
|------|---------|
| **规范先行** | 改资产前先改规范——删 test/重构前，对应维护规范先写进 AGENTS/规范 md。若"直接改资产没先立规范" = 违规（AGENTS 不够全到"一读就有规范可循"）|
| **SKILL 派发 prompt 边界** | 编排 SKILL 派发 agent 的 prompt = 场外信息（issue/paths/env.md/mode/适配）+ 小判断（编排 routing 留 LLM）；**流程步骤全在 agent.md**（不重抄 a-g，单一权威源）。SKILL prompt 重抄 agent 步骤 = 双源漂移 GAP |
| **去模型层级 framing** | 不绑死模型层级（"medium/strong 模型"）。workflow 驾驭模型跑闭环，模型层级是可替换底座，不该写进设计 framing。出现"medium 模型"等 = stale |
| **脚本驱动理念** | 好的 workflow 编排**理想可转脚本驱动 agent**——脚本（卡口/状态机）是硬骨架、agent 干真正需 LLM 的活。审计判：哪些是脚本可驱动的（workflow 骨架），哪些真要 LLM（agent）？边界由脚本框 → agent 不越权 |
| **逐行 check 不可省** | 重构不能只按 plan 点改——整文件逐行 check 才发现"§2.3 改了但 §零/§1.1 medium 没跟""§三角色表复述 agent 60 行"等漏改。逐行 check 是规范落地的保证 |

> 这 5 条是 fixer 重构（3.10.6-3.10.8）被用户纠正后沉淀的。随 fixer 继续演进，本节继续补。

## 七、双北极星偏离（反哺自 fixer builders 看板实践，2026-07）

> loop-buddy 主张"唯一北极星"。fixer 实践偏离为**互相约束的双北极星**——有理由偏离，非违反 loop-buddy。

| 偏离 | 实践取舍 | 理由 |
|------|---------|------|
| 唯一北极星 → 双北极星 | fixer 用户价值有两面：**省心(效率北极星 NS-A) + 不修坏(质量北极星 NS-B)**，双北极星互相约束 | 单北极星会被钻空子：放水修降介入率（NS-A↓ 但回归↑）/ 少修保质量（NS-B↓ 但介入↑）。双北极星互相约束防单点作弊 |

> **适用判据**：用户价值有**两面且互相矛盾**时，可用双北极星互相约束。单面价值项目仍用唯一北极星。
