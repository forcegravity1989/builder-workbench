# Workbench 起手 Loop 内部调研报告与分阶段落地 Plan

> **30 秒导读**：本报告把 `workbench-start`（当前"人驱动的开发入口"）拷问成一份诚实 GAP，再给出从"入口"到"能自转的交付 loop"的分阶段路线。判断框架的**原文**在同目录 [`workflow-audit/`](workflow-audit/SKILL.md)，通用套路见 [`loop-method.md`](loop-method.md)，一个真实实例见 [`fixer-record.md`](fixer-record.md)。
> **读者与时机**：BW 侧负责落地的专家 agent，以及决定节奏的人；落地开工前读一次，每个阶段收口时对照 §4 的验收判据。
> **职责与边界**：**本报告只做调研与规划，不做 BW 落地**——具体改哪些 SKILL/agents/脚本、每步怎么写，由落地任务按其正本产出。报告不含产品主张，不记变更流水。
> **来源与自包含**：方法论综合自同目录的 `workflow-audit/`（原文）与 `fixer-record.md`（实例），**自包含，不依赖任何外部路径、无需联网**。文中对 BW 现状的判断均为"读取到的现状"，**以落地任务的复核为准**。

## 1. 结论 · 目标 · 边界

**一句话结论**：`workbench-start` 现在是一段高质量的**人读 SOP**；六个转型动作里**动作 ①②③ 基本为空**——没有状态外存、没有编排与 worker 分工、没有 loop 级机械卡口。要让它"既能人起手、也能自动跑"，不是加自动化开关，而是**先补外存骨架与机械卡口**，再谈自动化触发。

**目标**：把 `workbench-start` 从"人驱动的一次性入口"升级为**双触发交付 loop**——同一套骨架，既能由人在外部 IDE 起手，也能由巡检/定时自动起手。

**本次范围锁定（按已对齐的口径）**：

| 维度 | 本次范围 |
|------|---------|
| **工单** | BW Issue（`issue-state.md` 的状态机与标签正本） |
| **终点** | **只到 MR**（同 `fixer-record.md` 所述形态）；**不**延伸六环/STATUS/验收/发布 |
| **首期催熟路** | **小 bug / 已有特性修复**（复现 RED → 最小修 → 验证 GREEN → 独立检视 → 报告 → MR）；其余路先挂人 gate |
| **分层** | 开发方法资产（`.claude/skills/`）；**不算产品特性**，不走 `docs/05-features/` 链 |
| **铁律** | 自动化/agent/定时**不得推 Done**；模型只可把 issue 状态改到"待评审"；完成/合入/验收只由人确认 |

## 2. 现状盘点

### 2.1 `workbench-start` 现在是什么

一个仓内 pilot（`.claude/skills/workbench-start/`，0.4.3-pilot）：起手核对目标仓/分支/证据 → 按**意图与影响**分流（六种工作类型表）→ 按影响接**六环**（原则 02 §6.2）→ 实施与知识最小同步 → 验证/交付（含**推 PR 前 SOP**：验收门禁 → subagent 四维检视 → 修正复验 → 提交 PR）→ 反哺。

- **强的**：分流判据清晰、六环与横切站 B 对齐、反哺节完整、证据层级（实现/运行/认可/价值）分得开。
- **形态**：**文字 SOP**——告诉模型"该怎么做"，但**流程状态不在文件里、没有编排分层、没有机械卡口**。

### 2.2 BW 已有的 loop-adjacent 资产（事实清单，非建议）

| 资产 | 与本 loop 的关系 |
|------|-----------------|
| `standard/system-prompt/references/issue-state.md` | **Issue 状态机与标签正本**——loop 的工单状态必须服从它 |
| `standard/system-prompt/references/build.md` | 改仓规则（分支 / MR / 合入是人 / 提完 MR 改 `bw:status:inreview`） |
| `standard/system-prompt/references/review.md` + `.claude/skills/.../mr-review` | 独立评审（"只评不改"） |
| `docs/01-principles/02-working-backwards.md` §6.2 | **六环正本 + 横切站 B**；本 loop 首期只到 MR |
| `.claude/skills/project-knowledge/` | 知识治理方法 + **固定评估案例**（`evals/cases.md`） |
| `src/renderer/src/workbench/version-cycle/`（`cycle-prompt.ts` 等） | BW 现有**提示词注入 + 原生自动化登记**机制 |
| `.github/workflows/pr.yml`、`husky`、`check:vitest-count-ratchet` | **提交点门禁**（横切站 A） |
| 外部可见的 `gts-codeharness-engine`（MCP workflow 引擎，本会话工具集可见） | 声明式 activity DAG 底座**候选**；**未接入 BW 仓**（仓内 `**/harness-workflow/**`、`.codeharness/**` 零命中） |

## 3. GAP 报告：用判据拷问 `workbench-start`

（判据原文见 [`workflow-audit/framework.md`](workflow-audit/framework.md)。**到位度** ✅/⚠️/❌ 为读取到的现状，**待落地任务复核**。）

### 3.1 六要素到位度

| 要素 | 现状 | 到位度 | Gap |
|------|------|:---:|------|
| 上下文 | 薄 SKILL 入口 + references 渐进披露 + `docs` 知识库 + `AGENTS.md` 按任务读取 | ⚠️ | 有"读什么"，无"**谁读哪段**"的编排约定；无 per-对象记忆 |
| 工具 | 提交点门禁齐（husky / `pr.yml` / ratchet） | ⚠️ | **无 loop 级卡口**：门禁在"提交"这一点，不在"分诊/复现/验证"各流程点；无工具白名单 |
| 编排 | 纯 SOP；步骤在文字里 | ❌ | **最大缺口**：无编排/worker 分工、无单一权威状态机、无断点续跑、无执行轨迹 |
| 记忆 | `STATUS.md` 六环 + `intent/spec` + commit/PR 留痕 | ⚠️ | **项目记忆有、作物记忆无**：被处理对象无"一对象一条账"的持续记忆 |
| 评估观测 | 横切站 B 独立 subagent 四维检视；`/code-review` 召唤制独立评审 | ⚠️ | 无**复现→验证证据链**（RED→GREEN 同批测试点）；无 oracle；**结果/过程评估器未分离** |
| 约束恢复 | intent/spec 人 gate + CI 门禁 + 人验收 | ⚠️ | GATE **未状态机化**；无 `human_decision` 落盘；"验证有效性"未门禁化 |

### 3.2 四大器到位度

| 器 | 现状 | 到位度 | Gap |
|----|------|:---:|------|
| 生成器 | `workbench-start` 可作编排雏形 | ⚠️ | 无**单一职责 worker** 拆分；无"跑通至少 1 条闭环"的运行证据 |
| 评估器 ×2 | 独立评审（reviewer-agent） | ⚠️ | **结果/过程两器未分开** |
| 报告 ×2 | PR 验证报告（四件套截图）、版本验收材料 | ⚠️ | 无"**从证据编译**"的编译脚本；无**过程报告**（执行轨迹卡） |
| 改进器 | `project-knowledge` 固定评估案例 + 维修方法 | ⚠️ | 无"**离线可跑案例集**"；规范未分**公共 spec / 私有两套** |

### 3.3 事实小结

- 六要素：**上下文与记忆最强，编排与工具最弱**——这正是"入口 ≠ loop"的根因。
- 四大器：**一器都没有"到位"**（缺运行证据或部件缺失）；首期最小集是**生成器 + 结果评估器**（跑通一条 MR 闭环）。
- **不是推倒重来**：BW 的上下文、记忆、门禁、独立评审都是好底子，**缺口集中在外存骨架、卡口与证伪链**。

## 4. 分阶段落地 Plan

节奏原则（参照成熟 loop 的落地节奏，见 `fixer-record.md` §1）：**架构可一次想清，但成熟度一条路一条路催熟**——先把"小 bug 路"跑稳到可靠，需求/文档路先用人盯门挡住，逐轮再催熟。**每阶段都在上一阶段真实跑通后才开始。**

> 每阶段列：**目标 / 交付物 / 验收判据 / 人 gate / 风险**。交付物里"文件"是**建议落点**，最终由落地任务定。

### P0 · 起手骨架（先把"入口"变"编排"）——人全程盯
- **目标**：把 SOP 提炼成**状态机 + 编排只调度 + 最小 worker 分工**，能对一条真实 BW Bug Issue 跑完"分诊 → 复现 RED → 修 → 验证 GREEN → 检视 → MR"。
- **交付物（建议）**：状态机单一权威源（状态 + 转移表 + 终态）；编排入口（只调度不执行）；最小 worker 拆分（分诊/复现取证/修复/验证判定/终审，各一薄 md）；断点续跑脚本；append-only 执行轨迹文件。
- **验收判据**：对**一条真实** BW Bug Issue 跑通闭环并产出 MR；期间**杀掉重开**，脚本能读回正确状态续跑；执行轨迹完整。
- **人 gate**：**全程人盯**（每步可打断）；未复现 → 人确认；任何越界立即停。
- **风险**：worker 拆分过细导致透传舞 → 先粗粒度起步；编排被模型上下文吞掉 → 关键决策**外存到文件**再做。

### P1 · 机械卡口 + 独立证伪（把纪律钉死）
- **目标**：把"总想绕过/总忘"的纪律下沉成脚本门禁；把"验证"变成不可自审的证据链。
- **交付物（建议）**：卡口脚本（产物是否产出 / 证据是否非空 / diff 范围是否越界 / 关键记录是否存在）；**RED→GREEN 同批测试点**表；评估器与执行器分离；未复现的 **GATE 落盘**（人决策记录）；**禁 mock** 硬约束。
- **验收判据**：卡口能**机械拦住**一次真实越界（构造违规，脚本以非零退出码拒绝）；验证判定能给出**可观测翻转**（RED→GREEN 有 stdout/退出码/diff 的可观测差异）。
- **人 gate**：未复现门、规模门（大改走人确认）保持人盯。
- **风险**：卡口过度 → 把简单问题复杂化。**卡口只覆盖"反复被绕过"的少数纪律**，其余靠规范与 worker md（参照 `fixer-record.md` §13）。

### P2 · 报告编译 + 自动起手（patrol）
- **目标**：结果报告**从证据编译**；让 loop 能**自动起手**（事件/定时触发）。
- **交付物（建议）**：报告编译脚本（证据 → 前后对账 HTML）；过程报告数据源（执行轨迹 + 各 worker 派发/返回原文）；触发层（巡检 BW Issue → spawn/续跑）。
- **验收判据**：人**看报告**即可决策是否推 PR，不必翻代码；**到点/到事件真触发**一次真实 run；报告含回退/重试/GATE 轨迹。
- **人 gate**：MR 前的人确认；**自动起手只建"待处理"，不替人拍板**；完成仍由人点。
- **风险**：自动触发与 BW 现有原生自动化（`version-cycle`）的关系要理清——避免两套调度。

### P3 · 改进器 + 指标（让它能自转改进）
- **目标**：离线案例集可回放 + 两套规范；接双指标，看板反向约束规范。
- **交付物（建议）**：离线案例集（把真实 issue 沉淀成可重跑案例）；**公共 spec + 私有资产规范**两套；引领/滞后指标口径 + 采集（能统计才算规范）；本地复盘存档（旁路，不推远端）。
- **验收判据**：案例能**离线回放**并在改动后重现；指标**可统计、可复核**（统计不到即标灰，不标绿充数）。
- **人 gate**：指标口径经人确认；改进结论回流规范**待对比验证**，不盲回流。
- **风险**：改进器最易被跳过 → 它是"能自转"的分水岭，至少先留一个能跑的示范案例。

## 6. 与四铁律 / 现有资产的接线（不可省）

| 接点 | 约束 |
|------|------|
| Issue 状态与标签 | 服从 `issue-state.md`；模型**只可**把状态改到 `bw:status:inreview`，**不得**关闭/合入/标完成 |
| 完成 | **人**在 Workbench 点；自动化/agent/定时**不得**推 Done |
| 改仓 | 服从 `build.md`（分支 / 提 MR / 合入是人） |
| 独立评审 | 复用 `review.md` / `mr-review` 的"只评不改" |
| 知识同步 | 复用 `project-knowledge` 的方法，不另造台账 |
| 自动起手 | 关系需理清：与 `version-cycle` 原生自动化登记/触发，避免两套调度 |
| 本地零业务库 | loop 的账/案例/轨迹落**文件**，用 `git`/`gh` 独立读回；不引数据库 |

## 7. 反哺点与未决

**反哺素材（本方法对公共规范的候选偏差，待对比后回流）**：
- loop 的终点取"只到 MR"，比"六环全链"窄——场景取舍，记理由。
- BW 已有"召唤制独立评审"，与"内建过程评估器"如何共存——待实践后定。

**未决（需人/落地任务决定）**：
- 底座 A/B/C 的最终选型；

- 是否/如何把方法回灌到 `standard/`（面向被管项目）——**本报告不主张自动分发**。
