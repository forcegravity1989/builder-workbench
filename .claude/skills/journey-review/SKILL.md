# BW 旅程走查与整改

围绕用户选定的入门项、工作旅程或功能屏，边走边修、边补引导，更新两张内容矩阵中的对应行。面向 BW 研发会话，不向被管项目分发。产品分工、状态口径与内容标准只在[引导与旅程规范](../../../docs/04-design-system/guidance.md)维护，本篇负责执行。

## 起手与范围

1. 完整读取目标仓的 [AGENTS](../../../AGENTS.md)、[workbench-start](../workbench-start/SKILL.md)、[开发规范](../../../docs/development.md)及[引导与旅程规范](../../../docs/04-design-system/guidance.md)。执行其中适用的隔离、验证、检视和交付要求；不另加一套本机 CI 或平台操作规定。
2. 从已有会话与 Issue 采用用户指定的范围、角色、环境和授权，定位 **BW 入门**或**探索 BW（工作/功能）**的具体行；读该行各格的资产、证据及复用行，再读 [architecture](../../../docs/architecture.md)对应入口、[特性矩阵](../../../docs/05-features/README.md)及相关 intent/spec/STATUS、原型和实际调用链。核对当前源码与运行版本，既有截图或旧验证不自动适用。
3. 用一段话说明选中哪行、起点、可见结果、最短路径及验证方式。工作行按需串起入门和功能行；用户只指定一个屏幕或配置项时，就处理该项并维护复用关系，不扩大到整条工作旅程或所有行。只要求梳理或评审时保持只读，只报告建议、不修改矩阵；实施时尚无对应行的已选内容，按规范归类补一行。

有真正未决的意图、交互取舍或用户独有条件时，用 AskUser 给出具体差异、推荐及影响，只暂停依赖答案的部分；已确认决定与授权直接沿用。用户要开发且依据充分时，连续推进修复、资料同步和 PR，不能只交盘点报告。用户未指定旅程且上下文无法确定时才请其选择，不自行排子窗口或启动所有旅程。

## 走一遍，定位阻力

- 复用用户指定环境和数据，从真实入口开始，记录基线版本、前提、动作、预期/实际结果与失败恢复。新安装旅程才核对安装和首次启动；不为走查擅自卸载、清配置或登录其他账号。
- 核对这条路径涉及的必要组件、智能体与权限是否可检测、可配置、失败后可继续；可选能力未启用和数据未知时，哪些动作仍可使用。不能用全部配置完成或全部教程看完代替开工条件。
- 观察用户在哪一步找不到入口、不懂对象、重复输入、等待无结果、被额外选项打断，或切屏/重开后丢失上下文。优先查当前已采用的 Orca 原生能力及扩点，再判断是否缺实现。
- 按选中行逐格核对入门/探索内容、屏内问号、首次触发、指南与传播资产，记录各自真实入口、跳过、回看、语言和链接。涉及新功能提示时另核对稳定 ID、适用条件、去重、动作结果及常驻回看；自动提示不能充当问号回看证据。逐项注明观察的是文字、截图、原型动画、产品内动画，还是指向真实控件的引导。把体验缺陷与需要新增的产品决定分开；BUG 先复现再修，不能凭源码猜测宣称修复。

问题沿原 Issue 或按主要用户结果复用/新建 Issue，遵守 AGENTS 的提单读取路径；不在矩阵另记待办进度。跨窗口已有工作先读实际 Issue/PR 状态，只处理本旅程的缺口，不重复实现其他窗口负责的改动。

## 修复、瘦身并补引导

执行 workbench-start 的分流：明确行为的小修直接做；缺失必要定义、新布局或重要行为变化，按原则 02 补所属特性资料与所需原型，并 AskUser 对齐后继续。实现安排留仓外，包含资料与旧内容清理，不把计划塞进指南。

先让主要操作清楚、快捷，再补必要引导；先复用原生机制、布局和已有演示。用同一段已认可流程组织探索介绍、屏内动作与指南，不另造业务状态、引导引擎或安装系统。引导设计只讲实际修改的范围，复用部分引用现状，避免原型让用户误以为整屏都会重做。

做探索原型时，按[引导规范](../../../docs/04-design-system/guidance.md#展示与结果)从实际调用链核对动作名称、可用前提和可见结果，再用安全样例编排片段。只交原型的阶段先核对目录、步骤关系、播放和窗口尺寸，原型证据单独记录。

按本条旅程的适用性调整首次进入、跳过、回看和进度含义；例如配置未完成只阻止确实依赖它的动作，浏览演示不能记成项目工作完成。撤下被替代的文案、旧入口或素材，同批修好引用。

## 验证并形成产出

1. 按开发规范实际走通修复后的同一路径，并完成适用的独立复验与检视。按[展示与结果](../../../docs/04-design-system/guidance.md#展示与结果)分别走首次进入、真实控件推进、跳过后再进入、问号重播、弹窗协调和缺前提后的继续路径。修改了持久状态再核对重启读回。需要运行环境时完整读取 [verification](../workbench-start/references/verification.md)及其宿主入口。静态检查、模拟动画、真壳和真实多人/远端结果分别记录；环境不可用时完成独立部分，依赖部分保留未验。
2. 同步所属特性行为与证据边界；**直接更新两张矩阵中本次受影响的格**，填实际资产/入口和适用证据，不增设“现有内容”或整改流水表。按规范区分就绪、待验、缺失、不采用；只有来源与相应验证都支持才打勾。已有但未实走保留待验，缺的正常留缺；只验一个入口不勾整行，功能行就绪不自动勾引用它的完整工作旅程。核对关联行仍指向同一内容，撤下过时链接。
3. 按规范的内容标准维护已验证指南，复用同一旅程的说明和素材。尚未实走的路径留在规格与 PR 的未验范围，不包装成用户操作指南。指南不讲内部协议、施工历史或修 BUG 的过程。
4. 按本轮用户要求与旅程特点选择传播形式。已有传播要求或已确认采用的矩阵安排时直接制作，不重复索取制作许可；尚未选择传播产出时给一种建议，不把建议强加成必需交付。只有新增产品主张、受众或发布范围等真实未决选择才 AskUser。素材使用已验证路径，概念示意明确标示；只制作不自行发布。不为凑齐弹窗/动画/海报/多期漫画阻塞基本旅程，已承诺的产出也不能静默省略。

改文档前完整读取[文档组织原则](../../../docs/01-principles/01-document-organization.md)与目标头部；仅同步本次受影响的正本和入口。需要治理职责或旧资料时读取 [project-knowledge](../project-knowledge/SKILL.md)，不把普通同步升级为全库审计。

## 交付与下一条

每次旅程整改收尾，读取 [ref/upstream.md](../../../ref/upstream.md) 的头部约定与相关记录。按最终改动检查影响 Orca 同步的 BW 稳定差异，有变化就同批更新对应记录，说明原生复用与 BW 适配边界、关键扩点或路径、保留理由及 PR/验证入口，并清理失效说明。交付说明写明检查结论及适用的更新位置，便于后续同步逐项保留和复验。

沿 workbench-start 连续完成适用门禁、独立检视、修正复核与 PR ready；完成、合入和对外发布按实际授权执行。报告让人能判断：这条路现在能走到哪里、哪里更简单、引导从哪里进入/回看、矩阵与指南/素材在哪，以及真实未验部分和所需下一步。执行证据留 PR，矩阵只留当前覆盖与来源。

一条旅程的完成不自动启动下一条。后续按用户指定的旅程与窗口继续；若真实使用暴露规范或本 Skill 的问题，按已有反馈流程提出有证据的修订，确认后修改唯一正本，不在多个入口叠加同一句规则。
