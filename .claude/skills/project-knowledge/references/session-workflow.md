# 跨任务版本、依赖与交接

> 30 秒导读：单轮整改按 Skill 入口与维护方法执行。本篇只补充跨任务或并行工作时的版本选择、依赖合入和交接信息；历史状态从真实 Git/PR 读回。

## 按完整主题划分任务

默认当前任务完成整改与复盘，无需每轮新开方法维护任务。用户也可以让整改任务交付文件与验证，由维护任务读回真实 diff、反馈和证据，按 [维护方法](maintenance.md) 收敛方法修订。

- 一篇主文档带必要联动文件构成一轮；同一特性的 intent/spec/STATUS/验收关系可合在一轮，避免各篇都是半成品。
- 长文按完整职责段拆，同类且规则稳定的小文档可以一批；独立产品决定或跨主题取舍分开处理。
- 从实际已合入内容与在途任务中选择下一个主题；队列只放项目已有任务，不按 MD 数机械排轮次，也不为旧示例恢复已退役文件。

## 固定输入与依赖顺序

并行任务使用固定 Skill 快照，记录加载路径和版本。维护方更新方法来源，不能悄悄替换正在执行的输入；确需换版时说明差异与影响，明确选用版本。已指定维护方时由其收敛反馈，避免多份试验包分叉。

分支从已认可基线建立。下一轮依赖上一轮时，待人合入并读回后开始；已授权并行准备的任务可从同一固定起点独立交付，但必须标明依赖 PR 的集成顺序。前件经人合入后，将真实目标基线纳入后件，复核受影响适配、示例、扫描与验证，再交人判断；未集成不可称下一阶段已就绪。

沿用已有授权与真实合入来源，“本地改完”“已开 PR”都不能预填为已合入。方法修订与项目整改分别写清 diff 和版本，可随同或单独交付；下一轮采用明确选择的版本，不凭聊天记忆或来源分支的旧结果判断。

## 交接只补差异

沿用原任务/PR/commit 链接，让接手方自行读回 [维护方法](maintenance.md) 已要求的处置、验证与反馈记录，不要求用户再写一份报告。跨任务额外补齐：

| 信息 | 要记录什么 |
|---|---|
| 目标与版本 | 实际仓根、分支/交付提交；方法加载路径、采用版本；与上轮基线的差异 |
| 已有决定 | 可定位的报告/用户认可来源、继续有效的授权；不重演已确认决策 |
| 依赖与状态 | 依赖 PR、合入顺序、真实读回结果；未合入和未集成明确标出 |
| 下一动作 | 本块未完成项、范围外债务、负责方及下轮目标；读取入口和方法选版 |

只有仓或决定确实无法定位时才询问。扫描 HTML 是生成视图，不在网页上维护任务状态；没有定时或事件触发，不能宣称自动监控或自动收到反馈。
