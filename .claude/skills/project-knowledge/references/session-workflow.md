# 多会话整改与逐轮反哺

> 30 秒导读：一轮围绕一篇主文档或一个完整小主题。交付可独立评审的修改，你验收合入后读回，再复盘方法、开始下一轮。每轮必复盘，不要求每轮强行改 Skill。

多文档盘点、职责/格式尚未对齐时，用户可见的阶段和 HTML 决策出口按 [评审与对齐流程](review-workflow.md) 执行。下表补充跨会话版本与合入交接，不另起一套内部 SOP。

## 一轮的标准流程

| 环节 | 执行者要做什么 | 出口 |
|---|---|---|
| 1. 接手 | 读取最新已合入基线、Skill 版本和上一轮交接；核对当前工作树及并行修改 | 本轮主文档、关联文件、范围、已有决定明确 |
| 2. 建立基线与对齐 | 先对照当地规范、Skill 类型契约和实际正文；职责/格式未定时用 HTML 展示具体取舍，已认可则复用来源直接实施；扫描作为附录 | 人能判断具体目标；不重复已有决定，下一步明确 |
| 3. 实际整改 | 改主文档，合并/删除/迁移/归档旧内容，同步必要引用与读取方 | 实际 diff；本块没有悬空的迁移半成品 |
| 4. 验证与交付 | 后扫描、语义检查、必要执行验证；记录改善、未验和剩余债 | 一份可独立合入的改动与验证说明 |
| 5. 人验收合入 | 用户判断并合入；agent 根据授权提供提交/PR 或本地 diff | 真实验收/合入来源；仅“本地改完”不能标已合入 |
| 6. 读回与反哺 | 确认合入的是哪版；读取实际反馈；定位方法是否有缺陷 | 修 Skill 并复验，或记录“无需修订”及依据 |
| 7. 交给下一轮 | 记录采用的 Skill 版本、已合入基线、遗留项与下个目标 | 下一会话不用依赖聊天记忆就能继续 |

发现明显方法缺陷时可在交付前准备修订，不必等待合入才动手；合入后仍核对用户反馈是否带来额外修订。方法修订与项目整改分别写清 diff 和版本，下一轮只采用已选择的那版。

## 会话怎样分

默认当前任务完成整改与本轮复盘；用户也可以分为两个职责：**整改会话**执行本轮文件修改并交付，你评审合入；**方法维护会话**读回真实 diff、验证和你的反馈，修订 Skill/检查规则或说明本轮无需修订。下一整改会话加载选定的新版本。无需为方法维护每轮新开会话，也不依赖它凭记忆判断发生了什么。

并行使用时给整改会话一份固定版本的 Skill 快照，记录版本和加载路径；方法维护会话更新维护源，不在运行中悄悄替换该轮输入。确需换版时明确说明变更与影响后选择版本。整改会话反馈方法缺陷，已指定维护方时由维护方统一收敛，避免多份试验 Skill 分叉。

交接可以直接提供原任务/PR/commit 链接，由维护会话读回现有记录；无需用户再手写一份报告。未建立定时或事件触发时，不能宣称自动监控、自动收到了反馈。Skill 的后续版本由实际采用的仓内包维护：对齐项目规则、整合真实反馈、完成适用验证，通过 Git/PR 交付完整变更。不要求每轮都改包；方法修订可随同本轮 PR 或单独交付，须写清依据和验证。

- 默认一篇主文档加必要联动文件；例如 AGENTS 主改、CLAUDE 导入同步。不是只允许改一个文件。
- 同一特性的 intent/spec/STATUS/验收关系可以是一轮，否则容易每篇都半成品。特别长的文档可按完整职责段拆轮，但每轮保持可用。
- 小、同类且规则稳定的文档可以一批；出现独立产品决定或跨主题取舍就拆开。
- 会话数量按真实整改块计算，不按 MD 数机械计算。首批排小队列，后续依据扫描和实际成本续排。
- 分支从已认可基线建立；下一轮依赖上一轮时，在人合入并读回之后开始，不拿未合入结果冒充共享依据。
- 已授权并行准备的任务可从同一固定起点独立交付，但依赖 PR 必须标明集成顺序。前件经人合入后，将真实目标基线纳入后件，复核受影响适配/示例/扫描和验证，再交人判断；不能提前宣布下一阶段已就绪。

## 如何安排后续队列

先读取实际已合入内容和正在进行的任务，再选择下一个完整主题。下表以 BW 为例；具体队列记在项目已有任务中，本包不维护会漂移的 PR 状态或完成清单。已删除的文档不因示例提到就恢复。

| 轮次 | 主目标 | 必要联动 |
|---|---|---|
| 1 | 试用已选的顶层规范 | 用下一件实际维护任务观察找依据、选落点、同步引用及不必要确认；以事实反哺方法 |
| 2 | 特性候选总表：价值、来源与缺口入口 | 复用已有特性梳理任务；目录数量不能代表特性数量，不创建虚构 KPI |
| 3 | 一个完整特性的指标与验收关系 | 优先复用周一屏原开发任务成果，连到当前 CI 用例/证据入口；不另做设计 |

后续按已识别的特性组、architecture、各模块、指南、视觉与历史资料继续排队；一轮结束只细化下一轮，避免预先编造全部工作量。

## 每轮交接写在哪里

沿用本轮 Issue/PR/交付记录的一段，不另建手工状态系统。扫描 HTML 是生成的只读视图，不在网页上维护任务状态。

```text
本轮：主文档/关联件/采用规范与 Skill 版本
基线 → 交付版本：真实 commit 或工作树说明
存量处置：保留/合并/迁移/删除/归档的来源与去向
验证：前后扫描、语义检查、执行证据、未验证
验收合入：PR/commit 或待人处理；不能预填完成
方法复盘：偏差与根因；修订及复验，或无需修订的依据
遗留：本块未完成内容、范围外债务及下一动作
下一轮：目标、依赖、要读取的来源和选定 Skill 版本
```

用户只需说明本轮目标，例如“用 project-knowledge 整改 AGENTS”。自行从当前仓和 Git/PR 核对上轮记录；只有仓或决定确实无法定位时才询问。不要要求用户补写以下完整交接模板，也不要重演已经确认的决策。

需要跨仓或提供精确版本时，可选用较完整的开场：

```text
读取 <Skill 绝对路径>/SKILL.md，按会话运作整改 <目标仓> 的 <主文档>。
上一轮交接或合入来源：<任务记录 / PR / commit；首轮写无>。
本轮包括必要关联引用及存量清理，交付独立可评审的修改与验证。
记录实际遇到的规范/工具问题，供方法维护会话复盘；完成与合入权遵循现有授权。
```

## 每轮反哺的判定

文档事实错误修项目；BW 特例修适配；通用流程/格式有缺陷修 Skill；检查误报修脚本/映射。每轮输出这次判断，但没有新证据时保持规则稳定。一个任务跑完不自动证明长期收益，也不自动触发发布共享版。

文档规范尚在试跑时，扫描/HTML 同样是试验版；规范、机器检查、视图的逐步收敛顺序见 [扫描说明](scanning.md)。不为了尽早固定页面而强迫文档迁就不成熟字段。
