# 规范与文档职责的评审

> 30 秒导读：本篇处理尚未对齐的规则、文档职责与格式。先谈清规则，再用简短对照呈现维护方案；已经认可的范围直接实施，整改、验收和反馈读维护方法。

## 何时需要决策报告

多文档或结构治理先辨认哪些规则沿用、调整或尚未确定。影响执行行为、范围或验收的未决项，说明现状、推荐调整及影响，与人逐项对齐后再确定文档落点；已有明确的资料归属直接采用。不能先假定旧规则全部保留，再只让人选择搬到哪里。

需要人判断维护结构时，给可审查的目标结构、样例与取舍，默认以 HTML 呈现。用户指定其他格式时遵从；只要求评审时保留源文件。已明确的小修不强迫生成报告，也不重演已确认的决定。

报告准备所需的读取和检查先完成，不在调查不足时只问“要不要继续”。说明当前阶段、随后交付与待决内容；方案变化时更新同一报告，保留已有决定。只有无法从上下文判断的仓库、互斥目标或语义取舍才交给人。

## 四层规范要说清

| 层 | 是什么 | 怎么使用 |
|---|---|---|
| 项目现行规则 | 当地已认可、适用的规范 | 定位原文和认可来源；它也可能是本轮授权的整改对象 |
| Skill 类型契约 | document-contracts 中可适配的职责、内容与格式 | 主动用于草案；未写进主仓不等于没有规范，也不能自动当全仓门禁 |
| 文档实际内容 | 当前文件承载什么、谁使用它 | 区分事实错误、结构问题、历史依据与无须改变的内容 |
| 本轮目标规范 | 将现行依据、类型契约和用户判断结合后的方案 | 标明已认可/待判断，明确采纳后要清理的存量与读取入口 |

规范可达性至少跟踪：AGENTS（或当地入口）→ 文档组织/索引 → 对应类型规范。静态可达、实际读取与正确采用分别取证。

缺口应明确为“职责已有、格式不全”“Skill 有候选、主仓未采纳”“规则存在但入口不可达”或“未找到依据”，不能把未知统称无规范。

## HTML 决策报告最少要回答什么

源文件和 Git 是正本，报告呈现本轮待评审或已认可方案，不另建手工状态台账。正文以「现状 → 调整后 → 影响或待决项」的简短对照为主，已认可内容与真正待决项分清；证据和详细样例折叠，不让人从长篇盘点中自行提炼变化。

1. **范围与决定**：目标、当前阶段、随后交付；哪些已认可，哪些仍需判断。
2. **规则对照**：现行依据、实际问题、推荐调整及影响；必要时给替代方案，不重问已决定的事项。
3. **维护契约**：文档位置、读者与职责边界、正文结构/格式、直接引用者与读取时机、更新触发。优先复用既有头部和格式，不再叠同义维护块。
4. **实施与证据**：旧内容去向、一起改的文件、可观察验收及未覆盖项。具体段落、样例、扫描与读取记录按需展开，区分静态检查和实际执行。

扫描器的 knowledge.html 是资产和引用视图，不能代替语义决策报告。拟用格式必须按文档类型给出具体样例，只写“建议精简、加索引”不够。

可复用本轮决策编号连接 PR，不另建永久编号系统。用户认可后保留报告版本/任务来源，以便检查实施偏差；正式规范仍回到项目原件。

## 评审出口

人已能判断职责、格式与取舍，且下一步明确，才算评审完成；这不表示存量已整改。进入 [维护方法](maintenance.md) 落实决定与验收，职责/入口重构的效果观察也在那里记录。跨任务只追加 [会话运作](session-workflow.md) 要求的版本和依赖信息。
