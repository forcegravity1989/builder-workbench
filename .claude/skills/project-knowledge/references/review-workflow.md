# 人可见的治理流程与决策报告

> 30 秒导读：用户只需说明处理对象和意图。执行方先展示当前阶段、接下来的交付和需要人决定的内容；多文档治理先让人看懂职责、规范与目标格式，再把已对齐的决定落实到原件和存量。

## 怎样接受自然语言起手

“盘点一下顶层几个 MD”足以开始工作。自行识别当前目标仓、相关文档、已有授权、已有决定与适用契约，不要求用户补成正式任务书。Skill 路径仅是方法来源，不自动决定业务仓根。

先用简短说明让人知道本轮走到哪里：本轮对象、现在要解决的问题、随后交付什么、哪些语义决定还缺失。遇到多个仓或互斥目标且无法从上下文判断时，才问具体问题；其余读取、检查、报告准备继续。

“盘点”本身不固定等于只读查错或直接重写。多文档治理且职责/格式尚未定时，先进行下面的体系评审；用户明确只看不改时只交评审，明确要求直接修复且依据已定时直接执行。不要把所有任务都变成等待审批的流程。

## 一轮让用户看见的阶段

| 阶段 | 本阶段要让人看懂什么 | 出口与下一步 |
|---|---|---|
| 1. 定位规范与现状 | 这些文件是否必要，各自写什么；现行规则、Skill 候选契约、正文现状分别在哪 | 对照具体差异，不以零散事实错误替代整体职责判断 |
| 2. 展示目标与对齐 | 建议的职责、格式样例、旧段落去向、规范落点、读取路径，以及待决定项 | 多文档治理默认提供 HTML 决策报告；按用户反馈更新同一报告，保留已认可项 |
| 3. 落实已定决定 | 规范写回适合的正本，正文与受影响存量同步整改，入口与实际读取方同步 | 可审查 diff；无需重复确认已经认可的方向 |
| 4. 验证与评审 | 报告中的哪些决定落实到哪些文件/段落、验证了什么、还剩什么 | PR/diff 与认可方案能对应；验收与合入按实际授权推进 |
| 5. 回传方法反馈 | 哪些步骤产生误读、额外打断或无用产物；本轮修订与后续待观察项 | 原任务可供维护会话读回；候选方法经复验后选版 |

阶段变化或发现改变方案的事实时更新当前状态和下一步，不让用户猜接下来会做什么。已经对齐的阶段直接复用；仅有确定性小修时不强迫生成完整 HTML 或再过一遍语义决策。

体系方向仍待用户选择时，交付具体、可审查的目标结构和样例，再处理该选择；不在调查尚不充分时只问“要不要继续”。用户明确要求先看方案后改，就在方案认可前保留源文件。

## 四层规范要说清

| 层 | 是什么 | 怎么使用 |
|---|---|---|
| 项目现行规则 | 当地已认可、适用的规范 | 定位原文和认可来源；它也可能是本轮授权的整改对象 |
| Skill 类型契约 | document-contracts 中可适配的职责、内容与格式 | 主动用于形成草案；不能因未写进主仓就说没有任何规范，也不能自动当全仓门禁 |
| 文档实际内容 | 当前文件里实际承载什么、谁使用它 | 区分事实错误、结构问题、历史依据与无须改变的内容 |
| 本轮目标规范 | 将现行依据、类型契约和用户判断结合后的方案 | 标明已认可/待判断；本轮采纳时同步清理适用存量并建立读取入口 |

规范可达性至少跟踪：AGENTS（或当地入口）→ 文档组织/索引 → 对应类型规范。静态路径可达与模型本轮实际读取分别取证；读取了也不等于正确采用。

描述缺口时明确是“职责已有、格式不全”“Skill 有候选规范、主仓尚未采纳”“规则存在但入口不可达”还是“没有找到相关依据”。未知不统一写成无规范。

## HTML 决策报告最少要回答什么

围绕本轮判断组织一份可持续更新的报告，不再并列多个手工状态台账。多文档/结构治理默认使用 HTML；用户指定其他格式时遵从。源文件和 Git 是正本，报告是待评审或已认可方案的呈现。

1. **本轮地图与流程**：目标、范围、当前阶段、接下来什么、已有决定和剩余判断。
2. **逐篇对照**：文件是否合适、面向谁、职责/非职责、现行规范来源、Skill 候选契约、当前结构、拟用章节和简短样例、旧内容去向。
3. **规范与读取关系**：规范拟落在哪个已有正本，从 AGENTS 怎么读到；明确是否需要改入口。
4. **决策与取舍**：仅列真实分歧，给推荐、理由、替代方案和影响；不把已决定或可自行完成的编辑细节重新交给用户。
5. **实施及 PR 审核地图**：本轮哪些文件一起改，每项决定对应的文件/段落和可观察验收，哪些后置及原因。
6. **证据与限制**：静态扫描、源码事实、读取记录、实际执行分别标层级；支持折叠或附录，不占据主结论。

扫描器生成的 `knowledge.html` 是资产和引用视图，不能单独替代上述语义决策报告。报告中的拟用格式要根据文档类型具体写出来；只给“建议精简、加索引”不足以让人判断。

报告可以使用本轮决策编号连接 PR，复用用户已有编号。不要由此新建永久全局编号系统。用户认可后，保留报告版本/任务来源，让评审能看出执行是否偏离；合入后正式规范回到项目原件，报告不成为另一份永久规则。

## 完成如何分开

职责或入口重构开始时，选本次真正要改善的一项维护任务，例如“把新规则写入正确原件”或“按入口找到当前验收依据”。在原报告/任务中说明改前障碍、预期动作、如何观察；已有导读能做到的事不算新增收益。后续用自然请求检验是否还需用户纠正、是否写错位置或重复建文档，并记录额外阅读和确认成本。未实际试用就标待观察，不为每篇建立评分表，也不因缺少长期数据阻塞局部清债。

- 评审阶段完成：用户已能判断每篇职责、格式和必要取舍，下一步明确；不代表存量已整改。
- 本块整改完成：已采纳规范、正文与旧债、引用/读取方、适用验证一起交付。
- 方法修订有效：真实任务或可比输入复验改善已观察到；不能用“规则已写好”代替。
