# 文档类型契约

> 30 秒导读：整改某篇时，找到它的类型，按「写什么 / 不写什么 / 何时更新」对照。「不写」一列多半是会漂移的精确细节或别处的正本。这是可适配的基线；目标项目已认可的头部与规则优先，采用后写回项目自己的正本，不在本包另养一份。

## 共同格式

- 一个明确标题，加一段简短导读或维护约定：给谁、何时读、写什么不写什么、依赖哪些正本。导入文件、生成文件、上游镜像沿用各自格式。
- 章节按读者的问题组织。事实、目标、假设、示例分开写；已实现、已通过只写给有证据的陈述。
- 同一规则或公式只在一处维护，别处链接。删除或改名时处理入站引用、示例与实际加载方。
- 三种状态不混用：文档的**候选 / 已认可 / 历史**说的是适用性；任务的进行中、已验收来自任务系统；测试的未运行、通过、失败来自执行记录。
- 面向模型的入口同时写「这是什么」和「什么任务要读」；一个概念的定义、规则和例外放在一起。

## 入口与词表

| 类型 | 写什么 | 不写什么 | 何时更新 |
|---|---|---|---|
| 产品 README | 是什么 → 为谁解决什么 → 当前能做什么 → 快速开始 → 继续阅读 | 开发门禁、全部特性规格 | 产品入口或操作变化 |
| AGENTS | 规则来源 → 按任务读取 → 硬约束 → 建跑测 → 交付权限与知识同步 | 产品介绍全文、模块实现、Skill 的步骤副本 | 规矩、命令、目录或入口变化；必要约束一条不丢 |
| CLAUDE 等工具入口 | 工具支持的最小导入 | AGENTS 副本 | 上游加载方式变化 |
| 词表 | 术语 → 含义与易混边界 → 权威正本 | 流程、实现清单、工作进度 | 概念变化；改文案不偷改协议值 |
| 文档地图 / 特性总表 | 读者目标 → 正本入口 → 适用范围 | 正文副本、另一套任务状态 | 新增、迁移或退役文档 |

## 原则、设计与决策

| 类型 | 写什么 | 不写什么 | 何时更新 |
|---|---|---|---|
| 原则 | 原则与理由 → 范围和例外 → 如何落实 | 单次施工步骤、读数、修订流水 | 经人拍板时；同步它覆盖的存量 |
| 产品主张 / PR-FAQ | 用户与问题 → 目标体验 → FAQ → 假设与衡量 → 约束 | 把目标体验写成已交付；实现进度 | 产品选择变化 |
| architecture | 旅程 → 模块边界 → 数据流与依赖 → 关键约束与取舍 → 关联特性与 ADR | 逐文件清单、字段表、任务历史 | 跨模块边界变化 |
| 模块篇 | 心智模型 → 主要矛盾与取舍 → 相关特性与 ADR | 代码路径、数据字段、没建清单 | 模块新增、大改或主要选择变化 |
| ADR | 背景、决定、原因，一段话即可；有价值时加备选、后果、取代关系 | 操作协议与命令细节（放操作正本）、日常修订流水 | 新决定取代旧决定时新增，不无痕改写 |
| 设计系统 / 原型 | 适用场景 → token 与组件状态 → 交互 → 验证引用 | 业务规格；过期原型冒充现行 | 界面变化；机读资源保持原格式 |
| 外部参考提炼 | 来源与读取日期 → 采用什么 → 怎么适配 → 不采用与原因 | 上游全文、无出处的「业界标准」 | 来源变化或本地偏离 |

ADR 只在三条都成立时写：难回头、没有上下文会让人意外、确有备选并做了取舍。

## 特性与变更

| 类型 | 写什么 | 不写什么 | 何时更新 |
|---|---|---|---|
| intent | 用户与痛点 → 价值假设及依据 → 范围与排除 → 成功衡量 → 未决问题 | 实现流水 | 价值或范围变化 |
| spec | 状态与范围 → 行为要求 → 失败与边界 → 验收点 → 原型链接或输入输出样例 → 未决问题 | 当前行为与拟变化混写；历史累加 | 行为变化 |
| plan | 原因与范围 → 改哪些对象 → 顺序与风险 → 如何证明 | 小修的完整 intent/spec | 本次实施时 |
| STATUS | 结论与适用版本 → 状态来源链接 → 已验证 / 未验证 → 下一动作 | 讨论轮次流水、PR 号清单、测试条数 | 进展或证据变化 |

验收点最少写到：前提 → 操作 → 预期与失败结果 → 用例入口 → 独立读回方式。证据层（单测、静态检查、真实桌面、模型会话、真实远端）分开标，不把替身接口叫成真实 E2E。

## 使用文档

按 [Diátaxis](https://diataxis.fr/) 的读者需要选，不为每个特性凑四篇：**教程**（练习与每步可见结果）、**操作指南**（任务 → 操作 → 结果 → 常见失败与恢复）、**参考**（对象、字段、命令、限制与来源）、**解释**（背景 → 概念关系 → 原因与取舍）。已有 HTML 指南保留，写清输入源与展示层的关系，不另做 Markdown 镜像。

## 衡量与证据

| 类型 | 写什么 | 何时更新 |
|---|---|---|
| 指标定义 | 关联目标、引领或滞后及假设、公式与分母、窗口、来源与排除、采集入口、基线与目标状态、防失真的约束 | 口径或来源变化；口径认可、脚本可跑、读数有效分三件事验证 |
| 用例定义 | 关联验收点、场景、前提与数据、操作、断言与独立读回、执行入口、环境与清理 | 行为或环境变化；要能识别不满足要求的结果 |
| 运行证据 | 版本、用例、环境、命令、时间、结果、读回、限制 | 每次执行生成，不手改历史结果 |

没有可信读数就写未知；不拿文档数、提交数、关闭数凑指标。

## 方法与交付记录

| 类型 | 写什么 | 何时更新 |
|---|---|---|
| Skill | frontmatter → 输入与交付 → 步骤与异常 → 验证 → 按需参考 | 真实偏差或适配变化 |
| 系统提示词 / 规则 | 适用对象与触发 → 必要上下文 → 约束 → 按需入口 | 注入方式或行为规则变化；核对实际生成与加载 |
| Issue | 问题与预期 → 范围 → 关联特性或约束 → 验收 → 缺的决定 | 工作输入变化 |
| PR | 实际变化与原因 → 受影响知识 → 验证与证据 → 未验与遗留 | 以最终 diff 为准 |

审查模型指令时，先查每条指令为什么存在（Git、原问题、它保护的约束），再给具体改法；旧、长、语气重都不是删除理由。改了有争议的指令，用同类真实输入对照行为，字数变少不算改善证据。
