# 文档职责、格式与更新契约

> 30 秒导读：选择目标文档的类型，按“写什么、怎样写、何时更新、如何核验”整改。下面是便于适配的基线；项目认可后写回当地规范，并同步清理受影响旧内容。不要新建所有类型。

## 如何用于本轮评审

这些契约是可用的候选规范，不是只有主仓采纳后才能拿来讨论的空白占位。多文档盘点时逐篇把对应契约与当地规则、正文现状对照，给出具体目标格式和落点；采用状态与读取路径按 [评审与对齐流程](review-workflow.md) 标明。

## 共同格式

- 用一个明确标题和简短导读说明读者、用途与边界。导入文件、生成文件等特殊载体沿用其协议，不机械塞入导读。
- 已有导读足以表达职责时保留原写法，只补会影响编辑判断的缺项；不要再叠一份同义维护块。职责约定应能说明某类具体内容应写入还是另找正本。标题、表格列等可机械检查，语义边界仍需实际任务核验。
- 在易混淆时写明候选/现行/历史、适用版本和依据。别给所有 MD 添加没有读取方的统一 YAML；Skill 与现有工具协议使用其要求的 frontmatter。
- 章节按读者问题组织。事实、目标、假设、示例分别表述；只给已有证据的陈述标“已实现/已通过”。
- 跨文档写引用，同一规则/公式不多处维护。删除或改名时处理入站引用、示例及实际加载方。
- 模板标题可以同义替换、合并成短段；自动检查必须先适配项目采用的格式。语义齐全不等于标题字符串匹配。
- 对规则明确适用范围、理由、执行/检查方式和需要判断的部分。新规则覆盖到的旧正文要在该整改块一起处理。
- 面向模型的资料入口同时说明“这是什么”和“什么任务要读”。必要材料没被读到，先修触发指针；只有对应任务需要的细节再下沉参考。把一个概念的定义、规则与例外放在一起，避免散落各处。

## 入口与词表

| 类型 | 最小格式/内容 | 留在别处 | 更新与核验 |
|---|---|---|---|
| 产品 README | 是什么 → 为谁解决什么 → 当前可用范围 → 快速开始 → 知识入口 | 详细开发门禁、全部特性规格 | 产品入口/操作改变；读者能按步骤开始，未验证步骤明确 |
| AGENTS | 范围/规则来源 → 任务读取入口 → 项目硬约束 → 建跑测 → 交付权限与知识同步 | 产品介绍全文、所有模块实现、重复 Skill SOP | 项目规矩/工具/目录变化；约束保留、命令与入口可核验，职责冲突已处理 |
| CLAUDE / 其他工具入口 | 工具支持的最小导入或指向方式 | 复制一份 AGENTS | 上游入口变化；核对该工具实际加载行为，非所有工具均支持 @ 导入 |
| CONTEXT / 术语表 | 术语｜含义与易混淆边界｜权威使用位置 | 普通词词典、工作进度、重复产品规格 | 概念变化；跨规则/规格语义一致，协议标识不被文案重命名偷改 |
| docs 索引 / 特性总表 | 读者目标｜正本入口｜适用范围｜缺口来源 | 正文副本、另一套任务状态 | 新增/迁移/退役；无失效入口，生成字段注明来源 |
| DESIGN 等指针 | 指向唯一正文；必要时一句用途 | architecture 全文 | 目标改变；引用可到达 |

AGENTS 瘦身先区分应留下的必要约束与重复背景。把所有内容搬成 references 只会转移阅读成本；应减少重复并让任务只读取相关内容。

AGENTS 可以先整改，不要求先定完整个知识库。入口保留当前认可的项目约束、任务读取路由和必要命令，完整文档目录由已有 docs 索引维护；不逐篇登记全部文档。任务必须直接读取的关键规范可保留直链，不能为减少链接而藏掉必读材料。

后续轮次如果改变目录、规则正本、执行命令或加载入口，就在该轮同步微调 AGENTS、相关工具入口及真实读取方；变化只涉及正文或指标时，不必重写 AGENTS。不能为“索引永远不变”保留失效路径或兼容副本。第一轮不预填尚未认可的全库规范。

## 原则、产品和实现

| 类型 | 建议章节顺序 | 边界 | 更新与核验 |
|---|---|---|---|
| 文档/开发原则 | 原则及理由 → 范围/例外 → 如何落实 → 变更依据 | 单次施工步骤、指标读数不入正文 | 授权改变规则时；同步适用存量、Skill 与检查 |
| 产品主张 / PR-FAQ | 用户与问题 → 目标体验/价值 → FAQ → 假设和衡量 → 约束/决策依据 | 目标体验不冒充交付实况 | 产品选择改变时；产品负责人判断价值取舍，实现另列证据 |
| architecture | 整体目标/旅程 → 模块边界 → 数据流与依赖 → 关键约束/取舍 → 关联特性/ADR | 逐文件实现清单、每条任务历史 | 跨模块边界变化；代码/运行来源支持实现陈述 |
| 模块说明 | 职责/非职责 → 输入输出与依赖 → 主要矛盾/选择 → 相关特性和 ADR | 重写全部用户规格、API 自动文档副本 | 模块边界/主要选择变化；来源与实现一致 |
| ADR | 日期/状态 → 背景 → 决策/备选 → 后果 → 取代关系 | 日常小修流水；无痕改写历史决定 | 重要选择变化；新决定取代旧记录并可追溯 |
| 设计系统/交互规范 | 适用场景 → token/组件状态 → 交互和可访问性 → 实现/验证引用 | 完整业务规格、过期原型冒充现行 | 组件/交互改变；实际界面核验；已有机读资源保持格式 |
| 外部参考提炼 | 来源/版本或读取日期 → 采用机制 → 项目适配 → 不采用与原因 → 验证 | 全文复制上游、无出处“业界标准” | 来源变更或本地偏差；许可与采用范围可追溯 |

## 特性与单次变化

| 类型 | 建议章节顺序 | 边界 | 更新与核验 |
|---|---|---|---|
| intent | 用户/痛点 → 价值假设及依据 → 范围/排除 → 成功衡量引用 → 未决问题 | 实现流水、不为小 bug 重新立项 | 新价值或范围改变；假设与事实分开 |
| spec | 状态/适用范围 → 行为要求 → 失败/边界 → 验收点 → 指标/用例引用 → 原型或输入输出样例 → 未决问题 | 当前行为与拟变化混写；累加全部历史 | 行为变化；验收可观察、来源明确；当前协议与提案分清 |
| 变化记录 / plan | 原因与范围 → 增/改/删的行为 → 影响对象 → 实施/验证/同步 → 剩余决定 | 小修复制完整 intent/spec；固定要求人人审批 plan | 本次改动时；交付后现行正文同步，历史留来源 |
| STATUS / 实践段 | 结论适用日期/版本 → 状态来源 → 已验证范围 → 未验证/缺口 → 下一动作 | 另一套 Issue 状态、旧验收冒充新证据 | 实际进展或证据改变；读者能回到真实任务与执行记录 |

项目若把 spec 用作变更制品，先保留该语义，明确“当前依据 / 拟变化”并提出本轮必要修改。不能仅套 OpenSpec 术语就宣称已存在持续规格。合并新规范与对应存量时才改变实际约定。

可嵌入现有 spec 的最小格式：

```markdown
# 特性名称
> 为谁提供什么能力；本文管行为与验收。
状态与范围：候选/已认可；适用版本与决定来源
## 行为
### 具体现行要求（使用稳定锚点或既有标识）
前提：...
操作：...
预期/失败结果：...
## 衡量
引领假设与结果指标：引用各自口径，不重复公式
## 验收与证据
| 验收点 | 场景/用例入口 | 运行证据 | 未覆盖 |
|---|---|---|---|
## 本次拟变化与未决问题
```

## 使用文档按目的写

借鉴 Diátaxis 的四种读者需要，按实际内容选择，不为每个特性强造四份文档：

| 类型 | 格式 | 核验 |
|---|---|---|
| 教程 | 学习目标/准备 → 可复现练习 → 每步可见结果 → 学会什么 | 新手能走完该版本的练习 |
| 操作指南 | 要完成的任务/前提 → 操作 → 结果 → 常见失败与恢复 | 实际路径和失败处理有验证 |
| 参考 | 对象/版本 → 字段/命令/参数/限制 → 示例与来源 | 与真实接口或配置协议一致 |
| 解释 | 问题背景 → 概念关系 → 原因与取舍 → 相关操作入口 | 解释与实际设计选择一致 |

原有 HTML 指南可以保留；输入源和展示层关系写清。不新增同内容 Markdown 手工镜像。

## 衡量、用例和证据

详细定义见 [特性与证据](feature-evidence.md)。这些字段可以在一份特性文档内成段，不要求各建文件。

| 类型 | 最小内容 | 更新与核验 |
|---|---|---|
| 指标定义 | 关联目标、引领/滞后及假设、公式/分母、窗口、来源/排除、采集入口、基线/目标状态 | 口径或数据来源改变；口径认可、脚本可用、结果有效分别验证 |
| 用例定义 | 关联验收点、场景、前提/数据、操作、断言/独立读回、执行入口、环境/清理 | 行为/环境改变；能执行而且能识别不满足要求的结果 |
| 运行证据 | 源码/文档/方法版本、用例、环境、命令、时间、结果、日志/读回、限制 | 每次执行生成；不手改历史结果，不将静态检查写成 E2E |
| 方法评估 | 固定输入/仓版本、期望行为、失败判据、运行设置、实际输出、人工介入 | 真实方法偏差或依赖改变；可比输入，未观察不写零失败 |

## 方法与交付记录

| 类型 | 最小格式/内容 | 更新与核验 |
|---|---|---|
| Skill | frontmatter 的 name/description → 输入与交付 → 规则入口 → 执行/异常 → 验证 → 按需参考 | 真实偏差/适配变化；发现、读取、执行与效果分别验证 |
| system prompt / rule | 适用对象/触发 → 必要上下文 → 约束/职责 → 按需入口 | 注入或行为规则改变；核对实际生成和加载，不用“文件存在”代替注入证据 |
| reference | 一个具体主题、范围、来源、执行细则及正本链接 | 上游/项目约束改变；已定规则不留长期重复试验副本 |
| Issue | 问题/预期 → 范围 → 特性或工程约束来源 → 验收 → 缺失决定 | 工作输入变化；小修引用已有规格；不复制任务系统状态 |
| PR / 交付说明 | 实际变化/原因 → 关联任务/受影响知识 → 验证及证据 → 未验/遗留 | 以最后 diff 为准；遵循项目验证格式，模板覆盖 CLI 与模型入口 |
| CHANGELOG | 版本/日期 → 实际行为变化/修复 → 限制/来源 | 随实际交付；不把待实施内容写成上线 |
| 归档记录 | 当时状态/日期/版本 → 历史内容 → 现行替代入口 | 仅保留追溯有用内容；现行默认索引不误指历史 |

外部参考、方法包、示例文件采用原格式时可免除不适用栏目；说明具体原因，不能把空栏目填满当作质量。

## CHANGELOG 的可采用写法

仅适用于项目决定继续维护 CHANGELOG 的情况。若项目已选择用 commit/PR 留变更证据、正文保存现行知识，核对有效内容与读取方后删除即可；不因本包有模板而恢复文件或另建替身。DESIGN 等指针同样先判断是否有独立用途。

每条说明一个对使用者或维护者有意义的变化：触发/问题、现在怎样、适用范围或重要限制、来源。按已证实的版本或日期分组；没有版本事实时不用猜号。项目选择日期制还是版本制在本轮定清，不能用重排伪造发布史。

```markdown
## 未发布（或真实版本 / 日期）
### 修复
- 保存配置后重启仍能读取所选工具。此前某条件下会恢复旧值。来源：关联 PR。
### 方法与文档
- 更新某类文档的职责，并整理受影响的旧内容。来源：本轮整改记录。
### 限制
- 尚未验证的范围：具体说明；详细命令和证据引用验证报告。
```

上例只示格式，不是已交付事实。无需每组都填齐所有分类；直接列表足够时不再叠小标题。

存量大段按独立变化拆条：保留当时版本/状态，合并重复摘要；长验证日志引用原报告，重要决策理由回 ADR；没有可引用证据时保留必要原文或标明缺口，不能为了瘦身删掉唯一证据。过程中的“第几轮改稿”等若无后续价值可清理，不能无痕改写旧承诺为完成。

可统计分组数、每组条目/段落、超长段落、来源链接和重复候选。条目可读性与历史真实仍需审查；字符阈值只作导航，不是硬性质量分数。
