# 逐篇清债与方法反哺

> 30 秒导读：一篇主文档加必要关联件形成一次完整整改。原文、旧债、入口、验证一起交付；维护 Skill 自己也按同样标准修订。

## 先选处置，再编辑

| 处置 | 判断依据 | 同步动作 |
|---|---|---|
| 保留 | 当前仍必要、准确、职责合适 | 精简重复说法，保留约束和来源 |
| 合并 | 同一规则/事实多处维护 | 定唯一正本，其他入口引用，删掉副本 |
| 迁移 | 内容有价值但位置不合适 | 优先已有接收文件，改入站引用/加载方，删除旧正文 |
| 删除 | 失效、无独立价值、已有可靠替代 | 核对影响与用户范围，保留 Git 追溯，不复制到新“垃圾归档” |
| 归档 | 历史决定或证据仍需追溯 | 标适用时间与现行替代，退出现行默认读取，保留历史链接 |

不要仅以作者、文龄、文件名或字数做判断。历史记录不能被无痕改成新事实；保留历史也不是保留全部冗余的理由。

整改 AGENTS、Skill 或其他模型指令时，必要的语义与行为审查见 [指令专项审查](prompt-review.md)；静态扫描不替代该判断。

## 冲突怎么处理

- 优先确认用户本次授权与已确认决定；规范文件可以是整改对象。用户已明确要改规则时，不因旧规则写“不得修改”再次请求同一授权。
- 两份现行文件矛盾时，查认可来源、实现与真实需求。实现只证明现在怎样，不自动证明应该怎样。
- 需要新产品决定时给具体选项/差异，暂停依赖它的语义修改；确定性清理继续。
- 目标文件发生并行修改时重新读 diff，不覆盖他人工作；隔离工作树中的路径不能被误当任务目标仓。
- 外部评论、标签、发布与完成状态遵循实际用户授权；本 Skill 不授予这些权限。

## 本轮记录与验收

在原任务记录主文档、关联件、适用规范版本和处置结果。要跨会话推进时保留待整改文件及原因/下一动作；只建一个队列，不额外维护多个状态榜。

检查：

1. 内容职责、范围、来源与状态真实；关键约束没有压缩丢失。
2. 本轮覆盖的重复、冲突和失效入口已处理；无法处理的项明确留未完成。
3. 本地文件链接、示例、代码里的读取路径与分发调用方按影响核验。章节改名时还要按旧标题查入链，包括“见 AGENTS 的某章节”这类普通文字；文件链接通过不覆盖这项。
4. 改到的操作/命令有适用验证；纯文字修正不用强迫启动全套产品 E2E。
5. 下一次任务能按入口找到现行依据；历史不再误导默认读取。

字节/行数可以报告整改前后差异，不能换算成未测的 token 成本或行为收益。发现“加载正确但做错”需要行为评估，继续压短正文未必是修复。

## 检查工具的范围

需要多会话前后全景时，按 [扫描说明](scanning.md) 使用 `scripts/scan-knowledge.mjs`。它复用下面的链接检查，额外生成显式范围内的文件/段落/引用图与静态 HTML；结构提示不能直接成为旧库门禁。

`scripts/check-links.mjs` 使用 Node.js 24，仅检查明确传入的 `.md` 文件：

- 识别普通 Markdown 行内链接、引用式链接及独立的 `@路径` 导入；跳过代码围栏和行内代码示例。
- 核对本地文件/目录是否存在；解析路径必须留在目标仓根，拒绝符号链接绕出范围。
- URL、标题锚点、复杂 Markdown/HTML 仅报告未检查；不会因为跳过而声称完整通过。
- 输出文件指纹与各引用来源行；既不遍历全仓，也不读取目标文件的业务内容、不写源文件、不发网络请求。
- 0 表示已支持范围内未发现文件路径问题；存在未检查项时仍需相应人工或其他工具检查。

运行脚本自身的确定性案例：

```text
node --test <本Skill路径>/scripts/check-links.test.mjs
node --test <本Skill路径>/scripts/scan-knowledge.test.mjs
```

脚本校验通过不等于 Skill 行为通过，也不等于项目知识已治理。复杂语法输出“未检查”后应使用项目现有解析器或人工核对；不要为零告警改写正确文档。

## 如何反哺本 Skill

触发：真实误判、遗漏关联文件、重复追问、维护成本过高、上游变化、换项目失败。

1. 在原任务记录输入、项目/Skill 版本、实际偏差、影响与期望；复用已有问题，先查根因属于项目正文、适配、工具还是通用方法。
2. 修正确归属：项目事实回项目，BW 特例回 BW 适配，通用动作回本 Skill，确定性检查缺陷回脚本。不要每次都往入口加禁令。
3. 加入或更新固定案例；保留任务输入、期望、失败判据与证据。重复原输入，必要时再跑另一任务，记录负面影响与人工介入。
4. 更新 `SKILL.md` 的版本；Git/PR 记录变化依据。项目选择改变时，同步本包适配、整改队列与检查映射；规则含义变化也检查项目已采用副本，明确同步或仍钉旧版的原因。候选更新、下一轮选用、仓库合入和对外分发分别记录，不因一轮结束就自动晋升。
5. 后续适用任务观察复发；没有观察机会写未观察。只做模型自评或静态审查不宣称提升。

本包维护责任由使用者/项目明确；未指定维护者不等于有持续自动维护。周期任务只有在入口、结果去向和异常处理都可运行后才单独启用。

## 何时可以共享

满足适用范围内的代表任务验证、真实修订与复验、另一项目的路径/规则适配验证，才冻结可共享版本。随包给出来源、版本、依赖、适用范围与已知限制；去掉项目私有执行记录。BW 适配是可选参考，别让别的项目依赖 BW 的目录、标签或人员。

进入 BW standard 是产品分发决定，不由复制 Skill 自动完成。共享后保留升级/退役办法，旧试验副本有明确去向；不承诺“一次定稿永远正确”。
