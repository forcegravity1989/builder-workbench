# 扫描流程与候选报告

> 30 秒导读：热点定范围 → 脚本收信号 → 读原文套三条检验 → 仓外 HTML 候选报告 → 人挑一项。脚本只给线索；候选、强弱和处置靠读原文判断。定期运行的机械部分交给 CI，出候选报告需要一次模型会话。

## 1. 定范围

- 用户给了方向（某模块、某目录、某个痛点）就按方向走，跳过热点推断。
- 否则先看脚本的两张热点表：**文档改动热点**、**代码改动热点与文档同步**。近期改动多的代码区域，对应的 architecture 段落、模块篇和特性目录优先；「同提交改了文档」占比低的区域，文档很可能落后于代码。
- 浅克隆时热点不完整：本地先 `git fetch --unshallow`，CI 用 `fetch-depth: 0`。
- 先读词表和相关 ADR。目标文档取舍段或 ADR 里已写明否决理由的方向不重提；情况确实变了才重提，并说明变了什么。

## 2. 信号怎么读

| 信号 | 提示什么 | 常见误报 |
|---|---|---|
| 没人链接 | 删除测试的候选 | 工具直接加载的入口、只被 HTML 或代码引用的文件 |
| 超长文档 | 一篇文档承担了多种职责，或堆了流水 | 产品主张与大特性规格本来就长；看是不是一篇多职 |
| 重复段落 | 合并候选 | 模板与固定声明 |
| 漂移细节 | 精确的错误最容易出在这里 | ADR 与历史记录里的日期是事实；协议值是契约 |
| 缺取舍 | 模块篇、ADR 或 architecture 没说为什么 | 用了映射词表之外的说法表达取舍 |
| 断链 | 机械错误，直接修 | — |
| 代码改了、文档没跟 | 文档可能描述的是旧行为 | 纯重构、测试或格式修改 |

## 3. 从信号到候选

- 读原文，套三条检验；可用时先 `codegraph explore` 对照代码，确认描述是否仍然成立。
- 一个候选 = 一个 PR 能做完的改动，写得出去向。「整体优化 docs」不是候选。
- **强**：证据清楚、处置明确、风险低，例如确认过期的段落、完全重复、与现行规则矛盾。**值得探索**：方向对，但要人判断取舍或涉及产品主张。**推测**：只有信号，还没读到足够证据。
- 涉及已认可原则或产品主张的候选标「需拍板」；不在报告里替人做产品决定。

## 4. 报告格式

- 写一份自包含 HTML 到目标仓之外（系统临时目录或会话 scratchpad，文件名 `knowledge-scan-<时间>.html`），能发布成 artifact 时就发布。从 [scan-report.html](../assets/scan-report.html) 起步，不引外部脚本。
- **头部**：仓名、日期、基于的 commit、范围、信号摘要（几个数字）、图例。
- **每张卡**：标题（动词开头，说清处置）、强度徽章、检验标签（删除 / 漂移 / 取舍 / 机械）、涉及文件、问题一句、处置一句、收益（不超过三个短语）、改前 → 改后的结构示意或一小段样例、需拍板或风险（有才写）。
- **末尾**：首选推荐（先做哪项、为什么）；看过但没列入的信号及原因；已否决、本轮不重提的项。
- 卡片文字要短。一张卡需要大段解释，说明候选还没想清楚。

## 5. 挑中之后

- 人挑一项 → 按 SKILL 的「整改一块」执行。设计分歧大时先用 grilling / grill-with-docs 质询，结论写回正本。
- 人否决 → 理由以后还用得上，就写进目标文档的取舍段或 ADR。
- 合入后可再跑一次脚本看信号是否消失；信号消失只说明线索没了，不说明改对了。

## 6. 定期运行

- BW：CI 的 `knowledge-scan` 任务在推送到 `bw-orca`、且改动了文档或本包时运行，也可以手动触发。它先跑脚本自测，再收信号：Checks 的 Summary 显示 `signals.md`，Artifacts 里有 `signals.json`，出现断链时任务变红。它只产信号，不出候选报告，不改文件，不开 Issue 或 PR。
- GitHub 的定时触发只在默认分支上执行，`bw-orca` 不是默认分支，所以这里不写 `schedule`，免得写了也不会跑。要按周期出候选报告，开一次模型会话（或建一个定时 Routine）说「用 project-knowledge 扫描知识库」，可以读最近一次 CI 的信号，也可以本地重跑。
- 其他项目：复制映射、按自己的目录改，接进已有的定时任务；同样只产信号。
