# 同步 Orca 到 BW

从当前 BW main 的独立工作树开始。读 [采用矩阵和同步取舍](../../../ref/upstream.md)、[仓库约定](../../../AGENTS.md)，确认用户要修的具体问题或要对齐的发布版。周期性查看新发布可以帮助选择目标，发现新版本本身不触发升级。

## 移植一个修复 PR

1. 定位上游 PR、实际合入提交及其相对父提交的补丁。用用户能观察到的失败和预期结果界定范围。对照 BW 当前调用路径，确认是否仍有该问题、上游修复是否已经等价存在。
2. 复用原补丁和它依赖的必要改动。若必须连带替换成片的共享协议、桌面入口或运行时，先说明原问题、被牵连的用户旅程和升版成本，请人决定是否切换为发布版对齐。
3. 从 BW 实际入口验证该问题及受影响的共享调用方。PR 关联上游 PR/SHA；只在采用矩阵记录相应修复或稳定差异，保留上次整版基线。

## 对齐一个发布版

1. 固定三点：本次 BW main SHA、上次采用的 Orca 发布版及 SHA、目标 Orca 发布版及 SHA。核实两个 Orca 提交来自上游。先前单独移植的修复按矩阵逐一对照目标版，避免重复实现。
2. 做两份比较：旧 Orca → 新 Orca，旧 Orca → 当前 BW。可用 `git diff --name-status -M <旧上游> <目标上游>` 和 `git diff --name-status -M <旧上游> <BW-main>` 从目录与重命名起步，再读实际补丁。以 BW 已采用的产品范围为准，沿共享依赖追到调用方。矩阵有漏项时，以主干源码和实际入口核实并补记。
3. 交集里逐项问：BW 原来为谁改了什么，新版哪个入口接走这段逻辑？优先保留 BW 既有实现，在新版接缝上适配；确认新版已覆盖同一用户行为时，删除已被替代的改造。未定制的原生代码直接复用。单独检查自动合并、被拆分的组件、BW 已移除的入口、默认值与旧档迁移，以及启动、定时和重连触发的后台行为。这些变化即使没有 Git 冲突也会影响用户。品牌文案重点核对新增键、迁移后的界面和原生菜单，按 upstream 对应行复验 Monica 自称与实际 Orca 服务名。
4. 先验 BW 存量，再验新版能力。按本轮实际影响选择旅程，例如首次安装与旧档覆盖升级分别验证；共享项目验证动作最终落在哪台主机；外发检查实际接收方。需要扩大采用范围、改写既有数据或改变既有用户能力时，给人看操作前后的差异再选。长 PR 期间 main 前进时，用新主干重新检查交集和已验证旅程。

## 交付与下次起点

验证按[开发规范](../../../docs/development.md)执行，沿用 BW 门禁和受影响的上游用例。在 PR 给出同步模式、源码锚点、沿用或适配的依据、实际验证 SHA 和仍需真机/双机确认的项目；新 head 单独核对 CI。与代码同一 PR 更新 [ref/upstream.md](../../../ref/upstream.md) 的对应行，区分已采用、主动排除和未经核实的范围。整版对齐后更新发布版锚点，保留有差异的例外。逐文件对照、过程和截图留在 PR。
