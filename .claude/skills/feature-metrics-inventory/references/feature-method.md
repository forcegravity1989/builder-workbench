# 特性梳理方法

> 30 秒导读：站 3 读本篇。特性用四层追问定义、7 要素成卡、名字过六问、孤儿归 Not Now、数量 3–5。冷启动项目用 Impact Mapping 提问；已有用户且特性膨胀的项目用「主干 + 圈选」收敛。模板在 [../assets/feature-card.md](../assets/feature-card.md)。

## 方法选择

| 项目状态 | 主方法 | 依据 |
|---|---|---|
| 冷启动（名片没想清、零数据） | Impact Mapping 四层提问 | 只需干系人已有知识即可画；官方引导手册明说指标可选、「别强求，数字可以后补」——与北极星允许缺席、Unknown 不装绿兼容 |
| 已有用户、特性膨胀 | brainstorm→圈选 + 孤儿判定收敛 | OST 有三条硬前置（价值主张假设、明确 outcome、3–4 次故事访谈在先）；内部项目用户即同事，访谈成本近零，需要时先补 3 次结构化访谈再收敛 |

## 四层追问（Impact Mapping 原书句式，1–3 人裁剪）

1. **目标（WHY）**：「我们为什么做这件事？」写问题不写方案、无设计约束；过反退化测试（见 [名片与北极星](card-and-northstar.md)）。
2. **谁的行为改变（WHO）**：「谁是 Job Executor——当下真正动手把活干完的人？谁能促成？谁能阻挠？」**禁写「用户」**，具体到个人/角色/下游团队（Patton 与 Adzic 同禁；具体度排序：具体个人 > 画像 > 角色 > 群体）。
3. **行为怎么变（HOW）**：写变化量不写行为（「卖票快 5 倍」而非「卖票」）；负面/阻碍性影响也要写（谁的工作会变多）。
4. **我们给什么（WHAT）**：特性候选。原书明言这是**最不重要的一层**：只列选项、非软件手段（流程/话术/文档）同样算。地图箴言：「永不实现整张图，找到达目标的最短路径。」

1–3 人可用 Adzic 2024 年认可的三层简化（2、3 层合一：目标 → 谁的行为怎么变 → 特性）。省掉：多干系人对齐工作坊、多张地图互比、信心投票——它们服务组织对齐，小团队无此问题。保留：反退化测试、变化量句式、孤儿判定。

## brainstorm → 圈选 → grill

1. brainstorm 5–20 个候选：模型从侦察证据 + 人的 info dump 起草；**每个候选必须挂到第 3 层的一个「行为改变」**，不出悬空特性；模型的候选标「建议」。
2. 人圈选，语法示例：「保留 1,4,7 / 删 3（与 1 重复）/ 合并 5,6」。
3. 每个保留候选过四层 grill（追问到具体）+ 特性卡 7 要素。
4. **确定性断言先行**（结构检查，先于任何语义判断——便宜的断言挡住了大部分「纸牌屋」）：数量 3–5；每卡 7 要素齐（第 6、7 项可标「待站 4」）；无孤儿；名字不含纯组件名词。

## 特性卡 7 要素

1. **名称**：对象 + 动作 + 结果，人话（判据见下）。
2. **谁**：具体角色，禁「用户/所有人」。
3. **场景触发**：何时、什么条件下。
4. **旅程线**：起点（第一次触碰）→ 3–7 个动词短语步骤 → 终点（拿到价值），一行箭头，**不展开分支流程图**——地图不是流程图，保持平面（Patton 五误用之「纠结分支」）。
5. **价值对照**：相对现状凑合法好/快/省在哪。
6. **引领指标**：待站 4。
7. **滞后指标**：待站 4。

1–5 对应 Patton 误用防御（不丢故事、不陷细节、只画「从第一次触碰到获得价值」的小地图）；6–7 对应「发布必须锚 outcome + 少量度量」。

## 命名

### 判据四条（一手出处）

- **描述性而非独特性**：GitLab 产品手册原文 "Give products and features descriptive, not distinctive, names"（反例是它自家早年黑话 CI/CD ATOM）。
- **用户原话，不用实现黑话**：HBR JTBD 原文——「公司爱上自己的行话，盯着提供的技术而不是交付的价值」（用户说 engage，公司偏叫 outbound messaging）。
- **动词短语优于抽象名词短语**：Productboard 官方命名专文（2026-06-05 更新）：动词短语更直接，抽象名词「留下过多解释空间」。
- **名字承载情境**：好名字应让人猜出「谁、在什么情境、做什么」。

### 六问检验（任一不过打回重命名）

1. **外行测试**：项目外的人只看名字能猜出「谁在什么场景想完成什么」吗？
2. **句式补全测试**：名字能补进 "When〈情境〉, I want to〈动机〉, so that〈结果〉"（job story，Klement 2013）吗？
3. **动宾测试**：有用户动作动词 + 用户对象吗？只有组件名词（引擎/服务/网关/链路/中台）= 实现视角。
4. **指标挂钩测试**：能由名字直接写出一条「minimize/maximize + 度量 + 对象 + 情境」的结果陈述（outcome statement，Ulwick）吗？写不出 = 不可测。
5. **旅程回推测试**：口述旅程线首尾各一步，名字与旅程脱节即改名。
6. **数量测试**：全项目 3–5 个，超了走合并规则。

### 正反例

| 正例 | 反例 | 病症 |
|---|---|---|
| 观察用户行为 | CI/CD ATOM | 独特性黑话（GitLab 手册自举反例） |
| 新客户签约时通知我 | Outbound messaging | 实现术语，用户不这么说 |
| 批准一次生产变更 | 「XX 服务接入」「XX 引擎重构」 | 无动宾、主语是组件不是人 |
| 导出本周报告 | 「数据链路治理专项」 | 像部门不像能力，不可测 |

### 改名纪律

名字 = 对需求的当前理解，随理解演进**改名是常态**（Productboard 官方例子：Export to CSV → Share data with colleagues → Weekly summary emails）。但 metrics.toml 靠 `feature` 字符串关联指标，所以改名是**显式迁移步骤**（见 [落盘与交接](asset-writing.md)），不顺手改。

## 孤儿判定（任一命中不上主干）

1. **链条断**：特性 → 行为改变 → 目标逐层连不上、跳层。
2. **行为不可验**：所挂「行为改变」不可外部观察、发布后短期不可测（outcome 而非 output）。
3. **多解测试不过**：所挂层容不下第二个不同特性 → 那层其实是 solution 不是 impact，追问 why 上移一层重挂。
4. **原书硬判据**：「不支持任何行为改变的 deliverable，即使技术上正确，也是失败——移除或改造。」
5. **处置**：归 **Not Now** 清单（特性卡文档尾部），记原因与重议触发条件；pet feature 同样处理，不静默删除。

## 合并/拆分规则

- **合并**：两个特性能用同一条 job story 讲完（同 executor、同 job）→ 合并。
- **拆分**：一个名字含两组动宾；或在 job map 八步（define/locate/prepare/confirm/execute/monitor/modify/conclude，Ulwick）上占据指标不同的步骤簇 → 拆分。

## 数量纪律与依据（如实标注）

3–5 的依据是**管理实践**而非心理学：OKR 传统（每周期 3–5 个目标，Google re:Work / Doerr）、Productboard 官方「每团队 ≤3 objectives、每 objective 1–3 KR」、路线图 3–5 theme 共识。**不是 Miller's law**——「7±2 当数量上限」是被 UX Myths 点名的神话，其正当用法是分组（chunking）不是限数。病症：>5 → 名片退化成特性清单、指标被稀释（feature-team 病）；<3 → 单特性承载多个 job、旅程讲不完、一对指标测不住——不足 3 如实记，不凑数。

## 一行主干与最小切片（轻量用法，不画全图）

项目级只留两样：

- **一行主干**：3–5 个特性按「向人解释项目」的叙述顺序排一行、各一句话——查缺口（主干某步没有特性承接）与重叠（两个特性讲同一件事）。
- **每特性一条最小切片**：让旅程线走通的最小端到端集合（Patton 2005 切片原文：横穿全流程、首尾打通——「别发布没刹车的车」；缩用户段或缩变化幅度都算有效切片）。

载体是对话不是图：盘点对话即 mapping，落盘只有特性卡文档。验收时逐步重讲旅程线（walk the map）：每步有数据走通、由人确认——对接项目自身验收流程与 BW 验收屏理念。

## AI 时代注意

- deliverable 变便宜后，唯一还能快速证伪的层是「行为改变」层——**grill 重心放在第 3 层**，不在第 4 层纠缠（Adzic 2026-06：「Air Sandwich 计划」——目标 + 特性清单、中间因果全是空气——大量暴死；这正是本 Skill 要防的病，也是 PM 素养成为通用识字能力的原因）。
- agent 起草纪律（Torres 2026 一手教训）：AI 草稿有「纸牌屋」风险（底层一个错传染全树）——**人按 目标 → 行为改变 → 特性 的顺序逐层修正，不整树一次点头**；便宜的确定性断言先于 LLM 判断；产出方式偏好「先拿完整草稿、再人工修正」，但草稿全程标「未生效」。
- agent 接管做卡与写码后，story mapping 的「拆任务」用途贬值，被强化的是「范围收敛」与「验收对照」——本 Skill 只用这两个用途。
