# 指标口径卡库

> 30 秒导读：站 4 的选配库，三组卡——A 默认极简集（工程交付类特性，git/issue 零埋点可现算）、B 决定→指标映射（按要做的决定选指标）、C 零埋点滞后代理（「有人真的用了」的证据形态）。先库内选配，库外新拟回 [指标纪律](metric-rules.md) 过判据。选中后口径由人确认再钉死。

**使用规则**：每行是候选不是承诺——过可行性门槛（数据源可脚本化读回）才能进配置；进配置沿[指标协议](../../../../standard/system-prompt/references/metrics.md)正本（collect = script + retro=true；窗口左闭右开、周一到周一切边；未结束窗口带 coverage；失败不写 0）；「同一变更」的配对规则（特性目录 / issue 号）先写进 def 再开始算。

## A 组：默认极简集与备选池

来源：Anthropic SDLC playbook 29 项官方指标按「仅 git/PR/CI/issue 原生数据可现算」筛出的 A 档子集。官方材料证据等级为厂商操作指南（推荐，非实证）。

**默认极简配（工程交付类特性）**：引领 = 需求返工次数；滞后 = 实施至合入耗时。两条都是纯原生时间戳/计数，特性生命周期早期即可观测，杀进程重开可完整重算。

| 指标 | 角色 | 口径 | 数据源与采集方式 | 服务的决定 | 已知失真 |
|---|---|---|---|---|---|
| 需求返工次数 | 引领（默认） | 同一变更首个 plan/实施约定提交后，spec/需求文档的提交次数 | `git log --format=%aI -- <spec路径>` 过滤晚于 plan 首提交者计数 | 需求是否稳定、是否值得进实施 | 合理澄清与返工无法自动区分；配对规则先钉死；小样本记「次数」不记「率」 |
| 实施至合入耗时 | 滞后（默认） | plan 批准（plan 合入提交或首个 approving review）→ PR merged 的日历时长 | `gh pr view --json mergedAt,reviews` + git 提交时间 | 交付节奏、瓶颈定位 | PR 拆分粒度影响大；跨周末失真；小样本列个体不聚合 |
| 首次 CI 成功率 | 引领（测试重特性） | 首个 head SHA 上 CI 全绿的 PR ÷ 同期 PR；rerun 不算首次 | `gh api repos/{o}/{r}/commits/{sha}/check-runs` | 自验回路是否生效（交人前自己查过） | agent 归属只能靠 commit trailer 近似（可被剥离/误挂），如实标注 |
| 首次评审时长 | 引领（协作重特性） | PR 创建 → 首个 review 提交的时长中位数 | `gh pr view --json reviews,createdAt` | 评审响应是否跟上产出速度 | bot review 是否计入先钉死 |
| 返工轮次 | 滞后 | 每 PR 的 request-changes 次数（或 push 段数，二选一钉死） | `gh pr view --json reviews,commits` | 评审与实施质量是否同步改善 | nit 评论计入会虚高；bot 与人评审分离 |
| 每 PR 审阅时间 | 滞后 | 首审 → 合入，或创建 → 首审（二选一钉死） | 同上 | 人审是否成为新瓶颈 | 日历时间 vs 工时窗口差异大 |
| 发现→合并修复率 | 滞后（维护回路类特性固定用它） | 被人确认关闭为完成的 issue 中，有关联合并修复 PR 的占比 | `gh issue list --json state,stateReason` × 关联 PR merged 交叉 | 回路是否真闭合（发现不是终点，修复合并才是） | issue-PR 关联需约定（closing keyword / 计划材料）；关闭原因由人定——天然契合「完成由人确认」 |

纪律：吞吐类（人均周合并量）不单独展示——playbook 原文要求与返工率成对读。

## B 组：决定→指标映射（按决定选指标，不是反过来）

DORA「从决定出发选度量」的操作化：先写下这个特性本期要支持的决定，再从对应行选配对。全部零埋点可算；没数据 = Unknown；不做跨项目排名（DORA 官方立场）。

| 决定 | 引领（口径） | 滞后（口径） | 失真与对策 |
|---|---|---|---|
| 继续投入该特性？ | 近 30 天与该特性关联（issue 标签/里程碑/分支名归组）且有实质推进的 PR 数 | 该特性 issue 由人确认关闭为「完成」的比例（原生关闭原因，区分 done/决定不做/重复） | 活跃 ≠ 价值（feature factory）；必须与「用户接触」行联读，单独看会奖励瞎忙 |
| 缩范围？ | 批量大小：PR 开→合时长中位数 + 变更行数分布；>1 周或巨型 diff 占比（DORA：超一周即太大） | 一周内可完成的 issue 占比趋势 | 拆票博弈（Goodhart）：行数骤降但 PR 数暴涨时人工抽查 |
| 改方向 / 停止？ | 近 90 天用户反馈记录数（反馈 issue、访谈纪要/changelog 提交数） | 反馈驱动重排次数：可追溯到「因反馈改优先级/改 spec」的 commit/PR/issue 条数（DORA user-centric 官方信号） | 内部工具用户=同事，反馈通道易退化为口头；连续两期 0 记录判 Unknown，不判「无问题」 |
| 先修可靠性？ | 变更失败率代理：revert/hotfix commit 占比 | 部署返工率代理：近 6 个月为修用户可见 bug 的非计划发布次数（DORA 2025 问卷原口径）；恢复时间 = revert → 修复合入时长 | 发布事件少、分母小波动大；按季度滚动窗口，单月不作数 |
| 先补用户接触？ | 反馈通道存在性与活性：反馈入口是否在仓、近 30 天有无新反馈 | 工程师直接观察用户使用的记录次数（纪要文件计数；DORA：不经转译） | 存在 ≠ 使用；只认有日期的记录文件 |
| 减少人工搬运？ | 变更前置时间：commit → 合入/部署时长中位数（起点口径钉死：首 commit vs 分支创建） | CI 失败重跑占比、需人工介入的发布步骤数 | 起点口径社区有争议——钉死写进 def 后不改 |
| 验收是否可信（AI 大量生成下的审阅负担）？ | 单 PR 变更行数 P90（DORA：机器生成代码每行审阅认知负荷更高，小批量是安全网） | 返工率：合入后 7 天内同模块 follow-up fix/revert 的 PR 占比 | 行数可用豁免清单修正（锁文件/生成物）；7 天窗口是约定值，人确认后固定 |
| AI 是否真的在帮（辅助判断）？ | commit 频率（DORA version-control 页：高频与个体效能正相关，AI 使用时尤甚） | 回滚使用频率（DORA：常用回滚放大 AI 的正向影响——回滚是能力不是事故） | 频率受 squash 策略扭曲，按仓统一口径；不得配「自报省时」类（METR 警示） |

## C 组：零埋点滞后代理卡（「有人真的用了」）

证据分级 S1–S4 与使用边界（人工证据只用于使用事实/受益事实，不用于自报提效）见 [指标纪律](metric-rules.md)。

| 代理 | 级 | 记录形式 | 读回方式 | 主要风险与对策 |
|---|---|---|---|---|
| 发布记录 + 版本号对账 | S1 | release notes 声明版本 ↔ 用户侧实际版本（issue 回填 / 访谈记录 / `--version` 输出） | `gh release list` × issue/访谈文件交叉 | 只证明「装上了」不证明「在用」；须与使用类代理配对 |
| 真实使用产物 | S1 | 用户用工具产出的报告/配置/数据文件，入库或归档 | git 历史 / 文件计数 | 一次性产物 ≠ 持续使用；配复购信号 |
| 服务端日志导出 | S1 | 访问/调用日志按月导出归档 | 文件条目现算 | 调用 ≠ 受益；留存与隐私策略先定；纯桌面单机无此源，如实 Unknown |
| issue 关闭记录读回 | S2 | 用户提 issue → 解决 → 关闭，关闭时填版本与证据链接 | `gh issue list --state closed` + label + 时间戳 | 自提自关 = 伪需求；关闭 ≠ 用户确认受益——用原生关闭原因 + 用户回帖佐证 |
| 结构化试用访谈 | S2 | 固定题单归档（受访人 + 日期 + 原话），落项目文档 | 仓内文件 | 只记事实题（用过吗/哪个任务/结果如何/产出在哪）；态度题（还会用吗）礼貌性偏置仅参考 |
| 复购 / 反馈整合信号 | S2 | 同一用户第二次提 issue；访谈确认仍在用；反馈引发重排的记录 | issue 按作者聚合、访谈文件 | 样本小不外推；「反馈驱动重排次数」本身即可计数（B 组第 3 行） |
| 值班表 + 完成勾记 | S3 | 「某日某人用 X 完成 Y」，签名 + 日期 | 文件 / issue checklist | 单方记录造假与漏记都可能；与第二来源对账后才升级 S2 |

## 可移植官方口径与命名对齐

- **engaged**：一个周期内至少两天真实使用（移植 GitHub 官方「28 天窗口 ≥2 个不同日活跃」）。
- **DORA 命名用新版**：failed deployment recovery time（原 MTTR，2023 重定义：只算变更引发的失败）、deployment rework rate（2024 新增）；不用退役名。
- **DORA 四指标 git 级口径三家差异大，选用必须钉死自家 def**：部署频率（release/tag 计数；桌面/CLI 工具注意「发布 ≠ 用户装上」；merged PR 当部署代理会虚高）；变更前置时间（首 commit vs merge 起点差数倍；squash/rebase 重写时间戳——FourKeys README 明文警告）；变更失败率（归因靠 issue 标注引入版本，没标注配不了对；小分母巨幅波动）；恢复时间（issue createdAt→closedAt；关闭 ≠ 恢复，先修后关）。
- **个体产量禁入**：diffs per engineer 禁用于个人层（DX 三前提：对抗性指标、不挂奖惩、防滥用沟通）；agent 产出计入团队吞吐，不单独立户；acceptance rate 与代码行数 DX 明确不纳入核心指标。
