# feature-metrics-inventory — 特性与核心指标梳理

> 30 秒导读：带 builder 按六站盘完一个项目——读回现状 → 名片 → 北极星（允许缺席）→ 特性 3–5 个 → 每特性 1 引领 + 1 滞后指标 → 落盘交接。每站模型只起草、人确认才落定；没数据记 Unknown；记录格式全沿项目既有正本与 BW 资产协议，不造平行账本。
>
> **状态：仓内 `0.1.0-pilot` 试用。** 任何使用者可采用；仓内采用不等于分发到 standard/。方法有效性按真实盘点任务证据检验，通过文件检查只说明可用，不说明成熟。

## 1. 适用范围与边界

- 适用于 BW 自身与被管项目的「项目定义 + 可跟踪指标」收敛，主要客群是 1–3 人内部项目（内部工具/平台型居多，常无营收指标、无埋点）。
- 本 Skill 只做盘点上半程：盘出名片、北极星、特性与指标候选口径，经人确认。指标配置写入、采集脚本、试采与合入沿 metrics-refresh SOP 与指标协议正本（见 [落盘与交接](references/asset-writing.md)），本 Skill 不另写一套。
- 分流：名片→北极星→特性→指标的全程盘点归本 Skill；已有特性文档的特性指标验收证据连接与知识库治理归 project-knowledge（其 feature-evidence 为口径契约正本，本 Skill 引用遵循、不另立契约）；版本计划 → week-planning；被管项目缺开发约定 → project-handbook。加载本 Skill 不新增 push、合入、关闭 Issue 或确认完成的授权；一切远端写入沿项目 PR 流，人审人合。
- 路径规则：本目录仅用于定位本 Skill 的 references 与模板；被盘项目以当前会话工作目录与 Git 信息为准，借树使用时分别记录方法路径与目标仓路径。

## 2. 追问协议（全站点总纲）

每一问三段式，缺一不可：

1. **目的先行**：说清这个信息用来干什么——落哪个字段、影响哪个决定、缺了会怎样。
2. **给建议**：给出候选或建议并附依据（口径卡库、项目侦察证据），标明「这是建议，不是决定」。
3. **结合实际 grill**：模糊答案追到具体——「用户」追问到是谁、「提效」追问到哪个数怎么动、「应该」追问证据；与侦察证据或前文矛盾当场指出。

补充规则：

- **表达型问题**（项目做什么、为谁、痛点）让人先说、倾倒完再按缺口整理——先给选项会锚定答案；**判定型问题**（北极星选哪个、口径怎么定）目的+建议先行再 grill——判定标准先亮出来反而省时间。
- 缺口阶段一次给编号问题 5–10 个、允许简答（"1: 是；3: 见 #12"）；发散阶段一次一问。
- 草稿一律标「草稿·未生效」；模型的推测显式标「这是猜测/这是我的建议」；人说的与模型代补的分开记录，模型的选择绝不记成人同意过。
- 人的确认只覆盖被明确展示的内容；「行/挺好」不构成对未展示部分的批准；没有答复不算认可，也不因旧模板一句「必须确认」反复索要相同批准。
- 每站一个确认门：展示本站产出清单 → 人逐项通过或改 → 才进下一站。受阻（人缺席、数据源不可达、归属分歧）就停下记录阻塞与解锁所需，不猜着往下盘。

## 3. 六站分流

| 站 | 目标 | 到达时读 | 确认门（退出条件） |
|---|---|---|---|
| 0 读回与分流 | 现算盘到哪一层 | 本文即可 | 向人复述进度，人选择继续或纠正 |
| 1 名片 | 一句话讲清为谁/什么问题/什么价值 | [名片与北极星](references/card-and-northstar.md) | 四空模板 + 反退化测试过检，人逐句确认 |
| 2 北极星 | ≤1 个量化北极星，或显式缺席 | 同上 | 二选一落定：确认 1 个，或记缺席+原因+重议触发 |
| 3 特性 | 3–5 个有旅程、人话命名的特性 | [特性方法](references/feature-method.md) | 确定性断言过（数量/孤儿/命名六问），逐卡确认 |
| 4 指标 | 每特性 1 引领 + 1 滞后，口径可脚本化 | [指标纪律](references/metric-rules.md) + [口径卡库](references/metric-catalog.md) | 可行性门槛 + 互牵制检查过，人确认口径与归属 |
| 5 落盘交接 | 写入项目资产，交接 metrics-refresh | [落盘与交接](references/asset-writing.md) | 落盘读回一致 + reader test 过，PR 人审人合 |

人要求跳站或自由梳理时给自由度，但落盘纪律与确认门不变；跳站导致落盘缺必要字段时说明后果，记「暂无 + 原因」。

## 4. 站 0：读回现状，现算盘点进度

不靠记忆、不建状态文件——进度是可从资产推导的值，杀会话重开可完整重算：

1. 读 `.bw/project.toml`（名片字段是否已填）、`.bw/metrics.toml`（有无 `[north_star]`；指标条数；`feature` 标签与 `leads` 是否齐）、特性卡文档（被管项目默认 `docs/features.md`，BW 自身为 `docs/05-features/`）。
2. 分流三档：**冷启动**（名片指标皆无）→ 从站 1 顺序走；**部分缺失** → 直接进缺失站，已有内容直接采用、不重问已确认的问题；**资料齐备** → 只做一致性体检（feature 标签与特性卡对得上、leads 唯一、有无触发退役判据的指标），报告结论。
3. 向人复述进度（例：「名片已确认；北极星缺席有记录；特性卡 3 张缺旅程线；2 条指标缺采集脚本」），从人认的地方继续。

## 5. 站 1–4 摘要（方法细节在 references，正文只留决策信息）

**站 1 名片**：先侦察项目（README、文档、近期 issue 与 commit），列「证据/缺口」两清单，只按缺口提问。产出四空一句话：「为〈具体谁〉，在〈场景触发〉时，能〈做到/得到什么〉，不再靠〈现状凑合法〉。」**凑合法填不出 = 问题不真实**，打回重问。落点与失败模式检查见 [名片与北极星](references/card-and-northstar.md)。

**站 2 北极星**：人先说候选；没想过则由模型补无营收项目候选清单（每个带坑与护栏配对）。过 6 判据（价值/唯一/不可直达/前瞻/可复算/可换代）。**缺席是合法产出**：记「本期缺席 + 原因 + 重议触发条件」；定性「目标方向」不冒充量化北极星，单特性牵引数不硬立为北极星。

**站 3 特性**：brainstorm 5–20 候选（每个必须挂到一个「行为改变」，不出悬空特性）→ 人圈选（保留/删/合并）→ 逐个过四层追问 → 特性卡 7 要素（名称/谁/场景/旅程线/价值对照/引领/滞后，后两项可待站 4）。**确定性断言先于语义判断**：数量 3–5（不足 3 如实记，不凑数）；无孤儿（挂不上目标归 Not Now 记原因）；每个名字过命名六问。旅程线一行箭头（起点 → 3–7 个动词短语 → 终点），不展开分支流程图。

**站 4 指标**：先从 [口径卡库](references/metric-catalog.md) 选配（A 默认极简集 / B 决定映射 / C 零埋点滞后代理），库外新拟过 [指标纪律](references/metric-rules.md) 全判据。**可行性硬门槛**：每条指标当场回答「数据源能否写成脚本从 git/issue/文件独立读回」并记录采集方式草案；不能 → 标「Unknown 候选」记入特性卡变更记录，不进配置。**互牵制检查**：刷高引领会被配对滞后暴露吗？不会就换。1+1 是下限纪律而非上限教条——多一条要多养一个采集脚本，超出须人说理由。

## 6. 站 5：落盘、读回、交接

1. 按 [落盘与交接](references/asset-writing.md) 的落点总表写入：名片 → `project.toml` 补空（PR 流）；北极星与指标 → `metrics.toml`（配置写入与合入交接 metrics-refresh）；特性卡 → 被管项目 `docs/features.md`（模板 [assets/feature-card.md](assets/feature-card.md)），BW 自身落 `docs/05-features/` 对应目录。
2. 写后读回逐字段展示核对；特性改名走显式迁移步骤（同步所有指标 `feature` 标签、文档标题与主干行、计划材料引用），不顺手改。
3. **reader test**：请一个无上下文的新会话只读落盘文件回答三问——这个项目为谁解决什么问题？某特性的旅程是什么？某指标的口径与数据源是什么？答不出打回对应站重做。
4. 如实区分「盘完」与「总览可见」：指标没有采集脚本时界面显示为问题而非读数；交接时说清走到哪一步。
5. 本次梳理结论与未决项记入项目 PR/Issue，不另建梳理台账。

## 7. 红线纪律（判据全文见 metric-rules.md）

- 没数据 = Unknown：不装绿、不写 0、不估数；采集不到就如实标。
- 口径、目标、特性归属与完成由人定，模型只起草；指标不做跨项目排名、不挂考核奖惩——度量成为目标就不再是好度量。
- 禁用：自报省时类指标；无法独立重算的平台归属数字；计数类（PR 数/提交数/任务关闭数/token）当北极星或价值证明。
- 小样本列个体 + 中位数，不造百分比；口径经人确认即钉死，改口径走重新确认。
- 每条指标要能回答「最近一次改变了哪个决定」；答不出进退役审议。剪枝是内建机制，不是失败。

## 8. 试用状态与来源

- 验收首先是「能在真实项目盘点中带回可确认的产出、且不产生编造」；触发与分流用代表性请求冒烟观察，静态检查不证明行为改善。
- 方法内容来源均一手，各 reference 附来源表：Impact Mapping / OST（Adzic、Torres）、Story Mapping / Working Backwards（Patton、Bryar & Carr）、JTBD（Christensen、Ulwick、Klement）、北极星（Ellis、Amplitude）、DORA / METR / DX / GitHub 度量、Anthropic AI-native SDLC playbook、GitLab / Productboard 命名实践与 Linear 状态实践。
- 工作流与写作结构参照（不是盘点判据，故不入 references 来源表）：Anthropic Agent Skills 官方规范与官方示例 skill（渐进披露、阶段确认门、批量编号提问、草稿标未生效），OpenAI Goals 与工作流指导（受阻停止条件、每站小确认门）。
- 证据边界：盘点方法自身的有效性未经受控研究验证，以真实试点证据为准；外部来源的证据等级在各来源表逐条标注（如 METR RCT 是度量纪律的受控研究证据，不是对本方法的检验）。不预填行为改善。
- 反馈回写：在原任务记录哪一站卡住、哪个提问没带回真实信息、哪条纪律被绕过；授权内修本 Skill 原件，方法缺陷不推广到 standard/ 或全仓。
