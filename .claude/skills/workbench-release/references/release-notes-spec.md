# 版本描述规范（Release body）

> **30 秒导读**：这是 Builder Workbench 每次 GitHub Release 的**版本描述正文**写法正本。发布 workflow `.github/workflows/bw-release.yml` 经 `notes` 输入读取按本规范写好的正文，**不用 `gh --generate-notes`**。骨架模板见 [`../assets/release-notes-template.md`](../assets/release-notes-template.md)。
>
> **维护约定**：给写 Workbench Release 正文的人/模型读。本篇只定正文的读者、语域、结构与诚实边界；发布操作契约在 [SKILL.md](../SKILL.md) 与 [spec.md](../../../../docs/05-features/workbench-release/spec.md)。正文结构或语域变化时改本篇并同步模板。本篇是 **Workbench 专用**规范。

## 读者与语域（最重要）

- **读者**：升级试用的同事、看版本进展的领导。**不是开发**。
- **语域**：**人话，约半页**。讲用户会用到的功能这版**有什么变化、能做什么**。往版好正文：`v0.6.0`（单节定稿后的第一版）；更早的 `v0.5.0-rc.20261007.2` / `.3` 是六节时期参考。参照 [03 §A 新闻稿](../../../../docs/01-principles/03-press-release-faq-flywheel.md)（人话、技术细节不进正文）。
- **禁止进正文**（这些是开发追溯信息，读者看不懂也不需要）：
  - 旅程编号（`PJ01` / `AJ01` / `MJ01` / `RJ01` / `CJ01`）；
  - 文件名与实现符号（`data.json` / `*.mjs` / `*.ts` / `workflow.stage` 等）；
  - 逐条 issue / PR 号（`#351`、`#332`…）；
  - 六环矩阵与 `●◐○待建—` 格值、「特性矩阵 / 验收点 E2E」这类内部词；
  - 任何内部协议、目录路径、代号黑话。
- **特性树与用户旅程是「取材与查漏的组织依据」，不是照抄进正文的内容**：用[特性树](../../../../docs/05-features/README.md)确保没漏掉本版动了的功能，用注册旅程确保写的是用户真能走的事——但正文一律用**用户认得出的功能名**（项目墙 / 计划 / 验收 / 总览 / CodeHub 接入 / 出包发布）和**用户做的事**来表达。

## 为什么只有一节

读者要的是「这版哪件完整的事变好了」。v0.6.0 实跑检验了旧六节骨架：只有【这版有什么变化】对读者有增量——下载安装步骤 Assets 区自带，升级流程在讲变化时自然带出，验证清单与来源行是开发追溯信息，读者不需要。`--generate-notes` 的 PR 罗列同样看不出这版变好了什么。本规范冻结**人话单节**：按用户认得出的功能讲变化，诚实标注没做到的。

## 硬规则

1. **人话**：面向升级试用者与领导，技术细节与内部编号不进正文。
2. **只有【这版有什么变化】一节**：节名固定 `### 这版有什么变化`，不改、不加节、不拆节；开头不加版本定位段（Release 标题已带 `Workbench <version>`）。
3. **不是罗列**：不粘 `--generate-notes` 的 PR 清单，不逐条列 issue 号，不堆文件名/编号；按**功能**组织。
4. **诚实边界**：没做到或部分做到的变化写清「没做到 + 原因 + 下一步」；缺数如实写、不填 0、不冒充绿（参照 [`evidence-and-follow-up.md`](../../../../standard/skills/version-acceptance/references/evidence-and-follow-up.md)、四铁律）。

## 「这版有什么变化」怎么写

- 功能名用**用户认得出的**：项目墙、计划屏、验收屏、总览、CodeHub 接入、出包发布；给维护者用的（如 BW 自身 CI）注明「给维护 BW 的人」。
- 每个功能：这版用户**能感知的变化**，一句话到几句话；可以是新能力，也可以是「此前会怎样 → 现在怎样」。
- **覆盖检查**：对照[特性树](../../../../docs/05-features/README.md)确认本版动了的功能都写到，但正文**不出现**「特性矩阵 / 六环 / 格值 / 目录名」。

## 反例（不要这样写）

- ❌ 粘 `--generate-notes` 的 `## What's Changed` + PR 标题列表。
- ❌ 写「`PJ01`：进入计划 → …」「feature 5 验收点 `待建(P-01–P12)`」「见 `data.json`」「合入 `#351`/`#332`」这类编号 / 文件 / 黑话。
- ❌ 把 issue 清单、目标清单、验收屏用例原样罗列成正文。
- ❌ 只报喜不写没做到的；缺数写 0 或留空冒充达成。
- ❌ 加回下载安装、升级流程、验证清单、来源等节——v0.6.0 已实证这些节对读者无增量。
