# 版本描述规范（Release body）

> **30 秒导读**：这是 Builder Workbench 每次 GitHub Release 的**版本描述正文**写法正本。发布脚本 `config/scripts/release-win-workbench.mjs` 用 `--notes-file` 读取按本规范写好的正文，**不用 `gh --generate-notes`**。骨架模板见 [`../assets/release-notes-template.md`](../assets/release-notes-template.md)。
>
> **维护约定**：给写 Workbench Release 正文的人/模型读。本篇只定正文的读者、语域、分节与诚实边界；发布操作契约在 [SKILL.md](../SKILL.md) 与 [spec.md](../../../../docs/05-features/workbench-release/spec.md)。分节名或语域变化时改本篇并同步模板。本篇是 **Workbench 专用**规范。

## 读者与语域（最重要）

- **读者**：升级试用的同事、看版本进展的领导。**不是开发**。
- **语域**：**人话，约一页**。讲用户会用到的功能这版**有什么变化、能做什么**。参照往版好正文（`v0.5.0-rc.20261007.2` / `.3`）与 [03 §A 新闻稿](../../../../docs/01-principles/03-press-release-faq-flywheel.md)（人话、技术细节不进正文）。
- **禁止进正文**（这些是开发追溯信息，读者看不懂也不需要）：
  - 旅程编号（`PJ01` / `AJ01` / `MJ01` / `RJ01` / `CJ01`）；
  - 文件名与实现符号（`data.json` / `*.mjs` / `*.ts` / `workflow.stage` 等）；
  - 逐条 issue / PR 号（`#351`、`#332`…）；
  - 六环矩阵与 `●◐○待建—` 格值、「特性矩阵 / 验收点 E2E」这类内部词；
  - 任何内部协议、目录路径、代号黑话。
- **特性树与用户旅程是「取材与查漏的组织依据」，不是照抄进正文的内容**：用[特性树](../../../../docs/05-features/README.md)（7 特性）确保没漏掉本版动了的功能，用注册旅程确保写的是用户真能走的事——但正文一律用**用户认得出的功能名**（项目墙 / 计划 / 验收 / 总览 / CodeHub 接入 / 出包发布）和**用户做的事**来表达。

## 为什么要有规范

`--generate-notes` 产出的是**已合 PR 标题的扁平罗列**（见 `v0.5.0-rc.20261011.4`），读者看不出这版哪件完整的事变好了。反过来，把开发追溯信息（旅程编号、文件名、issue 号、六环格值）堆进正文，读者同样看不懂。本规范冻结一个**人话骨架**：按用户认得出的功能讲变化、按用户能走的流程讲体验，诚实标已验/未验，追溯只留末尾一行。

## 硬规则

1. **人话**：面向升级试用者与领导，技术细节与内部编号不进正文。
2. **六节齐全、节名固定**：按下方骨架，不改节名、不缺节（防 `.2` / `.3` 式漂移）。无内容的节写「本版无」并说明，不删节。
3. **不是罗列**：不粘 `--generate-notes` 的 PR 清单，不逐条列 issue 号，不堆文件名/编号；按**功能**与**用户能做的事**组织。
4. **诚实边界**：已验与未验同段写清；缺数如实 **Unknown，不填 0、不冒充绿**；未做到的判据写「没做到 + 原因 + 下一步」（参照 [`evidence-and-follow-up.md`](../../../../standard/skills/version-acceptance/references/evidence-and-follow-up.md)、四铁律）。
5. **追溯只留末尾一行**：源码 commit（出包后再补资产名/大小/SHA-256）。**不在正文逐节引用内部文件**。

## 骨架（六节）

| # | 节名 | 写什么（人话） |
|---|---|---|
| 0 | 标题 + 定位 | `Workbench <version>`；开头一段：这版**最明显的变化**是什么、给谁用。 |
| 1 | 下载与安装 | 编号步骤：登录有私有仓权限的账号 → Assets 下载 `orca-windows-setup.exe` → 退旧版跑安装向导选目录 → 校验；**未签名提示**。未出包时如实写「待补」。 |
| 2 | 这版有什么变化 | 按**用户认得出的功能**分组，每个功能讲**用户可观察的变化**（现在能做什么 / 什么变好了 / 不再怎样）。 |
| 3 | 升级后你可以这样用 | 用户能走的流程，用「做的事」口吻描述；未验或走不通的标「未验」或不列。 |
| 4 | 验证到哪、还没验到哪 | 已验（自动检查、真机验证、实测读回）与**未验 / 没做到**同段写清，不淡化。 |
| 5 | 来源 | 一行：源码 commit；出包后补三资产名/大小与安装包 SHA-256（发布脚本 `prepare` 会算出）。 |

## 第 2 节「这版有什么变化」怎么写（功能层）

- 功能名用**用户认得出的**：项目墙、计划屏、验收屏、总览、CodeHub 接入、出包发布；给维护者用的（如 BW 自身 CI）注明「给维护 BW 的人」。
- 每个功能：这版用户**能感知的变化**，一句话到几句话；可以是新能力，也可以是「此前会怎样 → 现在怎样」。
- **覆盖检查**：对照[特性树](../../../../docs/05-features/README.md)确认本版动了的功能都写到，但正文**不出现**「特性矩阵 / 六环 / 格值 / 目录名」。

## 第 3 节「升级后你可以这样用」怎么写（流程层）

- 用「你可以这样用」的口吻描述**真实能走的流程**，例如：「打开项目墙，一屏看全组内项目，点进任一项目看详情」「走一遍计划：定版本 → 写目标 → 建任务 → 提 PR → 合入后重启，读回一致」。
- **对照注册旅程**（各特性 spec 的 PJ/AJ/MJ/RJ/CJ）确保写的是真实流程、没漏关键步，但正文**不出现旅程编号**。
- **模拟不算数**：本版没真壳走通的流程标「未验」或不列入「可以这样用」。

## 反例（不要这样写）

- ❌ 粘 `--generate-notes` 的 `## What's Changed` + PR 标题列表。
- ❌ 写「`PJ01`：进入计划 → …」「feature 5 验收点 `待建(P-01–P12)`」「见 `data.json`」「合入 `#351`/`#332`」这类编号 / 文件 / 黑话。
- ❌ 把 issue 清单、目标清单、验收屏用例原样罗列成正文。
- ❌ 只报喜不写未验；缺数写 0 或留空冒充达成。
