# 验收报告规范（版本收尾）

> **30 秒导读**：这是 Builder Workbench **版本收尾验收报告**的写法正本，取代已退役的 `version-report` 扁平模板报告。报告给**领导 / 验收人**看：用**人话**讲这版想做成什么、实际交付了什么、目标达成到什么程度、还没做到什么。骨架模板见 [`../assets/acceptance-report-template.html`](../assets/acceptance-report-template.html)。
>
> **维护约定**：给做版本收尾、出验收报告的人/模型读。本篇定报告的读者、语域、分节与诚实边界；发布操作契约在 [SKILL.md](../SKILL.md)，版本描述正文规范在 [release-notes-spec.md](release-notes-spec.md)。分节或语域变化时改本篇并同步模板。本篇是 **Workbench 专用**规范。

## 读者与语域（最重要）

- **读者**：看版本进展与是否验收通过的**领导 / 验收人**，不是开发。
- **语域**：**人话**。讲功能与目标达成，不讲实现。
- **禁止进正文**：旅程编号（`PJ01` / `AJ01` / `MJ01` / `RJ01` / `CJ01`）、文件名与实现符号（`data.json` / `*.mjs` / `workflow.stage` 等）、逐条 issue / PR 号、六环矩阵与 `●◐○待建—` 格值、内部黑话。这些留在开发侧（git、特性 STATUS、计划材料），不进给领导看的报告。
- **特性树与用户旅程是取材与查漏的组织依据**：用[特性树](../../../../docs/05-features/README.md)确保按功能讲全、用注册旅程确保「关键流程」写的是真事——但正文用**用户认得出的功能名**和**用户做的事**表达。

## 定位：派生叙事层，不是第二份事实正本

- **事实正本**在开发侧：版本计划材料、任务跟踪、特性现状清单、自动检查与出包读回。报告把这些事实**织成人话叙事**，**不新造事实、不改事实正本**。
- 退役的 `version-report`（确定性回填扁平模板）不再使用；其「事实只从来源读回、缺失留空、不编造读数/编号/哈希」的纪律**由本规范的诚实与溯源条款承接**。
- **完成永远由人确认**：报告不代替人工验收结论，不自动判目标达成，不打 tag、不建 Release（四铁律）。

## 硬规则

1. **人话**：面向领导，功能与达成讲清楚，实现细节与编号不进正文。
2. **诚实边界**：证据分层（Issue 关闭 = 任务事实，不等于目标验收）；缺数如实 **Unknown，不填 0**；未达项写清「原承诺哪里没达到、原因、下一步」，**不从原计划删除以制造达成**；**报告完整 ≠ 目标全达成**（参照 [`evidence-and-follow-up.md`](../../../../standard/skills/version-acceptance/references/evidence-and-follow-up.md)、[`version-records.md`](../../../../standard/system-prompt/references/version-records.md)）。
3. **按功能 / 目标组织，不裸罗列**：工作与任务归到**功能**和**目标**下用人话讲，不是把 issue 清单、目标清单、用例清单原样倒出来。
4. **达成口径统一**：目标用 `达成 / 大体达成 / 部分达成 / 未达成`；流程与用例未跑的标 `未验`；不用格值符号。
5. **文本周整**：分段换行，多条用序号或短横线，不把多件事挤成一段。

## 骨架（六节）

| # | 节名 | 写什么（人话） |
|---|---|---|
| 一 | 这版想做成什么 | 逐目标用**人话**转述目标与「要看到的结果」，不 paraphrase 成空承诺。 |
| 二 | 这版实际交付了什么 | 按**用户认得出的功能**分组，每个功能一句话讲变化 + 达成标签（已交付 / 有改进 / 有修复 / 已打通）。 |
| 三 | 目标达成到什么程度 | 逐目标：`达成 / 大体达成 / 部分达成 / 未达成` + **做到啥 · 没做到啥 · 下一步**。 |
| 四 | 关键流程能走到哪 | 按屏（项目墙 / 计划 / 验收 / 总览 / 出包发布）用「用户做的事」描述，截图槽位；本版没真壳走通的标 `未验`。 |
| 五 | 工作完成情况 | 「本版一共 N 项工作：完成 X、进行中 Y」，按**能力**人话列举完成项与进行中项，**不列 issue 号**。 |
| 六 | 还没做到 / 风险与下一步 | 逐条诚实缺口与风险，配下一步；不淡化、不冒充达成。 |

**页脚**（必填，人话）：一句话说明事实依据（版本计划与目标、任务跟踪读回、功能现状清单、变更记录、自动检查结果），并注明「未发布 / 未人工收尾的项如实标待补·未达·未验；是否验收通过由人确认，本报告不代替」。**不在正文逐条 cite 内部文件路径**。

## 产出与归档

- 输出 HTML 到 `.bw/planning/<版本>/acceptance-report.html`，截图放 `.bw/planning/<版本>/shots/`。
- 在 `.bw/planning/<版本>/acceptance.json` 的 `preparedArtifacts` 登记：`kind=showcase`、`location` 指向本报告、`candidateRef` 指向候选提交。（v0.5 曾把该数组留空、报告散在 `docs/` 未登记——本版起报告必须登记。）
- 随工作分支提 PR；**完成由人确认**，报告与 `acceptance.json` 的 `decision` 由人在验收屏落。

## 与发布的关系

验收报告是**版本收尾**产物（给领导 / 验收人），Release 版本描述（[release-notes-spec.md](release-notes-spec.md)）是**对外发布**产物（给升级试用者）；两者都用人话、都按功能与流程组织、都守同一套诚实边界，但详略不同：报告要讲清目标达成与缺口，版本描述只讲用户能感知的变化与能走的流程。发布脚本不生成任一正文，均按规范由人/模型写好后传入。
