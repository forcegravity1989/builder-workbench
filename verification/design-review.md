## 初审问题及依据（现已关闭）

### R1 · P2：通用 SYSTEM 仍强制每个会话都是一个 Issue

- 位置：`standard/system-prompt/SYSTEM.md.tmpl:1–5,19`；相关承诺：`docs/05-features/overview-metrics/spec.md:24`、`design.md:43`。
- 当前模板无条件声明“处理一个 Issue”，输出 `#{{number}}`，且要求提 PR 后给“此 Issue”换标签。但指标配置按新规格是独立 Orca 原生项目任务，不保证有远端 Issue；计划/验收的周期会话也不应凭模板虚构 Issue 身份。
- 后果：按计划接入通用 SYSTEM 后，会向没有 Issue 的任务注入错误身份和远端状态副作用，与独立配置任务的旅程不一致。
- 建议：把任务上下文改为通用项目/流程/原生任务身份，仅在宿主提供真实 Issue 引用时渲染 Issue 块并执行对应标签规则。R1 的提示构造契约及用例明确覆盖无 Issue 的配置任务和真实 Issue 两种情况，不增加第二套 SYSTEM。
- 收口时机：共享提示契约冻结前；不要求现在实现宿主渲染。

### R2 · P2：固定配置修订没有绑定真正执行的脚本修订

- 位置：`standard/system-prompt/references/metrics.md:22,28`；`docs/05-features/overview-metrics/design.md:27–29,43`。
- 文档要求目录读取固定配置提交，但采集只要求在“明确的项目源码工作区”运行相对脚本；没有约束执行文件/依赖必须与该配置修订一致，也没有要求它们进入指纹和缓存键。
- 后果：计划树、验收树或主工作区落后/有未提交脚本修改时，同一指标定义和窗口可能运行不同代码；只改脚本不改 TOML 时还可能沿用旧缓存或把不可比读数认成可比，破坏三屏同源。
- 建议：在唯一指标协议里明确已采用配置与采集脚本/相关依赖的修订身份、执行根核验及指纹；配置任务试采独立标草稿，缺正确脚本版本就不可采集，不能用常驻树旧脚本顶替。采集器读取的数据目标与脚本来源分别记录。将“同 TOML、脚本变化”及“常驻树落后”纳入 M06/M08 与 R1 冻结向量。
- 收口时机：MetricsPort/共享类型冻结前；实施由指标线完成。

### R3 · P2：同一加载链仍把指标配置导回旧计划 Issue/账本

- 位置：`standard/system-prompt/references/bw-assets.md:44,48,66–73`；`standard/README.md:27,39,51`；`standard/skills/asset-audit/SKILL.md:28`。
- bw-assets 新小节已指向独立“配置指标”任务，但紧接着的脚本段及后部表格仍要求“更新指标与版本计划 Issue”；README 的创建/采用入口相同。asset-audit 又断言 readings 位于指标记录工作树，与新协议不迁 ledger、无每日账本冲突。
- 后果：模型从新 Skill/旧盘点入口进入同一规范时得到两套互斥指引，容易重走用户刚否定的计划会话和账本流程。
- 建议：只清理受此次指标决定影响的这些入口，把配置统一指向独立指标任务；保留旧资产诊断身份，明确不恢复账本。旧 progress_updates 的当前 schema2 调用可保留其现状说明与原子切换债，不必扩大成全库重写。
- 收口时机：本轮文档定稿、实施窗口交接前。
