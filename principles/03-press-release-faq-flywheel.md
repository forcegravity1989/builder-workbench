## A. 新闻稿（Press Release）

> 模拟产品「可对内/对外讲清」当天的公告。人话，≤约一页。技术细节不进正文。

### 标题

**Builders' Workbench：一个人也能搭起来的 AI 时代项目管理台**

### 副标题

给端到端 own 项目的构建者——用内置方法论 + AI 队友真干活，带走一套可复制的打法，而不只是看板卡片。

### 总结

Builders' Workbench（仓库名 loop-buddy，产品里的 AI 程序自称 buddy）是本机桌面工作台。它把项目拆成清晰阶段，每阶段自带「为什么、节奏、做到什么算完」；把活派给 AI 队友在你的项目目录里真实改代码、跑检查；你只在评审与「完成」处拍板。健康与战绩来自真实记录，难造假。

### 痛点

传统项目管理默认一桌专职角色、厚 PRD、周会和口头绿灯。一个人做产品时：

- 看板只存卡片，不告诉你「现在该干什么、做到什么算完」；
- AI 能写代码，但要么看不见它在干嘛，要么自说自话「做完了」；
- 仪表盘数字可以手填，绿灯可以假装——三个月后想不起当初对标谁、何谓成功。

### 解决方案

工作台打开即带五阶段方法论（原型 → 构建 → 优化 → 运营推广 → 运维，运维洞察可回流原型）。你建项目时先回答对标谁与成功长什么样；日常在项目墙与看板上派活、一键开工；队友在真实目录里干活，干完停在「评审中」，**「完成」只能由你点**；做完的活可蒸馏成技能，下次同类活更像你的打法。没有数据时健康灯是灰的「未知」，绝不假装绿。

### 为何做（负责人视角）

我们相信：AI 时代瓶颈不在「能不能写代码」，而在「一个人有没有一套跟得上的管理体系」。工具应内置方法、诚实记账、把验收权留在人手上——而不是再做一个会发光的看板。

### 客户会怎么说（目标体验，非虚构背书）

「我早上扫一眼项目墙就知道哪盏灯灰、哪件活在评；agent 真改了我的仓，我点完成才算数；带险交棒也留痕。用久了，技能库里都是我自己项目里蒸馏出来的打法。」

### 如何获得

本机安装桌面应用（macOS / Windows）；数据在本地 SQLite。开发者克隆仓库按 README / DEVELOPMENT 编译运行。▶跑 需本机可用的 agent CLI（如 `claude`）。当前以内部构建者试用为主；对外分发与签名见产品欠账清单，不以本文冒充已上架商店。

### 五大拷问（产品级摘要）

| 拷问 | 答案 |
|---|---|
| 谁是客户？ | **单人构建者（Builder）**：端到端 own 一个项目的系统设计者；不是协作套件里的「全员」。 |
| 痛点/机会？ | 无 PM 编制时仍要把管理搭起来；AI 能干但缺可信验收与可复制方法。 |
| 核心利益？ | 走完带走**可复制的项目管理方法** + 真干活、人守门、难造假的健康。 |
| 如何知道？ | 命题源自产品自我表述与持续实践读回；工程侧用数据库读回与自动化叙事验收（见 plan/07）。直觉不单独充当依据。 |
| 体验什么样？ | 项目墙 → 建/接项目 → 看板派活 → ▶跑 → 人点完成 → 蒸馏技能；交棒可带险但留痕。 |

## B. 外部 FAQ（客户会问）

**这是什么？和 Jira / 看板工具有何不同？**  
工作台内置阶段方法论与 AI 派活/验收纪律，目标是「方法可复制」，不是通用协作看板或甘特图。

**谁适合用？**  
一个人（或强单人决策）端到端 own 项目的构建者。不是多人权限/群聊/收件箱型团队套件。

**AI 会替我点「完成」吗？**  
不会。「完成」永远由人点。定时能力可以自动**建**活，绝不自动**完成**活。

**健康灯绿灯是不是我自己填的？**  
健康信号只能从真实数据推导；没数据就是灰「未知」。手填数字会带标记，且不等于随意点绿。

**数据在哪？要上云吗？**  
默认本机数据库文件；界面数字应可用本地工具复核。AI 执行走你本机的 agent CLI。

**怎么开始？**  
安装/编译桌面壳 → 建项目并回答对标与成功标准 → 在看板上派活 ▶跑 → 评审后亲手完成。细节见产品指南（只写已实践的部分）。

**现在成熟度如何？**  
主环与铁律已落地并在迭代（含 V4 新壳试点）。真 agent 受本机网关/CLI 环境影响；部分创建「起草」曾为演示替身（有标注）。签名分发等见 `docs/LEFTOVERS.md`，不以新闻稿夸大。

**和 Claude Code / Cursor 什么关系？**  
它们是执行引擎之一；Workbench 管的是项目方法、派活、验收与诚实度量。可与多工具并存；团队规则同步可用 TeamAI 等分发层（见原则 01）。

## C. 内部 FAQ（硬核挑战）

**技术难点在哪？**  
本机桌面（Dioxus/WebView）+ 领域内核与执行器；内嵌终端/PTY 真跑 agent；健康与记账的派生纪律（难造假、不重复结算）；V3/V4 壳并存期的边界。细节与锚点见 plan/07 §5、DEVELOPMENT、设计正本。

**成本与代价？**  
工程：Rust 桌面与 agent 集成维护成本；用户：本机需可用 agent CLI 与相应配额。ROI 叙事：减少「假进度 / 假绿灯 / 重复踩坑」，换可复用技能与可读回的管理闭环——不以未验证的收入模型写进本文。

**主要风险？**  
agent 网关不稳定导致「真干活」体验抖动；用户误当成多人协作或云 SaaS；文档/演示与实况漂移。缓解：铁律进类型与门禁、读回纪律、指南只写已实践、欠账单一清单。

**成功怎么量？**  
产品侧：构建者能否不靠周会口头绿灯，用墙/灯/读回判断项目；方法是否沉淀为技能并再次被用。工程侧：关键路径数据库读回、验收流/测试锁命题子项（plan/07）。具体北极星数字属各**用户项目**，不是把 Workbench 自己的北极星写死成单一公开 KPI。

**为何不是云多人协作？**  
反命题明确：假设 1 个 Builder + Agent Loop；云协作与审批套件是另一类产品。扩大范围须先改新闻稿与命题，再开特性级 `changes/`。

## D. 飞轮（The Flywheel）

```text
         ┌─────────────────────────────────────────┐
         │                                         │
         ▼                                         │
   内置方法论让人「知道此刻该干什么」                    │
         │                                         │
         ▼                                         │
   派活给 AI 队友 → 真实改仓 / 跑检查                   │
         │                                         │
         ▼                                         │
   人点完成 → 诚实记账（战绩·吞吐·难造假健康）            │
         │                                         │
         ▼                                         │
   蒸馏成技能 → 下次同类活更贴这个构建者的打法             │
         │                                         │
         ▼                                         │
   方法可复制、项目持续闭环回流 ──→ 更愿意在台里真干活 ──┘
```

**飞轮检验（任何特性级变更都要答）：**  
它加强的是上面哪一截？会不会破坏「人点完成 / 灰灯未知 / 不重复记账 / 只建不完成」？  
说不清或削弱铁律 → intent 人闸应驳回或拆小。
