# Intent · 独立评审（reviewer agent）

> **30 秒导读**：这是什么——本次变更的**意图件**：给 Workbench 补上「评审」能力——一件活的 MR/PR 由一个**独立的评审会话**（不是写代码那个会话）出具评审意见，落在 MR 评论上，给人合入前当证据。给谁看——过意图 gate 的人、审这批改动的人。现在作数吗——**草稿**（2026-08-27，发起人 /goal 拍板要做，规格与实现随本分支一并进评审）。

**发起人**：Gravity（2026-08-27 `/goal` 拍板，原话见下）。**状态**：draft（做不做已由发起人定，长什么样待规格 gate）。

## 拍板原话（约束的来源）

> 「很明显我发现我们缺少一个 code-reviewer 的能力，包括 github 的 PR 审核 review，包括当前项目代码开发的 reviewer。你需要帮我们构建出 workbench 的 reviewer agent。」

## 痛点

一件活干完最远到「评审中」，合并永远是人点——但今天人在「合不合」这一下手上只有两样：diff 本身，和**写代码的 agent 自己的汇报**。产品主张（[`principles/03`](../../principles/03-press-release-faq-flywheel.md)）写得很硬：**写代码的队友不能给自己放行**——可现状是除了它的自述根本没有第二双眼睛。于是只剩两条歧路：

- **逐行读 diff**：人被按回全职评审岗，违背「少 gate、认过即自动跑」的主张；
- **盲合**：假完成直接进主干。

两条旁证说明缺口是真的：本仓自己的开发规矩（`AGENTS.md`）规定质量靠 `/code-review`——那是人在仓外终端手动跑的，Workbench 产品里没有这个能力，被管项目更没有；过程指标目录（[`changes/process-metrics`](../process-metrics/intent.md)）已经收了「评审等待 / 首过率 / 返工轮数」这些量评审的数——**量得到评审，产不出评审**。

## 解决方案（体验语言）

活在「评审中」、MR 开着时，一键**「请评审」**：Workbench 起一个**独立的评审会话**——不是写代码那个会话——它读这张活要干什么、读 MR 的真实 diff、对照项目自己的开发手册，把一份结构化评审意见**落在 MR 评论上**（结论 / 必须改 / 建议 / 大风险）。

- 你合入前扫一眼评审意见，就有了不由写码会话出具的第二意见；不满意就在会话里接着聊（「错误处理再看一遍」「把 #123 那个 PR 也看了」）。
- 评审绝不代替你：**不合并、不改活状态、不代点完成**；认、退回仍然是你的显式动作。评审没跑过就是没跑过，界面不装「已评审」。
- GitHub 和 codehub 都行；Workbench 自己的仓也是被管项目，同一能力审自己的 PR（自狗食）。

## 飞轮检验（对齐 03）

- **加强哪一截**：「认过即自动跑」里的自检段（自己先跑一遍检查，由独立目光完成），以及「灯不装绿、gate 少但硬 → 你更敢放手」——合入 gate 上证据变厚，人敢让队友自己跑更久。
- **不把人拽回搬运工 / 审批流**：不新增任何必过的人工关卡——「每 PR 必人审」正是 03 点名的失败形态。评审是一键产证据，人的 gate 数量不变，变的是点「合入」时手上有没有独立意见。
- **不破坏铁律**：完成永远人点（评审会话被禁止推状态与合并）；写码会话不能给自己放行（独立评审会话正是这条的产品化）；记录只追加（意见落 MR 评论，事后抹不掉）；没数据不装绿（没评审就如实没有）。

## 约束

- **评审产物唯一落点是 MR/PR 评论**——可核、只追加；不落本地库，不造第二份评审台账。
- **独立性**：评审会话与写码会话不是同一个会话；评审专用系统提示词，禁 merge / 禁改状态 / 禁改实现代码。
- 命中**大风险清单**（03 内部 FAQ 初值：破坏性迁移、权限/密钥面扩大、对外契约变更、不可逆发布、跨边界数据流出）的，必须在意见顶部显著标出。
- 没有 MR 的活没有可评之物，入口如实灰；评审失败如实报，不产「已评审」假象。

## 影响的用户与系统

单人 Builder（合入判断多一份独立证据）；`standard/skills/`（新增评审剧本）；`standard/system-prompt/`（评审阶段规范）；`crates/bw`（评审 run 命令与编排）；`app-shell`（入口按钮与会话呈现）。

## 五大拷问摘要

| 拷问 | 答案 |
|---|---|
| 谁是客户？ | Super builder：每天要合 agent 提的 MR 的那个人（第一个用户是发起人自己）。 |
| 痛点？ | 合入 gate 上没有独立证据，只能逐行读 diff 或盲合；写码会话自述「全绿」不算数。 |
| 核心利益？ | 每个 MR 一份不由写码会话出具的评审意见，扫一眼就敢点合或打回。 |
| 如何知道？ | 发起人 /goal 拍板原话；本仓自身实践（AGENTS.md 靠仓外 `/code-review` 顶着）；过程指标已量评审而无产评审能力。 |
| 体验什么样？ | 活到评审中 → 点「请评审」→ 独立会话读活/读 diff/对照手册 → 意见落 MR 评论 → 人扫结论点合或打回。原型见 `prototype.html`。 |

## 开放问题（留给评审拍）

1. 推到评审中时**自动触发**评审（评审不推状态，不违背「定时只建队列」，但会花预算）——MVP 先手动一键，自动留给用后再定。
2. 评审结论要不要**结构化读回界面**（活详情标「已评审 n 条意见」）——MVP 不解析评论，人去 MR 上看。
3. 「当前项目代码开发的 reviewer」是否含未开 MR 的裸 worktree 审（WIP 审）——MVP 评审对象=MR/PR；WIP 审可在评审会话里人工指路，不做专门入口。
