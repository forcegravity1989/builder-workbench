# Intent · `.bw/` 人机分目录 + 配置去冗留真

> **30 秒导读**:这是什么——本次变更的**意图件**:把 `.bw/`(Workbench 铺进被管项目的资产目录)按「给人读的 / 给机器解析的」分目录隔离,同时删掉审计实锤的假配置与死文件。给谁看——审这条产物链的人、以及接手实现批次的会话。现在作数吗——**方向已拍板,规格在 gate**(2026-08-29;经三轮对抗评审收敛,评审记录见 STATUS)。

**发起人**:Gravity(2026-08-29 会话定向,原话见引文)。**状态**:方向已接受,规格在 gate。**承载**:活 [#133](https://github.com/forcegravity1989/builder-workbench/issues/133)(2026-08-29 补建——「先建活」当时未成文,这个缺口本身催生了同批 02/AGENTS 制度补丁)。

## 问题

2026-08-29 对 `.bw/` 五份文件做了一次「谁读谁写」的全链审计,两个问题实锤:

1. **人机混放**。`.bw/` 顶层同时躺着给人读的章程(`PROJECT.md`)和给机器逐字段解析的配置(`project.toml` / `issue-policy.toml` / `managed.toml` / `standard.toml`),还有机器写的流水(`metrics/readings.jsonl`)。打开目录分不出「哪份该人编、哪份机器管」。(注:「注释过多」的直接原因是下条的假配置需要散文解释 + 各 `render()` 硬编码文案,由注释纪律与去冗解决;目录隔离解决的是「分不清谁写谁读」——两个问题相关但不是因果。)
2. **假配置**。一部分字段/文件解析了但**零消费**,注释还在为不存在的行为背书:
   - `issue-policy.toml` 的 `[[tool]]` 段四个字段(`kind`/`probe`/`version_cmd`/`capabilities`)无任何代码读——探活与工具→CLI 解析全部硬编码在适配模块(`tools.rs::probe` / `agent_for` / `probe_env`);
   - `[review]` 整段(`who_can_merge`/`require_pr_for`)除测试外零消费;
   - `ops1_trigger`/`ops2_trigger` 只用于配置屏显示文字,调度器不检查它们(只看 `ops2_schedule` 非空)——把 trigger 改成 `manual` 定时照样触发,是躺着的谎言;
   - `schema_version` 无人校验(metrics 文件有校验,这份没有);
   - `standard.toml`:**解析器**(`standard_file.rs`)全仓零调用,文件头却声称「Workbench 用它做对账」——实际对账正本是 `managed.toml` 指纹。评审轮二修正:文件本身有一个活消费者——运作活③「规范铺底」的完成判据查它在不在 git HEAD(`vm_derive.rs:49`),删除时判据要换锚点(见 spec);
   - `project.toml` 的 `standard_version` 镜像已失真(本仓自己就是 5.0 vs standard.toml 的 5.8),因为没有代码维护这个一致性。

## 定向原话(约束的来源)

1. 「给人看的,给 agent 看的,需要用目录隔离下。」
2. 「你说的很对,我们要去冗留真。」(指上述审计结论:删假配置、注释收敛到真行为)

## 五大拷问速答(02 §2)

1. **谁是客户**:发起人自己——单人 Builder,同时也是被管仓里干活的 agent 会话的运营者。自狗食语境:客户=发起人,成立且如实写明。
2. **痛点**:打开 `.bw/` 分不清谁写谁读;更疼的是改了配置以为会生效、实际是硬编码在演(假配置)。
3. **最核心利益**:`.bw/` 里**每个字段都有消费者、每行注释都描述真行为、目录名直接回答「谁写的」**——信任不用靠读源码建立。
4. **怎么知道想要**:不是直觉——发起人先自发观察到「注释过多」,审计给出零消费实证(grep 级证据链,见 STATUS 评审记录),发起人两句定向拍板。
5. **体验长什么样**:见 `prototype.html`——目录树前后对照、瘦身后文件全文、名片对账摘要、写权与出错分支。

## 对齐 03(飞轮检验,三问实答)

1. **加强哪截**:「可信所以敢放手」(目录即写权答案、对账只反映真人改动)与「架构盘账回流」(资产盘点能按目录问责:state/ 异常=机器问题,config/ 异常=人的决定)。
2. **会不会拽回搬运工/模板代填/开树变主业**:不会——不触待办、gate、开树任何主路径;人对 `.bw/` 的日常交互反而变少(读顶层 Markdown 即可,config/ 只在拍板时碰)。
3. **会不会破坏八条**:逐条过——不涉「做不做人认/聊过≠gate/开树≠gate/没认不动主仓/该升 gate 不许继续/写码队友不给自己放行/定时只建队列」;**强化**「没数据显示未知」(假配置删除、对账摘要如实分类)。无一条被削弱。

## 盼到的结果

- 打开任何被管项目的 `.bw/`,不看文档就能分辨:顶层 Markdown 全是给人(和 agent)通读的;`config/` 是人拍板的输入;`state/` 是机器写、人只审的。
- 配置文件里**每一个字段都有消费者**;每一行机器盖章的注释都描述真实行为,一节至多一行;对账的「人改过」只指真人改。
- `standard.toml` 这类「解析器无人调、文件头撒谎」的文件不存在;历史碑文死在 git 历史里,不占数据文件。

## 约束

- **不留兼容路径**(AGENTS.md 纪律):不写迁移代码、不双读旧位置。迁移敞口经核查:本机(macOS)注册表 `projects.toml` 尚不存在——零库时代未接管过项目,敞口=本仓,随实现批搬;**其余注册表位置待验**(data_dir 有多分支含 `BW_DB` 覆盖,pre-flight 逐条查,见 plan 第 0 步)。
