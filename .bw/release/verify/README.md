# 交付验证入口

> **30 秒导读**：开发会话在当前工作树运行一次命令，门禁和已注册 E2E 按确定顺序执行，结果保存成可离线查看的 HTML、机器结果和证据清单。GitHub CI 调用同一入口。这里不开发周一屏，不决定 PR 合入，不出包、不发布版本。

## 工作会话怎么用

在 Windows 仓根执行（Node 22+、Rust、Git Bash、WebView2；Playwright 按锁文件准备）：

```powershell
node .bw/release/verify/verify.mjs --profile pr
```

修改“添加项目”旅程时，在本机登录 GitHub 且 Orca 已打开的环境运行：

```powershell
node .bw/release/verify/verify.mjs --profile pr-onboarding
```

它包含普通 PR 的全部内容，并额外操作固定沙箱仓、读回 Orca 后清理本次远端对象。GitHub PR workflow 仍使用 `pr`，不向待评审代码提供跨仓写凭据。

`plan.json` 保存项目的命令、顺序和超时；`pr` 包括完整 Rust 门禁、构建真实壳和该 profile 已注册的 E2E（写远端的添加项目旅程只在 `pr-onboarding` 运行）。Linux 的 `--profile headless` 只验证内核、底座及结构门禁，不能代替桌面验证。macOS 与 CodeHub 调度尚未接入；`headless` 与 `pr` 不依赖 `gh`，`pr-onboarding` 需要本机已登录的 `gh`。

两个 profile 同时运行知识扫描器的确定性测试，核对路径边界、只读性、报告转义、比较口径及失败退出码。这里看护工具本身，不将历史知识库的结构提示设为 CI 门禁，也不证明 Skill 的模型行为有效。

一次执行一个 `.bw/release/out/verify/<时间-随机号>/`，不会覆盖历史结果。运行期间不要编辑源码。未提交改动可以本地验证，但报告明确标记；正式 PR 证据应在干净的最新提交上重跑。任何源码变化使本次结果失效。命令非零、超时、必跑用例失败/未跑、不完整结果或缺失证据均返回非零。修复后重新执行生成新记录。

| 交付件 | 用途 |
|---|---|
| `report.html` | 人读：结果、耗时、所验源码、逐项截图与留白；截图已内嵌，离线打开 |
| `result.json` | 程序读：执行编号、源码指纹、环境、每步退出码、用例与证据；状态不能从评论推断 |
| `manifest.json` | 本次所有交付文件的相对路径、大小和 SHA-256 |
| `review.md` | 原开发会话发布 PR 验证 Review 的基础摘要，仍须补本次验收判据及截图远端地址 |
| 每步目录 | 执行日志；E2E 的真壳截图、设置读回、被测二进制 SHA-256、清理回执 |

## 特性会话怎么增加专项用例

### 维护原则：少量用例，各自证明一条重要规则

- **按用户旅程分目录**：新的业务脚本放在 `e2e/journeys/<旅程>/`，同一旅程的小量用例放在一起，由 `e2e/suites/<旅程>.json` 注册。共享启动、运行时和依赖脚本留在 `e2e/`；不按页面或每个按钮建套件。当前 `core.mjs` 是桌面基础烟测，不代表“添加项目”业务已验过。
- **本轮业务范围只有添加项目和后续周一屏**。添加项目须读回真实测试仓的 Issue、PR、Git 工作树与项目名片；周一屏用例由原特性会话接入。旧功能暂不批量补 E2E。涉及安装器的变更才追加验包，不能把源码构建叫作验包。
- **每条用例写清六件事**：保护哪条用户规则、需要什么环境和数据、执行哪些真实动作、用什么独立读回断言、保存哪些证据、如何清理。可直接写在脚本开头；复杂旅程在同目录放短 README。用例必须有稳定 id；改规则时同步判据和证据，删行为时一起删失效用例。
- **固定用例由脚本运行**：不让模型逐次猜控件、临时生成点击脚本或从“成功”日志推断通过。模型只维护规则与脚本、判断本次改动是否需要专项、诊断失败。真实模型会话需要单独列明模型环境、预算和已验范围，不混进普通 UI 用例。
- **新增不是默认答案**：Bug 优先加强已有用例；新特性保留主旅程和最重要的失败边界即可，不以用例数、覆盖率或“每个函数一个测试”为目标。重复判据删较弱的一条，模拟测试不能充作真实远端或桌面证据。

Rust 测试在 `plan.json` 的 `test`（Windows）或 `test-headless`（Linux）步骤执行。它们是快速验证解析、状态约束、数据读写和隔离规则的资产；**TDD 是先写测试再实现的开发方法，不是这些测试的名称**。保留会拦住实际错误且难以用少量 E2E 定位的判据；纯粹重复实现、重复同一输入结论或保护已删除行为的测试应删除。禁止依赖固定临时目录、删除其他运行的数据、调用正式远端或模型；每次生成自己的目录并清理。此次删去“无数据不是绿”的重复断言，保留更强的“无数据必须是 Unknown”，并修正两处测试共用临时目录的问题；这不等于已完成其余存量用例的逐条价值审查。

### 远端测试环境边界

已准备的专用仓是 **`yuzhup/bw-e2e-sandbox`（私有，GitHub repository id `1374096542`）**；它只承载测试数据。测试代码仍随 BW 源码评审和版本化，测试仓不维护第二份测试实现。CodeHub 后续使用自己的测试仓和适配，不通过 GitHub 转接。

远端执行脚本须固定核验仓名和不可变 repository id，禁止模型临时换成 WB 主仓；每次运行先取得同一测试仓的独占资格，再造数。仅用 GitHub workflow concurrency 不能排斥本地同时运行。每次保存 run-id、基线、对象编号、分支 SHA 与清理回执；只清理能证明归属本次的对象，身份不明则失败并保留待处理。超时后不得无条件接管其他运行或批量删除仓库对象。

BW 注册表、运行日志和 WebView2 使用本次独立目录。沙箱 Git 仓保留在 `.bw/release/out/e2e-workspaces/`，Orca 可长期登记它；三条自动化必须读回为关闭状态，测试不启用、不立即执行，也不触发模型。测试结束只移除“项目约定”工作树、关闭本次 Issue/PR 并删除远端 `bw/project`，保留沙箱主仓、三条运作工作树和自动化，确保 Orca 中的路径长期有效。

**凭据边界**：测试仓已创建。云端访问另一私有仓需要专用凭据，不能沿用主仓的默认 `GITHUB_TOKEN`，也不能把本机完整登录凭据复制到 CI。跨仓写凭据不得暴露给普通 `pull_request` 执行；后续只接入合入后的 main、定时或人工触发的可信提交。云端普通 PR 报告只声明自己实际运行的范围，不把本机远端用例算作云端通过。

### 注册与输出协议

由开发该特性的会话在 `.bw/release/e2e/suites/` 增加一个 JSON 注册文件及确定性测试脚本；`profiles` 明确它在哪个入口运行。普通固定用例进入 `pr`，会写远端或有专项环境要求的旅程进入命名 profile；不得靠运行时静默跳过。参照 `core.json`，给出稳定 id、人能理解的标题、`layer`（desktop/browser/remote/local）、参数数组 `command`、超时和完整 `expectedCases`。代码变更不自动证明专项覆盖充分；PR 人审必须检查“需求判据 → 用例 → 证据”是否相符。

命令在仓根执行，`{node}`、`{root}`、`{shared}`、`{out}` 分别替换为 Node 绝对路径、当前工作树仓根、所有工作树共用的主检出仓根和本步骤全新输出目录，**不经过 shell 拼接**。脚本只在 `{out}` 写证据和如下 `result.json`：

```json
{"v":1,"cases":[{"id":"save-reopens","title":"保存后重新打开仍可读回","status":"passed","evidence":["screen.png","readback.json"]}]}
```

状态只能是 `passed` / `failed` / `not_run` / `not_applicable`。本批注册的是必跑用例，后三种都阻止 PR 验证通过；减少用例、悄悄跳过和仅打印成功都无效。证据必须是本步骤目录内非空的真实文件，不接受越界路径和文件链接。测试代码负责判据真实性，执行器检查结果完整性；不得把模拟接口的证据标作真实桌面或远端。

现有核心套件固定完成：真壳启动 → 修改工作区并读回文件 → 点击进入接入页 → 停止自己的壳、重启并核对界面及磁盘。Playwright 通过 CDP 连接真实 WebView2；每次隔离数据/工作区/WebView 目录，只清理本次拥有的进程和目录。本地默认额外创建独立 Windows 桌面，避免干扰使用者；独占的临时 CI 虚拟机显式设置 `BW_E2E_DESKTOP=current`，复用该机器已有桌面，绕开旧 WebView2 在自建桌面上的启动问题。两种环境跑同一套真实控件和读回判据，均不用系统键鼠。用条件读回等待，不用固定睡眠猜“写完了”。没有真实远端造数，不污染 WB 仓，也尚不能代表独立 E2E 仓的远端场景已建成。

## GitHub 上去哪看

PR 创建和更新时运行 Linux、Windows 两项检查；合入 main 后及手动触发也运行。分支 push 不另跑同一套 CI。PR **Checks → 对应任务 → Summary** 始终是结果摘要入口；**Actions run → Artifacts → verification-windows/linux** 下载完整证据包（14 天）。这是固定脚本写入，不依赖模型评论。

独立代码 Review 使用已有 Claude GitHub App，审当前 SHA，程序读回带该 SHA 标记的结论并保存回执；旧评论不代表新提交已审。检查通过只代表审查结论已交付，是否有待修问题仍须阅读结论。默认交付 PR，用户说「只本地」时才停在本地；合入、关闭 Issue 和正式发布仍须已有明确授权。开发会话开好 PR 后，用下面的 GitHub 适配命令发布独立验证 Review（需要已登录的 `gh`、Git push 权限）：

```powershell
node .bw/release/verify/publish-review.mjs --pr <PR号> --run <本次结果目录>
```

命令校验干净工作树、最新 PR 提交和所有证据哈希，将证据推到永不合入的 `shots/<PR分支>`，以不可变 SHA 内嵌真壳截图，发布后再读回 Review，保存 `github-review.json` 回执。同一执行重复调用不重复发 Review；上传期间 PR 改变则拒发过时结果。它不动特性工作树或暂存区，不合并 PR、不关闭 Issue。测试判据和代码审查不能由这一机械摘要代替。

没有替人设置仓库的 required checks。强制合并闸口尚需另设，检查存在本身不等于已启用分支保护。

## 与后续出包的边界

第一批只落源码的交付验证。既有 `pack/pack.cmd`、`e2e/e2e.cmd` 仍是旧安装包入口，不得把本批源码 E2E 报告说成验包通过。后续候选包将接入同一结果和证据格式，再处理安装隔离、包与源码绑定及归档；正式发布需要明确授权。本周周一屏的用例、资产分发修复、功能 PR 仍由原开发会话提交。

## 关键技术来源

- [GitHub 托管运行机](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)：每个 Windows job 使用 GitHub 提供的新虚拟机；它不是连接开发者的电脑。环境差异与首次构建耗时以实际报告为准。
- [微软 WebView2 分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)：检查 Evergreen 运行时注册信息；CI 缺失时安装官方运行时，本地验证只预检。实际 WebView2 版本随证据记录。
- [Playwright WebView2 官方说明](https://github.com/microsoft/playwright/blob/main/docs/src/webview2.md)：用 CDP 附着 WebView2，已有用例运行不调用模型；新增判据和失败诊断才需要模型参与。
